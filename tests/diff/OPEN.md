# Open findings

This list holds the bugs and questions that the testing harnesses found and that are not fixed yet. Each entry names the harness, the smallest reproducer, and what is known. A fixed bug leaves this list and gains a regression test in `tests/conformance`.

## A worker whose creation fails can leave `worker.receive` waiting

Harness: `tests/oom/run.lus` through the coverage build. With `LUS_FAIL_ALLOC=928`, `receive_in_the_main_chunk_runs_the_coroutines_test` of `tests/conformance/workercoro_test.lus` usually fails with "failed to create worker state", which is correct, but some runs wait forever in the `worker.receive` of the main chunk. The sweep saw the hang again when it ran the file alone, and one run of three hung afterwards on the same machine, then none of 21. The numbering of allocations follows the timing of the worker threads, so the failing allocation lands in different places, and the hanging runs have not yet printed their stack with `LUS_FAIL_ALLOC_TRACE`. The creator of a worker must see its failure and never wait for it, which part 11 of `spec/design/testing.md` checks at every step of message handling. `tests/faults/workers.lus` now fails every step of the message handling and every allocation of a worker thread, with a creator that waits plainly and one that waits through the scheduler, and none of those runs hung. Forty runs of `LUS_FAIL_ALLOC=928` on a ReleaseSafe build did not hang either, since the numbering of that build differs from the coverage build that found the hang.
