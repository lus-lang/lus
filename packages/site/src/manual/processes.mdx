A Lus program runs another program with `os.spawn`, which starts it without a shell and connects its standard streams to pipes, files, or the streams of the program. It handles the signals that ask it to stop with `os.signal`. Both are part of the `os` library and wait the way the network does: inside a [detached coroutine](/manual/concurrency#detached-coroutines) a wait suspends that coroutine while the others run.

## Running a program

[`os.spawn(argv, options)`](/manual/api#os.spawn) starts the program that `argv[1]` names with the arguments in the rest of `argv` and returns a _process object_ that represents it. No shell reads the arguments, so a file name with a space or a quote reaches the program as written. A name without a separator is looked up in the directories of `PATH`. A name with a separator is a path.

The options name what each standard stream of the child is connected to. `"inherit"`, the default, shares the stream of the program. `"pipe"` connects it to a pipe whose other end is the field of the same name on the process object. `"null"` discards the stream. An open file connects the stream to that file. `stderr = "stdout"` sends the errors of the child to the same place as its output. `env` replaces the environment of the child with a table of strings. `cwd` sets its working directory.

The following program sorts a list of names with the system command `sort` and reads the result from a pipe.

```lus
pledge("exec=sort")

local p <close> = os.spawn({ "sort" }, { stdin = "pipe", stdout = "pipe" })
p.stdin:write("Grace\nAda\nLinus\n")
p.stdin:close()

for name in p.stdout:lines() do
    print(name)
end
--> Ada
--> Grace
--> Linus
```

The pipe ends are files with the methods of files from `io.open`. The program writes to `p.stdin` and closes it to mark the end of the input. It reads `p.stdout` and `p.stderr` with `read` and `lines`. A `<close>` variable closes the pipes when its scope ends and then waits for the program to exit. When the program cannot be found or started, `os.spawn` returns `nil` and a message.

## Waiting for a program

`p.exit` is a coroutine that waits for the program to end. Resuming it returns `true` followed by the same three values as [`os.execute`](/manual/api#os.execute): `true` for a successful exit or `nil` otherwise, then `"exit"` or `"signal"`, then the exit status or the number of the signal that ended the program. Once it has returned them the coroutine is dead, like any coroutine that ended. `p:poll()` returns those three values without waiting, or nothing while the program runs, and `p:kill()` asks the program to stop.

The following program runs a compiler and reports how it ended.

```lus nocheck
pledge("exec=cc")

local p = os.spawn({"cc", "-o", "app", "app.c"}, {stderr = "pipe"})
local messages = p.stderr:read("a")
local _, ok, how, code = coroutine.resume(p.exit)
if not ok then
    print(`cc failed with $how $code`)
    print(messages)
end
```

## Many programs at once

Reading a pipe and waiting for an exit are suspension points, so several programs run at the same time when each one has a detached coroutine. The following program starts three downloads with `curl` and collects their results as they finish.

```lus nocheck
pledge("exec=curl")

local urls = {"https://lus.dev/a", "https://lus.dev/b", "https://lus.dev/c"}
local sizes = {}
local tasks = {}
for i, url in ipairs(urls) do
    tasks[i] = coroutine.detach(coroutine.create(function()
        local p = os.spawn({"curl", "-s", url}, {stdout = "pipe"})
        sizes[url] = #p.stdout:read("a")
    end))
end
for _, task in ipairs(tasks) do
    coroutine.resume(task)
end
```

A child that writes much to both of its pipes can fill one while the program reads the other, which leaves both waiting for each other. A detached coroutine for each pipe keeps both flowing.

## Permissions

`os.spawn` requires the [`exec` permission](/manual/permissions#program-values) for the program it starts. `pledge("exec")` allows every program. A value without a separator allows the programs whose name, as `argv[1]` writes it, matches the value, so `pledge("exec=git")` allows `git` and nothing else. A value with a separator allows the programs whose absolute path matches it, such as `pledge("exec=/usr/bin/*")`.

`os.execute` and `io.popen` run a command line in the system shell, which can start any program, so they require `exec` without a value.

## Signals

A _signal_ is a request from the system or another program for a program to stop. [`os.signal(names...)`](/manual/api#os.signal) starts handling the named signals and returns a coroutine. Each resume waits until one of the signals arrives and returns `true` and its name. `"interrupt"` is the signal that Ctrl-C sends, `"terminate"` is the signal that service managers send to stop a program, and `"hangup"` is the signal sent when a terminal closes, which exists on POSIX systems only. While a coroutine handles a signal, the signal no longer ends the program. Closing the coroutine gives the signal its usual effect again.

A program that has received an interrupt and receives a second one before it waits for interrupts again ends at once with exit status 130. Ctrl-C pressed twice therefore stops a program whose shutdown hangs.

## Stopping a server gracefully

Closing the coroutine that runs [`network.serve`](/manual/network#http-server) stops the server: it accepts no new connection, closes the connections that wait between requests, and lets each request in progress finish before its connection closes. Together with `os.signal`, this stops a server without cutting off a client in the middle of a response.

The following server stops on Ctrl-C or on SIGTERM.

```lus nocheck
pledge("network:server=127.0.0.1:8080")

local serving = coroutine.detach(coroutine.create(network.serve), "127.0.0.1", 8080, function(req)
    return 200, "hello"
end)
local stop = os.signal("interrupt", "terminate")
local _, name = coroutine.resume(stop)
print(`stopping on $name`)
coroutine.close(serving)
```

The `drain_timeout` option of `network.serve` limits how long the requests in progress may take, 10 seconds by default.

## Events as coroutines

`p.exit`, `os.signal`, [`fs.watch`](/manual/filesystem#watching-for-changes), and [`coroutine.sleep`](/manual/concurrency#sleeping) follow one rule. A function that waits for something to happen returns a coroutine whose resume waits for the next occurrence. A coroutine that hands over a series of events, such as signals or file changes, gives one per resume. One loop over `coroutine.resume` therefore serves for every kind of event, and a detached coroutine that resumes it waits without holding up the others. Closing a detached coroutine while it waits in such a resume closes the event coroutine too, so a cancelled task stops its sleep, its watch, or its wait for a signal.
