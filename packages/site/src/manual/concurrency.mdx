Lus runs several tasks at once with detached coroutines or with workers, which solve different problems.

A _detached coroutine_ is for waiting on many things at once. A program that serves a hundred network connections spends most of its time waiting for one of them to send something. With detached coroutines, the code for each connection is ordinary code that reads, computes, and writes, while Lus switches to another connection whenever one has to wait. All detached coroutines run in one thread and share the variables of the program.

A _worker_ is for computing on several processor cores at once. A worker runs a script on a thread of its own, in parallel with the program that created it. It has its own variables and exchanges messages with its creator, so two workers never change the same data.

## Choosing between coroutines and workers

The choice depends on what the task spends its time on. A task that mostly waits, for a socket or for another task, belongs in a detached coroutine. A task that mostly computes, such as parsing a large file or resizing images, belongs in a worker.

| | Detached coroutine | Worker |
| --- | --- | --- |
| Use it for | Many waits at once, such as network connections | Computation that should use several cores |
| How it runs | One at a time, in the thread of the program | In parallel, on a thread of its own |
| Data | Shares the variables of the program | Has its own variables and receives copies in messages |
| Started from | A function | A script file |
| A long computation inside it | Delays every other coroutine | Delays nothing else |
| Cost of each one | Small, so a program may run thousands | A thread and separate memory, so a program runs a few |

A program may use both, such as a server that runs its connections as detached coroutines and gives heavy computations to workers. Waiting for a worker suspends only the coroutine that waits, as [Detached coroutines in a worker](#detached-coroutines-in-a-worker) and [Suspension points](#suspension-points) describe.

## Detached coroutines

A coroutine is a function that can pause in the middle and continue later, as [Coroutines](/manual/guide#coroutines) in the guide describes. A program continues a plain coroutine itself with `coroutine.resume`, but Lus continues a detached coroutine. Whenever a detached coroutine waits for a socket or a worker, Lus pauses it, runs the other detached coroutines, and continues it when the socket or the worker is ready.

The following server answers each line a client sends with the same line in capitals. It detaches one coroutine that accepts connections and one more for each connection. While the first client stays silent, the second client still gets its answer at once. A server that handled one connection at a time would wait for the first client and never reach the second.

```lus
pledge("network")

local server = network.tcp.bind("127.0.0.1", 0)
local _, port = server:getsockname()

local function serve(conn)
    local closing <close> = conn

    while true do
        local line = conn:receive("*l", 1024)

        if #line == 0 then
            break
        end

        conn:send(`$(vector.tostring(line):upper())\n`)
    end
end

local acceptor = coroutine.detach(coroutine.create(function()
    while true do
        coroutine.detach(coroutine.create(serve), server:accept())
    end
end))

local slow <close> = network.tcp.connect("127.0.0.1", port)
local quick <close> = network.tcp.connect("127.0.0.1", port)

quick:send("second client\n")
print(vector.tostring(quick:receive("*l")))  --> SECOND CLIENT
slow:send("first client\n")
print(vector.tostring(slow:receive("*l")))  --> FIRST CLIENT

coroutine.close(acceptor)
server:close()
```

The function `serve` is plain sequential code with a loop, local variables, and a `<close>` variable that closes the connection on every path. The waiting happens inside `accept` and `receive`. [`network.serve`](/manual/network#http-server) is an HTTP server that works the same way.

Detached coroutines run one at a time. Each runs until it waits, yields, or ends, then the next one that is ready runs. Code between two waits is therefore never interrupted, so coroutines can share tables without locks.

### Detaching a coroutine

[`coroutine.detach(co, ...)`](/manual/api#coroutine.detach) detaches the suspended coroutine `co` and returns `co`. From then on, Lus resumes the coroutine. For a coroutine that has not started, the extra arguments are the arguments of its function. For a coroutine that already ran and yielded, they become the results of the `coroutine.yield` it is paused in. The following program detaches a coroutine with one argument and collects the result with `coroutine.resume`, which [Waiting for a detached coroutine](#waiting-for-a-detached-coroutine) describes.

```lus
local function greet(name)
    print(`hello, $name`)
    return #name
end

local co = coroutine.detach(coroutine.create(greet), "world")
print(coroutine.status(co))  --> suspended
print(coroutine.resume(co))
--> hello, world
--> true  5
```

`detach` returns at once, before the coroutine has run. Detached coroutines run while the rest of the program waits: during a socket operation, during `worker.receive`, during a `coroutine.resume` of a detached coroutine, and after the main chunk has ended. The _main chunk_ is the code of the script itself, outside every coroutine. While the main chunk computes without waiting, no detached coroutine runs.

Detaching raises an error when `co` is the main thread, or when it is running, normal, dead, or already detached. The message names the case, as in `"cannot detach the main thread"`, `"cannot detach a running coroutine"`, `"cannot detach a normal coroutine"`, `"cannot detach a dead coroutine"`, and `"cannot detach a detached coroutine"`.

### Yielding during long computations

Only one coroutine runs at a time, so a detached coroutine that computes for a long time delays all the others. A call to [`coroutine.yield`](/manual/api#coroutine.yield) inside such a computation lets the other detached coroutines run before Lus continues the coroutine. Detached coroutines run in the order in which they became ready. Inside a detached coroutine, `yield` discards its arguments and returns no values.

In the following program, two coroutines take turns because each one yields after every step.

```lus
local log = {}

local function step(name)
    for i = 1, 2 do
        log[#log + 1] = `$name$i`
        coroutine.yield()
    end
end

local a = coroutine.detach(coroutine.create(step), "a")
local b = coroutine.detach(coroutine.create(step), "b")
coroutine.resume(a)
coroutine.resume(b)
print(table.concat(log, " "))  --> a1 b1 a2 b2
```

A plain coroutine works as usual inside a detached one, so a generator made with [`coroutine.wrap`](/manual/api#coroutine.wrap), or run with `coroutine.resume`, yields its values to the code that resumed it. The following detached coroutine collects three numbers from a generator.

```lus
local task = coroutine.detach(coroutine.create(function()
    local numbers = coroutine.wrap(function()
        for i = 1, 3 do
            coroutine.yield(i)
        end
    end)

    local seen = {}

    for n in numbers do
        seen[#seen + 1] = n
    end

    return table.concat(seen, ",")
end))

print(coroutine.resume(task))  --> true  1,2,3
```

### Sleeping

[`coroutine.sleep(seconds)`](/manual/api#coroutine.sleep) returns a coroutine whose resume waits until `seconds` have passed, counted from that resume, then ends it. A wait of ten seconds is therefore `coroutine.resume(coroutine.sleep(10))`. The time is a number of seconds, fractions included, or a [duration](/manual/time). Inside a detached coroutine the wait suspends the coroutine, and the other coroutines run until the time is up.

The following program runs two tasks that sleep for different times, so the one with the shorter sleep finishes first.

```lus
local log = {}

local function task(name, seconds)
    coroutine.resume(coroutine.sleep(seconds))
    log[#log + 1] = name
end

local slow = coroutine.detach(coroutine.create(task), "slow", 0.2)
local fast = coroutine.detach(coroutine.create(task), "fast", 0.1)
coroutine.resume(slow)
coroutine.resume(fast)
print(table.concat(log, " "))  --> fast slow
```

Closing a detached coroutine while it sleeps ends the sleep too, as [Cancelling](#cancelling) describes.

### Waiting for a wake-up

A coroutine that must wait until another coroutine wakes it, such as a task waiting for a free connection in a pool, resumes a sleep of `math.huge`, which never runs out. The coroutine that wakes it closes the sleep, and the resume of the waiter then returns `false` and `"closed"`. A parked coroutine uses no processor time, and the program ends after its main chunk when every detached coroutine left is parked.

The following program parks a task until another task wakes it.

```lus
local wakeup = coroutine.sleep(math.huge)
local log = {}

local waiter = coroutine.detach(coroutine.create(function()
    local ok, why = coroutine.resume(wakeup)
    log[#log + 1] = `woken: $(tostring(ok)) $why`
end))

local waker = coroutine.detach(coroutine.create(function()
    coroutine.resume(coroutine.sleep(0.05))
    coroutine.close(wakeup)
end))

coroutine.resume(waiter)
print(log[1])  --> woken: false closed
```

A gate that wakes many waiters gives each one a sleep of its own, or keeps a list of sleeps and closes every one of them.

### Waiting for a detached coroutine

A program waits for a detached coroutine and gets its result with [`coroutine.resume(co)`](/manual/api#coroutine.resume). On a detached coroutine, `resume` waits until `co` has ended, then returns `true` and the results of the function, or `false` and the error object. Extra arguments passed to `resume` are ignored.

The following program waits for a coroutine that succeeds and for one that fails.

```lus
local ok = coroutine.detach(coroutine.create(function()
    return "a", "b"
end))

local bad = coroutine.detach(coroutine.create(function()
    error("failed", 0)
end))

print(coroutine.resume(ok))  --> true  a  b
print(coroutine.resume(bad))  --> false  failed
print(coroutine.resume(ok))  --> false  cannot resume dead coroutine
```

A detached coroutine that ends before anything resumes it keeps its results, or its error, until the first `resume` collects them. Every caller that was already waiting when the coroutine ended receives them as well. A later `resume` returns `false` and `"cannot resume dead coroutine"`.

A detached coroutine that resumes another detached coroutine is suspended while it waits, so `coroutine.status` reports `"suspended"` for it. The main chunk runs the detached coroutines of the program while it waits. When the coroutines that are left can only wait for each other, none of them can continue, so the waiting `resume` returns `false` and `"deadlock: every coroutine waits for another coroutine"`.

### Cancelling

[`coroutine.close(co)`](/manual/api#coroutine.close) cancels a detached coroutine that is no longer needed, such as the accept loop of a server that shuts down. Lus stops the coroutine, closes its pending `<close>` variables, and sets its status to `"dead"`, then `close` returns `true`. Callers that were waiting for the coroutine in `resume` receive `false` and `"cannot resume dead coroutine"`.

In the following program, one coroutine cancels another, whose `<close>` variable runs its cleanup.

```lus
local log = {}

local ticker = coroutine.detach(coroutine.create(function()
    local mark <close> = setmetatable({}, {
        __close = function()
            log[#log + 1] = "cleaned up"
        end,
    })

    while true do
        log[#log + 1] = "tick"
        coroutine.yield()
    end
end))

local stopper = coroutine.detach(coroutine.create(function()
    coroutine.yield()
    return coroutine.close(ticker)
end))

print(coroutine.resume(stopper))  --> true  true
print(log[#log], coroutine.status(ticker))  --> cleaned up  dead
```

Closing a detached coroutine that already failed returns `false` and its error object, which counts as collecting that error.

A detached coroutine that waits in a resume of a coroutine that the runtime made to hand over events, which are [`coroutine.sleep`](#sleeping), the `exit` coroutine of a process, [`os.signal`](/manual/api#os.signal), and [`fs.watch`](/manual/api#fs.watch), closes that coroutine as well when it is closed. A cancelled task therefore ends its sleep or stops its watch, and the program does not wait for a sleep that nothing needs.

### Suspension points

A _suspension point_ is an operation that waits for something outside the program and lets the other coroutines run during the wait. The following operations are suspension points.

- `network.tcp.connect`.
- `accept` on a TCP server.
- `send` and `receive` on a TCP socket.
- `receive` and `sendto` on a UDP socket.
- [`worker.receive`](/manual/api#worker.receive).
- [`worker.peek`](/manual/api#worker.peek) inside a worker.
- `read` and `write` on the pipes of a process that [`os.spawn`](/manual/processes) started.
- [`network.fetch`](/manual/api#network.fetch), while it connects, sends the request, and reads the response.
- Resuming a coroutine that waits for an event: the exit of a process (`p.exit`), a signal ([`os.signal`](/manual/api#os.signal)), a change to a file ([`fs.watch`](/manual/api#fs.watch)), or the end of a time ([`coroutine.sleep`](/manual/api#coroutine.sleep)).

Inside a detached coroutine, a suspension point suspends the coroutine until it can continue. During the wait, `coroutine.status` reports `"suspended"` for it. In the main chunk, or in a plain coroutine that no detached coroutine resumed, the same operation blocks its caller while the detached coroutines run. In the server example of [Detached coroutines](#detached-coroutines), the acceptor and the connections run during the `receive` calls of the main chunk.

Every other operation that takes time, such as reading and writing files, SQLite calls, `os.execute`, or `io.popen`, blocks the whole program, detached coroutines included.

A plain coroutine that reads a socket inside a detached coroutine suspends the detached coroutine with it. A line iterator written with `coroutine.wrap` therefore works unchanged on a connection that a detached coroutine serves. A suspension point reached inside a function that a library function calls back, such as the comparison function of `table.sort`, cannot suspend its coroutine, so it blocks the coroutine while the other coroutines run.

A timeout set with `settimeout` limits each wait and raises `"receive timeout"`, `"send timeout"`, `"sendto timeout"`, or `"accept timeout"` when it runs out. A zero timeout never waits. [Timeouts](/manual/network#timeouts) describes the timeouts of sockets.

### Errors that nothing collects

The error of a detached coroutine goes to the code that resumes or closes it. A detached coroutine that fails closes its pending `<close>` variables at once, with its error, so a socket that it holds is released before anything collects the error. When a detached coroutine fails and nothing collects its error, the program stops with that error and the traceback of the coroutine, so a failed task cannot go unnoticed. The program stops when `lus` has finished running the coroutines after the main chunk, or earlier, when the garbage collector finds that nothing refers to the failed coroutine any more. Results that nothing collects are dropped.

The following program detaches a coroutine that fails and never resumes it.

```lus nocheck
coroutine.detach(coroutine.create(function()
    coroutine.yield()
    error("lost")
end))
print("main done")
--> main done
--> lus: script.lus:3: lost
--> stack traceback: ...
```

### After the main chunk

When the main chunk returns, `lus` keeps running the detached coroutines until every one of them has ended. A program whose main chunk only starts coroutines, such as a server, therefore keeps running. The following coroutine prints three ticks after the main chunk has ended.

```lus
coroutine.detach(coroutine.create(function()
    for i = 1, 3 do
        print("tick", i)
        coroutine.yield()
    end
end))

print("the main chunk is done")
--> the main chunk is done
--> tick  1
--> tick  2
--> tick  3
```

A host program that [embeds Lus](/manual/embedding) calls `lus_runpending(L, wait)` for the same effect. With `wait` nonzero it runs the coroutines until none is left. With `wait` zero it runs the ones that are ready and returns, which is the mode for a host with an event loop of its own. `lus_pending` returns how many detached coroutines have not ended. `lus_close` closes the ones that remain.

## Workers

A worker runs a script in parallel with the program that created it, on another processor core when one is free. A program uses workers to finish a computation sooner by splitting it, or to keep answering requests while a long computation runs.

Each worker has its own global variables and its own memory. It shares no values with its creator, so the two exchange copies of values as messages. Because no worker can change a table that another one is reading, workers are safe to run in parallel.

The following program counts the prime numbers below two million. It splits the range into four parts and gives each part to a worker, so the four parts are counted at the same time.

```lus
pledge("fs", "load")

local script = os.tmpname()
io.open(script, "w"):write([[
    local first, last = ...
    local count = 0
    for n = first, last do
        local prime = n > 1
        for d = 2, math.floor(math.sqrt(n)) do
            if n % d == 0 then
                prime = false
                break
            end
        end
        if prime then
            count = count + 1
        end
    end
    worker.message(count)
]]):close()

local workers = {}

for i = 0, 3 do
    workers[#workers + 1] = worker.create(script, i * 500000 + 1, (i + 1) * 500000)
end

local total = 0

for _, handle in ipairs(workers) do
    total = total + worker.receive(handle)
end

print(total)  --> 148933
fs.remove(script)
```

Workers run in the process of their creator. [Permissions of a worker](#permissions-of-a-worker) describes what a worker may do. The WebAssembly build of Lus leaves the worker library out.

### Creating a worker

[`worker.create(path, ...)`](/manual/api#worker.create) starts a worker that runs the script at `path` and returns a handle to it. The extra arguments are copied to the worker and become the values of `...` in the script. A script that cannot be read makes the worker fail, so the first `worker.receive` raises the error `"cannot open worker script 'PATH': REASON"`.

[`worker.status(handle)`](/manual/api#worker.status) returns `"running"` while the worker runs and `"dead"` after it has finished or failed.

When the program ends, `lus` stops every worker that waits for a message. A worker that is still computing runs until its script ends or until it waits for a message. A program collects the results it needs with `worker.receive` before it ends.

### Messages

A worker and its creator exchange messages. Each direction has its own queue.

- Inside a worker, [`worker.message(value)`](/manual/api#worker.message) sends a copy of `value` to the creator. The creator calls `worker.receive(handle)`, which waits for the next message of that worker and returns it.
- The creator calls [`worker.send(handle, value)`](/manual/api#worker.send) to send a copy of `value` to the worker. The worker calls `worker.peek()`, which waits for the next message and returns it.

Each queue keeps its messages in the order they were sent. `worker.receive` returns `nil` for a worker that has finished and has no message left.

The following program starts a worker that doubles every number it is sent until it is told to stop. A worker of this kind stays ready for more work, which saves the cost of starting one for each job.

```lus
pledge("fs", "load")

local script = os.tmpname()
io.open(script, "w"):write([[
    while true do
        local job = worker.peek()
        if job == "stop" then
            break
        end
        worker.message(job * 2)
    end
]]):close()

local handle = worker.create(script)
worker.send(handle, 21)
print(worker.receive(handle))  --> 42
worker.send(handle, 4)
worker.send(handle, 5)
print(worker.receive(handle), worker.receive(handle))  --> 8  10
worker.send(handle, "stop")
print(worker.receive(handle))  --> nil
print(worker.status(handle))  --> dead
fs.remove(script)
```

`worker.receive` accepts several handles, which lets a program take results in the order in which the workers produce them. It waits until at least one of the workers has a message or has ended, then returns one value per handle, in the order of the arguments. The value for a handle without a ready message is `nil`.

The following program starts two workers and collects their messages in whichever order they arrive.

```lus
pledge("fs", "load")

local script = os.tmpname()
io.open(script, "w"):write("worker.message(...)"):close()

local first = worker.create(script, "first")
local second = worker.create(script, "second")

local results = {}

while #results < 2 do
    local a, b = worker.receive(first, second)

    if a then
        results[#results + 1] = a
    end

    if b then
        results[#results + 1] = b
    end
end

table.sort(results)
print(table.concat(results, " "))  --> first second
fs.remove(script)
```

### Values in messages

`nil`, booleans, numbers of every kind, strings, tables, and vectors may be passed to `worker.create` and sent as messages. Every other type, such as functions, coroutines, userdata, enum values, and queries, raises an error such as `"cannot serialize function to worker"`.

A table arrives as a copy, so the receiver never changes the table of the sender. The copy keeps the structure of the original, so two references to one table arrive as two references to one copy. The copy has no metatable. A table that contains itself arrives as a copy that contains itself. A table nested deeper than 100 levels raises `"table nesting too deep for serialization"`.

The following worker checks that the table it receives kept both kinds of reference.

```lus
pledge("fs", "load")

local script = os.tmpname()
io.open(script, "w"):write([[
    local t = ...
    worker.message(t.a == t.b and t.self == t)
]]):close()

local shared = {}
local value = { a = shared, b = shared }
value.self = value
print(worker.receive(worker.create(script, value)))  --> true
fs.remove(script)
```

A vector is moved, which makes sending a large buffer of bytes cheap. The receiver gets the bytes, which leaves the vector of the sender empty. Sending that vector again raises `"cannot send a vector that was transferred to another worker"`, as does `vector.tostring` on it. A sender that still needs the bytes sends [`vector.clone`](/manual/api#vector.clone) of the vector.

In the following program, the vector of the sender is empty after the worker has received its three bytes.

```lus
pledge("fs", "load")

local script = os.tmpname()
io.open(script, "w"):write("worker.message(#(...))"):close()

local bytes = vector.fromstring("abc")
local handle = worker.create(script, bytes)
print(worker.receive(handle))  --> 3
print(#bytes)  --> 0
fs.remove(script)
```

### Errors in a worker

An error that ends the script of a worker is raised in the creator by `worker.receive`, then again by every later `worker.receive` on that handle. The error object arrives as a string, which a `catch` around the call captures as usual. The following program catches the error of a worker that fails.

```lus
pledge("fs", "load")

local script = os.tmpname()
io.open(script, "w"):write('error("worker broke", 0)'):close()

local handle = worker.create(script)
local ok, err = catch worker.receive(handle)
print(ok, err)  --> false  worker broke
print(worker.status(handle))  --> dead
fs.remove(script)
```

[`os.exit`](/manual/api#os.exit) ends the process when the main program calls it. Inside a worker it raises the error `"os.exit is unavailable in a worker"`, which the worker may catch. When the worker does not catch it, `worker.receive` raises the error in the creator, like any other error of the worker.

### Permissions of a worker

Creating a worker requires the `load` permission and `fs:read` for its script. The worker starts with a sealed copy of the permissions of its creator, so it may use everything its creator held when it created the worker. Because the copy is sealed, every `pledge` inside the worker returns `false`. [Permissions in workers](/manual/permissions#permissions-in-workers) describes the rule.

### Detached coroutines in a worker

Because `worker.receive` and `worker.peek` are suspension points, a detached coroutine may wait for a worker. A worker may also run detached coroutines of its own.

In the creator, a detached coroutine that waits for a worker in `worker.receive` is suspended, so the other coroutines run until the worker answers. A server uses this to give a long computation to a worker while it keeps serving its other connections. In the following program, the coroutine `ticking` runs while `waiting` waits for the worker.

```lus
pledge("fs", "load")

local script = os.tmpname()
io.open(script, "w"):write([[
    local n = ...
    local total = 0
    for i = 1, n do
        total = total + i % 7
    end
    worker.message(total)
]]):close()

local log = {}

local waiting = coroutine.detach(coroutine.create(function()
    local total = worker.receive(worker.create(script, 20000000))
    log[#log + 1] = "worker done"
    return total
end))

local ticking = coroutine.detach(coroutine.create(function()
    for i = 1, 3 do
        log[#log + 1] = `tick $i`
        coroutine.yield()
    end
end))

print(coroutine.resume(waiting))  --> true  60000003
print(table.concat(log, ", "))  --> tick 1, tick 2, tick 3, worker done
fs.remove(script)
```

A worker runs its script, then the coroutines that the script detached, as `lus` does for a program. The worker ends when the last of them has ended. When a detached coroutine in a worker fails and nothing in the worker collects its error, that error becomes the error of the worker, which `worker.receive` then raises in the creator.
