Editor support shows mistakes while you type, completes names, and shows the documentation of a function when the pointer rests on it. Lus provides an extension for VSCode-based editors. Every other editor, and every coding agent with a Language Server Protocol client, starts the language server that is built into `lus`.

## VSCode-based editors

The [Lus extension](https://open-vsx.org/extension/lus/lus) provides syntax highlighting, diagnostics, code completion, hover information, go-to-definition, references, and formatting. The extension contains the language server and the Lus runtime as a WebAssembly module, so these features work without a local installation of `lus`, which only [debugging](#debugging) needs. The extension reads every `.lus` and `.lua` file of the workspace, so it finds definitions and references in other files.

The extension runs in the Node-based extension host of VS Code, so it also works in remote workspaces.

### VSCodium, Cursor, and Antigravity

These editors use the Open VSX registry, which hosts the extension. Search for `Lus` in the extensions panel and install it.

### Visual Studio Code

Visual Studio Code uses the Visual Studio Marketplace, which does not host the Lus extension. Install the extension from its file:

1. Download the latest `.vsix` file from the [Open VSX page](https://open-vsx.org/extension/lus/lus).
2. Open VSCode, go to the Extensions panel, click the `...` menu, and select **Install from VSIX...**.
3. Select the downloaded `.vsix` file.

The `code` command also installs the file. Replace `version` with the version of the downloaded extension:

```bash
code --install-extension lus-version.vsix
```

### Package completion

Inside the string of a `require`, the extension completes the URLs of packages on `atmosp.here` when the `atmos` command is installed. The setting `lus.atmosphere.servers` adds the base URLs of other package servers, such as `https://pkgs.example.com`, whose packages the completion offers too.

### Testing

The Testing view lists every `*_test.lus` file of the workspace with its tests and benchmarks, with a run button beside each definition in the editor. A run starts `lus test`, so it needs the `lus` command, which the setting `lus.executablePath` names. A failed test shows its message at the line of the failed assertion. **Run with Coverage** marks the lines of the code under test that ran.

### Debugging

The extension registers the `lus` debugger, so **Run and Debug** works on any `.lus` file. The debugger runs the program with a local installation of `lus`, which it starts as `lus debug`. The `lus.executablePath` setting names the command to start and defaults to `lus`, which must then be in a directory of the `PATH`. A launch configuration in `.vscode/launch.json` sets the program, its arguments, its working directory, and the permissions it receives:

```json
{
  "type": "lus",
  "request": "launch",
  "name": "Debug Lus File",
  "program": "${file}",
  "pledges": ["fs:read"]
}
```

Breakpoints can have conditions, hit counts, and log messages. The debugger stops on uncaught errors by default. [Developer tools](/manual/tools#debugger) describes every feature of the debugger. Any other editor with a Debug Adapter Protocol client can run `lus debug` in the same way.

## Other editors

The language server is built into `lus`, so every other editor runs it with a local installation of `lus`. The command `lus lsp` starts the server, which reads Language Server Protocol messages from standard input and writes its replies to standard output. It serves files with the `.lus` extension under the language id `lus`. The server comes with the runtime, so its version always matches the installed `lus`, which `lus lsp --version` prints.

Most editors do not recognize `.lus` files, so the instructions for each editor also give those files a file type. The syntax of Lus grew from that of Lua, so each configuration highlights Lus with the Lua support of the editor, which colors most Lus code correctly. An editor that reads TextMate grammars can use the Lus grammar, [`packages/textmate/lus.tmLanguage.json`](https://github.com/lus-lang/lus/blob/main/packages/textmate/lus.tmLanguage.json) in the repository, whose scope is `source.lus`.

### Neovim

Neovim 0.11 and later start the server with the built-in client. Add the following to the Neovim configuration, which registers the `lus` file type for `.lus` files, highlights them with the Lua parser, and enables the server for that file type:

```lua
vim.filetype.add({ extension = { lus = "lus" } })
vim.treesitter.language.register("lua", "lus")

vim.lsp.config["lus"] = {
    cmd = { "lus", "lsp" },
    filetypes = { "lus" },
    root_markers = { ".git" },
}
vim.lsp.enable("lus")
```

### Helix

Add the following to `languages.toml`. The `grammar` line highlights Lus with the Lua grammar of Helix:

```toml
[[language]]
name = "lus"
scope = "source.lus"
file-types = ["lus"]
grammar = "lua"
language-servers = ["lus"]

[language-server.lus]
command = "lus"
args = ["lsp"]
```

### Zed

Zed adds a language and its server only through an extension. To highlight `.lus` files with the Lua support of Zed, add the following to its `settings.json`:

```json
{
  "file_types": {
    "Lua": ["lus"]
  }
}
```

### Sublime Text

To highlight `.lus` files with the Lua syntax of Sublime Text, open a `.lus` file and choose **View > Syntax > Open all with current extension as... > Lua**. Then install [LSP for Sublime Text](https://github.com/sublimelsp/LSP) and add the following to its settings. The selector matches Lua files, so the server also starts for `.lua` files and reads them as Lus:

```json
{
  "clients": {
    "lus": {
      "enabled": true,
      "command": ["lus", "lsp"],
      "selector": "source.lua"
    }
  }
}
```

### Emacs

Install [lsp-mode](https://github.com/emacs-lsp/lsp-mode) and [lua-mode](https://github.com/immerrr/lua-mode), then add the following to the Emacs configuration. It defines `lus-mode` for `.lus` files as a mode derived from `lua-mode` and registers the server for `lus-mode`:

```elisp
(define-derived-mode lus-mode lua-mode "Lus")
(add-to-list 'auto-mode-alist '("\\.lus\\'" . lus-mode))

(with-eval-after-load 'lsp-mode
  (add-to-list 'lsp-language-id-configuration '(lus-mode . "lus"))
  (lsp-register-client
    (make-lsp-client
      :new-connection (lsp-stdio-connection '("lus" "lsp"))
      :activation-fn (lsp-activate-on "lus")
      :server-id 'lus)))
```

## Refactoring

The language server offers refactorings for the selected code in every editor, as code actions. Each one is offered only where it keeps what the program does and where its result checks as cleanly as the source did.

| Refactoring | Offered when |
| --- | --- |
| Extract into a local | The selection is one whole expression that calls no function, outside the right side of `and` or `or` and outside a loop condition, with no call that runs before it in the same statement. The new local goes immediately before the statement. |
| Inline the local | The cursor is on a local declared as `local name = value` and never assigned again. Every use must be in the function of the declaration. A literal value replaces every use. Any other value must call no function and have exactly one use, in the same loop as the declaration, with no call or field write between the declaration and the use and no assignment to a variable that the value reads. |
| Extract into a function | The selection is a run of whole statements without `return`, `break`, `continue`, `goto`, a label, `...`, a `<close>` local, or `_ENV`. The function is defined immediately before the run. A local that nothing assigns and that no function inside the run captures becomes a parameter. Any other local from outside stays shared with the new function. A local that the run declares and later code reads comes back as a result. |
| Convert to concatenation | The selection is a string with interpolation. Each value becomes `tostring(value)`, which writes the same text. |
| Convert to a string with interpolation | The selection is a concatenation of string literals, numbers, and calls of `tostring`, which interpolation writes the same way. |

The new names are `extracted`, then `extracted2` and so on when the name is taken, so a rename usually follows. A local with an attribute other than `<const>`, such as `<lazy>` or `<observe>`, is never inlined, extracted from, or moved into a new function. A program that reads its own locals or lines with the debug library, such as with `debug.getlocal` or `debug.getinfo`, gets no refactoring.

A few differences remain observable. A metamethod with side effects can tell an extracted local from the original code, because the value is computed before the rest of its statement. An error message can name another variable or line, because a refactoring adds or removes lines and an inlined value has no name of its own. A value held by an extracted local stays reachable until the end of its block, which a weak table or a finalizer can notice.

## Coding agents

A coding agent that starts the language server reads its diagnostics after each edit, so it sees an error in the turn that caused it. Every agent that starts the server needs `lus` in a directory of the `PATH`.

### Claude Code

The `lus` plugin installs the Lus skills and registers `lus lsp` for every `.lus` file. Install it with the following command:

```bash
claude plugin install lus --marketplace lus-lang/lus
```

### opencode

Add the following to `opencode.json` in the project or in the global configuration of opencode:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "lsp": {
    "lus": {
      "command": ["lus", "lsp"],
      "extensions": [".lus"]
    }
  }
}
```

### Codex and other agents

An agent without a Language Server Protocol client checks its edits with `lus check`. Run [`lus agents init`](/manual/cli#lus-agents) in the project to install the Lus skills, which tell the agent to check its files with `lus check --json` and to fix every diagnostic.
