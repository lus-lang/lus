`lus debug` runs a script under the [Debug Adapter Protocol](https://microsoft.github.io/debug-adapter-protocol/), the protocol that VS Code and many other editors use to drive debuggers. The adapter is part of the interpreter, so any editor with a DAP client can set breakpoints in Lus code, step through it, and inspect its state with nothing installed beyond `lus`.

## Running the adapter

```
lus debug [--stdio | --port N] [-P perm]... [SCRIPT [ARGS...]]
```

By default the adapter speaks the protocol on standard input and output, which is how editors launch it. `--port N` accepts one client on `127.0.0.1:N` instead, which suits clients that connect to a running adapter. The script comes from the command line or from the `program` field of the launch request, and `-P` grants permissions to the program exactly as `lus -P` does.

The program's standard output and standard error are forwarded to the editor as output events. In stdio mode its standard input reads as empty, because the protocol owns the real one.

## Visual Studio Code

The [Lus extension](/manual/ide-setup) registers the `lus` debugger type, so **Run and Debug** works on any `.lus` file. A launch configuration in `.vscode/launch.json` names the program and its options.

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "lus",
      "request": "launch",
      "name": "Debug Lus File",
      "program": "${file}",
      "cwd": "${workspaceFolder}",
      "args": [],
      "pledges": ["fs:read=${workspaceFolder}/*"],
      "stopOnEntry": false
    }
  ]
}
```

| Field | Meaning |
| --- | --- |
| `program` | The Lus script to run. |
| `args` | The arguments passed to the script. |
| `cwd` | The working directory of the program. |
| `stopOnEntry` | Stop at the first line of the program. |
| `pledges` | The permissions granted to the program, as with `lus -P`. |

The extension starts the `lus` found on the `PATH`. The setting `lus.executablePath` names another executable, and a relative path with a directory part is resolved against the workspace folder.

## Features

The adapter supports the debugging features that editors expose for most languages.

- **Breakpoints** on any line, with a **condition** (a Lus expression that must be truthy), a **hit count**, or a **log message** that prints instead of stopping. A hit count is a number, which stops on exactly that hit, or a number after one of the operators `>=`, `<=`, `>`, `<`, `==`, and `%`, where `%3` stops on every third hit. A log message interpolates expressions written in braces, as in `x is {x}`.
- **Error breakpoints** with two filters. _Uncaught Errors_, on by default, stops on an error that no `catch` handles. _All Raised Errors_ stops on every error at the point where it is raised, including errors that a `catch` will handle.
- **Stepping** with step over, step in, and step out, plus **pause** while the program runs. New breakpoints take effect immediately, even while the program is running.
- **Call stacks** that follow coroutines. A coroutine's frames stack on top of the frames of the code that resumed it, so stepping out of a coroutine lands in its resumer.
- **Variables** in three scopes for each frame: its locals, its upvalues, and the globals. Tables, vectors, and other values expand in place.
- **Evaluation** of expressions in the context of the selected frame, from the debug console and on hover.

## How it works

The adapter is written in Zig and runs no Lus code inside the program of its own. It attaches through a native hook in the interpreter: while debugging, every thread runs the hooked dispatch loop with line events, and the interpreter reports each error before it searches for a handler. Breakpoints, stepping, and pausing are decided on line events, which cost one hash lookup by source and one bit test when breakpoints exist. A program that runs without the debugger runs the unhooked loop and pays nothing.

While the program runs, a reader thread queues incoming requests, and the line hook handles them between lines. While the program is stopped, the interpreter thread waits for requests and answers them, which is when the stack, variables, and expressions are inspected.

## Motivation

### Standard protocol, no extra install

Speaking the Debug Adapter Protocol lets every editor with a DAP client use the debugger. Shipping the adapter inside `lus` keeps it in step with the interpreter it debugs, so a breakpoint, a stack frame, or a variable always means the same thing to the debugger as it does to the runtime.

### Debugging under permissions

Programs run under the same [permission](/manual/acquis-10) model when they are debugged. The launch configuration lists the pledges the program receives, so a debugging session reproduces the conditions of a real run.
