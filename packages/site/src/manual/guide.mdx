## Welcome

Lus is a small language for scripts, command line tools, and network servers. The `lus` executable runs programs. It also formats, checks, tests, and debugs them.

### A first program

Three friends share a dinner bill of 97.29. This program computes what each of them owes.

```lus
local bill = 97.29
local people = 3

print(`Each of us pays $(bill / people)`)   --> Each of us pays 32.43
```

`local bill = 97.29` creates a variable named `bill` that holds 97.29. The next line creates `people`. The text between backticks is a template. `$( )` inserts the result of a calculation into it. `print` writes the text to the terminal.

Save the program as `bill.lus` and run it with `lus`. [Getting started](/manual/getting-started) shows how to install `lus`.

```sh
lus bill.lus
```

### Comments

A comment is a note for people who read the code. Lus ignores everything from `--` to the end of the line. A comment that starts with `--[[` continues until the next `]]`, so it can span several lines.

```lus
-- Prices include tax.
local price = 4.50   -- per cup

--[[
    The shop closes early on Sundays,
    so the Sunday totals cover fewer hours.
]]
```

A comment that starts with `-->` shows what its line prints. `print` separates several values with a tab, which the comments show as two spaces.

```lus
print(2 + 2)            --> 4
print("tea", 4.50)      --> tea  4.5
```

## Values and types

A _value_ is a piece of data, such as the number `97.29`, the text `"tea"`, or `true`. Every value has a _type_. The type determines the operations that apply to the value. Numbers can be added and text can be searched. Comparing the text `"tea"` with `true` is an error, which Lus reports when the line runs.

The type belongs to the value. A variable can hold a number at one point and text later.

### Nil

`nil` means "no value". A variable that is declared without a value holds `nil`. This is useful for a result that is not known yet.

```lus
local winner   -- decided when the race ends
print(winner)  --> nil
```

### Booleans

The booleans are `true` and `false`. They are the answers to yes-or-no questions, such as whether a door is locked. Comparisons such as `age >= 18` produce booleans, as [Comparison](#comparison) shows.

```lus
local door_locked = true
print(door_locked)   --> true
```

A condition in Lus accepts any value. `false` and `nil` count as false and are called _falsy_. Every other value counts as true and is called _truthy_. This includes `0` and the empty string `""`.

### Numbers

Lus has four kinds of numbers, called the _subtypes_ of the type `number`. Most programs use two of them. An _integer_ is a whole number, such as `42`. A _float_ is a number with a fractional part, such as `1.5`.

A float stores most fractions approximately. That is acceptable for measurements but wrong for money. A _decimal_ keeps its digits exactly. A decimal is written with a `d` after it.

```lus
print(0.1 + 0.2)      --> 0.30000000000000004
print(0.1d + 0.2d)    --> 0.3
print(19.90d)         --> 19.90
```

An integer has a limit of about nine quintillion. A calculation that passes the limit wraps around to a wrong answer. A _bigint_ has no limit. A bigint is written with an `n` after it.

```lus
print(9223372036854775807 + 1)    --> -9223372036854775808
print(9223372036854775807n + 1)   --> 9223372036854775808
```

Underscores make long numbers easier to read, so `1_000_000` is one million. A float always prints with a decimal point, as in `3.0`. [Arithmetic](#arithmetic) shows how the subtypes combine.

### Strings

A _string_ is text. Strings can be written with single quotes, double quotes, or backticks. Single and double quotes are equivalent.

```lus
print("It's ready")          --> It's ready
print('She said "now"')      --> She said "now"
```

A string in backticks can also contain values. `$name` inserts the value of a variable. `$( )` inserts the result of an expression.

```lus
local name = "Ada"
local unread = 3

print(`Hello, $name! You have $unread new messages.`)
--> Hello, Ada! You have 3 new messages.
print(`That is $(unread * 2) since yesterday.`)
--> That is 6 since yesterday.
```

A backslash in a string starts an _escape sequence_, which stands for a character that is hard to type. `\n` is a line break. `\t` is a tab. `\\` is a backslash. `\u{E9}` is the character with the Unicode number E9, which is `é`.

```lus
print("Name:\tAda\nRole:\tEngineer")
--> Name:  Ada
--> Role:  Engineer
```

A long string is written between `[[` and `]]`. It can span several lines. Its text is kept exactly as written. The help text of a command line tool is a typical long string.

```lus
local help = [[
Usage: split TOTAL PEOPLE
Divides a bill evenly.]]
print(help)
--> Usage: split TOTAL PEOPLE
--> Divides a bill evenly.
```

A string cannot change after it is created. Functions that modify text, such as converting it to upper case, return a new string. [Strings and patterns](#strings-and-patterns) describes these functions.

### Other types

A _table_ holds many values, as a list or as named fields. A _function_ is code that a program can call. [Tables](#tables) and [Functions](#functions) describe them. [Enums](#enums), [coroutines](#coroutines), and [queries](#queries) are also types. A _vector_ holds raw bytes. A _userdata_ is an object from the runtime or from a C library, such as an open file.

## Variables

A _variable_ is a name for a value. Variables keep values for later use. A good name also tells the reader what a value means.

### Local variables

The `local` statement declares a variable and gives it a first value. An assignment, written with `=`, gives an existing variable a new value.

```lus
local visitors = 1
print(visitors)          --> 1

visitors = visitors + 1
print(visitors)          --> 2
```

A declaration without a value leaves the variable `nil`. One statement can declare or assign several variables, with commas between the names and between the values. A name without a matching value gets `nil`.

```lus
local width, height = 80, 24
print(width, height)      --> 80  24

local first, second = "a"
print(first, second)      --> a  nil
```

An assignment computes all the values on its right side before it changes any variable. This is how two variables exchange their values in one statement.

```lus
local low, high = 9, 2
low, high = high, low
print(low, high)          --> 2  9
```

A name consists of letters, digits, and underscores. It cannot start with a digit. Names are case sensitive, so `total` and `Total` are different names. Reserved words such as `local`, `if`, and `end` cannot be names.

### Blocks and scope

A _block_ is a sequence of statements. A file is a block. The body of a loop, of a conditional statement, or of a function is also a block. `do ... end` creates a block where one is needed.

The _scope_ of a local variable starts at the statement after its declaration and ends at the end of its block. Outside its scope, the name does not refer to the variable. Two parts of a program can therefore use the same name without interfering.

```lus
local total = 0
do
    local bonus = 5          -- bonus exists only inside this block
    total = total + bonus    -- total is still in scope here
end
print(total)                 --> 5
```

A `do ... end` block is useful for a temporary variable that only a few statements need.

### Shadowing

A declaration can reuse the name of a variable that is already in scope. The new variable _shadows_ the old one until the end of its block. The old variable then becomes visible again with its value unchanged.

```lus
local price = 20
do
    local price = price * 1.2   -- the price with tax, for this block only
    print(price)                --> 24.0
end
print(price)                    --> 20
```

The new variable enters scope after its own declaration. The `price` on the right side of the inner declaration is therefore still the outer one.

### Global variables

A _global variable_ is visible in every file of a program. The built-in functions are global variables, so `print` works in every file. Assigning to a name that has no `local` declaration creates a global variable. A global that was never assigned is `nil`.

```lus
attempts = 1          -- no local declaration, so attempts is a global
print(attempts)       --> 1
print(retries)        --> nil
```

Local variables are the better default. A local is only visible in its block, which makes it easy to find every place that changes it. Lus also reads and writes locals faster than globals. Globals are for the few values that the whole program shares.

A misspelled name is also an undeclared name. The misspelling therefore creates a new global that holds `nil`. The program then continues with a wrong value. The `global` statement prevents this. It declares the globals that a file uses. After it, every other undeclared name in the block is an error.

```lus
global print
global attempts = 0

attempts = attempts + 1
print(attempts)       --> 1
```

The built-in names are globals too, so the declaration includes `print`. `global attempts = 0` also gives the global a first value. If another part of the program has already defined `attempts`, this declaration stops the program with the error `global 'attempts' already defined`.

With these declarations, a misspelling is a _compile error_. Lus reports a compile error when it loads the file, before any statement runs.

```lus nocheck
global print
global attempts = 0

attemps = attempts + 1    -- compile error: variable 'attemps' not declared
```

A file without a `global` statement treats every undeclared name as a global.

### Constants

An _attribute_ is a word in angle brackets after a variable name. It changes how the variable behaves. A variable with the `<const>` attribute keeps its first value. Any assignment to it is a compile error.

```lus
local MAX_RETRIES <const> = 3
local TIMEOUT <const> = MAX_RETRIES * 10
print(TIMEOUT)            --> 30
```

```lus nocheck
local MAX_RETRIES <const> = 3
MAX_RETRIES = 5           -- compile error: attempt to assign to const variable 'MAX_RETRIES'
```

A global can be constant too, as in `global VERSION <const> = "2.0"`. [Variable attributes](#variable-attributes) describes the other attributes.

## Built-in functions

A _function_ is a named piece of code. A program _calls_ a function by writing its name followed by parentheses. The values inside the parentheses are the _arguments_. Many functions return a value, called the _result_. `print` is one of many built-in functions.

`tonumber` converts text to a number. Input from a person or from a file is text, even when it contains digits, so a program converts it before it calculates.

```lus
local typed = "42"
local count = tonumber(typed)
print(count + 1)   --> 43
```

These built-in functions are the most common:

- `tonumber(text)` returns the number in `text`, or `nil` if the text is not a number.
- `tostring(value)` returns a value as text.
- `type(value)` returns the name of the type of a value. A program uses it to check data that it did not create.

```lus
print(tonumber("twelve"))                               --> nil
print(type(tonumber("12")), type(tonumber("twelve")))   --> number  nil
```

Most built-in functions belong to a _library_. A library is a group of functions about one subject, such as `math` or `string`. The name of a library function has a dot: `math.floor` is the function `floor` in the `math` library. It rounds a number down. `string.upper` converts text to upper case. A library can also contain constants, such as `math.pi`.

```lus
local minutes = 135
print(math.floor(minutes / 60), "hours")   --> 2  hours
print(math.max(72, 95, 58))                --> 95
print(string.upper("receipt"))             --> RECEIPT
```

The [API reference](/manual/api) lists every built-in function. In a terminal, `lus help NAME` prints the entry for one function, as in `lus help math.floor`.

## Operators

An _operator_ combines one or two values into a new value. An _expression_ is anything that produces a value: a _literal_ (a value written directly in the code, such as `42` or `"tea"`), a variable, a function call, or operators applied to smaller expressions.

### Arithmetic

Lus has the usual arithmetic operators.

| Operator | Meaning | Example | Result |
| --- | --- | --- | --- |
| `+` | addition | `7 + 2` | `9` |
| `-` | subtraction | `7 - 2` | `5` |
| `*` | multiplication | `7 * 2` | `14` |
| `/` | division | `7 / 2` | `3.5` |
| `//` | floor division | `7 // 2` | `3` |
| `%` | remainder | `7 % 2` | `1` |
| `^` | exponentiation | `7 ^ 2` | `49.0` |
| `-` before a value | negation | `-7` | `-7` |

#### Integers and floats

If both operands of `+`, `-`, `*`, `//`, or `%` are integers, the result is an integer. If one operand is a float, the result is a float. With integers and floats, `/` and `^` always produce a float, so `6 / 2` is `3.0`.

```lus
print(7 + 2)        --> 9
print(7 + 2.0)      --> 9.0
print(6 / 2)        --> 3.0
print(2 ^ 10)       --> 1024.0
```

Floor division rounds its result down, toward negative infinity. The remainder is what floor division leaves over. It has the sign of the right operand. Together, the two operators split a quantity into units, such as seconds into minutes and seconds. A remainder of `0` means that a division is exact.

```lus
local seconds = 200
print(seconds // 60)    --> 3
print(seconds % 60)     --> 20
print(-7 // 2)          --> -4
print(-7 % 2)           --> 1
print(seconds % 2)      --> 0
```

The largest integer is `math.maxinteger`. A result past it wraps around to the most negative integer. A calculation that can grow that large needs bigints.

```lus
print(math.maxinteger)        --> 9223372036854775807
print(math.maxinteger + 1)    --> -9223372036854775808
print(2n ^ 63)                --> 9223372036854775808
```

Dividing an integer by zero with `//` or `%` raises an error. Float division by zero produces an infinity, which prints as `inf` or `-inf`.

#### Bigints

A bigint behaves like an integer without limits. An operation between a bigint and an integer produces a bigint.

```lus
print(2n ^ 100)             --> 1267650600228229401496703205376
print(2n ^ 64 + 1)          --> 18446744073709551617
print(7n // 2)              --> 3
```

#### Decimals

A decimal computes in base 10, as a person does on paper. Its sums, differences, and products are exact. An operation between a decimal and an integer or a bigint produces a decimal. A division of decimals keeps up to 34 significant digits and rounds the rest.

```lus
local price = 19.99d
print(price * 3)        --> 59.97
print(10d / 4)          --> 2.5
print(1d / 3)           --> 0.3333333333333333333333333333333333
```

#### Mixed subtypes

The table gives the subtype of the result of `+`, `-`, `*`, `//`, and `%` for every pair of operand subtypes.

| | integer | float | bigint | decimal |
| --- | --- | --- | --- | --- |
| **integer** | integer | float | bigint | decimal |
| **float** | float | float | float | error |
| **bigint** | bigint | float | bigint | decimal |
| **decimal** | decimal | error | decimal | decimal |

`/` follows the same table, except that it produces a float when no operand is a decimal. `^` produces a float when both operands are integers or floats. A bigint or a decimal raised to a positive whole number stays exact. For example, `2n ^ 100` is a bigint. `1.5d ^ 2` is the decimal `2.25`.

A decimal is exact and a float is approximate. An operation between the two is an error, because Lus cannot know which of the two the program needs. The program converts one side first. `decimal(x)` converts a number to a decimal. `tonumber(d)` converts a decimal to a float.

```lus
local price = 19.99d
local rate = 0.5

print(price * decimal(rate))     --> 9.995
print(tonumber(price) * rate)    --> 9.995
```

```lus nocheck
print(19.99d * 0.5)    -- error: attempt to mix decimal and float in arithmetic
```

#### Strings in arithmetic

An arithmetic operator converts a string that contains a number, so `"10" + 5` is `15`. An explicit `tonumber` is clearer. It also lets the program handle text that is not a number.

### Comparison

A comparison produces `true` or `false`.

| Operator | Meaning |
| --- | --- |
| `==` | equal |
| `~=` | not equal |
| `<` and `>` | less than and greater than |
| `<=` and `>=` | less than or equal and greater than or equal |

Numbers compare by value, whatever their subtypes.

```lus
print(1 == 1.0)         --> true
print(1 == 1n)          --> true
print(2 < 2.5d)         --> true
print(0.1d == 0.1)      --> false
```

The last line is `false` because the float `0.1` is only close to one tenth.

Two strings are equal if they have the same characters. `<` and the other ordering operators compare strings character by character, by Unicode number. Every upper case English letter therefore comes before every lower case one.

```lus
print("apple" < "banana")    --> true
print("Zebra" < "apple")     --> true
```

Values of different types are never equal, so `"10" == 10` is `false`. Ordering a number against a string is an error. The program converts one side first.

```lus
print("10" == 10)              --> false
print(tonumber("10") == 10)    --> true
```

Two tables are equal only when they are the same table, as [Tables](#variables-refer-to-tables) explains. The same holds for functions.

### Logical operators

The logical operators `and`, `or`, and `not` combine conditions. They treat each operand as [truthy or falsy](#booleans).

`not` produces `true` for a falsy operand and `false` for a truthy operand.

`and` produces its left operand if that operand is falsy. Otherwise it produces its right operand. `or` produces its left operand if that operand is truthy. Otherwise it produces its right operand. The result is one of the operands, unchanged. It is a boolean only if that operand is a boolean.

```lus
local age = 30
print(age >= 18 and age < 65)    --> true
print(not (age >= 18))           --> false

print(nil or "default")          --> default
print(false and "unused")        --> false
print(1 and 2)                   --> 2
```

`and` and `or` evaluate the right operand only when the left operand does not already decide the result. A check on the left can therefore protect the expression on the right.

```lus
local divisor = 0
print(divisor ~= 0 and 10 // divisor > 2)    --> false
```

The division never runs, because `divisor ~= 0` is `false`.

`or` is the usual way to give a default to a value that may be `nil`.

```lus
local requested
local size = requested or 10
print(size)                      --> 10
```

The default also replaces `false`. A setting where `false` is a valid choice needs an explicit comparison with `nil`.

Together, `and` and `or` choose between two values. `condition and a or b` is `a` when the condition is truthy. Otherwise it is `b`. This only works when `a` is truthy. A falsy `a` makes the expression produce `b`.

```lus
local stock = 0
print(stock > 0 and "in stock" or "sold out")   --> sold out
```

### Concatenation

`..` joins two strings into a new string. A number is converted to a string first.

```lus
local name = "Ada"
print("Hello, " .. name)       --> Hello, Ada
print("Total: " .. 42)         --> Total: 42
```

Any other operand, such as `nil` or a boolean, is an error. A string in backticks accepts values of every type. It is usually easier to read when text and values alternate.

### Length

`#` before a string produces its length in characters.

```lus
print(#"hello")    --> 5
print(#"héllo")    --> 5
print(#"")         --> 0
```

Before a list, `#` produces the number of items, as [Lists](#lists) shows.

### Bitwise operators

The bitwise operators work on the 64 bits of an integer. They store several yes-or-no settings in one number. They also read and write binary formats.

| Operator | Meaning |
| --- | --- |
| `&` | AND: a bit is 1 if it is 1 in both operands |
| `\|` | OR: a bit is 1 if it is 1 in either operand |
| `~` between two values | XOR: a bit is 1 if it is 1 in exactly one operand |
| `~` before a value | NOT: every bit is inverted |
| `<<` | shift the bits left |
| `>>` | shift the bits right |

This example stores three permissions in one integer, with one bit for each.

```lus
local READ <const> = 1 << 0
local WRITE <const> = 1 << 1
local EXECUTE <const> = 1 << 2

local mode = READ | WRITE
print(mode)                    --> 3
print(mode & WRITE ~= 0)       --> true
print(mode & EXECUTE ~= 0)     --> false

mode = mode & ~WRITE           -- clear the WRITE bit
print(mode)                    --> 1
```

A float operand must be a whole number. Lus converts it to an integer. If either operand is a bigint, the result is a bigint without the 64-bit limit. `1n << 64` is `18446744073709551616`.

### Precedence

_Precedence_ is the order in which the operators of an expression apply. The table lists the operators from the highest precedence to the lowest. Operators in the same row have the same precedence.

| Precedence | Operators |
| --- | --- |
| 1 | `^` |
| 2 | `not`, `#`, `-` and `~` before a value |
| 3 | `*`, `/`, `//`, `%` |
| 4 | `+`, `-` |
| 5 | `..` |
| 6 | the bitwise operators, from `<<` and `>>` to `\|` |
| 7 | `<`, `>`, `<=`, `>=`, `~=`, `==` |
| 8 | `and` |
| 9 | `or` |

Among the bitwise operators, the shifts apply first, then `&`, then `~`, then `|`.

Operators of the same precedence apply from left to right. `^` and `..` are the exceptions. They apply from right to left. Parentheses override precedence. They also make an unclear order explicit.

```lus
print(1 + 2 * 3)        --> 7
print((1 + 2) * 3)      --> 9
print(2 ^ 3 ^ 2)        --> 512.0
print(-2 ^ 2)           --> -4.0
```

Two rules cause frequent mistakes. Exponentiation applies before negation, so `-2 ^ 2` is `-(2 ^ 2)`. `not` applies before a comparison, so `not a == b` compares `not a` with `b`. To negate a comparison, write `not (a == b)` or use `~=`.

```lus
local a, b = 1, 2
print(not a == b)       --> false
print(not (a == b))     --> true
print(a ~= b)           --> true
```

## Control flow

Statements run in order, from the top of a file to the bottom. An `if` statement runs a block only when a condition is true. A loop runs a block several times.

### `if` statements

The `if` statement runs a block when its condition is [truthy](#booleans). An `elseif` branch tests another condition if the previous conditions were falsy. The `else` branch runs if every condition was falsy. Both are optional. An `if` statement can have any number of `elseif` branches.

```lus
local temperature = 31

if temperature > 30 then
    print("hot")            --> hot
elseif temperature > 15 then
    print("mild")
else
    print("cold")
end
```

Lus tests the conditions in order. It runs the block of the first truthy condition and then continues after the `end`. Each branch is a block, so a local variable declared in a branch exists only in that branch.

### Conditions that declare variables

Programs often compute a value, test it, and use it only if the test passes. A condition of the form `name = expression` does all three. It declares a local variable with the value of the expression. The condition is true if that value is truthy.

```lus
local input = "42"

if n = tonumber(input) then
    print(n + 1)                      --> 43
else
    print(`$input is not a number`)
end
```

`tonumber` returns `nil` for text that is not a number. The first branch therefore runs only with a usable `n`. The variable exists in every branch of the `if` and ends at its `end`.

A condition can declare several variables, which is useful with a function that returns several values. The condition is true only if every declared variable is truthy. `string.find` searches a string. It returns the positions where the match starts and ends, or `nil` if there is no match.

```lus
local line = "level=warn"

if first, last = string.find(line, "warn") then
    print(`found from $first to $last`)    --> found from 7 to 10
else
    print("not found")
end
```

An `elseif` condition can declare variables in the same way.

### `while` loops

The `while` loop repeats its body as long as its condition is truthy. It tests the condition before each pass, so the body may not run at all. A `while` loop is for repetition when the number of passes is not known in advance.

This loop halves the width of an image until the image fits in 1000 pixels.

```lus
local width = 4000
local halvings = 0

while width > 1000 do
    width = width // 2
    halvings = halvings + 1
end
print(width, halvings)   --> 1000  2
```

A `while` condition can also [declare variables](#conditions-that-declare-variables). The expression is evaluated before every pass. The loop ends when a declared variable is falsy. This loop counts the fields of a line of comma-separated values by finding each comma. The third argument of `string.find` is the position where the search starts.

```lus
local line = "tea,4.50,3,shelf 2"
local fields = 1
local start = 1

while found = string.find(line, ",", start) do
    fields = fields + 1
    start = found + 1
end
print(fields)   --> 4
```

Without the declaration in the condition, the call to `string.find` would appear twice: once before the loop and once at the end of its body.

### `repeat` loops

The `repeat` loop runs its body first and tests its condition afterwards. It ends when the condition is truthy. The body therefore always runs at least once. Counting the digits of a number needs this, because even `0` has one digit.

```lus
local n = 4096
local digits = 0
repeat
    n = n // 10
    digits = digits + 1
until n == 0
print(digits)   --> 4
```

With `n = 0`, the body runs once and the count is 1.

The condition after `until` can use the local variables of the body. In this example, the body records whether a connection attempt succeeded. The condition reads the result.

```lus
local attempts = 0

repeat
    attempts = attempts + 1
    local connected = attempts >= 3   -- stands for a real connection attempt
until connected
print(attempts)   --> 3
```

### Numeric `for` loops

The numeric `for` loop runs its body once for each number in a range. The loop variable holds the current number. The start and the stop are both included.

```lus
for day = 1, 3 do
    print(`day $day`)
end
--> day 1
--> day 2
--> day 3
```

An optional third number is the step. The default step is 1. A negative step counts down. A float step produces floats.

```lus
for seconds = 3, 1, -1 do
    print(seconds)
end
print("liftoff")
--> 3
--> 2
--> 1
--> liftoff

for dose = 0, 1, 0.5 do
    print(dose)
end
--> 0.0
--> 0.5
--> 1.0
```

The start, the stop, and the step are evaluated once, before the first pass. If the start is already past the stop, the body does not run. The loop variable is local to the body. The body cannot assign to it.

The other form of `for` goes through the items of a table, as [Iteration](#iteration) describes.

### `break` and `continue`

`break` ends a loop immediately. The program continues after the loop. `continue` skips the rest of the current pass and starts the next pass. In a `while` or `repeat` loop, the next pass starts with the test of the condition.

This theatre numbers its seats from 1 and has no seat 13. The loop sells 15 tickets.

```lus
local sold = 0
for seat = 1, 20 do
    if seat == 13 then
        continue                           -- no seat 13
    end
    sold = sold + 1
    if sold == 15 then
        print(`last seat sold: $seat`)     --> last seat sold: 16
        break
    end
end
```

`break` and `continue` apply to the innermost loop that contains them. With `continue`, the rest of the loop body does not need to be inside an `if`. This helps when a pass can end early for several reasons.

### `goto`

The `goto` statement jumps to a _label_. A label is a name between double colons, such as `::done::`. `goto` is mainly used to leave several nested loops at once. `break` only leaves the innermost loop.

```lus
local target = 12

for i = 1, 9 do
    for j = 1, 9 do
        if i * j == target then
            print(`$i x $j`)      --> 2 x 6
            goto found
        end
    end
end
print("no pair found")
::found::
```

A `goto` can jump to a label in its own block or in an enclosing block. It cannot jump into the scope of a local variable, so labels are usually at the end of a block. Loops, `break`, and `continue` are clearer in most cases. `goto` is for the remaining cases.

## Functions

A _function_ is a piece of code with a name. A program can call it many times with different inputs. A calculation in a function is written once. Its name says what it does.

### Declaring and calling

A function declaration has a name, a list of parameters in parentheses, and a body that ends with `end`. The `return` statement ends the function and returns a result. This function computes the area of a rectangle.

```lus
local function area(width, height)
    return width * height
end

print(area(3, 4))   --> 12
print(area(10, 2))  --> 20
```

`local function` declares the function as a [local variable](#local-variables). Most functions of a program are local. Functions that other files need go into a [module](#modules).

A call can be part of an expression, as in `print(area(3, 4))`, or a statement of its own. A function that reaches its `end` without a `return` returns no result. A call whose only argument is a string literal can omit the parentheses, so `print "ready"` is the same as `print("ready")`.

### Parameters and arguments

A _parameter_ is a local variable of the function. Each parameter holds one argument of the call, matched by position. A parameter without an argument is `nil`. An argument without a parameter is ignored.

```lus
local function show(a, b)
    print(a, b)
end

show(1)        --> 1  nil
show(1, 2, 3)  --> 1  2
```

Because a missing argument is `nil`, `or` gives a parameter a default value. In this function, `times` is 1 when the call leaves it out.

```lus
local function greet(name, times)
    times = times or 1
    for i = 1, times do
        print(`Hello, $name!`)
    end
end

greet("Ada")      --> Hello, Ada!
greet("Lin", 2)   --> Hello, Lin!
                  --> Hello, Lin!
```

`or` also replaces `false`. A parameter for which `false` is a valid value needs `if times == nil then` before the default is assigned.

### Multiple results

A function can return several values, separated by commas. This is useful for a calculation with more than one answer, such as a quotient and its remainder. A multiple assignment receives the values.

```lus
local function clock(seconds)
    return seconds // 3600, seconds % 3600 // 60, seconds % 60
end

local hours, minutes, secs = clock(7384)
print(hours, minutes, secs)  --> 2  3  4

print(clock(7384))           --> 2  3  4
print(clock(7384), "end")    --> 2  end
print((clock(7384)))         --> 2
```

An assignment takes as many results as it has variables. Extra results are ignored. Extra variables are `nil`. A call keeps all of its results only when it is the last expression in a list, as in the first `print`. Elsewhere in a list, as before `"end"`, a call produces only its first result. Parentheses around a call also keep only the first result.

### Variable arguments

Some functions accept any number of arguments, as `print` does. Three dots as the last parameter accept all the extra arguments. In the body, three dots stand for those arguments. This `log` function adds a prefix and passes the rest of its arguments to `print`.

```lus
local function log(level, ...)
    print(`[$level]`, ...)
end

log("info", "started")              --> [info]  started
log("warn", "disk at", 91, "%")     --> [warn]  disk at  91  %
```

### Functions as values

A function is a value, like a number or a string. It can be stored in a variable, passed to another function, and returned from one. The `retry` function repeats an action until the action succeeds. The action is a function that is passed as an argument.

```lus
local function retry(attempts, action)
    for attempt = 1, attempts do
        local result = action(attempt)
        if result then
            return result, attempt
        end
    end
    return nil, attempts
end

local value, tries = retry(5, function(attempt)
    return attempt >= 3 and "connected"
end)
print(value, tries)  --> connected  3
```

The expression `function(attempt) ... end` creates a function without a name. A declaration such as `local function f() end` creates the same kind of value and stores it in the variable `f`.

### Functions that remember local variables

A function can use the local variables that are in scope where it is written. It keeps them after their block has ended. This gives a function private state that no other code can reach.

`counter` returns a new function on each call. Each call of `counter` creates a new `count` variable, so each returned function has its own count.

```lus
local function counter()
    local count = 0
    return function()
        count = count + 1
        return count
    end
end

local next_ticket = counter()
local next_order = counter()
print(next_ticket(), next_ticket(), next_ticket())  --> 1  2  3
print(next_order())                               --> 1
```

This is also how a program prepares a _callback_, which is a function that other code calls later. `logger` returns a function that keeps its `prefix`. Each part of a program gets its own logging function. The prefix is written only once.

```lus
local function logger(prefix)
    return function(message)
        print(`[$prefix] $message`)
    end
end

local db_log = logger("db")
local http_log = logger("http")
db_log("connected")       --> [db] connected
http_log("listening")     --> [http] listening
```

Two functions written in the same block share the variables of that block. When one function assigns a variable, the other sees the new value.

```lus
local function account(balance)
    local function deposit(amount)
        balance = balance + amount
    end
    local function report()
        return `balance: $balance`
    end
    return deposit, report
end

local deposit, report = account(100)
deposit(50)
print(report())  --> balance: 150
```

### Recursion

A function can call itself. This is called _recursion_. It is useful for problems that contain a smaller version of themselves, such as a tree of folders or a factorial.

```lus
local function factorial(n)
    if n <= 1 then
        return 1
    end
    return n * factorial(n - 1)
end

print(factorial(5))   --> 120
print(factorial(20))  --> 2432902008176640000
```

`local function` makes the name visible inside the body, which a recursive function needs. Every call that has not returned uses memory. A recursion that goes too deep fails with the error `stack overflow`.

## Tables

A _table_ is a collection of values, each stored under a _key_. The key is what a program uses to find the value again. A table whose keys are the integers 1, 2, 3, and up is a list. A table whose keys are names is a record. Keys of any kind make a dictionary.

The table is the collection type of Lus. Lists, records, dictionaries, objects, and modules are all tables, so one syntax and one library serve every one of them.

### Creating tables

Curly braces create a table. Values written between the braces, separated by commas, receive the keys 1, 2, 3, and up. A value written as `name = value` is stored under the string key `"name"`.

```lus
local empty = {}
local primes = { 2, 3, 5, 7 }
local point = { x = 10, y = 20 }

print(primes[1], primes[4])  --> 2  7
print(point.x, point.y)      --> 10  20
```

`primes[1]` reads the first item of the list, and `point.x` reads the field named `x`, as [Records](#records) explains.

Square brackets after a table read or assign the value under a key. A key that the table does not hold reads as `nil`, and assigning `nil` to a key removes it.

```lus
local stock = {}
stock["apples"] = 30
stock["pears"] = 12
print(stock["apples"], stock["plums"])  --> 30  nil

stock["pears"] = nil
print(stock["pears"])                   --> nil
```

### Lists

A _list_ is a table whose keys are the integers from 1 to its length, with no gaps. Lists hold ordered data: the lines of a file, the rows of a result, the arguments of a command. The first item is at index 1, and the length operator `#` gives the number of items, which is also the index of the last one.

```lus
local days = { "Mon", "Tue", "Wed" }
print(#days, days[1], days[#days])  --> 3  Mon  Wed

days[#days + 1] = "Thu"
print(#days, days[4])               --> 4  Thu
```

The [`table`](/manual/api#table-library) library changes lists in place. [`table.insert`](/manual/api#table.insert) appends an item, or inserts it at a position and moves the later items up. [`table.remove`](/manual/api#table.remove) removes and returns the last item, or the item at a position, and moves the later items down.

```lus
local queue = { "b", "c" }
table.insert(queue, "d")        -- b c d
table.insert(queue, 1, "a")     -- a b c d

print(table.remove(queue))      --> d
print(table.remove(queue, 1))   --> a
print(#queue, queue[1])         --> 2  b
```

The length operator counts correctly only when the list has no gaps. To delete an item from the middle of a list, call `table.remove`, which closes the gap. Assigning `nil` to a middle index leaves a gap, and `#` may then report either side of it.

[`table.sort`](/manual/api#table.sort) sorts a list in place. With one argument it uses the `<` operator, so it sorts numbers upward and strings alphabetically. The optional second argument is a function that receives two items and returns `true` when the first must come before the second. [`table.concat`](/manual/api#table.concat) joins a list of strings and numbers into one string with a separator between the items.

```lus
local scores = { 72, 95, 58, 81 }
table.sort(scores)
print(table.concat(scores, " "))   --> 58 72 81 95

table.sort(scores, function(a, b)
    return a > b
end)
print(table.concat(scores, ", "))  --> 95, 81, 72, 58
```

The library also filters, transforms, groups, and summarizes lists. [Table functions](/manual/data#table-functions) presents those functions.

### Records

A _record_ is a table that describes one thing with named fields. A field name that is a valid [name](#local-variables) can be written after a dot, so `user.name` means the same as `user["name"]`. The dot form is the usual way to read and assign fields.

```lus
local user = { name = "Ada", age = 36 }
user.email = "ada@example.org"
user.age = user.age + 1

print(user.name, user.age, user.email)  --> Ada  37  ada@example.org
print(user.phone)                       --> nil
```

Records make calls with many optional settings readable. The function takes one table, and the caller names the settings it wants. A call whose only argument is a table written in curly braces may omit the parentheses.

```lus
local function connect(options)
    local port = options.port or 80
    return `$(options.host):$port`
end

print(connect({ host = "example.org", port = 8080 }))  --> example.org:8080
print(connect{ host = "example.org" })                 --> example.org:80
```

### Collecting arguments into a list

A function that accepts any number of arguments often needs to count them or visit them one at a time. A name after the three dots collects the arguments into a list, and its field `n` holds how many there are.

```lus
local function average(...numbers)
    if numbers.n == 0 then
        return 0
    end
    local total = 0
    for i = 1, numbers.n do
        total = total + numbers[i]
    end
    return total / numbers.n
end

print(average(4, 8, 6))  --> 6.0
print(average())         --> 0
```

The count in `n` includes arguments that are `nil`, so `average(1, nil, 3)` sees three arguments, where `#` could stop at the gap. The plain dots stay usable in a function that names them, which lets it pass the same arguments on to another function.

[`table.unpack`](/manual/api#table.unpack) goes the other way and turns the items of a list into separate values, for example to pass them as the arguments of a call. `print(table.unpack({ 1, 2, 3 }))` prints the same line as `print(1, 2, 3)`.

### Dictionaries

A _dictionary_ maps keys to values when the keys are data, such as the words of a text or the identifiers of users. Any value except `nil` and the float NaN (the result of `0 / 0`, which means "not a number") can be a key: strings, numbers, booleans, and even tables and functions. Between curly braces, a key that is not a valid name is written between square brackets.

```lus
local capitals = {
    ["New Zealand"] = "Wellington",
    ["South Korea"] = "Seoul",
    France = "Paris",
}

local country = "South Korea"
print(capitals[country])    --> Seoul
print(capitals.France)      --> Paris
print(capitals["Germany"])  --> nil
```

The dot form reads the key that is literally written, so `capitals.country` reads the key `"country"`. The bracket form evaluates the expression between the brackets and uses its value as the key.

A common use of a dictionary is counting. The following loop counts how often each word occurs.

```lus
local words = { "tea", "milk", "tea", "sugar", "tea" }
local counts = {}
for i = 1, #words do
    local word = words[i]
    counts[word] = (counts[word] or 0) + 1
end

print(counts.tea, counts.milk, counts.salt)  --> 3  1  nil
```

The length operator counts only the keys 1, 2, 3, and up, so `#counts` is 0 here. [Iteration](/manual/guide#iteration) shows how to visit every key of a dictionary.

### Nested tables

A table can hold other tables. This is how a program represents structured data: a list of records, a record with a list inside it, or a grid of rows. Each index or field access is applied to the result of the one before it.

```lus
local order = {
    id = 1042,
    customer = { name = "Ada", city = "London" },
    items = {
        { name = "tea", price = 4.50 },
        { name = "mug", price = 12.00 },
    },
}

print(order.customer.city)   --> London
print(order.items[2].name)   --> mug
print(#order.items)          --> 2
```

Data read from JSON has this shape. [`fromjson`](/manual/api#fromjson) turns a JSON document into nested tables, and [`tojson`](/manual/api#tojson) turns nested tables into JSON.

### Variables refer to tables

A variable refers to a table, and several variables can refer to the same one. Assigning a table to a second variable, or passing it to a function, gives a second reference to the same table, so a change made through one reference is visible through the other.

```lus
local a = { 1, 2, 3 }
local b = a
b[1] = 99
print(a[1])  --> 99

local function clear(list)
    for i = #list, 1, -1 do
        list[i] = nil
    end
end
clear(a)
print(#b)    --> 0
```

For the same reason, `==` compares two tables by identity. Two tables are equal only when they are the same table, so `{} == {}` is `false`. [Copying tables](/manual/guide#copying-tables) shows how to make an independent copy.

### Methods

A table can hold functions next to its data. A function that is stored in a table and works on that table is a _method_. Lus has a short syntax for calling one: `account:deposit(50)` calls the function `account.deposit` and passes `account` itself as the first argument.

The same colon in a declaration adds a first parameter named `self`, which receives the table.

```lus
local account = { balance = 100 }

function account:deposit(amount)
    self.balance = self.balance + amount
end

function account:report()
    return `balance: $(self.balance)`
end

account:deposit(50)
print(account:report())  --> balance: 150
```

The call `account:deposit(50)` is the same as `account.deposit(account, 50)`. The colon form names the table once, which matters when the table comes from a longer expression.

The methods above belong to one table. A program that needs many accounts shares one set of methods among them with a metatable, which [Metatables and objects](/manual/guide#metatables-and-objects) explains.

### Tables as modules

A table can group related functions and constants under one name. The libraries are organized this way: `string`, `table`, and `math` are global variables that each hold a table, and `math.floor` is the field `floor` of the table `math`. A declaration such as `function shapes.circle(radius) ... end` stores a function in a field in the same way, here the field `circle` of the table `shapes`.

```lus
print(type(math), type(math.floor))  --> table  function
print(math.floor(7.8), math.max(3, 9))  --> 7  9
```

A program splits its own code the same way. A _module_ is a file that builds such a table and returns it, and another file loads it with [`require`](/manual/api#require), which returns that table, as [Modules](#modules) shows.

### Destructuring with `from`

Code that uses several fields of one table often copies them into local variables first. Written as ordinary assignments, each name appears twice and the table appears once per field: `local host, port = config.host, config.port`. The `from` keyword states the names once. Each variable receives the field with the same name.

```lus
local config = { host = "example.org", port = 8080, debug = false }

local host, port from config
print(host, port)  --> example.org  8080
```

A name that the table does not hold as a field becomes `nil`. The expression after `from` is evaluated once, so it may be a function call that builds or loads a table.

Destructuring is the usual way to take functions out of a module. The following line makes two functions of the `table` module available under short names.

```lus
local insert, remove from table

local stack = {}
insert(stack, "a")
insert(stack, "b")
print(remove(stack), #stack)  --> b  1
```

It works on the result of `require` as well, because `require` returns a table. `local parse, format from require("dates")` loads the module file `dates.lus` and keeps two of its functions.

Without `local`, `from` assigns variables that already exist. This suits a loop that refreshes several variables from a new record on each pass and uses them before the next one. The following loop follows a route and adds up the distance between each point and the one before it.

```lus
local route = { { x = 0, y = 0 }, { x = 3, y = 4 }, { x = 3, y = 10 } }

local x, y from route[1]
local distance = 0
for i = 2, #route do
    local previous_x, previous_y = x, y
    x, y from route[i]
    distance = distance + math.sqrt((x - previous_x) ^ 2 + (y - previous_y) ^ 2)
end
print(distance)  --> 11.0
```

`global width, height from settings` declares global variables in the same way.

### Optional chaining

Nested data often has optional parts. A user may or may not have an address, and a configuration may or may not have a section. Reading a field of a missing part is an error, because the missing part is `nil` and `nil` has no fields. With `local user = { name = "Ada" }`, the expression `user.address.city` stops the program with the message `attempt to index a nil value (field 'address')`.

A `?` after a value makes the rest of the chain conditional on that value. If the value is `nil` or `false`, Lus skips everything after the `?` and the whole chain evaluates to that value. Otherwise the chain continues. Put a `?` after each part that may be absent.

```lus
local reply = {
    user = { name = "Ada", address = { city = "London" } },
}

print(reply.user.address?.city)           --> London
print(reply.user.employer?.name)          --> nil
print(reply.user.employer?.name or "none")  --> none
```

The last line combines the chain with `or` to supply a default. Without the `?`, each level needs its own test: `reply.user.employer and reply.user.employer.name`.

The `?` works before every kind of access: a field with `?.name`, an index with `?[i]`, a method call with `?:method()`, and a call with `?(arguments)`. The call form runs a function only if it exists, which suits optional callbacks.

```lus
local handlers = {
    resize = function(width, height)
        return width * height
    end,
}

print(handlers.resize?(80, 24))  --> 1920
print(handlers.close?())         --> nil

local tags = nil
print(tags?[1])                  --> nil
```

A chain that contains a `?` produces a value, and the program must use that value, for example in an assignment, a condition, or an argument. Such a chain cannot be the target of an assignment.

### Slices

A _slice_ copies part of a list, a string, or a vector of bytes. Two positions separated by a comma between square brackets select the first and last item to copy, and either position may be left out to mean the start or the end.

```lus
local letters = { "a", "b", "c", "d", "e" }

print(table.concat(letters[2, 4], " "))  --> b c d
print(table.concat(letters[, 2], " "))   --> a b
print(table.concat(letters[4, ], " "))   --> d e
print(("hello world")[1, 5])             --> hello
```

The result is a new value, so changing a slice of a list leaves the original list as it was.

### Copying tables

Assignment shares a table, so a program that wants to change a table while keeping the original needs a copy. [`table.clone`](/manual/api#table.clone) returns a new table with the same keys and values.

```lus
local defaults = { color = "blue", size = 10 }
local mine = table.clone(defaults)
mine.color = "red"

print(defaults.color, mine.color)  --> blue  red
```

The copy is _shallow_: a nested table is shared between the original and the copy. Passing `true` as the second argument makes a _deep_ copy, in which every nested table is copied too.

```lus
local original = { name = "report", tags = { "draft" } }
local shallow = table.clone(original)
local deep = table.clone(original, true)

original.tags[1] = "final"
print(shallow.tags[1], deep.tags[1])  --> final  draft
```

## Iteration

To _iterate_ is to visit the items of a collection one after another. The [numeric `for`](/manual/guide#numeric-for-loops) counts through numbers. The _generic `for`_ visits whatever an _iterator_, a function that hands out one item per call, produces: the items of a list, the keys of a dictionary, the matches in a string, the lines of a file.

### The generic for

A generic `for` names one or more loop variables, then `in`, then an expression that says what to iterate over. The body runs once for each item, with the loop variables set to that item. The most common iteration is over a list, with [`ipairs`](/manual/api#ipairs).

```lus
local days = { "Mon", "Tue", "Wed" }

for index, day in ipairs(days) do
    print(index, day)
end
--> 1  Mon
--> 2  Tue
--> 3  Wed
```

The loop variables are local to the body and are created anew for each item. The first loop variable is read-only, so assigning to it is a compile error. The other loop variables are ordinary local variables of the body. `break` and `continue` work as they do in every loop. A loop that needs only the second variable names the first one `_` by convention.

### `ipairs` and `pairs`

`ipairs(t)` visits a list in order. It produces the index and the value for 1, 2, 3, and up, and stops before the first index whose value is `nil`.

[`pairs(t)`](/manual/api#pairs) visits every key of a table, whatever its type, and produces the key and its value. It is the way to walk a dictionary or the fields of a record.

```lus
local prices = { tea = 4.50, mug = 12.00, spoon = 2.25 }

local total, count = 0, 0
for name, price in pairs(prices) do
    total = total + price
    count = count + 1
end
print(count, total)  --> 3  18.75
```

The order in which `pairs` visits keys is unspecified. A program that needs a fixed order collects the keys into a list and sorts it, as [`sorted_pairs`](#writing-an-iterator-with-a-function) does.

During a `pairs` loop, the body may assign to existing keys, including assigning `nil` to remove them. Adding a new key to the table during the loop makes the rest of the traversal unpredictable.

### Counting with range

[`range`](/manual/api#range) produces a sequence of numbers. `range(n)` counts from 1 to `n`, `range(first, last)` counts from `first` to `last`, and a third argument sets the step, which may be negative to count down. `range` works with numbers only.

```lus
for lap in range(3) do
    print(`lap $lap`)
end
--> lap 1
--> lap 2
--> lap 3

local countdown = {}
for i in range(10, 1, -3) do
    countdown[#countdown + 1] = i
end
print(table.concat(countdown, " "))  --> 10 7 4 1
```

A `for` loop that calls `range` directly runs exactly the numeric `for` with the same bounds, at the same speed and with the same rules. A float start or step makes every value a float, so `range(1, 2, 0.5)` counts `1.0`, `1.5`, and `2.0`. The choice between the two forms of a counting loop is a matter of style. `range` is also useful when the sequence itself is a value: when a function takes a sequence of numbers as an argument, or when a program stores the sequence and takes numbers from it over time.

Outside a `for` loop, `range` returns an iterator function. Each call of that function returns the next number, and `nil` after the last one. A function that loops over an iterator it receives works with `range` and with every other iterator, so the caller chooses the numbers.

```lus
local function squares(numbers)
    local result = {}
    for n in numbers do
        result[#result + 1] = n * n
    end
    return result
end

print(table.concat(squares(range(4)), " "))           --> 1 4 9 16
print(table.concat(squares(range(10, 30, 10)), " "))  --> 100 400 900
```

A stored range returns the numbers of a fixed pool, one per call, and returns `nil` once the pool is empty.

```lus
local free_seats = range(1, 3)

print(free_seats(), free_seats())  --> 1  2
print(free_seats(), free_seats())  --> 3  nil
```

### Writing an iterator with a function

An _iterator_ is a function that returns the next item each time it is called and returns `nil` when no items remain. The generic `for` calls the iterator once per pass, assigns its results to the loop variables, and stops when the first result is `nil`.

Writing an iterator gives a traversal a name, so that every loop that needs it reads as plainly as a loop over `ipairs`. The usual way is a function that creates the iterator and returns it. The iterator keeps its position in a local variable of the creating function, as described under [Functions that remember local variables](/manual/guide#functions-that-remember-local-variables).

The following `sorted_pairs` visits a dictionary in the order of its keys, which `pairs` does not promise.

```lus
local function sorted_pairs(t)
    local keys = {}
    for key in pairs(t) do
        keys[#keys + 1] = key
    end
    table.sort(keys)

    local i = 0
    return function()
        i = i + 1
        local key = keys[i]
        if key ~= nil then
            return key, t[key]
        end
    end
end

local stock = { pears = 12, apples = 30, figs = 4 }
for name, count in sorted_pairs(stock) do
    print(name, count)
end
--> apples  30
--> figs  4
--> pears  12
```

The loop calls `sorted_pairs(stock)` once, before the first pass, and then calls the function it returned once per pass.

An iterator can also let the loop keep its position. When the expression after `in` produces three values, an iterator function, a value, and a starting position, the loop calls the function with the value and the previous position on each pass. One function then serves every loop, since it keeps nothing of its own. The `reversed` function below visits a queue from its last name to its first.

```lus
local function previous(list, i)
    i = i - 1
    if i >= 1 then
        return i, list[i]
    end
end

local function reversed(list)
    return previous, list, #list + 1
end

local queue = { "ada", "lin", "grace" }
for position, name in reversed(queue) do
    print(position, name)
end
--> 3  grace
--> 2  lin
--> 1  ada
```

`ipairs` works this way: it returns its iterator, the list, and the starting index 0.

The standard library returns iterators from several functions. [`string.gmatch`](/manual/api#string.gmatch) iterates over the matches of a pattern in a string, as [Strings and patterns](/manual/guide#every-match-with-stringgmatch) describes, and [`io.lines`](/manual/api#io.lines) iterates over the lines of a file.

## Strings and patterns

Programs spend much of their time on text: cleaning up what a person typed, taking a log line apart, building a report. The [`string`](/manual/api#string-library) library measures, cuts, transforms, searches, and replaces text. Its searching functions use _patterns_, a notation that describes the shape of the text a program looks for.

Every string function returns a new string and leaves its argument as it was.

Every function of the library can be called as a method of a string, so `name:upper()` is the same call as `string.upper(name)`. A string literal needs parentheses around it for this form, as in `("abc"):upper()`.

### Length and parts

The length operator `#` gives the number of characters in a string. Positions in a string count characters from 1, and a character is one Unicode code point, so an accented letter or an emoji counts as one.

[`string.sub(s, first, last)`](/manual/api#string.sub) returns the part of `s` from position `first` to position `last`. Both ends are included. A negative position counts from the end of the string, so `-1` is the last character, and `last` defaults to the end.

```lus
local s = "héllo wörld"

print(#s)             --> 11
print(s:sub(1, 5))    --> héllo
print(s:sub(7))       --> wörld
print(s:sub(-3))      --> rld
print(s:sub(2, -2))   --> éllo wörl
```

A [slice](/manual/guide#slices) reads the same part with brackets. `s[1, 5]` is `s:sub(1, 5)`, and `s[7, ]` is `s:sub(7)`. A slice takes no negative positions, so `s:sub` is the way to count from the end.

### Case, repetition, and reversal

[`string.upper`](/manual/api#string.upper) and [`string.lower`](/manual/api#string.lower) change the case of the letters `a` to `z` and leave every other character as it is. [`string.rep`](/manual/api#string.rep) repeats a string a number of times, with an optional separator between the copies. [`string.reverse`](/manual/api#string.reverse) reverses the order of the characters.

```lus
print(("Hello"):upper(), ("Hello"):lower())  --> HELLO  hello
print(("-"):rep(20))                         --> --------------------
print(("?"):rep(3, ", "))                    --> ?, ?, ?
print(("stressed"):reverse())                --> desserts
```

Comparing two strings without regard to case is done by lowering both: `a:lower() == b:lower()`.

### Splitting, joining, and trimming

[`string.split`](/manual/api#string.split) cuts a string at every occurrence of a delimiter and returns the pieces as a list. [`string.join`](/manual/api#string.join) does the reverse. It joins the items of a list into one string with the delimiter between them, and converts items that are not strings as `tostring` does.

```lus
local fields = ("ada,36,london"):split(",")
print(#fields, fields[1], fields[3])  --> 3  ada  london

print(string.join(fields, " | "))     --> ada | 36 | london
print(string.join({ 1, true, "x" }, "-"))  --> 1-true-x
```

`string.join` is also the efficient way to build a long string from many parts. Collect the parts in a list and join them once at the end.

[`string.trim`](/manual/api#string.trim) removes whitespace from both ends of a string. Text that a person typed or that came from a file usually needs it. [`string.ltrim`](/manual/api#string.ltrim) and [`string.rtrim`](/manual/api#string.rtrim) trim one end. A second argument lists the characters to remove in place of whitespace.

```lus
local input = "   ada@example.org \n"
print("[" .. input:trim() .. "]")       --> [ada@example.org]
print(("--title--"):trim("-"))          --> title

local parts = ("red, green , blue"):split(",")
for i, part in ipairs(parts) do
    parts[i] = part:trim()
end
print(string.join(parts, "|"))          --> red|green|blue
```

The delimiter of `string.split` is literal text. To split on something that varies, such as any run of whitespace, use a pattern with [`string.gmatch`](#every-match-with-stringgmatch).

### Formatting values

[String interpolation](/manual/guide#strings) covers most messages. [`string.format`](/manual/api#string.format) is for output that needs a fixed number of decimals, padding to a width, or another number base. Its first argument is a template in which each `%` item is replaced by the next argument, formatted as the item says.

| Item | Output |
| --- | --- |
| `%d` | An integer. |
| `%f` | A number with six decimals. `%.2f` gives two. |
| `%s` | Any value, converted as `tostring` does. |
| `%x` | An integer in hexadecimal. `%X` uses capital letters. |
| `%q` | A string in quotes with escapes, which Lus can read back. |
| `%%` | A percent sign. |

A number between the `%` and the letter sets a minimum width. The value is padded with spaces on the left, with spaces on the right if a `-` precedes the width, or with zeros if a `0` precedes it.

```lus
print(string.format("%.2f", 3.14159))            --> 3.14
print(string.format("[%5d|%-5d|%05d]", 42, 42, 42))  --> [   42|42   |00042]
print(string.format("#%02x%02x%02x", 255, 128, 0)) --> #ff8000
print(string.format("%-8s%8.2f", "tea", 4.5))    --> tea         4.50
print(string.format("%d%% of %s", 80, "disk"))   --> 80% of disk
```

The result of `string.format` is a string like any other, so it can be interpolated: `` `total: $(string.format("%.2f", total))` ``.

### Characters and code points

Each character has a number, its Unicode _code point_. [`string.byte`](/manual/api#string.byte) returns the code point of the character at a position, or of each character in a range of positions. [`string.char`](/manual/api#string.char) builds a string from code points. They are useful for arithmetic on characters, such as shifting a letter or producing the alphabet.

```lus
print(("A"):byte())              --> 65
print(("héllo"):byte(1, 3))      --> 104  233  108
print(string.char(72, 105))      --> Hi
print(string.char(("a"):byte() + 3))  --> d
```

### Why patterns

A program often knows the shape of the text it wants and not the exact characters: a number, a word followed by a colon, a date, everything between two quotes. A _pattern_ is a string that describes such a shape. Four functions take a pattern:

- [`string.find`](/manual/api#string.find) says where the shape occurs.
- [`string.match`](/manual/api#string.match) extracts the text that has the shape, or parts of it.
- [`string.gmatch`](/manual/api#string.gmatch) iterates over every occurrence.
- [`string.gsub`](/manual/api#string.gsub) replaces every occurrence.

One line with a pattern replaces a loop that would examine the text character by character. The following line takes a log entry apart into its time, its level, and its message.

```lus
local entry = "12:30:07 ERROR connection lost"
local time, level, message = entry:match("(%S+) (%u+) (.*)")
print(time, level, message)  --> 12:30:07  ERROR  connection lost
```

In this pattern, `%S+` matches a run of characters other than spaces, `%u+` a run of capital letters, and `.*` the rest of the line. The parentheses mark the parts that `match` returns.

A pattern is made of _items_. Each item matches one character, or a run of characters, and the items match one after another from left to right. The examples below use `string.match`, which returns the first part of the string that the whole pattern matches, or `nil` if no part does.

### Literal text

A letter, a digit, or a space in a pattern matches itself. A pattern made only of such characters finds that exact text.

```lus
print(("status: ready"):match("ready"))  --> ready
print(("status: ready"):match("done"))   --> nil
```

Matching is case sensitive, so `"Ready"` does not match `ready`.

The punctuation characters `( ) . % + - * ? [ ] ^ $` have special meanings in a pattern. A `%` before one of them makes it match itself, as in `%.` for a dot.

### Character classes

A _character class_ is an item that matches any one character of a kind. The dot matches any character at all. The other classes are a `%` followed by a letter.

| Class | Matches one |
| --- | --- |
| `.` | character of any kind |
| `%d` | digit, `0` to `9` |
| `%a` | letter, `a` to `z` and `A` to `Z` |
| `%l` | lowercase letter |
| `%u` | uppercase letter |
| `%w` | letter or digit |
| `%s` | whitespace character: space, tab, or line break |
| `%x` | hexadecimal digit |
| `%p` | punctuation character |
| `%c` | control character |

The capital form of a class matches the opposite: `%D` matches any character that is not a digit, and `%S` matches any character that is not whitespace.

Classes and literal characters combine into a shape. The following pattern describes a time: two digits, a colon, and two digits.

```lus
print(("opens at 09:30 daily"):match("%d%d:%d%d"))  --> 09:30
print(("room B7"):match("%u%d"))                    --> B7
print(("a-b"):match("%a.%a"))                       --> a-b
```

The lettered classes describe ASCII characters, so `%a` matches `e` and does not match `é`. The dot matches any character, including `é`, and a [set](#sets) may list characters outside ASCII.

### Sets

A _set_ is a class that the pattern defines itself, by listing characters between square brackets. It matches any one of them. Inside a set, two characters joined by `-` form a range, and the `%` classes may appear.

```lus
print(("grey"):match("gr[ae]y"), ("gray"):match("gr[ae]y"))  --> grey  gray
print(("id: x9"):match("[a-z][0-9]"))                        --> x9
print(("file_name.txt"):match("[%w_]+"))                     --> file_name
```

The `+` after the set in the last line repeats it, so `[%w_]+` matches a run of one or more letters, digits, and underscores.

A set that starts with `^` matches any character that is not listed. This is the usual way to say "everything up to a delimiter".

```lus
print(("name=Ada;age=36"):match("[^;]+"))  --> name=Ada
print(("path/to/file"):match("[^/]+"))     --> path
```

### Repetition

A repetition character after an item says how many times the item may match in a row. It applies to the single item before it: a literal character, a class, or a set.

| Item | Matches |
| --- | --- |
| `x+` | one or more `x`, as many as possible |
| `x*` | zero or more `x`, as many as possible |
| `x-` | zero or more `x`, as few as possible |
| `x?` | zero or one `x` |

`+` is the one to use for "a run of": `%d+` is a whole number, `%a+` is a word, and `%s+` is a stretch of whitespace. `*` is the same but also accepts an empty run, which fits optional whitespace. `?` makes one item optional.

```lus
print(("order 1042 shipped"):match("%d+"))      --> 1042
print(("x =   5"):match("x%s*=%s*%d"))          --> x =   5
print(("x=5"):match("x%s*=%s*%d"))              --> x=5
print(("https://lus.dev"):match("https?://"))   --> https://
print(("-12 degrees"):match("-?%d+"))           --> -12
```

`+` and `*` are _greedy_: they take as many characters as they can while the rest of the pattern still matches. `-` is _lazy_: it takes as few as it can. The difference shows when the text contains the closing delimiter more than once. In the following example, the greedy form runs to the last `>` and the lazy form stops at the first.

```lus
local html = "<b>bold</b> and <i>italic</i>"

print(html:match("<.*>"))  --> <b>bold</b> and <i>italic</i>
print(html:match("<.->"))  --> <b>
```

Use `.-` followed by a delimiter to match up to the nearest occurrence of that delimiter.

### Anchors

A pattern normally matches anywhere in the string. A `^` at the start of a pattern requires the match to begin at the start of the string, and a `$` at the end of a pattern requires the match to finish at the end of the string. With both, the pattern must describe the whole string, which is how a program validates input.

```lus
print(("item 42"):match("%d+"))        --> 42
print(("item 42"):match("^%d+"))       --> nil
print(("42 items"):match("^%d+"))      --> 42
print(("42 items"):match("^%d+$"))     --> nil
print(("42"):match("^%d+$"))           --> 42
```

The following function accepts a string only if it is a valid identifier: a letter or underscore, followed by any number of letters, digits, and underscores. The anchors reject strings that only contain an identifier somewhere.

```lus
local function is_identifier(s)
    return s:match("^[%a_][%w_]*$") ~= nil
end

print(is_identifier("user_name"))   --> true
print(is_identifier("_tmp2"))       --> true
print(is_identifier("2fast"))       --> false
print(is_identifier("first name"))  --> false
```

### Captures

Matching a shape is half the work. A program usually wants specific parts of the match: the key and the value, the year and the month. Parentheses around part of a pattern mark a _capture_. When a pattern has captures, `string.match` returns the text of each capture, in order, in place of the whole match.

```lus
local key, value = ("timeout = 30"):match("(%w+)%s*=%s*(%w+)")
print(key, value)  --> timeout  30
```

The parentheses do not match any character themselves. The pattern above matches the same text as `%w+%s*=%s*%w+`, and the parentheses select which parts come back.

A date has three parts, and one pattern captures all of them. The `-` between the numbers is written `%-` so that it means a literal hyphen. Captures are always strings, so `tonumber` converts them when the program needs numbers.

```lus
local year, month, day = ("2026-03-04"):match("^(%d%d%d%d)%-(%d%d)%-(%d%d)$")
print(year, month, day)                  --> 2026  03  04
print(tonumber(month) + 1)               --> 4

print(("2026-3-4"):match("^(%d%d%d%d)%-(%d%d)%-(%d%d)$"))  --> nil
```

If the pattern does not match, `string.match` returns a single `nil`, so every variable is `nil`. An [`if` that declares a variable](/manual/guide#conditions-that-declare-variables) tests the match and uses the captures in one step.

```lus
local line = "Content-Length: 348"
if name, value = line:match("^([%w%-]+):%s*(.*)$") then
    print(name, value)  --> Content-Length  348
end
```

An empty pair of parentheses is a _position capture_. It captures the position in the string where the match has arrived, as a number. This tells a program where something was found, for example to cut the string there.

```lus
local text = "key:value"
local stop = text:match(":()")
print(stop)             --> 5
print(text:sub(stop))   --> value

print(("hello world"):match("()wor()"))  --> 7  10
```

Inside a pattern, `%1` matches another copy of the text that the first capture matched, `%2` the second, and so on. This finds a repeated word, or a closing quote that equals the opening quote.

```lus
print(("it was the the best"):match("(%a+) %1"))        --> the
print(([[say "it's fine" now]]):match("([\"'])(.-)%1")) --> "  it's fine
```

### Finding with `string.find`

[`string.find`](/manual/api#string.find) returns the positions of the first and last character of the first match, or `nil` when the pattern does not occur. It answers "does this text contain the shape" and "where".

```lus
local s = "error at line 42"
print(s:find("line"))    --> 10  13
print(s:find("%d+"))     --> 15  16
print(s:find("warning")) --> nil

if s:find("^error") then
    print("failed")      --> failed
end
```

A third argument sets the position where the search starts, as the [`while` loop](#while-loops) that counts commas shows.

To search for literal text that contains special characters, pass `true` as the fourth argument. The search then treats the pattern as plain text. The third argument must be present in this form, and `1` searches from the start.

```lus
local price = "total (USD): 3.50"

print(price:find("(USD)", 1, true))  --> 7  11
print(price:find(".", 1, true))      --> 15  15
print(price:find("."))               --> 1  1
```

The last line shows the pattern meaning of the dot, which matches the first character of any string. Use the plain form whenever the text to find comes from a user or a file.

### Extracting with `string.match`

[`string.match`](/manual/api#string.match) returns the captures of the first match, or the whole match when the pattern has no captures, or `nil` when the pattern does not match. Like `string.find`, it accepts a starting position as its third argument.

The following example takes a web address apart. The scheme is a run of letters, the host is everything up to the next slash, and the path is the rest.

```lus
local url = "https://lus.dev/manual/guide"
local scheme, host, path = url:match("^(%a+)://([^/]+)(.*)$")
print(scheme, host, path)  --> https  lus.dev  /manual/guide
```

### Every match with `string.gmatch`

[`string.gmatch`](/manual/api#string.gmatch) returns an [iterator](/manual/guide#iteration) that produces each match of a pattern in turn, from left to right. A `for` loop over it visits every occurrence. Each pass receives the captures, or the whole match when the pattern has no captures.

The pattern `%S+` matches a run of characters that are not whitespace, so it splits a string into words however many spaces separate them.

```lus
local words = {}
for word in ("  the quick   brown fox "):gmatch("%S+") do
    words[#words + 1] = word
end
print(#words, string.join(words, ","))  --> 4  the,quick,brown,fox
```

Extracting numbers from text is the same loop with a different pattern. The following example adds up the durations in a line of timings.

```lus
local timings = "GET /a 12ms, GET /b 250ms, GET /c 31ms"
local total = 0
for duration in timings:gmatch("(%d+)ms") do
    total = total + tonumber(duration)
end
print(total)  --> 293
```

With several captures, each pass receives several values. The following example reads a configuration text in `key = value` form into a table. The outer loop visits the lines, and the pattern for one line skips surrounding spaces. A comment line has no `=`, so the pattern does not match it and `key` is `nil`.

```lus
local text = [[
# server settings
host = example.org
port = 8080

debug=true
]]

local config = {}
for line in text:gmatch("[^\n]+") do
    local key, value = line:match("^%s*([%w_]+)%s*=%s*(.-)%s*$")
    if key then
        config[key] = value
    end
end

print(config.host, config.port, config.debug)  --> example.org  8080  true
```

The line pattern reads as follows: optional spaces, a captured name of letters, digits, and underscores, an equals sign with optional spaces around it, a captured value that is as short as possible, and optional spaces before the end. The lazy `.-` leaves trailing spaces to the `%s*` after it, which trims the value.

In `string.gmatch`, a `^` at the start of the pattern is a literal character, because an anchored pattern could match only once.

### Replacing with `string.gsub`

[`string.gsub(s, pattern, replacement)`](/manual/api#string.gsub) returns a copy of `s` in which every match of the pattern is replaced. It returns a second result, the number of matches. The replacement may be a string, a table, or a function.

A replacement string is inserted in place of each match. Inside it, `%1` to `%9` stand for the captures and `%0` stands for the whole match, so the replacement can reuse and reorder parts of what was matched. A literal percent sign in the replacement is written `%%`.

```lus
print(("hello world"):gsub("o", "0"))            --> hell0 w0rld  2
print(("a  b    c"):gsub("%s+", " "))            --> a b c  2
print(("2026-03-04"):gsub("(%d+)%-(%d+)%-(%d+)", "%3/%2/%1"))  --> 04/03/2026  1
print(("ada lin"):gsub("%a+", "<%0>"))           --> <ada> <lin>  2
```

A replacement table is a lookup. Each match, or its first capture if the pattern has one, is looked up as a key, and the value found replaces the match. This fills a template with `$name` placeholders in one call. The `$` is a special character, so the pattern writes it as `%$`.

```lus
local template = "Dear $name, your order $id ships on $day."
local values = { name = "Ada", id = 1042, day = "Friday" }

local letter = template:gsub("%$(%w+)", values)
print(letter)  --> Dear Ada, your order 1042 ships on Friday.
```

A replacement function is called with the captures of each match, and its result replaces the match. This is for replacements that must be computed. The following example fills the same kind of template and marks the placeholders that have no value.

```lus
local values = { name = "Ada" }

local letter = ("Hi $name, see you $day."):gsub("%$(%w+)", function(key)
    return values[key] or `<missing $key>`
end)
print(letter)  --> Hi Ada, see you <missing day>.
```

The next example decodes the `%20` escapes of a web address. The pattern matches a percent sign followed by two hexadecimal digits, and the function converts the digits to the character with that code point.

```lus
local encoded = "tea%20%26%20milk%3F"
local decoded = encoded:gsub("%%(%x%x)", function(hex)
    return string.char(tonumber(hex, 16))
end)
print(decoded)  --> tea & milk?
```

When the table has no value for a match, or the function returns `nil` or `false`, the match stays as it was.

A fourth argument limits the number of replacements, so `s:gsub(" ", "", 1)` removes only the first space.

Because `gsub` returns two results, a call that is the last argument of another call passes both. Parentheses around the call keep the string only.

```lus
print(("a-b"):gsub("-", "+"))    --> a+b  1
print((("a-b"):gsub("-", "+")))  --> a+b
```

### Balanced pairs and word boundaries

Two items handle shapes that repetition cannot describe.

`%b` followed by two characters matches a balanced pair: text that starts with the first character, ends with the second, and contains equally many of each in between. `%b()` matches a parenthesized expression including the parentheses nested inside it, where `%(.-%)` would stop at the first closing parenthesis.

```lus
local code = "total = max(a, min(b, c)) + 1"

print(code:match("%(.-%)"))        --> (a, min(b, c)
print(code:match("%b()"))          --> (a, min(b, c))

local name, arguments = code:match("(%a+)(%b())")
print(name, arguments:sub(2, -2))  --> max  a, min(b, c)
```

`%b` works with any two characters, such as `%b[]`, `%b{}`, and `%b<>`.

`%f` followed by a set matches a _boundary_: a position where the character before is outside the set and the character after is inside it. It matches a position and no characters. With `%f[%w]` for the start of a word and `%f[%W]` for the end of one, a pattern matches whole words only.

```lus
print(("cat concat cat"):gsub("cat", "dog"))                  --> dog condog dog  3
print(("cat concat cat"):gsub("%f[%w]cat%f[%W]", "dog"))      --> dog concat dog  2
print(("the quick fox"):gsub("%f[%w]%l", string.upper))       --> The Quick Fox  3
```

The last line capitalizes each word. The pattern matches a lowercase letter at the start of a word, and `string.upper` is the replacement function.

### Escaping

A `%` before a punctuation character makes it literal. `%.` matches a dot, `%(` matches an opening parenthesis, and `%%` matches a percent sign. Escaping a punctuation character that has no special meaning is allowed, so the safe rule is to escape every punctuation character that must match itself.

```lus
print(("version 2.10.3"):match("%d+%.%d+%.%d+"))   --> 2.10.3
print(("50% off (today)"):match("%d+%%"))          --> 50%
print(("50% off (today)"):match("%((%a+)%)"))      --> today
```

When the text to find is not known in advance, a program can escape it before placing it in a pattern. The following function puts a `%` before every punctuation character.

```lus
local function escape(text)
    return (text:gsub("%p", "%%%0"))
end

local name = "report (v1.2).txt"
print(escape(name))                                  --> report %(v1%.2%)%.txt
print(("open report (v1.2).txt now"):match(escape(name)))  --> report (v1.2).txt
```

For a plain search, the fourth argument of `string.find` does the same with less work.

### Worked examples

#### A log line

Each field is described by what ends it. The date and the time are runs without spaces, the level is uppercase letters, the source is a word before a colon, and the message is the rest.

```lus
local line = "2026-03-04 12:30:07 ERROR db: connection lost (attempt 3)"

local date, time, level, source, message =
    line:match("^(%S+) (%S+) (%u+) (%w+): (.*)$")
print(date, time, level)  --> 2026-03-04  12:30:07  ERROR
print(source, message)    --> db  connection lost (attempt 3)

print(tonumber(message:match("attempt (%d+)")))  --> 3
```

#### Numbers in text

A number here is an optional minus sign, digits, and optionally a dot with more digits. `%.?%d*` accepts both `3` and `2.5`.

```lus
local note = "Order 1042: 3 items, 2.5 kg, total 59.90 EUR"
local numbers = {}
for number in note:gmatch("-?%d+%.?%d*") do
    numbers[#numbers + 1] = tonumber(number)
end
print(string.join(numbers, " "))  --> 1042 3 2.5 59.9
```

#### Fields with a varying delimiter

`string.split` needs one exact delimiter. A set that excludes the delimiters accepts any mix of commas, semicolons, and spaces between the fields.

```lus
local tags = {}
for tag in ("lus, lua;zig  wasm"):gmatch("[^,;%s]+") do
    tags[#tags + 1] = tag
end
print(#tags, string.join(tags, "|"))  --> 4  lus|lua|zig|wasm
```

#### Converting a naming style

The pattern finds each place where a lowercase letter meets an uppercase letter and puts an underscore between the two captures.

```lus
local snake = ("maxRetryCount"):gsub("(%l)(%u)", "%1_%2"):lower()
print(snake)  --> max_retry_count
```

#### Validating input

Anchors on both ends make the pattern describe the whole string. The following function accepts a time such as `09:30` and checks the ranges with ordinary comparisons, which a pattern cannot express.

```lus
local function parse_time(s)
    local hours, minutes = s:match("^(%d%d):(%d%d)$")
    if not hours then
        return nil
    end
    hours, minutes = tonumber(hours), tonumber(minutes)
    if hours > 23 or minutes > 59 then
        return nil
    end
    return hours, minutes
end

print(parse_time("09:30"))   --> 9  30
print(parse_time("9:30"))    --> nil
print(parse_time("25:00"))   --> nil
```

#### A query string

Two captures per match turn `key=value` pairs into a table.

```lus
local query = "page=2&sort=name&desc"
local params = {}
for key, value in query:gmatch("([^&=]+)=([^&=]*)") do
    params[key] = value
end
print(params.page, params.sort, params.desc)  --> 2  name  nil
```

### The limits of patterns

Patterns are small on purpose. They cover the shapes that most programs need, and a few shapes call for other tools.

- Alternatives between whole words, such as `cat` or `dog`, take several patterns tried in turn. A set covers alternatives between single characters, as in `[Cc]at`.
- A repetition character applies to one character, class, or set, so a sequence such as `ab`, or a capture, repeats only through a loop.
- A count such as "exactly four digits" is written by repeating the item, as in `%d%d%d%d`, or with [`string.rep`](/manual/api#string.rep) for larger counts: `("%d"):rep(4)`.
- Matching without regard to case works on text lowered with `string.lower`, or with sets such as `[Yy]es`.
- The classes `%a`, `%l`, `%u`, and `%w` describe ASCII letters, and a set such as `[%aéèà]` extends one by hand.
- Formats with real nesting, such as JSON or a programming language, need a parser. `%b` handles one kind of balanced pair.

The following example handles alternatives by trying patterns in order. Each pattern recognizes one way of writing a date, and the first that matches decides the result.

```lus
local function parse_date(s)
    local year, month, day = s:match("^(%d%d%d%d)%-(%d%d)%-(%d%d)$")
    if not year then
        day, month, year = s:match("^(%d%d)/(%d%d)/(%d%d%d%d)$")
    end
    if not year then
        return nil
    end
    return tonumber(year), tonumber(month), tonumber(day)
end

print(parse_date("2026-03-04"))  --> 2026  3  4
print(parse_date("04/03/2026"))  --> 2026  3  4
print(parse_date("March 4"))     --> nil
```

For the common data formats, the standard library has parsers that handle quoting, escapes, and nesting correctly. [`fromjson`](/manual/api#fromjson) reads JSON and [`fromcsv`](/manual/api#fromcsv) reads CSV, and [Data formats](/manual/data) describes both. Use them for those formats in place of patterns.

### Text and bytes

A string is text. It always holds whole Unicode characters, and every string function counts in characters. Data that is not text, such as an image, a compressed file, or a binary network protocol, belongs in a [vector](#vector), a buffer of bytes.

## Errors

An _error_ stops the work in progress when that work cannot continue: a file is missing, an argument has the wrong type, or the input is malformed. Lus raises errors itself, for example when a program adds a number to `nil`, and a program raises its own with [`error`](/manual/api#error). An error travels up through the calling functions until a `catch` captures it.

### Raising errors

A function raises an error when it cannot do what its caller asked. The argument of `error` is the _error object_, the value that describes what went wrong. The function below refuses a withdrawal that the balance cannot cover.

```lus nocheck
local function withdraw(balance, amount)
    if amount > balance then
        error("insufficient funds")
    end
    return balance - amount
end

print(withdraw(100, 30))    --> 70
print(withdraw(100, 300))
print("this line never runs")
```

The second call raises an error that nothing captures, which ends the program. The `lus` command prints the error object and the chain of calls that led to it on standard error, then exits with status 1.

```text
lus: bank.lus:3: insufficient funds
stack traceback:
        [C]: in global 'error'
        bank.lus:3: in local 'withdraw'
        bank.lus:8: in main chunk
        [C]: in ?
```

When the error object is a string, `error` puts the file name and the line number in front of it, as in `bank.lus:3:` above. That position helps the programmer who reads the message. A message meant for the user of the program reads better without it, and a second argument of `0` leaves it out, as in `error("insufficient funds", 0)`.

[`assert`](/manual/api#assert) is a short way to raise an error when a condition does not hold. It returns its first argument if that argument is truthy. Otherwise it raises an error with its second argument as the message.

```lus
local function average(values)
    assert(#values > 0, "average needs at least one value")
    local sum = 0
    for _, value in ipairs(values) do
        sum = sum + value
    end
    return sum / #values
end

print(average({ 4, 6, 8 }))   --> 6.0
```

### Catching errors

Some failures are expected, and the program should deal with them and continue. Text that comes from outside the program is the usual case: [`fromjson`](/manual/api#fromjson) raises an error when the text is not valid JSON, and a program that reads a settings file should report the problem to the user. Write `catch` in front of an expression to capture any error raised while that expression is evaluated.

A `catch` expression always produces a status first. If the expression succeeds, `catch` produces `true` followed by the values of the expression. If the expression raises an error, `catch` produces `false` followed by the error object.

```lus
local ok, settings = catch fromjson('{"port": 8080}')
print(ok, settings.port)   --> true  8080

local ok, message = catch fromjson('{"port": ')
print(ok)        --> false
print(message)   --> JSON parse error at position 10: unexpected end of input
```

The program is still running after the second `catch`, and it holds the message in a variable. It can print the message, fall back to default settings, or ask the user for another file.

`catch` protects everything to its right, and that expression can be any expression. The next example protects a division, which raises an error when an integer is divided by zero.

```lus
local total, count = 120, 0
local ok, share = catch total // count
print(ok)   --> false
```

A [condition that declares variables](/manual/guide#conditions-that-declare-variables) checks the status and names the result in one line. The branch runs when every declared variable is truthy, so it runs when the expression succeeded and produced a truthy value.

```lus
local function parse_port(text)
    local port = math.tointeger(tonumber(text))
    if not port or port < 1 or port > 65535 then
        error(`invalid port: $text`, 0)
    end
    return port
end

if ok, port = catch parse_port("8080") then
    print(`listening on port $port`)   --> listening on port 8080
end

if ok, port = catch parse_port("http") then
    print(`listening on port $port`)
else
    print(port)   --> invalid port: http
end
```

`math.tointeger` returns a whole number as an integer and `nil` for anything else, so `parse_port` rejects `"80.5"` as well as `"http"`. When the call fails, `port` holds the second value of the `catch`, the error message, which is what the `else` branch prints.

### Error objects

A string is enough when a person reads the error. Code that has to decide what to do next needs more: it should retry after a timeout, ask again after a wrong password, and stop after anything else. Comparing message text is fragile, because rewording a message breaks the comparison. The error object can be any value, so a function can raise a table whose fields the capturing code inspects.

```lus
local function fetch_page(attempt)
    if attempt < 3 then
        error({ code = "timeout", retry_after = 2 })
    end
    return "<html>...</html>"
end

local page
for attempt = 1, 5 do
    local ok, result = catch fetch_page(attempt)
    if ok then
        page = result
        break
    elseif result.code == "timeout" then
        print(`attempt $attempt timed out, waiting $(result.retry_after) seconds`)
    else
        error(result)
    end
end
print(page)
--> attempt 1 timed out, waiting 2 seconds
--> attempt 2 timed out, waiting 2 seconds
--> <html>...</html>
```

The last branch passes an error that the loop cannot handle to `error` again, so that a `catch` further up the chain of calls receives the same table. `error` adds a position only to strings, so the table arrives unchanged.

### Catch handlers

A program that raises tables still receives strings from the runtime and from the standard library, such as the JSON message above. Code that inspects `err.code` would then need a type check after every `catch`. A _catch handler_ removes that repetition. Write a function in brackets after `catch`. When the expression fails, Lus calls the function with the error object and uses its result as the error object.

```lus
local function as_table(err)
    if type(err) == "table" then
        return err
    end
    return { code = "internal", message = tostring(err) }
end

local ok, err = catch[as_table] fromjson("[1, 2")
print(ok, err.code)   --> false  internal
print(err.message)    --> JSON parse error at position 6: expected ']' after array element

local ok, err = catch[as_table] error({ code = "timeout" })
print(ok, err.code)   --> false  timeout
```

Every `catch[as_table]` in the program now yields an error object with a `code` field, whatever raised the error. The handler runs only on failure. A successful expression produces `true` and its values as usual.

### The catch statement

Some operations are worth attempting and not worth reporting: removing a temporary file that may already be gone, closing a connection that the other side may have closed, or sending a usage statistic. A `catch` at the start of a statement runs its expression, discards the results, and discards any error.

```lus
local listeners = {
    function(event) print("saved", event) end,
    function(event) error("listener failed") end,
    function(event) print("logged", event) end,
}

for _, listener in ipairs(listeners) do
    catch listener("upload")
end
--> saved  upload
--> logged  upload
```

One failing listener does not stop the others. Use the statement form only when the program has nothing useful to do with the error, because it leaves no trace of what failed.

### Warnings

A _warning_ reports a problem that does not prevent the program from continuing, such as a deprecated setting or a slow response. [`warn`](/manual/api#warn) joins its arguments into one message and writes it to standard error with the prefix `Lus warning:`. Execution continues with the next statement.

Warnings are off when a program starts, so that a finished program stays quiet for its users. The `-W` option of the `lus` command turns them on for one run, and a program turns them on and off itself with the control messages `"@on"` and `"@off"`.

```lus
warn("@on")
warn("the option 'colour' is deprecated, use 'color'")
--> Lus warning: the option 'colour' is deprecated, use 'color'
warn("@off")
warn("this message is dropped")
```

## Do expressions

Some values take several statements to compute: a choice among several cases, a loop, or a step that needs a temporary variable. A _do expression_ is a `do ... end` block written where a value is expected. The block runs like any other block, and a `provide` statement inside it ends the block and gives the expression its value.

A do expression keeps a computation in the place where its value is used.

### Constants computed by statements

A [`<const>`](/manual/guide#constants) variable receives its value in its declaration and never changes. When the value depends on an `if`, the form without a do expression has to give up the `<const>`, because the variable is declared first and assigned in a branch afterwards. The block below decides whether a program shows a progress bar. It leaves `show_progress` open to accidental reassignment for the rest of the program.

```lus
local mode = "quiet"
local is_terminal = true

local show_progress
if mode == "quiet" then
    show_progress = false
elseif mode == "verbose" then
    show_progress = true
else
    show_progress = is_terminal
end
print(show_progress)   --> false
```

The [`and` and `or` choice](#logical-operators) does not fit here, because one of the values is `false`. In `mode == "quiet" and false or ...`, the `false` makes `or` continue to the next case, as [Logical operators](#logical-operators) explains. A do expression computes the value inside the declaration, so the variable can be `<const>`. Each `provide` ends the block at once, which is why the branches need no `else`.

```lus
local mode = "quiet"
local is_terminal = true

local show_progress <const> = do
    if mode == "quiet" then
        provide false
    end
    if mode == "verbose" then
        provide true
    end
    provide is_terminal
end
print(show_progress)   --> false
```

The same holds for a value that a loop builds. The following constant maps each column name of a CSV header to its position, which no library function computes. The variable `index` that the loop fills is out of scope after the `end`, so the rest of the program sees only the finished constant.

```lus
local header = { "name", "email", "city" }

local column <const> = do
    local index = {}
    for position, name in ipairs(header) do
        index[name] = position
    end
    provide index
end
print(column.email, column.city)   --> 2  3
```

### The first match in a loop

A search through a list ends as soon as it finds what it is looking for. A `provide` inside a loop leaves the loop and the whole do expression in one step. A block that reaches its `end` without running a `provide` produces `nil`, which is the result a search that found nothing should give.

```lus
local users = {
    { name = "ada", admin = false },
    { name = "grace", admin = true },
    { name = "linus", admin = true },
}

local admin = do
    for _, user in ipairs(users) do
        if user.admin then
            provide user
        end
    end
end
print(admin.name)   --> grace

local guest = do
    for _, user in ipairs(users) do
        if user.name == "guest" then
            provide user
        end
    end
end
print(guest)   --> nil
```

Without a do expression, the search needs a variable declared before the loop, an assignment inside it, and a `break` after the assignment. The do expression states the same search as one declaration.

### Several statements under one catch

`catch` protects one expression. That fits when the risky work is one call, as in `catch fromjson(text)`. Often the risky work is a sequence of statements, and an error in any of them should end up in the same place. Loading settings is an example: the text has to parse, a field has to have the right type, and another field has to exist. No single function call covers the three steps. Using `catch f()` would mean moving the steps into a new function that exists only to be called on the next line.

`catch do ... end` protects the statements where they stand. In the example, `math.type` returns `"integer"` only for a whole number stored as an integer. The values that `provide` lists follow the `true` status, in the same way that the results of a call do.

```lus
local function load_settings(text)
    local ok, port, host_count = catch do
        local settings = fromjson(text)
        if math.type(settings.port) ~= "integer" then
            error("port must be an integer", 0)
        end
        provide settings.port, #settings.hosts
    end
    print(ok, port, host_count)
end

load_settings('{"port": 8080, "hosts": ["a", "b"]}')   --> true  8080  2
load_settings('{"port": "eighty", "hosts": []}')       --> false  port must be an integer  nil
load_settings('{"port": ')
--> false  JSON parse error at position 10: unexpected end of input  nil
```

The first call succeeds. The second fails in the type check and the third fails in the parser, and both failures arrive at the same `catch` as `false` and an error object. The statements inside the block read the parameter `text` directly, which a separate function would need to receive as an argument.

### Fields in table constructors

A field whose value needs statements normally forces a choice. Either the value is computed into a local variable before the constructor, away from the field it belongs to, or the field is assigned after the table exists. A do expression keeps the computation in the field. The field `missing` below names the first item of an order that is out of stock, and the search stops at that item.

```lus
local stock = { tea = 10, mug = 0, spoon = 4 }
local orders = {
    { id = 1, items = { "tea", "spoon" } },
    { id = 2, items = { "tea", "mug", "spoon" } },
}

local invoices = {}
for _, order in ipairs(orders) do
    table.insert(invoices, {
        id = order.id,
        count = #order.items,
        missing = do
            for _, item in ipairs(order.items) do
                if stock[item] == 0 then
                    provide item
                end
            end
        end,
    })
end

for _, invoice in ipairs(invoices) do
    print(invoice.id, invoice.count, invoice.missing)
end
--> 1  2  nil
--> 2  3  mug
```

A do expression can stand anywhere an expression can, so the same technique works for a function argument.

`provide` belongs to the nearest enclosing do expression. A `provide` outside every do expression is a compile error, and so is a statement that follows a `provide` in the same block, because that statement could never run.

## Metatables and objects

Tables come with a fixed set of operations: reading and writing fields, measuring the length, and comparing two tables for identity. A _metatable_ is a second table, attached to the first, that tells Lus what to do for operations the table does not define by itself. With a metatable, a missing field can fall back to a default, `a + b` can add two points, `print` can show a readable form, and a block can release a resource when it ends. Each of these behaviors is one field of the metatable with a reserved name that starts with two underscores, such as `__index` or `__add`. These fields are called _metamethods_.

[`setmetatable`](/manual/api#setmetatable) attaches a metatable to a table and returns the table. [`getmetatable`](/manual/api#getmetatable) returns the metatable of a value. Several tables can share one metatable, which is how every object of one kind gets the same behavior.

### Defaults and shared methods

Reading a field that a table does not have gives `nil`. The `__index` metamethod changes that: when the field is missing, Lus looks for it in the table that `__index` names. This gives a table default values that it does not store itself.

```lus
local defaults = { color = "black", width = 1 }

local pen = setmetatable({ width = 3 }, { __index = defaults })
print(pen.width)   --> 3
print(pen.color)   --> black
```

The table `pen` has its own `width`, so `pen.width` reads 3. It has no `color`, so the read continues in `defaults`. Writing `pen.color = "red"` stores the field in `pen` itself and leaves `defaults` unchanged.

`__index` can also be a function, which Lus calls with the table and the missing key. The result of the function is the result of the read. The next example counts words with a table whose missing entries read as `0`, so the loop needs no check for the first occurrence.

```lus
local counts = setmetatable({}, {
    __index = function(t, key)
        return 0
    end,
})

for _, word in ipairs({ "pear", "fig", "pear" }) do
    counts[word] = counts[word] + 1
end
print(counts.pear, counts.fig, counts.plum)   --> 2  1  0
```

The same lookup shares functions among many tables. A [method call](/manual/guide#methods) such as `stack:push(1)` reads the field `push` from `stack`, and `__index` lets every stack find that one function in a common table. The objects then store only their data.

```lus
local Stack = {}
Stack.__index = Stack

function Stack.new()
    return setmetatable({ items = {} }, Stack)
end

function Stack:push(value)
    table.insert(self.items, value)
end

function Stack:pop()
    return table.remove(self.items)
end

local stack = Stack.new()
stack:push("a")
stack:push("b")
print(stack:pop(), #stack.items)   --> b  1
```

Here `Stack` plays two roles. It is the metatable of every stack, and its `__index` field points back at itself, so it is also the table where missing fields are looked up. The matching metamethod for writes is `__newindex`, which Lus calls with the table, the key, and the value when a program assigns to a field that the table does not have.

### Operator metamethods

An operator applied to a table raises an error unless the metatable defines the operation. Defining it lets values such as points, money amounts, or durations use the same notation as numbers. Each arithmetic operator has a metamethod that receives the two operands and returns the result: `__add` for `+`, `__sub` for `-`, `__mul` for `*`, `__div` for `/`, `__mod` for `%`, `__pow` for `^`, `__idiv` for `//`, and `__unm` for the negation `-x`. `__concat` defines `..` and `__len` defines `#`.

```lus
local Point = {}
Point.__index = Point

local function point(x, y)
    return setmetatable({ x = x, y = y }, Point)
end

function Point.__add(a, b)
    return point(a.x + b.x, a.y + b.y)
end

function Point.__mul(a, b)
    if type(a) == "number" then
        return point(a * b.x, a * b.y)
    end
    return point(a.x * b, a.y * b)
end

function Point.__unm(a)
    return point(-a.x, -a.y)
end

local sum = point(1, 2) + point(3, 4)
print(sum.x, sum.y)   --> 4  6

local scaled = 2 * point(1, 2)
print(scaled.x, scaled.y)   --> 2  4

local opposite = -point(1, 2)
print(opposite.x, opposite.y)   --> -1  -2
```

Lus calls the metamethod when either operand has one. That is why `__mul` checks which operand is the number: both `2 * p` and `p * 2` reach the same function.

### Equality and ordering

Two tables are equal only when they are the same table, so two points with the same coordinates compare as different. The `__eq` metamethod defines what equality means for a kind of object. `__lt` defines `<` and `__le` defines `<=`. Lus evaluates `a > b` as `b < a` and `a >= b` as `b <= a`, so the two metamethods cover all four ordering operators.

```lus
local Version = {}
Version.__index = Version

local function version(major, minor)
    return setmetatable({ major = major, minor = minor }, Version)
end

function Version.__eq(a, b)
    return a.major == b.major and a.minor == b.minor
end

function Version.__lt(a, b)
    if a.major ~= b.major then
        return a.major < b.major
    end
    return a.minor < b.minor
end

function Version.__le(a, b)
    return a == b or a < b
end

print(version(2, 0) == version(2, 0))   --> true
print(version(1, 9) < version(2, 0))    --> true
print(version(2, 1) >= version(2, 0))   --> true

local releases = { version(2, 0), version(1, 4), version(1, 10) }
table.sort(releases)
print(releases[1].minor, releases[2].minor, releases[3].minor)   --> 4  10  0
```

[`table.sort`](/manual/api#table.sort) compares elements with `<`, so a list of objects with `__lt` sorts without a comparison function. Lus calls `__eq` only when both operands are tables, which means that a version never equals a number or a string.

### String conversion

`print` shows a table as `table:` followed by an address, which says nothing about its contents. The `__tostring` metamethod returns the text that represents the object. [`tostring`](/manual/api#tostring), `print`, and string interpolation all use it.

```lus
local Point = {}
Point.__index = Point

function Point.__tostring(point)
    return `($(point.x), $(point.y))`
end

local origin = setmetatable({ x = 0, y = 0 }, Point)
print(origin)                  --> (0, 0)
print(`starting at $origin`)   --> starting at (0, 0)
```

### Callable tables

The `__call` metamethod lets a table be called like a function. Lus passes the table itself first, followed by the arguments of the call. This suits an object that has one main operation and also carries settings that the program reads and changes by name. Code that expects a function accepts the object, and the settings stay visible as fields, where a function that remembers its local variables would keep them out of reach.

The `rule` below builds a check for names. It is called like a function, and its minimum length is a field that the program can change later.

```lus
local Rule = {}
Rule.__index = Rule

function Rule.__call(self, text)
    return #text >= self.min_length and not text:find("%s")
end

local function rule(min_length)
    return setmetatable({ min_length = min_length }, Rule)
end

local function count_valid(list, is_valid)
    local count = 0
    for _, item in ipairs(list) do
        if is_valid(item) then
            count = count + 1
        end
    end
    return count
end

local valid_name = rule(5)
local names = { "ada", "grace", "lin", "barbara" }
print(valid_name("grace"), valid_name("ada"))   --> true  false
print(count_valid(names, valid_name))           --> 2

valid_name.min_length = 3
print(count_valid(names, valid_name))           --> 4
```

Functions of the standard library that take a function, such as `table.filter`, require a real function and reject a callable table. A callable table fits functions that the program writes itself, such as `count_valid`.

### Resources that close themselves

A program that opens a file, takes a lock, or starts a transaction has to release it later, on every path out of the code that uses it. Those paths include the normal end, an early `return`, a `break`, and an error raised several calls deep. Releasing by hand on each path is easy to forget.

The `<close>` attribute ties the release to the scope of a variable. When a `<close>` variable goes out of scope for any reason, Lus calls the `__close` metamethod of its value. Files opened with `io.open` have this metamethod, so a file declared `<close>` is closed when its block ends, as [`io`](#io) shows.

A table gets the same treatment by defining `__close`. Lus calls it with the value and with the error object that is ending the block, or `nil` when the block ends normally. The transaction below uses that second argument to decide between committing and rolling back.

```lus
local log = {}

local function transaction()
    table.insert(log, "begin")
    return setmetatable({}, {
        __close = function(self, err)
            table.insert(log, err and "rollback" or "commit")
        end,
    })
end

do
    local tx <close> = transaction()
    table.insert(log, "insert row")
end

catch do
    local tx <close> = transaction()
    error("constraint failed")
end

print(table.concat(log, ", "))   --> begin, insert row, commit, begin, rollback
```

A `<close>` variable is also constant, so it holds the same value until its scope ends. When one block declares several `<close>` variables, Lus closes them in reverse order of declaration, which releases a resource before the resources it depends on. The value must have a `__close` metamethod or be `nil` or `false`. A `nil` or `false` value is left alone, so the result of an operation that returns `nil` on failure can go straight into a `<close>` variable.

### Classes

A _class_ describes a kind of object: the data each object holds and the methods all of them share. In Lus a class is one table that holds the methods and serves as the metatable of every object, together with a function that creates the objects, as `Stack` does. The `Account` class below also checks its input in the constructor and describes each account.

```lus
local Account = {}
Account.__index = Account

function Account.new(owner, balance)
    assert(balance >= 0, "the opening balance must not be negative")
    return setmetatable({ owner = owner, balance = balance }, Account)
end

function Account:deposit(amount)
    self.balance = self.balance + amount
end

function Account:describe()
    return `$(self.owner) has $(self.balance)`
end

local account = Account.new("Ada", 100)
account:deposit(50)
print(account:describe())   --> Ada has 150
```

Each call of `Account.new` returns a new table with its own `owner` and `balance`. The methods exist once, in `Account`. `getmetatable(account) == Account` is true for every account, which gives a program a way to test whether a value is an account.

### Inheritance

A class _inherits_ from another when its objects have everything the other class provides and add or replace some methods. The lookup that `__index` performs can continue through several tables, and inheritance uses exactly that. A savings account is an account that also earns interest and describes itself differently. The `Savings` class below builds on `Account`.

```lus nocheck
local Savings = setmetatable({}, { __index = Account })
Savings.__index = Savings

function Savings.new(owner, balance, rate)
    local account = Account.new(owner, balance)
    account.rate = rate
    return setmetatable(account, Savings)
end

function Savings:add_interest()
    self:deposit(self.balance * self.rate // 100)
end

function Savings:describe()
    return Account.describe(self) .. ` at $(self.rate)%`
end

local savings = Savings.new("Grace", 1000, 5)
savings:add_interest()
print(savings:describe())   --> Grace has 1050 at 5%
```

A read of `savings.deposit` looks in the object first, then in `Savings`, then in `Account`, where it finds the method. `Savings:describe` replaces the inherited method because the lookup finds it in `Savings` first. It still reaches the original by naming it, as in `Account.describe(self)`, and passing the object explicitly.

### Finalizers and weak tables

Lus frees a table automatically once the program can no longer reach it. Two metatable fields interact with that process, and both are for uncommon cases.

The `__gc` metamethod is a _finalizer_: a function that Lus calls with the object some time after the object becomes unreachable. A finalizer releases something outside the program's memory that an object owns, when the program forgot to release it. The moment it runs is unspecified, so a resource that must be released at a known point belongs in a `<close>` variable.

A table normally keeps its keys and values alive, which is wrong for a cache or for extra data attached to objects stored elsewhere. The `__mode` field makes the references of a table _weak_, meaning that they do not keep an object alive by themselves. The string `"k"` makes the keys weak, `"v"` makes the values weak, and `"kv"` does both. Lus removes an entry when its weak key or value has been freed. [`collectgarbage`](/manual/api#collectgarbage) runs a collection at once, so the effect is visible on the next line.

```lus
local cache = setmetatable({}, { __mode = "v" })

local report = { "kept" }
cache.kept = report
cache.dropped = { "temporary" }

collectgarbage()
print(cache.kept == report, cache.dropped)   --> true  nil
```

The variable `report` still refers to the first table, so its cache entry stays. Nothing else refers to the second table, so the collection frees it and removes its entry.

## Variable attributes

An _attribute_ in angle brackets after a variable name changes how the variable behaves, as [`<const>`](#constants) and [`<close>`](#resources-that-close-themselves) do. A program can also write attributes of its own, and the `<group>` attribute bundles several local variables under one name.

### Runtime attributes

A _runtime attribute_ is a function that Lus calls whenever a value is assigned to the variable. The function receives the name of the variable and the new value. It can reject the value, replace it, or record it. Declaring the behavior once on the variable keeps every assignment in the program plain.

The first use is validation. An attribute that raises an error rejects the value. The attribute below returns nothing, and a `nil` result keeps the assigned value as it is.

```lus
local function positive(name, value)
    if value <= 0 then
        error(`$name must be positive, got $value`, 0)
    end
end

local width <positive> = 80
width = 120
print(width)   --> 120

local ok, message = catch do
    width = -5
end
print(message)   --> width must be positive, got -5
print(width)     --> 120
```

An error raised by an attribute propagates from the assignment, which prevents the variable from being written. That is why `width` is still `120` at the end.

The second use is conversion. A result other than `nil` replaces the assigned value, so the variable always holds the converted form.

```lus
local function trimmed(name, value)
    return value:trim()
end

local title <trimmed> = "   Annual report  "
print(`[$title]`)   --> [Annual report]

title = "\tDraft\n"
print(`[$title]`)   --> [Draft]
```

The third use is logging. The attribute receives the variable name, so one function can report the changes of any variable it is attached to.

```lus
local function traced(name, value)
    print(`$name = $value`)
end

local retries <traced> = 0   --> retries = 0
retries = retries + 1        --> retries = 1
retries = retries + 1        --> retries = 2
```

### Function decorators

Functions are values, so an attribute on a variable that holds a function receives that function and can return another one in its place. The replacement usually calls the original and adds something around the call. The attribute `logged` below prints every call of the function it decorates.

```lus
local function logged(name, fn)
    return function(...)
        print(`calling $name`)
        return fn(...)
    end
end

local greet <logged> = function(who)
    return `Hello, $who`
end

print(greet("Ada"))
--> calling greet
--> Hello, Ada
```

The same shape adds caching, timing, or permission checks to a function without changing its body. The attribute `memoized` below remembers the result for each argument, so the decorated function computes each square once.

```lus
local function memoized(name, fn)
    local results = {}
    return function(n)
        if results[n] == nil then
            results[n] = fn(n)
        end
        return results[n]
    end
end

local computed = 0
local square <memoized> = function(n)
    computed = computed + 1
    return n * n
end

print(square(12), square(12), computed)   --> 144  144  1
```

### Parameterized attributes

The attribute can be any expression that evaluates to something callable. A function that returns an attribute therefore makes the behavior configurable. The function `only` below takes a type name and returns an attribute that accepts values of that type.

```lus
local function only(kind)
    return function(name, value)
        if type(value) ~= kind then
            error(`$name must be a $kind, got a $(type(value))`, 0)
        end
    end
end

local count <only "number"> = 0
local label <only "string"> = "total"

count = count + 1
local ok, message = catch do
    count = "three"
end
print(message)   --> count must be a number, got a string
print(count)     --> 1
```

`only "number"` is a call of `only` with one string argument, written without parentheses. An attribute with several arguments uses the usual call syntax, as in `<clamped(0, 10)>`. Lus evaluates the attribute expression once, when the variable is declared.

### Chained attributes

A variable can carry several attributes, separated by commas. They run from left to right, and each receives the result of the one before it. The last result is stored. The example combines `only` with `clamped`, an attribute that keeps a number within a range.

```lus nocheck
local function clamped(low, high)
    return function(name, value)
        return math.max(low, math.min(high, value))
    end
end

local volume <only "number", clamped(0, 10)> = 5
volume = 42
print(volume)   --> 10
volume = -3
print(volume)   --> 0
```

The order matters here. `only "number"` runs first, so `clamped` never receives a value that it cannot compare.

### Rules for runtime attributes

A few rules decide when an attribute runs.

- An attribute runs when the variable is initialized and on every assignment to it in the function that declares it. An assignment made inside a nested function stores the value without running the attribute.
- Assigning `nil` stores `nil` without running the attribute, so an attribute never has to handle `nil`.
- A `nil` result keeps the value. Any other result, including `false`, replaces it.
- An error raised by an attribute prevents the write.
- Runtime attributes apply to a `local` statement that declares one variable. `<const>` and `<close>` can share the list and must come first, as in `local limit <const, only "number"> = 10`.

### Local groups

A table is the usual way to keep related values under one name, such as the `x` and `y` of a position. Creating a table allocates memory, which the garbage collector frees later. That cost is too small to notice in most code. It adds up in a function that runs millions of times and builds a small table on each call only to hold a few working values.

A _local group_ is a named bundle of local variables. The `<group>` attribute declares one from a constructor that lists the fields. The fields are read and written with the same `name.field` syntax as a table, and the group allocates no table, because each group field is a local variable.

Separate local variables such as `sum_x` and `sum_y` also avoid the allocation, but the code then loses the structure of the data. A group keeps that structure. A table in hot code becomes a group when `<group>` is added to its declaration, and every use of its fields stays as it was. In the function below, removing `<group>` gives the version that allocates a table on every call.

```lus
local function centroid(points)
    local sum <group> = { x = 0, y = 0 }
    for _, point in ipairs(points) do
        sum.x = sum.x + point.x
        sum.y = sum.y + point.y
    end
    return sum.x / #points, sum.y / #points
end

print(centroid({ { x = 0, y = 0 }, { x = 4, y = 2 }, { x = 2, y = 4 } }))   --> 2.0  2.0
```

A field initializer can be any expression. The following group computes one of its fields with a loop.

```lus
local words = { "pear", "fig", "banana" }

local summary <group> = {
    count = #words,
    longest = do
        local best = ""
        for _, word in ipairs(words) do
            if #word > #best then
                best = word
            end
        end
        provide best
    end,
}
print(summary.count, summary.longest)   --> 3  banana
```

Assigning a constructor to a group overwrites the fields that the constructor lists and leaves the others unchanged. This resets part of a group in one statement.

```lus
local stats <group> = { count = 4, sum = 22, max = 9 }

stats = { count = 0, sum = 0 }
print(stats.count, stats.sum, stats.max)   --> 0  0  9
```

Assigning another group copies each of its fields into the field of the same name. Every field of the assigned group must also be a field of the target, and the other fields of the target keep their values.

```lus
local start <group> = { x = 0, y = 0 }
local pos <group> = { x = 5, y = 7 }

pos = start
print(pos.x, pos.y)   --> 0  0
```

A field marked `<const>` cannot be reassigned, and a field marked `<group>` is a nested group with its own fields. Nesting is where the structure matters most. The `body` group below would otherwise need five separate names such as `body_position_x`.

```lus
local body <group> = {
    mass <const> = 2,
    position <group> = { x = 0, y = 0 },
    velocity <group> = { x = 1, y = 3 },
}

for step = 1, 3 do
    body.position.x = body.position.x + body.velocity.x
    body.position.y = body.position.y + body.velocity.y
end
print(body.position.x, body.position.y)   --> 3  9
```

Groups follow four rules that tables do not.

- The fields are fixed by the declaration. Reading or writing a field that the group does not declare, such as `stats.average`, is a compile error.
- A group exists only as its local variables. It cannot be passed to a function, returned, or stored in a table, so `print(stats)` is a compile error. Pass the fields that the other code needs, as `centroid` does in its `return`.
- Groups are always local. Therefore, declaring a global as a group is an error.
- A group can be copied into a new group. `local backup <group> = stats` declares `backup` with the same fields and the current values of `stats`.

A table remains the right choice whenever the bundle has to leave the function, grow, or be iterated.

## Enums

Programs often need a value that is one of a few fixed choices: a log level, the state of a connection, or a direction. Strings and numbers can stand for the choices, with drawbacks. A misspelled string such as `"warnning"` is still a valid string, so the mistake goes unnoticed. A number such as `2` says nothing to the reader and is equal to every other `2` in the program, whatever that other number means. An _enum_ is a fixed set of named values that are distinct from every string, every number, and every other enum.

### Declaring an enum

An `enum ... end` expression lists the names of its _members_, separated by commas. Store the result in a variable and reach each member as a field of that variable.

```lus
local Level = enum debug, info, warning, error end

local current = Level.warning
print(type(current))             --> enum
print(current == Level.warning)  --> true
print(current == "warning")      --> false
print(current == 3)              --> false
```

A member is equal only to itself. A name that the enum does not list, such as `Level.fatal`, reads as `nil`.

### Ordering

The members of one enum are ordered by their position in the declaration, so the comparison operators work between them. A log filter is the typical use: a message is shown when its level is at least the configured threshold.

```lus nocheck
local threshold = Level.warning

local function log(level, message)
    if level >= threshold then
        print(message)
    end
end

log(Level.info, "cache warmed")
log(Level.error, "disk full")   --> disk full
```

Ordering is defined within one enum. Comparing members of two different enums with `<` raises an error, and `==` between them is always `false`, even when the members share a name.

```lus nocheck
local Mode = enum debug, release end

print(Level.debug == Mode.debug)   --> false
local ok = catch Level.debug < Mode.release
print(ok)                          --> false
```

### Enums as table keys

A member can be a table key, which attaches data to each choice. `tostring` of a member gives the text `enum:` followed by an address, so a table of names keyed by member is also the way to print a member.

```lus nocheck
local names = {
    [Level.debug] = "DEBUG",
    [Level.info] = "INFO",
    [Level.warning] = "WARN",
    [Level.error] = "ERROR",
}

local function log(level, message)
    print(`[$(names[level])] $message`)
end

log(Level.warning, "disk almost full")   --> [WARN] disk almost full
```

Printing a member directly shows only an address, which differs from run to run.

```lus nocheck
print(Level.info)   --> enum: 0x0000010303c090
```

### Positions

[`tonumber`](/manual/api#tonumber) returns the position of a member in its declaration, counting from 1. Indexing the enum with a position returns the member at that position. The two conversions are useful for storing a member in a file or a database as a number and reading it back.

```lus nocheck
local stored = tonumber(Level.warning)
print(stored)   --> 3

local restored = Level[stored]
print(restored == Level.warning)   --> true
```

## Permissions

A Lus script starts with access to nothing outside itself. It cannot read or write files, open network connections, run other programs, or read environment variables until it asks for the _permission_ to do so. The function [`pledge`](/manual/api#pledge) does the asking.

This default limits the damage of mistakes and of code that the author did not write. A script that pledged only to read `./data` and then [sealed](#rejecting-and-sealing) its permissions cannot delete a home directory because of a wrong path, and no module it loads afterwards can open a network connection. The `pledge` calls of a program are also a short, searchable list of everything the program may touch. Finally, whoever runs a script may set the limit from the command line, and the script then receives only what that person allowed.

### Asking with `pledge`

An operation that needs a permission the program does not hold raises an error. `io.open` opens a file, and the following one-line script, saved as `report.lus`, tries to open one without asking first.

```lus nocheck
local file <close> = io.open("sales.csv")
```

Running it stops at that line with an error that names the missing permission and the file.

```text
lus: report.lus:1: permission "fs:read" denied for 'sales.csv'
```

`pledge` takes one or more permission names and returns one boolean for each: `true` when the permission was granted and `false` when it was refused. A script run with plain `lus script.lus` is granted every permission it asks for. A request is refused when the command line set a narrower limit or when the program has [sealed](#rejecting-and-sealing) its permissions.

`pledge` is an ordinary function, and a program may call it at any point. Many scripts pledge everything they need at the top, where a reader sees it first. A program may equally ask for a permission at the moment a feature needs it and adapt when the answer is `false`.

```lus
if pledge("network:http") then
    print("checking for updates")
else
    print("skipping the update check")
end
--> checking for updates
```

### Permission names

A permission name has a group, such as `fs` for the filesystem, and usually a part after a colon that selects one kind of operation in the group. The name of a group alone grants every operation in it, so `pledge("fs")` allows both reading and writing.

| Permission | What it allows |
| --- | --- |
| `fs:read` | Reading files, listing directories, and inspecting paths. |
| `fs:write` | Creating, changing, moving, and removing files and directories. |
| `network:http` | HTTP and HTTPS requests with `network.fetch`. |
| `network:tcp` | Opening TCP connections and listening for them. |
| `network:udp` | Sending and receiving UDP datagrams. |
| `network:server` | Serving HTTP with `network.serve`, together with `network:tcp`. |
| `exec` | Running other programs with `os.execute` and `io.popen`. |
| `env` | Reading environment variables with `os.getenv`. |
| `load` | Running code that the program loads while it runs, with `load`, `require` of a file, or a worker. |

Some operations need two permissions. Loading a module file or starting a worker needs `load` to run the code and `fs:read` to read the file.

### Narrowing a permission

A permission for the whole filesystem or the whole network is often more than a program needs. A value after `=` narrows a permission to the paths, hosts, or names that match it. In a value, `*` matches any run of characters. The following script may read the files below `./data` and nothing else. It reads the first line of one file, with `file:read("l")`, and fails to open another.

```lus nocheck
pledge("fs:read=./data/*")

local file <close> = io.open("data/sales.csv")
print(file:read("l"))                    --> region,amount
print((catch io.open("secrets.txt")))    --> false
```

A filesystem value is an absolute path or a path that starts with `.`, which is taken from the working directory. A network value names a host, with an optional port and path, as in `network:http=api.example.com/*` or `network:tcp=127.0.0.1:*`. An `env` value names a variable. `os.getenv` reads an environment variable, and the following script may read `EDITOR` and no other, so it cannot reach the credentials that other variables hold.

```lus
pledge("env=EDITOR")

print((catch os.getenv("EDITOR")))                  --> true
print((catch os.getenv("AWS_SECRET_ACCESS_KEY")))   --> false
```

Several pledges of the same permission with different values add up, and an operation is allowed when any of the values matches.

### Rejecting and sealing

A program can also give permissions up, which matters most before it starts to handle input it does not trust. A name with the prefix `~` _rejects_ a permission for the rest of the program. Every later operation that needs it fails, and a later `pledge` of it raises an error. Because any part of a program may call `pledge`, a rejection is how the main program makes sure that no module it loads acquires that permission later. `os.execute` runs another program, and the example forbids it.

```lus
pledge("fs:read", "exec")
pledge("~exec")

local ran = catch os.execute("ls")
print(ran and "listed the files" or "running programs is forbidden")
--> running programs is forbidden

local granted = catch pledge("exec")
print(granted and "granted" or "refused for good")   --> refused for good
```

The name `"seal"` freezes the whole set. After it, every `pledge` returns `false`, so the program keeps exactly the permissions it held at that moment. A server typically pledges what it serves from and listens on, then seals before it accepts its first connection.

```lus
pledge("fs:read", "network:tcp", "seal")

print(pledge("exec"))       --> false
print(pledge("fs:write"))   --> false
```

### Granting from the command line

The `-P` option of `lus` grants a permission before the script starts. It takes the same names as `pledge`, with values and with the `~` prefix, and it may appear several times.

```bash
lus -Pnetwork:http -Pfs:read=./report.lus -Pfs:read=./data/* report.lus
```

When the command line grants at least one permission, those grants are the limit for the whole run. A `pledge` in the script succeeds for what the command line allowed and returns `false` for everything else. This is how a person runs a script they did not write without reading all of it first: the script receives the permissions named on the command line and no others. A filesystem grant on the command line must cover the script file itself, which is why the command above names `./report.lus`.

A command line that only rejects, such as `lus -P~exec script.lus`, sets no limit. The script may pledge anything except what was rejected.

[Permissions](/manual/permissions) is the complete reference. It lists every permission and the functions that check it, the matching rules for paths and hosts, and how rejection, sealing, the command line, and embedding hosts interact.

## Coroutines

A _coroutine_ is a function that can pause partway through and continue later from the same place, with its local variables intact. An ordinary function runs from its first line to a `return` before its caller continues. A coroutine may stop at any point, give control back to its caller, and pick up again when the caller asks.

Coroutines serve three purposes in Lus:

- A coroutine produces a sequence of values one at a time, as a [generator](#generators).
- A coroutine holds a task that needs input at several points, such as a conversation, and keeps its place between inputs.
- A _detached coroutine_ lets one program wait for many things at once, such as many network connections, while each task stays ordinary sequential code.

Computing on several processor cores at the same time is the work of [workers](#workers).

### Creating and resuming

Three functions drive a coroutine. [`coroutine.create`](/manual/api#coroutine.create) takes a function and returns a coroutine that has not started. [`coroutine.resume`](/manual/api#coroutine.resume) runs the coroutine until it pauses or ends. Inside the coroutine, [`coroutine.yield`](/manual/api#coroutine.yield) pauses it and returns control to the code that called `resume`.

Values travel in both directions. The arguments of `yield` come out as the results of `resume`, after a first result of `true`. The extra arguments of the next `resume` go in as the results of that `yield`. The following coroutine asks two questions. The answers may arrive from a keyboard, a web form, or a chat message, and the coroutine keeps its place between them.

```lus
local signup = coroutine.create(function()
    local name = coroutine.yield("What is your name?")
    local email = coroutine.yield(`Hello $name. What is your email address?`)
    return `Registered $name <$email>`
end)

print(coroutine.resume(signup))
--> true  What is your name?
print(coroutine.resume(signup, "Ada"))
--> true  Hello Ada. What is your email address?
print(coroutine.resume(signup, "ada@example.com"))
--> true  Registered Ada <ada@example.com>
```

The first `resume` starts the function, and any extra arguments become the parameters of the function. When the function returns, `resume` returns `true` and the return values, and the coroutine is finished. Without a coroutine, this program would store the current step and the answers so far in a table and decide what to do on each input. The coroutine stores them in its local variables and in the position where it paused.

An error inside a coroutine stops the coroutine and does not propagate to the caller. `resume` returns `false` and the error object, so the caller decides what to do with it. Resuming a finished coroutine also returns `false`.

```lus
local task = coroutine.create(function()
    error("out of paper", 0)
end)

print(coroutine.resume(task))   --> false  out of paper
print(coroutine.resume(task))   --> false  cannot resume dead coroutine
```

### Generators

Some traversals are easy to write as a loop or a recursive function that handles each item where it finds it, and hard to write as a function that returns one item per call. Walking a tree is the usual case, because the position in a tree is a whole path of nested calls.

[`coroutine.wrap`](/manual/api#coroutine.wrap) turns such a function into an [iterator](#writing-an-iterator-with-a-function), often called a _generator_. Inside the function, `coroutine.yield` gives one value to the `for` loop and pauses the function. The next pass of the loop continues the function from where it paused. The loop ends when the function returns.

The following example lists the files of a folder tree. The `walk` function is an ordinary recursive traversal that yields each file path it reaches.

```lus
local tree = {
    name = "project",
    children = {
        { name = "README.md" },
        { name = "src", children = {
            { name = "main.lus" },
            { name = "util.lus" },
        } },
    },
}

local function walk(node, prefix)
    local path = prefix .. node.name
    if node.children then
        for _, child in ipairs(node.children) do
            walk(child, path .. "/")
        end
    else
        coroutine.yield(path)
    end
end

local function files(root)
    return coroutine.wrap(function()
        walk(root, "")
    end)
end

for path in files(tree) do
    print(path)
end
--> project/README.md
--> project/src/main.lus
--> project/src/util.lus
```

### Status and closing

[`coroutine.status`](/manual/api#coroutine.status) returns the state of a coroutine as a string. A coroutine is `"suspended"` before it starts and while it is paused, `"running"` while its code runs, `"normal"` while it waits for another coroutine that it resumed, and `"dead"` once it has returned or failed.

[`coroutine.close`](/manual/api#coroutine.close) ends a suspended coroutine that the program no longer needs. Closing also closes the [`<close>` variables](#resources-that-close-themselves) of the coroutine, which releases the files or connections it holds.

```lus
local counter = coroutine.create(function()
    local n = 0
    while true do
        n = n + 1
        coroutine.yield(n)
    end
end)

print(coroutine.resume(counter))   --> true  1
print(coroutine.status(counter))   --> suspended
print(coroutine.close(counter))    --> true
print(coroutine.status(counter))   --> dead
```

### Detached coroutines

Many programs spend most of their time waiting. A chat server holds a thousand connections, and each one sends a line every few minutes. A script asks five services for data, and each answer takes a second to arrive. Sequential code handles one wait at a time: while it waits for a line from the first connection, the other 999 get no service.

A _detached coroutine_ solves this. [`coroutine.detach`](/manual/api#coroutine.detach) starts a coroutine that Lus runs by itself, beside the rest of the program. When a detached coroutine reaches an operation that waits, such as reading from a network connection, the runtime pauses that coroutine and runs the others. It resumes the coroutine when its data has arrived. The program therefore creates one detached coroutine for each connection or request, and each one stays plain sequential code.

The following program is a server that answers price requests on port 7000. `network.tcp.bind` opens a socket that listens on a port, `server:accept()` waits for the next client and returns its connection, and `conn:send` writes text to that client. The function `serve` handles one connection from start to end. Each client sends the name of an item on a line, and the server replies with its price. A connection returns what it reads as a [vector](#vector) of bytes, which `vector.tostring` turns into a string. `conn:receive("*l", 1024)` reads one line, and its second argument limits the line to 1024 bytes, so a client that never sends a line break cannot make the server use memory without limit. At the end of a connection, `receive` returns an empty vector. Declaring `closing` with `<close>` closes the connection when `serve` returns, and the `pledge` call asks for the network [permission](#permissions) that the program needs.

```lus nocheck
pledge("network:tcp")

local prices = { apple = 3, pear = 5 }

local function serve(conn)
    local closing <close> = conn
    while true do
        local item = vector.tostring(conn:receive("*l", 1024))
        if item == "" then
            break
        end
        conn:send(`$(prices[item] or "unknown")\n`)
    end
end

local server = network.tcp.bind("127.0.0.1", 7000)
while true do
    coroutine.detach(coroutine.create(serve), server:accept())
end
```

`coroutine.detach(co, ...)` passes its extra arguments to the function of the coroutine, here the new connection, and returns the coroutine at once. A client that stays silent for an hour pauses only its own coroutine inside `receive`. The loop at the bottom keeps accepting new clients, and every other connection is answered as its lines arrive.

Clients gain in the same way. The following program asks that server for three prices at the same time, each over a connection of its own. `network.tcp.connect` opens a connection to a server.

```lus nocheck
pledge("network:tcp")

local function lookup(item)
    local conn <close> = network.tcp.connect("127.0.0.1", 7000)
    conn:send(item .. "\n")
    local price = tonumber(vector.tostring(conn:receive("*l", 1024)))
    if not price then
        error(`no price for $item`, 0)
    end
    return price
end

local tasks = {}
for i, item in ipairs({ "apple", "kiwi", "pear" }) do
    tasks[i] = coroutine.detach(coroutine.create(lookup), item)
end
for _, task in ipairs(tasks) do
    print(coroutine.resume(task))
end
--> true  3
--> false  no price for kiwi
--> true  5
```

The first loop only starts the three lookups, and the second loop collects what each one produced. The three lookups wait for their answers at the same time.

### Results, errors, and cancellation

`coroutine.resume` on a detached coroutine waits until that coroutine has ended. It then returns what `resume` returns for any coroutine that ends: `true` and the return values, or `false` and the error object. The client collects one result or one error per lookup this way. While `resume` waits, the runtime keeps running every detached coroutine, which is how all three lookups make progress during the second loop.

A detached coroutine that ends before anything resumes it keeps its results until the first `resume` asks for them. An error works the same way, with one addition. If a detached coroutine fails and the program never collects the error, `lus` reports it and exits with status 1, so that the failure is not lost.

```lus nocheck
coroutine.detach(coroutine.create(function()
    error("lost")
end))
print("main program done")
--> main program done
--> lus: script.lus:2: lost
```

`coroutine.close` cancels a detached coroutine. The runtime stops resuming it and closes its `<close>` variables, so a cancelled task releases its connection. A loop that accepts clients forever, run in a detached coroutine, ends this way when the program shuts its server down.

When the top-level code of a script ends, `lus` keeps running the detached coroutines until every one of them has ended. A script may therefore start its tasks and return, and the tasks still run to completion.

```lus
coroutine.detach(coroutine.create(function()
    for i = 1, 3 do
        print("tick", i)
        coroutine.yield()
    end
end))
print("the script has reached its last line")
--> the script has reached its last line
--> tick  1
--> tick  2
--> tick  3
```

Inside a detached coroutine, `coroutine.yield()` pauses the coroutine until the others have had a turn, as the example shows. A task with a long computation calls it from time to time so that the other tasks stay responsive.

Detached coroutines run one at a time, and the runtime switches between them only where one waits, yields, or ends. The code between two waits is never interrupted, so detached coroutines read and change the same tables without locks.

### Workers

Detached coroutines share one processor core, which suits tasks that mostly wait. A program that computes, such as one that resizes images or searches a large data set, gains nothing from them, because a computation never waits. A _worker_ is a second copy of the Lus interpreter that runs a script on a thread of its own, in parallel with the program that created it. Several workers therefore compute at the same time, each on its own core.

[`worker.create(path, ...)`](/manual/api#worker.create) starts a worker that runs the script file at `path`. The extra arguments arrive in the script as the values of `...`. The worker reports results with [`worker.message`](/manual/api#worker.message), and the creator reads them with [`worker.receive`](/manual/api#worker.receive), which waits for the next message of that worker.

The following program counts the prime numbers below one million on four workers, each of which checks a quarter of the range. The worker script is a file of its own, `primes.lus`.

```lus nocheck
-- primes.lus
local first, last = ...
local count = 0
for n = first, last do
    local prime = n > 1
    for d = 2, math.floor(math.sqrt(n)) do
        if n % d == 0 then
            prime = false
            break
        end
    end
    if prime then
        count = count + 1
    end
end
worker.message(count)
```

The main program starts the four workers and adds up their counts. Starting a worker reads and runs a script file, so it needs the `load` and `fs:read` permissions.

```lus nocheck
pledge("load", "fs:read")

local workers = {}
for i = 1, 4 do
    workers[i] = worker.create("primes.lus", (i - 1) * 250000 + 1, i * 250000)
end

local total = 0
for _, handle in ipairs(workers) do
    total = total + worker.receive(handle)
end
print(total)   --> 78498
```

All four workers are running before the first `worker.receive`, so the loop that adds the counts waits only for the slowest one.

### Messages between workers

A worker has its own global variables and its own memory. It shares no variable with its creator, which is what allows the two to run at the same time safely. They communicate only through messages, and every message is a copy of the value that was sent.

Messages flow in both directions. The creator sends with [`worker.send(handle, value)`](/manual/api#worker.send), and the worker reads with [`worker.peek()`](/manual/api#worker.peek), which waits for the next value. The worker answers with `worker.message(value)`, and the creator reads with `worker.receive(handle)`. A worker that stays alive and handles one request after another is written as a loop around `worker.peek`. The following worker, saved as `count_words.lus`, counts the words of each text it receives.

```lus nocheck
-- count_words.lus
while true do
    local job = worker.peek()
    local words = 0
    for _ in job.text:gmatch("%S+") do
        words = words + 1
    end
    worker.message({ id = job.id, words = words })
end
```

The program sends it two jobs and reads the two replies.

```lus nocheck
pledge("load", "fs:read")

local counter = worker.create("count_words.lus")
worker.send(counter, { id = 1, text = "the quick brown fox" })
worker.send(counter, { id = 2, text = "jumps over the lazy dog" })
for i = 1, 2 do
    local reply = worker.receive(counter)
    print(reply.id, reply.words)
end
--> 1  4
--> 2  5
```

A worker that is waiting in `worker.peek` when the program ends is stopped with it, which is why this worker needs no instruction to quit.

A message may be `nil`, a boolean, a number, a string, a table of such values, or a vector. A function or a coroutine cannot be sent, and trying raises an error. An error that ends the script of a worker is raised in the creator by the next `worker.receive` on that worker, where a [`catch`](#errors) captures it like any other error. Once a worker has finished and its messages have been read, `worker.receive` returns `nil`.

### Choosing between detached coroutines and workers

The choice follows from what the task does with its time. A task that mostly waits belongs in a detached coroutine. A task that mostly computes belongs in a worker.

| | Detached coroutine | Worker |
| --- | --- | --- |
| Use it for | Waiting on many things at once: connections, requests, replies | Computing on several processor cores |
| Runs | One at a time, in the thread of the program | In parallel, on a thread of its own |
| Data | Shares the variables and tables of the program | Has its own globals and exchanges copies as messages |
| Starts from | A function | A script file |
| Cost of each | Small, so a program may run thousands | A whole interpreter, so about one per core is useful |

The two combine. `worker.receive` is one of the operations that pauses a detached coroutine, so a server that handles each connection in a detached coroutine may pass a heavy computation to a worker and keep answering other connections while that coroutine waits for the result.

[`network.fetch`](/manual/api#network.fetch) is the exception among the network operations. Called from the top-level code of a script, it lets the detached coroutines run while it waits. Called inside a detached coroutine, it holds up every other coroutine until its response arrives. In both cases it waits for one response at a time, so a program that sends several HTTP requests at the same time calls `fetch` from one worker per request.

[Coroutines and workers](/manual/concurrency) is the full description of both, including every operation that pauses a detached coroutine, timeouts, and the rules for values that cross between workers.

### Permissions of coroutines and workers

A coroutine starts with a copy of the permissions of the code that created it, and later changes on either side stay on that side. A function can therefore run a piece of code with fewer permissions by rejecting them inside a coroutine, as [Running code with its own environment](#running-code-with-its-own-environment) shows. A worker starts with a sealed copy of the permissions of its creator.

## Queries

A program often holds a list of records, such as the rows of a CSV file or the products of a catalog, and needs an answer from it: the records that match a condition, sorted in some order, or a total for each category. Written by hand, each answer takes a loop with an `if`, a call to `table.sort` with a comparison function, and a table of running totals. A _query_ states the answer in a few clauses, and Lus does the filtering, sorting, and totaling. The same query also runs against a table of a SQLite database.

The following program finds the two longest science fiction books of a small list.

```lus
local books = {
    { title = "Dune", author = "Herbert", genre = "scifi", pages = 600, rating = 5 },
    { title = "Emma", author = "Austen", genre = "novel", pages = 450 },
    { title = "Neuromancer", author = "Gibson", genre = "scifi", pages = 270, rating = 4 },
    { title = "Persuasion", author = "Austen", genre = "novel", pages = 250, rating = 3 },
    { title = "Solaris", author = "Lem", genre = "scifi", pages = 210 },
}

for book in query(@books where books.genre == "scifi" order by books.pages desc limit 2) do
    print(book.title, book.pages)
end
--> Dune  600
--> Neuromancer  270
```

The query says: from `books`, keep the entries whose genre is `"scifi"`, sort them from the most pages to the fewest, and stop after two. The queries that follow all read this same `books` list.

### Sources and rows

A query starts with `@` followed by the list it reads, which is called its _source_. A source is an array of records, and a record is a table with named fields. Each record is one _row_. The function [`query`](/manual/api#query) runs a query. It is used in a `for` loop, like `pairs`, and the loop variable receives one result per iteration. A query that consists of a source alone yields every row in the order of the array.

Inside a query, the _row variable_ stands for the row being examined. It has the name of the source, so in a query over `books` the expression `books.pages` reads the `pages` field of the current row. The word `as` gives the row variable another name, which keeps longer queries short.

```lus nocheck
for book in query(@books as b where b.pages > 500) do
    print(book.title)   --> Dune
end
```

The row variable `b` exists only inside the query. The loop variable `book` is an ordinary local variable that holds each result.

### Filtering with `where`

The `where` clause holds a condition. The query evaluates it once for each row and keeps the rows for which it is truthy. The condition is an ordinary expression built from comparisons, `and`, `or`, `not`, arithmetic, and calls to functions and methods. One difference applies inside a query: a comparison with `nil` is false, as [nil in queries](#nil-in-queries) explains.

```lus nocheck
for book in query(@books as b where b.genre == "novel" or b.title:sub(1, 1) == "S") do
    print(book.title)
end
--> Emma
--> Persuasion
--> Solaris
```

### Choosing fields with `select`

A query without a `select` clause yields the records of the source themselves. The `select` clause makes the query build a new record for each row, which holds only the listed values. A value written as a field of the row, such as `b.title`, keeps the name of that field. Any other expression takes its name from `as`.

```lus nocheck
-- How many days each long book takes at 30 pages a day.
for row in query(@books as b where b.pages > 400 select b.title, b.pages // 30 as days) do
    print(row.title, row.days, row.author)
end
--> Dune  20  nil
--> Emma  15  nil
```

Each result has the fields `title` and `days` and no others, which is why `row.author` is `nil`.

### Sorting with `order by`

The `order by` clause sorts the results by one or more expressions. Each expression may be followed by `asc` for ascending order, which is the default, or `desc` for descending order. When two rows are equal on the first expression, the second one decides, and so on. The following query sorts by author and puts the longer book first among the books of one author.

```lus nocheck
for book in query(@books as b order by b.author, b.pages desc) do
    print(book.author, book.title)
end
--> Austen  Emma
--> Austen  Persuasion
--> Gibson  Neuromancer
--> Herbert  Dune
--> Lem  Solaris
```

### Taking part of the result with `limit` and `offset`

`limit n` ends the result after `n` rows, and `offset n` skips the first `n` rows. Together they cut a sorted result into pages. The following query yields the second page of a listing with two books per page.

```lus nocheck
for book in query(@books as b order by b.title limit 2 offset 2) do
    print(book.title)
end
--> Neuromancer
--> Persuasion
```

### Removing duplicates with `distinct`

`select distinct` yields each different record once. The list holds two books by Austen, and the following query names her a single time.

```lus nocheck
for row in query(@books as b select distinct b.author order by b.author) do
    print(row.author)
end
--> Austen
--> Gibson
--> Herbert
--> Lem
```

### Summarizing with aggregates

An _aggregate_ computes one value from many rows, such as how many there are or what they add up to. Lus has five aggregates:

- `count(*)` is the number of rows.
- `count(expr)` is the number of rows for which `expr` is not `nil`.
- `sum(expr)` adds the values of `expr`.
- `avg(expr)` is the average of the values of `expr`, as a float.
- `min(expr)` and `max(expr)` are the smallest and the largest value of `expr`. They compare numbers by size and strings alphabetically.

Aggregates are written in the `select` clause, and each one takes a name with `as`. A query whose `select` holds aggregates yields a single row that summarizes all the rows it kept. Every aggregate ignores `nil` values, so in the following query the average rating covers the three books that have a rating. The query is stored in a variable and spans several lines. A query extends over the clauses that follow it, and inside a call such as `query(...)` the closing parenthesis ends it.

```lus nocheck
local summary = @books as b select
    count(*) as total,
    count(b.rating) as rated,
    avg(b.rating) as rating,
    sum(b.pages) as pages,
    min(b.pages) as shortest,
    max(b.pages) as longest

for row in query(summary) do
    print(row.total, row.rated, row.rating)        --> 5  3  4.0
    print(row.pages, row.shortest, row.longest)    --> 1780  210  600
end
```

### Grouping with `group by`

A summary of the whole list is one use of aggregates. The more common need is one summary for each category: the number of books in each genre, or the total sales of each region. The `group by` clause divides the rows into groups, one for each different value of its expression, and the aggregates are then computed for each group. The result has one row per group.

```lus nocheck
local by_genre = @books as b
    select b.genre, count(*) as titles, sum(b.pages) as pages
    group by b.genre
    order by pages desc

for row in query(by_genre) do
    print(row.genre, row.titles, row.pages)
end
--> scifi  3  1080
--> novel  2  700
```

A group stands for several rows, so the `select` of a grouped query may hold only values that are the same for the whole group. Each value is either an expression of the `group by` clause, here `b.genre`, or an aggregate. A field such as `b.title`, which differs from row to row within a group, raises an error when the query runs.

The `order by` clause of this query uses `pages`, a name that `select` gave with `as`. A plain name in `order by` refers to the selected value of that name. Such names are known to `order by` and `having` only, and in `where` the same name refers to a variable of the surrounding code.

### Filtering groups with `having`

`where` decides which rows enter the groups, and it runs before any aggregate is computed, so it cannot ask about a count or a total. The `having` clause holds a condition on the groups. It runs after grouping and keeps the groups for which the condition is truthy. A condition in `having` may name an aggregate directly, as in `having count(*) >= 2`, or use the name that `as` gave it in `select`, as in `having rated >= 2`. The following query uses both clauses: `where` keeps the books that have a rating, and `having` keeps the genres with at least two such books.

```lus nocheck
local well_rated = @books as b
    where b.rating
    select b.genre, count(*) as rated, avg(b.rating) as rating
    group by b.genre
    having rated >= 2

for row in query(well_rated) do
    print(row.genre, row.rated, row.rating)   --> scifi  2  4.5
end
```

### Joining two sources

Related data is often held in two lists. One list holds books with the name of their author, and another holds authors with their country. A _join_ answers questions that need both, such as the country each book comes from. The query names both sources, separated by a comma, and each source has its own row variable. The query then considers every pairing of a row from the first source with a row from the second, and the `where` clause keeps the pairings that belong together.

```lus nocheck
local authors = {
    { name = "Austen", country = "England" },
    { name = "Herbert", country = "United States" },
    { name = "Lem", country = "Poland" },
}

local origins = @books as b, authors as a
    where b.author == a.name
    select b.title, a.country
    order by b.title

for row in query(origins) do
    print(row.title, row.country)
end
--> Dune  United States
--> Emma  England
--> Persuasion  England
--> Solaris  Poland
```

A row that has no partner produces no result. The list of authors has no entry for Gibson, so `Neuromancer` is absent from the output. A join always has a `select` clause, because each result combines fields from two rows. The other clauses work on a join as they do on one source, so the query above could count the books of each country with `group by a.country`.

### Values from the surrounding code

A clause may use the local variables around the query, which is how a query takes a parameter such as a search term or a page size. The query reads such a variable once, at the moment the query is built. Assigning to the variable afterwards leaves the query as it was. The contents of the source are different: the query reads them again every time it runs, so it sees rows that were added in the meantime.

```lus nocheck
local longest = 260
local short = @books as b where b.pages <= longest select b.title
longest = 1000   -- the query keeps 260

books[#books + 1] = { title = "Candide", author = "Voltaire", genre = "novel", pages = 130 }

for row in query(short) do
    print(row.title)
end
--> Persuasion
--> Solaris
--> Candide
```

A function that builds a query from its parameters gives the query a name and lets each call supply its own values.

```lus nocheck
local function shortest(genre, n)
    return @books as b where b.genre == genre order by b.pages limit n
end

for book in query(shortest("scifi", 1)) do
    print(book.title)   --> Solaris
end
for book in query(shortest("novel", 1)) do
    print(book.title)   --> Persuasion
end
```

### Running a query

A query is a value, and writing one only describes the work. It may be stored in a variable, passed to a function, or returned, as the examples above do. The work happens when `query` runs it in a `for` loop, and each loop runs the query from the start against the current contents of its sources. The only way to get results is that loop, so a program that needs the results as a list builds the list inside it.

```lus nocheck
local novels = @books as b where b.genre == "novel" select b.title

local titles = {}
for row in query(novels) do
    titles[#titles + 1] = row.title
end
print(table.concat(titles, ", "))   --> Emma, Persuasion

books[2].genre = "romance"
for row in query(novels) do
    print(row.title)   --> Persuasion
end
```

The clauses of a query may be written in any order, and each appears at most once. Whatever the written order, a query always works in the same sequence. It filters the rows with `where`, forms the groups, filters the groups with `having`, builds the results with `select`, removes duplicates for `distinct`, sorts with `order by`, and finally applies `offset` and `limit`.

The clause words `where`, `select`, `distinct`, `as`, `order`, `by`, `asc`, `desc`, `limit`, `offset`, `group`, and `having`, and the aggregate names `count`, `sum`, `avg`, `min`, and `max`, have their special meaning only inside a query. Everywhere else they are ordinary names, so a program may have a variable named `count` or a function named `select`.

### `nil` in queries

A missing field reads as `nil`, and queries treat `nil` in a few fixed ways:

- A comparison with `nil` is false. `where b.rating < 5` and `where b.rating ~= 5` both skip the books without a rating, and `where b.rating == nil` matches no row at all. The condition `where not b.rating` finds the rows where a field is missing.
- `order by` places rows whose sort value is `nil` first in ascending order and last in descending order.
- Aggregates ignore `nil` values. When a query keeps no rows, `count` yields `0` and every other aggregate yields `nil`.

### Queries on a database

A table of a SQLite database is a source like any other. A database opened with [`io.sqlite`](/manual/api#io.sqlite) offers each of its tables as a field, so `@db.books` is a query over the table `books`, and SQLite does the filtering. A function that receives its source as a parameter runs the same query over a Lus table or a database table.

The example opens a database in memory, which needs no permission. The two `db:run` lines after `CREATE TABLE` each insert one row, with the values given as arguments in place of the `?` marks. [SQLite](#sqlite) explains these statements.

```lus
local function short_books(source)
    return @(source) as b where b.pages < 300 select b.title
end

local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (title TEXT, pages INTEGER)")
db:run("INSERT INTO books VALUES (?, ?)", "Dune", 600)
db:run("INSERT INTO books VALUES (?, ?)", "Solaris", 210)

for row in query(short_books(db.books)) do
    print(row.title)   --> Solaris
end
for row in query(short_books({ { title = "Emma", pages = 450 }, { title = "Candide", pages = 130 } })) do
    print(row.title)   --> Candide
end
```

A source that is written as a parenthesized expression, such as `@(source)`, always takes its row variable from `as`. [SQLite](/manual/sqlite) describes databases, how to create and fill their tables, and how queries run on them.

## Modules

A program that grows past a few hundred lines is easier to work on as several files, each with one responsibility. A _module_ is a file of Lus code that another file loads by name. The local variables of a module stay private to it, and the module chooses what it shares, so two files never collide over a helper function with the same name. Several programs may also load the same module, which keeps shared code in one place.

The standard library is built in and needs no loading. JSON, CSV, the filesystem, networking, and the other libraries of [The standard library](#the-standard-library) are available in every file. Modules are for the code of the project itself.

### Writing a module

A module is a file that ends with `return`. The value it returns is the module, and it is usually a table of functions. The following file is a module named `shapes`, saved as `shapes.lus`.

```lus
local shapes = {}

local function square(x)
    return x * x
end

function shapes.circle(radius)
    return math.pi * square(radius)
end

function shapes.rectangle(width, height)
    return width * height
end

return shapes
```

The functions `circle` and `rectangle` are fields of the returned table, so other files may call them. The function `square` is a local variable of the file and stays invisible outside it.

### Loading a module with `require`

[`require`](/manual/api#require) takes the name of a module, which is its file name without the extension, and returns the value the file returned. Loading a module file requires the `load` and `fs:read` [permissions](#permissions). The following program sits in the same directory as `shapes.lus`.

```lus nocheck
pledge("load", "fs:read")

local shapes = require("shapes")
print(shapes.rectangle(3, 4))                       --> 12
print(string.format("%.2f", shapes.circle(1)))      --> 3.14
print(require("shapes") == shapes)                  --> true
```

`require` runs a module file once. It remembers the result, and every later `require` of the same name returns the same value without reading the file again, as the last line shows. A module is therefore also a place for state that the whole program shares, such as a cache or a configuration table.

A program that needs only some functions of a module takes them with [`from`](#destructuring-with-from), which declares one local variable for each named field.

```lus nocheck
pledge("load", "fs:read")

local circle, rectangle from require("shapes")
print(rectangle(2, 5))   --> 10
```

### Search paths

`require` finds a module file through [`package.path`](/manual/api#package.path), a string of file name templates separated by semicolons. In each template, `require` replaces the `?` with the module name and tries the resulting file. The first file that exists is the module.

```lus
print(package.path)   --> ./?.lus;./?/init.lus;./?.lua;./?/init.lua
```

With this default, `require("shapes")` tries `./shapes.lus`, then `./shapes/init.lus`, and then the same two names with the `.lua` extension. The paths start at the working directory, which is the directory the program was started from. A dot in a module name stands for a directory separator, so `require("geometry.units")` tries `./geometry/units.lus` first. When no template leads to a file, `require` raises an error that lists every file it tried.

A project that keeps its modules elsewhere adds a template. A program may assign to `package.path` before its first `require`, as in `package.path = "./lib/?.lus;" .. package.path`. The environment variable `LUS_PATH` does the same from outside the program: when it is set, its value is the starting value of `package.path`.

```bash
LUS_PATH="./lib/?.lus;./?.lus" lus main.lus
```

### Preincluded modules

A program that handles untrusted input often gives up its permissions once it has started, as [Permissions](#permissions) explains. Such a program can no longer `require` a module file, because reading and running a file are exactly what it gave up. A _preincluded module_ solves this. The `--include` option of the `lus` command names a module file, and the interpreter reads and compiles that file at startup, before the program runs. `require` later returns the module from memory and needs no permission at all.

The following command starts `server.lus` with `shapes.lus` preincluded.

```bash
lus --include shapes.lus server.lus
```

The program may then seal its permissions in its first line and still load `shapes`. A module that was not preincluded cannot be loaded.

```lus nocheck
pledge("seal")

local shapes = require("shapes")
print(shapes.rectangle(2, 5))               --> 10
print((catch require("geometry.units")))    --> false
```

`--include` may appear several times. `--include path/to/file.lus:name` gives the module the name after the colon. `--include lib` names a directory and preincludes every module file below it, each named by its path with dots, so `lib/geometry/units.lus` becomes the module `lib.geometry.units`.

### Standalone executables with `lus build`

`lus build` turns a program and its modules into a single executable file, which runs on a machine that has neither Lus nor the source files.

```bash
lus build -o app main.lus
```

The command follows every `require` whose argument is a literal string, such as `require("shapes")`, and bundles those modules with `main.lus`. A module that the program loads under a computed name is added with `--include`, which takes the same forms as it does for `lus`. Inside the executable, `require` returns bundled modules from memory, without the `load` and `fs:read` permissions. [Developer tools](/manual/tools) describes `lus build` in full.

## The environment

The _environment_ of a piece of code is the set of global names it sees: `print`, `math`, `string`, and the globals of the program. Lus keeps these names in an ordinary table. A program may read that table, give a piece of code a different one, or make it read-only.

### Globals as a table

Every global variable is a field of one table, and the global `_G` holds that table. Reading the global `score` and reading `_G.score` are the same operation. The table form is useful when the name of a global is known only while the program runs, or when a program needs to list its globals.

```lus
score = 10
print(_G.score)        --> 10

local name = "score"
print(_G[name])        --> 10
print(_G.print == print)   --> true
```

The compiler reaches the table through a variable named `_ENV`. Any name that is not a local variable is read as a field of `_ENV`, so `score` means `_ENV.score`. At the start of a program, `_ENV` and `_G` are the same table. A block that declares its own local `_ENV` gives the code inside it another set of globals.

```lus
score = 10

local function isolated()
    local _ENV = { print = print }
    print(score)       --> nil
    answer = 42
    return _ENV.answer
end

print(isolated(), answer)   --> 42  nil
```

Inside `isolated`, the global `score` is unknown, and the assignment to `answer` writes into the small table and leaves the globals of the program untouched.

### Running code with its own environment

Some programs run code they receive as text: a formula from a configuration file, a rule typed by a user, or a plugin. [`load`](/manual/api#load) compiles a string of Lus code and returns it as a function. Its fourth argument is the environment of that code, a table that holds the only global names the code can use. `load` requires the `load` permission.

```lus
pledge("load")

local formula = "return price * quantity * 0.9"   -- text from a user or a file
local compute = load(formula, "formula", "t", { price = 20, quantity = 3 })
print(compute())   --> 54.0
```

The second argument names the code in error messages. The third argument, `"t"`, makes `load` accept source text only, which is the right setting for text from an untrusted party. If the text does not compile, `load` returns `nil` and the error message.

The environment decides which names the loaded code sees. Code that receives `{ math = math }` can compute and has no `os`, `io`, `fs`, or `network` to call. Permissions add a second, independent limit on what the code can do. The following function loads a piece of text into the given environment and runs it in a coroutine that first rejects every permission and seals the set. The rejection ends with the coroutine, so the rest of the program keeps its permissions.

```lus
pledge("load", "fs:read")

local function run_untrusted(source, env)
    local chunk, message = load(source, "untrusted", "t", env)
    if not chunk then
        return false, message
    end
    local co = coroutine.create(function()
        pledge("~fs", "~network", "~exec", "~env", "~load", "seal")
        return chunk()
    end)
    return coroutine.resume(co)
end

print(run_untrusted("return math.max(2, 7)", { math = math }))
--> true  7
print(run_untrusted("return os.getenv('HOME')", { math = math }))
--> false  untrusted:1: attempt to index a nil value (global 'os')
print(run_untrusted("return fs.list('.')", { fs = fs }))
--> false  untrusted:1: permission "fs:read" denied for '.'
```

The second call fails because the environment has no `os`. The third call shows the second limit: the code was handed the real `fs` library, and the operation still fails because the coroutine rejected the permission. Neither limit bounds how long the loaded code runs or how much memory it uses, so a loop that never ends still never returns.

### The `--readonly-env` option

In a large program, any function may assign to a global or replace a library function, and every other part of the program then sees the change. The cause may be a forgotten `local` or a module that redefines `print` for its own purposes, and the effect appears far from the cause. The `--readonly-env` option of `lus` prevents this. Once the interpreter has started, the table of globals and the library tables in it, such as `math` and `string`, are read-only.

```bash
lus --readonly-env script.lus
```

Under this option, each of the commented lines in the following script raises the error `attempt to modify a readonly table`.

```lus nocheck
local total = 0              -- local variables work as usual
local list = { 1, 2, 3 }
list[4] = 4                  -- tables that the program creates stay writable

counter = 1                  -- error: creates a global
math.pi = 3                  -- error: changes a library table
print = nil                  -- error: replaces a global
setmetatable(math, {})       -- error: a metatable could redirect every access
```

A program that runs under `--readonly-env` keeps its state in local variables and in the tables of its modules, which stay writable.

### Build flags

One source file often has to behave in two ways: with extra logging while it is developed and without it in production, or with a feature that only test builds include. A _build flag_ is a named value given on the command line with `-F`. The program reads it from the table `flags`, which exists in every file without a declaration and is read-only.

```bash
lus -Fdebug -Flevel=3 -Fchannel=beta script.lus
```

A flag without a value is `true`. A value that reads as a number becomes a number, and any other value is a string. A flag that was not given reads as `nil`. With the command above, `flags.debug` is `true`, `flags.level` is `3`, and `flags.channel` is `"beta"`.

```lus
if flags.debug then
    print("debug build")
end
print("level", flags.level or 1)   --> level  1
```

Run without flags, this program prints only the level. An `if` whose condition is a flag alone, as in `if flags.debug then` or `if not flags.debug then`, is decided when the file is compiled, and the branch that the flags rule out is left out of the compiled code. Debugging code under such an `if` therefore costs nothing in a run without the flag.

`lus build` accepts `-F` as well and stores the flag values in the executable, which then always runs with them. [Developer tools](/manual/tools) describes `lus build`, and [CLI](/manual/cli) lists every option of the `lus` command.

## The standard library

The standard library is the set of functions that every Lus program can call without loading anything. It is compiled into the `lus` executable, and its functions are grouped into global tables such as `string`, `table`, and `math`. A few functions that almost every program uses, such as `print`, `tostring`, and `fromjson`, are plain globals.

Functions that read or write files, contact the network, read environment variables, or start processes need a [permission](#permissions), which the program asks for with `pledge`.

### `string`

The `string` library works on text. It measures, slices, searches, replaces, splits, and formats strings, and its pattern functions take apart text that follows a known form. [Strings and patterns](#strings-and-patterns) shows its functions at work, and the [string library reference](/manual/api#string-library) lists every one.

### `table`

The `table` library holds the operations on lists, starting with `table.insert`, `table.remove`, `table.sort`, and `table.concat` from [Lists](#lists).

The comparison function of `table.sort` can order records by several fields. The following call sorts people by age, and by name among people of the same age.

```lus
local people = {
    { name = "Mira", age = 31 },
    { name = "Tom", age = 25 },
    { name = "Ada", age = 31 },
}

-- Youngest first. People of the same age are ordered by name.
table.sort(people, function(a, b)
    if a.age ~= b.age then
        return a.age < b.age
    end
    return a.name < b.name
end)

for _, person in ipairs(people) do
    print(person.name, person.age)
end
--> Tom  25
--> Ada  31
--> Mira  31
```

When the order depends on one value per element, [`table.sortby`](/manual/api#table.sortby) is shorter. It takes a function that returns the sort key of an element, and a third argument of `false` sorts in descending order.

```lus
local words = { "pear", "fig", "banana", "kiwi" }
table.sortby(words, function(word) return #word end)
print(table.concat(words, " "))  --> fig pear kiwi banana
```

[`table.move`](/manual/api#table.move) copies a range of elements to another position or into another table. Its most common use is to append one list to another.

```lus
local first, second = { 1, 2, 3 }, { 4, 5 }
table.move(second, 1, #second, #first + 1, first)
print(table.concat(first, " "))  --> 1 2 3 4 5
```

The library also has functions that process a whole list in one call. They replace the loops that most programs would otherwise write by hand.

- [`table.map`](/manual/api#table.map) returns a new list with a function applied to every element.
- [`table.filter`](/manual/api#table.filter) returns a new list with the elements for which a function returns a truthy value.
- [`table.reduce`](/manual/api#table.reduce) combines all elements into one value by calling a function with the result so far and the next element.
- [`table.groupby`](/manual/api#table.groupby) divides the elements into groups. It returns a table that maps each key the function returns to the list of elements with that key.
- [`table.sum`](/manual/api#table.sum), [`table.mean`](/manual/api#table.mean), [`table.median`](/manual/api#table.median), and [`table.stdev`](/manual/api#table.stdev) compute the total, the average, the middle value, and the standard deviation of a list of numbers. Each returns a float.

A planner that holds the length of each task in minutes adds a buffer to every task, totals the day, picks the quick tasks, and finds the longest one.

```lus
local tasks = { 30, 45, 15, 90 }

local buffered = table.map(tasks, function(minutes) return minutes + 10 end)
print(table.concat(buffered, " "))               --> 40 55 25 100
print(table.sum(tasks), table.mean(tasks))       --> 180.0  45.0

local quick = table.filter(tasks, function(minutes) return minutes <= 30 end)
print(table.concat(quick, " "))                  --> 30 15

local longest = table.reduce(tasks, function(best, minutes)
    return minutes > best and minutes or best
end)
print(longest)                                   --> 90
```

The functions above suit a single step on a plain list. To group and summarize records, such as the total sales of each region, a [query](/manual/guide#queries) states the whole computation in one expression. [Data formats](/manual/data#table-functions) describes the remaining table functions, such as `table.zip` and `table.transpose`, and the [table library reference](/manual/api#table-library) lists them all.

### `math`

The `math` library holds the numeric functions that the operators do not cover: rounding, minimum and maximum, roots, trigonometry, logarithms, and random numbers.

[`math.floor`](/manual/api#math.floor) rounds down to the nearest integer and [`math.ceil`](/manual/api#math.ceil) rounds up. [`math.max`](/manual/api#math.max) and [`math.min`](/manual/api#math.min) return the largest and the smallest of their arguments. [`math.abs`](/manual/api#math.abs) returns the absolute value and [`math.sqrt`](/manual/api#math.sqrt) the square root.

```lus
print(math.floor(3.7), math.ceil(3.2), math.floor(-3.7))  --> 3  4  -4
print(math.max(4, 9, 2), math.min(4, 9, 2))               --> 9  2
print(math.abs(-5), math.sqrt(16))                        --> 5  4.0
```

[`math.pi`](/manual/api#math.pi) is the constant π. [`math.huge`](/manual/api#math.huge) is positive infinity, a float that is larger than every other number. It serves as the starting value when a loop searches for a minimum and must also remember which element had it.

```lus
local radius = 2
print(string.format("%.2f", math.pi * radius ^ 2))  --> 12.57

local items = { { name = "tea", price = 8 }, { name = "mug", price = 3 }, { name = "jam", price = 5 } }
local lowest, cheapest = math.huge, nil
for _, item in ipairs(items) do
    if item.price < lowest then
        lowest, cheapest = item.price, item.name
    end
end
print(cheapest, lowest)  --> mug  3
```

[`math.type`](/manual/api#math.type) returns the subtype of a number as a string: `"integer"`, `"float"`, `"bigint"`, or `"decimal"`. [`math.tointeger`](/manual/api#math.tointeger) returns a whole number as an integer, and `nil` for a number with a fractional part, which is how a program checks that a count or a port number is whole.

[`math.random`](/manual/api#math.random) returns a random number. Without arguments it returns a float from 0 up to, but not including, 1. With one integer `n` it returns an integer from 1 to `n`, and with two integers it returns an integer between them, both ends included. The numbers differ on every run of a program. [`math.randomseed`](/manual/api#math.randomseed) with a number makes the sequence repeatable, because the same seed always produces the same numbers. A repeatable sequence is useful in tests and simulations.

```lus nocheck
print(math.random())       --> 0.6394267984578837
print(math.random(1, 6))   --> 4
```

A test of a dice game seeds the generator so that every run rolls the same dice.

```lus
local function roll_three()
    return { math.random(1, 6), math.random(1, 6), math.random(1, 6) }
end

math.randomseed(42)
local first = roll_three()
math.randomseed(42)
local second = roll_three()
print(table.concat(first) == table.concat(second))  --> true
```

The generator is fast and well distributed, but its output can be predicted from earlier output. Passwords, tokens, and keys must come from a cryptographic source, such as the bytes of `/dev/urandom` on Linux and macOS, read as a binary file. The [math library reference](/manual/api#math-library) lists every function, including the trigonometric and logarithmic ones.

### `io`

The `io` library reads and writes files and the standard streams of the program. Opening a file needs the `fs:read` permission, the `fs:write` permission, or both, depending on the mode.

[`io.open`](/manual/api#io.open) opens a file and returns a _file handle_, a value with methods that read, write, and close the file. Its second argument is the mode: `"r"` reads and is the default, `"w"` writes and empties the file first, and `"a"` writes at the end of the file. A handle must be closed when the program is done with it. Declaring the handle with `<close>` closes it when the variable goes out of scope, including when an error ends the block early.

```lus nocheck
pledge("fs")

do
    local file <close> = io.open("notes.txt", "w")
    file:write("first line\n", "second line\n")
end

do
    local file <close> = io.open("notes.txt")
    print(file:read("l"))  --> first line
    print(file:read("a"))  --> second line
end
```

`file:write` writes each of its arguments, which may be strings or numbers, and adds nothing between or after them. `file:read` takes a format that says how much to read. `"l"` reads one line without its line break, `"a"` reads everything that remains, `"n"` reads a number, and an integer reads that many characters. At the end of the file, `"l"` returns `nil`.

[`io.lines`](/manual/api#io.lines) opens a file, returns an iterator over its lines, and closes the file after the last line. It is the shortest way to process a text file line by line. Given a file `stock.txt` that lists a count for each fruit,

```text
apples 3
pears 12
plums 7
```

the following program adds up the counts.

```lus nocheck
pledge("fs:read")

local total = 0
for line in io.lines("stock.txt") do
    local count = line:match("%d+")
    total = total + tonumber(count)
end
print(total)  --> 22
```

When a file cannot be opened, `io.open` returns `nil` and a message, so a program can test the result and decide what to do. `io.lines` raises an error in the same situation.

```lus
pledge("fs")
local file, problem = io.open("/no/such/directory/notes.txt")
print(file)     --> nil
print(problem)  --> /no/such/directory/notes.txt: No such file or directory
```

A program has three standard streams, and each is a file handle that is already open. `io.stdin` is the input, usually the keyboard or a pipe. `io.stdout` is the output that `print` writes to. `io.stderr` is the stream for diagnostics, which stays visible when the output is redirected to a file. [`io.write`](/manual/api#io.write) writes to the standard output without the line break that `print` adds, and [`io.read`](/manual/api#io.read) reads from the standard input with the formats of `file:read`. The following program numbers the lines of its input, which makes it useful at the end of a pipe such as `cat notes.txt | lus number.lus`, and reports its count on the diagnostic stream.

```lus nocheck
local number = 0
for line in io.lines() do
    number = number + 1
    io.write(number, "  ", line, "\n")
end
io.stderr:write(`numbered $number lines\n`)
```

A file opened with a `b` in its mode, such as `"rb"`, is read as raw bytes and returns [vectors](#vector) in place of strings. Text mode checks that what it reads is valid text. The [io library reference](/manual/api#io-library) lists every function and every method of a file handle, and [Text and bytes](/manual/text#files) describes the two modes.

### `os`

The `os` library asks the operating system for the time, the environment, and temporary files, and ends the program.

[`os.time`](/manual/api#os.time) returns the current time as a count of seconds since the start of 1970, which is the form in which most systems store times. Given a table with the fields `year`, `month`, and `day`, and optionally `hour`, `min`, and `sec`, it returns the count for that local date and time. [`os.date`](/manual/api#os.date) turns such a count into text. Its format string uses codes such as `%Y` for the year, `%m` for the month, `%d` for the day, `%H` for the hour, and `%M` for the minute. A format that starts with `!` shows the time in UTC, and any other format shows the local time.

```lus
local release = os.time({ year = 2031, month = 4, day = 12, hour = 9 })
print(os.date("%Y-%m-%d %H:%M", release))          --> 2031-04-12 09:00
print(os.date("!%Y-%m-%d %H:%M:%S", 1700000000))   --> 2023-11-14 22:13:20
```

These functions cover timestamps and simple formatting. The [`time` library](#time) handles time zones, durations, and parsing.

[`os.clock`](/manual/api#os.clock) returns the processor time that the program has used, in seconds. The difference between two readings measures how much work a piece of code took.

```lus nocheck
local start = os.clock()
local sum = 0
for i = 1, 1000000 do
    sum = sum + i
end
print(string.format("%.3f seconds", os.clock() - start))  --> 0.004 seconds
```

[`os.getenv`](/manual/api#os.getenv) returns the value of an environment variable, or `nil` when the variable is not set. Environment variables often hold secrets such as access tokens, so reading one needs the `env` permission. The permission can name the variables that the program may read, as in `pledge("env=HOME")`.

```lus nocheck
pledge("env")
print(os.getenv("HOME"))                  --> /home/ada
local editor = os.getenv("EDITOR") or "vi"
```

[`os.tmpname`](/manual/api#os.tmpname) creates an empty file with a fresh name in the temporary directory of the system and returns its path. It needs the `fs:write` permission. The file stays until the program removes it with `fs.remove`.

[`os.exit`](/manual/api#os.exit) ends the program at once. Its argument is the exit status that the program reports to the shell: `true` or no argument reports success, `false` reports failure, and an integer reports that status. Variables declared with `<close>` are not closed when `os.exit` runs, so a program that holds resources ends by reaching the last line of its script. The block below checks the global `arg`, which is a list of the command line arguments that follow the script name.

```lus nocheck
if #arg == 0 then
    io.stderr:write("usage: lus report.lus FILE\n")
    os.exit(false)
end
```

[`os.platform`](/manual/api#os.platform) returns the name of the operating system, such as `"linux"`, `"darwin"`, or `"windows"`. The [os library reference](/manual/api#os-library) lists every function.

### `utf8`

The `utf8` library converts between characters and their Unicode code points, and it checks that text is valid Unicode. A _code point_ is the number that Unicode assigns to a character, such as 233 for `é`. A Lus string may hold a _lone surrogate_, a code point that is not valid Unicode by itself and that can occur in a file name from Windows. `utf8.len` returns `nil` and the position of such a code point, and `utf8.codes` raises an error when it reaches one, so a program can check text before it passes the text to a system that requires valid Unicode.

[`utf8.char`](/manual/api#utf8.char) builds a string from code points. [`utf8.codepoint`](/manual/api#utf8.codepoint) returns the code points of the characters in a range of a string. [`utf8.codes`](/manual/api#utf8.codes) is an iterator that visits each character with its position and its code point.

```lus
print(utf8.char(233, 9749))        --> é☕
print(utf8.codepoint("héllo", 2))  --> 233
print(utf8.len("héllo"))           --> 5
print(utf8.len("a\u{D800}b"))      --> nil  2

for position, code in utf8.codes("añb") do
    print(position, code)
end
--> 1  97
--> 2  241
--> 3  98
```

The [UTF-8 library reference](/manual/api#utf-8-library) lists every function. To see the bytes that encode a string, convert it to a vector, as the next part shows.

### `vector`

A _vector_ is a buffer of bytes that a program can read and change in place. Strings hold text and cannot be modified, so they are the wrong tool for data that is not text. Vectors are for binary data: the contents of an image or an archive, a network packet, or a file format with fields at fixed offsets. Every library function that produces raw bytes, such as a read from a binary file or from a socket, returns a vector.

[`vector.create`](/manual/api#vector.create) makes a vector of a given size filled with zeros. Offsets into a vector start at 0. [`vector.get`](/manual/api#vector.get) and [`vector.set`](/manual/api#vector.set) read and write single bytes, and `#v` is the size in bytes. [`vector.pack`](/manual/api#vector.pack) and [`vector.unpack`](/manual/api#vector.unpack) write and read numbers that span several bytes. Their format string says how each number is laid out. In the following example, `>I4I4` means two unsigned integers of 4 bytes each, with the most significant byte first.

```lus
-- The header of an image: width and height as 4-byte integers.
local header = vector.create(8)
vector.pack(header, 0, ">I4I4", 640, 480)

print(#header)                                  --> 8
print(vector.get(header, 2), vector.get(header, 3))  --> 2  128

local width, height = vector.unpack(header, 0, ">I4I4")
print(width, height)                            --> 640  480
```

[`vector.fromstring`](/manual/api#vector.fromstring) returns the bytes that encode a string, and [`vector.tostring`](/manual/api#vector.tostring) decodes bytes back into text. The byte count of a string differs from its character count when the text has characters outside ASCII.

```lus
local bytes = vector.fromstring("héllo")
print(#"héllo", #bytes)         --> 5  6
print(vector.tostring(bytes))   --> héllo
```

The `vector.archive` modules compress and decompress vectors with gzip, deflate, Zstandard, Brotli, and LZ4. [Text and bytes](/manual/text#vectors) describes vectors, transcoding, and compression in full, and the [vector library reference](/manual/api#vector-library) lists every function.

### `coroutine`

The `coroutine` library creates and controls coroutines, which are functions that can pause and continue later. [`coroutine.wrap`](/manual/api#coroutine.wrap) turns a function into a generator, and [`coroutine.detach`](/manual/api#coroutine.detach) lets the runtime resume a coroutine whenever the network operation it waits for is ready, so that one program can serve many connections. The `worker` library runs code on other processor cores.

[Coroutines](/manual/guide#coroutines) teaches all three and says when to use each. [Coroutines and workers](/manual/concurrency) is the complete description, and the references are the [coroutine library](/manual/api#coroutine-library) and the [worker library](/manual/api#worker-library).

### `debug`

The `debug` library lets a program inspect itself: which functions are running, from which line, and with which local variables. It exists for diagnostics and for building tools such as debuggers and profilers. Ordinary program logic should not depend on it, because its functions are slow and can read and change variables that the rest of the language keeps private.

The function most programs use is [`debug.traceback`](/manual/api#debug.traceback). It returns a _traceback_, a text that lists the chain of function calls that led to the current line. `lus` prints a traceback by itself when an error ends the program. Calling `debug.traceback` produces one at any other moment, for example to log which caller still uses an old function.

```lus
local stats = {}

function stats.old_total(items)
    print(debug.traceback("old_total is deprecated"))
    return #items
end

function stats.report()
    local count = stats.old_total({ "a", "b" })
    print(`$(count) items`)
end

stats.report()
```

Saved as `report.lus`, the program prints the message followed by one line per active function, the innermost first.

```
old_total is deprecated
stack traceback:
	report.lus:4: in field 'old_total'
	report.lus:9: in field 'report'
	report.lus:13: in main chunk
	[C]: in ?
2 items
```

Each line gives a file, a line number, and the function that was running there. The last line stands for the runtime, which started the script.

[`debug.getinfo`](/manual/api#debug.getinfo) returns a table of facts about one active function, such as its source file and current line. The library also holds the entry points of several tools: [`debug.parse`](/manual/api#debug.parse) returns the syntax tree of Lus source text, and [`debug.format`](/manual/api#debug.format) formats source text as `lus fmt` does. The [debug library reference](/manual/api#debug-library) lists every function.

The `package` library holds the settings of `require`. [`package.path`](/manual/api#package.path) is the list of file name templates that `require` tries when it looks for a module, and [`package.loaded`](/manual/api#package.loaded) is the table of modules that are already loaded. Most programs never touch either. [Modules](/manual/guide#modules) explains `require`, the search path, and how to write a module, and the [package library reference](/manual/api#package-library) lists every field.

### JSON and CSV

JSON and CSV are the two text formats that programs exchange data in most often. JSON carries nested data, such as the body of a web request or a configuration file. CSV carries rows of fields, such as the export of a spreadsheet. Lus reads and writes both with four global functions.

[`fromjson`](/manual/api#fromjson) parses JSON text and returns the matching Lus value. A JSON object becomes a table with string keys, an array becomes a list, and `null` becomes `nil`. [`tojson`](/manual/api#tojson) does the reverse and returns JSON text. A table whose keys are 1 to `n` is written as an array, and any other table is written as an object.

```lus
local order = fromjson('{"id": 17, "items": ["tea", "cup"], "paid": true}')
print(order.id, order.items[2], order.paid)  --> 17  cup  true

order.items[#order.items + 1] = "spoon"
print(tojson(order.items))                   --> ["tea","cup","spoon"]
print(tojson({ total = 12.5 }))              --> {"total":12.5}
```

Text that is not valid JSON raises an error that names the position of the problem. Input that comes from outside the program is therefore parsed inside a `catch`.

```lus
local ok, problem = catch fromjson("{broken")
print(ok, problem)  --> false  JSON parse error at position 2: expected string key in object
```

[`fromcsv`](/manual/api#fromcsv) parses CSV text into a list of rows, where each row is a list of strings. When its second argument is `true`, the first row is taken as the column names, and every other row becomes a table with those names as keys. Fields stay strings, so a program converts the numeric ones with `tonumber`. [`tocsv`](/manual/api#tocsv) writes a list of rows as CSV text and adds quotes around the fields that need them.

```lus
local text = "name,age\nAda,36\nTom,25\n"

local people = fromcsv(text, true)
print(#people, people[1].name, tonumber(people[1].age) + 1)  --> 2  Ada  37

io.write(tocsv({
    { "name", "note" },
    { "Ada", "likes tea, cake" },
}))
--> name,note
--> Ada,"likes tea, cake"
```

[Data formats](/manual/data) describes both formats in full, including exact numbers, filters, and other delimiters.

### The filesystem

The `fs` library manages files and directories as a whole: it lists, creates, copies, moves, and removes them. Reading and writing the contents of a file is the job of `io`. Every `fs` function needs the `fs:read` or `fs:write` permission for the paths it touches, and every function raises an error when it fails.

The following program keeps an old copy of a to-do list. It makes a `backup` directory, copies `notes/todo.txt` into it, and renames the copy. [`fs.path.join`](/manual/api#fs.path.join) builds a path from its parts with the separator of the operating system, which keeps a program portable between Windows and other systems.

```lus nocheck
pledge("fs")

local todo = fs.path.join("notes", "todo.txt")
local copy = fs.path.join("backup", "todo.txt")

fs.createdirectory("backup")
fs.copy(todo, copy)
fs.move(copy, fs.path.join("backup", "todo-old.txt"))

print(table.concat(fs.list("backup"), " "))   --> todo-old.txt
print(fs.type(todo))                          --> file  false
print(fs.type("backup"))                      --> directory  false
print(fs.path.name(todo))                     --> todo.txt
```

[`fs.list`](/manual/api#fs.list) returns the names in a directory in no particular order. A second argument such as `"*.txt"` keeps only the matching names. [`fs.type`](/manual/api#fs.type) returns `"file"` or `"directory"`, followed by whether the path is a symbolic link. It raises an error for a path that does not exist, so a program tests for existence with `catch fs.type(path)`.

[Filesystem](/manual/filesystem) describes every function, symbolic links, and the path helpers, and the reference is the [filesystem library](/manual/api#filesystem-library).

### Networking

The `network` library sends web requests, serves them, and opens plain sockets. Every function checks a `network` permission for the host it contacts.

[`network.fetch`](/manual/api#network.fetch) sends one HTTP or HTTPS request and returns three values: the status code, the body of the response, and its headers. The body is a vector, because a response can hold any bytes, and `vector.tostring` turns it into text. The following program reads one user from a web service.

```lus nocheck
pledge("network:http=api.example.com/*")

local status, body = network.fetch("https://api.example.com/users/17")
if status == 200 then
    local user = fromjson(vector.tostring(body))
    print(user.name)
end
```

The optional arguments after the address are the method, a table of request headers, and a request body, in that order. A status such as 404 is a normal result. An error is raised only when no response arrives, for example because the host does not exist.

[`network.serve`](/manual/api#network.serve) runs a web server. It takes a host, a port, and a _handler_, a function that the server calls once for every request. The handler receives a table that describes the request, with the fields `method`, `path`, `query`, `headers`, and `body`. It returns the status code, the body, and optionally a table of headers. The server handles each connection in its own [detached coroutine](/manual/guide#coroutines), so a slow client does not delay the others. `network.serve` returns only when the server stops.

```lus nocheck
pledge("network:server=127.0.0.1:8080")

network.serve("127.0.0.1", 8080, function(request)
    if request.path == "/time" then
        return 200, tojson({ now = os.time() }), { ["Content-Type"] = "application/json" }
    end
    return 404, "not found\n"
end)
```

A program can also serve on a server socket that it opened itself, which lets it run the server in a [detached coroutine](#detached-coroutines) beside other work.

```lus nocheck
pledge("network")

local function handler(request)
    return 200, "hello\n"
end

local server = network.tcp.bind("127.0.0.1", 8080)
local serving = coroutine.detach(coroutine.create(network.serve), server, handler)
-- the program continues with other work while the server answers requests
```

The `network.tcp` and `network.udp` modules open sockets for protocols other than HTTP. A TCP socket has the methods `send`, `receive`, `settimeout`, and `close`. [Network](/manual/network) describes requests, the server and its limits, sockets, and timeouts, and the reference is the [network library](/manual/api#network-library).

### Time

The `time` library works with dates, clock times, and time zones. `os.time` and `os.date` are enough to stamp a log line. The `time` library is for the questions they cannot answer: what a moment is on the clock of another city, how long it is until a deadline, or what date falls one month after another.

The library separates three kinds of value, because mixing them up is the usual source of date bugs.

- An _instant_ is one moment in time, the same everywhere in the world. [`time.now`](/manual/api#time.now) returns the current instant.
- A _zoned time_ is a date and a clock reading in a particular time zone, such as 09:30 on 29 March in Paris. A _zone_ is a named set of rules such as `"Europe/Paris"`, which includes its daylight saving changes.
- A _duration_ is a length of time, such as 45 minutes.

The following example schedules a call at 09:30 in Paris. It finds the instant of the call, shows that instant on a clock in Tokyo, and computes a reminder 45 minutes earlier.

```lus
local paris = time.zone("Europe/Paris")
local tokyo = time.zone("Asia/Tokyo")

local call = time.zoned({ year = 2030, month = 3, day = 29, hour = 9, minute = 30 }, paris)
print(call:iso())                              --> 2030-03-29T09:30:00+01:00

local moment = call:instant()
print(moment:at(tokyo):format("%A %H:%M"))     --> Friday 17:30

local reminder = moment - time.minutes(45)
print(reminder:at(paris):format("%H:%M"))      --> 08:45
```

Arithmetic on instants counts real elapsed time. Arithmetic on zoned times follows the calendar, through the `add` method. The two differ when the clocks change. In the example, daylight saving time starts in Paris two days after the call, so the same clock time one week later is only 167 hours away.

```lus nocheck
local next_call = call:add({ weeks = 1 })
print(next_call:iso())                                         --> 2030-04-05T09:30:00+02:00
print((next_call:instant() - call:instant()):seconds() / 3600) --> 167.0
```

[`time.parse`](/manual/api#time.parse) reads a date and time from text in the ISO 8601 form, and instants compare with `<` and `==`. [`time.monotonic`](/manual/api#time.monotonic) reads a clock that never jumps, which is the right clock for measuring how long something took.

```lus
local due = time.parse("2030-04-01T12:00:00Z")
local sent = time.parse("2030-03-29T08:30:00Z")
print(sent < due, (due - sent):parts().days)  --> true  3
```

The following program measures how long building a long string takes.

```lus nocheck
local start = time.monotonic()
local text = string.rep("x", 100000)
print(string.format("%.6f seconds", (time.monotonic() - start):seconds()))  --> 0.000041 seconds
```

The zone rules are built into the runtime, so zones work without any permission and give the same results on every system. [Time](/manual/time) describes the three types, formatting, and parsing in full, and the reference is the [time library](/manual/api#time-library).

### SQLite

A _database_ stores data in tables of rows and columns and keeps it on disk between runs of a program. It answers questions such as "all books by this author, oldest first" without the program reading everything into memory, and it keeps the data consistent when several changes belong together. SQLite is a database engine that stores a whole database in one file. It is built into Lus, so a program can use a database without installing or starting anything.

A program talks to a database in SQL, a language of statements. The SQLite site documents the [whole language](https://www.sqlite.org/lang.html).

[`io.sqlite`](/manual/api#io.sqlite) opens a database and returns a database handle. Given a file path, it opens that file and creates it when it does not exist, which needs the `fs:read` and `fs:write` permissions for the file. Given the special name `":memory:"`, it creates a temporary database in memory that needs no permission and disappears when it is closed. A database in memory suits tests and short-lived work. Declaring the handle with `<close>` closes the database when the variable goes out of scope.

A database starts empty. The `CREATE TABLE` statement defines a table: its name, its columns, and the type of each column. `db:exec` runs statements that return no rows.

```lus
local db <close> = io.sqlite(":memory:")

db:exec([[
    CREATE TABLE books (
        id INTEGER PRIMARY KEY,
        title TEXT NOT NULL,
        author TEXT NOT NULL,
        year INTEGER
    )
]])
```

The statements that follow all work on this `books` table, which has four columns. `INTEGER` and `TEXT` are column types. `NOT NULL` means that the column must have a value in every row. `id INTEGER PRIMARY KEY` makes `id` the number that identifies a row, and SQLite assigns the next free number to every new row.

The `INSERT` statement adds a row. The SQL text holds a `?` in place of each value, and the values follow as arguments. Such a `?` is called a _parameter_. `db:run` runs one statement with parameters and returns the number of rows it changed and the `id` of the last inserted row.

```lus nocheck
print(db:run("INSERT INTO books (title, author, year) VALUES (?, ?, ?)", "Emma", "Jane Austen", 1815))
--> 1  1

local author = "Flann O'Brien"
print(db:run("INSERT INTO books (title, author) VALUES (?, ?)", "The Third Policeman", author))
--> 1  2
```

Parameters matter for two reasons. The first is correctness. The name `O'Brien` contains a quote, and a quote ends a text value in SQL. Pasted into the statement, the name would break it. The second reason is security. If a program builds SQL text from input and a user types SQL where a name is expected, the database runs what the user typed. This attack is called SQL injection. A parameter is always treated as a value and never as SQL, so both problems disappear. The following example shows the statement that breaks.

```lus nocheck
local author = "Flann O'Brien"
print(catch db:exec("INSERT INTO books (title, author) VALUES ('x', '" .. author .. "')"))
--> false  near "Brien": syntax error
```

The `SELECT` statement reads rows. It names the columns to return and the table to read. A `WHERE` clause keeps only the rows that satisfy a condition, and `ORDER BY` sorts the result. `db:query` runs a `SELECT` and returns an iterator for a `for` loop. Each row is a table with the column names as keys. A column that holds no value is `nil` in the row.

```lus nocheck
db:run("INSERT INTO books (title, author, year) VALUES (?, ?, ?)", "Persuasion", "Jane Austen", 1817)
db:run("INSERT INTO books (title, author, year) VALUES (?, ?, ?)", "Dracula", "Bram Stoker", 1897)

for book in db:query("SELECT title, year FROM books WHERE author = ? ORDER BY year", "Jane Austen") do
    print(book.title, book.year)
end
--> Emma  1815
--> Persuasion  1817
```

The `UPDATE` statement changes the rows that match a condition, and the `DELETE` statement removes them. Both run through `db:run`, whose first result says how many rows were affected.

```lus nocheck
print((db:run("UPDATE books SET year = ? WHERE title = ?", 1816, "Emma")))  --> 1
print((db:run("DELETE FROM books WHERE year > ?", 1850)))                   --> 1
```

Some changes belong together. Moving money between two accounts takes two `UPDATE` statements, and the data is wrong if only one of them happens. A _transaction_ is a group of statements that the database applies completely or not at all. `db:transaction` takes a function and runs it inside a transaction. If the function returns, every change it made is kept. If it raises an error, every change it made is undone and the error continues to the caller.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER NOT NULL)")
db:run("INSERT INTO accounts VALUES (?, ?)", "ada", 100)
db:run("INSERT INTO accounts VALUES (?, ?)", "tom", 20)

local function transfer(source, target, amount)
    db:transaction(function()
        db:run("UPDATE accounts SET balance = balance - ? WHERE name = ?", amount, source)
        db:run("UPDATE accounts SET balance = balance + ? WHERE name = ?", amount, target)
        for account in db:query("SELECT balance FROM accounts WHERE name = ?", source) do
            if account.balance < 0 then
                error("insufficient funds", 0)
            end
        end
    end)
end

transfer("ada", "tom", 30)
print(catch transfer("tom", "ada", 500))  --> false  insufficient funds

for account in db:query("SELECT name, balance FROM accounts ORDER BY name") do
    print(account.name, account.balance)
end
--> ada  70
--> tom  50
```

The second transfer failed after both `UPDATE` statements had run, and the balances show that neither of them was kept. A transaction also makes many inserts in a row much faster, because the database writes to disk once at the end.

A table of a database can also be the source of a query, as [Queries on a database](#queries-on-a-database) shows.

[SQLite](/manual/sqlite) describes prepared statements, named parameters, how Lus values map to column types, and the permissions of a database file. The reference entry is [`io.sqlite`](/manual/api#io.sqlite).

## Tools

The `lus` executable contains the tools that a project needs besides running code. Each one is a subcommand, so a machine that can run Lus programs can also test, format, and package them. The [command line reference](/manual/cli) lists every option.

### Testing

`lus test` finds and runs tests. A _test_ is a function whose name ends in `_test`, in a file whose name ends in `_test.lus`. A test passes when it returns and fails when it raises an error, so a test checks its expectations with `assert`.

```lus
-- price_test.lus
local function with_tax(amount)
    return amount * 1.2
end

local function tax_test()
    assert(with_tax(100) == 120)
end

local function zero_test()
    assert(with_tax(0) == 0)
end
```

Running `lus test` in the directory of this file runs both tests and prints a summary. When an `assert` fails, the report shows the expression and the values on both sides of the comparison, so the cause is usually visible without adding `print` calls. Each test file runs in its own process, and the files run in parallel.

[Testing](/manual/testing) describes test files, tables of cases, the helpers for errors and recorded output, and how the examples in documentation are tested.

### Formatting and checking

`lus fmt` rewrites source files in one standard layout, so every file of a project has the same layout and changes stay small in version control. `lus fmt --write src` formats the files in place, and `lus fmt --check src` only reports the files that are not formatted.

`lus check` reads source files without running them and reports problems: code that does not compile, and code that compiles but is probably a mistake, such as a variable that is never used or an assignment to a global that was never declared. Each report carries the file, the line, and a code that names the kind of problem.

[Developer tools](/manual/tools) describes both tools and lists the problems that `lus check` reports.

### Documentation

`lus doc` produces reference documentation from comments in the source. A comment that starts with `---` and sits directly above a function describes that function, and lines such as `@param` and `@return` describe its parameters and results. The command writes Markdown or JSON. [Developer tools](/manual/tools#documentation) describes the comment format.

`lus help`, introduced under [Built-in functions](#built-in-functions), prints the reference from the executable itself, so it always matches the installed version.

### Debugging

`lus debug` runs a program under a debugger. A debugger pauses the program at a chosen line, called a breakpoint, and shows the variables and the chain of calls at that moment. It can then run the program one line at a time. The command speaks the Debug Adapter Protocol, which the Lus extension for Visual Studio Code and many other editors use, so the debugging happens in the editor. [Developer tools](/manual/tools#debugger) describes the setup, and [IDE setup](/manual/ide-setup) describes the extension.

### Building executables

`lus build` packages a program, its modules, and the runtime into one executable file for people who do not have Lus installed. ## Embedding

Lus can run inside another program. A game, an editor, or a server written in C, Zig, Rust, or any language that can call C functions links the Lus library and uses Lus as its scripting language. The program that contains Lus is called the _host_. Embedding lets the users of the host change its behavior with scripts while the host stays in control of what those scripts may do.

The host works with Lus through the header `lus.h` and the library `liblus`. It creates a _state_, which is one independent Lus runtime with its own globals and memory. It registers its own functions as Lus globals, runs scripts, and reads their results. The following host offers a function `add` to a script.

```c
#include "lus.h"

static int add(lus_State *L) {
  lus_pushinteger(L, lus_tointeger(L, 1, NULL) + lus_tointeger(L, 2, NULL));
  return 1;
}

int main(void) {
  lus_State *L = lus_newstate();
  lus_openlibs(L);
  lus_grant(L, "fs:read=/srv/data/*");
  lus_pushcfunction(L, add);
  lus_setglobal(L, "add");
  if (lus_dostring(L, "print(add(2, 3))") != LUS_OK)
    lus_pop(L, 1);
  lus_close(L);
  return 0;
}
```

Values travel between the host and a script on a stack that belongs to the state. `add` reads its two arguments from positions 1 and 2 of that stack, pushes one result, and returns the number of results. A new state has no permissions, and the host decides which ones its scripts receive. Here `lus_grant` allows them to read the files under `/srv/data` and nothing else.

[Embedding](/manual/embedding) describes the interface in full, and the [C API reference](/manual/api/c) documents every function. The same interface is what the [WebAssembly build](/manual/webassembly) exports to run Lus in a browser.

## Internals

Knowing how the runtime executes a program helps to predict what each part of a program costs.

The runtime is written in Zig. It has a compiler that turns source text into bytecode, an interpreter that runs the bytecode, two compilers that turn frequently run bytecode into machine code, a garbage collector, and the standard library.

### From source to bytecode

A program is compiled before it runs, in three steps.

1. The _lexer_ splits the source text into _tokens_: names, numbers, strings, keywords, and operators.
2. The _parser_ builds a _syntax tree_ from the tokens. The tree mirrors the structure of the program, with a node for each statement and expression. `lus fmt`, `lus check`, `lus doc`, and the language server of the editors work on this same tree, which is why they agree with the interpreter about what a program means.
3. The _code generator_ walks the tree and emits _bytecode_, a compact list of instructions for a virtual machine. The generator computes constant expressions such as `2 * 3` itself, and it leaves out the branches that a [build flag](/manual/guide#build-flags) rules out.

Every function in the source becomes a _prototype_: its instructions, its constants, and the information that error messages and debuggers need, such as line numbers and the names of local variables. `lus --dis` prints the prototypes of a script. The following script defines and calls a function.

```lus
local function area(width, height)
    return width * height
end
print(area(3, 4))  --> 12
```

Its listing shows two prototypes, one for the script itself and one for `area`.

```
function <area.lus:0> (9 instructions, 0 params+, 5 slots, 1 upvalues, 1 constants)
     0 [  0] varargprep  0 0 0
     1 [  1] closure     0 0
     2 [  4] gettabup    1 0 0
     3 [  4] move        2 0 0
     4 [  4] loadi       3 3
     5 [  4] loadi       4 4
     6 [  4] call        2 3 0
     7 [  4] call        1 0 1
     8 [  5] ret0        0 0 0
function <area.lus:1> (3 instructions, 2 params, 3 slots, 0 upvalues, 0 constants)
     0 [  2] mul         2 0 1
     1 [  2] ret1        2 0 0
     2 [  3] ret0        0 0 0
```

Each instruction is 32 bits wide and holds an operation code and up to three operands. The number in brackets is the source line. Most operands name _registers_. A register is a numbered slot that belongs to one call of a function, and it holds a local variable or an intermediate result. In `area`, the parameters are registers 0 and 1, and `mul 2 0 1` multiplies them into register 2, which `ret1` returns. A machine of this kind is called a _register machine_. It needs fewer instructions than a machine that pushes and pops every operand on a stack, since one instruction reads its operands and writes its result where they already are.

At run time, a function value is a _closure_: a prototype together with the variables that the function captures from the code around it, which the listing calls _upvalues_. The instruction `closure` creates one. The script itself has one upvalue, the table of global variables, and `gettabup` reads the global `print` from it.

`lus compile` saves the bytecode of a script to a file, and `lus build` stores it inside an executable. Both skip the three steps above when the program starts.

### Value representation

Every value that a program handles is stored in 16 bytes: 8 bytes of _payload_ and a _tag_ that says what type the payload has. For `nil`, booleans, integers, and floats, the payload is the value itself. Such values are stored _inline_. Creating one allocates no memory, and copying one copies 16 bytes.

For every other type, the payload is the address of an _object_ in the heap, the region of memory that the garbage collector manages. Strings, tables, functions, coroutines, vectors, bigints, and decimals are objects. Each object starts with a header that holds its type and the bits that the collector needs. Assigning a table to a second variable copies the 16-byte value, so both variables refer to one object.

The tag is what makes the fast paths cheap. To add two values, the interpreter and the compiled code compare two tags and then add two payloads. Integers keep all 64 bits and floats are standard double precision numbers, with no bits taken away for the tag.

### String representation

A string is an immutable object that holds its text as bytes in the WTF-8 encoding. WTF-8 is UTF-8, the common encoding of Unicode text, extended to allow the unpaired surrogate code points that file names on Windows and text from JavaScript can contain. Such text passes through Lus unchanged. Raw bytes that are not text belong in a vector.

A string indexes by character, and a character takes one to four bytes in this encoding, so finding the tenth character takes more than adding ten to an address. The string object handles this in three ways.

- It stores its character count, so `#s` is a single read.
- It records whether it is pure ASCII. In an ASCII string every character is one byte, so any position is found at once. Most strings in most programs are ASCII.
- A longer string with other characters builds a _character index_ the first time a program indexes into it. The index records the byte position of characters at regular intervals, so finding a position takes one lookup and a short scan. The index also remembers the last positions it found, which makes a loop that walks forward through a string, as a tokenizer does, proceed without rescanning.

Short strings are _interned_: the runtime keeps a table of all of them, and creating a string that already exists returns the existing object. Two interned strings are equal exactly when they are the same object, so comparing them compares two addresses, and a table lookup with a string key such as a field name compares addresses as well. The hash of a string is computed once and stored in the object. Long strings are not interned when they are created, since a long text such as a line of a file is rarely created twice, and they compare by hash and content.

Functions that build a long result, such as `table.concat` and the `..` operator, compute the final length first where they can and write the pieces directly into the new string.

### Table representation

A table has an array part for its keys 1, 2, 3, and up, and either a hash part or a shape for its other keys. A program cannot tell these forms apart.

The _array part_ holds the values for the keys 1, 2, 3, and so on, in a contiguous block of memory, without storing the keys. Reading `t[i]` is a bounds test and a load. The array part also adapts to its content. While every element is an integer, or every element is a float, a string, or a table, the part stores bare 8-byte payloads and keeps the common tag once. A list of numbers therefore takes half the memory of a list of full values, and the collector skips it, since numbers refer to nothing. The first value of another kind converts the part to full 16-byte values.

The _hash part_ of a dictionary holds the other keys. It is an array of _nodes_, each with a key and a value, and its size is a power of two. The hash of a key selects a node, and when that node holds another key, the lookup tries the following nodes in order. This scheme is called open addressing with linear probing, and it keeps a lookup inside one small region of memory. When the part fills up, the table is rebuilt at a larger size.

Record-like tables get particular care, since a program that models data creates them in large numbers. The instruction that runs a constructor such as `{ x = 1, y = 2 }` knows the number of fields and makes room for exactly that many. A small table also keeps its parts in the same block of memory as the table object, so creating it is a single allocation.

A table whose keys are all short strings, which describes most records, keeps its keys in a _shape_ and has no hash part. A shape is an ordered list of keys, shared by every table that received the same keys in the same order. The table itself stores only the values, one slot per key, so a million records with the same fields store their field names once. Adding a key moves the table to the shape that extends its own with that key. A table that receives a key of another kind, such as a long string or a table, becomes a dictionary with a hash part.

Field access rarely searches at all, because of the inline caches described under [The interpreter](#the-interpreter). The cache of an instruction such as `point.x` holds the shape it saw and the slot where `x` was. Tables built by the same code share that shape, so the access costs one comparison and one load.

A metatable also remembers which metamethods it lacks. A table whose metatable has no `__index` or `__newindex` therefore pays almost nothing for having one.

### The interpreter

The _interpreter_ is a loop that reads one instruction, runs the code for its operation, and moves on to the next. This is how every function starts out, and how code that runs rarely stays.

The registers of all active calls are in one array, the _stack_ of the running coroutine, and each call has a small record called a _frame_ that says which function runs, where its registers start, and where to continue after it returns. A call from one Lus function to another pushes a frame and continues in the same loop, so deep recursion uses the Lus stack, which grows in the heap, and a coroutine can be suspended in the middle of any chain of calls.

A plain interpreter does a lot of work per instruction for a dynamic language. `a + b` must find out whether its operands are integers, floats, or something with an `__add` metamethod, and `point.x` must search a table for the key `"x"`. _Quickening_ is the name for techniques that make an instruction cheaper using what is known about the place where it stands. Lus uses four.

- The code generator picks _specialized instructions_ where it can. It picks a narrower instruction whenever the source allows it. Adding a small constant compiles to `addi`, reading a field with a constant name compiles to `getfield`, and comparing with a constant compiles to its own instruction. Each has a short path for the common case and falls back to the general code for everything else.
- _Fused instructions_ handle pairs that often follow each other. Some pairs of instructions often follow each other, such as the addition at the end of a loop body and the loop instruction after it. The compiler marks the first of such a pair, and the interpreter then runs both in one step.
- _Inline caches_ speed up access by name. Every instruction that reads or writes a field by name has a small record next to the code, its _inline cache_. The cache remembers the shape of the table it saw and the slot where the key was. The next execution compares the shape and loads the slot, which replaces a lookup with one comparison in nearly every case. The same mechanism remembers where a method was found in a class table.
- _Size feedback_ sizes new tables. The instruction that creates a table remembers how large the tables it created became. Later tables from the same place are created at that size at once, which saves growing them step by step.

Arithmetic takes a short path when both operands are integers or floats, which the interpreter sees from their type tags. Any other operand, such as a bigint, a decimal, or a table with a metamethod, takes the general path.

A `catch` costs nothing until an error occurs. Each prototype has a table that maps ranges of instructions to their handlers, and the runtime consults it only when an error is raised.

### The baseline JIT

A _just-in-time compiler_, or JIT, turns bytecode into machine code while the program runs. Machine code avoids the work that the interpreter repeats for every instruction: fetching it, decoding its operands, and jumping to the code for its operation. Lus has two such compilers. The first is the _baseline JIT_, which exists for the aarch64 and x86-64 processors on macOS and Linux. On other systems, the program runs in the interpreter.

Compiling takes time, so only code that runs often is compiled. Every function counts its calls and the iterations of its loops. When the count passes a threshold, the function is _hot_, and the baseline JIT compiles it at once. A loop that is about to run many iterations is counted before it starts, so even a script that is one long loop moves to machine code. The switch happens in the middle of the running function: the interpreter stops between two instructions, and the machine code continues from the same point.

The baseline JIT translates one function at a time, one instruction at a time, in a single pass. For each instruction it emits one of two things.

- For the common cases of frequent instructions, it emits machine code that does the work directly. These cases include integer and float arithmetic, comparisons, a field read or write whose inline cache predicts correctly, an array access with an integer index, and a call to another compiled function.
- For everything else, it emits a call to the routine of the interpreter that implements that instruction.

The second point is how the two stay consistent. The interpreter loop and the per-instruction routines are generated from one definition when the runtime itself is built. When the direct code meets a case it does not handle, such as an operand with a metamethod, it runs the whole instruction in that routine. Metamethods, conversions, error messages, and coroutine switches therefore have a single implementation, and machine code cannot behave differently from the interpreter.

Baseline code keeps every value where the interpreter keeps it, in the registers on the Lus stack, and uses the same frames. Every boundary between two instructions is therefore a point where execution can pass from one to the other in either direction. The garbage collector, tracebacks, the debug library, and coroutines read the same frames whichever one is running. While a debugger is attached, the program runs in the interpreter.

Machine code is stored in memory that the runtime requests from the operating system as executable. The garbage collector frees the code of a function together with the function. A system that refuses executable memory leaves the program in the interpreter.

### The optimizing tier

Baseline code is fast to produce and still does more than necessary. It stores every intermediate result back to the stack, and it tests the type of every operand each time. Code that stays hot after it was compiled once is compiled a second time by the _optimizing tier_, which spends more time to produce better code. Baseline code counts its own calls and loop iterations for this purpose. The optimizing tier compiles either a whole function or, when a loop inside a long-running function becomes hot, the code from that loop onward.

The optimizing tier works from predictions. It compiles while the function is running, so it can look at the actual values in the registers, at the tables they refer to, and at the cache records of the interpreter. From these it predicts the type of each value: this register holds an integer, this table has its field `x` at that position, this call always reaches the same function. It then produces machine code that is correct only when the predictions hold, and puts a _guard_ in front of each use. A guard is a short test of one prediction.

Within the guarded code, the compiler can do what the baseline JIT cannot.

- It keeps numbers in processor registers in _unboxed_ form, as the bare integer or float without its type tag, and writes them to the Lus stack only when something needs them there.
- It represents the function in _static single assignment_ form, in which every value is assigned exactly once. This form makes it visible where each value comes from, and standard optimizations follow from it: a table field that is read twice is loaded once, a computation that gives the same result on every iteration moves in front of the loop, and results that nothing uses are removed.
- In a loop that walks over an array with a counting `for`, it checks once before the loop that every index lies inside the array, and the loop body then loads elements without further bounds tests.
- It compiles a small function into its caller, which removes the call. A call to a larger optimized function, or a recursive call, becomes a plain machine call that passes its arguments in processor registers, when the called function needs no frame of its own while it runs.

When a guard fails, the prediction was wrong for this execution, and the optimized code cannot continue. The runtime then _deoptimizes_. It writes every value from the processor registers back to its place on the Lus stack, rebuilds the frames of any functions that were compiled into their callers, and continues in baseline code at the instruction the guard belongs to. Guards are placed before an instruction has any effect, so the instruction runs again from its start and nothing happens twice. The program observes nothing except the time it takes.

Each failed guard is recorded. A place that fails repeatedly causes the function to be compiled again with the new information. A place that keeps failing after that is compiled in its baseline form inside the optimized code, so one unpredictable operation does not cost the rest of the function its speed.

The optimizing tier stays consistent with the interpreter in the same way the baseline JIT does. An instruction that it has no typed form for is emitted with the baseline JIT's own translation, and every case that a guard rejects ends in baseline code, which ends in the routines of the interpreter.

The environment variable `LUS_JIT` selects what runs: `off` uses the interpreter only, `baseline` adds the baseline JIT, and `on`, the default, adds both compilers. The setting changes speed and nothing else, which makes it a useful test when a program behaves unexpectedly. [`debug.jit`](/manual/api#debug.jit) reports the setting and whether a given function has been compiled.

### The WebAssembly build

The runtime also compiles to a WebAssembly module, which runs Lus in browsers and in other WebAssembly hosts. The playground on the website and the Lus extension for Visual Studio Code use it. The module contains the same compiler, interpreter, and collector as the native runtime. It leaves out the network and worker libraries, which the WebAssembly environment cannot support.

A WebAssembly program cannot write machine code into its own memory and run it, so the native compilers do not apply. The WebAssembly build has its own baseline JIT, which produces WebAssembly. For each hot function it emits a small WebAssembly module, and it passes the module to the JavaScript code that hosts the runtime. That code asks the browser engine to compile the module and installs the result where the runtime can call it. The engine then turns it into real machine code. The translation follows the design of the native baseline JIT: direct code for the common cases, and a call to the interpreter's routine for the rest.

A host that offers no way to compile modules, such as a plain command line WebAssembly runner, runs everything in the interpreter. [WebAssembly](/manual/webassembly) describes how to load and use the module.

### The garbage collector

A program never frees memory itself. The _garbage collector_ finds the objects that the program can no longer reach and reuses their memory. Its work has two phases. _Marking_ starts from the _roots_, which are the stacks, the globals, and a few internal tables, and follows every reference to mark each object that is still reachable. _Sweeping_ then goes through the heap and frees every object that was not marked.

The collector of Lus has four properties that shape the rest of the runtime.

It is **precise**. The collector knows of every word in every object whether it is a reference, because every value carries its tag. It never mistakes a number for an address, so it never keeps a dead object alive by accident.

It is **non-moving**. An object stays at one address from its creation to its death. Machine code can therefore contain the addresses of objects, inline caches stay valid, and a C host can hold a pointer to the contents of a string. The cost is that the heap cannot be compacted. The collector limits fragmentation by grouping objects of the same size into the same pages of memory, where a freed slot fits the next object of that size exactly.

It is **generational**. Most objects die soon after they are created: temporary strings, intermediate tables, and closures used once. The collector therefore divides objects into _young_ ones, created since the last collection, and _old_ ones, which survived a collection. A _minor collection_ marks and sweeps only the young objects, and its cost depends on how many of them survive and not on the size of the heap. An object that survives becomes old. A _major collection_ examines the whole heap and runs much less often, when the old generation has grown enough.

A minor collection must know about old objects that refer to young ones, since it does not trace the old ones. The runtime records them as they arise. Every store of a reference into an object runs a short test called a _write barrier_, and when the object is old, the barrier adds it to a list that the next minor collection traces. The interpreter and the code from both compilers run the same barrier.

It is partly **parallel**. Marking a large heap is the expensive part of a major collection. When a collection runs while the program is paused and has enough work, the collector spreads the marking over several threads of the processor. Each thread takes a share of the objects to trace, and they pass work to one another when one runs out. A small heap is marked by one thread, since starting helpers would cost more than it saves. Sweeping is _lazy_: after marking, the pages of the heap are swept one at a time as the program allocates from them, so the cost of sweeping is spread over the allocations that follow.

The collector decides when to run from the amount of live data. After a collection it measures what survived and lets the heap grow by a proportion of that before the next one. The option `--gc-pause` of `lus` sets the proportion, which trades memory for time. For a program that cannot tolerate the pause of a major collection on a large heap, `collectgarbage("incremental")` selects a mode that marks in small steps between the program's own work. [`collectgarbage`](/manual/api#collectgarbage) lists the controls.

Finalizers and weak tables, described in [Metatables and objects](/manual/guide#metatables-and-objects), are handled at the end of marking: an unreachable object with a `__gc` metamethod is kept for one more cycle so that its finalizer can run, and entries of weak tables that refer to dead objects are cleared.

### How coroutines run

A coroutine is an object with its own stack of registers and its own list of frames. Creating one allocates that object and a small stack, and the coroutine runs on the thread of its creator, which is why a program can have many thousands of coroutines.

`coroutine.resume` makes the interpreter run on the stack of the coroutine. `coroutine.yield` leaves every frame of the coroutine in place and returns control to the code that resumed it. The next resume continues after the yield. This works at any depth of calls because the interpreter and baseline code keep calls between Lus functions on the Lus stack, as described under [The interpreter](#the-interpreter). Compiled code takes part in the same way. A yield leaves machine code at a boundary between two instructions, and the resume enters it again at that point.

The runtime's _scheduler_ resumes detached coroutines. The scheduler keeps a queue of coroutines that are ready to run, a list of deadlines for timeouts, and a _poller_, the facility of the operating system that reports which network connections have data to read or room to write. It is kqueue on macOS and epoll on Linux.

Suspension needs no special syntax, because it happens inside the library functions that would otherwise block. A function such as the `receive` method of a socket first tries to read without waiting. If no data is there, it tells the scheduler which socket it waits for and suspends its coroutine through the same mechanism as a yield. The scheduler runs other coroutines, and when the poller reports the socket as readable, it resumes the waiting coroutine, whose `receive` tries again and now succeeds. The Lus code that called `receive` sees a function that returned a result.

The same `receive`, called from the main program, cannot suspend anything. It runs the scheduler from inside the call until its own socket is ready, so the detached coroutines still make progress while the main program waits. All coroutines of a state run on one thread, one at a time, and switch only at these waiting points and at explicit yields. Code between two such points is never interrupted, so coroutines need no locks to share data.

### How workers run

A worker runs Lus code on another thread of the processor, in parallel with its creator. Each worker has a complete runtime state of its own: its own heap, its own garbage collector, its own globals, and its own compiled code. No object is ever reachable from two states.

This separation is the reason the rest of the runtime needs no locks. Tables, strings, inline caches, and the collector assume a single thread, and a collection in one worker does not pause any other. The cost is that data must cross between heaps as messages. A message is transferred in one of three ways, chosen for each value in it.

- Tables, numbers, booleans, and short strings are copied. The sender writes the value into a packet that belongs to no heap, and the receiver rebuilds it in its own heap. Tables that are referenced several times within one message, including cycles, keep their structure.
- A vector is moved. The receiver takes over the buffer of the sender's vector without copying the bytes, and the sender's vector becomes empty.
- A long string is shared. Its bytes are kept once, outside both heaps, with a count of the states that refer to them. Strings are immutable, so sharing them is safe, and a large text passes between workers without being copied.

The threads that help with marking are shared by all states of a process. [Coroutines and workers](/manual/concurrency#workers) describes the worker library.

### Permission checks

The permission system is implemented in the library functions that act on the outside world, and the interpreter and the compilers know nothing of it. A function that opens a file, connects to a host, reads an environment variable, or starts a process calls one check immediately before it acts. The check receives the name of the permission, such as `fs:read`, and the value concerned, such as the path of the file. Compiled code reaches these functions through the same calls as the interpreter, so there is no faster path that skips a check.

Each state has a registry of the permissions that exist. An entry holds the name, the names of its parts such as `read` and `write`, and the kind of value it takes, which decides how a granted value is compared with a requested one: as a path, as a host, or as a pattern. Extensions written in C register their own permissions in the same registry and check them with the same call.

What a program has been granted is its _permission set_. Each coroutine refers to a set, and a new coroutine shares the set of its creator. A set is copied only when a coroutine changes its permissions while others still share the set, so creating a coroutine costs nothing extra and a change inside one coroutine does not affect the others. A worker receives a sealed copy of the set of its creator, which it can never extend.

A check looks up the entry for the exact permission, then the entry for the permission it is part of, so a grant of `fs` covers `fs:read`. An entry granted without a value allows the operation. Otherwise the requested value must match one of the granted values. Paths are compared in a canonical form. A granted path is resolved through symbolic links when the grant is made, and a requested path is resolved again at each check, so a link inside an allowed directory cannot lead an operation outside it. A check that fails raises an error that names the permission and the value, and the operation does not start.

Sealing sets one flag in the set, and every later attempt to change the set is refused. [Permissions](/manual/permissions) is the complete reference for the system as a program sees it.
