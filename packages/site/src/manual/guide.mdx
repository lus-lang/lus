## Welcome!

This handy guide will give you a brief rundown on the language. If you manage to make it through, you will be equipped with a good understanding of the language's internals and know everything necessary to write idiomatic Lus code.

## Variables

Variables in Lus are _dynamically typed_. Any variable can hold any type of value at any time. Its declaration gives it local or global scope.

### Scope

Lus is lexically scoped. The scope of a local variable begins at the first statement after its declaration and extends to the end of its enclosing block. A declaration _shadows_ any outer declaration of the same name within its scope:

```lus
local x = 10
do
  local x = x + 1   -- new 'x' initialized from outer 'x'
  print(x)          --> 11
  do
    local x = x + 1
    print(x)        --> 12
  end
  print(x)          --> 11
end
print(x)            --> 10 (the outer one)
```

Note that in `local x = x`, the new `x` is not yet in scope, so the right-hand side refers to the outer variable.

### Global variables

By default, assigning to an undeclared name creates a global variable. All chunks start with an implicit `global *` declaration that allows this behavior. You can also explicitly declare globals:

```lus
counter = 0         -- implicit global (allowed by default)

global config       -- explicit declaration
config = {}
```

Inside an explicit `global` declaration, every global name is declared explicitly. An undeclared name produces an error, which catches typos and supports strict code.

```lus nocheck
x = 1               -- Ok, global by default
do
  global y          -- voids implicit declaration for this block
  y = 1             -- Ok, y is declared
  x = 1             -- ERROR: x not declared in this scope
end
x = 2               -- Ok, global by default again
```

### Upvalues

Local variables can be accessed by functions defined within their scope. A local variable used by an inner function is called an _upvalue_. Each execution of a `local` statement creates new variables:

```lus
local callbacks = {}
local x = 20

for i = 1, 3 do
  local y = 0
  callbacks[i] = function()
    y = y + 1
    return x + y
  end
end
```

This creates three closures, each with its own `y` but sharing the same `x`.

### Table destructuring

The `from` keyword extracts named fields from a table into variables. The variable names determine which fields are read:

```lus
local point = {x = 10, y = 20, z = 30}
local x, y from point
print(x, y)  --> 10  20
```

The table expression is evaluated once, and missing fields become `nil`. The `from` keyword works with `local`, bare assignment, and `global` declarations:

```lus nocheck
local x, y from getPosition()   -- local declaration
x, y from otherPoint             -- assigns to existing variables
global width, height from getDimensions()
```

Each name reads its field with an ordinary indexed read, so the order of the names is free and an `__index` metamethod applies. A source of `nil` or another value that cannot be indexed raises the usual `attempt to index` error. The source can be any expression, including a call, a field chain, or a parenthesized conditional, and a call runs once however many names it fills:

```lus
local calls = 0
local function config()
    calls = calls + 1
    return { host = "localhost", port = 8080 }
end

local port, host from config()
print(host, port, calls)   --> localhost  8080  1

local size from (false and { size = 10 } or { size = 50 })
print(size)                --> 50
```

The bare assignment form requires each target to be a local, an upvalue, or a global name. A field such as `t.x` as a target is a compile error, `'from' requires simple variable names`.

### Variable attributes

Local variables can carry _attributes_ that modify their behavior. There are two compile-time attributes and a runtime attribute system.

The `<const>` attribute makes a variable immutable after initialization, so any attempt to reassign it is a compile-time error:

```lus nocheck
local MAX <const> = 100
MAX = 200  -- ERROR: attempt to assign to const variable
```

The `<close>` attribute marks a variable as _to-be-closed_. When the variable goes out of scope (whether normally or via an error), its `__close` metamethod is called:

```lus
do
  local f <close> = io.open("data.txt", "r")
  -- use f...
end  -- f:close() called automatically here
```

Runtime attributes use the `<attr>` syntax to attach a function that is called on every assignment. The function receives the variable name and the new value. If it returns a non-nil value, that value replaces the assigned one:

```lus nocheck
local function typed(name, value)
  if type(value) ~= "number" then
    error(`$name must be a number, got $(type(value))`)
  end
  return value
end

local x <typed> = 10     -- ok
x = 20                   -- ok
x = "hello"              -- ERROR: x must be a number, got string
```

The attribute function is not called when assigning `nil`. Multiple runtime attributes can be chained with commas (`<first, second>`) and run in order. Compile-time attributes must come before runtime ones.

An attribute runs on the initialization of the variable and on every assignment to it in the function that declares it. A declaration without an initializer skips it. A `nil` result keeps the value it received, and a `false` result stores `false`. In a chain, each attribute receives the result of the one before it, and the last result is stored:

```lus
local function first(name, value)
    print("first", name, value)
    return value + 1
end

local function second(name, value)
    print("second", name, value)
    return value * 2
end

local x <first, second> = 10   --> first  x  10, then second  x  11
print(x)                       --> 22
```

An assignment made from a nested function through an upvalue stores the value as written, without running the attribute:

```lus
local function scale(name, value)
    return value * 10
end

local x <scale> = 1
local function set(v) x = v end
set(2)
print(x)   --> 2
x = 3
print(x)   --> 30
```

The attribute is any expression that evaluates to something callable, including a call written in the short string form. A function that returns an attribute makes the behavior a parameter, as in `<only "number">` below. The attribute expression runs once, at the declaration and before the initializer, and its value stays alive until the end of the enclosing block. An error raised by an attribute propagates from the assignment, and the variable keeps its previous value.

```lus
local function only(kind)
    return function(name, value)
        if type(value) ~= kind then
            error(`$name must be a $kind`, 0)
        end
        return value
    end
end

local n <only "number"> = 10
local ok, err = catch do
    n = "ten"
end
print(ok, err, n)   --> false  n must be a number  10
```

Runtime attributes apply to a `local` statement with one name. A `local` statement with several names, a `from` declaration, an assignment condition, a group field, or a `global` declaration rejects them with a compile error. Writing a runtime attribute before a compile-time one, as in `<check, const>`, fails with `compile-time attribute 'const' must come before runtime attributes`.

### Local groups

The `<group>` attribute creates a stack-allocated named bundle of fields with dot access, without allocating a heap table:

```lus
local pos <group> = { x = 0, y = 0 }
print(pos.x)  --> 0
pos.x = 10
```

Groups are not first-class values, so they cannot be passed to functions or stored in tables. A group name is usable only as the prefix of a field path such as `pos.x`, as the target of an overwrite, as the initializer of another group, and as a `from` source. Anywhere else, including `print(pos)`, it is a compile error, `cannot pass local group`. You also cannot add new fields after initialization. However, you can perform partial reassignment to update only specific fields:

```lus
local pos <group> = { x = 0, y = 0 }
pos = { x = 5 }    -- only updates x
print(pos.x, pos.y)  --> 5  0
```

The set of fields is fixed when the code is compiled. An overwrite that names a field the group lacks, such as `pos = { z = 1 }`, fails with `'z' is not a field of group 'pos'`. A new group declaration may take another group as its initializer, which copies the current field values. A field initializer is any expression, including a [do expression](#do-expressions):

```lus
local a <group> = {
    x = 1,
    y = do local t = 1 provide t + 1 end,
}
local b <group> = a   -- copies x and y
b.x = 10
print(a.x, b.x, b.y)  --> 1  10  2
```

Each field of a group is a local variable of its own, so a nested function that names a field captures it like any other local. Groups are always local, and `global g <group>` is a compile error.

Groups can contain subgroups and `<const>` fields:

```lus nocheck
local player <group> = {
  name <const> = "Alice",
  pos <group> = { x = 0, y = 0 }
}
player.pos.x = 10    -- ok
player.name = "Bob"  -- ERROR: const field
```

A subgroup is the field marked `<group>`. A field without that attribute whose value is a table constructor holds an ordinary table. A subgroup cannot be overwritten as a whole, so `player.pos = { x = 1 }` and `player = { pos = ... }` are compile errors, while its fields can be assigned one at a time.

## Values

There are eleven types of values in Lus: `nil`, `boolean`, `number`, `string`, `table`, `function`, `thread`, `userdata`, `enum`, `vector`, and `query`.

### `nil`

Nil values, represented by the universal constant `nil`, express the _absence_ of a value. A function result adjusted to a value becomes `nil` when the function returns no values. An absent table field also reads as `nil`. Nil is a first-class value that can be passed as an argument and used wherever absence has meaning.

### `boolean`

Boolean values are `true` and `false`. In conditional contexts, `nil` and `false` are _falsy_. Every other value, including `0` and empty strings, is _truthy_.

### `number`

Numbers in Lus have one type, `number`, with four subtypes. An _integer_ is a 64-bit two's complement value and a _float_ is an IEEE 754 binary64 value, as in Lua. A _bigint_ is an integer of any size, written with an `n` suffix such as `2n` or `0xffn`. A _decimal_ is an exact base 10 number that keeps the digits it was given, written with a `d` suffix such as `19.90d`. [`math.type`](/manual/api#math.type) reports the subtype.

```lus
print(math.type(1), math.type(1.0))   --> integer  float
print(2n ^ 100)                       --> 1267650600228229401496703205376
print(0.1d + 0.2d == 0.3d)            --> true
```

The table below lists the four subtypes.

| Subtype | `math.type` | Representation | Literal |
| --- | --- | --- | --- |
| integer | `"integer"` | 64-bit two's complement | `42`, `0xff` |
| float | `"float"` | IEEE 754 binary64 | `1.5`, `1e9` |
| bigint | `"bigint"` | arbitrary precision integer | `42n`, `0xffn` |
| decimal | `"decimal"` | arbitrary precision base 10 coefficient with a 32-bit exponent | `1.50d`, `3d`, `1e-2d` |

A decimal or hexadecimal integer literal followed directly by `n` is a bigint. The `n` suffix applies only to integer literals, so `1.5n` and `1e3n` are malformed numbers. A numeric literal in decimal notation followed directly by `d` is a decimal, and it keeps its digits exactly as written, so `1.50d` has two fractional digits. Hexadecimal digits include `d`, so `0xffd` is the integer 4093, and a hexadecimal float such as `0x1p4` takes no suffix. An integer literal that overflows 64 bits without a suffix becomes a float, as in Lua.

```lus
print(0xffn, math.type(0xffn))   --> 255  bigint
print(1.50d, 1e-2d, 3d)          --> 1.50  0.01  3
print(0xffd)                     --> 4093
```

Integer arithmetic wraps around on overflow, as in Lua. A program that needs exact results beyond 64 bits uses bigints:

```lus
print(math.maxinteger + 1 == math.mininteger)  --> true
print(bigint(math.maxinteger) + 1)             --> 9223372036854775808
```

All four subtypes compare by mathematical value, so `1 == 1.0`, `1 == 1n`, and `1n == 1.00d` are all true. A decimal also compares exactly with a float, so `0.5d == 0.5` is true and `0.1d == 0.1` is false. A number used as a table key is normalized first. A float or decimal with an integral value and a bigint that fits in 64 bits all become the matching integer key, so `t[1]`, `t[1.0]`, `t[1n]`, and `t[1d]` name the same slot.

```lus
local t = {}
t[1] = "one"
print(t[1.0], t[1n], t[1d])  --> one  one  one
```

Two global functions build exact numbers, and the standard conversions accept them:

- [`bigint(x)`](/manual/api#bigint) converts an integer, an integral float, a decimal with an integral value, or a numeric string to a bigint. A number without an integer value raises `number has no integer representation`.
- [`decimal(x)`](/manual/api#decimal) converts an integer, a bigint, or a numeric string to a decimal exactly. A float converts through the shortest decimal string that reads back as the same float, so `decimal(0.1)` is `0.1d`.
- [`math.tointeger(x)`](/manual/api#math.tointeger) returns an integer when `x` has an integral value that fits in 64 bits, whatever its subtype.
- `tostring` prints a bigint in decimal without a suffix, and a decimal with exactly its stored digits.

```lus
print(bigint("123456789012345678901234567890") * 2)  --> 246913578024691357802469135780
print(decimal("2.50"), decimal(1 / 3))               --> 2.50  0.3333333333333333
print(math.type(math.tointeger(5n)))                 --> integer
```

The [JSON](#json) functions carry bigints and decimals through a document with the option `{ exact = true }`. The rules of arithmetic between the subtypes are in [Arithmetic operators](#arithmetic-operators).

### `string`

Strings are immutable sequences of characters. Every string is well formed WTF-8, the superset of UTF-8 that also encodes lone surrogate code points, so text from any Unicode source round trips without loss. String functions index and measure strings by character: `#"héllo"` is 5 and `string.sub("héllo", 2, 2)` is `"é"`. The [`utf8` library](/manual/api#utf-8-library) works with code points, and [`string.transcode`](/manual/api#string.transcode) converts between text and byte encodings.

Raw bytes live in the [`vector`](#vector) type. `vector.fromstring` returns the bytes of a string and `vector.tostring` decodes bytes back into one. A string literal must be valid text, so an escape such as `\xFF` that would produce an invalid sequence is a compile error.

String literals come in several forms. Single-quoted (`'hello'`) and double-quoted (`"hello"`) strings support escape sequences: `\n` (newline), `\t` (tab), `\\` (backslash), `\"`, `\'`, `\xNN` (a byte of a UTF-8 sequence), `\u{NNNN}` (Unicode codepoint), and `\z` (skip following whitespace). Long strings use `[[...]]` or `[=[...]=]` (with matching equals signs) and preserve their content verbatim:

```lus
local a = "line one\nline two"
local b = [[
This is a long string.
No escapes are processed: \n stays as \n.
]]
```

Backtick strings support _string interpolation_. Use `$name` for simple identifiers and `$(expr)` for arbitrary expressions. Values are converted via `tostring` (which respects `__tostring` metamethods). Backtick strings can span multiple lines:

```lus
local name = "Alice"
local age = 30
print(`Hello, $name!`)                 --> Hello, Alice!
print(`Next year you'll be $(age+1).`) --> Next year you'll be 31.
print(`Multi-line:
  name = $name
  age  = $age`)
```

A `$name` takes only the characters of one identifier, so `` `$t.x` `` interpolates `t` followed by the literal text `.x`. A `$(expr)` keeps only the first value of its expression. The parts are evaluated and converted from left to right. The conversion is the one that `tostring` performs, built into the runtime, so it works the same when the global `tostring` is replaced or `nil`. A `$` followed by a reserved word, as in `` `$nil` ``, is a compile error, and the value is written `` `$(nil)` ``.

### `table`

Tables are the primary data structure in Lus. They contain an array component for sequential access and a map component for keyed access. Both use the same `t[n]` syntax. Numeric keys can use the array component, while other non-nil keys use the map component.

Tables represent arrays, sets, maps, trees, and other structures through automatic dispatch between their array and map components. _Metatables_ define additional behavior for operations such as indexing, comparison, and arithmetic.

Tables are constructed with curly braces:

```lus
local empty = {}
local list  = {1, 2, 3}
local map   = {name = "Alice", age = 30}
local mixed = {"a", "b", x = 10, [true] = "yes"}
```

Tables are covered in depth in [Tables](#tables), and metatables in [Metatables and metamethods](#metatables-and-metamethods).

### `function`

Functions are first-class objects in Lus. They can be assigned to variables, passed as arguments, returned from other functions, and constructed at runtime. A function combines a prototype containing its _code_ with a closure containing its _context_. Captured context values are called _upvalues_.

Functions can return multiple values (`return a, b, c`), accept a variable number of arguments (`...`), and be called with method syntax (`:`) which automatically passes the receiver as the first argument. Functions are covered in depth in [Functions](#functions).

### `thread`

Threads represent _coroutines_, which are lightweight units of execution that can be paused and resumed. They support iterators, generators, and other cooperative control-flow patterns. The type name `thread` is preserved for compatibility. [Workers](/manual/guide#workers) provide concurrent interpreter states scheduled on operating system threads.

### `userdata`

Userdata are pointers to arbitrary data. Like tables, they can receive a metatable to define their behavior. Programs embedding the Lus runtime and parts of the standard library create userdata values. The [`io` library](/manual/api#io-library) uses them for file handles.

### `enum`

Enums define a closed set of named constants. Each declaration creates one interned object per member. Name access such as `Color.Red` and 1-based numeric access such as `Color[1]` return those cached member objects.

Members from one declaration order by declaration position. `Color.Red == Color.Red` is true, while members from different enum declarations remain distinct even when they share a name or position. An ordering comparison between different declarations raises `attempt to compare members of different enums`. Duplicate member names are compile-time errors.

An enum is declared with the `enum ... end` expression, which lists at least one comma-separated name and evaluates to the first member. Every member indexes the whole enum, so `e.x.y` is `e.y` and `e[1][3]` is `e.z`. A name or position outside the enum reads as `nil`. [`tonumber`](/manual/api#tonumber) returns the 1-based position of a member, and `type` returns `"enum"`:

```lus
local priority = enum low, medium, high end

print(priority == priority.low)            --> true
print(priority.low.high == priority[3])    --> true
print(priority.medium < priority.high)     --> true
print(tonumber(priority.high), type(priority.high))  --> 3  enum
```

Members work as table keys and stay distinct from strings and numbers, so `priority.low ~= "low"` and `priority.low ~= 1`. Arithmetic and length raise an error on a member. One `enum` expression yields the identical enum each time it is evaluated, for example in a loop or across calls of the same function, while two separate `enum` expressions always yield distinct enums. An enum holds at most 255 members.

### `vector`

Vectors are resizable byte buffers, and they are the type of all raw binary data in Lus. Binary file reads, network reads, compressed data, the results of `string.pack`, byte encodings from `string.transcode`, and compiled chunks from `string.dump` are all vectors. Vector offsets are zero based. `vector.pack` and `vector.unpack` read and write values of various sizes at given offsets, `vector.get` and `vector.set` access single bytes, and `#v` is the size in bytes. `vector.fromstring` and `vector.tostring` convert between text and its WTF-8 bytes. [Text and bytes](/manual/text) describes how strings and vectors divide the work between text and bytes.

### `query`

Query values are compiled `@` query expressions: first-class, immutable descriptions of a filter, projection, and ordering over one or more sources. A query captures its sources and any values it references when it is built, and nothing runs until the [`query`](/manual/api#query) iterator consumes it, so queries can be stored, passed around, and rerun. Two query values are equal only when they are the same object. [Queries](#queries) describes the query language and its evaluation.

## Operators

### Arithmetic operators

Lus provides the usual arithmetic operators: `+` (addition), `-` (subtraction), `*` (multiplication), `/` (division), `//` (floor division), `%` (modulo), `^` (exponentiation), and unary `-` (negation). When both operands are integers, the result is an integer, and `/` produces a float. If either operand is a float, the other is converted to float before the operation. Integer arithmetic wraps around on overflow.

```lus
print(7 + 3)    --> 10      (integer)
print(7 / 2)    --> 3.5     (always float)
print(7 // 2)   --> 3       (integer floor division)
print(7 % 2)    --> 1       (integer modulo)
print(2 ^ 10)   --> 1024.0  (always float)
print(-3)       --> -3      (negation)
```

Bigints and decimals take part in the same operators. An integer combined with a bigint gives a bigint, an integer or bigint combined with a decimal gives a decimal, and `/` on two decimals gives a decimal rounded to 34 significant digits. Mixing a decimal and a float raises an error, so the program converts one side explicitly with `decimal` or `tonumber`.

```lus
print(2n ^ 64 + 1)  --> 18446744073709551617
print(1.10d * 3)    --> 3.30
print(10d / 4d)     --> 2.5
```

The table below gives the subtype of the result of an arithmetic operation, where the rows and columns are the subtypes of the operands.

| | integer | float | bigint | decimal |
| --- | --- | --- | --- | --- |
| **integer** | integer | float | bigint | decimal |
| **float** | float | float | float | error |
| **bigint** | bigint | float | bigint | decimal |
| **decimal** | decimal | error | decimal | decimal |

Decimal addition, subtraction, and multiplication are exact, so `0.1d + 0.2d == 0.3d` is true. The exponent of a decimal is a 32-bit integer, and an operation whose exact result needs an exponent beyond that range, such as `1e2147483647d * 1e2147483647d`, raises `decimal exponent out of range`. The error for an operation between a decimal and a float is `attempt to mix decimal and float in arithmetic`.

The `/` operator produces a float for integers and bigints, as in Lua. For decimals its result rounds half to even. The `//` and `%` operators keep the subtype from the table and floor toward negative infinity for bigints, as they do for integers. Exponentiation produces a float, except that a decimal or bigint base with a non-negative integer exponent gives an exact result.

```lus
print(1.10d + 2.205d)        --> 3.305
print(1d / 3d)               --> 0.3333333333333333333333333333333333
print(-7n // 2n, -7n % 2n)   --> -4  1
print(2d ^ 10)               --> 1024
print(catch 1.5d + 1.5)      --> false  ...: attempt to mix decimal and float in arithmetic
```

### Relational operators

The relational operators are `==` (equal), `~=` (not equal), `<`, `>`, `<=`, and `>=`. They always produce a boolean. Equality (`==`) compares by value for numbers, strings, and booleans, but by _reference_ for tables, functions, and userdata. Two values of different types are never equal. Numbers compare by mathematical value whatever their subtype, so `1 == 1.0` and `1 == 1n` are true.

Custom equality and ordering behavior can be defined through the `__eq`, `__lt`, and `__le` [metamethods](#metatables-and-metamethods).

### Optional chaining

The `?` suffix operator short-circuits a chain of indexing or call operations when any intermediate value is nil (or false), avoiding nested nil checks. There are four forms:

```lus
local host = config?.server?.host       -- field access
local first = list?[1]                  -- bracket access
local name = user?:getName()            -- method call
local result = callback?()              -- function call
```

If the value before `?` is falsy, the entire remaining chain is skipped and that falsy value is returned. `false` is preserved. Multiple `?` operators can appear in a single chain. A common pattern combines optional chaining with `or` for fallbacks:

```lus
local timeout = config?.database?.timeout or 30
```

The skipped part includes the argument expressions of later calls, which never run. The part of the chain before the first `?` evaluates normally, and a suffix with no `?` before it is unprotected, so `t?.a.b` raises if `t.a` is `nil`. The `?` tests only for `nil` and `false`, so with `local t = true`, `t?.x` raises `attempt to index a boolean value`.

```lus
local data = { items = { { name = "first" } } }
print(data?.items?[1]?.name)   --> first
print(data?.items?[2]?.name)   --> nil

local flag = false
print(flag?.field)             --> false
```

A call after the first `?` produces exactly one value in every context. A chain that contains a `?` is an expression. It cannot be the target of an assignment and it cannot stand alone as a statement, so `t?.a = 1` and `obj?:process()` on their own line are syntax errors. A call kept only for its effect is assigned, as in `local _ = obj?:process()`.

### Logical operators

The logical operators `and`, `or`, and `not` use short-circuit evaluation. Importantly, `and` and `or` return one of their operands rather than a boolean:

```lus
print(1 and 2)        --> 2      (first truthy, return second)
print(nil and 2)      --> nil    (first falsy, return it)
print(1 or 2)         --> 1      (first truthy, return it)
print(nil or 2)       --> 2      (first falsy, return second)
print(not nil)        --> true
print(not 0)          --> false  (0 is truthy)
```

A common idiom is `x = a or default` to provide a fallback value when `a` might be nil.

### String concatenation

The `..` operator concatenates two strings. Numbers are automatically converted to strings when concatenated:

```lus
print("Hello, " .. "world!")  --> Hello, world!
print("value: " .. 42)       --> value: 42
```

For building large strings from many pieces, use [`table.concat`](/manual/api#table.concat) instead, as repeated `..` creates intermediate string objects. Backtick strings support interpolation (see [string](#string) above), which is often cleaner for inline expressions.

### Length operator

The `#` operator returns the length of a string (in characters), the length of a table's sequence (array portion), or the size of a vector (in bytes):

```lus
print(#"hello")       --> 5
print(#"héllo")       --> 5
print(#{10, 20, 30})  --> 3
```

For tables, `#t` returns the length of the _sequence_. If the array portion has holes (nil values between entries), the result is not well-defined. Custom behavior can be defined with the `__len` metamethod.

### Bitwise operators

Lus provides bitwise operators that work on integers: `&` (AND), `|` (OR), `~` (XOR), `<<` (left shift), `>>` (right shift), and unary `~` (bitwise NOT). Floats with an integral value are converted to integers before the operation. On integers the operators act on 64 bits. When either operand is a bigint they act on an unbounded two's complement value and produce a bigint, so `1n << 64` is `18446744073709551616`.

```lus
print(0xFF & 0x0F)   --> 15
print(1 << 4)         --> 16
print(~0)             --> -1   (all bits set)
```

### Operator precedence

Operators are evaluated in the following order, from highest to lowest precedence:

| Precedence | Operators                        |
| ---------- | -------------------------------- |
| 1          | `^`                              |
| 2          | unary `not`, `#`, `-`, `~`       |
| 3          | `*`, `/`, `//`, `%`              |
| 4          | `+`, `-`                         |
| 5          | `..`                             |
| 6          | `<<`, `>>`                       |
| 7          | `&`                              |
| 8          | `~`                              |
| 9          | `\|`                             |
| 10         | `<`, `>`, `<=`, `>=`, `~=`, `==` |
| 11         | `and`                            |
| 12         | `or`                             |

Exponentiation (`^`) and concatenation (`..`) are right-associative. All other binary operators are left-associative. Parentheses override precedence.

## Control flow

### if, elseif, else

The `if` statement executes a block when its condition is truthy. Optional `elseif` and `else` branches handle alternative cases:

```lus nocheck
if x > 0 then
  print("positive")
elseif x < 0 then
  print("negative")
else
  print("zero")
end
```

Only `nil` and `false` are falsy. Values such as `0`, `""`, and empty tables are truthy.

An `if` or `elseif` condition can include an assignment using `=`. The assigned variables are scoped to the entire conditional block (all branches), and the condition succeeds when all assigned values are truthy:

```lus nocheck
if user = findUser(id) then
  print(user.name)
elseif guest = findGuest(id) then
  print(guest.name)  -- 'user' still in scope here (nil)
end
```

Multiple assignments work the same way, so the branch is taken only when every assigned value is truthy: `if a, b = getTwoValues() then`.

The names in a condition are new local variables, so they shadow any outer variable of the same name until the `end` of the statement. A variable declared in the `if` condition or in an `elseif` condition is visible in its own block, in every later `elseif` condition and block, and in the `else` block. The expression list is evaluated in full and adjusted to the number of names, as in a `local` statement, before any value is tested. A call that returns fewer values than there are names leaves the extra names `nil`, which makes the condition false.

```lus
local x = "outer"
if x = 5 then
    print(x)          --> 5
end
print(x)              --> outer

if a, b, c = 1, nil, 3 then
    print("not reached")
elseif d = 4 then
    print(a, b, c, d) --> 1  nil  3  4
end
```

An assignment condition composes with [`catch`](#error-handling), which keeps the status and the result or error object in scope for both branches:

```lus
if ok, value = catch tonumber("42") + 1 then
    print(value)      --> 43
else
    print("failed", value)
end
```

The names in a condition may carry the compile-time attributes `<const>`, `<close>`, and `<group>`. Runtime attributes there are a compile error. A condition may also use `from`, as in `if host, port from settings then`, which reads the fields as described in [Table destructuring](#table-destructuring).

### while

The `while` loop repeats its body as long as the condition is truthy:

```lus
local i = 1
while i <= 5 do
  print(i)
  i = i + 1
end
```

The same assignment syntax works in `while` conditions. The expression is evaluated on each iteration, and the loop exits when any assigned value is falsy. The assigned variables are scoped to the loop body.

```lus nocheck
while line = file:read() do
  process(line)
end
```

The rules of the `if` form apply: the names are new locals, the expression list is adjusted to the names, and the loop runs while every value is truthy. The condition variables are one binding that each iteration assigns again, so closures created in different iterations share them. A local declared in the body and copied from the condition variable gives each iteration its own value.

```lus
local queue = { "a", "b", "c" }
while item = table.remove(queue, 1) do
    print(item)       --> a, then b, then c
end
```

### repeat ... until

The `repeat` loop executes its body at least once, then repeats until the condition is true. Uniquely, the condition can reference local variables declared inside the body:

```lus
local x = 0
repeat
  x = x + math.random(10)
  local msg = `total is $x`
until x > 50
-- 'msg' was visible in the until condition
```

### Numeric for

The numeric `for` loop iterates a variable from a start value to a stop value, with an optional step:

```lus
for i = 1, 5 do       -- 1, 2, 3, 4, 5
  print(i)
end

for i = 10, 1, -2 do  -- 10, 8, 6, 4, 2
  print(i)
end
```

The loop variable is local to the body and cannot be assigned. The start, stop, and step expressions are evaluated once before the loop begins.

The global function [`range`](/manual/api#range) writes the same loop in the form of a generic `for`. `range(a, b, step)` counts from `a` to `b`, the step defaults to 1, and `range(n)` counts from 1 to `n`. When a `for` loop calls `range` directly, the compiler emits exactly the numeric loop above:

```lus
for i in range(1, 5) do       -- 1, 2, 3, 4, 5
  print(i)
end

for i in range(10, 1, -2) do  -- 10, 8, 6, 4, 2
  print(i)
end
```

A direct call follows the rules of the numeric loop: the bounds and the step are evaluated once, the loop variable is local to the body, and an integer loop stays in integers. A negative step counts down, and a step of zero raises `bad argument #3 to 'range' (step must not be zero)`.

Elsewhere `range` returns an ordinary iterator triple that any generic `for` can consume, so it can be stored and passed around. A local or global that shadows `range` is called like any other iterator.

```lus
local iter, state, control = range(2, 10, 2)
for i in iter, state, control do
    print(i)          --> 2, 4, 6, 8, 10
end

for i in range(3) do
    print(i)          --> 1, 2, 3
end
```

### Generic for

The generic `for` loop iterates over values produced by an iterator function:

```lus
local t = {a = 1, b = 2, c = 3}
for key, value in pairs(t) do
  print(key, value)
end

for i, v in ipairs({10, 20, 30}) do
  print(i, v)     --> 1 10, 2 20, 3 30
end
```

The iterator protocol is covered in [Iterators](#iterators).

### break, continue, and goto

`break` exits the innermost enclosing loop:

```lus
for i = 1, 100 do
  if i * i > 50 then
    break
  end
  print(i)
end
```

`continue` skips the rest of the current iteration and starts the next one. In a `repeat` loop it jumps to the `until` condition:

```lus
for i = 1, 10 do
  if i % 3 == 0 then continue end
  print(i)
end
```

`continue` belongs to the innermost loop of the current function: a numeric `for`, a generic `for`, a `while`, or a `repeat`. In a `for` loop it advances to the next value, and in a `while` loop it evaluates the condition again. Before the next iteration starts, it closes the upvalues and to-be-closed variables of the blocks it leaves. Statements may follow it in the same block.

```lus
local attempts = 0
repeat
    attempts = attempts + 1
    if attempts % 2 == 1 then continue end
    print(`even attempt $attempts`)   --> even attempt 2, 4, 6
until attempts >= 6
```

The `until` condition of a `repeat` loop can read the locals of the body. A `continue` that would skip the declaration of such a local is a compile error, because the condition would then read a variable that was never initialized. The loop below fails with `<continue> at line 4 jumps into the scope of 'done'`, and declaring `done` before the `continue` makes it valid:

```lus nocheck
local i = 0
repeat
    i = i + 1
    if i < 3 then continue end
    local done = true
until done
```

A `continue` outside every loop raises `continue outside loop` at compile time. The same error applies to a `continue` inside a function literal nested in a loop, since the function body is not part of the loop. `continue` is a reserved word, so it cannot name a variable or a label.

`goto` jumps to a named label within the same block. Labels are declared with `::name::`. A common use is to leave a nested loop in one step:

```lus
for i = 1, 3 do
  for j = 1, 3 do
    if i * j == 4 then goto done end
    print(i, j)
  end
end
::done::
```

Labels cannot jump into a nested block, out of a function, or into the scope of a local variable.

### Do expressions

A `do`/`end` block is normally a plain scoping block (as seen in the [Variables](#variables) examples). By using the `provide` keyword inside it, the block becomes an expression that evaluates to the provided value:

```lus nocheck
local result = do
  local temp = compute()
  provide temp * 2
end
```

Multiple values can be provided for multiple assignment targets:

```lus nocheck
local x, y = do
  local p = getPoint()
  provide p.x, p.y
end
```

Do expressions combine naturally with `catch` for inline error handling:

```lus
local ok, value = catch do
  provide riskyOperation()
end
```

A `do` in expression position is a do expression, and a `do` at the start of a statement is a plain block. A do expression is an atom, so it may stand anywhere an expression may, as in `1 + do provide 2 end * 3`, which is `7`. Its body is an ordinary scope, and its locals are invisible outside it.

A `provide` may appear at any depth inside the body, including inside loops and `if` branches, and the innermost do expression of the same function receives its values. It ends its block, so a statement after it is a compile error. When it runs, Lus closes the upvalues and to-be-closed variables of the body and leaves the do expression with the provided values. A body that completes without a `provide` produces a single `nil`, and so does an empty `provide`:

```lus
local first = do
    for i = 1, 10 do
        if i * i > 20 then provide i end
    end
    provide -1
end
print(first)                       --> 5

local none = do local unused = 1 end
print(none)                        --> nil
```

A `provide` outside every do expression, including one in a plain `do` block or in a function literal nested in a do expression, fails with `'provide' outside do expression`. `break`, `continue`, `goto`, and `return` inside a do expression act as in any block, and the do expression then produces no value.

## Functions

### Declaration

A function declaration is syntactic sugar for assigning a function value to a variable:

```lus
function greet(name)
  print(`Hello, $name!`)
end
-- equivalent to: greet = function(name) ... end

local function factorial(n)
  if n <= 1 then return 1 end
  return n * factorial(n - 1)
end
-- equivalent to: local factorial; factorial = function(n) ... end
```

The `local function` form pre-declares the variable, which is essential for recursive functions.

### Parameters and arguments

Extra arguments are discarded. Missing arguments become `nil`.

```lus
local function f(a, b, c)
  print(a, b, c)
end

f(1, 2)        --> 1  2  nil
f(1, 2, 3, 4)  --> 1  2  3
```

### Multiple return values

Functions can return multiple values. A function call in the final position of an expression list keeps all its results. A call in an earlier position is adjusted to one result.

```lus
local function two() return 10, 20 end

local a, b = two()       -- a=10, b=20
local t = {two()}        -- t = {10, 20}
local c = two()          -- c=10 (adjusted to one)
print(two(), "end")      --> 10  end (adjusted to one)
print("start", two())    --> start  10  20 (last expr, all kept)
```

Use [`select("#", ...)`](/manual/api#select) to count values and [`select(n, ...)`](/manual/api#select) to access values by index from a variadic argument list.

### Variadic functions

Functions declared with `...` accept a variable number of arguments:

```lus
local function printf(fmt, ...)
  io.write(string.format(fmt, ...))
end

printf("%s is %d years old\n", "Alice", 30)
```

Use [`table.pack(...)`](/manual/api#table.pack) to collect variadic arguments into a table (with an `n` field for the count), and [`table.unpack(t)`](/manual/api#table.unpack) to expand a table back into multiple values.

### Method calls

The colon syntax is sugar for passing the receiver as the first argument:

```lus
local obj = {name = "Alice"}

function obj:greet(greeting)
  print(greeting .. ", " .. self.name)
end

obj:greet("Hello")  --> Hello, Alice
-- equivalent to: obj.greet(obj, "Hello")
```

The `:` can be used in both declaration and call. In a declaration, it implicitly adds `self` as the first parameter.

### Closures

Every function is a closure that captures variables from its enclosing scope. Each call to the enclosing function creates a new closure with its own set of upvalues:

```lus
local function counter(start)
  local n = start
  return function()
    n = n + 1
    return n
  end
end

local c1 = counter(0)
local c2 = counter(10)
print(c1(), c1())  --> 1  2
print(c2(), c2())  --> 11  12
```

See [Upvalues](#upvalues) for more on how captured variables work.

### Tail calls

A `return f(args)` in tail position does not consume a stack frame, allowing unbounded recursion:

```lus
local function find(node, target)
  if node == nil then return nil end
  if node.value == target then return node end
  return find(node.next, target)  -- tail call
end
```

Only `return f(args)` is a proper tail call, so wrapping the call in parentheses or adding operations after it breaks the optimization.

## Tables

### Constructors

Tables are created with constructor expressions using curly braces. Entries can be positional (array), keyed (map), or use arbitrary expressions as keys:

```lus
local empty = {}
local array = {10, 20, 30}
local map   = {x = 1, y = 2}
local mixed = {"a", "b", x = 10}
local expr  = {[1+1] = "two", [true] = "yes"}
```

Positional entries fill indices starting from 1. The last entry may be a function call or `...` that expands to fill multiple positions.

### Array operations

Tables used as arrays are 1-indexed. Use `#t` to get the sequence length and the [`table` library](/manual/api#table-library) for common operations.

```lus
local t = {10, 20, 30}
print(#t)                --> 3

table.insert(t, 40)      -- append: {10, 20, 30, 40}
table.insert(t, 2, 15)   -- insert at index 2: {10, 15, 20, 30, 40}
table.remove(t, 1)       -- remove index 1: {15, 20, 30, 40}
table.sort(t)            -- in-place sort: {15, 20, 30, 40}
```

Removing entries never shrinks a table's storage. After clearing a large table, [`table.compact`](/manual/api#table.compact) releases the unused capacity.

### Map operations

String keys can be accessed with dot syntax, which is sugar for bracket indexing:

```lus
local t = {name = "Alice"}
print(t.name)            --> Alice  (same as t["name"])
t.age = 30               -- add a field
t.name = nil             -- remove a field

-- test if a table has any entries
if next(t) ~= nil then
  print("not empty")
end
```

### Iteration

Use [`pairs`](/manual/api#pairs) to iterate over all entries (in no guaranteed order) and [`ipairs`](/manual/api#ipairs) to iterate the sequential integer keys:

```lus
local t = {a = 1, b = 2, "x", "y"}

for k, v in pairs(t) do    -- all entries
  print(k, v)
end

for i, v in ipairs(t) do   -- sequential: 1="x", 2="y"
  print(i, v)
end
```

The full iterator protocol is covered in [Iterators](#iterators).

### Table cloning

[`table.clone`](/manual/api#table.clone) creates a copy of a table. Without a second argument, it performs a shallow copy (sub-tables are shared references). With `true` as the second argument, it performs a deep copy where all nested tables are fully independent and circular references are correctly reconstructed.

```lus
local original = {1, 2, {3, 4}}
local shallow  = table.clone(original)        -- inner table is shared
local deep     = table.clone(original, true)  -- fully independent copy
print(shallow[3] == original[3], deep[3] == original[3])  --> true  false
```

A deep copy reproduces the shape of the references, so a table that refers to itself produces a copy that refers to the copy:

```lus
local t = {}
t.self = t
local copy = table.clone(t, true)
print(copy.self == copy, copy == t)   --> true  false
```

### Slices

The slice syntax `t[start, end]` extracts a subsequence from a table, string, or vector. Either bound may be omitted. `t[, 3]` starts from 1, and `t[3, ]` ends at the last element. A table produces a new table, a string produces a substring, and a vector produces a new vector. The `__slice(self, start, finish)` metamethod defines custom behavior and receives `nil` for omitted bounds.

```lus
local t = {10, 20, 30, 40, 50}
local a = t[2, 4]   -- {20, 30, 40}
local b = t[, 3]    -- {10, 20, 30}

local s = "hello"
local c = s[2, 4]   -- "ell"
```

The object is evaluated first, then the start bound, then the end bound. A bound must be an integer, a float with an integral value, or a string that converts to one. Any other value raises `slice index must be an integer`. A slice is an expression, so it cannot be the target of an assignment.

Strings and vectors follow the same rules. Positions are 1-based and inclusive, a string counts in characters, and a vector counts in bytes. A start below 1 rises to 1 and an end past the length falls to the length. If the end is below 1 or the start is past the length, the result is empty. If the start is greater than the end, the result runs backward from the start down to the end:

```lus
print(("héllo")[2, 3])        --> él
print(("hello")[4, 2])        --> lle
print(("hello")[0, 100])      --> hello
local v = vector.fromstring("abcdef")
print(vector.tostring(v[1, 3]))  --> abc
```

A table slice reads the positions from the start to the end, stepping backward if the start is greater, and stores them in a new table from index 1. The default end is the border `#t`. Table bounds are not clamped, and a position without a value leaves a hole in the result, so `({1, 2, 3})[0, 2]` holds `1` at index 2 and `2` at index 3. The slice reads each position raw, without `__index`, and copies no keys outside the integer positions. A span of more than 2^26 positions raises `slice span too large`.

A value with a `__slice` metamethod, a table or any other type, calls it with the object and the two raw bounds, with `nil` for an omitted bound, and the first result is the slice. Any other value raises `attempt to slice a TYPE value`.

```lus
local evens = setmetatable({}, {
    __slice = function(self, first, last)
        local result = {}
        for i = first or 1, last do
            result[#result + 1] = i * 2
        end
        return result
    end,
})
print(table.concat(evens[2, 4], " "))  --> 4 6 8
```

## Metatables and metamethods

A _metatable_ is a regular table that defines the behavior of another table (or userdata) when certain operations are performed on it. The functions in the metatable that implement these behaviors are called _metamethods_.

### Setting and getting metatables

Use [`setmetatable`](/manual/api#setmetatable) to assign a metatable and [`getmetatable`](/manual/api#getmetatable) to retrieve it:

```lus
local t = {}
local mt = {}
setmetatable(t, mt)
print(getmetatable(t) == mt)  --> true
```

Setting the `__metatable` field in the metatable makes `getmetatable` return that value instead, and prevents `setmetatable` from modifying it. This is useful for protecting objects from external tampering.

### Indexing metamethods

When you access a key that does not exist in a table, Lus looks for an `__index` metamethod. If `__index` is a table, it is searched recursively (forming a prototype chain). If it is a function, it is called with `(table, key)`:

```lus
local prototype = {greet = function(self) print(`Hello, $(self.name)`) end}
prototype.__index = prototype

local obj = setmetatable({name = "Alice"}, prototype)
obj:greet()  --> Hello, Alice
```

The `__newindex` metamethod is triggered when assigning to a key that does not exist in the table. It receives `(table, key, value)` and can be used to intercept or redirect writes.

### Arithmetic metamethods

When an arithmetic operation involves a table (or userdata), Lus calls the corresponding metamethod: `__add`, `__sub`, `__mul`, `__div`, `__mod`, `__pow`, `__unm` (negation), and `__idiv` (floor division). The metamethod receives both operands:

```lus
local Vec2 = {}
Vec2.__index = Vec2

function Vec2.new(x, y)
  return setmetatable({x = x, y = y}, Vec2)
end

function Vec2:__add(other)
  return Vec2.new(self.x + other.x, self.y + other.y)
end

function Vec2:__tostring()
  return `($(self.x), $(self.y))`
end

local a = Vec2.new(1, 2)
local b = Vec2.new(3, 4)
print(a + b)  --> (4, 6)
```

### Comparison metamethods

The `__eq` metamethod defines equality for tables and userdata. The `__lt` (less than) and `__le` (less or equal) metamethods define ordering, which also enables `>` and `>=`. Both operands must share the same metamethod for it to be called.

### Other metamethods

Lus supports many other metamethods:

- `__concat(a, b)`: the `..` operator
- `__len(t)`: the `#` operator
- `__call(t, ...)`: calling a table as a function
- `__tostring(t)`: string conversion (used by [`tostring`](/manual/api#tostring) and [`print`](/manual/api#print))
- `__gc(t)`: finalizer, called when the object is garbage collected
- `__close(t)`: called when a to-be-closed variable goes out of scope
- `__slice(t, start, finish)`: handles the slice syntax `t[i, j]` and receives `nil` for omitted bounds
- `__json(t)`: returns a replacement value for custom JSON serialization through [`tojson`](/manual/api#tojson)
- `__pairs(t)`: custom iterator for [`pairs`](/manual/api#pairs)
- `__mode`: not a function, but a string (`"k"`, `"v"`, or `"kv"`) that makes the table's keys and/or values _weak_, allowing the garbage collector to reclaim them

```lus
-- __call: make a table callable
local Multiplier = setmetatable({}, {
  __call = function(self, x) return x * self.factor end
})
Multiplier.factor = 3
print(Multiplier(10))  --> 30

-- __tostring: readable output
local point = setmetatable({x = 1, y = 2}, {
  __tostring = function(self) return `($(self.x), $(self.y))` end
})
print(point)  --> (1, 2)

-- __json: custom serialization
local mt = { __json = function(self) return {x = self.x, y = self.y} end }
local obj = setmetatable({x = 1, y = 2, internal = true}, mt)
print(tojson(obj))  --> {"x":1,"y":2}
```

### Object-oriented programming

The `__index` prototype chain is the foundation for OOP in Lus. A "class" is simply a table that serves as both the metatable and the `__index` for its instances:

```lus
local Animal = {}
Animal.__index = Animal

function Animal.new(name, sound)
  return setmetatable({name = name, sound = sound}, Animal)
end

function Animal:speak()
  print(`$(self.name) says $(self.sound)!`)
end

-- Inheritance
local Dog = setmetatable({}, {__index = Animal})
Dog.__index = Dog

function Dog.new(name)
  return setmetatable(Animal.new(name, "woof"), Dog)
end

function Dog:fetch(item)
  print(`$(self.name) fetches the $item!`)
end

local d = Dog.new("Rex")
d:speak()         --> Rex says woof!
d:fetch("ball")   --> Rex fetches the ball!
```

The call to `setmetatable(Dog, {__index = Animal})` ensures that methods not found in `Dog` are looked up in `Animal`.

## Iterators

### The generic for loop

The generic `for` loop calls an _iterator function_ on each iteration. The loop:

```lus nocheck
for var1, var2 in iterator, state, initial do
  -- body
end
```

calls `iterator(state, control)` each cycle, where `control` starts as `initial` and takes the value of `var1` on each subsequent call. The loop ends when the first returned value is `nil`.

### pairs and ipairs

[`pairs(t)`](/manual/api#pairs) returns an iterator that traverses all entries of a table using [`next`](/manual/api#next). [`ipairs(t)`](/manual/api#ipairs) returns an iterator that traverses sequential integer keys starting from 1:

```lus
for k, v in pairs({a = 1, b = 2}) do
  print(k, v)       -- unordered
end

for i, v in ipairs({"x", "y", "z"}) do
  print(i, v)       --> 1 x, 2 y, 3 z
end
```

### Stateless iterators

A stateless iterator relies only on the invariant state and the control variable, so no closures or mutable state. This is the most efficient form:

```lus
local function squares_iter(limit, current)
  current = current + 1
  if current > limit then return nil end
  return current, current * current
end

local function squares(n)
  return squares_iter, n, 0
end

for i, sq in squares(3) do
  print(i, sq)  --> 1 1, 2 4, 3 9
end
```

### Stateful iterators

A stateful iterator uses a closure to maintain internal state across calls:

```lus nocheck
local function lines(filename)
  local file = io.open(filename, "r")
  return function()
    local line = file:read("l")
    if line == nil then file:close() end
    return line
  end
end

for line in lines("data.txt") do
  print(line)
end
```

### Coroutine-based iterators

[`coroutine.wrap`](/manual/api#coroutine.wrap) creates an iterator from a function that yields values. This is the most flexible form, suitable for complex traversals:

```lus
local function traverse(node)
  if node == nil then return end
  traverse(node.left)
  coroutine.yield(node.value)
  traverse(node.right)
end

local function inorder(tree)
  return coroutine.wrap(function() traverse(tree) end)
end

for value in inorder(root) do
  print(value)
end
```

See [Coroutines](#coroutines) for the full coroutine API.

## Queries

A _query_ is an expression, written with the `@` sigil, that describes a filter, a projection, grouping, and ordering over one or more sources in clauses that read like SQL. Building a query runs nothing. The [`query`](/manual/api#query) iterator evaluates it in memory over a plain table, or hands parts of it to a backend such as an [SQLite](#sqlite) database.

### Query expressions

The `@source` form begins a query and binds a _row variable_ named after the last name of the source, or after an `as` alias. A source is a name, a dot chain such as `db.users`, a chain with a literal bracket index, or a parenthesized expression. A source that ends in an index or is parenthesized requires `as`. Clauses follow the sources:

```lus
local people = {
    { name = "Ada", age = 36 },
    { name = "Linus", age = 17 },
    { name = "Grace", age = 45 },
}

local adults =
    @people as p
    where p.age > 18
    select p.name, p.age
    order by p.age desc
    limit 100

for row in query(adults) do
    print(row.name, row.age)   --> Grace  45, then Ada  36
end
```

The clause keywords `where`, `select`, `order`, `by`, `limit`, `offset`, `group`, `having`, `as`, `distinct`, `asc`, and `desc`, and the aggregate names, are keywords only inside an `@` query. Outside a query they are ordinary names, so a local called `select` or `count` keeps working. Row variables exist only inside the clauses of their query. Clauses may appear in any order, each clause appears at most once, and the first name that is not a clause keyword ends the query.

The `select` clause always produces a record. `select p.name` yields a record `{ name = ... }` keyed by the field name. Any other expression and every aggregate take a name with `as`, as in `select count(*) as n`. `select p` alone passes the whole source record through unchanged, and a query with no `select` does the same. `select distinct` removes duplicate records from the projection.

Several sources separated by commas form a join whose condition is written in the `where` clause. A join requires a `select` clause:

```lus
local orders = { { cust_id = 1, total = 150 }, { cust_id = 2, total = 50 } }
local customers = { { id = 1, name = "Ada" }, { id = 2, name = "Linus" } }

local big = @orders as o, customers as c
    where o.cust_id == c.id and o.total > 100
    select c.name, o.total

for row in query(big) do
    print(row.name, row.total)   --> Ada  150
end
```

The aggregates are `count`, `sum`, `avg`, `min`, and `max`. `count(*)` counts rows, and `count(expr)` counts the rows where `expr` is not `nil`. In a grouped query every projection must be an aggregate or a group key, so the result is the same with every provider. An `order by` item is an expression with an optional `asc` or `desc`, and the default is ascending. A bare name in `order by` refers to a projection alias, so the query below orders by the computed `total`:

```lus
local sales = {
    { region = "north", amount = 600 },
    { region = "north", amount = 700 },
    { region = "south", amount = 100 },
}

local totals = @sales as s
    select s.region, sum(s.amount) as total
    group by s.region
    having sum(s.amount) > 1000
    order by total desc

for row in query(totals) do
    print(row.region, row.total)   --> north  1300
end
```

### Captured values and host closures

Inside a clause, literals, columns of a row variable, comparisons, boolean logic, arithmetic, string concatenation, and the aggregates become plan nodes that a backend can translate. A name from the enclosing scope, alone or as a dot chain such as `limits.adult`, is captured as a bound parameter. Its value is read once, when the query value is built, so a later assignment to the local leaves an already built query unchanged. The sources are also evaluated once, at build time, while the contents of a source table are read on each run:

```lus
local people = { { name = "Ada", age = 36 } }
local minimum = 40
local older = @people as p where p.age > minimum select p.name
minimum = 0                                   -- the query keeps 40

people[#people + 1] = { name = "Grace", age = 45 }
for row in query(older) do
    print(row.name)                           --> Grace
end
```

Every other expression becomes a _host closure_ that runs in memory once per row: a call, a method call, a row chain deeper than one field such as `p.address.city`, or a constructor. A host closure is an ordinary Lus function, so it sees its upvalues live, and it receives the current row of every source. A bare column is a filter by truthiness, so `where r.active` keeps the rows whose `active` field is truthy.

### Running a query

A query is lazy and read-only. The `query` iterator runs it and is used like `pairs`. Each call to `query(q)` produces a fresh iterator, so a stored query runs again on each loop and observes changes to its sources. A count is written `select count(*) as n`, a single row `limit 1`, and a list is built inside the loop.

The logical pipeline is fixed: fetch each source, join, `where`, `group by`, `having`, `select` and `distinct`, `order by`, then `limit` and `offset`. Every provider follows the same SQL-flavored rules, so the same query returns the same rows wherever it runs:

- A comparison with a `nil` operand is false.
- `nil` orders first in ascending order, and NaN keys order and group with `nil`.
- Integer and float keys unify, so `1` and `1.0` form one group.
- Aggregates skip `nil` values. Over zero rows an aggregate yields an absent field, except `count`, which yields `0`.
- A `nil` value never becomes a field of a record.
- Group and distinct keys must be primitive values, and an integer `sum` raises an error on overflow.

### Sources and providers

A _provider_ evaluates the sources of one kind. A plain table, meaning an array of records, is served by the built-in in-memory provider, which implements every clause. A database opened with [`io.sqlite`](/manual/api#io.sqlite) exposes its tables by indexing the handle, so `db.users` is a source. Any other value becomes a source by supplying a `__query` metamethod that returns an iterator over its rows.

At execution time the engine splits the `where` clause at its top-level `and` into _conjuncts_ and offers each conjunct that names one source and contains no host closure to that source's provider. The SQLite provider translates each conjunct it accepts into a parameterized `SELECT`, and every literal and captured value travels as a bound parameter. It accepts only the shapes whose SQL meaning matches the in-memory engine exactly, so division, booleans in SQL positions, and `not` stay in memory. A join whose sources use different providers fetches each side with its own pushed conjuncts and joins the rows in memory. The engine performs `order by`, `limit`, and grouping in memory for every provider. [`debug.queryplan(q)`](/manual/api#debug.queryplan) returns a description of the split as a string, naming the provider of each source and where each conjunct runs.

```lus nocheck
@db.users as u
    where u.age >= 18 and matches(u.name, "^A")
    select u.name
-- the comparison runs in SQLite, and matches() runs in memory
-- on each returned row
```

### The query value

A query value has type `query`. It holds its sources, captured parameters, and host closures, so a query keeps an otherwise unreachable source alive. Two query values are equal only when they are the same object, a query works as a table key, and `tostring` prints an address. Comparison, length, and arithmetic raise an error, and a query cannot be sent to a worker. A function that builds a query survives `string.dump`, and the plan is rebuilt when the chunk loads.

A query holds at most 8 sources and 200 captured operands, and clause expressions nest at most 64 levels deep. Aggregates appear only in `select` and `having` and cannot nest. Bitwise operators, the length operator, a nested `@` query, and a suffix on a parenthesized clause expression are compile errors inside a clause.
## Coroutines

Coroutines are cooperative threads of execution. Control transfers explicitly through `resume` and `yield`, giving one coroutine execution at a time within its interpreter state.

### Creating and resuming

[`coroutine.create`](/manual/api#coroutine.create) creates a coroutine from a function. [`coroutine.resume`](/manual/api#coroutine.resume) starts or continues it, and [`coroutine.yield`](/manual/api#coroutine.yield) pauses it. Values flow in both directions:

```lus
local co = coroutine.create(function(x)
  print("received", x)      --> received  10
  local y = coroutine.yield(x + 1)
  print("resumed with", y)  --> resumed with  20
  return x + y
end)

local ok, a = coroutine.resume(co, 10)   -- ok=true, a=11
local ok, b = coroutine.resume(co, 20)   -- ok=true, b=30
```

### Coroutine status

[`coroutine.status`](/manual/api#coroutine.status) returns one of four states:

- `"suspended"`: created but not yet started, or yielded
- `"running"`: currently executing
- `"normal"`: resumed another coroutine (waiting for it to yield)
- `"dead"`: finished or stopped with an error

[`coroutine.running`](/manual/api#coroutine.running) returns the currently running coroutine and a boolean indicating whether it is the main thread.

### coroutine.wrap

[`coroutine.wrap`](/manual/api#coroutine.wrap) provides a simpler interface: it returns a function that resumes the coroutine on each call. Errors propagate directly to the caller instead of being returned as a status:

```lus
local next_id = coroutine.wrap(function()
  local id = 0
  while true do
    id = id + 1
    coroutine.yield(id)
  end
end)

print(next_id())  --> 1
print(next_id())  --> 2
print(next_id())  --> 3
```

### Closing coroutines

[`coroutine.close`](/manual/api#coroutine.close) terminates a suspended coroutine, running any pending to-be-closed variables (those declared with the `<close>` attribute). After closing, the coroutine enters the `"dead"` state.

### Detached coroutines

[`coroutine.detach`](/manual/api#coroutine.detach) hands a suspended coroutine to the runtime, which then resumes it by itself. The extra arguments start the coroutine, and `detach` returns the coroutine at once. Detached coroutines take turns in the order in which they became ready. Inside one, [`coroutine.yield`](/manual/api#coroutine.yield) gives the next turn to the others and returns no values.

```lus
local function count(name, n)
    for i = 1, n do
        print(name, i)
        coroutine.yield()
    end
    return name .. " is done"
end

local a = coroutine.detach(coroutine.create(count), "a", 2)
local b = coroutine.detach(coroutine.create(count), "b", 2)

print(coroutine.resume(a))  --> a 1, b 1, a 2, b 2, then: true  a is done
print(coroutine.resume(b))  --> true  b is done
```

[`coroutine.resume`](/manual/api#coroutine.resume) on a detached coroutine waits until it has ended and returns what `resume` always returns for a coroutine that ends: `true` and the results of the body, or `false` and the error. A coroutine that ends before anything resumes it keeps its results until the first `resume` collects them, and a later `resume` finds a dead coroutine. [`coroutine.close`](/manual/api#coroutine.close) cancels a detached coroutine and runs its pending to-be-closed variables.

A blocking operation inside a detached coroutine, such as `receive` on a socket, suspends that coroutine while the others run. The same operation in the main chunk keeps the main chunk waiting and runs the detached coroutines in the meantime. When the main chunk returns, `lus` keeps running the detached coroutines until every one of them has ended.

```lus
local results = {}
local tasks = {}
for i = 1, 3 do
    tasks[i] = coroutine.detach(coroutine.create(function()
        coroutine.yield()
        results[i] = i * i
    end))
end
for i = 1, 3 do
    assert(coroutine.resume(tasks[i]))
end
print(table.concat(results, " "))  --> 1 4 9
```

The error of a detached coroutine belongs to whoever resumes or closes it. When a detached coroutine fails and nothing collects its error, `lus` stops with that error and the traceback of the coroutine, either once the remaining coroutines have ended or when the collector frees the coroutine. [Coroutines and workers](/manual/concurrency) describes detached coroutines in full.

## String patterns

Lus uses its own pattern language for string matching, which is lighter than full regular expressions but covers most common use cases.

### Pattern syntax

| Element         | Meaning                                                   |
| --------------- | --------------------------------------------------------- |
| `.`             | any character                                             |
| `%a`            | letter                                                    |
| `%d`            | digit                                                     |
| `%l`            | lowercase letter                                          |
| `%u`            | uppercase letter                                          |
| `%w`            | alphanumeric                                              |
| `%s`            | whitespace                                                |
| `%x`            | hexadecimal digit                                         |
| `%p`            | punctuation                                               |
| `%c`            | control character                                         |
| `%A`, `%D`, ... | complement of the class (non-letter, non-digit, etc.)     |
| `[set]`         | custom character class (e.g. `[aeiou]`, `[0-9]`, `[^%s]`) |
| `*`             | 0 or more (greedy)                                        |
| `+`             | 1 or more (greedy)                                        |
| `-`             | 0 or more (lazy)                                          |
| `?`             | 0 or 1                                                    |
| `^`             | anchor to start                                           |
| `$`             | anchor to end                                             |
| `(...)`         | capture                                                   |
| `%bxy`          | balanced match between chars x and y                      |

Special characters `( ) . % + - * ? [ ] ^ $` are escaped with `%` (e.g. `%.` matches a literal dot).

### Pattern functions

The [`string` library](/manual/api#string-library) provides four pattern functions.

[`string.find`](/manual/api#string.find) returns the start and end positions of a match:

```lus
local s = "hello world"
local i, j = string.find(s, "world")
print(i, j)  --> 7  11
```

[`string.match`](/manual/api#string.match) returns the captured values (or the whole match if there are no captures):

```lus
local date = "2026-03-04"
local y, m, d = string.match(date, "(%d+)-(%d+)-(%d+)")
print(y, m, d)  --> 2026  03  04
```

[`string.gmatch`](/manual/api#string.gmatch) returns an iterator over all matches:

```lus
for word in string.gmatch("one two three", "%S+") do
  print(word)
end
--> one
--> two
--> three
```

[`string.gsub`](/manual/api#string.gsub) replaces matches with a string, table lookup, or function result:

```lus
local result = string.gsub("hello world", "%w+", string.upper)
print(result)  --> HELLO WORLD
```

### Common patterns

Patterns are _not_ regular expressions, so they lack alternation (`|`), backreferences, and other regex features. However, they handle most practical tasks:

```lus nocheck
-- Match a number (integer or float)
string.match(s, "-?%d+%.?%d*")

-- Match an identifier
string.match(s, "[%a_][%w_]*")

-- Trim whitespace
string.gsub(s, "^%s+", ""):gsub("%s+$", "")
```

## The environment

### \_ENV and \_G

Every chunk in Lus has an implicit upvalue called `_ENV`. Free names (names not bound to any local) are rewritten as `_ENV` lookups: `x` is really `_ENV.x`. By default, `_ENV` points to `_G`, the global table:

```lus
x = 10
print(_ENV.x)   --> 10
print(_G.x)     --> 10
print(_ENV == _G)  --> true
```

### Sandboxing

You can replace `_ENV` with a custom table to restrict what code can access:

```lus
local safe_env = {print = print, math = math}
local chunk = load("print(math.sqrt(16))", "sandbox", "t", safe_env)
chunk()  --> 4.0
```

Loading code requires the `load` permission. The `"t"` mode accepts text only and is the appropriate mode for source from an untrusted party. A binary chunk is a vector produced by [`string.dump`](/manual/api#string.dump), a version-dependent runtime artifact for trusted build and storage paths. Treat every binary chunk as trusted input.

For security-critical sandboxing, the `pledge` function provides fine-grained capability-based access control. Permissions follow a hierarchical naming scheme, so granting a base permission implicitly grants all sub-permissions:

```lus
pledge("fs:read")           -- allow reading files
pledge("network:http")      -- allow HTTP requests
pledge("seal")              -- lock permissions permanently
```

Path and URL restrictions can be added: `pledge("fs:read=/var/log/*")`. Permanent rejection is done with a `~` prefix: `pledge("~exec")` denies command execution forever, even if `seal` has not been called. Permissions can also be pre-granted from the command line:

```bash
lus -Pfs -Pnetwork script.lus
```

Coroutines start with the permissions of their creator. Later permission changes remain local to the parent or coroutine that makes them.

### Readonly environment

The `--readonly-env` option freezes the global environment and the standard library once the interpreter has loaded its libraries and created the `arg` table. It freezes tables to two levels below `_ENV`:

- `_ENV` itself, the global table.
- Every table stored in `_ENV`, such as `math`, `string`, `table`, `io`, `os`, `fs`, `network`, `worker`, and `arg`.
- Every table stored in those tables, such as `network.tcp` and `network.udp`.

A write to a frozen table, including one through `rawset`, raises `attempt to modify a readonly table`. A new global is such a write, so a program under `--readonly-env` keeps its state in locals. Tables that the program creates stay writable. `package.loaded` also stays writable, because `require` stores every module it loads there, and the global bindings stay frozen around it:

```lus nocheck
-- lus --readonly-env script.lus
print(math.abs(-5))                  --> 5
local t = { 1, 2, 3 }
t[4] = 4                             -- a table of the program stays writable

counter = 1                          -- ERROR: attempt to modify a readonly table
math.abs = function(n) return n end  -- ERROR: attempt to modify a readonly table
```

Workers inherit the setting from the interpreter that creates them. The option and [`pledge`](/manual/api#pledge) are independent: a pledge limits the operations a program may perform, and `--readonly-env` keeps the environment that every function shares in place, so the two combine.

### Compile-time flags

The `flags` table holds the values given on the command line with `-F NAME` or `--flag NAME`. A flag without a value is `true`. A value after `=` that reads as a number becomes a number, and any other value, including an empty one, becomes a string. A repeated flag keeps its last value, and a flag that was not given reads as `nil`:

```bash
lus -Fdebug script.lus            # flags.debug == true
lus -Fversion=1.5 script.lus      # flags.version == 1.5
lus -Fname=alpha script.lus       # flags.name == "alpha"
lus --flag channel=beta script.lus
```

The table always exists when `lus` runs a script, even without flags, and it is readonly. `flags` is a reserved name that needs no `global` declaration. Assigning to it raises `attempt to assign to const variable 'flags'` at compile time, declaring it with `global` raises `cannot declare 'flags' (reserved name)`, and writing a field raises `attempt to modify a readonly table` at run time. A local named `flags` shadows it like any other name.

An `if` or `elseif` condition of exactly the form `flags.NAME`, `flags["NAME"]`, `not flags.NAME`, or `not flags["NAME"]` is decided while the chunk compiles. A branch that the flags rule out is still parsed and checked, so a syntax error in it is reported whichever flags are set, and then its code is discarded. When a condition is decided true, the later `elseif` and `else` branches are discarded the same way:

```lus
if flags.prerelease then
    print("this is a pre-release build")   -- compiled only with -Fprerelease
end

if not flags.quiet then
    print("starting up")
end
```

Any other condition, such as a comparison, a parenthesized lookup, or an `and` or `or` chain, compiles normally and reads the table at run time with the same result. `while` and `repeat` conditions and expressions outside a condition never fold:

```lus
if flags.name == "alpha" then   -- read at run time
    print("alpha channel")
end
```

Workers see the same flags as the interpreter that created them, and chunks loaded with [`load`](/manual/api#load) fold against the same table. The flag values are fixed for the lifetime of the process, and the folding decisions are part of the compiled code, so a chunk written by [`string.dump`](/manual/api#string.dump) keeps them. `lus build` accepts `-F` and bakes the flags into the executable, so the bundled program folds with them and reads the same values at run time. `lus compile` folds with the flags of its own `-F` options. Without any, every folded condition is decided as if the flag were absent, whatever flags the interpreter that later runs the chunk has.

## Modules and require

### Using require

[`require`](/manual/api#require) loads and caches modules. On the first call, it searches for the module, runs it, and stores the return value in [`package.loaded`](/manual/api#package.loaded). Subsequent calls return the cached value:

```lus nocheck
local json = require("json")
local data = json.decode('{"x": 1}')
```

The `from` keyword (see [Table destructuring](#table-destructuring)) works with `require` to import specific names:

```lus
local insert, remove from require("table")
```

### Writing modules

A module is simply a file that returns a value. The idiomatic pattern is to build a table and return it:

```lus
-- mymath.lus
local M = {}

function M.add(a, b) return a + b end
function M.sub(a, b) return a - b end

return M
```

### Search paths

`require("name")` consults [`package.searchers`](/manual/api#package.searchers) in this order: [`package.preload`](/manual/api#package.preload), modules preincluded with `--include`, modules bundled into a standalone executable by `lus build`, and source files found through [`package.path`](/manual/api#package.path). The `?` placeholder in a path template is replaced with the module name, with dots turned into directory separators.

```lus
print(package.path)
--> ./?.lus;./?/init.lus;./?.lua;./?/init.lua
```

The `.lus` templates come before their `.lua` compatibility templates. When the environment variable `LUS_PATH` is set, its value becomes the initial `package.path`, and the `-E` option ignores it. Loading a module from a file requires the `load` permission and `fs:read` for the file. Custom searchers can be added to the [`package.searchers`](/manual/api#package.searchers) table.

Modules given with `--include` are compiled when the interpreter starts, so `require` loads them from memory without `load` or `fs` permissions, as [Preincluded modules](#preincluded-modules) describes. For distributing a self-contained program, `lus build` bundles a script and every module it requires by a literal name into a single executable, as [Developer tools](/manual/tools) describes:

```bash
lus build -o app app.lus --include lib/
```

Native code extends Lus through the [embedding API](#embedding-lus), where a host program registers its functions directly. A native module found on `package.cpath` reports that native C libraries are unavailable.

### Preincluded modules

A _preincluded module_ is a module file that the `--include` option names on the command line. The interpreter reads and compiles each one when it starts, before any code runs and before any permission restriction applies, and keeps the module loader in memory. `require` then loads the module without the `load` or `fs` permissions, so a program that seals its permissions can still use the modules it was launched with:

```bash
lus --include json_helpers.lus --include config.lus:cfg app.lus
```

```lus nocheck
pledge("seal")

local cfg = require("cfg")               -- preincluded, loads from memory
assert(not catch require("other"))       -- any other module fails
```

The argument takes three forms:

- `--include path/to/mod.lus` names the module after the file, here `mod`.
- `--include path/to/mod.lus:alias` names the module `alias`.
- `--include path/to/dir` includes every `.lus` and `.lua` file under the directory, recursively, named by its path from the directory, as in `dir.sub.file`.

A missing or unparsable file, or two includes with the same module name, stops the interpreter at startup with an error that names the file or the module. A preincluded module takes part in the module system like any other. Its searcher comes right after `package.preload`, `package.loaded` caches its result, and repeated requires return the same value. Preincluded modules may require each other, and [workers](#workers) see the same preincluded modules as the interpreter that created them, loaded from memory. The module set is fixed by whoever builds the command line, so a sealed program can load exactly that set of modules and no other.

Preincluded modules are compiled from source at startup, so they always match the running interpreter. A compiled chunk from `lus compile` or [`string.dump`](/manual/api#string.dump) carries a format version, and a runtime rejects a chunk of another format with `bad binary format (truncated or corrupted chunk)`.

## Error handling

Several operations in Lus can raise an error. An error interrupts normal program flow, but the program can recover by catching it.

Use the [`error`](/manual/api#error) function to raise an error explicitly:

```lus
local function divide(a, b)
  if b == 0 then
    error("division by zero")
  end
  return a / b
end
```

The `catch` expression evaluates a sub-expression and captures any error that occurs. Success returns `true` followed by every expression result. Failure returns exactly `false` and the raw error object:

```lus
local ok, result = catch divide(10, 0)
if ok then
  print("Result:", result)
else
  print("Error:", result)  --> Error: script.lus:3: division by zero
end
```

The message carries a `file:line:` position prefix because `error` adds one to string messages by default. Pass a level of `0` to `error` to raise the message without a prefix.

If an error is not caught, it propagates up to the host program, which can handle it appropriately (for example, by printing a message and exiting).

An error object can have any type. Strings, tables, and other values pass through catch unchanged. A `nil` error payload becomes the string `"<no error object>"`.

The error object keeps its identity, so a table raised with `error` is the same table that `catch` returns:

```lus
local marker = { code = 42 }
local ok, err = catch error(marker)
print(ok, err == marker, err.code)   --> false  true  42
```

The operand of `catch` is any expression, not only a call, so `catch t.x`, `catch 1 + 2`, and `catch do ... end` are all valid. `catch` extends as far to the right as an expression can, so `catch a + b` protects `a + b`. An operand that produces no values, such as a call to a function that returns nothing, gives one result, the `true` status. A failure always gives two results. The usual rules for expression lists still apply, so parentheses or a position other than the last truncate a catch to its first result:

```lus
local function values() return "a", "b", "c" end
local function nothing() end

print(catch values())              --> true  a  b  c
print(select("#", catch nothing()))  --> 1
print((catch error("e")))          --> false
assert(not catch type())
```

On failure, the to-be-closed variables opened inside the operand are closed before `catch` returns. A yield inside the operand is allowed, and an error raised after the coroutine resumes is captured by the same `catch`.

A `catch` at the start of a statement is a _catch statement_. It evaluates the operand, discards every result, and suppresses any error:

```lus
local log = {}
catch error("ignored")
catch table.insert(log, "ran")
print(#log)   --> 1
```

Lus also provides a warning system through [`warn`](/manual/api#warn). Warnings emit a message while execution continues.

### Catch handlers

The `catch` expression supports an optional handler function that transforms errors before they are returned:

```lus
local function simplify(err)
  return err:match("^[^:]+:[^:]+: (.+)") or err
end

local ok, err = catch[simplify] divide(10, 0)
-- err is now just "division by zero" without file/line prefix
```

When an error occurs, the handler is called with the raw error object and its first return value replaces the original error. Additional handler results are discarded. On success, the handler is not called. The handler can also be an inline anonymous function. If the handler itself throws, that error propagates to an outer catch or the host. The bracketed expression must evaluate to a function, and any other value raises an error at the catch site.

The handler expression is evaluated first, before the operand and outside the protection. A value other than a Lus or C function, including a table with a `__call` metamethod, raises `attempt to use a TYPE value as a catch handler`. A handler result of `nil`, or no result, makes `nil` the error object, and failure still returns exactly `false` and one value. A catch statement with a handler runs the handler on failure and discards its result.

```lus
local ok, err = catch[function(e) return e:upper() end] error("oops", 0)
print(ok, err)   --> false  OOPS

local failed, issue = catch[function(e)
    return { cause = e, operation = "load settings" }
end] error("missing file", 0)
print(failed, issue.operation, issue.cause)   --> false  load settings  missing file
```

The handler below normalizes errors from different sources into one shape:

```lus
local function normalize(err)
    if type(err) == "table" then
        return err
    end
    return { code = "UNKNOWN", message = tostring(err) }
end

local ok, err = catch[normalize] error("disk full", 0)
print(err.code, err.message)   --> UNKNOWN  disk full
```

An error raised inside the handler escapes the inner `catch`, so an outer `catch` captures it:

```lus
local function failing(err)
    error("handler failed", 0)
end

print(catch (catch[failing] error("original")))   --> false  handler failed
```

### Errors in the embedding API

_This section is primarily relevant for programs embedding the Lus runtime in C or another language with a C interface._

Every function of `lus.h` that can fail returns a status code, and an error never jumps across C frames. `lus_pcall` calls a function and returns `LUS_OK` on success. On failure it returns the status and leaves the error value on the stack in place of the results, and `lus_traceback` returns the traceback of that error:

```c
#include "lus.h"

void report_error(const char *message);

int run_work(lus_State *L) {
  int status;
  lus_getglobal(L, "work");
  status = lus_pcall(L, 0, 0);
  if (status != LUS_OK) {
    const char *message = lus_tostring(L, -1, NULL);
    report_error(message ? message : "(error object is not a string)");
    lus_pop(L, 1);
  }
  return status;
}
```

A C function raises an error by returning `lus_error(L)`, which takes the top value as the error, or `lus_errorf(L, fmt, ...)`, which formats a message and prefixes the position of the calling Lus code. [Embedding Lus](#embedding-lus) introduces the whole interface.

## Standard library

In addition to the core libraries (`math`, `string`, `table`, `io`, `os`, `utf8`, `coroutine`, `debug`, `package`), Lus ships with extended libraries for common tasks. Every function that produces or consumes raw bytes uses [vectors](#vector), and every string function works in characters. See the [API reference](/manual/api) for complete documentation.

### Permissions

The [`pledge`](/manual/api#pledge) function (covered in [Sandboxing](#sandboxing)) controls access to sensitive operations. All libraries below that perform I/O require appropriate permissions. Available permission categories include `fs`, `fs:read`, `fs:write`, `fs:exec`, `network`, `network:http`, `network:tcp`, `network:udp`, `network:tls`, `network:server`, `exec`, `env`, `load`, and `worker`. The `io` library is gated by the `fs` permissions, [`os.getenv`](/manual/api#os.getenv) by `env`, and [`load`](/manual/api#load) and loading modules from files by `load`.

### JSON

[`fromjson`](/manual/api#fromjson) parses a complete JSON value from a string or from the textual form of a numeric argument, and [`tojson`](/manual/api#tojson) serializes a Lus value. JSON null maps to `nil`, arrays become integer-keyed tables, and objects become string-keyed tables:

```lus
local data = fromjson('{"name": "Alice", "scores": [95, 87]}')
print(data.name)       --> Alice
print(data.scores[1])  --> 95

local json = tojson({name = "Bob", scores = {95, 87}})
```

Integer JSON syntax preserves the integer subtype, while a decimal point or exponent produces a float. With the option `{ exact = true }`, integers beyond 64 bits become bigints and numbers with a fraction or exponent become decimals, and `tojson` writes both back with their exact digits. JSON null becomes an absent table field or an array hole because it maps to `nil`. A contiguous table key set from 1 through `n` serializes as an array. Other tables serialize as objects, which retain string keys and omit keys of other types. The empty table serializes as `[]`. JSON object member order is unspecified, so consumers should parse objects and access members by name.

`tojson` accepts an optional filter function as a second argument for transforming or omitting fields. The filter first receives the root with a `nil` key, then integer array keys or string object keys. Tables with a `__json` metamethod can return any serializable replacement value. Special float values such as [`math.huge`](/manual/api#math.huge), negative infinity, and NaN serialize as `null`. Functions, threads, userdata, vectors, and enum values serialize as `null` at the root or in arrays, while object fields with these values are omitted. Shared acyclic tables serialize by value and circular references raise an error. [Data formats](/manual/data) gives the full mapping.

The [`fromcsv`](/manual/api#fromcsv) and [`tocsv`](/manual/api#tocsv) globals provide CSV parsing and serialization.

### Filesystem

The `fs` library provides cross-platform filesystem operations. All `fs` functions throw on failure. Use `catch` for error handling.

```lus nocheck
local files = fs.list("src", "*.lus")
fs.createdirectory("build", true)   -- true creates parent directories
fs.copy("src/main.lus", "build/main.lus")
```

Key functions include `fs.type(path)` (returns `"file"` or `"directory"` and whether it is a symlink), `fs.remove(path, recursive)`, `fs.move(from, to)`, and the [`fs.path`](/manual/api#fs.path) utilities ([`fs.path.join`](/manual/api#fs.path.join), [`fs.path.split`](/manual/api#fs.path.split), [`fs.path.name`](/manual/api#fs.path.name), [`fs.path.parent`](/manual/api#fs.path.parent)).

### Networking

The [`network` library](/manual/api#network-library) provides HTTP, HTTPS, TCP, and UDP communication.

```lus nocheck
local status, body, headers = network.fetch("https://api.example.com/data")
local sock = network.tcp.connect("example.com", 80)
```

`network.fetch(url, method, headers, body)` uses positional optional arguments and returns the status code, the response body as a vector, and lowercase response headers. The method defaults to `"GET"`, and response bodies are capped at 64 MiB. A text body is decoded with `vector.tostring(body)`.

Connecting, accepting, sending, and receiving wait for the network. Inside a [detached coroutine](#detached-coroutines) each of them suspends the coroutine until its socket is ready, so one program holds many connections at once. A timeout set with `settimeout` raises the same `"receive timeout"`, `"send timeout"`, and `"accept timeout"` errors in every case.

`network.serve(host, port, handler)` is an HTTP/1.1 server built on those coroutines. It runs every connection in a detached coroutine and calls the handler with a table that holds the `method`, `path`, `query`, `headers`, and `body` of each request. The handler returns `status, body, headers`, in the order in which `network.fetch` returns them.

```lus nocheck
pledge("network")

network.serve("127.0.0.1", 8080, function(req)
    if req.path ~= "/" then
        return 404, "not found\n"
    end
    return 200, "hello\n", { ["Content-Type"] = "text/plain" }
end)
```

`serve` blocks its caller while the server runs. A handler that raises an error answers 500 and closes that connection. The server passes the error to `options.on_error` when it is set, and otherwise writes `lus: network.serve: ` and the message to standard error.

TCP sockets support `send`, `receive`, `settimeout`, and `close`. Every receive returns a vector. A numeric receive reads up to 1 MiB. `receive("*l", max_bytes)` reads a line with a 1 MiB default limit. `receive("*a", max_bytes)` reads through EOF with a 64 MiB default limit. Exceeding a line or all-data limit closes the connection and raises `"receive limit exceeded"`. TCP servers and UDP sockets expose `getsockname()` so a bind to port `0` can report the selected address and port. UDP receives default to 8 KiB and accept a maximum size of 1 MiB. [Network](/manual/network) documents the socket methods.

### Workers

[Workers](/manual/api#worker-library) are separate interpreter states, each running on its own operating system thread. They provide concurrency through serialized message passing. Arguments passed to [`worker.create`](/manual/api#worker.create) are deep-copied into the worker's state:

```lus nocheck
local w = worker.create("task.lus", {data = "input"})
worker.send(w, "a message")
while result = worker.receive(w) do
  print(result)
end
```

Inside a worker, `worker.message(data)` sends data back to the parent, and `worker.peek()` blocks until a parent message arrives. [`worker.receive`](/manual/api#worker.receive) accepts one or more workers and returns one aligned value per handle after any handle becomes ready. Worker states have separate globals and heaps, but they share the host process and runtime pool. The host process remains the security boundary. Workers inherit the parent's permissions in sealed form. Creating a worker requires the `load` and authorized `fs:read` permissions for its script file.

On the main interpreter, [`os.exit`](/manual/api#os.exit) terminates the process. Inside a worker, the call raises the catchable error `"os.exit is unavailable in a worker"`. A worker can catch that error and continue. An uncaught instance reaches the parent as the worker's execution error.

### Time

The [`time`](/manual/api#time) library provides date, time, and duration handling through three immutable types: an `instant` (an absolute point on the UTC timeline), a `zoned` (a civil date and time in some zone), and a `duration` (a signed span). Keeping them distinct means arithmetic is never ambiguous: adding a `duration` to an `instant` is exact SI-seconds, while calendar arithmetic is a separate operation on a `zoned`.

```lus
local now = time.now()                 -- instant
local later = now + time.hours(72)     -- exact
local ny = time.zone("America/New_York")
print(later:at(ny):iso())              -- civil wall clock, DST-aware
```

Named zones resolve from an IANA tzdata database embedded in the runtime, so `time.zone` and `time.localzone` need no filesystem access and behave identically across platforms. `time.offset(seconds)` builds a fixed-offset zone, and `time.tzdata_version()` reports the embedded release.

Formatting uses `strftime` specifiers (as in `os.date`), with `:iso()` as an ISO 8601 shortcut. Bridge to the legacy epoch API with `time.instant(os.time())` and `instant:epoch()`. `time.monotonic()` returns a separate monotonic reading for measuring elapsed time. [Time](/manual/time) describes this library in full.

### SQLite

The runtime embeds SQLite for local, file-backed and in-memory databases. [`io.sqlite(path)`](/manual/api#io.sqlite) returns a database handle with a small method set:

- `db:exec` runs statements for their side effects.
- `db:run` runs a single write and reports the affected rows.
- `db:query` returns an iterator over rows keyed by column name.
- `db:prepare` compiles a reusable statement.
- `db:transaction` wraps a function in a commit-or-rollback transaction.

Values always travel through `?` or named placeholders, and handles close through `<close>`, `__gc`, or an explicit `db:close()`, just like `io.open` file objects.

```lus nocheck
local db <close> = io.sqlite("app.db")
db:run("INSERT INTO users (name) VALUES (?)", name)
for row in db:query("SELECT id, name FROM users WHERE age >= ?", 18) do
  print(row.id, row.name)
end
```

Opening a file-backed database checks the database path against `fs:read` and, for the default writable mode, `fs:write`. A per-connection pledge-aware VFS then authorizes every SQLite file operation, including access to `-journal`, `-wal`, and `-shm` sidecars when SQLite uses them. Read-only mode uses existing WAL and SHM state with `fs:read`, shared coordination locks, and read-only WAL-index access. A sidecar state that needs creation or recovery raises an `fs:write` permission error. The path-changing PRAGMAs `data_store_directory`, `temp_store_directory`, and `lock_proxy_file` are denied case-insensitively. A `":memory:"` database needs no filesystem pledge.

Indexing a handle with a table name yields a query source, so `@db.users as u where u.age >= 18 select u.name` pushes down as a parameterized SELECT. [SQLite](/manual/sqlite) describes this library in full.

## Tools

The `lus` executable carries the tools of a Lus project as subcommands, all built on the parser of the interpreter. The [CLI page](/manual/cli) lists every option.

### Testing

`lus test` runs every function whose name ends in `_test` inside files whose names end in `_test.lus`. Each file runs in its own process and temporary directory, and the files run in parallel. Inside a test file, `assert` reports the values of the operands of a failed comparison, a local `NAME_cases` table runs `NAME_test` once per entry, and the helpers `raises`, `same`, `skip`, and `snapshot` cover errors, structural equality, skipped tests, and recorded output:

```lus
-- add_test.lus
local function add(a, b) return a + b end

local add_cases = {
  { 1, 2, 3 },
  { -1, 1, 0 },
}

local function add_test(a, b, want)
  assert(add(a, b) == want)
end

function errors_test()
  raises(function() add(nil, 1) end, "arithmetic")
end
```

[Testing](/manual/testing) describes the runner in full.

### Formatting, checking, and documentation

`lus fmt` formats source files, `lus check` reports compile errors and lint warnings with stable codes, `lus doc` turns `---` doc comments into Markdown or JSON reference documentation, and `lus ast` prints the syntax tree of a file as JSON. `lus build` bundles a script and its modules into a standalone executable, and `lus compile` writes a script as a binary chunk. [Developer tools](/manual/tools) describes each tool.

### Debugging

`lus debug` runs a script under the Debug Adapter Protocol, with conditional breakpoints, log points, error breakpoints, stepping through coroutines, and inspection of locals, upvalues, and globals. The VS Code extension uses it for **Run and Debug**, and any editor with a DAP client can drive it. [Developer tools](/manual/tools) describes the debugger.

## Embedding Lus

_This section is primarily relevant for programs embedding the Lus runtime in C or another language with a C interface._

A host program embeds Lus through the C header `lus.h` and the library `liblus`. The host creates a state, opens the standard libraries, decides the permissions of the scripts it runs, and exchanges values with them through a stack:

```c
#include "lus.h"

static int add(lus_State *L) {
  lus_pushinteger(L, lus_tointeger(L, 1, NULL) + lus_tointeger(L, 2, NULL));
  return 1;
}

int main(void) {
  lus_State *L = lus_newstate();
  lus_openlibs(L);
  lus_grant(L, "fs:read=/srv/data/*");
  lus_pushcfunction(L, add);
  lus_setglobal(L, "add");
  if (lus_dostring(L, "print(add(2, 3))") != LUS_OK)
    lus_pop(L, 1);
  lus_close(L);
  return 0;
}
```

Every function that can fail returns a status, as described in [Errors in the embedding API](#errors-in-the-embedding-api). References keep values alive between calls, userdata carry host memory with a metatable, and extensions declare their own capabilities so scripts can pledge them. [Embedding](/manual/embedding) documents the interface, and the same interface is exported by the [WebAssembly](/manual/webassembly) that runs Lus in browsers and in the VS Code extension.

## Internals

### Implementation

Lus is an _interpreted language_, meaning that it is not compiled to machine code. Instead, the input is transformed into an _intermediate representation_ that efficiently details the structure of your code, which is then fed to a _virtual machine_ (or the _interpreter_) for execution. The intermediate representation, which we call _bytecode_, is highly compact and resembles traditional machine code. The runtime is written in Zig, and `lus --dis script.lus` prints the bytecode of a script instead of running it.

The Lus interpreter is a register-based virtual machine. Every instruction is 32 bits wide, and its operands name either a slot in the current frame or a constant of the running function. Each instruction maps closely to a language construct: `slice` implements the slice syntax (`t[i, j]`), `add` implements additive arithmetic (`a + b`), and so on.

Generic instructions _quicken_ as the program runs: an instruction that observes integer operands, or a table field at a stable position, rewrites itself in place into a specialized variant with a short fast path. Calls between Lus functions never recurse on the native stack, and entering a `catch` costs nothing until an error occurs. Running with [`--readonly-env`](#readonly-environment) freezes `_ENV` and the module tables after startup, which lets the compiler and the interpreter rely on the standard library staying in place.

### Memory management

Lus manages memory with a precise, non-moving, mark-and-sweep garbage collector. Objects allocated by the runtime are tracked by the collector. As allocations accumulate, it marks everything reachable from the program's roots and reclaims the rest, with full support for weak tables, ephemeron tables, and finalizers through `__gc`.

You rarely need to think about garbage collection in practice. However, if you're working with performance-sensitive code or managing large amounts of data, Lus exposes the [`collectgarbage`](/manual/api#collectgarbage) function to let you interface with the garbage collector.

The interpreter flag `--gc-pause N` bounds how far the heap may grow past the live set (in percent) before a collection starts, trading CPU for a smaller peak footprint.
