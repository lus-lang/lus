## Welcome

Lus is a small language for scripts, command line tools, and network servers. The `lus` executable runs programs and also formats, checks, tests, and debugs them.

### A first program

This program computes what each of three friends owes when they share a dinner bill of 97.29.

```lus
local bill = 97.29
local people = 3

print(`Each of us pays $(bill / people)`)   --> Each of us pays 32.43
```

`local bill = 97.29` creates a variable named `bill` that holds 97.29. The next line creates `people` in the same way. The text between backticks is a string, into which `$( )` inserts the result of a calculation. `print` writes the text to the terminal.

Save the program as `bill.lus` and run it with `lus`. [Getting started](/manual/getting-started) shows how to install `lus`.

```sh
lus bill.lus
```

### Comments

A comment is a note for people who read the code. Lus ignores everything from `--` to the end of the line. A comment that starts with `--[[` continues until the next `]]`, so it can span several lines.

```lus
-- Prices include tax.
local price = 4.50   -- per cup

--[[
    The shop closes early on Sundays,
    so the Sunday totals cover fewer hours.
]]
```

In the examples, a comment after `-->` shows what the line prints. `print` separates several values with a tab, which the comments show as two spaces.

```lus
print(2 + 2)            --> 4
print("tea", 4.50)      --> tea  4.5
```

## Values and types

A _value_ is a piece of data, such as the number `97.29`, the text `"tea"`, or `true`. Every value has a _type_, which determines the operations that apply to the value. Numbers can be added and text can be searched. Adding `"tea"` to `true` is an error, which Lus reports when the line runs.

The type belongs to the value, so a variable can hold a number at one point and text later.

### Nil

`nil` means "no value". A variable that is declared without a value holds `nil`, which is useful for a result that is not known yet.

```lus
local winner   -- decided when the race ends
print(winner)  --> nil
```

### Booleans

The booleans are `true` and `false`. A boolean records whether something is the case, such as whether a door is locked. Comparisons such as `age >= 18` produce booleans, as [Comparison](#comparison) shows.

```lus
local door_locked = true
print(door_locked)   --> true
```

When Lus tests a value, as an `if` statement does, `false` and `nil` count as false and are called _falsy_. Every other value, including `0` and the empty string `""`, counts as true and is called _truthy_.

### Numbers

Lus has several kinds of numbers, called the _subtypes_ of the type `number`. Most programs use two of them. An _integer_ is a whole number, such as `42`. A _float_ is a number with a fractional part, such as `1.5`.

A float stores most fractions approximately, which is acceptable for measurements but wrong for money. A _decimal_ keeps its digits exactly and is written with a `d` after it.

```lus
print(0.1 + 0.2)      --> 0.30000000000000004
print(0.1d + 0.2d)    --> 0.3
print(19.90d)         --> 19.90
```

An integer has a limit of about nine quintillion, past which a calculation wraps around to a wrong answer. A _bigint_ has no limit and is written with an `n` after it.

```lus
print(9223372036854775807 + 1)    --> -9223372036854775808
print(9223372036854775807n + 1)   --> 9223372036854775808
```

Underscores make long numbers easier to read, so `1_000_000` is one million. A float always prints with a decimal point, as in `3.0`. [Arithmetic](#arithmetic) shows how the subtypes combine.

### Strings

A _string_ is text, written between single quotes, double quotes, or backticks. Single and double quotes are equivalent.

```lus
print("It's ready")          --> It's ready
print('She said "now"')      --> She said "now"
```

A string in backticks can also contain values, inserted with `$name` for a variable or `$( )` for the result of an expression.

```lus
local name = "Ada"
local unread = 3

print(`Hello, $name! You have $unread new messages.`)
--> Hello, Ada! You have 3 new messages.
print(`That is $(unread * 2) since yesterday.`)
--> That is 6 since yesterday.
```

A backslash in a string starts an _escape sequence_, which stands for a character that is hard to type. Common escape sequences are `\n` for a line break, `\t` for a tab, `\\` for a backslash, and `\u{E9}` for the character with the Unicode number E9, which is `é`.

```lus
print("Name:\tAda\nRole:\tEngineer")
--> Name:  Ada
--> Role:  Engineer
```

A long string is written between `[[` and `]]`, can span several lines, and keeps its text exactly as written. The help text of a command line tool is a typical long string.

```lus
local help = [[
Usage: split TOTAL PEOPLE
Divides a bill evenly.]]
print(help)
--> Usage: split TOTAL PEOPLE
--> Divides a bill evenly.
```

A string cannot change after it is created, so functions that modify text, such as converting it to upper case, return a new string. [Strings and patterns](#strings-and-patterns) describes these functions.

### Other types

A _table_ holds many values, as a list or as named fields. A _function_ is code that a program can call, such as `print`. [Tables](#tables) and [Functions](#functions) describe them. [Enums](#enums), [coroutines](#coroutines), and [queries](#queries) are also types. A _vector_ holds raw bytes. A _userdata_ is an object from the runtime or from a C library, such as an open file.

## Variables

A _variable_ is a name that keeps a value for later use. A well-chosen name also makes the code easier to read.

### Local variables

The `local` statement declares a variable and gives it a first value. An assignment, written with `=`, gives an existing variable a new value.

```lus
local visitors = 1
print(visitors)          --> 1

visitors = visitors + 1
print(visitors)          --> 2
```

One statement can declare or assign several variables, with commas between the names and between the values. A name without a matching value gets `nil`.

```lus
local width, height = 80, 24
print(width, height)      --> 80  24

local first, second = "a"
print(first, second)      --> a  nil
```

An assignment computes all the values on its right side before it changes any variable, so two variables can exchange their values in one statement.

```lus
local low, high = 9, 2
low, high = high, low
print(low, high)          --> 2  9
```

A name consists of letters, digits, and underscores but cannot start with a digit. Names are case sensitive, so `total` and `Total` are different names. Reserved words such as `local`, `if`, and `end` cannot be names.

### Blocks and scope

A _block_ is a sequence of statements, such as a file or the body of a loop, of a conditional statement, or of a function. `do ... end` creates a block where one is needed.

The _scope_ of a local variable starts at the statement after its declaration and ends at the end of its block. Outside its scope, the name does not refer to the variable, so two parts of a program can use the same name without interfering.

```lus
local total = 0
do
    local bonus = 5          -- bonus exists only inside this block
    total = total + bonus    -- total is still in scope here
end
print(total)                 --> 5
```

A `do ... end` block is useful for a temporary variable that only a few statements need.

### Shadowing

A declaration can reuse the name of a variable that is already in scope. The new variable _shadows_ the old one until the end of its block, after which the old variable is visible again with its value unchanged.

```lus
local price = 20
do
    local price = price * 1.2   -- the price with tax, for this block only
    print(price)                --> 24.0
end
print(price)                    --> 20
```

The new variable enters scope after its own declaration, so the `price` on the right side of the inner declaration is still the outer one.

### Global variables

A _global variable_ is visible in every file of a program, which is why `print` works in every file. Assigning to a name that has no `local` declaration creates a global variable. A global that was never assigned is `nil`.

```lus
attempts = 1          -- no local declaration, so attempts is a global
print(attempts)       --> 1
print(retries)        --> nil
```

Local variables are the better default. A local is only visible in its block, which makes it easy to find every place that changes it. Lus also reads and writes locals faster than globals. Globals are for the few values that the whole program shares.

A misspelled name is also an undeclared name, so assigning to it creates a new global and reading it gives `nil`. In both cases the program continues with a wrong value. The `global` statement prevents this by declaring the globals that a file uses. After it, every other undeclared name in the block is an error.

```lus
global print
global attempts = 0

attempts = attempts + 1
print(attempts)       --> 1
```

The declaration includes `print` because `print` is a global. `global attempts = 0` also gives the global a first value. If another part of the program has already defined `attempts`, this declaration stops the program with the error `global 'attempts' already defined`.

With these declarations, a misspelling is a _compile error_, which Lus reports when it loads the file, before any statement runs.

```lus nocheck
global print
global attempts = 0

attemps = attempts + 1    -- compile error: variable 'attemps' not declared
```

### Constants

An _attribute_ is a word in angle brackets after a variable name that changes how the variable behaves. A variable with the `<const>` attribute keeps its first value, so any assignment to it is a compile error.

```lus
local MAX_RETRIES <const> = 3
local TIMEOUT <const> = MAX_RETRIES * 10
print(TIMEOUT)            --> 30
```

```lus nocheck
local MAX_RETRIES <const> = 3
MAX_RETRIES = 5           -- compile error: attempt to assign to const variable 'MAX_RETRIES'
```

A global can be constant too, as in `global VERSION <const> = "2.0"`. [Variable attributes](#variable-attributes) describes the other attributes.

## Built-in functions

A _built-in function_ is a function that Lus provides, such as `print`. A program _calls_ a function by writing its name followed by parentheses that contain the _arguments_. Many functions return a value, called the _result_.

`tonumber` converts text to a number. Input from a person or from a file is text, even when it contains digits, so a program converts it before it calculates.

```lus
local typed = "42"
local count = tonumber(typed)
print(count + 1)   --> 43
```

These built-in functions are the most common:

- `tonumber(text)` returns the number in `text`, or `nil` if the text is not a number.
- `tostring(value)` returns a value as text.
- `type(value)` returns the name of the type of a value. A program uses it to check data that it did not create.

```lus
print(tonumber("twelve"))                               --> nil
print(type(tonumber("12")), type(tonumber("twelve")))   --> number  nil
```

Most built-in functions belong to a _library_, which is a group of functions about one subject, such as `math` or `string`. The name of a library function has a dot: `math.floor`, which rounds a number down, is the function `floor` in the `math` library. `string.upper` converts text to upper case. A library can also contain constants, such as `math.pi`.

```lus
local minutes = 135
print(math.floor(minutes / 60), "hours")   --> 2  hours
print(math.max(72, 95, 58))                --> 95
print(string.upper("receipt"))             --> RECEIPT
```

The [API reference](/manual/api) lists every built-in function. In a terminal, `lus help NAME` prints the entry for one function, as in `lus help math.floor`.

## Operators

An _operator_ combines one or two values into a new value. An _expression_ is any code that produces a value, such as a literal, a variable, or a function call. A _literal_ is a value written directly in the code, such as `42` or `"tea"`. Operators applied to smaller expressions form a larger expression.

### Arithmetic

Lus has the usual arithmetic operators.

| Operator | Meaning | Example | Result |
| --- | --- | --- | --- |
| `+` | addition | `7 + 2` | `9` |
| `-` | subtraction | `7 - 2` | `5` |
| `*` | multiplication | `7 * 2` | `14` |
| `/` | division | `7 / 2` | `3.5` |
| `//` | floor division | `7 // 2` | `3` |
| `%` | remainder | `7 % 2` | `1` |
| `^` | exponentiation | `7 ^ 2` | `49.0` |
| `-` before a value | negation | `-7` | `-7` |

#### Integers and floats

If both operands of `+`, `-`, `*`, `//`, or `%` are integers, the result is an integer. If one operand is a float, the result is a float. With integers and floats, `/` and `^` always produce a float, so `6 / 2` is `3.0`.

```lus
print(7 + 2)        --> 9
print(7 + 2.0)      --> 9.0
print(6 / 2)        --> 3.0
print(2 ^ 10)       --> 1024.0
```

Floor division rounds its result down, toward negative infinity. The remainder is what floor division leaves over and has the sign of the right operand. Together, the two operators split a quantity into units, such as seconds into minutes and seconds. A remainder of `0` means that a division is exact.

```lus
local seconds = 200
print(seconds // 60)    --> 3
print(seconds % 60)     --> 20
print(-7 // 2)          --> -4
print(-7 % 2)           --> 1
print(seconds % 2)      --> 0
```

The largest integer is `math.maxinteger`. [Numbers](#numbers) shows what happens to a result past it.

Dividing an integer by zero with `//` or `%` raises an error. Float division by zero produces an infinity, which prints as `inf` or `-inf`.

#### Bigints

A bigint behaves like an integer without limits. An operation between a bigint and an integer produces a bigint.

```lus
print(2n ^ 100)             --> 1267650600228229401496703205376
print(2n ^ 64 + 1)          --> 18446744073709551617
print(7n // 2)              --> 3
```

#### Decimals

Decimal arithmetic is in base 10. Sums, differences, and products of decimals are exact. An operation between a decimal and an integer or a bigint produces a decimal. A division of decimals keeps up to 34 significant digits and rounds the rest.

```lus
local price = 19.99d
print(price * 3)        --> 59.97
print(10d / 4)          --> 2.5
print(1d / 3)           --> 0.3333333333333333333333333333333333
```

#### Mixed subtypes

The subtype of the result of `+`, `-`, `*`, `//`, and `%` depends on the subtypes of both operands.

| | integer | float | bigint | decimal |
| --- | --- | --- | --- | --- |
| **integer** | integer | float | bigint | decimal |
| **float** | float | float | float | error |
| **bigint** | bigint | float | bigint | decimal |
| **decimal** | decimal | error | decimal | decimal |

`/` follows the same table, except that it produces a float when no operand is a decimal. `^` produces a float when both operands are integers or floats. A bigint or a decimal raised to a positive whole number stays exact, so `2n ^ 100` is a bigint and `1.5d ^ 2` is the decimal `2.25`.

An operation between a decimal and a float is an error, so the program converts one side first, depending on whether it needs an exact or an approximate result. `decimal(x)` converts a number to a decimal. `tonumber(d)` converts a decimal to a float.

```lus
local price = 19.99d
local rate = 0.5

print(price * decimal(rate))     --> 9.995
print(tonumber(price) * rate)    --> 9.995
```

```lus nocheck
print(19.99d * 0.5)    -- error: attempt to mix decimal and float in arithmetic
```

#### Strings in arithmetic

An arithmetic operator converts a string that contains a number, so `"10" + 5` is `15`. An explicit `tonumber` is clearer and also lets the program handle text that is not a number.

### Comparison

A comparison produces `true` or `false`.

| Operator | Meaning |
| --- | --- |
| `==` | equal |
| `~=` | not equal |
| `<` and `>` | less than and greater than |
| `<=` and `>=` | less than or equal and greater than or equal |

Numbers compare by value, whatever their subtypes.

```lus
print(1 == 1.0)         --> true
print(1 == 1n)          --> true
print(2 < 2.5d)         --> true
print(0.1d == 0.1)      --> false
```

The last line is `false` because the float `0.1` is only close to one tenth.

Two strings are equal if they have the same characters. `<` and the other ordering operators compare strings character by character, by Unicode number, so every upper case English letter comes before every lower case one.

```lus
print("apple" < "banana")    --> true
print("Zebra" < "apple")     --> true
```

Values of different types are never equal, so `"10" == 10` is `false`. Ordering a number against a string is an error, which the program avoids by converting one side first.

```lus
print("10" == 10)              --> false
print(tonumber("10") == 10)    --> true
```

Two tables are equal only when they are the same table, as [Tables](#variables-refer-to-tables) explains. The same holds for functions.

### Logical operators

The logical operators `and`, `or`, and `not` combine conditions. They treat each operand as [truthy or falsy](#booleans).

`not` produces `true` for a falsy operand and `false` for a truthy operand.

`and` produces its left operand if that operand is falsy. Otherwise it produces its right operand. `or` produces its left operand if that operand is truthy. Otherwise it produces its right operand. The result is one of the operands, unchanged, so it is a boolean only if that operand is a boolean.

```lus
local age = 30
print(age >= 18 and age < 65)    --> true
print(not (age >= 18))           --> false

print(nil or "default")          --> default
print(false and "unused")        --> false
print(1 and 2)                   --> 2
```

`and` evaluates its right operand only when the left operand is truthy. `or` evaluates its right operand only when the left operand is falsy. A program puts a check on the left so that the expression on the right runs only when it is valid.

```lus
local divisor = 0
print(divisor ~= 0 and 10 // divisor > 2)    --> false
```

The division never runs, because `divisor ~= 0` is `false`.

`or` is the usual way to give a default to a value that may be `nil`.

```lus
local requested
local size = requested or 10
print(size)                      --> 10
```

The default also replaces `false`, so a setting where `false` is a valid choice needs an explicit comparison with `nil`.

The expression `condition and a or b` is `a` when the condition is truthy. Otherwise it is `b`. This only works when `a` is truthy, because a falsy `a` makes the expression produce `b`.

```lus
local stock = 0
print(stock > 0 and "in stock" or "sold out")   --> sold out
```

### Concatenation

`..` joins two strings into a new string, converting a number to a string first.

```lus
local name = "Ada"
print("Hello, " .. name)       --> Hello, Ada
print("Total: " .. 42)         --> Total: 42
```

Any other operand, such as `nil` or a boolean, is an error. A string in backticks accepts values of every type and is usually easier to read when text and values alternate.

### Length

`#` before a string produces its length in characters.

```lus
print(#"hello")    --> 5
print(#"héllo")    --> 5
print(#"")         --> 0
```

Before a list, `#` produces the number of items, as [Lists](#lists) shows.

### Bitwise operators

The bitwise operators work on the 64 bits of an integer. Programs use them to store several yes-or-no settings in one number and to read and write binary formats.

| Operator | Meaning |
| --- | --- |
| `&` | AND: a bit is 1 if it is 1 in both operands |
| `\|` | OR: a bit is 1 if it is 1 in either operand |
| `~` between two values | XOR: a bit is 1 if it is 1 in exactly one operand |
| `~` before a value | NOT: every bit is inverted |
| `<<` | shift the bits left |
| `>>` | shift the bits right |

This example stores three permissions in one integer, with one bit for each.

```lus
local READ <const> = 1 << 0
local WRITE <const> = 1 << 1
local EXECUTE <const> = 1 << 2

local mode = READ | WRITE
print(mode)                    --> 3
print(mode & WRITE ~= 0)       --> true
print(mode & EXECUTE ~= 0)     --> false

mode = mode & ~WRITE           -- clear the WRITE bit
print(mode)                    --> 1
```

A float operand must be a whole number, which Lus converts to an integer. If either operand is a bigint, the result is a bigint without the 64-bit limit, so `1n << 64` is `18446744073709551616`.

### Precedence

_Precedence_ is the order in which the operators of an expression apply. The table lists the operators from the highest precedence to the lowest. Operators in the same row have the same precedence.

| Precedence | Operators |
| --- | --- |
| 1 | `^` |
| 2 | `not`, `#`, `-` and `~` before a value |
| 3 | `*`, `/`, `//`, `%` |
| 4 | `+`, `-` |
| 5 | `..` |
| 6 | the bitwise operators, from `<<` and `>>` to `\|` |
| 7 | `<`, `>`, `<=`, `>=`, `~=`, `==` |
| 8 | `and` |
| 9 | `or` |

Among the bitwise operators, the shifts apply first, then `&`, then `~`, then `|`.

Operators of the same precedence apply from left to right, except `^` and `..`, which apply from right to left. Parentheses override precedence and also make an unclear order explicit.

```lus
print(1 + 2 * 3)        --> 7
print((1 + 2) * 3)      --> 9
print(2 ^ 3 ^ 2)        --> 512.0
print(-2 ^ 2)           --> -4.0
```

Two rules cause frequent mistakes. Exponentiation applies before negation, so `-2 ^ 2` is `-(2 ^ 2)`. `not` applies before a comparison, so `not a == b` compares `not a` with `b`. To negate a comparison, write `not (a == b)` or use `~=`.

```lus
local a, b = 1, 2
print(not a == b)       --> false
print(not (a == b))     --> true
print(a ~= b)           --> true
```

## Control flow

Statements run in order, from the top of a file to the bottom. An `if` statement runs a block only when a condition is true. A loop runs a block several times.

### `if` statements

The `if` statement runs a block when its condition is [truthy](#booleans). An `if` statement can have any number of optional `elseif` branches, each of which tests another condition when the previous conditions were falsy. The optional `else` branch runs if every condition was falsy.

```lus
local temperature = 31

if temperature > 30 then
    print("hot")            --> hot
elseif temperature > 15 then
    print("mild")
else
    print("cold")
end
```

Lus tests the conditions in order, runs the block of the first truthy condition, then continues after the `end`. Each branch is a block, so a local variable declared in a branch exists only in that branch.

### Conditions that declare variables

Programs often compute a value, test it, and use it only if the test passes. A condition of the form `name = expression` does all three by declaring a local variable that holds the value of the expression. The condition is true if that value is truthy.

```lus
local input = "42"

if n = tonumber(input) then
    print(n + 1)                      --> 43
else
    print(`$input is not a number`)
end
```

`tonumber` returns `nil` for text that is not a number, so the first branch runs only with a usable `n`. The variable exists in every branch of the `if` and ends at its `end`.

A condition can declare several variables when its expression produces several values. The condition is then true only if every declared variable is truthy. `string.find` searches a string and returns two values, the positions where the match starts and ends, or `nil` if there is no match.

```lus
local line = "level=warn"

if first, last = string.find(line, "warn") then
    print(`found from $first to $last`)    --> found from 7 to 10
else
    print("not found")
end
```

An `elseif` condition can declare variables in the same way.

### `while` loops

The `while` loop repeats its body as long as its condition is truthy. It tests the condition before each pass, so the body may not run at all. A `while` loop is for repetition when the number of passes is not known in advance.

This loop halves the width of an image until the image fits in 1000 pixels.

```lus
local width = 4000
local halvings = 0

while width > 1000 do
    width = width // 2
    halvings = halvings + 1
end
print(width, halvings)   --> 1000  2
```

A `while` condition can also [declare variables](#conditions-that-declare-variables). Lus evaluates the expression before every pass and ends the loop when a declared variable is falsy. This loop counts the fields of a line of comma-separated values by finding each comma. The third argument of `string.find` is the position where the search starts.

```lus
local line = "tea,4.50,3,shelf 2"
local fields = 1
local start = 1

while found = string.find(line, ",", start) do
    fields = fields + 1
    start = found + 1
end
print(fields)   --> 4
```

Without the declaration in the condition, the call to `string.find` would appear twice: once before the loop and once at the end of its body.

### `repeat` loops

The `repeat` loop runs its body first and tests its condition afterwards, ending when the condition is truthy, so the body always runs at least once. Counting the digits of a number needs this, because even `0` has one digit.

```lus
local n = 4096
local digits = 0
repeat
    n = n // 10
    digits = digits + 1
until n == 0
print(digits)   --> 4
```

With `n = 0`, the body runs once and the count is 1.

The condition after `until` can use the local variables of the body. This loop computes the square root of 2 by improving an estimate on each pass until a pass changes it by less than a millionth. `math.abs` returns a number without its sign.

```lus
local n = 2
local estimate = n
local passes = 0

repeat
    local better = (estimate + n / estimate) / 2
    local change = math.abs(better - estimate)
    estimate = better
    passes = passes + 1
until change < 0.000001
print(estimate, passes)   --> 1.414213562373095  5
```

### Numeric `for` loops

The numeric `for` loop runs its body once for each number in a range, with the loop variable holding the current number. The start and the stop are both included.

```lus
for day = 1, 3 do
    print(`day $day`)
end
--> day 1
--> day 2
--> day 3
```

An optional third number is the step, which defaults to 1. A negative step counts down. A float step produces floats.

```lus
for seconds = 3, 1, -1 do
    print(seconds)
end
print("liftoff")
--> 3
--> 2
--> 1
--> liftoff

for dose = 0, 1, 0.5 do
    print(dose)
end
--> 0.0
--> 0.5
--> 1.0
```

The start, the stop, and the step are evaluated once, before the first pass. If the start is already past the stop, the body does not run. The loop variable is local to the body, which cannot assign to it.

The other form of `for` loops over the items of a table, as [Iteration](#iteration) describes.

### `break` and `continue`

`break` ends a loop immediately, so the program continues with the statement after the loop. `continue` skips the rest of the current pass and starts the next pass, which in a `while` or `repeat` loop begins with the test of the condition.

This loop sells 15 tickets in a theatre that numbers its seats from 1 and has no seat 13.

```lus
local sold = 0
for seat = 1, 20 do
    if seat == 13 then
        continue                           -- no seat 13
    end
    sold = sold + 1
    if sold == 15 then
        print(`last seat sold: $seat`)     --> last seat sold: 16
        break
    end
end
```

`break` and `continue` apply to the innermost loop that contains them. With `continue`, the rest of the loop body does not need to be inside an `if`, which helps when a pass can end early for several reasons.

### `goto`

The `goto` statement jumps to a _label_, which is a name between double colons, such as `::done::`. `goto` is mainly used to leave several nested loops at once, since `break` only leaves the innermost loop.

```lus
local target = 12

for i = 1, 9 do
    for j = 1, 9 do
        if i * j == target then
            print(`$i x $j`)      --> 2 x 6
            goto found
        end
    end
end
print("no pair found")
::found::
```

A `goto` can jump to a label in its own block or in an enclosing block. It cannot jump into the scope of a local variable, so labels are usually at the end of a block. Loops, `break`, and `continue` are clearer in most cases.

## Functions

A program declares its own functions for code that it needs in several places, so the code is written once and called many times with different inputs. A well-chosen function name also makes each call easy to read.

### Declaring and calling

A function declaration has a name, a list of parameters in parentheses, and a body that ends with `end`. The `return` statement ends the function and returns a result. This function computes the area of a rectangle.

```lus
local function area(width, height)
    return width * height
end

print(area(3, 4))   --> 12
print(area(10, 2))  --> 20
```

`local function` declares the function as a [local variable](#local-variables). Most functions of a program are local, except those that other files need, which go into a [module](#modules).

A call can be part of an expression, as in `print(area(3, 4))`, or a statement of its own. A function that reaches its `end` without a `return` returns no result. A call whose only argument is a string literal can omit the parentheses, so `print "ready"` is the same as `print("ready")`.

### Parameters and arguments

A _parameter_ is a local variable of the function that holds one argument of the call, matched by position. A parameter without an argument is `nil`. An argument without a parameter is ignored.

```lus
local function show(a, b)
    print(a, b)
end

show(1)        --> 1  nil
show(1, 2, 3)  --> 1  2
```

Because a missing argument is `nil`, `or` gives a parameter a default value. In this function, `times` is 1 when the call leaves it out.

```lus
local function greet(name, times)
    times = times or 1
    for i = 1, times do
        print(`Hello, $name!`)
    end
end

greet("Ada")      --> Hello, Ada!
greet("Lin", 2)   --> Hello, Lin!
                  --> Hello, Lin!
```

A parameter for which `false` is a valid value needs the test `if times == nil then`, as [Logical operators](#logical-operators) explains.

### Multiple results

A function can return several values, separated by commas, which is useful for a calculation with more than one answer, such as a duration in hours, minutes, and seconds. A multiple assignment receives the values.

```lus
local function clock(seconds)
    return seconds // 3600, seconds % 3600 // 60, seconds % 60
end

local hours, minutes, secs = clock(7384)
print(hours, minutes, secs)  --> 2  3  4

print(clock(7384))           --> 2  3  4
print(clock(7384), "end")    --> 2  end
print((clock(7384)))         --> 2
```

An assignment takes as many results as it has variables, ignoring extra results and setting extra variables to `nil`. A call keeps all of its results only when it is the last expression in a list, as in the first `print`. Elsewhere in a list, as before `"end"`, a call produces only its first result, as does a call in parentheses.

### Variable arguments

Some functions accept any number of arguments, as `print` does. Three dots as the last parameter accept all the extra arguments. In the body, three dots stand for those arguments, so this `log` function can add a prefix and pass the rest of its arguments to `print`.

```lus
local function log(level, ...)
    print(`[$level]`, ...)
end

log("info", "started")              --> [info]  started
log("warn", "disk at", 91, "%")     --> [warn]  disk at  91  %
```

### Functions as values

A function is a value, like a number or a string. It can be stored in a variable, passed to another function, and returned from one. The `retry` function repeats an action, which is a function passed as an argument, until the action succeeds.

```lus
local function retry(attempts, action)
    for attempt = 1, attempts do
        local result = action(attempt)
        if result then
            return result, attempt
        end
    end
    return nil, attempts
end

local value, tries = retry(5, function(attempt)
    return attempt >= 3 and "connected"
end)
print(value, tries)  --> connected  3
```

The expression `function(attempt) ... end` creates a function without a name. A declaration such as `local function f() end` creates the same kind of value and stores it in the variable `f`.

### Functions that keep local variables

A function can use the local variables that are in scope where it is written, even after their block has ended. This gives a function private state that no other code can reach.

`counter` returns a new function on each call. Each call of `counter` creates a new `count` variable, so each returned function has its own count.

```lus
local function counter()
    local count = 0
    return function()
        count = count + 1
        return count
    end
end

local next_ticket = counter()
local next_order = counter()
print(next_ticket(), next_ticket(), next_ticket())  --> 1  2  3
print(next_order())                               --> 1
```

This is also how a program prepares a _callback_, which is a function that other code calls later. `logger` returns a function that keeps its `prefix`, so each part of a program gets its own logging function and writes the prefix only once.

```lus
local function logger(prefix)
    return function(message)
        print(`[$prefix] $message`)
    end
end

local db_log = logger("db")
local http_log = logger("http")
db_log("connected")       --> [db] connected
http_log("listening")     --> [http] listening
```

Two functions written in the same block share the variables of that block. When one function assigns a variable, the other sees the new value.

```lus
local function account(balance)
    local function deposit(amount)
        balance = balance + amount
    end
    local function report()
        return `balance: $balance`
    end
    return deposit, report
end

local deposit, report = account(100)
deposit(50)
print(report())  --> balance: 150
```

### Recursion

A function can call itself, which is called _recursion_. Recursion is useful for problems that contain a smaller version of themselves, such as a tree of folders or a factorial.

```lus
local function factorial(n)
    if n <= 1 then
        return 1
    end
    return n * factorial(n - 1)
end

print(factorial(5))   --> 120
print(factorial(20))  --> 2432902008176640000
```

`local function` makes the name visible inside the body, which a recursive function needs. Every call that has not returned uses memory, so a recursion that goes too deep fails with the error `stack overflow`.

## Tables

A _table_ is a collection of values, each stored under a _key_ that a program uses to read the value again.

The table is the collection type of Lus. [Lists](#lists), [records](#records), [dictionaries](#dictionaries), objects, and modules are all tables. The same syntax and the same library functions work on all of them.

### Creating tables

Curly braces create a table. The values between the braces are separated by commas and get the keys 1, 2, 3, and up, in the order in which they are written. A value written as `name = value` is stored under the string key `"name"`.

Square brackets after a table contain a key. `primes[1]` is the value that the table `primes` stores under the key 1. `point.x` is a short form of `point["x"]`, as [Records](#records) explains.

```lus
local empty = {}
local primes = { 2, 3, 5, 7 }
local point = { x = 10, y = 20 }

print(primes[1], primes[4])  --> 2  7
print(point.x, point.y)      --> 10  20
```

An assignment to `stock["apples"]` stores a value under the key `"apples"`. A key that is not in the table has the value `nil`. Assigning `nil` to a key removes the key from the table.

```lus
local stock = {}
stock["apples"] = 30
stock["pears"] = 12
print(stock["apples"], stock["plums"])  --> 30  nil

stock["pears"] = nil
print(stock["pears"])                   --> nil
```

### Lists

A _list_ is a table whose keys are the integers from 1 to the number of items, with no gaps. Lists hold ordered data, such as the lines of a file or the arguments of a command. The key of an item is its _index_, which is 1 for the first item. The length operator `#` produces the number of items, which is also the index of the last item.

```lus
local days = { "Mon", "Tue", "Wed" }
print(#days, days[1], days[#days])  --> 3  Mon  Wed

days[#days + 1] = "Thu"
print(#days, days[4])               --> 4  Thu
```

The functions of the [`table`](/manual/api#table-library) library change a list in place. [`table.insert`](/manual/api#table.insert) adds an item at the end of a list or, with a position as its second argument, inserts the item there and moves the later items up by one. [`table.remove`](/manual/api#table.remove) removes and returns the last item or, with a position, the item at that position, moving the later items down by one.

```lus
local queue = { "b", "c" }
table.insert(queue, "d")        -- b c d
table.insert(queue, 1, "a")     -- a b c d

print(table.remove(queue))      --> d
print(table.remove(queue, 1))   --> a
print(#queue, queue[1])         --> 2  b
```

`#` is reliable only for a list without gaps. Assigning `nil` to an index in the middle of a list leaves a gap, after which `#` can produce the index of the item before the gap or the index of the last item. To delete an item from the middle of a list, call `table.remove`, which moves the later items down.

[`table.sort`](/manual/api#table.sort) sorts a list in place. With one argument, it compares the items with `<`, so numbers are sorted from the smallest to the largest and strings [character by character](#comparison). The optional second argument is a comparison function, which `table.sort` calls with two items and which must return `true` if the first item belongs before the second. [`table.concat`](/manual/api#table.concat) joins a list of strings and numbers into one string, placing its second argument between the items as a separator.

```lus
local scores = { 72, 95, 58, 81 }
table.sort(scores)
print(table.concat(scores, " "))   --> 58 72 81 95

table.sort(scores, function(a, b)
    return a > b
end)
print(table.concat(scores, ", "))  --> 95, 81, 72, 58
```

The `table` library also has functions that filter, transform, group, and summarize lists. [Table functions](/manual/data#table-functions) describes them.

### Records

A _record_ is a table that describes one thing, such as a user, with string keys that name the properties of the thing. A key together with its value is a _field_. A key that is a valid [name](#local-variables) can be written after a dot, so `user.name` is the same as `user["name"]`. Fields are usually read and assigned with the dot.

```lus
local user = { name = "Ada", age = 36 }
user.email = "ada@example.org"
user.age = user.age + 1

print(user.name, user.age, user.email)  --> Ada  37  ada@example.org
print(user.phone)                       --> nil
```

A record is a readable way to pass many optional settings to a function. The function has one parameter that receives a table, in which the call names each setting that it passes. A call whose only argument is a table in curly braces can omit the parentheses.

```lus
local function connect(options)
    local port = options.port or 80
    return `$(options.host):$port`
end

print(connect({ host = "example.org", port = 8080 }))  --> example.org:8080
print(connect{ host = "example.org" })                 --> example.org:80
```

### Collecting arguments into a list

A function with [variable arguments](#variable-arguments) often needs to count the arguments or to process them one at a time. A name after the three dots declares a local variable that holds the arguments as a list, whose field `n` is the number of arguments. The following function computes the average of its arguments.

```lus
local function average(...numbers)
    if numbers.n == 0 then
        return 0
    end
    local total = 0
    for i = 1, numbers.n do
        total = total + numbers[i]
    end
    return total / numbers.n
end

print(average(4, 8, 6))  --> 6.0
print(average())         --> 0
```

`n` also counts arguments that are `nil`, so with the arguments `1, nil, 3` the field `n` is 3. The list then has a [gap](#lists), which makes `#` unreliable for it. In a function that names its extra arguments, three dots still stand for those arguments, so the function can pass them to another function.

[`table.unpack`](/manual/api#table.unpack) does the reverse, returning the items of a list as separate values. A program uses it to pass the items of a list as the arguments of a call. `print(table.unpack({ 1, 2, 3 }))` is the same as `print(1, 2, 3)`.

### Dictionaries

A _dictionary_ is a table whose keys are data, such as the words of a text or the identifiers of users. A program uses a dictionary to find the value that belongs to a key. A key can be a value of any type, such as a string, a number, a boolean, a table, or a function, except `nil` and NaN. NaN, short for "not a number", is the float that `0 / 0` produces. In curly braces, a key that is not a valid name is written in square brackets.

```lus
local capitals = {
    ["New Zealand"] = "Wellington",
    ["South Korea"] = "Seoul",
    France = "Paris",
}

local country = "South Korea"
print(capitals[country])    --> Seoul
print(capitals.France)      --> Paris
print(capitals["Germany"])  --> nil
```

The name after a dot is the key itself, so `capitals.country` reads the key `"country"`. In square brackets, the key is the value of the expression, so `capitals[country]` reads the key `"South Korea"`.

Dictionaries are often used for counting. The following loop counts how often each word occurs in a list.

```lus
local words = { "tea", "milk", "tea", "sugar", "tea" }
local counts = {}
for i = 1, #words do
    local word = words[i]
    counts[word] = (counts[word] or 0) + 1
end

print(counts.tea, counts.milk, counts.salt)  --> 3  1  nil
```

`#` counts only the keys 1, 2, 3, and up, so `#counts` is 0. [`pairs`](/manual/guide#ipairs-and-pairs) iterates over every key of a dictionary.

### Nested tables

A value in a table can be another table. Programs use nested tables for structured data, such as a list of records, a record that contains a list, or a grid of rows. Accesses apply from left to right, so `order.items[2].name` reads the field `items` of `order`, then item 2 of that list, then the field `name` of that item.

```lus
local order = {
    id = 1042,
    customer = { name = "Ada", city = "London" },
    items = {
        { name = "tea", price = 4.50 },
        { name = "mug", price = 12.00 },
    },
}

print(order.customer.city)   --> London
print(order.items[2].name)   --> mug
print(#order.items)          --> 2
```

JSON data has the same structure, so [`fromjson`](/manual/api#fromjson) converts JSON text to nested tables and [`tojson`](/manual/api#tojson) converts nested tables back to JSON text.

### Variables refer to tables

A variable that holds a table holds a _reference_ to it. An assignment copies the reference, so both variables then refer to the same table. Passing a table to a function copies the reference to the parameter in the same way. A change to the table is therefore visible from every variable that refers to it. In the following example, `a` and `b` refer to the same list, which the `clear` function empties.

```lus
local a = { 1, 2, 3 }
local b = a
b[1] = 99
print(a[1])  --> 99

local function clear(list)
    for i = #list, 1, -1 do
        list[i] = nil
    end
end
clear(a)
print(#b)    --> 0
```

`==` compares references. Two tables are equal only if they are the same table, so `{} == {}` is `false`. [`table.clone`](/manual/guide#copying-tables) makes an independent copy of a table.

### Methods

A field of a table can hold a function. A _method_ is such a function that works on the data of its table, so it needs the table as an argument, which the colon passes. `account:deposit(50)` calls the function `account.deposit` with `account` as the first argument and `50` as the second.

In a declaration, the colon adds a first parameter named `self`. `function account:deposit(amount)` declares the function `account.deposit` with the parameters `self` and `amount`.

```lus
local account = { balance = 100 }

function account:deposit(amount)
    self.balance = self.balance + amount
end

function account:report()
    return `balance: $(self.balance)`
end

account:deposit(50)
print(account:report())  --> balance: 150
```

With the colon, the table is written once, which is shorter when the table is the result of a long expression, as in `bank.accounts[id]:deposit(50)`.

These methods are fields of one table. A program with many accounts stores the methods once and shares them among all the accounts with a metatable, as [Metatables and objects](/manual/guide#metatables-and-objects) explains.

### Tables as modules

A table can hold related functions and constants under one name. Each [library](#built-in-functions) is such a table. `string`, `table`, and `math` are global variables that hold tables, so `math.floor` is the field `floor` of the table `math`. A function declaration can name a field of a table, as in `function shapes.circle(radius) ... end`, which stores the function in the field `circle` of the table `shapes`.

```lus
print(type(math), type(math.floor))  --> table  function
print(math.floor(7.8), math.max(3, 9))  --> 7  9
```

A program divides its own code in the same way. A _module_ is a file that creates such a table and returns it. Another file calls [`require`](/manual/api#require) with the name of the module and receives the table, as [Modules](#modules) shows.

### Destructuring with `from`

Code that uses several fields of a table often copies them to local variables first. An ordinary declaration writes each name twice: `local host, port = config.host, config.port`. A declaration with `from` writes each name once and gives each variable the value of the field with the same name. This is called _destructuring_.

```lus
local config = { host = "example.org", port = 8080, debug = false }

local host, port from config
print(host, port)  --> example.org  8080
```

A variable is `nil` if the table has no field with its name. The expression after `from` is evaluated once and can be a function call that returns a table.

`from` is the usual way to copy functions from a library or a module to local variables. The following example calls two functions of the `table` library by short names.

```lus
local insert, remove from table

local stack = {}
insert(stack, "a")
insert(stack, "b")
print(remove(stack), #stack)  --> b  1
```

`require` returns a table, so `from` also works on its result. `local parse, format from require("dates")` loads the module in the file `dates.lus` and stores two of its functions in local variables.

Without `local`, `from` assigns to variables that already exist, which is useful in a loop that reads the same fields from a different record on each pass. The following loop computes the length of a route by adding the distance between each point and the previous point.

```lus
local route = { { x = 0, y = 0 }, { x = 3, y = 4 }, { x = 3, y = 10 } }

local x, y from route[1]
local distance = 0
for i = 2, #route do
    local previous_x, previous_y = x, y
    x, y from route[i]
    distance = distance + math.sqrt((x - previous_x) ^ 2 + (y - previous_y) ^ 2)
end
print(distance)  --> 11.0
```

`global width, height from settings` declares global variables in the same way.

### Optional chaining

Nested data often has optional parts, such as the address of a user or a section of a configuration. Reading a field of a missing part, which is `nil`, is an error. After `local user = { name = "Ada" }`, the expression `user.address.city` stops the program with the error `attempt to index a nil value (field 'address')`.

A `?` after a part of an expression tests the value of that part. If the value is `nil` or `false`, Lus skips the rest of the expression, whose result is then that value. Otherwise the expression continues. Write a `?` after each part that can be missing.

```lus
local reply = {
    user = { name = "Ada", address = { city = "London" } },
}

print(reply.user.address?.city)           --> London
print(reply.user.employer?.name)          --> nil
print(reply.user.employer?.name or "none")  --> none
```

In the last line, `or` gives a default for the missing name. Without `?`, the program tests each part separately: `reply.user.employer and reply.user.employer.name`.

`?` can precede every kind of access: `?.name` reads a field, `?[i]` reads an index, `?:method()` calls a method, and `?(arguments)` calls a function. The call form calls a function only if the function exists, which is useful for optional callbacks.

```lus
local handlers = {
    resize = function(width, height)
        return width * height
    end,
}

print(handlers.resize?(80, 24))  --> 1920
print(handlers.close?())         --> nil

local tags = nil
print(tags?[1])                  --> nil
```

An expression with a `?` must be used as a value, for example in an assignment, in a condition, or as an argument. It cannot be a statement of its own or the target of an assignment.

### Slices

A _slice_ is a copy of part of a list, a string, or a vector, written with two positions in square brackets, separated by a comma. The slice contains the items from the first position to the second, both included. An omitted position extends the slice to the start or to the end.

```lus
local letters = { "a", "b", "c", "d", "e" }

print(table.concat(letters[2, 4], " "))  --> b c d
print(table.concat(letters[, 2], " "))   --> a b
print(table.concat(letters[4, ], " "))   --> d e
print(("hello world")[1, 5])             --> hello
```

A slice of a list is a new list, so changing it leaves the original list unchanged.

### Copying tables

An assignment copies a [reference](#variables-refer-to-tables) to a table, so a program that changes a table and also needs the original must copy the table itself. [`table.clone`](/manual/api#table.clone) returns a new table with the same keys and values.

```lus
local defaults = { color = "blue", size = 10 }
local mine = table.clone(defaults)
mine.color = "red"

print(defaults.color, mine.color)  --> blue  red
```

This copy is _shallow_. `table.clone` copies the reference to a nested table, so the original and the copy share the nested table. With `true` as the second argument, `table.clone` makes a _deep_ copy, in which every nested table is copied too.

```lus
local original = { name = "report", tags = { "draft" } }
local shallow = table.clone(original)
local deep = table.clone(original, true)

original.tags[1] = "final"
print(shallow.tags[1], deep.tags[1])  --> final  draft
```

## Iteration

To _iterate_ is to process the items of a collection one after another. The [numeric `for`](/manual/guide#numeric-for-loops) loop iterates over numbers. The _generic `for`_ loop iterates over the items of a list, the keys of a dictionary, the matches in a string, or the lines of a file. It gets the items from an _iterator_, which is a function that returns the next item each time it is called.

### The generic for

A generic `for` loop has one or more loop variables, the keyword `in`, and an expression that produces the items. The body runs once for each item, with the loop variables holding the values of the current item. [`ipairs`](/manual/api#ipairs) produces the items of a list, each with two values, the index and the value at that index.

```lus
local days = { "Mon", "Tue", "Wed" }

for index, day in ipairs(days) do
    print(index, day)
end
--> 1  Mon
--> 2  Tue
--> 3  Wed
```

Each pass creates new loop variables, which are local to the body. Assigning to the first loop variable is a compile error, but the body can assign to the others. [`break` and `continue`](#break-and-continue) work as in every loop. By convention, a loop that uses only the second variable names the first one `_`.

### `ipairs` and `pairs`

`ipairs(t)` produces the items of a list in order. It starts at index 1 and stops before the first index whose value is `nil`.

[`pairs(t)`](/manual/api#pairs) produces every key of a table, of any type, with its value. A program uses `pairs` to iterate over a dictionary or over the fields of a record. The following loop counts the entries of a price list and adds the prices.

```lus
local prices = { tea = 4.50, mug = 12.00, spoon = 2.25 }

local total, count = 0, 0
for name, price in pairs(prices) do
    total = total + price
    count = count + 1
end
print(count, total)  --> 3  18.75
```

`pairs` produces the keys in an unspecified order. A program that needs a fixed order copies the keys to a list and sorts the list, as [`sorted_pairs`](#writing-an-iterator-with-a-function) does.

The body of a `pairs` loop may assign to keys that the table already has or remove such a key by assigning `nil`. If the body adds a new key to the table, the keys that the rest of the loop produces are unpredictable.

### Writing an iterator with a function

The generic `for` loop calls its [iterator](#iteration) before each pass and assigns the results of the call to the loop variables, ending when the first result is `nil`. An iterator therefore returns the values of the next item on each call, or `nil` when no item is left.

A program writes its own iterator when several loops go over data in the same way, such as a dictionary in sorted order, so that each of those loops is as short as a loop over `ipairs`. An iterator is usually created and returned by another function. The iterator stores its position in a local variable of that function, which it [keeps between calls](/manual/guide#functions-that-keep-local-variables).

The following `sorted_pairs` function produces the keys of a dictionary in sorted order, with their values.

```lus
local function sorted_pairs(t)
    local keys = {}
    for key in pairs(t) do
        keys[#keys + 1] = key
    end
    table.sort(keys)

    local i = 0
    return function()
        i = i + 1
        local key = keys[i]
        if key ~= nil then
            return key, t[key]
        end
    end
end

local stock = { pears = 12, apples = 30, figs = 4 }
for name, count in sorted_pairs(stock) do
    print(name, count)
end
--> apples  30
--> figs  4
--> pears  12
```

The loop calls `sorted_pairs(stock)` once, before the first pass, then calls the returned function before each pass.

The loop can also store the position for the iterator. The expression after `in` then produces three values: an iterator, the collection, and a starting position. Before each pass, the loop calls the iterator with the collection and the current position and takes the first result of the call as the new position. Such an iterator has no variables of its own, so every loop can use the same function. The following `reversed` function produces the items of a list from the last to the first.

```lus
local function previous(list, i)
    i = i - 1
    if i >= 1 then
        return i, list[i]
    end
end

local function reversed(list)
    return previous, list, #list + 1
end

local queue = { "ada", "lin", "grace" }
for position, name in reversed(queue) do
    print(position, name)
end
--> 3  grace
--> 2  lin
--> 1  ada
```

`ipairs` works in this way, returning an iterator, the list, and the starting index 0.

Several library functions return iterators. [`string.gmatch`](/manual/api#string.gmatch) returns an iterator over the [matches of a pattern](/manual/guide#every-match-with-stringgmatch) in a string. [`io.lines`](/manual/api#io.lines) returns an iterator over the lines of a file.

## Strings and patterns

Many programs work with text: they clean input that a person typed, extract the fields of a log line, or build a report. The functions of the [`string`](/manual/api#string-library) library measure, cut, convert, search, and replace text. The functions that search and replace take a [pattern](#patterns).

Every function whose first argument is a string can be called as a [method](#methods) of that string, so `name:upper()` is the same as `string.upper(name)`. A string literal must be in parentheses for a method call, as in `("abc"):upper()`.

### Length and parts

`#` produces the [length](#length) of a string in characters, so an accented letter such as `é` counts as one. A _position_ in a string is the number of a character, counted from 1.

[`string.sub(s, first, last)`](/manual/api#string.sub) returns the part of `s` from position `first` to position `last`, both included. A negative position counts from the end of the string, so `-1` is the last character. Without `last`, the part extends to the end of the string.

```lus
local s = "héllo wörld"

print(#s)             --> 11
print(s:sub(1, 5))    --> héllo
print(s:sub(7))       --> wörld
print(s:sub(-3))      --> rld
print(s:sub(2, -2))   --> éllo wörl
```

A [slice](/manual/guide#slices) produces the same part: `s[1, 5]` is `s:sub(1, 5)` and `s[7, ]` is `s:sub(7)`. Only `s:sub` counts a negative position from the end.

### Case, repetition, and reversal

[`string.upper`](/manual/api#string.upper) and [`string.lower`](/manual/api#string.lower) convert the letters `a` to `z` to upper case or to lower case and leave every other character as it is. [`string.rep`](/manual/api#string.rep) repeats a string a given number of times, with an optional third argument as a separator between the copies. [`string.reverse`](/manual/api#string.reverse) reverses the order of the characters.

```lus
print(("Hello"):upper(), ("Hello"):lower())  --> HELLO  hello
print(("-"):rep(20))                         --> --------------------
print(("?"):rep(3, ", "))                    --> ?, ?, ?
print(("stressed"):reverse())                --> desserts
```

To compare two strings without regard to case, convert both to lower case first: `a:lower() == b:lower()`.

### Splitting, joining, and trimming

[`string.split`](/manual/api#string.split) cuts a string at every occurrence of a delimiter and returns the pieces as a list. [`string.join`](/manual/api#string.join) does the reverse. It joins the items of a list into one string with a delimiter between them, converting items that are not strings as `tostring` does.

```lus
local fields = ("ada,36,london"):split(",")
print(#fields, fields[1], fields[3])  --> 3  ada  london

print(string.join(fields, " | "))     --> ada | 36 | london
print(string.join({ 1, true, "x" }, "-"))  --> 1-true-x
```

`string.join` is also the efficient way to build a long string from many parts: add the parts to a list and join them once at the end.

[`string.trim`](/manual/api#string.trim) removes whitespace from both ends of a string, which text that a person typed or that was read from a file often has. [`string.ltrim`](/manual/api#string.ltrim) removes it from the start only, [`string.rtrim`](/manual/api#string.rtrim) from the end only. When the optional second argument is a string of characters, the functions remove those characters and keep whitespace.

```lus
local input = "   ada@example.org \n"
print("[" .. input:trim() .. "]")       --> [ada@example.org]
print(("--title--"):trim("-"))          --> title

local parts = ("red, green , blue"):split(",")
for i, part in ipairs(parts) do
    parts[i] = part:trim()
end
print(string.join(parts, "|"))          --> red|green|blue
```

The delimiter of `string.split` is literal text. To split at a delimiter that varies, such as any amount of whitespace, use a pattern with [`string.gmatch`](#every-match-with-stringgmatch).

### Formatting values

A [string in backticks](/manual/guide#strings) is enough for most messages. [`string.format`](/manual/api#string.format) is for output that needs a fixed number of decimals, padding to a width, or another number base. Its first argument is a template, in which `string.format` replaces each `%` item with the next argument, formatted as the table shows.

| Item | Output |
| --- | --- |
| `%d` | An integer. |
| `%f` | A number with six decimals. `%.2f` gives two. |
| `%s` | Any value, converted as `tostring` does. |
| `%x` | An integer in hexadecimal. `%X` uses upper case letters. |
| `%q` | A string in quotes with escapes, which Lus can read back. |
| `%%` | A percent sign. |

A number between the `%` and the letter is a minimum width, to which a shorter value is padded with spaces on the left. A `-` before the width puts the spaces on the right. A `0` before the width pads a number with zeros.

```lus
print(string.format("%.2f", 3.14159))            --> 3.14
print(string.format("[%5d|%-5d|%05d]", 42, 42, 42))  --> [   42|42   |00042]
print(string.format("#%02x%02x%02x", 255, 128, 0)) --> #ff8000
print(string.format("%-8s%8.2f", "tea", 4.5))    --> tea         4.50
print(string.format("%d%% of %s", 80, "disk"))   --> 80% of disk
```

The result of `string.format` is a string, so a string in backticks can contain the call: `` `total: $(string.format("%.2f", total))` ``.

### Characters and code points

Every character has a Unicode number, called its _code point_. [`string.byte`](/manual/api#string.byte) returns the code point of the character at a position, of each character in a range when given two positions, or of the first character when given no position. [`string.char`](/manual/api#string.char) returns the string made of the characters with the given code points. A program uses the two functions to calculate with characters, for example to find the letter three places after `a`.

```lus
print(("A"):byte())              --> 65
print(("héllo"):byte(1, 3))      --> 104  233  108
print(string.char(72, 105))      --> Hi
print(string.char(("a"):byte() + 3))  --> d
```

### Patterns

A program often searches for text of a certain form, such as a number, a date, a word followed by a colon, or everything between two quotes, whose exact characters differ from one occurrence to the next. A _pattern_ is a string that describes such a form. Text that has the form _matches_ the pattern. The following functions take a pattern:

- [`string.find`](/manual/api#string.find) returns the position of the first match.
- [`string.match`](/manual/api#string.match) returns the text of the first match, or parts of it.
- [`string.gmatch`](/manual/api#string.gmatch) iterates over every match.
- [`string.gsub`](/manual/api#string.gsub) replaces every match.

A pattern replaces a loop over the characters. The following call extracts the time, the level, and the message of a log entry.

```lus
local entry = "12:30:07 ERROR connection lost"
local time, level, message = entry:match("(%S+) (%u+) (.*)")
print(time, level, message)  --> 12:30:07  ERROR  connection lost
```

In this pattern, `%S+` matches one or more characters that are not whitespace, `%u+` matches one or more upper case letters, and `.*` matches the rest of the line. `match` returns the parts in parentheses.

A pattern consists of _items_, each of which matches one character or several characters in a row. The items match one after another, from left to right. `string.match` returns the first part of the string that matches the whole pattern, or `nil` if no part matches.

### Literal text

A letter, a digit, or a space in a pattern matches itself, so a pattern that consists only of such characters matches exactly that text.

```lus
print(("status: ready"):match("ready"))  --> ready
print(("status: ready"):match("done"))   --> nil
```

Matching is case sensitive, so the pattern `Ready` does not match the text `ready`. To match without regard to case, [convert the text to lower case](#case-repetition-and-reversal) first.

The punctuation characters `( ) . % + - * ? [ ] ^ $` have special meanings in a pattern. After a `%`, such a character matches itself, so `%.` matches a dot.

### Character classes

A _character class_ is an item that matches one character of a certain kind, such as a digit. Apart from the dot, which matches any character, every class is a `%` followed by a letter.

| Class | Matches one |
| --- | --- |
| `.` | character of any kind |
| `%d` | digit, `0` to `9` |
| `%a` | letter, `a` to `z` or `A` to `Z` |
| `%l` | lower case letter |
| `%u` | upper case letter |
| `%w` | letter or digit |
| `%s` | whitespace character: space, tab, or line break |
| `%x` | hexadecimal digit |
| `%p` | punctuation character |
| `%c` | control character |

A class with an upper case letter matches the opposite, so `%D` matches any character that is not a digit and `%S` any character that is not whitespace.

A pattern can combine classes and literal characters. The first pattern in the following example matches a time: two digits, a colon, and two digits.

```lus
print(("opens at 09:30 daily"):match("%d%d:%d%d"))  --> 09:30
print(("room B7"):match("%u%d"))                    --> B7
print(("a-b"):match("%a.%a"))                       --> a-b
```

The classes that are written with a letter contain ASCII characters only, so `%a` matches `e` but not `é`. The dot matches every character, including `é`. A [set](#sets) can contain characters outside ASCII.

### Sets

A _set_ is a list of characters in square brackets that matches one character in the list. In a set, two characters with a `-` between them are a range, so `[a-z]` contains every lower case letter. A set can also contain classes, as in `[%w_]`.

```lus
print(("grey"):match("gr[ae]y"), ("gray"):match("gr[ae]y"))  --> grey  gray
print(("id: x9"):match("[a-z][0-9]"))                        --> x9
print(("file_name.txt"):match("[%w_]+"))                     --> file_name
```

In the last line, the `+` after the set [repeats](#repetition) it. `[%w_]+` matches one or more characters that are letters, digits, or underscores.

A set that starts with `^` matches one character that is not in the list. Followed by a `+`, such a set matches everything up to a delimiter.

```lus
print(("name=Ada;age=36"):match("[^;]+"))  --> name=Ada
print(("path/to/file"):match("[^/]+"))     --> path
```

### Repetition

A _repetition character_ after an item allows the item to match several times in a row. It applies to one item: the literal character, the class, or the set before it.

| Item | Matches |
| --- | --- |
| `x+` | one or more `x`, as many as possible |
| `x*` | zero or more `x`, as many as possible |
| `x-` | zero or more `x`, as few as possible |
| `x?` | zero or one `x` |

`+` matches a sequence of one or more characters, so `%d+` matches a whole number, `%a+` a word, and `%s+` any amount of whitespace. `*` also matches when the item does not occur at all, which is useful for optional whitespace. `?` makes one item optional.

```lus
print(("order 1042 shipped"):match("%d+"))      --> 1042
print(("x =   5"):match("x%s*=%s*%d"))          --> x =   5
print(("x=5"):match("x%s*=%s*%d"))              --> x=5
print(("https://lus.dev"):match("https?://"))   --> https://
print(("-12 degrees"):match("-?%d+"))           --> -12
```

`+` and `*` are _greedy_, which means they match as many characters as possible while the rest of the pattern still matches. `-` is _lazy_ and matches as few characters as possible. The two differ when the text contains the closing delimiter more than once, as in the following example, where `.*` matches up to the last `>` and `.-` up to the first.

```lus
local html = "<b>bold</b> and <i>italic</i>"

print(html:match("<.*>"))  --> <b>bold</b> and <i>italic</i>
print(html:match("<.->"))  --> <b>
```

Use `.-` followed by a delimiter to match up to the nearest occurrence of that delimiter.

### Anchors

A pattern can match anywhere in the string unless it has _anchors_. A `^` at the start of the pattern requires the match to begin at the start of the string. A `$` at the end requires the match to end at the end of the string. With both anchors, the whole string must match the pattern, which is how programs validate input.

```lus
print(("item 42"):match("%d+"))        --> 42
print(("item 42"):match("^%d+"))       --> nil
print(("42 items"):match("^%d+"))      --> 42
print(("42 items"):match("^%d+$"))     --> nil
print(("42"):match("^%d+$"))           --> 42
```

The following function checks that a string is a valid identifier: a letter or an underscore, followed by any number of letters, digits, and underscores. Without the anchors, the pattern would also match a string that only contains an identifier, such as `first name`.

```lus
local function is_identifier(s)
    return s:match("^[%a_][%w_]*$") ~= nil
end

print(is_identifier("user_name"))   --> true
print(is_identifier("_tmp2"))       --> true
print(is_identifier("2fast"))       --> false
print(is_identifier("first name"))  --> false
```

### Captures

A program often needs specific parts of a match, such as the key and the value of a setting. Parentheses around a part of a pattern make that part a _capture_. `string.match` returns the text of each capture in order, or the whole match if the pattern has no captures.

```lus
local key, value = ("timeout = 30"):match("(%w+)%s*=%s*(%w+)")
print(key, value)  --> timeout  30
```

The parentheses match no characters, so this pattern matches the same text as `%w+%s*=%s*%w+`. They only determine which parts `string.match` returns.

The following pattern captures the three parts of a date, with the `-` between the numbers written `%-` so that it matches a hyphen. A capture is always a string, which `tonumber` converts when the program needs a number.

```lus
local year, month, day = ("2026-03-04"):match("^(%d%d%d%d)%-(%d%d)%-(%d%d)$")
print(year, month, day)                  --> 2026  03  04
print(tonumber(month) + 1)               --> 4

print(("2026-3-4"):match("^(%d%d%d%d)%-(%d%d)%-(%d%d)$"))  --> nil
```

When the pattern does not match, every variable of the assignment is `nil`. A [condition that declares variables](/manual/guide#conditions-that-declare-variables) tests the match and names the captures in one statement, as in the following example, which reads the name and the value of an HTTP header.

```lus
local line = "Content-Length: 348"
if name, value = line:match("^([%w%-]+):%s*(.*)$") then
    print(name, value)  --> Content-Length  348
end
```

An empty pair of parentheses is a _position capture_, whose value is the position in the string that the match has reached at that point of the pattern. A program uses it to learn where a match is, for example to cut the string there.

```lus
local text = "key:value"
local stop = text:match(":()")
print(stop)             --> 5
print(text:sub(stop))   --> value

print(("hello world"):match("()wor()"))  --> 7  10
```

In a pattern, `%1` matches the same text that the first capture matched. `%2` to `%9` do the same for the later captures. The following patterns find a repeated word and a quoted text whose closing quote is the same character as its opening quote.

```lus
print(("it was the the best"):match("(%a+) %1"))        --> the
print(([[say "it's fine" now]]):match("([\"'])(.-)%1")) --> "  it's fine
```

### Finding with `string.find`

A program calls [`string.find`](/manual/api#string.find) to test whether a string contains a match, or to learn where the match is. Its results are the [positions where the first match starts and ends](#conditions-that-declare-variables).

```lus
local s = "error at line 42"
print(s:find("line"))    --> 10  13
print(s:find("%d+"))     --> 15  16
print(s:find("warning")) --> nil

if s:find("^error") then
    print("failed")      --> failed
end
```

To search for literal text that contains special characters, pass `true` as the fourth argument, which makes `string.find` search for the second argument as plain text. The call must then also have the third argument, the [position where the search starts](#while-loops), so a plain search from the start passes `1`.

```lus
local price = "total (USD): 3.50"

print(price:find("(USD)", 1, true))  --> 7  11
print(price:find(".", 1, true))      --> 15  15
print(price:find("."))               --> 1  1
```

In the last line, the dot is a pattern, so it matches the first character of the string. Use the plain search whenever the text to find comes from a user or from a file.

### Extracting with `string.match`

[`string.match`](/manual/api#string.match) returns the [captures](#captures) of the first match, so a program calls it when it needs parts of a text. Like `string.find`, it accepts a starting position as its third argument.

The following example splits a web address into a scheme of one or more letters, a host that extends to the next slash, and a path that holds the rest.

```lus
local url = "https://lus.dev/manual/guide"
local scheme, host, path = url:match("^(%a+)://([^/]+)(.*)$")
print(scheme, host, path)  --> https  lus.dev  /manual/guide
```

### Every match with `string.gmatch`

[`string.gmatch`](/manual/api#string.gmatch) returns an [iterator](/manual/guide#iteration) that produces the matches of a pattern one after another, from left to right. A `for` loop over the iterator runs once for each match, with the captures in its loop variables, or the whole match if the pattern has no captures.

The following loop uses the pattern `%S+` to split a string into words, whatever the number of spaces between them.

```lus
local words = {}
for word in ("  the quick   brown fox "):gmatch("%S+") do
    words[#words + 1] = word
end
print(#words, string.join(words, ","))  --> 4  the,quick,brown,fox
```

With a different pattern, the same loop extracts numbers from text. The following example adds the durations in a line of timings.

```lus
local timings = "GET /a 12ms, GET /b 250ms, GET /c 31ms"
local total = 0
for duration in timings:gmatch("(%d+)ms") do
    total = total + tonumber(duration)
end
print(total)  --> 293
```

The following example reads a configuration text with lines of the form `key = value` into a table. For each line, `string.match` extracts the key and the value. A comment line has no `=`, so the pattern does not match it and `key` is `nil`.

```lus
local text = [[
# server settings
host = example.org
port = 8080

debug=true
]]

local config = {}
for line in text:gmatch("[^\n]+") do
    local key, value = line:match("^%s*([%w_]+)%s*=%s*(.-)%s*$")
    if key then
        config[key] = value
    end
end

print(config.host, config.port, config.debug)  --> example.org  8080  true
```

The pattern for a line consists of the following parts.

- `^%s*` matches optional whitespace at the start of the line.
- `([%w_]+)` captures the key, which consists of letters, digits, and underscores.
- `%s*=%s*` matches the equals sign and the optional whitespace around it.
- `(.-)` captures the value, with as few characters as possible.
- `%s*$` matches optional whitespace up to the end of the line.

Because `.-` is lazy, the `%s*` after it matches the whitespace at the end of the line. The captured value therefore has no trailing whitespace.

In `string.gmatch`, a `^` at the start of the pattern matches a literal `^`. An anchor there would allow only one match.

### Replacing with `string.gsub`

[`string.gsub(s, pattern, replacement)`](/manual/api#string.gsub) returns a copy of `s` in which every match of the pattern is replaced, with the number of matches as its second result. The replacement can be a string, a table, or a function.

In a replacement string, `%1` to `%9` stand for the captures and `%0` for the whole match, so the replacement can repeat or reorder parts of the match. A percent sign in the replacement is written `%%`.

```lus
print(("hello world"):gsub("o", "0"))            --> hell0 w0rld  2
print(("a  b    c"):gsub("%s+", " "))            --> a b c  2
print(("2026-03-04"):gsub("(%d+)%-(%d+)%-(%d+)", "%3/%2/%1"))  --> 04/03/2026  1
print(("ada lin"):gsub("%a+", "<%0>"))           --> <ada> <lin>  2
```

With a replacement table, `string.gsub` uses each match as a key of the table, or the first capture if the pattern has captures. The value under that key replaces the match. If the table has no value for a match, the match stays in the result unchanged. The following call fills a template that has placeholders of the form `$name`. Its pattern contains `%$` because `$` is a special character.

```lus
local template = "Dear $name, your order $id ships on $day."
local values = { name = "Ada", id = 1042, day = "Friday" }

local letter = template:gsub("%$(%w+)", values)
print(letter)  --> Dear Ada, your order 1042 ships on Friday.
```

With a replacement function, `string.gsub` calls the function with the captures of each match and replaces the match with the result. If the function returns `nil` or `false`, the match stays in the result unchanged. A function is for replacements that the program must compute. The following example fills a template of the same kind and marks each placeholder that has no value.

```lus
local values = { name = "Ada" }

local letter = ("Hi $name, see you $day."):gsub("%$(%w+)", function(key)
    return values[key] or `<missing $key>`
end)
print(letter)  --> Hi Ada, see you <missing day>.
```

The following example decodes the escapes of a web address, such as `%20` for a space. Its pattern matches a percent sign followed by two hexadecimal digits, which the function converts to the character with that code point.

```lus
local encoded = "tea%20%26%20milk%3F"
local decoded = encoded:gsub("%%(%x%x)", function(hex)
    return string.char(tonumber(hex, 16))
end)
print(decoded)  --> tea & milk?
```

A fourth argument is the maximum number of replacements, so `s:gsub(" ", "", 1)` removes only the first space.

[Parentheses](#multiple-results) around a call to `gsub` keep only the string.

### Balanced pairs and word boundaries

The items `%b` and `%f` match text that classes and repetition cannot describe: nested pairs of brackets and whole words.

`%b` followed by two characters matches a _balanced pair_, which starts with the first character, ends with the second, and contains the same number of each in between. `%b()` matches an expression in parentheses, including any parentheses nested in it, while `%(.-%)` ends at the first closing parenthesis.

```lus
local code = "total = max(a, min(b, c)) + 1"

print(code:match("%(.-%)"))        --> (a, min(b, c)
print(code:match("%b()"))          --> (a, min(b, c))

local name, arguments = code:match("(%a+)(%b())")
print(name, arguments:sub(2, -2))  --> max  a, min(b, c)
```

`%b` works with any two characters, such as `%b[]`, `%b{}`, and `%b<>`.

`%f` followed by a set matches a _boundary_, which is a position where the previous character is outside the set and the next character is in the set. `%f` matches the position only, without any character. `%f[%w]` matches at the start of a word and `%f[%W]` at the end of one, so a pattern between the two matches whole words only.

```lus
print(("cat concat cat"):gsub("cat", "dog"))                  --> dog condog dog  3
print(("cat concat cat"):gsub("%f[%w]cat%f[%W]", "dog"))      --> dog concat dog  2
print(("the quick fox"):gsub("%f[%w]%l", string.upper))       --> The Quick Fox  3
```

The last line capitalizes each word by passing `string.upper` as the replacement function for each lower case letter at the start of a word.

### Escaping

A `%` before a [special character](#literal-text) _escapes_ it. A `%` is also allowed before a punctuation character that has no special meaning, so a safe rule is to escape every punctuation character that must match itself.

```lus
print(("version 2.10.3"):match("%d+%.%d+%.%d+"))   --> 2.10.3
print(("50% off (today)"):match("%d+%%"))          --> 50%
print(("50% off (today)"):match("%((%a+)%)"))      --> today
```

A program that builds a pattern from text it receives when it runs, such as a file name, must escape that text first. The following function puts a `%` before every punctuation character of a text.

```lus
local function escape(text)
    return (text:gsub("%p", "%%%0"))
end

local name = "report (v1.2).txt"
print(escape(name))                                  --> report %(v1%.2%)%.txt
print(("open report (v1.2).txt now"):match(escape(name)))  --> report (v1.2).txt
```

A search for the text alone needs no escaping, because the [fourth argument](#finding-with-stringfind) of `string.find` makes the search literal.

### Worked examples

#### Numbers in text

The following loop collects every number in a text. A number is an optional minus sign, one or more digits, an optional dot, and optional further digits, so the pattern matches both `3` and `2.5`.

```lus
local note = "Order 1042: 3 items, 2.5 kg, total 59.90 EUR"
local numbers = {}
for number in note:gmatch("-?%d+%.?%d*") do
    numbers[#numbers + 1] = tonumber(number)
end
print(string.join(numbers, " "))  --> 1042 3 2.5 59.9
```

#### Fields with a varying delimiter

`string.split` cuts at one exact delimiter, but in the following text, commas, semicolons, and spaces separate the fields in any combination. The set `[^,;%s]` matches every character that is not a delimiter, so each match is one field.

```lus
local tags = {}
for tag in ("lus, lua;zig  wasm"):gmatch("[^,;%s]+") do
    tags[#tags + 1] = tag
end
print(#tags, string.join(tags, "|"))  --> 4  lus|lua|zig|wasm
```

#### Converting a naming style

The following example converts a name such as `maxRetryCount` to the style `max_retry_count`. The replacement puts an underscore between each lower case letter and the upper case letter that follows it, then `lower` converts the result to lower case.

```lus
local snake = ("maxRetryCount"):gsub("(%l)(%u)", "%1_%2"):lower()
print(snake)  --> max_retry_count
```

#### Validating input

The following function converts a time such as `09:30` to two numbers. The anchors require the whole string to be a time. A pattern cannot test that a number is within a range, so the function compares the hours and the minutes after the match.

```lus
local function parse_time(s)
    local hours, minutes = s:match("^(%d%d):(%d%d)$")
    if not hours then
        return nil
    end
    hours, minutes = tonumber(hours), tonumber(minutes)
    if hours > 23 or minutes > 59 then
        return nil
    end
    return hours, minutes
end

print(parse_time("09:30"))   --> 9  30
print(parse_time("9:30"))    --> nil
print(parse_time("25:00"))   --> nil
```

#### A query string

A query string is the part of a web address that holds parameters in the form `key=value` with `&` between them. The pattern has two captures, so each pass of the loop receives a key and a value. A parameter without `=`, such as `desc`, does not match.

```lus
local query = "page=2&sort=name&desc"
local params = {}
for key, value in query:gmatch("([^&=]+)=([^&=]*)") do
    params[key] = value
end
print(params.page, params.sort, params.desc)  --> 2  name  nil
```

### The limits of patterns

Patterns have no notation for the following tasks, which a program does in other ways.

- A pattern matches one sequence of items, so it cannot express a choice between two words, such as `cat` or `dog`. The program tries one pattern after the other. A set expresses a choice between single characters, as in `[Cc]at`.
- A repetition character applies to one character, class, or set. To repeat a sequence such as `ab`, or a capture, the program uses a loop.
- A count such as "exactly four digits" is written by repeating the item, as in `%d%d%d%d`. For larger counts, [`string.rep`](/manual/api#string.rep) builds the pattern: `("%d"):rep(4)`.
- Nested formats, such as JSON or the source code of a program, need a parser. `%b` matches only one kind of balanced pair.

The following function accepts a date in two notations. It tries one pattern for each notation and uses the first pattern that matches.

```lus
local function parse_date(s)
    local year, month, day = s:match("^(%d%d%d%d)%-(%d%d)%-(%d%d)$")
    if not year then
        day, month, year = s:match("^(%d%d)/(%d%d)/(%d%d%d%d)$")
    end
    if not year then
        return nil
    end
    return tonumber(year), tonumber(month), tonumber(day)
end

print(parse_date("2026-03-04"))  --> 2026  3  4
print(parse_date("04/03/2026"))  --> 2026  3  4
print(parse_date("March 4"))     --> nil
```

The standard library has parsers for the common data formats, which handle quoting, escapes, and nesting correctly. [`fromjson`](/manual/api#fromjson) reads JSON and [`fromcsv`](/manual/api#fromcsv) reads CSV. [Data formats](/manual/data) describes both.

### Text and bytes

A string is text made of whole Unicode characters. Every string function counts in characters. Data that is not text, such as an image, a compressed file, or a message of a binary network protocol, belongs in a [vector](#vector), which holds bytes.

## Errors

A program raises an _error_ when it cannot continue, typically because of a missing file, an argument of the wrong type, or malformed input. Code raises an error by calling [`error`](/manual/api#error). Lus itself raises one for an invalid operation, such as adding a number to `nil`. An error ends the current function, then the function that called it, then the caller of that function, until a `catch` captures the error.

### Raising errors

A function raises an error when it cannot produce its result. The argument of `error` is the _error object_, the value that describes what went wrong. The following function raises an error for a withdrawal that is larger than the balance.

```lus nocheck
local function withdraw(balance, amount)
    if amount > balance then
        error("insufficient funds")
    end
    return balance - amount
end

print(withdraw(100, 30))    --> 70
print(withdraw(100, 300))
print("this line never runs")
```

No `catch` captures the error of the second call, so the program ends. The `lus` command writes the error object and the chain of calls to standard error, then exits with status 1.

```text
lus: bank.lus:3: insufficient funds
stack traceback:
        [C]: in global 'error'
        bank.lus:3: in local 'withdraw'
        bank.lus:8: in main chunk
        [C]: in ?
```

When the error object is a string, `error` puts the file name and the line number in front of it, as in `bank.lus:3:`. The position is for the programmer, so a message for the user of the program passes a second argument of `0` to omit it, as in `error("insufficient funds", 0)`.

[`assert`](/manual/api#assert) raises an error when a condition is false. If its first argument is truthy, `assert` returns that argument. Otherwise it raises an error with its second argument as the message. The following function requires a list with at least one value.

```lus
local function average(values)
    assert(#values > 0, "average needs at least one value")
    local sum = 0
    for _, value in ipairs(values) do
        sum = sum + value
    end
    return sum / #values
end

print(average({ 4, 6, 8 }))   --> 6.0
```

### Catching errors

Some errors are expected, so the program should handle them and continue. Text from outside the program is the usual case. [`fromjson`](/manual/api#fromjson) converts JSON text to a value and raises an error when the text is not valid JSON. A program that reads a settings file should report that error to the user and keep running. `catch` before an expression captures any error that the expression raises.

The first value of a `catch` expression is a status. If the expression succeeds, `catch` produces `true` followed by the values of the expression. If the expression raises an error, `catch` produces `false` followed by the error object.

```lus
local ok, settings = catch fromjson('{"port": 8080}')
print(ok, settings.port)   --> true  8080

local ok, message = catch fromjson('{"port": ')
print(ok)        --> false
print(message)   --> JSON parse error at position 10: unexpected end of input
```

The program continues after the second `catch` with the error object in `message`. It can print the message, use default settings, or request another file from the user.

The expression after `catch` can be any expression, such as a call or an operation. In the following example, `catch` captures the error that integer division by zero raises.

```lus
local total, count = 120, 0
local ok, share = catch total // count
print(ok)   --> false
```

A [condition that declares variables](/manual/guide#conditions-that-declare-variables) can contain a `catch`, which tests the status and declares the result in one line. The branch runs when every declared variable is truthy, which is the case when the expression succeeded and its result is truthy. The following program converts text to a port number and reports invalid text.

```lus
local function parse_port(text)
    local port = math.tointeger(tonumber(text))
    if not port or port < 1 or port > 65535 then
        error(`invalid port: $text`, 0)
    end
    return port
end

if ok, port = catch parse_port("8080") then
    print(`listening on port $port`)   --> listening on port 8080
end

if ok, port = catch parse_port("http") then
    print(`listening on port $port`)
else
    print(port)   --> invalid port: http
end
```

`math.tointeger` returns a whole number as an integer and `nil` for any other value, so `parse_port` rejects `"80.5"` as well as `"http"`. When the call raises an error, `port` holds the error object, which the `else` branch prints.

### Error objects

A string is enough when a person reads the error. A program that handles errors must tell them apart, for example to retry after a timeout and stop after any other error. Comparing message text breaks when someone rewords the message. The error object can be any value, so a function can raise a table for the capturing code to read. The following loop retries a download that times out.

```lus
local function fetch_page(attempt)
    if attempt < 3 then
        error({ code = "timeout", retry_after = 2 })
    end
    return "<html>...</html>"
end

local page
for attempt = 1, 5 do
    local ok, result = catch fetch_page(attempt)
    if ok then
        page = result
        break
    elseif result.code == "timeout" then
        print(`attempt $attempt timed out, waiting $(result.retry_after) seconds`)
    else
        error(result)
    end
end
print(page)
--> attempt 1 timed out, waiting 2 seconds
--> attempt 2 timed out, waiting 2 seconds
--> <html>...</html>
```

The last branch raises every other error again, so a `catch` in a calling function receives the same table, unchanged, because `error` adds a position only to strings.

### Catch handlers

A program that raises tables still receives strings as error objects from the runtime and from the standard library, such as the JSON parse error in [Catching errors](#catching-errors). Code that reads `err.code` then needs a type check after every `catch`. A _catch handler_, written in brackets after `catch`, is a function that converts error objects in one place. When the expression raises an error, Lus calls the handler with the error object. The result of the handler replaces the error object that `catch` produces. The following handler converts every error object to a table with a `code` field.

```lus
local function as_table(err)
    if type(err) == "table" then
        return err
    end
    return { code = "internal", message = tostring(err) }
end

local ok, err = catch[as_table] fromjson("[1, 2")
print(ok, err.code)   --> false  internal
print(err.message)    --> JSON parse error at position 6: expected ']' after array element

local ok, err = catch[as_table] error({ code = "timeout" })
print(ok, err.code)   --> false  timeout
```

Every `catch[as_table]` produces an error object with a `code` field, whatever raised the error.

### The catch statement

The failure of some operations has no consequence for the program, such as removing a temporary file that may already be gone, closing a connection that the other side may have closed, or sending a usage statistic. A `catch` at the start of a statement evaluates its expression and discards the results along with any error. The following loop calls every listener of an event, even when one of them raises an error.

```lus
local listeners = {
    function(event) print("saved", event) end,
    function(event) error("listener failed") end,
    function(event) print("logged", event) end,
}

for _, listener in ipairs(listeners) do
    catch listener("upload")
end
--> saved  upload
--> logged  upload
```

The loop calls the third listener after the second one raises an error. The statement form keeps no record of the error, so use it only when the program has no use for the error.

### Warnings

A _warning_ reports a problem that lets the program continue, such as a deprecated setting or a slow response. [`warn`](/manual/api#warn) joins its arguments into one message and writes it to standard error with the prefix `Lus warning:`. The program then continues with the next statement.

Warnings are off when a program starts, so the users of a program see them only on request. The `-W` option of the `lus` command turns warnings on for one run. A program turns them on with `warn("@on")` and off with `warn("@off")`, as the following program does to report a deprecated option.

```lus
warn("@on")
warn("the option 'colour' is deprecated, use 'color'")
--> Lus warning: the option 'colour' is deprecated, use 'color'
warn("@off")
warn("this message is dropped")
```

## Do expressions

Some values take several statements to compute, because the computation needs an `if` with several cases, a loop, or a temporary variable. A _do expression_ is a `do ... end` block written where an expression is expected. A `provide` statement inside the block ends the block, with the value after `provide` as the value of the do expression.

A do expression keeps the computation of a value at the place where the value is used.

### Constants computed by statements

A [`<const>`](/manual/guide#constants) variable receives its value in its declaration. When the value depends on an `if` statement, a program usually declares the variable first and assigns it in a branch, so the variable cannot be `<const>`. The following code computes whether a program shows a progress bar. Any later statement can reassign `show_progress` by mistake.

```lus
local mode = "quiet"
local is_terminal = true

local show_progress
if mode == "quiet" then
    show_progress = false
elseif mode == "verbose" then
    show_progress = true
else
    show_progress = is_terminal
end
print(show_progress)   --> false
```

The [`and` and `or` choice](#logical-operators) gives a wrong result here, because one of the values is `false`. A do expression computes the value inside the declaration, so the variable can be `<const>`. Each `provide` ends the block, so the branches need no `else`.

```lus
local mode = "quiet"
local is_terminal = true

local show_progress <const> = do
    if mode == "quiet" then
        provide false
    end
    if mode == "verbose" then
        provide true
    end
    provide is_terminal
end
print(show_progress)   --> false
```

A do expression can also compute a constant with a loop, such as the following map from each column name of a CSV header to its position. The scope of the variable `index` ends with the block, so the rest of the program can only use `column`.

```lus
local header = { "name", "email", "city" }

local column <const> = do
    local index = {}
    for position, name in ipairs(header) do
        index[name] = position
    end
    provide index
end
print(column.email, column.city)   --> 2  3
```

### The first match in a loop

A search in a list stops at the first item that matches, which a `provide` inside a loop does by ending both the loop and the do expression. A do expression whose block ends without a `provide` produces `nil`, a suitable result for a search with no match. The following code searches a list of users for the first administrator and for a user named `guest`.

```lus
local users = {
    { name = "ada", admin = false },
    { name = "grace", admin = true },
    { name = "linus", admin = true },
}

local admin = do
    for _, user in ipairs(users) do
        if user.admin then
            provide user
        end
    end
end
print(admin.name)   --> grace

local guest = do
    for _, user in ipairs(users) do
        if user.name == "guest" then
            provide user
        end
    end
end
print(guest)   --> nil
```

The same search with a plain loop needs a variable declared before the loop, an assignment inside the loop, and a `break`. The do expression needs one declaration.

### Several statements under one catch

`catch` applies to one expression, which is enough when the code that can raise an error is one call, as in `catch fromjson(text)`. Often several statements can raise an error that the program handles in the same way. Loading settings, for example, takes three steps that can each raise an error: parsing the text, checking the type of one field, and reading another field. With `catch f()`, the program would need a new function that holds the three steps and is called once.

`catch do ... end` captures an error from any statement in the block. When the block succeeds, `catch` produces `true` followed by the values that `provide` lists. The following function loads a port and a host count from JSON text.

```lus
local function load_settings(text)
    local ok, port, host_count = catch do
        local settings = fromjson(text)
        if math.type(settings.port) ~= "integer" then
            error("port must be an integer", 0)
        end
        provide settings.port, #settings.hosts
    end
    print(ok, port, host_count)
end

load_settings('{"port": 8080, "hosts": ["a", "b"]}')   --> true  8080  2
load_settings('{"port": "eighty", "hosts": []}')       --> false  port must be an integer  nil
load_settings('{"port": ')
--> false  JSON parse error at position 10: unexpected end of input  nil
```

The first call succeeds. The second fails the type check, because `math.type` returns `"integer"` only for a number whose subtype is integer. The same `catch` also captures the error that `fromjson` raises in the third call. The statements in the block use the parameter `text` directly, which a separate function would need as an argument.

### Fields in table constructors

The value of a field in a table constructor can be a do expression, which puts the statements that compute the field inside the constructor. In the following constructor, the field `missing` is the first item of an order that is out of stock.

```lus
local stock = { tea = 10, mug = 0, spoon = 4 }
local orders = {
    { id = 1, items = { "tea", "spoon" } },
    { id = 2, items = { "tea", "mug", "spoon" } },
}

local invoices = {}
for _, order in ipairs(orders) do
    table.insert(invoices, {
        id = order.id,
        count = #order.items,
        missing = do
            for _, item in ipairs(order.items) do
                if stock[item] == 0 then
                    provide item
                end
            end
        end,
    })
end

for _, invoice in ipairs(invoices) do
    print(invoice.id, invoice.count, invoice.missing)
end
--> 1  2  nil
--> 2  3  mug
```

A do expression is allowed wherever an expression is allowed, for example as a function argument.

A `provide` ends the innermost do expression that contains it. A `provide` outside a do expression is a compile error, as is a statement after a `provide` in the same block, because that statement can never run.

## Metatables and objects

A table supports a few operations by default: reading and writing fields, measuring its length, and testing whether two variables refer to the same table. A _metatable_ is a table that defines more operations for another table. It can give a missing field a default, define `a + b` for two points, give `print` a readable text, or release a resource at the end of a block. Each operation is defined by one field of the metatable, whose reserved name starts with two underscores, such as `__index` or `__add`. These fields are called _metamethods_.

[`setmetatable`](/manual/api#setmetatable) attaches a metatable to a table and returns the table. [`getmetatable`](/manual/api#getmetatable) returns the metatable of a value. Several tables that share one metatable behave in the same way.

### Defaults and shared methods

A read of a missing field produces `nil` unless the metatable has an `__index` metamethod. Lus then reads the missing field from the table that `__index` holds, so that table provides default values. The following pen takes its `color` from a table of defaults.

```lus
local defaults = { color = "black", width = 1 }

local pen = setmetatable({ width = 3 }, { __index = defaults })
print(pen.width)   --> 3
print(pen.color)   --> black
```

`pen` has its own `width` but no `color`, so Lus reads `color` from `defaults`. The assignment `pen.color = "red"` stores the field in `pen` and leaves `defaults` unchanged.

`__index` can also be a function, which Lus calls with the table and the missing key to produce the result of the read. The following code counts words in a table where a missing entry reads as `0`, so the loop needs no special case for the first occurrence of a word.

```lus
local counts = setmetatable({}, {
    __index = function(t, key)
        return 0
    end,
})

for _, word in ipairs({ "pear", "fig", "pear" }) do
    counts[word] = counts[word] + 1
end
print(counts.pear, counts.fig, counts.plum)   --> 2  1  0
```

`__index` also lets many tables share their functions. A [method call](/manual/guide#methods) such as `stack:push(1)` reads the field `push` from `stack`. With `__index`, every stack reads `push` from one common table and stores only its own data. A table that combines its own data with shared methods is called an _object_.

```lus
local Stack = {}
Stack.__index = Stack

function Stack.new()
    return setmetatable({ items = {} }, Stack)
end

function Stack:push(value)
    table.insert(self.items, value)
end

function Stack:pop()
    return table.remove(self.items)
end

local stack = Stack.new()
stack:push("a")
stack:push("b")
print(stack:pop(), #stack.items)   --> b  1
```

`Stack` is the metatable of every stack. Its `__index` field holds `Stack` itself, so Lus reads missing fields from `Stack`. The `__newindex` metamethod is the equivalent for writes: when a program assigns to a field that the table does not have, Lus calls `__newindex` with the table, the key, and the value.

### Operator metamethods

An arithmetic operator applied to a table raises an error unless a metatable defines the operation. With operator metamethods, points, amounts of money, or durations use the same notation as numbers. Each arithmetic operator has a metamethod, which receives the two operands and returns the result. The metamethods are `__add` for `+`, `__sub` for `-`, `__mul` for `*`, `__div` for `/`, `__mod` for `%`, `__pow` for `^`, `__idiv` for `//`, and `__unm` for the negation `-x`. `__concat` defines `..` and `__len` defines `#`. The following code defines addition, multiplication by a number, and negation for points.

```lus
local Point = {}
Point.__index = Point

local function point(x, y)
    return setmetatable({ x = x, y = y }, Point)
end

function Point.__add(a, b)
    return point(a.x + b.x, a.y + b.y)
end

function Point.__mul(a, b)
    if type(a) == "number" then
        return point(a * b.x, a * b.y)
    end
    return point(a.x * b, a.y * b)
end

function Point.__unm(a)
    return point(-a.x, -a.y)
end

local sum = point(1, 2) + point(3, 4)
print(sum.x, sum.y)   --> 4  6

local scaled = 2 * point(1, 2)
print(scaled.x, scaled.y)   --> 2  4

local opposite = -point(1, 2)
print(opposite.x, opposite.y)   --> -1  -2
```

Lus calls the metamethod when either operand has it. `2 * p` and `p * 2` both call `Point.__mul`, so the function checks which operand is the number.

### Equality and ordering

By default, [two tables are equal only when they are the same table](#variables-refer-to-tables), so two points with the same coordinates are different. The `__eq` metamethod defines `==` for the tables that have it. `__lt` defines `<` and `__le` defines `<=`, which covers every ordering operator, because Lus evaluates `a > b` as `b < a` and `a >= b` as `b <= a`. The following code compares and sorts version numbers.

```lus
local Version = {}
Version.__index = Version

local function version(major, minor)
    return setmetatable({ major = major, minor = minor }, Version)
end

function Version.__eq(a, b)
    return a.major == b.major and a.minor == b.minor
end

function Version.__lt(a, b)
    if a.major ~= b.major then
        return a.major < b.major
    end
    return a.minor < b.minor
end

function Version.__le(a, b)
    return a == b or a < b
end

print(version(2, 0) == version(2, 0))   --> true
print(version(1, 9) < version(2, 0))    --> true
print(version(2, 1) >= version(2, 0))   --> true

local releases = { version(2, 0), version(1, 4), version(1, 10) }
table.sort(releases)
print(releases[1].minor, releases[2].minor, releases[3].minor)   --> 4  10  0
```

[`table.sort`](/manual/api#table.sort) compares elements with `<`, so it sorts a list of tables that have `__lt` without a comparison function. Lus calls `__eq` only when both operands are tables, so a version is never equal to a number or a string.

### String conversion

`print` shows a table as `table:` followed by an address, unless the table has a `__tostring` metamethod that returns a text describing it. [`tostring`](/manual/api#tostring), `print`, and strings in backticks call this metamethod. The following code prints a point as its coordinates.

```lus
local Point = {}
Point.__index = Point

function Point.__tostring(point)
    return `($(point.x), $(point.y))`
end

local origin = setmetatable({ x = 0, y = 0 }, Point)
print(origin)                  --> (0, 0)
print(`starting at $origin`)   --> starting at (0, 0)
```

### Callable tables

With the `__call` metamethod, a program can call a table like a function. Lus calls the metamethod with the table followed by the arguments of the call. A callable table is useful for an operation that has settings, because code that expects a function can call it. A [function with private local variables](#functions-that-keep-local-variables) hides its settings, while a callable table exposes them as fields that the program can read and change.

The following code checks names against a rule, which is called like a function and has its minimum length as a field that the program changes later.

```lus
local Rule = {}
Rule.__index = Rule

function Rule.__call(self, text)
    return #text >= self.min_length and not text:find("%s")
end

local function rule(min_length)
    return setmetatable({ min_length = min_length }, Rule)
end

local function count_valid(list, is_valid)
    local count = 0
    for _, item in ipairs(list) do
        if is_valid(item) then
            count = count + 1
        end
    end
    return count
end

local valid_name = rule(5)
local names = { "ada", "grace", "lin", "barbara" }
print(valid_name("grace"), valid_name("ada"))   --> true  false
print(count_valid(names, valid_name))           --> 2

valid_name.min_length = 3
print(count_valid(names, valid_name))           --> 4
```

Standard library functions that take a function, such as `table.filter`, raise an error for a callable table. Functions that the program defines, such as `count_valid`, accept one.

### Closing resources automatically

A program that opens a file, takes a lock, or starts a transaction must release the resource however the code that uses it ends: at its normal end, at an early `return`, at a `break`, or at an error. A release written by hand for each case is easy to forget.

The `<close>` attribute makes the release automatic. When the scope of a `<close>` variable ends for any reason, Lus calls the `__close` metamethod of its value. `io.open` returns a value that reads and writes the file and has a `__close` metamethod, so a file in a `<close>` variable is closed when its block ends, as [`io`](#io) shows.

A table with a `__close` metamethod is released in the same way. Lus calls `__close` with the value of the variable and a second argument, which is the error object if an error ends the block, or `nil` otherwise. The following transaction commits when its block ends normally and rolls back when an error ends it.

```lus
local log = {}

local function transaction()
    table.insert(log, "begin")
    return setmetatable({}, {
        __close = function(self, err)
            table.insert(log, err and "rollback" or "commit")
        end,
    })
end

do
    local tx <close> = transaction()
    table.insert(log, "insert row")
end

catch do
    local tx <close> = transaction()
    error("constraint failed")
end

print(table.concat(log, ", "))   --> begin, insert row, commit, begin, rollback
```

A `<close>` variable is also constant. When one block declares several `<close>` variables, Lus closes them in reverse order of declaration, so a resource is released before the resources that it depends on. The value of a `<close>` variable must have a `__close` metamethod or be `nil` or `false`. Lus skips a `nil` or `false` value, so a function that returns `nil` on failure can initialize a `<close>` variable directly.

### Classes

A _class_ describes a kind of object: the data that each object holds and the methods that all the objects share. In Lus, a class is a table that holds the methods and is the metatable of every object. A function of the class, usually named `new`, creates the objects. `Stack` in [Defaults and shared methods](#defaults-and-shared-methods) is a class. The following `Account` class also checks the arguments of `new`.

```lus
local Account = {}
Account.__index = Account

function Account.new(owner, balance)
    assert(balance >= 0, "the opening balance must not be negative")
    return setmetatable({ owner = owner, balance = balance }, Account)
end

function Account:deposit(amount)
    self.balance = self.balance + amount
end

function Account:describe()
    return `$(self.owner) has $(self.balance)`
end

local account = Account.new("Ada", 100)
account:deposit(50)
print(account:describe())   --> Ada has 150
```

Each call of `Account.new` returns a new table with its own `owner` and `balance`, while the methods exist once, in `Account`. `getmetatable(account) == Account` is true for every account, so a program can use this comparison to test whether a value is an account.

### Inheritance

A class _inherits_ from another class when its objects have the methods of the other class and add or replace some. Inheritance is built on `__index`. When the table that `__index` holds has a metatable with its own `__index`, Lus continues the read in that next table. A savings account is an account that also earns interest and has a different description, so the following `Savings` class inherits from `Account`.

```lus nocheck
local Savings = setmetatable({}, { __index = Account })
Savings.__index = Savings

function Savings.new(owner, balance, rate)
    local account = Account.new(owner, balance)
    account.rate = rate
    return setmetatable(account, Savings)
end

function Savings:add_interest()
    self:deposit(self.balance * self.rate // 100)
end

function Savings:describe()
    return Account.describe(self) .. ` at $(self.rate)%`
end

local savings = Savings.new("Grace", 1000, 5)
savings:add_interest()
print(savings:describe())   --> Grace has 1050 at 5%
```

For `savings.deposit`, Lus looks in the object first, then in `Savings`, then in `Account`, which has the method. For `savings.describe`, Lus finds the method in `Savings` first, so `Savings:describe` replaces the inherited method. The new method calls the original as `Account.describe(self)`, with the object as an explicit argument.

### Finalizers and weak tables

Lus frees a table when the program can no longer reach it. The metatable fields `__gc` and `__mode` change how Lus frees a table or what it holds, which few programs need.

The `__gc` metamethod is a _finalizer_, which Lus calls with the table some time after the table becomes unreachable. A finalizer releases a resource that the table owns, such as an open connection, if the program has not released it. The time of the call is unspecified, so a resource that must be released at a known point belongs in a [`<close>` variable](#closing-resources-automatically).

Lus keeps every key and value of a table in memory while the table is reachable, but a cache should hold a value only while another part of the program uses it. The `__mode` field makes the keys or the values of a table _weak_, so Lus frees a weak key or value when nothing else refers to it and removes its entry from the table. `__mode` is `"k"` for weak keys, `"v"` for weak values, or `"kv"` for both. The following example calls [`collectgarbage`](/manual/api#collectgarbage), which frees unreachable values immediately, so the cache loses the entry that only the cache refers to.

```lus
local cache = setmetatable({}, { __mode = "v" })

local report = { "kept" }
cache.kept = report
cache.dropped = { "temporary" }

collectgarbage()
print(cache.kept == report, cache.dropped)   --> true  nil
```

The variable `report` still refers to the first table, so its cache entry stays. Only the cache refers to the second table, so Lus frees it and removes its entry.

## Variable attributes

[`<const>`](#constants) and [`<close>`](#closing-resources-automatically) are built-in attributes. A program can also define its own attributes, which check or convert every value assigned to a variable. The `<group>` attribute declares several local variables under one name.

### Runtime attributes

A _runtime attribute_ is a function written in angle brackets after a variable name. Whenever a value is assigned to the variable, Lus calls the function with the name of the variable and the new value. The function can reject the value, replace it, or record it. The rule is written once, in the declaration, so the assignments need no extra code.

An attribute validates a value by raising an error when the value is invalid. The following attribute accepts only positive numbers and returns nothing for a valid value, so Lus stores the assigned value unchanged.

```lus
local function positive(name, value)
    if value <= 0 then
        error(`$name must be positive, got $value`, 0)
    end
end

local width <positive> = 80
width = 120
print(width)   --> 120

local ok, message = catch do
    width = -5
end
print(message)   --> width must be positive, got -5
print(width)     --> 120
```

When an attribute raises an error, the variable keeps its previous value, so `width` is still `120` at the end.

An attribute converts a value by returning the converted value, because any result other than `nil` replaces the assigned value. The following attribute removes the whitespace around every title.

```lus
local function trimmed(name, value)
    return value:trim()
end

local title <trimmed> = "   Annual report  "
print(`[$title]`)   --> [Annual report]

title = "\tDraft\n"
print(`[$title]`)   --> [Draft]
```

An attribute can also record every assignment. Because it receives the name of the variable, one function can report the changes of any variable. The following attribute prints each new value of a counter.

```lus
local function traced(name, value)
    print(`$name = $value`)
end

local retries <traced> = 0   --> retries = 0
retries = retries + 1        --> retries = 1
retries = retries + 1        --> retries = 2
```

### Function decorators

Functions are values, so an attribute can be applied to a variable that holds a function. An attribute that receives the function and returns another function to replace it is called a _decorator_. The replacement usually calls the original function and does some work before or after the call, as the following attribute `logged` does by printing a line for every call.

```lus
local function logged(name, fn)
    return function(...)
        print(`calling $name`)
        return fn(...)
    end
end

local greet <logged> = function(who)
    return `Hello, $who`
end

print(greet("Ada"))
--> calling greet
--> Hello, Ada
```

A decorator can add caching, timing, or a permission check to a function without a change to its body. The following attribute `memoized` stores the result for each argument, so the function computes each square once.

```lus
local function memoized(name, fn)
    local results = {}
    return function(n)
        if results[n] == nil then
            results[n] = fn(n)
        end
        return results[n]
    end
end

local computed = 0
local square <memoized> = function(n)
    computed = computed + 1
    return n * n
end

print(square(12), square(12), computed)   --> 144  144  1
```

### Parameterized attributes

The expression in the angle brackets can be any expression whose value can be called, including a call of a function that returns an attribute. The arguments of that call configure the attribute. The following function `only` takes a type name and returns an attribute that accepts only values of that type.

```lus
local function only(kind)
    return function(name, value)
        if type(value) ~= kind then
            error(`$name must be a $kind, got a $(type(value))`, 0)
        end
    end
end

local count <only "number"> = 0
local label <only "string"> = "total"

count = count + 1
local ok, message = catch do
    count = "three"
end
print(message)   --> count must be a number, got a string
print(count)     --> 1
```

`only "number"` is a call of `only` with one string argument, so it [omits the parentheses](#declaring-and-calling). Lus evaluates the expression once, when the variable is declared.

### Chained attributes

A variable can have several attributes, separated by commas, which Lus calls from left to right. Each attribute receives the value that the previous one produced. Lus stores the value that the last one produced. The following code combines `only` with `clamped`, an attribute that limits a number to a range.

```lus nocheck
local function clamped(low, high)
    return function(name, value)
        return math.max(low, math.min(high, value))
    end
end

local volume <only "number", clamped(0, 10)> = 5
volume = 42
print(volume)   --> 10
volume = -3
print(volume)   --> 0
```

`only "number"` comes first, so `clamped` only receives numbers, which `math.max` and `math.min` can compare. The call `clamped(0, 10)` has two arguments, so it keeps its parentheses.

### Rules for runtime attributes

Lus calls the attribute when the variable is initialized and at every assignment to it in the function that declares it. An assignment inside a nested function stores the value directly, without calling the attribute. An assignment of `nil` also stores `nil` directly, so an attribute never receives `nil`.

A result of `false` replaces the assigned value, as any result other than `nil` does.

A runtime attribute is allowed in a `local` statement that declares one variable. `<const>` and `<close>` can appear in the same list. They must come first, as in `local limit <const, only "number"> = 10`.

### Local groups

A table keeps related values under one name, such as the `x` and `y` of a position. Creating a table allocates memory, which Lus frees later. This cost is negligible in most code but becomes significant in a function that runs millions of times and creates a small table on each call.

A _local group_ is a set of local variables under one name. The `<group>` attribute declares a group from a table constructor that lists the fields, which a program reads and writes with the same `name.field` syntax as the fields of a table. Each field is a local variable, so Lus creates no table.

Separate local variables such as `sum_x` and `sum_y` also avoid the table, but their names no longer show that the values belong together. A group keeps the `sum.x` notation, so adding `<group>` to the declaration of a table turns the table into a group without a change to the code that uses the fields. The following function computes the center of a list of points. Without `<group>`, it would create a table on every call.

```lus
local function centroid(points)
    local sum <group> = { x = 0, y = 0 }
    for _, point in ipairs(points) do
        sum.x = sum.x + point.x
        sum.y = sum.y + point.y
    end
    return sum.x / #points, sum.y / #points
end

print(centroid({ { x = 0, y = 0 }, { x = 4, y = 2 }, { x = 2, y = 4 } }))   --> 2.0  2.0
```

The value of a field can be any expression. The following group computes the longest word of a list with a [do expression](#do-expressions).

```lus
local words = { "pear", "fig", "banana" }

local summary <group> = {
    count = #words,
    longest = do
        local best = ""
        for _, word in ipairs(words) do
            if #word > #best then
                best = word
            end
        end
        provide best
    end,
}
print(summary.count, summary.longest)   --> 3  banana
```

An assignment of a table constructor to a group sets the fields that the constructor lists and leaves the other fields unchanged. The following assignment resets two of three statistics.

```lus
local stats <group> = { count = 4, sum = 22, max = 9 }

stats = { count = 0, sum = 0 }
print(stats.count, stats.sum, stats.max)   --> 0  0  9
```

An assignment of one group to another copies each field to the field of the same name and leaves the other fields of the target unchanged. Every field of the source group must also be a field of the target group. The following assignment moves a position back to its start.

```lus
local start <group> = { x = 0, y = 0 }
local pos <group> = { x = 5, y = 7 }

pos = start
print(pos.x, pos.y)   --> 0  0
```

A group can also initialize a new group. `local backup <group> = stats` declares `backup` with the same fields and the current values of `stats`.

A field with the `<const>` attribute cannot be reassigned. A field with the `<group>` attribute is a nested group with its own fields. The following group describes a moving body, whose values would need five names such as `body_position_x` as separate local variables.

```lus
local body <group> = {
    mass <const> = 2,
    position <group> = { x = 0, y = 0 },
    velocity <group> = { x = 1, y = 3 },
}

for step = 1, 3 do
    body.position.x = body.position.x + body.velocity.x
    body.position.y = body.position.y + body.velocity.y
end
print(body.position.x, body.position.y)   --> 3  9
```

A group differs from a table in the following ways.

- The declaration fixes the fields. A read or write of any other field, such as `stats.average`, is a compile error.
- A group is a set of variables, so it cannot be passed to a function, returned, or stored in a table. `print(stats)` is a compile error. A program passes or returns the fields, as `centroid` does in its `return`.
- A group is always local, so a global declared with `<group>` is an error.

A table is the right choice when the values must leave the function, when fields are added later, or when the program iterates over the fields.

## Enums

Programs often need a value that is one of a few fixed choices, such as a log level, the state of a connection, or a direction. Strings and numbers can represent the choices, but both have drawbacks. A misspelled string such as `"warnning"` is still a string, so Lus reports no error. A number such as `2` has no meaning for the reader and is equal to every other `2` in the program. An _enum_ is a fixed set of named values that differ from every string, every number, and the values of every other enum.

### Declaring an enum

An `enum ... end` expression creates an enum from the names of its _members_, separated by commas. A program stores the enum in a variable and reads each member as a field, as with the following enum of log levels.

```lus
local Level = enum debug, info, warning, error end

local current = Level.warning
print(type(current))             --> enum
print(current == Level.warning)  --> true
print(current == "warning")      --> false
print(current == 3)              --> false
```

A member is equal only to itself. A name that the enum does not list, such as `Level.fatal`, reads as `nil`.

### Ordering

The members of an enum are ordered by their position in the `enum` expression, so `<`, `>`, `<=`, and `>=` compare two members of the same enum. The following function prints a message only when its level is at least the threshold.

```lus nocheck
local threshold = Level.warning

local function log(level, message)
    if level >= threshold then
        print(message)
    end
end

log(Level.info, "cache warmed")
log(Level.error, "disk full")   --> disk full
```

An ordering comparison between members of two different enums raises an error, while `==` between them is always `false`, even when the members have the same name.

```lus nocheck
local Mode = enum debug, release end

print(Level.debug == Mode.debug)   --> false
local ok = catch Level.debug < Mode.release
print(ok)                          --> false
```

### Enums as table keys

A member can be a table key, which lets a table hold data for each choice. `print` and `tostring` show a member as `enum:` followed by an address, so a program prints a member by reading its name from such a table.

```lus nocheck
local names = {
    [Level.debug] = "DEBUG",
    [Level.info] = "INFO",
    [Level.warning] = "WARN",
    [Level.error] = "ERROR",
}

local function log(level, message)
    print(`[$(names[level])] $message`)
end

log(Level.warning, "disk almost full")   --> [WARN] disk almost full
```

### Positions

[`tonumber`](/manual/api#tonumber) returns the position of a member in its enum, counting the first member as 1. Indexing the enum with a position produces the member at that position. A program uses the two conversions to store a member in a file or a database as a number and to read it back.

```lus nocheck
local stored = tonumber(Level.warning)
print(stored)   --> 3

local restored = Level[stored]
print(restored == Level.warning)   --> true
```

## Permissions

A _permission_ is the right to perform one kind of operation outside the program, such as reading files. A Lus script starts with no permissions, so it cannot read or write files, open network connections, run other programs, or read environment variables until it requests them with the function [`pledge`](/manual/api#pledge).

This default limits the damage that a mistake or a third-party module can cause. In a script that pledges to read `./data` and then [seals](#rejecting-and-sealing) its permissions, a wrong path cannot delete a home directory. A module that the script loads cannot open a network connection either. A search for `pledge` finds every kind of access the program has. The person who runs a script can also limit its permissions from the command line.

### Requesting permissions with `pledge`

An operation raises an error when the program does not hold the permission it needs. The following script, saved as `report.lus`, calls `io.open` to open a file without the permission to read it.

```lus nocheck
local file <close> = io.open("sales.csv")
```

The error names the missing permission and the file.

```text
lus: report.lus:1: permission "fs:read" denied for 'sales.csv'
```

`pledge` takes one or more permission names and returns one boolean for each name: `true` if the permission was granted and `false` if it was refused. A script run as `lus script.lus` is granted every permission it requests. A request is refused when the command line set a narrower limit or when the program has [sealed](#rejecting-and-sealing) its permissions.

A program may call `pledge` at any point. Many scripts pledge everything they need on their first lines, where a reader sees it first, but a program may also request a permission at the moment a feature needs it. The following program checks for updates only if it may use HTTP.

```lus
if pledge("network:http") then
    print("checking for updates")
else
    print("skipping the update check")
end
--> checking for updates
```

### Permission names

A permission name starts with a group, such as `fs` for the filesystem. Most names continue with a colon and a part that selects one kind of operation in the group. The group name alone grants every operation in the group, so `pledge("fs")` allows both reading and writing.

| Permission | What it allows |
| --- | --- |
| `fs:read` | Reading files, listing directories, and inspecting paths. |
| `fs:write` | Creating, changing, moving, and removing files and directories. |
| `network:http` | HTTP and HTTPS requests with `network.fetch`. |
| `network:tcp` | Opening TCP connections and listening for them. |
| `network:udp` | Sending and receiving UDP datagrams. |
| `network:server` | Serving HTTP with `network.serve`, together with `network:tcp`. |
| `exec` | Running other programs with `os.execute` and `io.popen`. |
| `env` | Reading environment variables with `os.getenv` and setting them with `os.setenv`. `env:read` and `env:write` allow one of the two. |
| `load` | Running code that the program loads while it runs, with `load`, `require` of a file, or a worker. |

Some operations need two permissions: loading a module file or starting a worker needs `load` to run the code and `fs:read` to read the file.

### Narrowing a permission

A program rarely needs the whole filesystem or the whole network. A value after `=` narrows a permission to the paths, hosts, or names that match the value, where `*` matches any run of characters. The following script may read only the files in `./data` and its subdirectories. It reads the first line of a sales file with `file:read("l")`, then fails to open a file outside `./data`.

```lus nocheck
pledge("fs:read=./data/*")

local file <close> = io.open("data/sales.csv")
print(file:read("l"))                    --> region,amount
print((catch io.open("secrets.txt")))    --> false
```

A filesystem value is an absolute path or a path that starts with `.`, which is relative to the working directory. A network value names a host, with an optional port and path, as in `network:http=api.example.com/*` or `network:tcp=127.0.0.1:*`. An `env` value names a variable. The following script may read only `EDITOR` with `os.getenv`, so it cannot read the credentials that other variables hold.

```lus
pledge("env=EDITOR")

print((catch os.getenv("EDITOR")))                  --> true
print((catch os.getenv("AWS_SECRET_ACCESS_KEY")))   --> false
```

Several pledges of the same permission with different values add up, so an operation is allowed when any of the values matches.

### Rejecting and sealing

A program can also give up permissions, which is most useful before it handles input it does not trust. A name with the prefix `~` _rejects_ a permission for the rest of the program. After that, every operation that needs the permission fails. Even a `pledge` of it raises an error. Any module may call `pledge`, so the main program rejects a permission to guarantee that no module acquires it later. The following program rejects `exec`, so its call to `os.execute`, which runs another program, fails.

```lus
pledge("fs:read", "exec")
pledge("~exec")

local ran = catch os.execute("ls")
print(ran and "listed the files" or "running programs is forbidden")
--> running programs is forbidden

local granted = catch pledge("exec")
print(granted and "granted" or "refused for good")   --> refused for good
```

After `pledge("seal")`, the set of permissions cannot change. Every later `pledge` returns `false`, so the program keeps exactly the permissions it held when it sealed. A server typically pledges the permissions it needs and seals before it accepts its first connection.

```lus
pledge("fs:read", "network:tcp", "seal")

print(pledge("exec"))       --> false
print(pledge("fs:write"))   --> false
```

### Granting from the command line

The `-P` option of `lus` grants a permission before the script starts. It may appear several times and takes the same names as `pledge`, including values and the `~` prefix.

```bash
lus -Pnetwork:http -Pfs:read=./report.lus -Pfs:read=./data/* report.lus
```

When the command line grants at least one permission, those grants are the limit for the whole run. A `pledge` in the script succeeds for a permission that the command line granted and returns `false` for any other. A person can therefore run a script they did not write without reading all of it first. A filesystem grant on the command line must cover the script file itself, which is why the example command grants `fs:read=./report.lus`.

A command line that only rejects, such as `lus -P~exec script.lus`, sets no limit. The script may pledge anything except the rejected permissions.

[Permissions](/manual/permissions) lists every permission, the functions that check it, and the matching rules for paths and hosts.

## Coroutines

A _coroutine_ is a function that can pause partway and continue later from the same place, with its local variables unchanged. An ordinary function runs from its first line to a `return` before its caller continues. A coroutine can stop at any point to return control to its caller, then continue from that point when the caller resumes it.

Coroutines have the following uses in Lus:

- A [generator](#generators) is a coroutine that produces a sequence of values one at a time.
- A coroutine can hold a task that needs input at several points, such as a conversation, keeping its place between inputs.
- A [detached coroutine](#detached-coroutines) lets one program wait for many things at once, such as many network connections.

### Creating and resuming

[`coroutine.create`](/manual/api#coroutine.create) takes a function and returns a coroutine that has not started. [`coroutine.resume`](/manual/api#coroutine.resume) runs the coroutine until it pauses or ends. Inside the coroutine, [`coroutine.yield`](/manual/api#coroutine.yield) pauses it and returns control to the code that called `resume`.

Values pass in both directions. `resume` returns `true` followed by the arguments of `yield`. The extra arguments of the next `resume` become the results of that `yield`. The following coroutine registers a user by asking two questions, whose answers may come from a keyboard, a web form, or a chat message. The coroutine keeps its place between the answers.

```lus
local signup = coroutine.create(function()
    local name = coroutine.yield("What is your name?")
    local email = coroutine.yield(`Hello $name. What is your email address?`)
    return `Registered $name <$email>`
end)

print(coroutine.resume(signup))
--> true  What is your name?
print(coroutine.resume(signup, "Ada"))
--> true  Hello Ada. What is your email address?
print(coroutine.resume(signup, "ada@example.com"))
--> true  Registered Ada <ada@example.com>
```

The first `resume` starts the function and passes its extra arguments as the parameters of the function. When the function returns, `resume` returns `true` followed by the return values, after which the coroutine is finished. Without a coroutine, a program would store the current step and the earlier answers in a table that it checks on each input. The coroutine keeps the answers in local variables and the current step in its paused position.

When an error ends a coroutine, `resume` returns `false` and the error object, so the caller receives the error as a value. Resuming a finished coroutine also returns `false`.

```lus
local task = coroutine.create(function()
    error("out of paper", 0)
end)

print(coroutine.resume(task))   --> false  out of paper
print(coroutine.resume(task))   --> false  cannot resume dead coroutine
```

### Generators

Walking a tree is easy with a recursive function but hard with an iterator function, which returns one item per call and has to store its position in the tree between calls.

[`coroutine.wrap`](/manual/api#coroutine.wrap) turns the recursive function into an [iterator](#writing-an-iterator-with-a-function) called a _generator_. Inside the function, `coroutine.yield` passes one value to the `for` loop and pauses the function until the next pass of the loop continues it from that point. The loop ends when the function returns.

The following program lists the files of a folder tree. Its `walk` function is an ordinary recursive traversal that yields each file path it reaches.

```lus
local tree = {
    name = "project",
    children = {
        { name = "README.md" },
        { name = "src", children = {
            { name = "main.lus" },
            { name = "util.lus" },
        } },
    },
}

local function walk(node, prefix)
    local path = prefix .. node.name
    if node.children then
        for _, child in ipairs(node.children) do
            walk(child, path .. "/")
        end
    else
        coroutine.yield(path)
    end
end

local function files(root)
    return coroutine.wrap(function()
        walk(root, "")
    end)
end

for path in files(tree) do
    print(path)
end
--> project/README.md
--> project/src/main.lus
--> project/src/util.lus
```

### Status and closing

[`coroutine.status`](/manual/api#coroutine.status) returns the state of a coroutine as a string. A coroutine is `"suspended"` before it starts and while it is paused, `"running"` while its code runs, `"normal"` while it waits for another coroutine that it resumed, and `"dead"` once it has returned or failed.

[`coroutine.close`](/manual/api#coroutine.close) ends a suspended coroutine that the program no longer needs and closes its [`<close>` variables](#closing-resources-automatically), which releases the files or connections they hold. The following counter never returns, so the program closes it after it has taken one number.

```lus
local counter = coroutine.create(function()
    local n = 0
    while true do
        n = n + 1
        coroutine.yield(n)
    end
end)

print(coroutine.resume(counter))   --> true  1
print(coroutine.status(counter))   --> suspended
print(coroutine.close(counter))    --> true
print(coroutine.status(counter))   --> dead
```

### Detached coroutines

Many programs spend most of their time waiting, such as a chat server whose thousand connections each send a line every few minutes, or a script that requests data from several services that each take a second to answer. Sequential code waits for one thing at a time, so while it waits for a line from the first connection, every other connection gets no answer.

A _detached coroutine_ is a coroutine that the runtime resumes by itself. [`coroutine.detach`](/manual/api#coroutine.detach) starts one. When a detached coroutine reaches an operation that waits, such as reading from a network connection, the runtime pauses that coroutine and runs the others until its data has arrived. A program therefore creates one detached coroutine for each connection or request, each written as sequential code.

The following program is a server that answers price requests on port 7000. A client sends the name of an item on each line and receives the price of that item in reply. The function `serve` handles one connection from start to end.

```lus nocheck
pledge("network:tcp")

local prices = { apple = 3, pear = 5 }

local function serve(conn)
    local closing <close> = conn
    while true do
        local item = vector.tostring(conn:receive("*l", 1024))
        if item == "" then
            break
        end
        conn:send(`$(prices[item] or "unknown")\n`)
    end
end

local server = network.tcp.bind("127.0.0.1", 7000)
while true do
    coroutine.detach(coroutine.create(serve), server:accept())
end
```

The program uses these operations:

- `network.tcp.bind` opens a socket that listens on a port.
- `server:accept()` waits for the next client and returns its connection.
- `conn:receive("*l", 1024)` reads one line of at most 1024 bytes, a limit that protects the memory of the server from a client that never sends a line break. It returns a [vector](#vector) of bytes, which `vector.tostring` converts to a string. At the end of a connection, it returns an empty vector.
- `conn:send` writes text to the client.

The `<close>` variable `closing` closes the connection when `serve` returns. The `pledge` call requests the network [permission](#permissions) that the program needs.

`coroutine.detach(co, ...)` passes its extra arguments, here the new connection, to the function of the coroutine, then returns the coroutine at once. A client that stays silent for an hour pauses only its own coroutine, inside `receive`. Meanwhile the server keeps accepting new clients in its last loop and answers every other connection as its lines arrive.

Clients benefit in the same way. The following program requests three prices from that server at the same time, each on its own connection, which `network.tcp.connect` opens.

```lus nocheck
pledge("network:tcp")

local function lookup(item)
    local conn <close> = network.tcp.connect("127.0.0.1", 7000)
    conn:send(item .. "\n")
    local price = tonumber(vector.tostring(conn:receive("*l", 1024)))
    if not price then
        error(`no price for $item`, 0)
    end
    return price
end

local tasks = {}
for i, item in ipairs({ "apple", "kiwi", "pear" }) do
    tasks[i] = coroutine.detach(coroutine.create(lookup), item)
end
for _, task in ipairs(tasks) do
    print(coroutine.resume(task))
end
--> true  3
--> false  no price for kiwi
--> true  5
```

The first loop starts the three lookups, which wait for their answers at the same time. The second loop collects the result of each one.

### Results, errors, and cancellation

`coroutine.resume` on a detached coroutine waits until that coroutine has ended, then returns `true` and the return values, or `false` and the error object. This is how the price client collects one result or one error per lookup. While `resume` waits, the runtime keeps running every detached coroutine, so all three lookups make progress during the second loop.

A detached coroutine that ends before the program resumes it keeps its results or its error until the first `resume`. If the program never collects the error of a detached coroutine, `lus` reports the error and exits with status 1.

```lus nocheck
coroutine.detach(coroutine.create(function()
    error("lost")
end))
print("main program done")
--> main program done
--> lus: script.lus:2: lost
```

`coroutine.close` cancels a detached coroutine: the runtime stops resuming it and closes its `<close>` variables, so a cancelled task releases its connection. A server that accepts clients in a detached coroutine closes that coroutine to shut down.

When the top-level code of a script ends, `lus` keeps running the detached coroutines until all of them have ended, so a script may start its tasks and end while the tasks run to completion. The following script reaches its last line before its task prints the first tick.

```lus
coroutine.detach(coroutine.create(function()
    for i = 1, 3 do
        print("tick", i)
        coroutine.yield()
    end
end))
print("the script has reached its last line")
--> the script has reached its last line
--> tick  1
--> tick  2
--> tick  3
```

Inside a detached coroutine, `coroutine.yield()` pauses the coroutine until the other detached coroutines have run. A task with a long computation calls it from time to time so that the other tasks stay responsive.

Detached coroutines run one at a time. The runtime switches between them only where one waits, yields, or ends, never in the code between, so detached coroutines read and change the same tables without locks.

### Workers

Detached coroutines share one processor core, which is enough for tasks that mostly wait. A computation never waits, so a program that resizes images or searches a large data set gains nothing from detached coroutines. A _worker_ is a second copy of the Lus interpreter that runs a script on its own thread, in parallel with the program that created it. Several workers compute at the same time, each on its own core.

[`worker.create(path, ...)`](/manual/api#worker.create) starts a worker that runs the script file at `path`, which receives the extra arguments as the values of `...`. The worker sends results with [`worker.message`](/manual/api#worker.message). The creator reads them with [`worker.receive`](/manual/api#worker.receive), which waits for the next message of that worker.

The following program counts the prime numbers below one million on four workers, each of which checks a quarter of the range. The worker script is the file `primes.lus`.

```lus nocheck
-- primes.lus
local first, last = ...
local count = 0
for n = first, last do
    local prime = n > 1
    for d = 2, math.floor(math.sqrt(n)) do
        if n % d == 0 then
            prime = false
            break
        end
    end
    if prime then
        count = count + 1
    end
end
worker.message(count)
```

The main program starts the four workers and adds up their counts. Starting a worker reads and runs a script file, so it needs the `load` and `fs:read` permissions.

```lus nocheck
pledge("load", "fs:read")

local workers = {}
for i = 1, 4 do
    workers[i] = worker.create("primes.lus", (i - 1) * 250000 + 1, i * 250000)
end

local total = 0
for _, handle in ipairs(workers) do
    total = total + worker.receive(handle)
end
print(total)   --> 78498
```

All four workers are running before the first `worker.receive`, so the loop that adds the counts takes only as long as the slowest worker.

### Messages between workers

A worker has its own global variables and its own memory. It shares no variable with its creator, so the two can run at the same time safely. They communicate only by messages, each of which is a copy of the value that was sent.

Messages pass in both directions. The creator sends a value with [`worker.send(handle, value)`](/manual/api#worker.send). The worker waits for it with [`worker.peek()`](/manual/api#worker.peek), then replies with `worker.message(value)`, which the creator reads with `worker.receive(handle)`. A worker that handles one request after another is a loop around `worker.peek`. The following worker, saved as `count_words.lus`, counts the words of each text it receives.

```lus nocheck
-- count_words.lus
while true do
    local job = worker.peek()
    local words = 0
    for _ in job.text:gmatch("%S+") do
        words = words + 1
    end
    worker.message({ id = job.id, words = words })
end
```

The following program sends it two jobs and reads the two replies.

```lus nocheck
pledge("load", "fs:read")

local counter = worker.create("count_words.lus")
worker.send(counter, { id = 1, text = "the quick brown fox" })
worker.send(counter, { id = 2, text = "jumps over the lazy dog" })
for i = 1, 2 do
    local reply = worker.receive(counter)
    print(reply.id, reply.words)
end
--> 1  4
--> 2  5
```

A worker that is waiting in `worker.peek` when the program ends stops with the program, so this worker needs no message that tells it to quit.

A message may be `nil`, a boolean, a number, a string, a table of such values, or a vector. Sending a function or a coroutine raises an error. When an error ends the script of a worker, the next `worker.receive` on that worker raises the error in the creator, where a [`catch`](#errors) captures it like any other error. Once a worker has finished and its messages have been read, `worker.receive` returns `nil`.

### Choosing between detached coroutines and workers

A task that mostly waits belongs in a detached coroutine. A task that mostly computes belongs in a worker.

| | Detached coroutine | Worker |
| --- | --- | --- |
| Use it for | Waiting on many things at once: connections, requests, replies | Computing on several processor cores |
| Runs | One at a time, in the thread of the program | In parallel, on a thread of its own |
| Data | Shares the variables and tables of the program | Has its own globals and exchanges copies as messages |
| Starts from | A function | A script file |
| Cost of each | Small, so a program may run thousands | A whole interpreter, so about one per core is useful |

A program can use both. `worker.receive` pauses a detached coroutine while it waits, so a server that handles each connection in a detached coroutine may pass a heavy computation to a worker. The server keeps answering other connections while that coroutine waits for the result.

[`network.fetch`](/manual/api#network.fetch) behaves differently from the other network operations. Called from the top-level code of a script, it lets the detached coroutines run while it waits, but called inside a detached coroutine, it blocks every other coroutine until its response arrives. In both cases it waits for one response at a time, so a program that sends several HTTP requests at the same time calls `fetch` from one worker per request.

[Coroutines and workers](/manual/concurrency) lists every operation that pauses a detached coroutine, the timeouts, and the rules for values that cross between workers.

### Permissions of coroutines and workers

A coroutine starts with a copy of the permissions of the code that created it, so later changes on either side stay on that side. A function can run a piece of code with fewer permissions by rejecting them inside a coroutine, as [Running code with its own environment](#running-code-with-its-own-environment) shows. A worker starts with a sealed copy of the permissions of its creator.

## Queries

A program often holds a list of records, such as the rows of a CSV file or the products of a catalog. It needs answers from that list: the records that match a condition, the records in sorted order, or a total for each category. Written by hand, such an answer needs a loop with an `if`, a call to `table.sort` with a comparison function, or a table of running totals. A _query_ describes the result in a few clauses and leaves the filtering, sorting, and totaling to Lus. The same query also runs on a table of a SQLite database.

The following program finds the two longest science fiction books in the list `books`. Every later query example in this chapter starts from this list as it is written here.

```lus
local books = {
    { title = "Dune", author = "Herbert", genre = "scifi", pages = 600, rating = 5 },
    { title = "Emma", author = "Austen", genre = "novel", pages = 450 },
    { title = "Neuromancer", author = "Gibson", genre = "scifi", pages = 270, rating = 4 },
    { title = "Persuasion", author = "Austen", genre = "novel", pages = 250, rating = 3 },
    { title = "Solaris", author = "Lem", genre = "scifi", pages = 210 },
}

for book in query(@books where books.genre == "scifi" order by books.pages desc limit 2) do
    print(book.title, book.pages)
end
--> Dune  600
--> Neuromancer  270
```

The query reads `books`, keeps the entries whose genre is `"scifi"`, sorts them from the most pages to the fewest, and stops after two.

### Sources and rows

A query starts with `@` followed by the list it reads, which is the _source_ of the query. A source is a list of [records](#records), each of which is one _row_. The function [`query`](/manual/api#query) runs a query in a `for` loop, in the same position as `pairs`. The loop variable receives one result per pass. A query that consists of a source alone yields every row in the order of the list.

Inside a query, the _row variable_ is the row that the query is examining. It has the name of the source, so in a query on `books` the expression `books.pages` reads the `pages` field of the current row. The word `as` gives the row variable another name, which shortens long queries.

```lus nocheck
for book in query(@books as b where b.pages > 500) do
    print(book.title)   --> Dune
end
```

The row variable `b` exists only inside the query. The loop variable `book` is an ordinary local variable that holds each result.

### Filtering with `where`

The `where` clause holds a condition that the query evaluates once for each row, keeping the rows for which it is truthy. The condition is an ordinary expression that may contain comparisons, `and`, `or`, `not`, arithmetic, and calls to functions and methods. A row with a missing field follows the rules of [`nil` in queries](#nil-in-queries). The following query finds the novels and the books whose title starts with S.

```lus nocheck
for book in query(@books as b where b.genre == "novel" or b.title:sub(1, 1) == "S") do
    print(book.title)
end
--> Emma
--> Persuasion
--> Solaris
```

### Choosing fields with `select`

A query without a `select` clause yields the records of the source. With a `select` clause, the query builds for each row a new record that holds only the listed values. A value written as a field of the row, such as `b.title`, keeps the name of that field, while any other expression gets its name from `as`. The following query computes how many days each long book takes to read.

```lus nocheck
-- How many days each long book takes at 30 pages a day.
for row in query(@books as b where b.pages > 400 select b.title, b.pages // 30 as days) do
    print(row.title, row.days, row.author)
end
--> Dune  20  nil
--> Emma  15  nil
```

Each result has only the fields `title` and `days`, so `row.author` is `nil`.

### Sorting with `order by`

The `order by` clause sorts the results by one or more expressions. `asc` after an expression sorts in ascending order, which is the default. `desc` sorts in descending order. Rows that are equal on the first expression are sorted by the second, then by the third. The following query sorts by author, putting the longer book first among the books of one author.

```lus nocheck
for book in query(@books as b order by b.author, b.pages desc) do
    print(book.author, book.title)
end
--> Austen  Emma
--> Austen  Persuasion
--> Gibson  Neuromancer
--> Herbert  Dune
--> Lem  Solaris
```

### Taking part of the result with `limit` and `offset`

Together, `limit n` and `offset n` divide a sorted result into pages: `offset n` skips the first `n` rows, then `limit n` ends the result after `n` more. The following query yields the second page of a listing with two books per page.

```lus nocheck
for book in query(@books as b order by b.title limit 2 offset 2) do
    print(book.title)
end
--> Neuromancer
--> Persuasion
```

### Removing duplicates with `distinct`

`select distinct` yields each different record once. The list holds two books by Austen, but the following query yields her name once.

```lus nocheck
for row in query(@books as b select distinct b.author order by b.author) do
    print(row.author)
end
--> Austen
--> Gibson
--> Herbert
--> Lem
```

### Summarizing with aggregates

An _aggregate_ computes one value from many rows, such as their number or their sum. Lus has the following aggregates:

- `count(*)` is the number of rows.
- `count(expr)` is the number of rows for which `expr` is not `nil`.
- `sum(expr)` adds the values of `expr`.
- `avg(expr)` is the average of the values of `expr`, as a float.
- `min(expr)` and `max(expr)` are the smallest and the largest value of `expr`. They compare numbers by size and strings alphabetically.

An aggregate is written in the `select` clause and gets its name from `as`. A query whose `select` holds aggregates yields a single row that summarizes all the rows it kept. Every aggregate ignores `nil` values, so the average rating in the following query covers the three books that have a rating. A query is also a value that a program may store in a variable, pass to a function, or return from one. The following query is stored in a variable and spans several lines. A query ends after its last clause, or at the closing parenthesis of a call.

```lus nocheck
local summary = @books as b select
    count(*) as total,
    count(b.rating) as rated,
    avg(b.rating) as rating,
    sum(b.pages) as pages,
    min(b.pages) as shortest,
    max(b.pages) as longest

for row in query(summary) do
    print(row.total, row.rated, row.rating)        --> 5  3  4.0
    print(row.pages, row.shortest, row.longest)    --> 1780  210  600
end
```

### Grouping with `group by`

A summary is often needed for each category: the number of books in each genre, or the total sales of each region. The `group by` clause divides the rows into groups, one for each different value of its expression. The query then computes the aggregates for each group and yields one row per group. The following query counts the titles and the pages of each genre.

```lus nocheck
local by_genre = @books as b
    select b.genre, count(*) as titles, sum(b.pages) as pages
    group by b.genre
    order by pages desc

for row in query(by_genre) do
    print(row.genre, row.titles, row.pages)
end
--> scifi  3  1080
--> novel  2  700
```

A group contains several rows, so the `select` of a grouped query may hold only values that are the same for the whole group. Each value is either an expression of the `group by` clause, here `b.genre`, or an aggregate. A field such as `b.title` differs from row to row within a group, so selecting it raises an error when the query runs.

The `order by` clause of this query uses `pages`, a name that `select` assigned with `as`. A plain name in `order by` or `having` refers to the selected value of that name, while in `where` the same name refers to a variable of the surrounding code.

### Filtering groups with `having`

`where` selects the rows that enter the groups. It runs before any aggregate is computed, so its condition cannot use a count or a total. The `having` clause holds a condition on the groups, which it checks after grouping to keep the groups for which the condition is truthy. A condition in `having` may contain an aggregate, as in `having count(*) >= 2`, or the name that `as` gave the aggregate in `select`, as in `having rated >= 2`. In the following query, `where` keeps the books that have a rating, then `having` keeps the genres with at least two such books.

```lus nocheck
local well_rated = @books as b
    where b.rating
    select b.genre, count(*) as rated, avg(b.rating) as rating
    group by b.genre
    having rated >= 2

for row in query(well_rated) do
    print(row.genre, row.rated, row.rating)   --> scifi  2  4.5
end
```

### Joining two sources

Related data is often held in two lists, such as a list of books with the name of their author and a list of authors with their country. A _join_ answers questions that need both lists, such as the country each book comes from. The query names both sources, separated by a comma, each with its own row variable. It forms every pair of one row from the first source and one row from the second, then the `where` clause keeps the pairs that belong together.

```lus nocheck
local authors = {
    { name = "Austen", country = "England" },
    { name = "Herbert", country = "United States" },
    { name = "Lem", country = "Poland" },
}

local origins = @books as b, authors as a
    where b.author == a.name
    select b.title, a.country
    order by b.title

for row in query(origins) do
    print(row.title, row.country)
end
--> Dune  United States
--> Emma  England
--> Persuasion  England
--> Solaris  Poland
```

A row without a partner produces no result. The list of authors has no entry for Gibson, so `Neuromancer` is absent from the output. A join always has a `select` clause, because each result combines fields from two rows. The other clauses work on a join as they do on one source, so a join with `group by a.country` can count the books of each country.

### Values from the surrounding code

A clause may use the local variables around the query, which is how a query takes a parameter such as a search term or a page size. The query reads such a variable once, when the query is built, so a later assignment to the variable leaves the query unchanged. The source is different: the query reads the contents of the source again every time it runs, so it sees rows that were added in the meantime.

```lus nocheck
local longest = 260
local short = @books as b where b.pages <= longest select b.title
longest = 1000   -- the query keeps 260

books[#books + 1] = { title = "Candide", author = "Voltaire", genre = "novel", pages = 130 }

for row in query(short) do
    print(row.title)
end
--> Persuasion
--> Solaris
--> Candide
```

A function can build a query from its parameters, so that each call supplies its own values.

```lus nocheck
local function shortest(genre, n)
    return @books as b where b.genre == genre order by b.pages limit n
end

for book in query(shortest("scifi", 1)) do
    print(book.title)   --> Solaris
end
for book in query(shortest("novel", 1)) do
    print(book.title)   --> Persuasion
end
```

### Running a query

Writing a query only describes the work, which happens when `query` runs it in a `for` loop. Each loop runs the query from the start on the current contents of its sources. The `for` loop is the only way to get the results, so a program that needs them as a list builds the list inside the loop.

```lus nocheck
local novels = @books as b where b.genre == "novel" select b.title

local titles = {}
for row in query(novels) do
    titles[#titles + 1] = row.title
end
print(table.concat(titles, ", "))   --> Emma, Persuasion

books[2].genre = "romance"
for row in query(novels) do
    print(row.title)   --> Persuasion
end
```

The clauses of a query may be written in any order, each at most once. A query always works in the same sequence, whatever the written order:

1. `where` filters the rows.
2. `group by` forms the groups.
3. `having` filters the groups.
4. `select` builds the results.
5. `distinct` removes duplicates.
6. `order by` sorts the results.
7. `offset` and `limit` take part of the sorted results.

The clause words `where`, `select`, `distinct`, `as`, `order`, `by`, `asc`, `desc`, `limit`, `offset`, `group`, and `having` have a special meaning only inside a query, as do the aggregate names `count`, `sum`, `avg`, `min`, and `max`. Everywhere else they are ordinary names, so a program may have a variable named `count` or a function named `select`.

### `nil` in queries

A missing field reads as `nil`. Queries treat `nil` as follows:

- A comparison with `nil` is false, so `where b.rating < 5` and `where b.rating ~= 5` both skip the books without a rating, while `where b.rating == nil` matches no row. The condition `where not b.rating` finds the rows where the field is missing.
- `order by` places rows whose sort value is `nil` first in ascending order and last in descending order.
- When a query keeps no rows, `count` yields `0` and every other aggregate yields `nil`.

### Queries on a database

A table of a SQLite database is also a source. A database opened with [`io.sqlite`](/manual/api#io.sqlite) has one field for each of its tables, so `@db.books` is a query on the table `books` that SQLite filters.

The following function `short_books` builds one query for any source, which the program runs on a database table and on a Lus table. The database is in memory, so it needs no permission. Each `db:run` line inserts one row, with its arguments in place of the `?` marks. [SQLite](#sqlite) explains these statements.

```lus
local function short_books(source)
    return @(source) as b where b.pages < 300 select b.title
end

local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (title TEXT, pages INTEGER)")
db:run("INSERT INTO books VALUES (?, ?)", "Dune", 600)
db:run("INSERT INTO books VALUES (?, ?)", "Solaris", 210)

for row in query(short_books(db.books)) do
    print(row.title)   --> Solaris
end
for row in query(short_books({ { title = "Emma", pages = 450 }, { title = "Candide", pages = 130 } })) do
    print(row.title)   --> Candide
end
```

A source written as a parenthesized expression, such as `@(source)`, always takes its row variable from `as`. [SQLite](/manual/sqlite) describes databases, how to create and fill their tables, and how queries run on them.

## Modules

A program that grows past a few hundred lines is easier to work on as several files, each with one job. Each such file is a [module](#tables-as-modules), which other files load by name. The local variables of a module are private to it. Other files see only the value that the module returns, so two files can each have a helper function with the same name. Several programs may also load the same module, which keeps shared code in one place.

The standard library is built in, so JSON, CSV, the filesystem, networking, and the other libraries of [The standard library](#the-standard-library) are available in every file without loading. Modules hold the code of the project itself.

### Writing a module

A module file ends with `return`. The value it returns is usually a table of functions. The following file is a module named `shapes`, saved as `shapes.lus`.

```lus
local shapes = {}

local function square(x)
    return x * x
end

function shapes.circle(radius)
    return math.pi * square(radius)
end

function shapes.rectangle(width, height)
    return width * height
end

return shapes
```

The functions `circle` and `rectangle` are fields of the returned table, so other files may call them. The function `square` is a local variable of the file, which other files cannot see.

### Loading a module with `require`

[`require`](/manual/api#require) takes the name of a module, which is its file name without the extension, then returns the value that the file returned. Loading a module file requires the `load` and `fs:read` [permissions](#permissions). The following program is in the same directory as `shapes.lus`.

```lus nocheck
pledge("load", "fs:read")

local shapes = require("shapes")
print(shapes.rectangle(3, 4))                       --> 12
print(string.format("%.2f", shapes.circle(1)))      --> 3.14
print(require("shapes") == shapes)                  --> true
```

`require` runs a module file once and stores the result. Every later `require` of the same name returns the stored value without reading the file again, as the last line of the program shows. A module is therefore also a place for state that the whole program shares, such as a cache or a configuration table.

A program that needs only some functions of a module takes them with [`from`](#destructuring-with-from), which declares one local variable for each named field.

```lus nocheck
pledge("load", "fs:read")

local circle, rectangle from require("shapes")
print(rectangle(2, 5))   --> 10
```

### Search paths

`require` reads [`package.path`](/manual/api#package.path) to find a module file. `package.path` is a string of file name templates separated by semicolons. `require` tries each template in turn with the `?` replaced by the module name, until it finds a file that exists.

```lus
print(package.path)   --> ./?.lus;./?/init.lus;./?.lua;./?/init.lua
```

With this default, `require("shapes")` tries `./shapes.lus`, then `./shapes/init.lus`, then the same two names with the `.lua` extension. The paths are relative to the working directory, which is the directory the program was started from. A dot in a module name is a directory separator, so `require("geometry.units")` tries `./geometry/units.lus` first. When no template matches a file, `require` raises an error that lists every file it tried.

A project that keeps its modules elsewhere adds a template, either by assigning to `package.path` before its first `require`, as in `package.path = "./lib/?.lus;" .. package.path`, or from outside the program with the environment variable `LUS_PATH`. When `LUS_PATH` is set, its value is the starting value of `package.path`.

```bash
LUS_PATH="./lib/?.lus;./?.lus" lus main.lus
```

### Preincluded modules

A program that handles untrusted input often [seals](#rejecting-and-sealing) its permissions once it has started, after which it can no longer `require` a module file, because it gave up the permissions to read and run files. A _preincluded module_ is a module that the interpreter reads and compiles at startup, before the program runs, so `require` later returns it from memory without any permission. The `--include` option of the `lus` command names the module file.

The following command starts `server.lus` with `shapes.lus` preincluded.

```bash
lus --include shapes.lus server.lus
```

The program may then seal its permissions on its first line and still load `shapes`, while a `require` of a module that was not preincluded fails.

```lus nocheck
pledge("seal")

local shapes = require("shapes")
print(shapes.rectangle(2, 5))               --> 10
print((catch require("geometry.units")))    --> false
```

`--include` may appear several times. `--include path/to/file.lus:name` gives the module the name after the colon. `--include lib` names a directory and preincludes every module file in it and in its subdirectories, each named by its path with dots, so `lib/geometry/units.lus` becomes the module `lib.geometry.units`.

### Standalone executables with `lus build`

`lus build` turns a program and its modules into a single executable file that runs on a machine with neither Lus nor the source files.

```bash
lus build -o app main.lus
```

`lus build` reads the source to find every call to `require` whose argument is a literal string, such as `require("shapes")`, then bundles those modules with `main.lus`. A module that the program loads under a computed name is added with `--include`, which takes the same forms as it does for `lus`. Inside the executable, `require` returns bundled modules from memory and needs no permission. [Developer tools](/manual/tools) describes `lus build` in full.

### Modules from the network

A program can use a package that someone else published without copying its files into the project. `require` takes the URL of a module and loads it from the network. The package registry of Lus is `atmosp.here`, where each package has a URL for each release line of Lus. The following program uses the package `dates` for Lus 2.0.

```lus nocheck
pledge("load", "network:http=atmosp.here")

local dates = require("https://atmosp.here/2.0/dates.lus")
print(dates.format(dates.parse("2027-03-01")))
```

The permission `network:http` for the host of the URL lets the program load modules from it. The permission `load` lets it run them. A program that loads modules from the network pledges both, as the first line shows.

`lus` downloads a package once and keeps it in a cache in the Lus home, `~/.lus` by default. Later runs load it from the cache. Before a program starts, `lus` reads it for calls of `require` with a literal URL and downloads those packages at once, so the program never waits for the network in the middle of its work. A `require` whose URL is computed while the program runs still works, but `lus` prints a warning, because that download stops the program until it finishes.

A URL such as `https://atmosp.here/2.0/dates.lus` always loads the newest release of `dates` for Lus 2.0. The registry accepts only releases that fix bugs under that URL, so a program keeps working when a package publishes a new release. A program that needs one exact release adds its version, as in `https://atmosp.here/2.0/dates@1.4.1.lus`. Every release on `atmosp.here` is signed. `lus` refuses a package whose signature or content does not match.

Any web server can serve a module file. `require` downloads it and runs it. A module from such a server may require files beside it by name, as a local module requires files of its project.

## The environment

The _environment_ of a piece of code is the set of global names it can use: `print`, `math`, `string`, and the globals of the program. Lus keeps these names in an ordinary table. A program may read that table, give a piece of code a different one, or make it read-only.

### Globals as a table

Every global variable is a field of one table, which the global `_G` holds, so reading the global `score` and reading `_G.score` are the same operation. The table form is useful when the name of a global is known only while the program runs, or when a program needs to list its globals.

```lus
score = 10
print(_G.score)        --> 10

local name = "score"
print(_G[name])        --> 10
print(_G.print == print)   --> true
```

The compiler reads and writes globals as fields of a variable named `_ENV`. Any name that is not a local variable is a field of `_ENV`, so `score` means `_ENV.score`. At the start of a program, `_ENV` and `_G` are the same table. A block that declares its own local `_ENV` gives the code inside it another set of globals.

```lus
score = 10

local function isolated()
    local _ENV = { print = print }
    print(score)       --> nil
    answer = 42
    return _ENV.answer
end

print(isolated(), answer)   --> 42  nil
```

Inside `isolated`, the global `score` is `nil`. The assignment to `answer` writes to the small table, which leaves the globals of the program unchanged.

### Running code with its own environment

Some programs run code that they receive as text: a formula from a configuration file, a rule typed by a user, or a plugin. [`load`](/manual/api#load) compiles a string of Lus code and returns it as a function. Its fourth argument is the environment of that code, which can use only the global names in that table. `load` requires the `load` permission. The following program computes a discounted total from a formula.

```lus
pledge("load")

local formula = "return price * quantity * 0.9"   -- text from a user or a file
local compute = load(formula, "formula", "t", { price = 20, quantity = 3 })
print(compute())   --> 54.0
```

The second argument names the code in error messages. The third argument, `"t"`, makes `load` accept source text only, which is the right setting for text from an untrusted party. If the text does not compile, `load` returns `nil` and the error message.

The environment determines which names the loaded code can use. Code that receives `{ math = math }` can compute, but it has no `os`, `io`, `fs`, or `network` to call. Permissions are a second, independent limit. The following function loads a piece of text with the given environment and runs it in a coroutine that first rejects every permission and seals the set. The rejection ends with the coroutine, so the rest of the program keeps its permissions.

```lus
pledge("load", "fs:read")

local function run_untrusted(source, env)
    local chunk, message = load(source, "untrusted", "t", env)
    if not chunk then
        return false, message
    end
    local co = coroutine.create(function()
        pledge("~fs", "~network", "~exec", "~env", "~load", "seal")
        return chunk()
    end)
    return coroutine.resume(co)
end

print(run_untrusted("return math.max(2, 7)", { math = math }))
--> true  7
print(run_untrusted("return os.getenv('HOME')", { math = math }))
--> false  untrusted:1: attempt to index a nil value (global 'os')
print(run_untrusted("return fs.list('.')", { fs = fs }))
--> false  untrusted:1: permission "fs:read" denied for '.'
```

The second call fails because the environment has no `os`. The third call receives the real `fs` library, but its operation still fails because the coroutine rejected the permission. Neither limit bounds the running time or the memory of the loaded code, so a call to loaded code that contains an endless loop never returns.

### The `--readonly-env` option

In a large program, any function may assign to a global or replace a library function, which changes it for every other part of the program. The cause may be a forgotten `local` or a module that redefines `print` for its own purposes, while the effect appears far from the cause. The `--readonly-env` option of `lus` prevents such changes by making the table of globals and the library tables in it, such as `math` and `string`, read-only once the interpreter has started.

```bash
lus --readonly-env script.lus
```

Under this option, each line marked `error` in the following script raises the error `attempt to modify a readonly table`.

```lus nocheck
local total = 0              -- local variables work as usual
local list = { 1, 2, 3 }
list[4] = 4                  -- tables that the program creates stay writable

counter = 1                  -- error: creates a global
math.pi = 3                  -- error: changes a library table
print = nil                  -- error: replaces a global
setmetatable(math, {})       -- error: a metatable could redirect every access
```

A program that runs under `--readonly-env` keeps its state in local variables and in the tables of its modules, which stay writable.

### Build flags

One source file often has to behave in two ways, such as logging more during development than in production, or including a feature only in test builds. A _build flag_ is a named value given on the command line with `-F`, which the program reads from the table `flags`. This table exists in every file without a declaration and is read-only.

```bash
lus -Fdebug -Flevel=3 -Fchannel=beta script.lus
```

A flag given without a value is `true`. A given value becomes a number when it reads as one and stays a string otherwise. A flag that was not given reads as `nil`. The example command sets `flags.debug` to `true`, `flags.level` to `3`, and `flags.channel` to `"beta"`. Run without flags, the following program prints only the level.

```lus
if flags.debug then
    print("debug build")
end
print("level", flags.level or 1)   --> level  1
```

The compiler resolves an `if` condition that the flags decide alone, then omits the branch that the flags rule out. Such a condition tests a flag, compares a flag with a string, number, boolean, or `nil` literal, or combines these tests with `and`, `or`, and `not`. Debugging code in such an `if` costs nothing in a run without the flag.

```lus
if flags.channel == "beta" and flags.level >= 2 then
    print("verbose beta logging")
end
```

Run with `-Fchannel=beta -Flevel=3`, this program compiles to the `print` alone, without a test. A condition that also reads a value of the running program, as in `flags.debug and verbose`, is resolved only when the flag part decides it. An ordering of a flag that was not given, such as `flags.level >= 2` in a run without `-Flevel`, raises an error when it runs, as `nil >= 2` does anywhere else.

`lus build` accepts `-F` as well and stores the flag values in the executable, which then always runs with them. [Developer tools](/manual/tools) describes `lus build`. [CLI](/manual/cli) lists every option of the `lus` command.

## The standard library

The standard library is the set of functions, compiled into the `lus` executable, that every Lus program can call without loading anything. Most of its functions are fields of global tables such as `string`, `table`, and `math`. A few functions that almost every program uses, such as `print`, `tostring`, and `fromjson`, are plain globals.

Functions that read or write files, contact the network, read environment variables, or start processes need a [permission](#permissions).

### `string`

The `string` library works on text. [Strings and patterns](#strings-and-patterns) explains its functions. The [string library reference](/manual/api#string-library) lists every one.

### `table`

The `table` library contains the functions that work on lists. [Lists](#lists) introduces `table.insert`, `table.remove`, `table.sort`, and `table.concat`.

The comparison function of `table.sort` can order records by several fields. The following call sorts people by age, with people of the same age sorted by name.

```lus
local people = {
    { name = "Mira", age = 31 },
    { name = "Tom", age = 25 },
    { name = "Ada", age = 31 },
}

-- Youngest first. People of the same age are ordered by name.
table.sort(people, function(a, b)
    if a.age ~= b.age then
        return a.age < b.age
    end
    return a.name < b.name
end)

for _, person in ipairs(people) do
    print(person.name, person.age)
end
--> Tom  25
--> Ada  31
--> Mira  31
```

When the order depends on one value per element, [`table.sortby`](/manual/api#table.sortby) is shorter. Its second argument is a function that returns the sort key of an element. A third argument of `false` sorts in descending order. The following call sorts words by length.

```lus
local words = { "pear", "fig", "banana", "kiwi" }
table.sortby(words, function(word) return #word end)
print(table.concat(words, " "))  --> fig pear kiwi banana
```

[`table.move`](/manual/api#table.move) copies a range of elements to another position or into another table. Its most common use is to append one list to another.

```lus
local first, second = { 1, 2, 3 }, { 4, 5 }
table.move(second, 1, #second, #first + 1, first)
print(table.concat(first, " "))  --> 1 2 3 4 5
```

The library also has functions that process a whole list in one call, each replacing a loop that many programs contain.

- [`table.map`](/manual/api#table.map) returns a new list with a function applied to every element.
- [`table.filter`](/manual/api#table.filter) returns a new list with the elements for which a function returns a truthy value.
- [`table.reduce`](/manual/api#table.reduce) combines all elements into one value by calling a function with the result so far and the next element.
- [`table.groupby`](/manual/api#table.groupby) divides the elements into groups. It returns a table that maps each key the function returns to the list of elements with that key.
- [`table.sum`](/manual/api#table.sum), [`table.mean`](/manual/api#table.mean), [`table.median`](/manual/api#table.median), and [`table.stdev`](/manual/api#table.stdev) compute the total, the average, the middle value, and the standard deviation of a list of numbers. Each returns a float.

The following planner holds the length of each task in minutes. It adds a buffer of 10 minutes to every task with `table.map`, computes the total and the average with `table.sum` and `table.mean`, selects the tasks of at most 30 minutes with `table.filter`, and finds the longest task with `table.reduce`.

```lus
local tasks = { 30, 45, 15, 90 }

local buffered = table.map(tasks, function(minutes) return minutes + 10 end)
print(table.concat(buffered, " "))               --> 40 55 25 100
print(table.sum(tasks), table.mean(tasks))       --> 180.0  45.0

local quick = table.filter(tasks, function(minutes) return minutes <= 30 end)
print(table.concat(quick, " "))                  --> 30 15

local longest = table.reduce(tasks, function(best, minutes)
    return minutes > best and minutes or best
end)
print(longest)                                   --> 90
```

These functions are for a single step on a plain list. A [query](/manual/guide#queries) groups and summarizes records, such as the total sales of each region, in one expression. [Data formats](/manual/data#table-functions) describes the remaining table functions, such as `table.zip` and `table.transpose`. The [table library reference](/manual/api#table-library) lists every function.

### `math`

The `math` library contains numeric functions for rounding, minimum and maximum, roots, trigonometry, logarithms, and random numbers.

[`math.floor`](/manual/api#math.floor) rounds a number down to the nearest integer and [`math.ceil`](/manual/api#math.ceil) rounds up. [`math.max`](/manual/api#math.max) and [`math.min`](/manual/api#math.min) return the largest and the smallest of their arguments. [`math.abs`](/manual/api#math.abs) returns the absolute value. [`math.sqrt`](/manual/api#math.sqrt) returns the square root.

```lus
print(math.floor(3.7), math.ceil(3.2), math.floor(-3.7))  --> 3  4  -4
print(math.max(4, 9, 2), math.min(4, 9, 2))               --> 9  2
print(math.abs(-5), math.sqrt(16))                        --> 5  4.0
```

[`math.pi`](/manual/api#math.pi) is the constant π, which the following example uses to compute the area of a circle. [`math.huge`](/manual/api#math.huge) is positive infinity, a float that is larger than every other number. It is the usual starting value for a loop that searches for a minimum, such as the loop in the example that finds the cheapest item and its price.

```lus
local radius = 2
print(string.format("%.2f", math.pi * radius ^ 2))  --> 12.57

local items = { { name = "tea", price = 8 }, { name = "mug", price = 3 }, { name = "jam", price = 5 } }
local lowest, cheapest = math.huge, nil
for _, item in ipairs(items) do
    if item.price < lowest then
        lowest, cheapest = item.price, item.name
    end
end
print(cheapest, lowest)  --> mug  3
```

[`math.type`](/manual/api#math.type) returns the name of the [subtype](#numbers) of a number. [`math.tointeger`](/manual/api#math.tointeger) returns `nil` for a number that is not whole, as [Catching errors](#catching-errors) shows.

[`math.random`](/manual/api#math.random) returns a random number that differs on every run of a program. Without arguments it returns a float from 0 up to, but not including, 1. With one integer `n` it returns an integer from 1 to `n`. With two integers it returns an integer between them, both ends included.

```lus nocheck
print(math.random())       --> 0.6394267984578837
print(math.random(1, 6))   --> 4
```

Calling [`math.randomseed`](/manual/api#math.randomseed) with a number makes the sequence repeatable, because the same seed always produces the same numbers. A repeatable sequence is useful in tests and simulations. The following test of a dice game seeds the generator so that every run rolls the same dice.

```lus
local function roll_three()
    return { math.random(1, 6), math.random(1, 6), math.random(1, 6) }
end

math.randomseed(42)
local first = roll_three()
math.randomseed(42)
local second = roll_three()
print(table.concat(first) == table.concat(second))  --> true
```

The generator is fast and its numbers are well distributed, but its output can be predicted from earlier output, so passwords, tokens, and keys must come from a cryptographic source. On Linux and macOS, a program can read such bytes from `/dev/urandom`, opened as a binary file. The [math library reference](/manual/api#math-library) lists every function, including the trigonometric and logarithmic ones.

### `io`

The `io` library reads and writes files and the standard streams of the program. Opening a file needs the `fs:read` permission, the `fs:write` permission, or both, depending on the mode.

[`io.open`](/manual/api#io.open) opens a file and returns a _file handle_, a value with methods that read, write, and close the file. Its second argument is the mode, which is `"r"` to read (the default), `"w"` to empty the file and write, or `"a"` to write at the end of the file. A program must close a handle when it has finished with it. A handle declared with [`<close>`](#closing-resources-automatically) is closed when its block ends. The following program writes two lines to a file and reads them back.

```lus nocheck
pledge("fs")

do
    local file <close> = io.open("notes.txt", "w")
    file:write("first line\n", "second line\n")
end

do
    local file <close> = io.open("notes.txt")
    print(file:read("l"))  --> first line
    print(file:read("a"))  --> second line
end
```

`file:write` writes each of its arguments, which may be strings or numbers, with nothing between or after them. The argument of `file:read` is a format that specifies how much to read. `"l"` reads one line without its line break and returns `nil` at the end of the file. `"a"` reads everything that remains. `"n"` reads a number. An integer reads that many characters.

[`io.lines`](/manual/api#io.lines) opens a file and returns an iterator over its lines, closing the file after the last line. It is the shortest way to process a text file line by line. The following file `stock.txt` lists a count for each fruit.

```text
apples 3
pears 12
plums 7
```

The following program adds up the counts.

```lus nocheck
pledge("fs:read")

local total = 0
for line in io.lines("stock.txt") do
    local count = line:match("%d+")
    total = total + tonumber(count)
end
print(total)  --> 22
```

When a file cannot be opened, `io.open` returns `nil` and a message, so a program can test the result, then report the problem or continue without the file. `io.lines` raises an error in the same situation.

```lus
pledge("fs")
local file, problem = io.open("/no/such/directory/notes.txt")
print(file)     --> nil
print(problem)  --> /no/such/directory/notes.txt: No such file or directory
```

A program has three standard streams, each a file handle that is already open. `io.stdin` is the input, usually the keyboard or a pipe. `io.stdout` is the output that `print` writes to. `io.stderr` is the stream for diagnostics, which stays visible when the output is redirected to a file. [`io.write`](/manual/api#io.write) writes to the standard output without the line break that `print` adds. [`io.read`](/manual/api#io.read) reads from the standard input with the formats of `file:read`. The following program, useful at the end of a pipe such as `cat notes.txt | lus number.lus`, numbers the lines of its input and reports their count on the diagnostic stream.

```lus nocheck
local number = 0
for line in io.lines() do
    number = number + 1
    io.write(number, "  ", line, "\n")
end
io.stderr:write(`numbered $number lines\n`)
```

[`file:isatty`](/manual/api#file:isatty) tells whether a handle is a terminal. A program that prints colors checks `io.stdout:isatty()` first, so its output stays plain text in a file or a pipe. [`file:setraw`](/manual/api#file:setraw) switches a terminal to raw input, where each key reaches the program as soon as it is pressed and nothing is echoed. Arrow keys arrive as escape sequences such as `"\27[A"`. A menu that moves with the arrow keys, or a prompt for a password, reads keys in raw mode and switches back when it is done. The process restores the terminal when it ends, even after an error. The following function reads one key.

```lus nocheck
local function readkey()
    io.stdin:setraw(true)
    local key = io.stdin:read(1)
    io.stdin:setraw(false)
    return key
end
```

A mode with a `b`, such as `"rb"`, opens a file in binary mode, where a read returns raw bytes as a [vector](#vector). In text mode, a read returns a string and checks that the string is valid text. The [io library reference](/manual/api#io-library) lists every function and every method of a file handle. [Text and bytes](/manual/text#files) describes the two modes.

### `os`

The `os` library reads the time and the environment from the operating system, creates temporary files, and ends the program.

[`os.time`](/manual/api#os.time) returns the current time as a count of seconds since the start of 1970, the form in which most systems store times. Given a table with the fields `year`, `month`, and `day`, plus the optional fields `hour`, `min`, and `sec`, it returns the count for that local date and time. [`os.date`](/manual/api#os.date) converts such a count to text with a format string that uses codes such as `%Y` for the year, `%m` for the month, `%d` for the day, `%H` for the hour, and `%M` for the minute. A format that starts with `!` gives the time in UTC. Any other format gives the local time.

```lus
local release = os.time({ year = 2031, month = 4, day = 12, hour = 9 })
print(os.date("%Y-%m-%d %H:%M", release))          --> 2031-04-12 09:00
print(os.date("!%Y-%m-%d %H:%M:%S", 1700000000))   --> 2023-11-14 22:13:20
```

These functions are enough for timestamps and simple formatting. The [`time` library](#time) provides time zones, durations, and parsing.

[`os.clock`](/manual/api#os.clock) returns the processor time that the program has used, in seconds, so the difference between two readings is the processor time of the code between them. The following program times a loop.

```lus nocheck
local start = os.clock()
local sum = 0
for i = 1, 1000000 do
    sum = sum + i
end
print(string.format("%.3f seconds", os.clock() - start))  --> 0.004 seconds
```

[`os.getenv`](/manual/api#os.getenv) returns the value of an environment variable, or `nil` when the variable is not set. It needs the `env:read` permission, which `env` includes and which a program can [narrow](#narrowing-a-permission) to the variables it reads. The following program reads the home directory of the user and picks `vi` when no editor is configured.

```lus nocheck
pledge("env")
print(os.getenv("HOME"))                  --> /home/ada
local editor = os.getenv("EDITOR") or "vi"
```

[`os.setenv`](/manual/api#os.setenv) sets an environment variable, and removes it when the value is `nil`. It needs the `env:write` permission. The new value reaches `os.getenv` and every program that `os.execute` or `io.popen` starts afterwards. The following program sets a variable before it runs a tool that reads it.

```lus nocheck
pledge("env", "exec")
os.setenv("TOOL_LEVEL", "debug")
os.execute("tool --check")
```

[`os.tmpname`](/manual/api#os.tmpname) creates an empty file with a fresh name in the temporary directory of the system and returns its path. It needs the `fs:write` permission. The file stays until the program removes it with `fs.remove`.

[`os.exit`](/manual/api#os.exit) ends the program at once with the exit status given by its argument, which is `true` or absent for success, `false` for failure, or an integer for that status. `os.exit` ends the program before variables declared with `<close>` are closed, so a program that holds resources should end by reaching the last line of its script. The following program exits with a failure status when `arg`, the global list of the command line arguments that follow the script name, is empty.

```lus nocheck
if #arg == 0 then
    io.stderr:write("usage: lus report.lus FILE\n")
    os.exit(false)
end
```

[`os.platform`](/manual/api#os.platform) returns the name of the operating system, such as `"linux"`, `"darwin"`, or `"windows"`. The [os library reference](/manual/api#os-library) lists every function.

### `utf8`

The `utf8` library converts between characters and their [code points](#characters-and-code-points) and checks that text is valid Unicode. A Lus string may hold a _lone surrogate_, a code point that is not valid Unicode by itself, which can occur in file names from Windows. On such a string, `utf8.len` returns `nil` and the position of the first lone surrogate, while `utf8.codes` raises an error when it reaches one. A program can use either function to check text before it passes the text to a system that requires valid Unicode.

[`utf8.char`](/manual/api#utf8.char) builds a string from code points. [`utf8.codepoint`](/manual/api#utf8.codepoint) returns the code points of the characters in a range of a string. [`utf8.codes`](/manual/api#utf8.codes) is an iterator that visits each character with its position and its code point.

```lus
print(utf8.char(233, 9749))        --> é☕
print(utf8.codepoint("héllo", 2))  --> 233
print(utf8.len("héllo"))           --> 5
print(utf8.len("a\u{D800}b"))      --> nil  2

for position, code in utf8.codes("añb") do
    print(position, code)
end
--> 1  97
--> 2  241
--> 3  98
```

The [UTF-8 library reference](/manual/api#utf-8-library) lists every function. The [`vector`](#vector) library converts a string to its bytes.

### `vector`

A _vector_ is a buffer of bytes that a program can read and change in place. It holds [data that is not text](#text-and-bytes), such as the contents of an image or an archive, a network packet, or a file format with fields at fixed offsets. Every library function that produces raw bytes, such as a read from a binary file or from a socket, returns a vector.

[`vector.create`](/manual/api#vector.create) makes a vector of a given size filled with zeros. [`vector.get`](/manual/api#vector.get) and [`vector.set`](/manual/api#vector.set) read and write single bytes at offsets that start at 0. `#v` is the size of the vector `v` in bytes. [`vector.pack`](/manual/api#vector.pack) and [`vector.unpack`](/manual/api#vector.unpack) write and read numbers that span several bytes, with a format string that describes the layout of each number. The following example writes the width and height of an image into an 8-byte header with the format `>I4I4`, which means two unsigned integers of 4 bytes each, most significant byte first.

```lus
-- The header of an image: width and height as 4-byte integers.
local header = vector.create(8)
vector.pack(header, 0, ">I4I4", 640, 480)

print(#header)                                  --> 8
print(vector.get(header, 2), vector.get(header, 3))  --> 2  128

local width, height = vector.unpack(header, 0, ">I4I4")
print(width, height)                            --> 640  480
```

[`vector.fromstring`](/manual/api#vector.fromstring) returns the bytes that encode a string, which [`vector.tostring`](/manual/api#vector.tostring) decodes back into text. The byte count of a string differs from its character count when the text has characters outside ASCII.

```lus
local bytes = vector.fromstring("héllo")
print(#"héllo", #bytes)         --> 5  6
print(vector.tostring(bytes))   --> héllo
```

The `vector.archive` modules compress and decompress vectors with gzip, deflate, Zstandard, Brotli, and LZ4. [Text and bytes](/manual/text#vectors) describes vectors, transcoding, and compression in full. The [vector library reference](/manual/api#vector-library) lists every function.

[Coroutines](#coroutines) explains both libraries, whose references are the [coroutine library](/manual/api#coroutine-library) and the [worker library](/manual/api#worker-library).

### `debug`

A program can inspect itself with the `debug` library, which reports which functions are running, the line that each one has reached, and the values of their local variables. It is for diagnostics and for tools such as debuggers and profilers. Program logic should stay independent of it, because its functions are slow and can read and change the local variables of other functions.

The function that most programs use is [`debug.traceback`](/manual/api#debug.traceback), which returns a _traceback_: text that lists the chain of function calls that led to the current line. `lus` prints a traceback when an error ends the program, but a program can call `debug.traceback` at any other point. The following module logs a traceback to find the callers that still use a deprecated function.

```lus
local stats = {}

function stats.old_total(items)
    print(debug.traceback("old_total is deprecated"))
    return #items
end

function stats.report()
    local count = stats.old_total({ "a", "b" })
    print(`$(count) items`)
end

stats.report()
```

Saved as `report.lus`, the program prints the message followed by one line per active function, the innermost first.

```
old_total is deprecated
stack traceback:
	report.lus:4: in field 'old_total'
	report.lus:9: in field 'report'
	report.lus:13: in main chunk
	[C]: in ?
2 items
```

Each line gives a file, a line number, and the function that was running there. The last line is the entry for the runtime, which started the script.

[`debug.getinfo`](/manual/api#debug.getinfo) returns a table of facts about one active function, such as its source file and current line. The library also contains functions that the tools are built on. [`debug.parse`](/manual/api#debug.parse) returns the syntax tree of Lus source text. [`debug.format`](/manual/api#debug.format) formats source text as `lus fmt` does. The [debug library reference](/manual/api#debug-library) lists every function.

### JSON and CSV

JSON and CSV are the two text formats that programs most often use to exchange data. JSON is for nested data, such as the body of a web request or a configuration file. CSV is for rows of fields, such as the export of a spreadsheet. Global functions read and write both formats.

[`fromjson`](/manual/api#fromjson) parses JSON text and returns the matching Lus value. It converts a JSON object to a table with string keys, a JSON array to a list, and `null` to `nil`. [`tojson`](/manual/api#tojson) converts a Lus value to JSON text. It writes a table whose keys are 1 to `n` as an array and any other table as an object.

```lus
local order = fromjson('{"id": 17, "items": ["tea", "cup"], "paid": true}')
print(order.id, order.items[2], order.paid)  --> 17  cup  true

order.items[#order.items + 1] = "spoon"
print(tojson(order.items))                   --> ["tea","cup","spoon"]
print(tojson({ total = 12.5 }))              --> {"total":12.5}
```

The error that `fromjson` raises for invalid JSON gives the position of the problem. [Catching errors](#catching-errors) shows how a program handles it.

```lus
local ok, problem = catch fromjson("{broken")
print(ok, problem)  --> false  JSON parse error at position 2: expected string key in object
```

[`fromcsv`](/manual/api#fromcsv) parses CSV text into a list of rows, each a list of strings. When the second argument is `true`, the first row gives the column names, which become the keys of every other row. Every field is a string, so a program converts numeric fields with `tonumber`. [`tocsv`](/manual/api#tocsv) returns a list of rows as CSV text, with quotes around the fields that need them.

```lus
local text = "name,age\nAda,36\nTom,25\n"

local people = fromcsv(text, true)
print(#people, people[1].name, tonumber(people[1].age) + 1)  --> 2  Ada  37

io.write(tocsv({
    { "name", "note" },
    { "Ada", "likes tea, cake" },
}))
--> name,note
--> Ada,"likes tea, cake"
```

[Data formats](/manual/data) describes both formats in full, including exact numbers, filters, and other delimiters.

### The filesystem

The `fs` library lists, creates, copies, moves, and removes files and directories. The [`io` library](#io) reads and writes the contents of a file. Every `fs` function needs the `fs:read` or `fs:write` permission for the paths it uses and raises an error when it fails.

The following program keeps an old copy of a to-do list. It creates a `backup` directory, copies `notes/todo.txt` into it, then renames the copy. [`fs.path.join`](/manual/api#fs.path.join) builds a path from its parts with the separator of the operating system, so the program works on Windows and on other systems.

```lus nocheck
pledge("fs")

local todo = fs.path.join("notes", "todo.txt")
local copy = fs.path.join("backup", "todo.txt")

fs.createdirectory("backup")
fs.copy(todo, copy)
fs.move(copy, fs.path.join("backup", "todo-old.txt"))

print(table.concat(fs.list("backup"), " "))   --> todo-old.txt
print(fs.type(todo))                          --> file  false
print(fs.type("backup"))                      --> directory  false
print(fs.path.name(todo))                     --> todo.txt
```

[`fs.list`](/manual/api#fs.list) returns the names in a directory in no particular order, or only the names that match a second argument such as `"*.txt"`. [`fs.type`](/manual/api#fs.type) returns `"file"` or `"directory"`, followed by whether the path is a symbolic link. It raises an error for a path that does not exist, so a program tests for existence with `catch fs.type(path)`.

[Filesystem](/manual/filesystem) describes every function, symbolic links, and the path helpers. The reference is the [filesystem library](/manual/api#filesystem-library).

### Networking

The `network` library has functions for sending web requests, serving them, and opening sockets. Every function needs a `network` permission for the host it contacts.

[`network.fetch`](/manual/api#network.fetch) sends one HTTP or HTTPS request and returns the status code, the body of the response, and its headers. The body is a vector, because a response can hold any bytes. `vector.tostring` converts it to text. The following program reads one user from a web service.

```lus nocheck
pledge("network:http=api.example.com/*")

local status, body = network.fetch("https://api.example.com/users/17")
if status == 200 then
    local user = fromjson(vector.tostring(body))
    print(user.name)
end
```

The optional arguments after the address are the method, a table of request headers, and a request body, in that order. A status such as 404 is a normal result: `network.fetch` raises an error only when no response arrives, for example because the host does not exist.

[`network.serve`](/manual/api#network.serve) runs a web server. Its arguments are a host, a port, and a _handler_, which is a function that the server calls once for every request. The handler receives a table that describes the request, with the fields `method`, `path`, `query`, `headers`, and `body`. It returns the status code, the body, and optionally a table of headers. The server runs each connection in its own [detached coroutine](/manual/guide#coroutines), so a slow client does not delay the others. `network.serve` returns when the server stops. The following server answers requests for `/time` with the current time as JSON.

```lus nocheck
pledge("network:server=127.0.0.1:8080")

network.serve("127.0.0.1", 8080, function(request)
    if request.path == "/time" then
        return 200, tojson({ now = os.time() }), { ["Content-Type"] = "application/json" }
    end
    return 404, "not found\n"
end)
```

`network.serve` also accepts a server socket in place of the host and the port. A program that opens the socket itself can run the server in a [detached coroutine](#detached-coroutines) and continue with other work.

```lus nocheck
pledge("network")

local function handler(request)
    return 200, "hello\n"
end

local server = network.tcp.bind("127.0.0.1", 8080)
local serving = coroutine.detach(coroutine.create(network.serve), server, handler)
-- the program continues with other work while the server answers requests
```

The `network.tcp` and `network.udp` modules open sockets for protocols other than HTTP. A TCP socket has the methods `send`, `receive`, `settimeout`, and `close`. [Network](/manual/network) describes requests, the server and its limits, sockets, and timeouts. The reference is the [network library](/manual/api#network-library).

### Time

The `time` library works with dates, clock times, and time zones. It computes the time of a moment in another city, the time that remains until a deadline, and the date one month after another.

The library distinguishes the following types of value, because many date bugs come from treating one type as another.

- An _instant_ is one moment in time, the same everywhere in the world. [`time.now`](/manual/api#time.now) returns the current instant.
- A _zoned time_ is a date and a clock reading in a particular time zone, such as 09:30 on 29 March in Paris. A _zone_ is a named set of rules such as `"Europe/Paris"`, which includes its daylight saving changes.
- A _duration_ is a length of time, such as 45 minutes.

The following example schedules a call at 09:30 in Paris, finds the instant of the call and the time in Tokyo at that instant, then computes a reminder 45 minutes earlier.

```lus
local paris = time.zone("Europe/Paris")
local tokyo = time.zone("Asia/Tokyo")

local call = time.zoned({ year = 2030, month = 3, day = 29, hour = 9, minute = 30 }, paris)
print(call:iso())                              --> 2030-03-29T09:30:00+01:00

local moment = call:instant()
print(moment:at(tokyo):format("%A %H:%M"))     --> Friday 17:30

local reminder = moment - time.minutes(45)
print(reminder:at(paris):format("%H:%M"))      --> 08:45
```

Arithmetic on instants counts elapsed time, while the `add` method of a zoned time follows the calendar. The two differ when the clocks change. Daylight saving time starts in Paris two days after the call, so the same clock time one week later is 167 hours away.

```lus nocheck
local next_call = call:add({ weeks = 1 })
print(next_call:iso())                                         --> 2030-04-05T09:30:00+02:00
print((next_call:instant() - call:instant()):seconds() / 3600) --> 167.0
```

[`time.parse`](/manual/api#time.parse) reads a date and time from text in the ISO 8601 form. Instants compare with `<` and `==`. The following example compares the time of a message with a deadline and computes the days between them.

```lus
local due = time.parse("2030-04-01T12:00:00Z")
local sent = time.parse("2030-03-29T08:30:00Z")
print(sent < due, (due - sent):parts().days)  --> true  3
```

[`time.monotonic`](/manual/api#time.monotonic) reads a clock that never moves backwards and ignores changes to the system time, which makes it the right clock for measuring how long something took. The following program measures how long it takes to build a long string.

```lus nocheck
local start = time.monotonic()
local text = string.rep("x", 100000)
print(string.format("%.6f seconds", (time.monotonic() - start):seconds()))  --> 0.000041 seconds
```

The zone rules are built into the runtime, so zones need no permission and give the same results on every system. [Time](/manual/time) describes the types of value, formatting, and parsing in full. The reference is the [time library](/manual/api#time-library).

### SQLite

A _database_ stores data in tables of rows and columns, which it keeps on disk between runs of a program. A database can return "all books by this author, oldest first" while the rest of the data stays on disk. It also keeps the data consistent when several changes belong together. SQLite is a database engine that stores a whole database in one file. It is built into Lus, so a program can use a database with nothing else installed or running.

A program gives a database its instructions as statements in a language called SQL. The SQLite site documents the [whole language](https://www.sqlite.org/lang.html).

[`io.sqlite`](/manual/api#io.sqlite) opens a database and returns a database handle. Given a file path, it opens that file, or creates the file if it does not exist, which needs the `fs:read` and `fs:write` permissions for the file. Given the name `":memory:"`, it creates a temporary database in memory, which needs no permission and is discarded when it is closed. Such a database is useful for tests and short-lived work. A handle declared with `<close>` closes the database when the variable goes out of scope.

A database starts empty. The `CREATE TABLE` statement defines a table: its name, its columns, and the type of each column. The following program creates a table of books with `db:exec`, which runs statements that return no rows.

```lus
local db <close> = io.sqlite(":memory:")

db:exec([[
    CREATE TABLE books (
        id INTEGER PRIMARY KEY,
        title TEXT NOT NULL,
        author TEXT NOT NULL,
        year INTEGER
    )
]])
```

The `books` table has four columns, whose types are `INTEGER` or `TEXT`. `NOT NULL` means that the column must have a value in every row. `id INTEGER PRIMARY KEY` makes `id` the number that identifies a row, which SQLite assigns to every new row as the next free number.

The `INSERT` statement adds a row. Its SQL text has a `?`, called a _parameter_, in place of each value. The values follow the SQL text as arguments to `db:run`, which runs one statement with parameters and returns the number of rows that the statement changed and the `id` of the last inserted row.

```lus nocheck
print(db:run("INSERT INTO books (title, author, year) VALUES (?, ?, ?)", "Emma", "Jane Austen", 1815))
--> 1  1

local author = "Flann O'Brien"
print(db:run("INSERT INTO books (title, author) VALUES (?, ?)", "The Third Policeman", author))
--> 1  2
```

Parameters are needed for correctness and for security. The name `O'Brien` contains a quote, which ends a text value in SQL, so a statement with the name inserted into its text is invalid. The security problem is called SQL injection: if a program builds SQL text from input, a user can type SQL where a name is expected, which the database then runs. SQLite treats a parameter as a value and never as SQL, which prevents both problems. The following statement fails because the name is inserted into its text.

```lus nocheck
local author = "Flann O'Brien"
print(catch db:exec("INSERT INTO books (title, author) VALUES ('x', '" .. author .. "')"))
--> false  near "Brien": syntax error
```

The `SELECT` statement reads rows, naming the columns to return and the table to read. A `WHERE` clause keeps only the rows that satisfy a condition. An `ORDER BY` clause sorts the result. `db:query` runs a `SELECT` and returns an iterator for a `for` loop. Each row is a table with the column names as keys, in which a column that holds no value is `nil`.

```lus nocheck
db:run("INSERT INTO books (title, author, year) VALUES (?, ?, ?)", "Persuasion", "Jane Austen", 1817)
db:run("INSERT INTO books (title, author, year) VALUES (?, ?, ?)", "Dracula", "Bram Stoker", 1897)

for book in db:query("SELECT title, year FROM books WHERE author = ? ORDER BY year", "Jane Austen") do
    print(book.title, book.year)
end
--> Emma  1815
--> Persuasion  1817
```

The `UPDATE` statement changes the rows that match a condition, while the `DELETE` statement removes them. `db:run` runs both, with the number of rows that the statement changed as its first result.

```lus nocheck
print((db:run("UPDATE books SET year = ? WHERE title = ?", 1816, "Emma")))  --> 1
print((db:run("DELETE FROM books WHERE year > ?", 1850)))                   --> 1
```

Some changes belong together. Moving money between two accounts takes two `UPDATE` statements, which leave the data wrong if only one of them is applied. A _transaction_ is a group of statements that the database applies completely or not at all. `db:transaction` runs a function inside a transaction. If the function returns, the database keeps every change that the function made. If the function raises an error, the database undoes every change, then the error propagates to the caller of `db:transaction`.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER NOT NULL)")
db:run("INSERT INTO accounts VALUES (?, ?)", "ada", 100)
db:run("INSERT INTO accounts VALUES (?, ?)", "tom", 20)

local function transfer(source, target, amount)
    db:transaction(function()
        db:run("UPDATE accounts SET balance = balance - ? WHERE name = ?", amount, source)
        db:run("UPDATE accounts SET balance = balance + ? WHERE name = ?", amount, target)
        for account in db:query("SELECT balance FROM accounts WHERE name = ?", source) do
            if account.balance < 0 then
                error("insufficient funds", 0)
            end
        end
    end)
end

transfer("ada", "tom", 30)
print(catch transfer("tom", "ada", 500))  --> false  insufficient funds

for account in db:query("SELECT name, balance FROM accounts ORDER BY name") do
    print(account.name, account.balance)
end
--> ada  70
--> tom  50
```

The balances show that the database undid both `UPDATE` statements of the second transfer, which failed after both had run. A transaction also makes a series of inserts much faster, because the database writes to disk once at the end.

A table of a database can also be the source of a query, as [Queries on a database](#queries-on-a-database) shows.

[SQLite](/manual/sqlite) describes prepared statements, named parameters, how Lus values map to column types, and the permissions of a database file. The reference entry is [`io.sqlite`](/manual/api#io.sqlite).

## Tools

The `lus` executable also contains the tools that a project needs. Each tool is a subcommand, so a machine that can run Lus programs can also test, format, and package them. The [command line reference](/manual/cli) lists every option.

### Testing

`lus test` finds and runs tests. A _test_ is a function whose name ends in `_test`, in a file whose name ends in `_test.lus`. A test passes when it returns and fails when it raises an error, so it checks its expectations with `assert`. The following file tests a function that adds tax to a price.

```lus
-- price_test.lus
local function with_tax(amount)
    return amount * 1.2
end

local function tax_test()
    assert(with_tax(100) == 120)
end

local function zero_test()
    assert(with_tax(0) == 0)
end
```

Running `lus test` in the directory of this file runs both tests and prints a summary. When an `assert` fails, the report shows the expression and the values on both sides of the comparison, which usually reveal the cause of the failure. Each test file runs in its own process, in parallel with the other files.

[Testing](/manual/testing) describes test files, tables of cases, the helpers for errors and recorded output, and how the examples in documentation are tested.

### Formatting and checking

`lus fmt` rewrites source files in one standard layout, which keeps changes small in version control because every file of a project has the same layout. `lus fmt --write src` formats the files of `src` in place. `lus fmt --check src` reports the files that are not formatted and leaves them unchanged.

`lus check` reads source files without running them and reports code that fails to compile, as well as code that compiles but is probably a mistake, such as a variable that is never used or an assignment to a global that was never declared. Each report gives the file, the line, and a code for the kind of problem.

[Developer tools](/manual/tools) describes both tools and lists the problems that `lus check` reports.

### Documentation

`lus doc` produces reference documentation in Markdown or JSON from comments in the source. A comment that starts with `---` directly before a function describes that function. Lines of the comment that start with `@param` and `@return` describe its parameters and results. [Developer tools](/manual/tools#documentation) describes the comment format.

`lus help` prints the reference that is stored in the executable, so it always matches the installed version. [Built-in functions](#built-in-functions) shows its use.

### Debugging

`lus debug` runs a program under a debugger, which pauses the program at a chosen line, called a _breakpoint_, to show the variables and the chain of calls at that point. The debugger can also run the program one line at a time. `lus debug` implements the Debug Adapter Protocol, which the Lus extension for Visual Studio Code and many other editors use, so a programmer controls the debugger from the editor. `lus build` packages a program, its modules, and the runtime into one executable file for people who do not have Lus installed. ## Embedding

Lus can run inside another program, called the _host_, such as a game, an editor, or a server. A host can be written in C, Zig, Rust, or any language that can call C functions. Users change the behavior of the host with Lus scripts, which can do only what the host allows.

The host includes the header `lus.h`, links the library `liblus`, and creates a _state_, which is one independent Lus runtime with its own globals and memory. The host can register its own functions as Lus globals, then run scripts in the state and read their results. The following host gives its script a function named `add`.

```c
#include "lus.h"

static int add(lus_State *L) {
  lus_pushinteger(L, lus_tointeger(L, 1, NULL) + lus_tointeger(L, 2, NULL));
  return 1;
}

int main(void) {
  lus_State *L = lus_newstate();
  lus_openlibs(L);
  lus_grant(L, "fs:read=/srv/data/*");
  lus_pushcfunction(L, add);
  lus_setglobal(L, "add");
  if (lus_dostring(L, "print(add(2, 3))") != LUS_OK)
    lus_pop(L, 1);
  lus_close(L);
  return 0;
}
```

The host and a script exchange values on a stack that belongs to the state. `add` reads its two arguments from positions 1 and 2 of that stack, pushes one result, then returns the number of results it pushed. A new state has no permissions, so the host grants the permissions that its scripts receive. In the example, `lus_grant` allows scripts to read the files under `/srv/data`, which is the only permission they have.

[Embedding](/manual/embedding) describes the interface in full. The [C API reference](/manual/api/c) documents every function. The [WebAssembly build](/manual/webassembly) exports the same interface to run Lus in a browser.

## Internals

The speed and memory use of a program depend on how the runtime executes it.

The runtime is written in Zig. It has a compiler that translates source text into bytecode, an interpreter that runs the bytecode, compilers that translate frequently run bytecode into machine code, a garbage collector, and the standard library.

### From source to bytecode

The runtime compiles a program in the following steps before it runs it.

1. The _lexer_ splits the source text into _tokens_: names, numbers, strings, keywords, and operators.
2. The _parser_ builds a _syntax tree_ from the tokens. The tree has a node for each statement and expression. `lus fmt`, `lus check`, `lus doc`, and the language server use the same parser, so they parse every program exactly as the compiler does.
3. The _code generator_ traverses the tree and emits _bytecode_, a compact list of instructions for a virtual machine. The generator computes constant expressions such as `2 * 3` at compile time. It omits the branches that a [build flag](/manual/guide#build-flags) disables.

The code generator produces one _prototype_ for every function in the source. A prototype holds the instructions of the function, its constants, and the information that error messages and debuggers need, such as line numbers and the names of local variables. `lus --dis` prints the prototypes of a script. The following script defines and calls a function.

```lus
local function area(width, height)
    return width * height
end
print(area(3, 4))  --> 12
```

Its listing shows two prototypes, one for the script itself and one for `area`.

```
function <area.lus:0> (9 instructions, 0 params+, 5 slots, 1 upvalues, 1 constants)
     0 [  0] varargprep  0 0 0
     1 [  1] closure     0 0
     2 [  4] gettabup    1 0 0
     3 [  4] move        2 0 0
     4 [  4] loadi       3 3
     5 [  4] loadi       4 4
     6 [  4] call        2 3 0
     7 [  4] call        1 0 1
     8 [  5] ret0        0 0 0
function <area.lus:1> (3 instructions, 2 params, 3 slots, 0 upvalues, 0 constants)
     0 [  2] mul         2 0 1
     1 [  2] ret1        2 0 0
     2 [  3] ret0        0 0 0
```

Each instruction is 32 bits wide and holds an operation code and up to three operands. The number in brackets is the source line. Most operands are the numbers of _registers_, which are numbered slots that belong to one call of a function and hold local variables or intermediate results. In `area`, the parameters are registers 0 and 1. `mul 2 0 1` multiplies them and stores the product in register 2, which `ret1` returns. A virtual machine of this kind is called a _register machine_. It needs fewer instructions than a machine that pushes and pops every operand on a stack, because one instruction reads its operands from registers and writes its result to a register.

At run time, a function value is a _closure_: a prototype together with the variables that the function uses from the code around it, which the listing calls _upvalues_. The instruction `closure` creates a closure. The script itself has one upvalue, the table of global variables, from which `gettabup` reads the global `print`.

`lus compile` saves the bytecode of a script to a file. `lus build` stores the bytecode inside an executable. A program that starts from saved bytecode skips compilation.

### Value representation

Every value takes 16 bytes: 8 bytes of _payload_ and a _tag_ that gives the type of the payload. For `nil`, booleans, integers, and floats, the payload is the value itself. Such values are stored _inline_, so creating one allocates no memory and copying one copies 16 bytes.

For every other type, the payload is the address of an _object_ in the heap, the region of memory that the garbage collector manages. Strings, tables, functions, coroutines, vectors, bigints, and decimals are objects. Each object starts with a header that holds its type and the bits that the collector needs. Assigning a table to a second variable copies the 16-byte value, so both variables refer to one object.

The tag makes the common operations fast: to add two values, the interpreter and the compiled code compare two tags, then add two payloads. The payload of an integer is a full 64-bit integer. The payload of a float is a standard double precision number.

### String representation

A string is an immutable object that holds its text as bytes in the WTF-8 encoding. WTF-8 is UTF-8, the common encoding of Unicode text, extended to allow the unpaired surrogate code points that file names on Windows and text from JavaScript can contain, so Lus reads and writes such text unchanged.

A string is indexed by character, but a character takes one to four bytes in this encoding, so the byte position of the tenth character depends on the characters before it. The string object stores the following information to make indexing fast.

- The object stores its character count, so `#s` is a single read.
- The object records whether its text is pure ASCII, as most strings in most programs are. Every character of an ASCII string is one byte, so the byte position of a character follows directly from its index.
- A longer string with other characters receives a _character index_ the first time a program indexes it. The index records the byte position of characters at regular intervals, so finding a position takes one lookup and a short scan. It also stores the most recently found positions, so a loop that moves forward in a string, as a tokenizer does, continues from the stored position and scans no part of the string twice.

Short strings are _interned_: the runtime keeps a table of all interned strings, so creating a short string that already exists returns the existing object. Two interned strings are equal exactly when they are the same object, so comparing them compares two addresses, as does a table lookup with a short string key such as a field name. The hash of a string is computed once and stored in the object. A long string is created without interning, because a long text such as a line of a file is rarely created twice, so long strings are compared by hash and content.

Operations that build a long result, such as `table.concat` and the `..` operator, compute the final length first when it can be computed in advance. They then write the pieces directly into the new string.

### Table representation

A table has an array part for the keys 1 to `n` and stores its other keys in either a hash part or a shape. A program gets the same results from every form.

The _array part_ holds the values for the keys 1 to `n` in a contiguous block of memory, without the keys, because the position of a value gives its key. Reading `t[i]` is a bounds test and a load. The array part has a compact form for elements of one type: while every element is an integer, or every element is a float, a string, or a table, it stores 8-byte payloads and the common tag once. A list of numbers therefore takes half the memory of a list of full values. The collector skips such a list, because numbers refer to no objects. Storing a value of another type converts the array part to full 16-byte values.

The _hash part_ holds the other keys of a dictionary in an array of _nodes_, each with a key and a value. The number of nodes is a power of two. A lookup starts at the node that the hash of the key selects and, when that node holds another key, tries the following nodes in order. This scheme, called open addressing with linear probing, keeps a lookup inside one small region of memory. When the hash part is full, the runtime rebuilds it at a larger size.

A program that models data creates tables with named fields in large numbers, so the runtime optimizes them. The instruction for a constructor such as `{ x = 1, y = 2 }` carries the number of fields, so the runtime allocates room for exactly that many. A small table also keeps its parts in the same block of memory as the table object, so creating it takes a single allocation.

A table whose keys are all short strings, as most tables with named fields are, keeps its keys in a _shape_ and has no hash part. A shape is an ordered list of keys, shared by every table that received the same keys in the same order. The table itself stores only the values, one slot per key, so a million tables with the same fields store their field names once. Adding a key gives the table the shape that has its current keys followed by the new key. A table that receives a key of another kind, such as a long string or a table, becomes a dictionary with a hash part.

Field access rarely needs a search. Tables built by the same code share a shape, so the [inline cache](#the-interpreter) of an instruction such as `point.x` usually reduces the access to one comparison and one load.

A metatable also records which metamethods are absent from it. An access to a table whose metatable has no `__index` or `__newindex` therefore costs almost the same as an access to a table without a metatable.

### The interpreter

The _interpreter_ is a loop that reads one instruction per pass and runs the code for its operation. Every function starts in the interpreter, where code that seldom runs stays.

The registers of all active calls are in one array, the _stack_ of the running coroutine. Each call has a small record called a _frame_, which records which function is running, where its registers start, and where execution continues after the call returns. A call from one Lus function to another pushes a frame and continues in the same loop, so deep recursion uses the Lus stack, which grows in the heap. For the same reason, a coroutine can be suspended in the middle of any chain of calls.

A simple interpreter of a dynamic language does a lot of work for each instruction. To run `a + b`, it tests whether the operands are integers, floats, or values with an `__add` metamethod. To run `point.x`, it searches a table for the key `"x"`. _Quickening_ is a set of techniques that make an instruction cheaper by using facts about its place in the program. Lus uses the following techniques.

- A _specialized instruction_ is an instruction for one common case, which the code generator emits whenever the source allows it. For example, the code generator compiles the addition of a small constant to `addi`, the read of a field with a constant name to `getfield`, and a comparison with a constant to its own instruction. Each specialized instruction has a short path for the common case and uses the general code for every other case.
- _Fused instructions_ run two instructions in one step. Some pairs of instructions often occur together, such as the addition at the end of a loop body and the loop instruction after it. The compiler marks the first instruction of such a pair so that the interpreter runs both in one step.
- _Inline caches_ speed up access by name. Every instruction that reads or writes a field by name has a small record next to the code, called its _inline cache_, which stores the shape of the last table and the slot of the key in that shape. The next execution compares the shape, then loads the slot, so in nearly every case one comparison replaces a lookup. An inline cache also stores where a method was found in a class table.
- _Size feedback_ sets the initial size of new tables. The instruction that creates a table records how large its earlier tables became, so later tables from the same instruction are created at that size, which saves the cost of growing them step by step.

For an arithmetic instruction, the interpreter reads the type tags of the operands and runs a short path when both are integers or floats. Any other operand, such as a bigint, a decimal, or a table with a metamethod, leads to the general path.

Each prototype has a table that maps ranges of instructions to their handlers, which the runtime reads only when an error is raised. A `catch` therefore costs nothing until then.

### The baseline JIT

A _just-in-time compiler_, or JIT, translates bytecode into machine code while the program runs. Machine code avoids the work that the interpreter repeats for every instruction: fetching it, decoding its operands, and jumping to the code for its operation. Lus first compiles frequently run code with the _baseline JIT_, which is available for the aarch64 and x86-64 processors on macOS and Linux. On other systems, the program runs in the interpreter.

Compiling takes time, so the runtime compiles only code that runs often. It counts the calls of every function and the iterations of its loops. When the count passes a threshold, the function is _hot_, so the baseline JIT compiles it at once. A loop that is about to run many iterations is counted before it starts, so a script that consists of one long loop also runs as machine code. The switch happens in the middle of the running function: the interpreter stops between two instructions, then the machine code continues from the same point.

The baseline JIT translates one function at a time, one instruction at a time, in a single pass. For each instruction it emits one of the following.

- For the common cases of frequent instructions, it emits machine code that does the work directly. These cases include integer and float arithmetic, comparisons, a field read or write whose inline cache predicts correctly, an array access with an integer index, and a call to another compiled function.
- For everything else, it emits a call to the routine of the interpreter that implements that instruction.

These calls keep machine code consistent with the interpreter, whose loop and per-instruction routines are generated from one definition when the runtime is built. When the direct code reaches a case outside the common ones, such as an operand with a metamethod, it calls the routine, which runs the whole instruction. Metamethods, conversions, error messages, and coroutine switches therefore have a single implementation, so machine code and the interpreter produce the same results.

Baseline code uses the same frames as the interpreter and keeps every value where the interpreter keeps it, in the registers on the Lus stack. At every boundary between two instructions, execution can therefore move from the interpreter to baseline code or back. The garbage collector, tracebacks, the debug library, and coroutines read the same frames in both cases. While a debugger is attached, the program runs in the interpreter.

Machine code is stored in memory that the runtime requests from the operating system as executable. The garbage collector frees the code of a function together with the function. On a system that refuses executable memory, the program runs in the interpreter.

### The optimizing tier

Baseline code is fast to produce, but it does more work than necessary: it stores every intermediate result to the stack and tests the type of every operand on every execution. The _optimizing tier_ compiles code a second time, taking more time to produce faster code, when the code stays hot after the baseline JIT compiled it. Baseline code counts its own calls and loop iterations to detect this. The optimizing tier usually compiles a whole function, but when a loop inside a long-running function becomes hot, it compiles the code from that loop onward.

The optimizing tier compiles a function while the function is running, so it can read the values in the registers, the tables they refer to, and the inline caches of the interpreter. From these it predicts facts about each value, such as that a register holds an integer, that a table has its field `x` in a certain slot, or that a call always reaches the same function. It then produces machine code that is correct only when the predictions hold, with a _guard_, a short test of one prediction, before each use of a prediction.

Guarded code allows the following optimizations, which are unavailable to the baseline JIT.

- The optimizing tier keeps numbers in processor registers in _unboxed_ form, as the integer or float without its type tag. The compiled code writes a number to the Lus stack only when another part of the runtime reads it there.
- It represents the function in _static single assignment_ form, in which every value is assigned exactly once. This form shows the origin of each value, which makes standard optimizations possible, such as loading a table field that is read twice only once, moving a computation that gives the same result on every iteration before the loop, and removing results that nothing uses.
- For a counting `for` loop over an array, it checks once before the loop that every index lies inside the array. The loop body then loads elements without bounds tests.
- It compiles a small function into its caller, which removes the call. A call to a larger optimized function, or a recursive call, becomes a machine call that passes its arguments in processor registers. This applies when the called function needs no frame of its own while it runs.

A guard fails when its prediction is wrong for the current execution. The optimized code cannot continue, so the runtime _deoptimizes_: it writes every value from the processor registers to its place on the Lus stack, rebuilds the frames of the functions that were compiled into their callers, then continues in baseline code at the instruction that the guard belongs to. A guard is placed before its instruction has any effect, so the instruction runs from its start and every effect happens once. The only effect that a program can observe is the time that deoptimization takes.

The runtime records each failed guard. When the guard of one instruction fails repeatedly, the function is compiled again with the new information. If that guard keeps failing afterward, the instruction is compiled in its baseline form inside the optimized code, so one unpredictable operation leaves the rest of the function optimized.

The optimizing tier is consistent with the interpreter for the same reason as the baseline JIT. An instruction without a typed form in the optimizing tier is emitted with the translation of the baseline JIT. Every case that a guard rejects continues in baseline code, which calls the routines of the interpreter for its uncommon cases.

The environment variable `LUS_JIT` selects the compilers. It is `off` for the interpreter only, `baseline` to add the baseline JIT, or `on`, the default, to add both compilers. The setting changes only the speed of a program, so running with `LUS_JIT=off` is a useful test when a program behaves unexpectedly. [`debug.jit`](/manual/api#debug.jit) reports the setting and whether a given function has been compiled.

### The WebAssembly build

The runtime also compiles to a WebAssembly module, which runs Lus in browsers and in other WebAssembly hosts. The playground on the website and the Lus extension for Visual Studio Code use it. The module contains the same compiler, interpreter, and collector as the native runtime, without the network and worker libraries, which the WebAssembly environment cannot support.

A WebAssembly program cannot write machine code into its own memory and run it, so the WebAssembly build has its own baseline JIT, which produces WebAssembly. For each hot function it emits a small WebAssembly module and passes it to the JavaScript code that hosts the runtime. That code has the browser engine compile the module into machine code, then installs the compiled function where the runtime can call it. The translation follows the design of the native baseline JIT, with direct code for the common cases and a call to the routine of the interpreter for every other case.

A host that offers no way to compile modules, such as a plain command line WebAssembly runner, runs everything in the interpreter. [WebAssembly](/manual/webassembly) describes how to load and use the module.

### The garbage collector

The _garbage collector_ frees memory for the program by finding the objects that the program can no longer reach and reusing their memory. Its work has two phases. _Marking_ starts from the _roots_, which are the stacks, the globals, and a few internal tables, then follows every reference and marks each object that it reaches. _Sweeping_ then visits every object in the heap and frees the ones that are unmarked.

The rest of the runtime depends on the following properties of the Lus collector.

It is **precise**. Every value carries its tag, so the collector determines exactly which words of an object are references and always finds an unreachable object.

It is **non-moving**. An object stays at one address from its creation until it is freed, so machine code and inline caches can hold the addresses of objects. A C host can also hold a pointer to the contents of a string. The cost is that the heap cannot be compacted. The collector limits fragmentation by grouping objects of the same size into the same pages of memory, where a freed slot has exactly the size of the next object allocated there.

It is **generational**. Most objects, such as temporary strings, intermediate tables, and closures that are used once, become unreachable soon after they are created. The collector therefore divides objects into two generations: _young_ objects were created since the last collection, while _old_ objects have survived one. A _minor collection_ marks and sweeps only the young objects, so its cost depends on the number of young objects that survive, whatever the size of the heap. An object that survives becomes old. A _major collection_ examines the whole heap and runs much less often, when the old generation has grown enough.

A minor collection skips the old objects, so it needs a list of the old objects that refer to young ones, which the runtime builds while the program runs. Every store of a reference into an object runs a short test called a _write barrier_, which adds the object to the list when the object is old. The next minor collection traces the list. The interpreter and the code from both compilers run the same barrier.

It is partly **parallel**. Marking a large heap is the expensive part of a major collection. When a collection runs while the program is paused and has enough objects to mark, the collector divides the marking among several threads, each of which takes a share of the objects to trace and takes work from another thread once it has finished its share. A small heap is marked by one thread, because starting more threads would cost more time than it saves. Sweeping is _lazy_: after marking, the collector sweeps each page of the heap when the program next allocates from it, so the cost of sweeping is divided among the allocations that follow.

The amount of live data determines when the collector runs. After a collection, the collector measures the memory of the surviving objects, then starts the next collection when the heap has grown by a proportion of that amount. The option `--gc-pause` of `lus` sets the proportion, where a larger proportion uses more memory and less time. A major collection on a large heap can pause the program for a noticeable time, so for a program that must respond quickly, `collectgarbage("incremental")` selects a mode that marks in small steps between the steps of the program. The entry for [`collectgarbage`](/manual/api#collectgarbage) lists the controls.

The collector processes finalizers and weak tables at the end of marking. [Metatables and objects](/manual/guide#metatables-and-objects) describes both. An unreachable object with a `__gc` metamethod is kept for one more cycle so that its finalizer can run. Entries of weak tables that refer to unreachable objects are cleared.

### How coroutines run

A coroutine is an object with its own stack of registers and its own list of frames. Creating a coroutine allocates that object and a small stack, so a coroutine costs little memory and a program can have many thousands of them. The coroutine runs on the thread of its creator.

`coroutine.resume` switches the interpreter to the stack of the coroutine. `coroutine.yield` keeps every frame of the coroutine in place and returns control to the code that resumed it, so the next resume continues after the yield. A coroutine can yield at any depth of calls, because the interpreter and baseline code keep calls between Lus functions on the [Lus stack](#the-interpreter). Compiled code yields in the same way: a yield leaves machine code at a boundary between two instructions, where the resume enters the machine code again.

The _scheduler_ of the runtime resumes detached coroutines. It keeps a queue of coroutines that are ready to run, a list of deadlines for timeouts, and a _poller_. The poller is the facility of the operating system that reports which network connections have data to read or room to write, which is kqueue on macOS and epoll on Linux.

A detached coroutine is suspended inside the library functions that wait for the network. A function such as the `receive` method of a socket first tries to read without waiting. If no data has arrived, it registers the socket with the scheduler and suspends its coroutine with the mechanism of a yield. The scheduler runs other coroutines until the poller reports the socket as readable, then resumes the waiting coroutine, whose `receive` reads again and succeeds. To the Lus code that called `receive`, the call is an ordinary function call that returned a result.

The main program has no coroutine to suspend, so when it calls `receive`, the function runs the scheduler inside the call until its own socket is ready. The detached coroutines therefore continue to run while the main program waits. All coroutines of a state run on one thread, one at a time, with switches only at these waiting points and at explicit yields, which is why detached coroutines [share tables without locks](#results-errors-and-cancellation).

### How workers run

A worker runs Lus code on another thread of the processor, in parallel with its creator. Each worker has a complete runtime state of its own: its own heap, its own garbage collector, its own globals, and its own compiled code. Every object belongs to exactly one state.

Because of this separation, the rest of the runtime needs no locks. Tables, strings, inline caches, and the collector are written for a single thread. A collection in one worker runs while the other workers continue. The cost is that workers exchange data only as messages, in which each value is transferred in one of the following ways.

- Tables, numbers, booleans, and short strings are copied. The sender writes the value into a packet that belongs to no heap, from which the receiver rebuilds the value in its own heap. A table that is referenced several times within one message is rebuilt once, so the copy keeps the structure of the original, including cycles.
- A vector is moved: the receiver takes the buffer of the sender's vector without copying the bytes, which leaves the sender's vector empty.
- A long string is shared. Its bytes are kept once, outside both heaps, with a count of the states that refer to them. Sharing is safe because strings are immutable, so a large text passes between workers without a copy.

The threads that help with marking are shared by all states of a process. [Coroutines and workers](/manual/concurrency#workers) describes the worker library.

### Permission checks

The permission system is implemented entirely in the library functions that have effects outside the program, so the interpreter and the compilers contain no permission code. A function that opens a file, connects to a host, reads an environment variable, or starts a process calls one check immediately before the operation. The check receives the name of the permission, such as `fs:read`, together with the value concerned, such as the path of the file. Compiled code calls the same library functions as the interpreter, so every path to an operation includes the check.

Each state has a registry of the permissions that exist. An entry holds the name of a permission, the names of its parts such as `read` and `write`, and the kind of value it takes. The kind determines how a granted value is compared with a requested one: as a path, as a host, or as a pattern. Extensions written in C add their own permissions to the same registry and check them with the same call.

Each coroutine refers to a _permission set_, which holds the permissions that have been granted. A new coroutine shares the set of its creator, so creating a coroutine copies nothing. When a coroutine changes its permissions while other coroutines share its set, the runtime copies the set first, so the change applies to that coroutine only. A worker receives a sealed copy of the set of its creator, which can never be extended.

A check looks up the entry for the exact permission, then the entry for the permission that contains it, so a grant of `fs` includes `fs:read`. An entry that was granted without a value allows the operation. Otherwise the requested value must match one of the granted values. Paths are compared in a canonical form: the runtime resolves the symbolic links in a granted path when the grant is made and those in a requested path at each check. A link inside an allowed directory therefore cannot give access to a file outside it. A check that fails raises an error, which names the permission and the value, before the operation starts.

Sealing sets one flag in the set, after which every attempt to change the set is refused.
