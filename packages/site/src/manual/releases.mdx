A Lus release consists of prebuilt archives for six targets, a Windows installer, a WebAssembly module, the VSCode extension, and a checksum manifest. This page describes what each download holds, how to check a download, and how versions are numbered.

### Release channels

Releases come in two channels, and the strip above shows the latest release of each. The _stable_ channel holds the full releases, which a production deployment runs. The _unstable_ channel holds prereleases, whose tags carry a suffix such as `v2.0.0-rc.1`. A prerelease lets people try the next version before it becomes stable, and what it adds may still change. It ships every archive and `lus.wasm`, but not the VSCode extension. A manual page that documents a feature of the unstable channel says so at its top.

Every archive holds the `lus` interpreter, the embedding libraries, and the `lus.h` header, so the same download runs scripts and [embeds Lus](/manual/embedding) in a host program. The name of an archive contains the release tag and the target.

| Platform | Architecture | Archive |
| --- | --- | --- |
| Linux | x86_64 | `lus-vX.Y.Z-x86_64-linux-musl.tar.gz` |
| Linux | aarch64 | `lus-vX.Y.Z-aarch64-linux-musl.tar.gz` |
| macOS | x86_64 | `lus-vX.Y.Z-x86_64-macos.tar.gz` |
| macOS | Apple Silicon | `lus-vX.Y.Z-aarch64-macos.tar.gz` |
| Windows | x86_64 | `lus-vX.Y.Z-x86_64-windows.zip` |
| Windows | aarch64 | `lus-vX.Y.Z-aarch64-windows.zip` |

The Linux builds link musl statically, so the same `lus` binary runs on any Linux distribution of its architecture.

The `install.sh` script on Linux and macOS downloads the archive for the machine it runs on, checks it against `SHA256SUMS`, and installs `bin/lus`. On Windows, `lus-setup.exe` installs the contents of the x86_64 archive and puts `lus` on `PATH`. It installs for the current user by default, and `/ALLUSERS` from an elevated prompt installs it for every user.

## Archive layout

An archive unpacks into three directories.

- `bin/lus` is the interpreter. On Windows it is `bin/lus.exe`, and `bin/` also holds the shared library `lus.dll`.
- `lib/` holds the static and the shared embedding library. On Linux these are `liblus.a` and `liblus.so`, on macOS `liblus.a` and `liblus.dylib`, and on Windows the static `lus_static.lib` and `lus.lib`, the import library for `bin/lus.dll`.
- `include/lus.h` is the header of the [C API](/manual/api/c).

A host program on Linux or macOS builds against an unpacked archive like this.

```sh
cc -o host host.c -Ilus/include lus/lib/liblus.a
```

Each library includes the C code of SQLite, Zstandard, and Brotli, so a host links that one file.

## WebAssembly

The release also includes `lus.wasm`, the runtime built for `wasm32-wasi`. It exports every function of `lus.h`, as [WebAssembly](/manual/webassembly) describes, and it is the module that the [playground](/playground) runs.

## Checking download integrity

Each release includes `SHA256SUMS`, which lists the SHA-256 digest of every archive, of `lus-setup.exe`, of `lus.wasm`, and of the VSCode extension files. The following commands download the manifest and check the files in the current directory against it.

```bash
curl -LO https://github.com/lus-lang/lus/releases/latest/download/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
```

On macOS, `shasum -a 256 -c --ignore-missing SHA256SUMS` performs the same check.

A matching digest proves that the download is complete and is the file that the release lists. The manifest comes from the same GitHub release as the files, so the check does not prove who published the release. An environment that needs that proof pins the tag it expects and verifies the origin of the release by its own policy.

## How a release is made

Every release is built from a version tag by the continuous integration of the repository. The build runs the full test suite, including the conformance suite and the documentation examples, before it compiles any target. It then cross-compiles every archive, builds `lus.wasm` and the Windows installer, tests that the installer installs and uninstalls, and writes `SHA256SUMS`. The result becomes a draft release, which a maintainer reviews before publishing it.

## Versioning

Lus follows semantic versioning for its language, standard library, C API, and command line.

- A patch release contains compatible fixes, security updates, packaging corrections, or documentation corrections.
- A minor release adds compatible features and can deprecate older functions and options.
- A major release can make breaking changes.

A production deployment should run a published release and pin its version.
