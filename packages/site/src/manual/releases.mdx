A Lus release consists of prebuilt archives for six targets, a Windows installer, a WebAssembly module, the VSCode extension, and a checksum manifest.

### Release channels

Releases come in two channels. The download strip shows the latest release of each. The _stable_ channel holds the full releases. A production deployment runs a stable release. The _unstable_ channel holds prereleases. The tag of a prerelease has a suffix, as in `v2.0.0-rc.1`. A prerelease lets people try the next version before it becomes stable. The features that it adds may still change. A prerelease includes every archive and `lus.wasm`. It omits the VSCode extension. A manual page that documents a feature of the unstable channel says so at its top.

Every archive holds the `lus` interpreter, the embedding libraries, and the `lus.h` header, so the same download runs scripts and [embeds Lus](/manual/embedding) in a host program. The name of an archive contains the release tag and the target.

| Platform | Architecture | Archive |
| --- | --- | --- |
| Linux | x86_64 | `lus-vX.Y.Z-x86_64-linux-musl.tar.gz` |
| Linux | aarch64 | `lus-vX.Y.Z-aarch64-linux-musl.tar.gz` |
| macOS | x86_64 | `lus-vX.Y.Z-x86_64-macos.tar.gz` |
| macOS | Apple Silicon | `lus-vX.Y.Z-aarch64-macos.tar.gz` |
| Windows | x86_64 | `lus-vX.Y.Z-x86_64-windows.zip` |
| Windows | aarch64 | `lus-vX.Y.Z-aarch64-windows.zip` |

The Linux builds link musl statically, so the same `lus` binary runs on any Linux distribution of its architecture.

On Linux and macOS, the `install.sh` script downloads the archive for the machine it runs on and checks it against `SHA256SUMS`. It then unpacks the archive into `~/.lus/versions` and adds `~/.lus/bin` to `PATH` in the profile of the shell. On Windows, `lus-setup.exe` installs the x86_64 archive into `%LOCALAPPDATA%\lus` the same way and adds its `bin` directory to `PATH`. It installs for the current user by default. Run it with `/ALLUSERS` from an elevated prompt to install for every user.

Both installers lay the files out as [`lus version`](/manual/cli#lus-version) expects, so `lus version install` adds further releases beside the first one. `lus version` reads the signed release index at `https://lus.dev/releases/index.json`. It verifies the Ed25519 signature of the index and the SHA-256 digest of each archive before it installs anything.

## Archive layout

An archive unpacks into three directories.

- `bin/lus` is the interpreter. On Windows it is `bin/lus.exe`. On Windows `bin/` also holds the shared library `lus.dll`.
- `lib/` holds the static and the shared embedding library. On Linux these are `liblus.a` and `liblus.so`. On macOS they are `liblus.a` and `liblus.dylib`. On Windows `lib/` holds the static library `lus_static.lib` and `lus.lib`, which is the import library for `bin/lus.dll`.
- `include/lus.h` is the header of the [C API](/manual/api/c).

The following command builds a host program on Linux or macOS against an archive unpacked into `lus/`.

```sh
cc -o host host.c -Ilus/include lus/lib/liblus.a
```

Each library includes the C code of SQLite, Zstandard, and Brotli, so a host links that one file.

## WebAssembly

The release also includes `lus.wasm`, the runtime built for `wasm32-wasi`. It exports every function of `lus.h`, as [WebAssembly](/manual/webassembly) describes. The [playground](/playground) runs this module.

## Checking download integrity

Each release includes `SHA256SUMS`, which lists the SHA-256 digest of every archive, of `lus-setup.exe`, of `lus.wasm`, and of the VSCode extension files. The following commands download the manifest and check the files in the current directory against it.

```bash
curl -LO https://github.com/lus-lang/lus/releases/latest/download/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
```

On macOS, `shasum -a 256 -c --ignore-missing SHA256SUMS` performs the same check.

A matching digest proves that the download is complete and is the file that the release lists. The manifest comes from the same GitHub release as the files, so the check does not prove who published the release. An environment that needs that proof must pin the tag it expects and verify the origin of the release by its own policy.

## How a release is made

Every release is built from a version tag by the continuous integration of the repository. The build runs the full test suite, including the conformance suite and the documentation examples, before it compiles any target. It then cross-compiles every archive and builds `lus.wasm` and the Windows installer. It tests that the installer installs and uninstalls. Last, it writes `SHA256SUMS`. The result is a draft release. A maintainer reviews the draft before publishing it.

## Versioning

Lus follows semantic versioning for its language, standard library, C API, and command line.

- A patch release contains compatible fixes, security updates, packaging corrections, or documentation corrections.
- A minor release adds compatible features and can deprecate older functions and options.
- A major release can make breaking changes.

A production deployment should run a published release and pin its version.
