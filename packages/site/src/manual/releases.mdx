Lus publishes stable releases for production use and unstable prereleases for compatibility testing against current development.

## Downloads

<ReleaseStrip />

Release archives contain the `lus` interpreter, `lusc` compiler, embedding SDK, package metadata, build metadata, and artifact-specific license notices. The SDK includes the complete public header set and separate Lus and SQLite static libraries. WASM, site, and VSIX artifacts carry their own redistributed-component license inventories. Compatibility assets provide individual executables for the installer and existing download links.

| Platform | Architecture | Primary archive | Compatibility assets |
| --- | --- | --- | --- |
| Windows | x64 | `lus-VERSION-windows-x64.zip` | `lus-windows.exe`, `lusc-windows.exe`, `lus-setup.exe` |
| macOS | Apple Silicon | `lus-VERSION-macos-arm64.tar.gz` | `lus-macos`, `lusc-macos` |
| Linux | x64, glibc | `lus-VERSION-linux-glibc-x64.tar.gz` | `lus-linux`, `lusc-linux` |
| Linux | x64, musl | `lus-VERSION-linux-musl-x64.tar.gz` | `lus-linux-musl`, `lusc-linux-musl` |

Source builds can also target FreeBSD, OpenBSD, NetBSD, DragonFlyBSD, SunOS, and other compatible systems. [Compiling Lus](/manual/compiling) describes that path. The release evidence and production support commitment cover only the platforms listed in the table.

## Checking download integrity

Each release includes `SHA256SUMS`. The Unix installer checks both `lus` and `lusc` against this manifest before installation. A manual download can be checked in the same way.

```bash
curl -LO https://github.com/lus-lang/lus/releases/latest/download/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
# macOS uses: shasum -a 256 -c SHA256SUMS
```

The digest detects corruption and a mismatch between an asset and its release manifest. The manifest and assets come from the same GitHub release and are not independently signed, so this check alone does not authenticate the publisher or protect against a compromised release account or origin. Environments that require publisher authentication should pin an expected tag and verify release provenance through their own trusted policy before using the assets.

## Release evidence

Every complete release bundle carries `release-evidence.json` and `SHA256SUMS`. The quality gate requires all configured jobs before the bundle is assembled. Evidence covers these surfaces.

- Runtime tests on Linux glibc, Linux musl, macOS arm64, and Windows x64.
- Build toolchains on those four platforms plus WebAssembly.
- Repository lint, address and undefined-behavior sanitizers, focused benchmarks, the VS Code extension, the website, and both installers.
- The exact commit, dependency versions, toolchain versions, assets, and licenses used for the build.

This evidence records what ran and whether it passed. It gives each release a reviewable qualification record without describing the test harness as exhaustive.

## Stable releases

A `vVERSION` tag starts the complete quality gate. After every required job passes, automation assembles and verifies the assets and creates a GitHub draft release for that exact tag. A maintainer reviews the draft, its evidence, and its inventory before explicitly publishing it. Tag creation alone does not publish a stable release.

Lus follows semantic versioning for its public language, standard library, C API, command-line, package, and supported artifact contracts.

- A patch release carries compatible fixes, security updates, packaging corrections, or documentation corrections.
- A minor release adds compatible features and can deprecate older surfaces.
- A major release can make breaking contract changes.

Production deployments should use a reviewed stable release and pin the version according to their update policy.

## Unstable releases

A successful complete build from `main` creates an `unstable-SHA` prerelease for that exact commit. It contains the same asset inventory and evidence format as a stable candidate. Unstable releases can change compatibility and behavior before the next stable release, so they are intended for development, integration testing, and early feedback.

Testing an application against the latest unstable prerelease is a direct way to discover upcoming compatibility changes while the stable deployment remains pinned.
