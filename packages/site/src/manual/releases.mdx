Each Lus release ships prebuilt archives for six targets, a Windows installer, a standalone WebAssembly module, the VSCode extension, and a checksum manifest.

## Downloads

<ReleaseStrip />

Every archive holds the `lus` interpreter together with the embedding libraries and the `lus.h` header, so one download serves both running scripts and [embedding Lus](/manual/api/c) in a C program. Archive names carry the release tag and the target.

| Platform | Architecture | Archive |
| --- | --- | --- |
| Linux | x86_64 | `lus-vX.Y.Z-x86_64-linux-musl.tar.gz` |
| Linux | aarch64 | `lus-vX.Y.Z-aarch64-linux-musl.tar.gz` |
| macOS | x86_64 | `lus-vX.Y.Z-x86_64-macos.tar.gz` |
| macOS | Apple Silicon | `lus-vX.Y.Z-aarch64-macos.tar.gz` |
| Windows | x86_64 | `lus-vX.Y.Z-x86_64-windows.zip` |
| Windows | aarch64 | `lus-vX.Y.Z-aarch64-windows.zip` |

The Linux builds link musl statically, so the same `lus` binary runs on any Linux distribution of its architecture.

The `install.sh` script on Linux and macOS downloads the archive for the machine it runs on, checks it against `SHA256SUMS`, and installs `bin/lus`. On Windows, `lus-setup.exe` installs the contents of the x86_64 archive and puts `lus` on `PATH`. It installs for the current user by default, and `/ALLUSERS` from an elevated prompt installs it for every user.

## Archive layout

An archive unpacks into three directories.

- `bin/lus` is the interpreter. On Windows it is `bin/lus.exe`, and `bin/` also holds the shared library `lus.dll`.
- `lib/` holds the static and the shared embedding library. On Linux these are `liblus.a` and `liblus.so`, on macOS `liblus.a` and `liblus.dylib`, and on Windows the static `lus_static.lib` and `lus.lib`, the import library for `bin/lus.dll`.
- `include/lus.h` is the header of the [C API](/manual/api/c).

A host program on Linux or macOS builds against an unpacked archive like this.

```sh
cc -o host host.c -Ilus/include lus/lib/liblus.a
```

Each library carries the vendored C code of SQLite, Zstandard, and Brotli, so a host links that one file.

## WebAssembly

The release also includes `lus.wasm`, the runtime built for `wasm32-wasi`. It exports every function of `lus.h`, as [WebAssembly](/manual/webassembly) describes, and it is the same module that powers the [playground](/playground).

## Checking download integrity

Each release includes `SHA256SUMS`, which lists the SHA-256 digest of every archive, of `lus-setup.exe`, of `lus.wasm`, and of the VSCode extension files. A download is checked against it with `sha256sum`.

```bash
curl -LO https://github.com/lus-lang/lus/releases/latest/download/SHA256SUMS
sha256sum -c --ignore-missing SHA256SUMS
```

On macOS, `shasum -a 256 -c --ignore-missing SHA256SUMS` performs the same check.

The digest detects corruption and any mismatch between an asset and the manifest of its release. The manifest and the assets come from the same GitHub release, so the check confirms consistency within that release. Environments that require publisher authentication pin an expected tag and verify the provenance of the release through their own trusted policy.

## How a release is made

Pushing a tag such as `v2.0.0` starts the release workflow. The workflow first confirms that the tag matches the version in `runtime/build.zig.zon`. It then runs the unit, embedding, bundle, check, and documentation tests along with the conformance suite and the language server tests. When they pass, it cross compiles every target from one runner with Zig, builds `lus.wasm`, and packages the VSCode extension with the Open VSX publisher that later uploads it. A Windows runner then compiles `lus-setup.exe` from the x86_64 archive and installs and uninstalls it as a smoke test. The last step writes `SHA256SUMS` over every asset.

The workflow publishes the result as a draft GitHub release titled after the version, with `CHANGELOG.md` as its notes. A maintainer reviews the draft and its assets and then publishes it.

## Versioning

Lus follows semantic versioning for its language, standard library, C API, and command line.

- A patch release carries compatible fixes, security updates, packaging corrections, or documentation corrections.
- A minor release adds compatible features and can deprecate older surfaces.
- A major release can make breaking changes.

Production deployments use a published release and pin its version according to their update policy.
