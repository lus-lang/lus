`lus test` is the test runner built into the interpreter. A test is a function whose name ends in `_test`, inside a file whose name ends in `_test.lus`. The runner needs no library and no configuration: it finds the files, runs every file in its own process, and reports each test.

## Writing tests

A test file is an ordinary Lus file. Its top-level code runs once as setup, and every top-level function whose name ends in `_test` is a test. A test passes when it returns and fails when it raises an error.

```lus
-- math_test.lus
local function add(a, b) return a + b end

function add_test()
    assert(add(2, 2) == 4)
end

local function negative_test()
    assert(add(-1, -1) == -2)
end
```

Both global functions and local functions count, so test files can keep their helpers and tests local. Tests run in the order they appear in the file.

## Running tests

`lus test` with no argument searches the current directory recursively for `*_test.lus` files. Arguments name files or directories to search instead. A file named on the command line runs whatever its name. The search skips the directories `node_modules`, `.git`, `zig-out`, `.zig-cache`, and `legacy`.

```sh
lus test                     # every *_test.lus below the current directory
lus test tests/parser        # one directory
lus test math_test.lus -v    # one file, listing every test
```

Each file runs in its own child process inside a fresh temporary directory, and the files run in parallel. A crash, a leaked global, or a file written by one test file never affects another. The runner prints one line per file, the failures with their messages and the output the file printed, and a summary.

```
FAIL ./math_test.lus (5 passed, 1 failed, 1 skipped, 2 ms)
  FAIL power_test
       math_test.lus:15: assertion failed: add(x, 1) == 5
         left:  4
         right: 5
  skip slow_test: needs the network

1 files, 5 passed, 1 failed, 1 skipped
```

The options are the following.

| Option | Effect |
| --- | --- |
| `-v` | List the skipped tests and the output of passing files too. |
| `--filter TEXT` | Run only the tests whose names contain `TEXT`. |
| `-u`, `--update` | Rewrite snapshots that no longer match. |
| `--json` | Print one JSON record per test with the fields `status`, `name`, and `message`. |
| `--jobs N` | Run at most `N` files at once. The default is the number of processors. |
| `--timeout S` | Stop a file that writes no output for `S` seconds. The default is 60. |
| `--file-timeout S` | Stop a file that runs longer than `S` seconds in all, even while it writes output. The default is ten times the timeout. |

The exit status is 0 when every file passes and 1 when a test fails, a file crashes, or a file times out.

## Power asserts

Inside a test file, `assert` reports the expression that failed together with the values of its operands. A comparison shows both sides, and any other expression shows its value.

```lus
local function area(w, h) return w * h end

function area_test()
    local w, h = 3, 4
    assert(area(w, h) == 13)
end
```

The failure reads as follows.

```
FAIL area_test
     area_test.lus:5: assertion failed: area(w, h) == 13
       left:  12
       right: 13
```

The runner rewrites the `assert` calls of the test file itself, so modules under test keep the standard `assert`.

## Case tables

A local table named `NAME_cases` runs `NAME_test` once per entry. An entry that is a table supplies its array items as the arguments, and any other entry is passed as the single argument. The runner names each run after its position, as in `add_test[2]`.

```lus
local function add(a, b) return a + b end

local add_cases = {
    { 1, 2, 3 },
    { -1, 1, 0 },
    { 0.5, 0.25, 0.75 },
}

local function add_test(a, b, want)
    assert(add(a, b) == want)
end
```

## Helpers

Test files get four helper functions as globals.

- `raises(f, pattern, ...)` calls `f(...)` and fails the test unless the call raises. With a `pattern`, the error message must match it. It returns the error value for further checks.
- `same(a, b)` compares two values structurally and returns a boolean. Tables are equal when they hold equal keys with equal values, nested tables included, and cycles are handled.
- `skip(reason)` stops the current test and records it as skipped with the reason.
- `snapshot(value)` compares a value with its recorded snapshot.

```lus
function parse_test()
    local err = raises(function() fromjson("{") end, "parse error")
    assert(type(err) == "string")
    assert(same(fromjson("[1, [2, 3]]"), { 1, { 2, 3 } }))
end

function network_test()
    skip("needs the network")
end
```

## Snapshots

`snapshot(value)` renders the value as Lus source and compares it with the recording in `__snapshots__/FILE.snap` beside the test file. The first run records the snapshot. A later run that renders something different fails and shows both versions, and `lus test -u` accepts the new rendering. Several snapshots in one test are numbered in order, and the snapshot files are plain text meant to be committed with the tests.

```lus
function config_test()
    snapshot({ name = "app", ports = { 80, 443 } })
end
```

The recorded file reads as follows.

```
== config_test #1
{name = "app", ports = {80, 443}}
```

## Fixtures and permissions

Each test file runs inside a fresh temporary directory, so tests can create and delete files freely. The global `TEST_DIR` names the directory that holds the test file, which is where fixtures live. The environment variable `LUS_EXE` names the interpreter running the tests, for tests that start a child interpreter with `io.popen` or `os.execute`.

A test file starts with no permissions and pledges the ones it needs, exactly like a script. Each test starts from the permissions the file holds after its setup code, and the pledges a test makes are undone when it ends, so tests stay independent of one another.

```lus
pledge("fs:read")

function fixture_test()
    local f <close> = io.open(`$TEST_DIR/fixtures/input.txt`)
    assert(f:read("l") == "first line")
end

function env_test()
    pledge("env")
    assert(os.getenv("LUS_EXE") ~= nil)
end
```

## Motivation

### Tests without a framework

A test runner in the interpreter means every Lus project can write tests the moment it exists. The conventions are names, so a test file is plain Lus that the language server, the formatter, and `lus check` understand without any special support.

### Isolation and speed

Running each file in its own process and directory makes tests independent by construction. A test that changes globals, writes files, or crashes the interpreter affects only its own file, and the files run in parallel on every processor.

### Useful failures

A failed assertion reports the values that made it fail, a case table names the case that failed, and a snapshot mismatch shows the expected and the actual rendering side by side. Most failures can be understood from the report alone.
