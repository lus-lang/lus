The WebAssembly build runs Lus in places where the native `lus` executable cannot run, such as a web page, a web worker, or a JavaScript application. With it, a web page can run Lus code that its visitors type. A tool can ship one build of Lus that runs on every platform. A JavaScript program can use Lus as its scripting language.

The Lus runtime compiles to a WebAssembly module for the target `wasm32-wasi`. The `lus-wasm` package contains the module and a small JavaScript host. The host loads the module and runs programs in browsers, web workers, and Node. The [playground](/playground) and the [VS Code extension](/manual/ide-setup) both use this package, so they run the same runtime as the native interpreter.

## The module

Each [release](/manual/releases#webassembly) includes the module as `lus.wasm`. To build it from source, run the `wasm` step, which compiles the same Zig sources as the native interpreter.

```sh
cd runtime
zig build wasm
```

The build writes `zig-out/wasm/lus.wasm`. It keeps the safety checks of a ReleaseSafe build, because the playground runs code from strangers and a failed check must stop the program in a defined way. `-Dwasm-optimize=small` produces a smaller module without the checks.

The module is a _WASI reactor_. A reactor exports functions for its host to call and has no `main` function. The module exports every function of the [embedding interface](/manual/embedding) in `lus.h`, a few helpers for the JavaScript host, and its memory. Its only imports are WASI functions, so any WASI runtime, such as wasmtime, can load it.

The module includes SQLite and the [`vector.archive`](/manual/text#compression) codecs. WASI provides neither sockets nor threads, so the module has no `network` and no `worker` library. It cannot start processes either, so `io.popen` and `os.execute` raise an error that ends in `not available on this platform`.

## Running programs

`Lus.load` compiles the module and returns a _host_, which is the JavaScript object that runs Lus programs. In a browser or a worker, `Lus.load` takes the module as bytes, a compiled `WebAssembly.Module`, a `Response`, or a URL. In Node, `loadLus` from `lus-wasm` reads the packaged module from disk. The following page script loads the module from a URL and runs a program that prints the Lus version. The comment shows the result of the run.

```js
import { Lus } from "lus-wasm/browser";

const lus = await Lus.load(new URL("/wasm/lus.wasm", location.href));
const result = lus.run('print("hello from " .. _VERSION)');
// { ok: true, stdout: "hello from Lus 2.0\n", stderr: "", output: "hello from Lus 2.0\n",
//   error: null, traceback: null, exitCode: 0, truncated: false }
```

`run(source, options)` runs a whole program in a new state and closes the state afterwards. The variables of one run are therefore gone before the next. Like the `lus` command, `run` returns only after every coroutine that the program detached has ended. `run` accepts the following options.

| Option | Meaning |
| --- | --- |
| `args` | Arguments, passed to the program as `...` and in `arg`. |
| `pledges` | [Permissions](/manual/permissions) granted by the host, as with `lus -P`. |
| `stdin` | The bytes that `io.read` returns. |
| `files` | Files written to the file system before the run. |
| `chunkname` | The chunk name used in messages. The default is `"=(playground)"`. |
| `maxOutputBytes` | Stops capturing output after this many bytes, which protects a page from a program that prints without end. |

The result has the following fields.

| Field | Meaning |
| --- | --- |
| `ok` | `true` when the program finished without an error and exited with status 0. |
| `stdout`, `stderr` | Standard output and standard error. |
| `output` | Standard output and standard error interleaved in write order. |
| `error` | The error message, or `null`. |
| `traceback` | The stack traceback of the error, or `null`. |
| `exitCode` | 0, 1 after an error, the status given to `os.exit`, or 134 after a trap. |
| `truncated` | `true` when the output went past `maxOutputBytes`. |

When the program raises an error, `run` returns normally and describes the error in the result.

```js
const r = lus.run('error("boom")');
// r.ok === false, r.exitCode === 1, r.error === "(playground):1: boom"
// r.traceback === "stack traceback:\n\t[C]: in global 'error'\n\t(playground):1: in main chunk\n\t[C]: in ?"
```

## Files and environment

A program in a browser has no disk, so the host provides a file system that exists only in memory. JavaScript code writes files to it before a run. After the run, it reads the files that the program wrote. One host holds any number of states. All of them share the file system and one set of environment variables.

`lus.fs` is the file system. Its methods `writeFile`, `readFile`, `exists`, `readdir`, `mkdir`, and `remove` operate on single files and directories. `mount` writes a whole set of files under a path prefix. `lus.env` holds the environment variables. A Lus program reads them with `os.getenv`, which requires the `env` permission. A Lus program opens the files with the `io` and `fs` functions, which require the same [permissions](/manual/permissions) as on a real disk. The following script writes a file from JavaScript. The Lus program then reads the file and prints each line with its length.

```js
lus.fs.writeFile("/data.txt", "one\ntwo\n");
const r = lus.run(`for line in io.lines("/data.txt") do print(#line, line) end`, {
  pledges: ["fs:read=/data.txt"],
});
console.log(r.output); // "3\tone\n3\ttwo\n"
```

`Lus.load` takes an optional second argument, which is an object with three fields. `fs` is a file system to share between hosts. `env` holds the initial environment variables. [The JIT](#the-jit) describes `jit`.

The host implements WASI in JavaScript and has no dependencies. It captures standard output and standard error, supplies standard input, and keeps files in memory with `/` as the only preopened directory. It also provides the environment variables, the clocks, random numbers, and sleeping. In Node and in web workers, a sleep blocks the thread with `Atomics.wait`.

## Long-lived states

An interactive console needs a state that keeps the variables of earlier inputs. `create(options)` returns such a state, with the standard libraries open. The state keeps its globals between calls. `destroy(state)` closes it. The option `pledges` grants permissions to the state. `execute(state, code)` runs one input as the playground does. If the input is an expression, `execute` prints its values. Any other input runs as a chunk. `execute` returns the output followed by any error message, limited to 256 KiB. Like `run`, `execute` returns only after the detached coroutines have ended. The following code assigns a global in one input and reads it in the next.

```js
const state = lus.create();
lus.execute(state, "x = 10");   // ""
lus.execute(state, "x * 2");    // "20\n"
lus.destroy(state);
```

The language server of Lus is written in Lus, so a state can run it. An editor in a browser gets completions and diagnostics this way. `loadLsp(state, source)` loads the server. It returns an empty string on success and an error message on failure. `handleMessage(state, json)` processes one JSON-RPC body. `handleFrame(state, frame)` processes one complete `Content-Length` frame. Both return the framed responses as a string. The VS Code extension runs the server with these functions and needs no native `lus`. In Node, `mountLanguageServer(lus, dir)` copies the language server sources into the file system of a host.

`lus.exports` contains every function of `lus.h`, for hosts that call the C interface directly.

## Exits and traps

A WebAssembly instance cannot continue after the program calls `os.exit` or after a safety check fails. WebAssembly calls such a failure a _trap_. `lus.dead` is `true` after either event. On the next call, the host starts a new instance with the same file system. Every state of the earlier instance is then invalid. `run` reports a trap as an error with exit code 134. The other calls throw a JavaScript exception.

## The JIT

The native runtime compiles the functions that run often to machine code. A WebAssembly module cannot generate machine code, so the WebAssembly build compiles those functions to WebAssembly, which the JavaScript engine then compiles to machine code. The runtime emits a small module for each such function. The host compiles the module and adds its function to the function table of the runtime. A module of up to 4 MiB compiles immediately. A larger module compiles in the background while the interpreter keeps running the function. `lus.jit` holds the statistics of the compiler. It is `null` when the options of `Lus.load` turned the JIT off or when the module was built without one.

The variable `LUS_JIT` in `lus.env` sets the JIT mode of each state, as the environment variable of the same name does for the native runtime. The default is `on`. `off` interprets every function. `eager` compiles every function on its first call. `LUS_JIT_THRESHOLD` sets the number of times a function runs before it compiles. The option `jit: false` of `Lus.load` creates a host without a compiler, so the module interprets every function.
