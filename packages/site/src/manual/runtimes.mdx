Lus is a dynamic language for complete programs: scripts, command line tools, and network services. The benchmarks compare Lus with other runtimes that are used for the same kinds of programs. The design choices that produce the results each have a cost.

## Benchmark results

The benchmark suite holds the following programs and an HTTP server. Each program is written once per language, in the usual style of that language and with its standard library wherever the library covers the task. Every version generates the same input and does the same work.

| Program | What it does |
| --- | --- |
| `csv` | Parses two million generated rows of CSV text and totals the quantity and revenue of each region. |
| `json` | Encodes one million records as JSON, then decodes the text and sums fields of the result. |
| `logs` | Parses one million generated web server log lines with one pattern and counts the requests for each status code and each path. |
| `lru` | Simulates four million requests to a cache of 50,000 entries that evicts the entry used least recently. |
| `template` | Renders an HTML report of one million items, escaping every title and tag. |
| `wordfreq` | Counts how often each word occurs in a text of ten million words, then sorts the words by count. |

The tables show one run of the suite, so their figures change with every new run. The best value of each row is in bold.

## Design choices

The results follow from a few decisions about the language and the runtime. Each decision gives a program something and costs it something.

### A small language

Lus uses the syntax of Lua and has one data structure, the table, which a program uses as an array, a dictionary, a record, an object, or a module. A program therefore has few constructs to learn and to read.

The cost is that Lus leaves out constructs that larger languages provide. Lus has no class syntax, so objects and inheritance are built from tables and metatables. Lus has no static type annotations, so types are checked when the program runs.

### One executable with a large standard library

The `lus` executable contains the whole standard library: JSON, CSV, SQLite, HTTP clients and servers, sockets, the filesystem, compression, and time zones. The same executable formats, checks, tests, documents, debugs, and bundles programs. A program that uses only the standard library depends on that one executable, so it has no packages to download and no versions to reconcile.

Much of the speed in the tables comes from the standard library. The JSON and CSV parsers and the string functions are part of the runtime and are compiled with it, so a program that spends its time in them runs compiled library code.

This choice has costs. The executable contains code for formats that a given program never uses. Functionality that the standard library lacks has to be written in Lus, or written in a host program and registered with the C interface.

### Concurrency with coroutines and workers

A Lus function that reads from a socket is written like any other function. Inside a [detached coroutine](/manual/concurrency#detached-coroutines), a read from a socket suspends the coroutine until data arrives, then the runtime resumes it. The same function runs unchanged in the main program, in a coroutine, and in a detached coroutine, so functions need no `async` marker and a library is written once. `network.fetch` waits for one response at a time, so a program that sends several requests at once sends them from workers. The HTTP server in the benchmark runs every connection as a detached coroutine on a single thread. It stays small under load because a suspended coroutine holds little memory.

Parallel work runs in [workers](/manual/concurrency#workers). Each worker is a separate instance of the runtime on its own thread, with its own memory and its own garbage collector. Workers exchange messages and share no data, so they need no locks. A garbage collection in one worker never pauses another worker.

Both have costs. Detached coroutines on one thread run one at a time, so a long computation with no wait in it delays every other coroutine on that thread. Workers communicate only by messages, in which the runtime copies most values from one worker to another. A server that handles requests on one thread also uses one processor core, so a runtime that spreads requests over several threads or processes can answer more requests per second.

### Compact memory layout

The runtime stores data compactly. Integers and floats are stored directly in the variable or table slot that holds them, so arithmetic allocates nothing. An array whose elements are all integers, all floats, all strings, or all tables takes less memory than an array of mixed values. A small table keeps its fields in the same block of memory as the table itself. Records with the same string keys share one list of those keys, called a _shape_, so each record stores only its values. A short string that occurs many times, such as a field name, is stored once.

The generational garbage collector collects recently created objects often and long-lived objects rarely, so a program that holds a steady amount of data stays close to the size of that data. The collector never moves an object, so the pointers that a host program holds stay valid.

The cost of a collector that never moves objects is fragmentation, because free space scattered between live objects stays part of the memory of the program until new objects of the same size fill it.

### The interpreter and the compilers

Lus starts a program in an interpreter, so the program begins running at once. A baseline compiler compiles a function that runs often to machine code in a single fast pass. Code that keeps running is compiled a second time by an optimizing compiler, which predicts the types of values from what the program has done so far and keeps numbers in processor registers. The interpreter and the compilers run every instruction from one shared definition, so a program behaves the same in each of them.

The cost is that compilation takes time and memory while the program runs, so a short script gains little from it. The compilers produce code for 64-bit ARM and x86 processors on macOS and Linux. The WebAssembly build has its own compiler. On every other target Lus runs in the interpreter alone.

Lus interprets its patterns. A program that spends most of its time matching one pattern, such as `logs`, therefore depends on the speed of the pattern interpreter more than on the compilers.

### Permissions

A Lus script starts with no access to files, the network, other processes, or environment variables until it calls [`pledge`](/manual/permissions) with the name of a permission, such as `fs:read` for one directory. The person who runs the script can also grant a permission on the command line. A program can seal its permissions, after which nothing it loads or runs can acquire more. A mistake or a compromised dependency can therefore affect only what the program was granted.

The cost is a line or two in every program that uses files, the network, other processes, or the environment. Each such operation checks its permission when it runs and raises an error if the permission is missing.

### Embedding

Lus can run inside another program, which links one library, creates an instance of the runtime, and calls the functions of a C interface to exchange values with the instance, as [Embedding](/manual/embedding) describes. The host chooses the permissions that its scripts receive and the host functions that they may call.

The cost falls on the host, which passes values to an instance one at a time by pushing them on a stack. That takes more code than calling a function of the host language directly. The host must also call into each instance from one thread at a time.

## How the measurements are made

The programs and the harness are in the Lus repository under `tests/bench/compare`, with one directory per program and one file per language. Every program prints one line with its name and a checksum of its result. Before it times anything, the harness runs each program at a small size on every runtime and compares the lines. A runtime that prints a different line is reported and left out of the timing for that program.

Lus runs with its default settings in a build made with `zig build -Doptimize=ReleaseFast`, as the release archives are. Ruby runs with `--yjit` and PHP with opcache and its tracing JIT enabled. The other runtimes run with their defaults. The timed runs alternate between the runtimes, so background activity on the machine affects all of them alike. Each cell shows the fastest of several runs and the peak memory of that run, as the operating system reports it.

For the HTTP table, the harness starts each server, checks its answers, warms it up, then loads it with the `oha` load generator. The first column of the table names the standard library server that each runtime uses. A row that gives only the name of a runtime is a small HTTP server written on the standard socket library of that language. The results file in the same directory records the machine, the operating system, and the version of every runtime, which the first table under [Benchmark results](#benchmark-results) lists.
