The `lus` executable includes the tools that a project needs besides the interpreter: a formatter, a checker, a documentation generator, a bundler, a debugger, and the library reference. A project installs nothing else, so every member of a team runs the same version of each tool. Each tool uses the parser of the interpreter, so it accepts exactly the programs that the interpreter accepts and reports positions as the compiler does. The [CLI page](/manual/cli) lists the options of every command. [Testing](/manual/testing) describes `lus test`.

The commands are the following.

```
lus fmt      format source files
lus check    check source files for errors and lint warnings
lus doc      generate API documentation from doc comments
lus ast      print the syntax tree of a file as JSON
lus build    bundle a script into a standalone executable
lus compile  compile a script to a binary chunk
lus debug    run a script under the Debug Adapter Protocol
lus help     print the standard library reference for a name
lus agents   set a project up for coding agents
```

## Files, input, and exit status

`lus fmt` and `lus check` accept files and directories. For a directory, they process every `.lus` file inside it and inside its subdirectories, except the files in a directory named `node_modules`, `.git`, `zig-out`, or `.zig-cache`. With no file, or with the file `-`, both read standard input. `lus doc` and `lus ast` take file names only.

The tools use the same exit statuses, so a script or a continuous integration job can test the status of any of them. The status is 0 on success. It is 1 when the tool reports a problem in the input, such as a syntax error, an unformatted file, or a diagnostic. It is 2 for a usage error or a file that cannot be read.

## Formatting

`lus fmt` gives every file of a project the same layout, so nobody formats by hand and a diff shows only the changes to the code. With no option, it prints the formatted text of each file to standard output. `--write` rewrites in place the files that change. `--check` changes nothing but lists each file that is not formatted as `FILE: not formatted`, then exits with status 1 if it listed any, so a continuous integration job can reject unformatted code. `--indent N` sets the width of one indentation level, which is 4 spaces by default.

```sh
lus fmt --write src
lus fmt --check src
```

When a file does not parse, the formatter leaves it unchanged, reports the syntax error, and exits with status 1. [`debug.format`](/manual/api#debug.format) runs the same formatter from Lus code.

## Checking

`lus check` finds mistakes before a program runs. Without it, a misspelled variable or an assignment to an undeclared global is found only when its line runs, which may be rare. The command parses, lints, and compiles each file without running it and prints each problem as `file:line:column: severity: message [code]`, where the code names the diagnostic. The following file has two problems.

```lus
local unused = 1
local function area(w, h)
    return w * h
end
total = area(4, 5)
```

`lus check` reports them as follows.

```
messy.lus:1:7: warning: unused local 'unused' [unused-local]
messy.lus:5:1: warning: global 'total' is assigned without a 'global' declaration [implicit-global]
```

An _error_ is a problem that makes the compiler reject the file, such as an assignment to a constant, a `goto` without a visible label, or a `continue` outside every loop. A _warning_ is code that runs but probably does not do what its author meant, such as an unused local, a shadowed name, or unreachable code. A _hint_ suggests a faster or shorter form of correct code, such as `ipairs` for a table built as a list. A variable whose name starts with an underscore is exempt from the unused checks, so use such a name for a variable that is unused on purpose. The exit status is 1 when `lus check` reports an error or a warning. Hints alone leave it at 0, so a build that runs `lus check` never fails on a hint. The language server shows the same hints in the editor, and [`debug.check`](/manual/api#debug.check) returns every diagnostic to a program.

### Diagnostic codes

Every diagnostic has a code that stays the same between releases, so a tool can filter on it. `lus check --list` prints each code with its severity and summary. The codes are the following.

| Code | Severity | Reports |
| --- | --- | --- |
| `unused-local` | warning | A local variable is never read. |
| `unused-function` | warning | A local function is never used. |
| `unused-param` | warning | A function parameter is never read. |
| `unused-loop-var` | warning | A loop variable is never read. |
| `unused-label` | warning | No `goto` jumps to a label. |
| `shadowed-local` | warning | A local hides another visible local of the same name. |
| `undefined-global` | warning | A free name is read but never defined in the file nor by the runtime. |
| `implicit-global` | warning | A global is assigned without a `global` declaration. |
| `unreachable-code` | warning | A statement follows a `break`, `continue`, or `goto` in the same block. |
| `duplicate-key` | warning | A table constructor sets the same constant key twice. |
| `self-assign` | warning | A variable or field is assigned to itself. |
| `deprecated-pcall` | warning | `pcall` or `xpcall` is used where Lus has `catch`. |
| `pledge-after-seal` | warning | A `pledge` follows `pledge("seal")` and has no effect. |
| `use-from` | hint | Fields of one table are copied into same-named locals one by one. |
| `use-optional-chain` | hint | Nested nil checks or an `and` chain do what optional chaining does. |
| `use-if-assign` | hint | A local exists only for the truth test of the next `if`. |
| `use-interpolation` | hint | A chain of three or more concatenations mixes literals and values. |
| `use-for-from` | hint | A generic `for` copies fields of its only loop variable into same-named locals. |
| `concat-in-loop` | hint | A string grows by concatenation in a loop, which copies it on every pass. |
| `insert-front-in-loop` | hint | `table.insert(t, 1, v)` in a loop moves the whole list on every pass. |
| `closure-in-loop` | hint | A function created in a loop captures nothing the loop declares. |
| `select-in-loop` | hint | `select(i, ...)` in a loop copies the arguments on every pass. |
| `table-to-group` | hint | A table that never leaves its function holds only named fields. |
| `pairs-over-list` | hint | `pairs` iterates a table built as a list. |
| `format-to-interpolation` | hint | `string.format` has a format of literal text and `%s` only. |
| `redundant-tostring` | hint | `tostring` of a number is an operand of a concatenation. |
| `doc-unknown-param` | warning | A doc comment documents a parameter the function does not have. |
| `package-flag` | warning | A package reads a flag that its [package header](#package-headers) does not declare. |
| `package-pledge` | warning | A package calls `pledge` at the top level, which acts on the permissions of the program. |
| `package-header` | error | A package header lacks a required annotation or has a malformed one. |
| `assign-const` | error | A constant, a close variable, or a loop control variable is assigned. |

| `undefined-label` | error | A `goto` names no visible label. |
| `duplicate-label` | error | A label repeats a visible label of the same function. |
| `continue-outside-loop` | error | A `continue` appears outside every loop. |
| `continue-into-scope` | error | A `continue` in a `repeat` loop skips a local that the condition can see. |
| `syntax` | error | The file does not parse. |
| `compile` | error | The compiler rejects the file for another reason. |

### A pledge after the seal

After `pledge("seal")`, the [permissions](/manual/permissions) of a program can no longer change, so a later `pledge` grants nothing. `lus check` reports such a call, because otherwise the operation that needs the permission fails later, far from the `pledge` that caused the failure.

```lus
pledge("fs")
pledge("seal")
pledge("network")  -- pledge() after pledge("seal") has no effect, permissions are frozen [pledge-after-seal]
```

### Faster forms

Some hints name a form of the same code that runs faster. Each one comes from a measured case, and the checker reports it only where it can prove from the file that the faster form computes the same result. A string that grows by concatenation in a loop is copied in full on every pass, so building a long text this way takes time that grows with the square of its length.

```lus
local lines = { "a", "b", "c" }
local text = ""
for _, line in ipairs(lines) do
    text = text .. line .. "\n"  -- 'text' grows by concatenation in a loop: ... [concat-in-loop]
end
io.write(text)
--> a
--> b
--> c
```

Collecting the parts in a list and joining them once copies each part once.

```lus
local lines = { "a", "b", "c" }
local parts = {}
for _, line in ipairs(lines) do
    parts[#parts + 1] = line
end
print(table.concat(parts, "\n"))
--> a
--> b
--> c
```

### Lua idioms with a Lus form

The following hints, which are useful when porting Lua code, report a Lua idiom that a Lus feature replaces. `deprecated-pcall` is a warning, because the Lua functions it names do not exist in Lus. The message of each diagnostic names the Lus feature.

Lus catches errors with the [`catch`](/manual/guide#errors) expression, which replaces the Lua functions `pcall` and `xpcall`. `lus check` reports a reference to either function.

```lus nocheck
local ok, err = pcall(risky)  -- 'pcall' no longer exists, use a 'catch' expression instead [deprecated-pcall]
```

The following code makes the same call with `catch`.

```lus
local function risky() error("failed", 0) end
local ok, err = catch risky()
print(ok, err)  --> false  failed
```

A local that is used only by the `if` statement after it can be declared in the condition of that `if`. [Control flow](/manual/guide#control-flow) describes this form.

```lus
local function lookup() return 42 end
local value = lookup()
if value then  -- local declaration can be moved to the if condition (use if-assignment) [use-if-assign]
    print(value)
end
```

The following form declares the local in the condition, so the variable is visible only in the body of the `if`, where it is used.

```lus
local function lookup() return 42 end
if value = lookup() then
    print(value)  --> 42
end
```

[Optional chaining](/manual/guide#tables) replaces an `and` chain that tests each step of a field access, as well as nested checks against `nil`.

```lus
local cfg = { server = { port = 8080 } }
local port = cfg and cfg.server and cfg.server.port  -- and-chain can use optional chaining: x?.y?.z [use-optional-chain]
if cfg ~= nil then  -- nested nil checks can use optional chaining: x?.y?.z [use-optional-chain]
    if cfg.server ~= nil then
        print(cfg.server.port)
    end
end
```

The following line reads the same field with optional chaining.

```lus
local cfg = { server = { port = 8080 } }
print(cfg?.server?.port)  --> 8080
```

[`from` destructuring](/manual/guide#tables) replaces a statement that copies fields of one table into locals of the same names.

```lus
local t = { a = 1, b = 2, c = 3 }
local a, b, c = t.a, t.b, t.c  -- use 'from' destructuring: local ... from t [use-from]
print(a, b, c)  --> 1  2  3
```

The `from` form names each field once.

```lus
local t = { a = 1, b = 2, c = 3 }
local a, b, c from t
print(a, b, c)  --> 1  2  3
```

### Syntax hints

When an operator from another language causes a syntax error, the message names the Lus spelling, which helps people and coding agents who write such an operator out of habit.

```
total.lus:2:3: error: syntax error near '+' (update a variable with 'x = x + y') [syntax]
```

The hints cover compound assignment such as `+=`, the increment `++`, comments that start with `//`, and the operators `!=`, `!`, `&&`, and `||`. A read of the undefined global `null` reports `undefined-global` with the hint `the absent value is written 'nil'`.

### Test files and machine output

A file whose name ends in `_test.lus` is checked as a [test file](/manual/testing). The helpers `snapshot`, `raises`, `same`, and `skip` and the global `TEST_DIR` count as defined. The top-level `NAME_test` functions and `NAME_cases` tables that the runner reads count as used.

`--json` prints all diagnostics as one JSON array, for editors and other tools. Each object has the fields `file`, `line`, `column`, `endLine`, `endColumn`, `severity`, `code`, and `message`.

```
[
  {"file": "messy.lus", "line": 1, "column": 7, "endLine": 1, "endColumn": 13, "severity": "warning", "code": "unused-local", "message": "unused local 'unused'"}
]
```

## Documentation

`lus doc` generates the reference documentation of a module from comments in its source. The description of a function is kept next to the function, so the two are changed together. A _doc comment_ is a run of `---` line comments or one `--[[- ... ]]` long comment, on lines of its own, that ends on the line directly above a declaration. Its text is Markdown, except that a line that starts with an annotation such as `@param` describes one parameter, one result, or another property of the declaration.

```lus
--- Joins strings with a separator.
---
--- The parts are converted with `tostring` first.
--- @param sep string The separator.
--- @param parts any The values to join.
--- @return string The joined text.
--- @since 2.0
local function join(sep, ...parts)
    local out = {}
    for i, part in ipairs(parts) do
        out[i] = tostring(part)
    end
    return table.concat(out, sep)
end

print(join(", ", 1, 2, 3))  --> 1, 2, 3
```

The annotations are the following.

- `@param NAME TYPE DESCRIPTION` documents a parameter. A `?` after the name or after the type makes the parameter optional. `...` documents unnamed variable arguments, while named variable arguments such as `...parts` are documented under their name without the dots.
- `@return TYPE DESCRIPTION` documents one result, in order. `@returns` is the same annotation.
- `@raise DESCRIPTION` documents an error that the function raises, such as its message and when it occurs. Each error takes an annotation of its own, and `@raises` is the same annotation. The output lists them under **Raises** and in the `raises` field of the JSON.
- `@since VERSION` records the release in which the entry appeared.
- `@stability LEVEL` records how settled the entry is.

A line indented under an annotation continues its description, while every other line is Markdown text.

### Modules and entries

Each file is one module, named after the file without its extension. A doc comment at the start of the file, followed by a blank line, describes the module. When the file ends with `return NAME`, a doc comment on the declaration of the local `NAME` describes the module too.

`lus doc` documents the top-level declarations of a file: functions, locals, globals, and the fields of the table that the module returns by name. Global functions and the functions stored in the returned table are public, so `lus doc` lists them even without a doc comment. Every other declaration is listed only when it has a doc comment.

```lus
local M = {}

--- Opens a resource.
--- @param path string The path to open.
function M.open(path)
    return path
end

function M.close() end

local function helper() end

return M
```

The name of an entry in the returned table starts with the name of the module. When this module is saved as `res.lus`, `lus doc` lists `res.open` with its comment and `res.close` without one but omits the local `helper`.

### Package headers

A package is a module that other programs load by URL, as [Modules from the network](/manual/guide#modules-from-the-network) describes. The doc comment at the start of the main module of a package is its _package header_. It describes the package and declares what a program needs to know to use it. The following header starts the package `dates`.

```lus nocheck
--- Parses, formats, and compares dates in ISO 8601.
---
--- @package dates
--- @version 1.4.1
--- @lus 2.0
--- @license 0BSD
--- @repository https://github.com/example/dates
--- @permission fs:read=/usr/share/zoneinfo/* Reads the system time zone database.
--- @flag tzdata string Path of a time zone database to use in place of the system one.

local dates = {}
```

The annotations of a package header are the following. The first four are required.

- `@package NAME` names the package. A name has 2 to 40 characters from `a` to `z`, `0` to `9`, and `_`. It starts with a letter.
- `@version VERSION` is the version of the package, as `MAJOR.MINOR.PATCH`.
- `@lus LINE` is the Lus line the package runs on, such as `2.0`. A release such as `2.0.3` also names the oldest release of the line it runs on.
- `@license EXPR` is the license, as an SPDX expression such as `MIT`.
- `@permission PLEDGE DESCRIPTION` declares a permission that functions of the package use, in the form that `pledge` accepts.
- `@flag NAME TYPE DEFAULT DESCRIPTION` declares a build flag. `TYPE` is `boolean`, `number`, `string`, or a list of strings such as `"fast"|"small"`. `DEFAULT` is optional: `true` or `false` for a boolean, a number for a number, or a string in double quotes.
- `@includes NAME URL VERSION` records a package copied into this one, with the URL and the version it came from.
- `@homepage URL` and `@repository URL` link to the project.

A program sets a flag of a package with the name of the package as a prefix, as in `lus -F dates.tzdata=/opt/tz main.lus`. Inside the package, `flags.tzdata` holds the value. `lus check` reports a header that lacks a required annotation, a read of a flag that the header does not declare, and a call of `pledge` at the top level of the package. `lus doc` adds the fields of the header to the frontmatter of its Markdown output and as a `package` object to its JSON output.

### Output

By default, `lus doc` writes Markdown to standard output, starting with the frontmatter of the module and continuing with one section per entry. `--format json` writes JSON, in which each entry has the frontmatter fields of the [standard library specification](https://github.com/lus-lang/lus/tree/main/spec): `name`, `module`, `kind`, `params`, `vararg`, `returns`, `since`, `stability`, and `receiver`. It also has `description`, `line`, and a description for each parameter. `-o DIR` writes one file per module into the directory `DIR`, named `MODULE.md` or `MODULE.json`.

```sh
lus doc -o docs src/*.lus
lus doc --format json strings.lus
```

Other tools read doc comments too. The language server shows the doc comment of a name when the pointer is over that name in an editor. `lus check` reports a `@param` that names no parameter as `doc-unknown-param`.

## Syntax trees

A _syntax tree_ is the tree of nodes that the parser builds from source text, with one node per statement and expression. A program that analyzes or rewrites Lus code, such as a custom lint rule or a code generator, reads the tree, so it needs no parser of its own. [`debug.parse`](/manual/api#debug.parse) returns the tree to a Lus program as nested tables, while `lus ast FILE` prints the same tree as JSON for tools written in other languages. The [JSON schema of the tree](https://github.com/lus-lang/lus/blob/main/spec/language/ast.schema.json) describes every node.

### `debug.parse`

`debug.parse(code, chunkname, options)` parses a source string or a vector of bytes and returns its tree. The optional `chunkname`, which defaults to `"=(parse)"`, is the name of the chunk in error messages.

```lus
local tree = debug.parse("local x = 1 + 2")
print(tree.type, tree.line, tree.children[1].type)  --> chunk  1  local
```

The `options` table has the boolean fields `comments` and `recover`, both true by default. With `comments`, the root lists every comment in a `comments` array. With `recover`, the parser continues past a syntax error, which is useful to an editor that analyzes a file while it is being typed. A token that cannot start a statement then becomes an `error_stat` node, after which parsing resumes at the next statement. The root lists every error in its `errors` array. With `recover` set to `false`, `debug.parse` returns `nil` and the error message for a source that does not parse.

```lus
local tree = debug.parse("local a = 1\n) 2\nlocal b = 3\n")
for _, node in ipairs(tree.children) do
    print(node.type, node.line)
end
--> local  1
--> error_stat  2
--> local  3
print(debug.parse("local = 1", "input.lus", { recover = false }))
--> nil  [string "input.lus"]:1: <name> expected near '='
```

### Nodes

Each node is a table with the following fields.

- `type` is the kind of node, such as `"chunk"`, `"local"`, or `"binop"`.
- `line` and `column` are the position where the node starts, both counting from 1, with the column counted in bytes.
- `endline` and `endcolumn` are the position of the last token of the node, when the node has one.
- The other fields depend on the type of the node, such as `op`, `left`, and `right` for a `binop`.
- `children` holds the statements of a block, the `elseif` and `else` nodes of an `if`, or the fields of a table. A list field is absent when the list is empty.

The node types are the following.

| Category | Types |
| --- | --- |
| Statements | `chunk`, `local`, `global`, `assign`, `if`, `elseif`, `else`, `while`, `repeat`, `fornum`, `forgen`, `funcstat`, `localfunc`, `return`, `callstat`, `break`, `continue`, `goto`, `label`, `catchstat`, `provide`, `do`, `error_stat` |
| Expressions | `nil`, `true`, `false`, `number`, `string`, `vararg`, `name`, `index`, `field`, `binop`, `unop`, `table`, `tablefield`, `funcexpr`, `callexpr`, `methodcall`, `enum`, `doexpr`, `catchexpr`, `slice`, `interp` |
| Queries | `query`, `qsource`, `qclause`, `qitem`, `qstar` |

A few common nodes have the following shapes.

```lus nocheck
{type = "binop", line = 1, column = 13, op = "+", left = {...}, right = {...}}
{type = "local", line = 1, column = 1, names = {...}, values = {...}, isfrom = false}
{type = "callstat", line = 1, column = 1, func = {...}, args = {...}}
{type = "if", line = 1, column = 1, cond = {...}, children = {...}}
{type = "fornum", line = 1, column = 1, var = {...}, init = {...}, limit = {...}, step = {...}, children = {...}}
```

### Walking a tree

A recursive function that follows `children` visits every statement. The following program prints an outline of a chunk, with each statement indented by its depth and followed by its line.

```lus
local code = [[
local x = 1 + 2
print(x)
]]

local function walk(node, depth)
    print(string.rep("  ", depth) .. node.type .. " (line " .. node.line .. ")")
    for _, child in ipairs(node.children or {}) do
        walk(child, depth + 1)
    end
end

walk(debug.parse(code), 0)
--> chunk (line 1)
-->   local (line 1)
-->   callstat (line 2)
```

A lint rule is a walk that tests each node. The following program reports every assignment to a bare name at the top level of a chunk.

```lus
local function check_globals(tree, filename)
    for _, stat in ipairs(tree.children or {}) do
        if stat.type == "assign" then
            for _, target in ipairs(stat.lhs or {}) do
                if target.type == "name" then
                    print(`$(filename):$(stat.line): assignment to '$(target.value)'`)
                end
            end
        end
    end
end

check_globals(debug.parse("local a = 1\ncount = a\n"), "input.lus")
--> input.lus:2: assignment to 'count'
```

### `lus ast`

`lus ast FILE` prints the syntax tree of a file as JSON. The fields of every node are in a fixed order: `type`, `line`, `column`, the end position, the fields that depend on the type, and `children`. The root lists the comments of the file before its children, unless `--no-comments` omits them. For a file with syntax errors, the command prints the tree with its `errors` array and exits with status 1. With `--no-recover`, it prints the first syntax error in place of the tree and exits with status 1.

```sh
lus ast app.lus > app.json
```

The following JSON is the first node of the tree that the command prints for the line `local x = 1 + 2`.

```json
{
  "type": "local",
  "line": 1,
  "column": 1,
  "endline": 1,
  "endcolumn": 15,
  "names": [{ "type": "name", "line": 1, "column": 7, "value": "x" }],
  "values": [
    {
      "type": "binop",
      "line": 1,
      "column": 13,
      "endline": 1,
      "endcolumn": 15,
      "op": "+",
      "left": { "type": "number", "line": 1, "column": 11, "endline": 1, "endcolumn": 11, "value": 1 },
      "right": { "type": "number", "line": 1, "column": 15, "endline": 1, "endcolumn": 15, "value": 2 }
    }
  ],
  "isfrom": false
}
```

## Standalone executables

`lus build SCRIPT` turns a program into one executable file. The executable runs on a machine that has neither `lus` nor the source files, so distributing the program means copying one file. The executable has the name of the script without its extension, with `.exe` added on Windows, unless `-o FILE` gives it another name.

```sh
lus build -o app main.lus
./app first-argument
```

The command compiles the script, finds every `require` whose argument is a string literal, and searches the module path for a file for each of those names, as `require` does. It compiles the files that it finds, then does the same for the modules that those files require. `LUS_PATH` changes the module path, as it does for the interpreter. When no file matches a name, the executable contains no module of that name, so `require` searches for the module when the program runs. A literal URL names a [remote module](/manual/guide#modules-from-the-network). `lus build` downloads it and bundles it with every module of its package, so the executable never contacts the network to load it.

### Including modules

A program may compute the name of a module when it runs, for example to load a plugin chosen by a setting. `lus build` cannot find such a module in the source, so `--include` bundles it under the file name without the extension.

```sh
lus build app.lus --include lib/utils.lus --include lib/config.lus
```

The program then loads the bundled modules by those names.

```lus nocheck
local utils = require("utils")    -- lib/utils.lus
local config = require("config")  -- lib/config.lus
```

A suffix `:alias` bundles a file under another name.

```sh
lus build app.lus --include vendor/markdown.lus:markdown
```

`--include` with a directory bundles every `.lus` and `.lua` file inside it, at any depth. The name of each module is its path with dots between the parts, starting with the name of the directory.

```sh
lus build app.lus --include lib
```

The program requires the modules of the directory `lib` as follows.

```lus nocheck
local render = require("lib.render")   -- lib/render.lus
local utils = require("lib.utils")     -- lib/utils.lus
local sub = require("lib.sub.module")  -- lib/sub/module.lus
```

A directory often holds more modules than one program uses. `lus build` keeps only the modules of a directory that a literal `require` reaches from the script or from a file named on its own with `--include`. It lists the modules it leaves out. The program might load any module by a computed name, so `lus build` keeps the whole directory when the program loads code dynamically anywhere. Code loads dynamically when it calls `require` with anything other than one string constant, uses `require` as a value, calls `load`, `loadfile`, `dofile`, or `rawget`, or reads `_G` or `_ENV` with a computed key.

### Running the executable

The executable is a copy of the running `lus` with the compiled code of the program appended. `require` looks for a bundled module before it searches any file, so a file of the same name in the working directory never replaces a module of the program. Loading a bundled module needs no permission, as for the [preincluded modules](/manual/guide#modules) of the interpreter.

The program runs with the permissions it pledges plus the permissions given to `lus build` with `-P`, every time it runs. The values of the [build flags](/manual/guide#the-environment) given with `-F` are fixed in the bundled code.

```sh
lus build app.lus -P fs:read -P network -F release
./app  # runs with fs:read and network, compiled with flags.release
```

The executable passes every command line argument to the program, including arguments that look like options of `lus`. The program reads them from `arg` and `...` as a script does, with the path of the executable in `arg[0]`.

### Compiling ahead of time

`--aot` compiles the program to machine code while it builds, so the executable starts with its hot code in place and needs no JIT. `lus build` first runs the bundle once, the training run, and puts every function that the JIT compiles during that run into the executable. `--train` gives the arguments of the training run, separated by spaces. The training run prints what the program prints. A training run that exits with a status other than 0 stops the build.

```sh
lus build --aot --train "input.csv 100" -o report report.lus
./report input.csv 1000
```

The executable starts from `lus-runtime`, the runtime that the release installs next to `lus`. The runtime holds neither the parser nor the compiler, so `load` of source text returns nil and the message "the compiler is not part of this executable". A function that the training run never made hot runs in the interpreter. `--aot-keep-jit` starts the executable from the running `lus` instead, which keeps the JIT and the compiler, so such a function still compiles when the program runs. Code compiled ahead of time runs only on the architecture and the system of the `lus` that trained it.

`LUS_AOT_REPORT=1` makes the executable print, as it exits, how many functions and optimized units of code compiled ahead of time it installed.

### Linking the runtime

On Linux, on macOS on Apple Silicon, and on Windows on x86_64, the release also installs `lus-runtime.lo`, the runtime as a link object. `lus build --aot` then links the executable from it and keeps only the parts of the runtime that the program reaches: the libraries it requires, the functions of those libraries that it calls, and the code they need in turn. An executable linked this way is a fraction of the size of the runtime.

`--link-object FILE` links from the link object `FILE`, with or without `--aot`. A link object of another target links an executable for that target, so a program builds on one system for another when the build compiles nothing ahead of time.

```sh
lus build --link-object linux-x64/lus-runtime.lo -o app-linux app.lus
```

A program that loads code dynamically, as described in [Including modules](#including-modules), might reach any function of any library, so the linker keeps every library function and prints the line that made it do so. `--link-all` keeps every library function from the start. `--link-map FILE` writes one line for each part that the linker kept, with its size and the part that first reached it, largest first.

`--runtime FILE` starts the executable from the runtime `FILE` in place of the one next to `lus`. `--aot-static` compiles ahead of time for a system that refuses executable memory to programs, such as iOS. The code then becomes part of the executable itself, which takes a link object for aarch64 macOS or iOS.

```lus nocheck
-- ./app foo bar
print(arg[0])  --> ./app
print(arg[1])  --> foo
print(...)     --> foo  bar
```

## Binary chunks

A _binary chunk_ is a compiled function stored as bytes, in the form that [`string.dump`](/manual/api#string.dump) writes. A binary chunk loads without parsing source text and can be distributed without its source. `lus compile SCRIPT` writes the compiled script as a binary chunk to `SCRIPT.lusc`, where `SCRIPT` is the script name without its extension, or to the file named by `-o`. `-s` omits debug information, which makes the chunk smaller and removes line numbers from its error messages. `-F` defines build flags as for `lus build`, with their values fixed in the chunk. `-P` grants a permission to the initializers of [`<meta>` variables](/manual/guide#values-computed-when-the-file-is-compiled), whose values the chunk stores.

```sh
lus compile -o report.lusc report.lus
lus report.lusc data.csv
```

`lus` runs a binary chunk as it runs a script. `load` reads a binary chunk in binary mode, which requires the `load` permission. A binary chunk works only with the version of the runtime that wrote it, so keep the source and compile it again for each release of Lus. A binary chunk is trusted input. `load` checks the header and the structure of a chunk, so a damaged chunk raises an error or loads. It does not check that the code of a chunk is safe to run. A program that loads code from an untrusted source passes the mode `"t"`, which rejects binary chunks. The following program compiles a function to a binary chunk with `string.dump`, then loads the chunk and calls the result.

```lus
pledge("load")

local chunk = string.dump(function(n) return n * 2 end)
local double = load(chunk, "double", "b")
print(double(21))  --> 42
```

## Debugger

A debugger stops a running program at a chosen line and shows its variables and its call stack, which usually finds a bug faster than adding `print` calls. `lus debug` runs a script under the [Debug Adapter Protocol](https://microsoft.github.io/debug-adapter-protocol/), the protocol that VS Code and many other editors use to control debuggers. The _adapter_ is the part of the `lus` executable that implements the protocol, so any editor with a client for the protocol can set breakpoints in Lus code, step through it, and inspect its state.

### Running the adapter

An editor starts the adapter with the following command.

```
lus debug [--stdio | --port N] [-P perm]... [SCRIPT [ARGS...]]
```

By default, the adapter reads requests from standard input and writes its replies to standard output, which is how editors start it. `--port N` makes the adapter accept one client on `127.0.0.1:N`, for a client that connects to an adapter that is already running. The script is named on the command line or in the `program` field of the launch request. `-P` grants [permissions](/manual/permissions) to the program as `lus -P` does, so a debugging session can run with the same permissions as a normal run.

The adapter sends the standard output and standard error of the program to the editor as output events. In stdio mode, the protocol uses the real standard input, so the program reads an empty standard input.

### Visual Studio Code

The [Lus extension](/manual/ide-setup) registers the `lus` debugger type, so **Run and Debug** works on any `.lus` file. A launch configuration in `.vscode/launch.json` names the program and its options.

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "lus",
      "request": "launch",
      "name": "Debug Lus File",
      "program": "${file}",
      "cwd": "${workspaceFolder}",
      "args": [],
      "pledges": ["fs:read=${workspaceFolder}/*"],
      "stopOnEntry": false
    }
  ]
}
```

The fields of a launch configuration are the following.

| Field | Meaning |
| --- | --- |
| `program` | The Lus script to run. It is required. |
| `args` | The arguments passed to the script. |
| `cwd` | The working directory of the program. |
| `stopOnEntry` | Stop at the first line of the program. The default is `false`. |
| `pledges` | The permissions granted to the program, as with `lus -P`. |

The extension starts the `lus` found on the `PATH`, unless the setting `lus.executablePath` names another executable. A relative path with a directory part is resolved against the workspace folder.

### Breakpoints and stepping

The adapter supports the debugging features that editors offer for most languages.

- **Breakpoints** stop on any line. A breakpoint may have a **condition**, a Lus expression that must be truthy for the breakpoint to stop the program. It may have a **hit count**: a plain number stops on exactly that hit, while a number after one of the operators `>=`, `<=`, `>`, `<`, `==`, and `%` stops on the hits that satisfy the operator, so `%3` stops on every third hit. A breakpoint with a **log message** lets the program continue after printing the message, with each expression in braces replaced by its value, as in `x is {x}`.
- **Error breakpoints** are set by filter. _Uncaught Errors_, on by default, stops on an error that no `catch` captures. _All Raised Errors_ stops on every error at the point where it is raised, including errors that a `catch` captures.
- **Stepping** covers step over, step in, and step out, plus **pause** while the program runs. New breakpoints take effect immediately, even while the program runs.
- **Call stacks** include coroutines. The frames of a coroutine are shown on top of the frames of the code that resumed it, so stepping out of a coroutine stops in the code that resumed it.
- **Variables** appear in the following scopes for each frame: _Locals_ holds the local variables of the function, _Upvalues_ holds the variables of enclosing functions that the function uses, and _Globals_ holds the global variables. Tables and vectors expand in place.
- **Evaluation** runs expressions in the context of the selected frame, from the debug console and on hover.

### How the adapter works

The adapter is native code inside the interpreter that runs no Lus code in the program being debugged. During a debugging session, the interpreter calls the adapter at every new line, where the adapter stops the program if a breakpoint, a step, or a pause applies. The interpreter also calls the adapter for each error, before it searches for a `catch`. Machine code compiled by the JIT never runs during a debugging session, so a program runs slower under the debugger, while its speed without the debugger is unchanged.

Stepping compares stack depths, where the depth of a thread is the number of its frames plus the frames of every thread that resumed it. Step over stops at the next line at the same depth or a smaller one. Step out stops at the next line at a smaller depth. Step in stops at the next line at any depth.

While the program runs, a second thread reads the requests of the editor, which the interpreter handles between two lines. While the program is stopped, the interpreter waits for requests and answers them, so the editor can read the stack and the variables and evaluate expressions.

## Standard library reference

`lus help` prints the reference of the standard library in the terminal, with no browser or network connection. The reference is part of the executable, so it describes the version that is running. `lus help NAME` prints the signature, the permissions the call needs, the stability, and the description of an entry. `lus help MODULE` lists a module with one line per entry. `lus help` with no argument lists the modules. `lus help --search TEXT` lists the entries whose name or description contains `TEXT`. When no entry has the given name, `lus help` lists the entries whose names contain it and exits with status 1.

```
$ lus help network.serve
network.serve(host, port, handler, options?)
needs network:server, network:tcp

Serves HTTP/1.1 on `host` and `port`, calls `handler` for every request, and returns only when the server stops.
...
```

## Agent setup

A coding agent writes better Lus when the project contains instructions for the language and its tools. `lus agents init [DIR]` writes the agent skills of the running version into `DIR/.agents/skills`, the folder that coding agents of several vendors read, where `DIR` defaults to the current directory. The command then links `.claude/skills` to that folder, or links each skill into it when `.claude/skills` is already a directory. On a system that refuses symbolic links, it copies the skills. Last, it writes a short Lus section to `AGENTS.md`, creating the file if needed. The section sits between the lines `<!-- lus agents init -->` and `<!-- /lus agents init -->`. Running the command again updates the skills and the text between those lines, and leaves the rest of `AGENTS.md` as it is. [The agents page](/agents) lists the skills and the prompts to start from.
