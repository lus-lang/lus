Lus is a small programming language for general-purpose programs. Its syntax is short and readable. Its standard library is large. One executable holds the runtime, the library, and the tools.

The language is [sovereign](#sovereignty), which means that its built-in facilities cover most tasks. The standard library includes files, networking, JSON and CSV, compression, time, and SQLite. The `lus` command includes a test runner, a formatter, a checker, and a debugger.

## Background

Lus is derived from Lua 5.5. It keeps Lua's syntax and its minimalism. Lus is a complete language with its own runtime. The runtime runs Lus source directly and compiles the code that runs often to machine code. [Lus for Lua programmers](/manual/lua) lists the changes that existing Lua code needs and explains why the two languages differ.

Lus was developed to bring Lua to general-purpose programming. Lua is designed first for embedding in a host program, so its standard library is small. A standalone Lua program depends on third-party packages for tasks such as reading a directory or opening a socket. The standard library of Lus includes those tasks. Lus keeps Lua's conciseness.

Lus is a personal project of [Louka Ménard Blondin](https://louka.sh). It is maintained on a best-effort basis.

## Sovereignty

_Language sovereignty_ is how much a language can do without depending on anything outside itself. It has three parts. **Implementation** is how far the environment that the language runs in limits it. **Use** is how much a program can do before it needs a third-party library. **Adoption** is how much effort the language takes to learn and use.

Lus addresses all three. Its standard library is cross-platform and covers complete programs. Its syntax is the small, readable syntax of Lua.

## Goals

Lus has the following design goals.

- **Boring is good.** Lus adopts an idea once the idea has proven useful in practice. The latest trends in programming language theory are left to other languages.

- **Use-first approach.** The language is easy to find, install, and use.

- **Solve real-world problems.** The language is designed for productivity, so practical needs come before theoretical purity.

- **Sovereignty.** The language is usable on its own. One executable holds the runtime, the standard library, and the tools, so a program needs no third-party runtime or library to do useful work.

- **Minimalism.** Lus has a concise, readable syntax and few keywords, as Lua does, so it is quick to adopt.

- **Explicit permissions.** A script starts with no access to files, the network, processes, or environment variables. It [pledges](/manual/permissions) each capability before it uses it. A program can also give up capabilities permanently, which limits what a bug or a loaded module can reach.

- **Strong release engineering.** The language has stable, tested releases. Its design changes deliberately.

- **Backwards _embeddability_.** Lua was engineered to be embedded in other programs. Lus keeps that ease of integration, although its first concern is the sovereignty of the runtime. The runtime is written in Zig and has a C interface, `lus.h`, so a host program [embeds Lus](/manual/embedding) much as it embeds Lua. The same runtime also runs in the browser as a [WebAssembly](/manual/webassembly) module.

Lus has the following **non-goals**.

- **Strong typing.** Lus keeps Lua's dynamic typing.

- **_Other language syndrome._** Developers often solve problems with patterns from the languages they already know. A feature of Lus is designed to suit Lus, even when another language solves the same problem in another way.

- **Modules.** The `require` function loads code from other files. A name declared with `local` is private to its file. Lus organizes programs with these two features alone.

- **Bureaucracy.** Lus has no committee to approve changes to the language, no organization to plan its development, and no foundation to manage its funding. It is a single-repository project dedicated to the public domain and maintained with as little process as possible.

## Contributing

Bug fixes, optimizations, and test cases are welcome, because they make the language better at what it already does. Most feature requests are declined. Design decisions stay with the author, which keeps the language coherent. Contributors need a working knowledge of Zig, Lua, and Lus. They also need to understand how an interpreter and a garbage collector work.

LLM use is permitted when the operator knows Lus and the implementation languages and understands the complete change. The operator must carefully review everything that gets pushed. A person examines every contribution thoroughly before it enters the repository.
