The `network` library connects a program to other machines. [`network.fetch`](/manual/api#network.fetch) sends an HTTP or HTTPS request, which is how a program calls a web API or downloads a file. [`network.serve`](/manual/api#network.serve) answers HTTP requests, which makes the program a web server. The `network.tcp`, `network.tls`, and `network.udp` functions open sockets for every other protocol.

Data that arrives from the network is bytes, so every function that receives data returns a [vector](/manual/text#vectors). [`vector.tostring`](/manual/api#vector.tostring) decodes a vector that holds text into a string. Every function that contacts the network requires a `network` [permission](#permissions).

## Permissions

Each operation checks one part of the `network` [permission](/manual/permissions). `pledge("network")` grants every part.

| Operation | Permission | Requested value |
| --- | --- | --- |
| `network.fetch` | `network:http` | The URL. |
| `network.tcp.connect`, `network.tcp.bind`, `network.tls.connect` | `network:tcp` | `host:port` |
| `network.udp.open`, `setsockname`, `sendto` | `network:udp` | `host:port`, or no value for an unbound socket |
| `network.serve` | `network:server` | `host:port` of the address it serves |

A permission with a value permits only the hosts that match it. A program that calls one API pledges `network:http=api.example.com/**`, so a bug or a misleading input cannot make it contact another host. [Restricting a permission to values](/manual/permissions#restricting-a-permission-to-values) describes the matching rules. `sendto` checks the permission for every destination, so a UDP grant for one host never permits datagrams to another. `network.serve` also binds a TCP server, so it requires `network:tcp` for the same address.

## HTTP requests

`network.fetch(url, method, headers, body, options)` sends one HTTP or HTTPS request and waits for the response. It returns three values: the integer status code, the response body as a vector, and a table of the response headers, whose names are lowercase.

The following program requests a JSON document and decodes it with [`fromjson`](/manual/api#fromjson).

```lus nocheck
pledge("network:http")

local status, body, headers = network.fetch("https://httpbin.org/get")
print(status)                    --> 200
print(headers["content-type"])   --> application/json
local data = fromjson(vector.tostring(body))
```

The arguments after `url` are optional and are given by position. `method` defaults to `"GET"`, `headers` is a table from header names to values, and `body` is a string or a vector. The following request posts a JSON body.

```lus nocheck
local status, body = network.fetch(
    "https://httpbin.org/post",
    "POST",
    { ["Content-Type"] = "application/json" },
    tojson({ name = "Lus" })
)
```

`fetch` returns whatever status the server sends, so a program checks the status before it uses the body. A 404 response, a 500 response, and a redirect are all normal results. For a redirect, `fetch` returns the 3xx status and the `location` header, so the program sends the next request itself. The following program downloads a CSV file and stops when the status is anything other than 200.

```lus nocheck
local status, body = network.fetch("https://example.com/report.csv")
if status ~= 200 then
    error(`download failed with status $status`)
end
local rows = fromcsv(vector.tostring(body), true)
```

`fetch` raises an [error object](#errors-of-socket-operations) when it cannot reach the server or cannot read the response, whose message is such as `"cannot resolve 'invalid.host.example': Domain name not found"` or `"cannot connect to 127.0.0.1:1: Connection refused"` and whose `code` says what failed. A connection that fails part way raises an error that names the step and the reason, such as `"failed to read response body: Connection reset by peer"`, so a response that arrives is always complete. A program that must continue after such a failure wraps the call in [`catch`](/manual/guide#errors).

```lus nocheck
local ok, err = catch network.fetch("https://invalid.host.example")
if not ok then
    print(`request failed: $err`)
end
```

`fetch` also follows these rules.

- Every request has the headers `Host`, `Connection: close`, and `User-Agent: Lus/VERSION`, where `VERSION` is the full version of the runtime, as in `Lus/2.0.0`. Then come the headers of the `headers` table, then `Content-Length` when the body is not empty. A header in the table replaces a default header of the same name, whatever its case.
- A response to a `"HEAD"` request, or with status 1xx, 204, or 304, has an empty body.
- The values of a response header that appears more than once are joined with `", "`.
- For an HTTPS URL, `fetch` verifies the certificate of the server against the certificates of the system and raises an error when the verification fails. The `tls` option takes the client options of [TLS sockets](#tls-sockets), such as `{ tls = { ca = pem } }` for a server whose certificate a private authority signed.
- The `timeout` option, 30 seconds by default, bounds each step of the request. Connecting, the TLS handshake, and receiving the headers each have that long in total. Sending the request and reading the body may wait that long for each part, so a stream stays open while it moves. The error of a step that runs out names it, such as `"fetch timeout while waiting for the response headers"`.
- A response body larger than 64 MiB raises `"response body too large"`.
- A URL with a scheme other than `http` or `https` raises `"invalid URL: URL"`. A URL, method, or header that contains a line break raises an error before anything is sent.

`fetch` waits for the network through the scheduler. Inside a [detached coroutine](/manual/concurrency#detached-coroutines) it suspends only that coroutine, so a program sends several requests at the same time from several detached coroutines. While the main chunk waits in `fetch`, the detached coroutines keep running, so a program can fetch from its own `network.serve` server.

### Streamed bodies

A response may be too large to hold at once, or it may arrive over a long time, as server-sent events and the answers of AI models do. With the option `stream = true`, `fetch` returns once the headers arrived, and the body is a coroutine in place of a vector. Each `coroutine.resume` of it returns `true` and the next part of the body as a vector, as soon as the part arrives. At the end of the body the coroutine ends and closes the connection.

```lus nocheck
local status, body = network.fetch("https://example.com/big.csv", "GET", nil, nil, { stream = true })
local size = 0
while true do
    local ok, part = coroutine.resume(body)
    if not ok then error(part) end
    if part == nil then break end
    size = size + #part
end
```

A failure while the body arrives makes the resume return `false` and the error. [`coroutine.close`](/manual/concurrency#cancelling) stops a stream early and closes its connection. [`network.lines(stream)`](/manual/api#network.lines) turns such a coroutine into an iterator over its lines. The following program reads a stream of server-sent events, where each event is a `data:` line followed by an empty line.

```lus nocheck
local status, events = network.fetch("https://api.example.com/v1/stream", "POST",
    { ["Content-Type"] = "application/json" }, tojson({ prompt = "hello" }), { stream = true })
for line in network.lines(events) do
    local data = vector.tostring(line):match("^data: (.*)$")
    if data and data ~= "[DONE]" then
        io.write(fromjson(data).text)
    end
end
```

A request body may stream too. A coroutine in place of the body yields the chunks of the body as strings or vectors and ends after the last one. `fetch` sends each chunk as the coroutine yields it, with chunked transfer coding unless the headers set `Content-Length`. A function that returns the next chunk on each call and `nil` at the end works the same way. The following program uploads a file in pieces of 64 KiB, so the whole file never sits in memory.

```lus nocheck
local file <close> = io.open("backup.tar", "rb")
local upload = coroutine.create(function()
    while piece = file:read(65536) do
        coroutine.yield(piece)
    end
end)
local status = network.fetch("https://storage.example.com/upload", "PUT", nil, upload)
```

## TCP clients

A _TCP socket_ is a two-way connection that delivers bytes in the order they were sent. A program uses one for a protocol other than HTTP, such as the protocol of a database, a mail server, or a service of its own.

[`network.tcp.connect(host, port, options)`](/manual/api#network.tcp.connect) opens a connection and returns a socket. `host` is a name or a numeric address. A connection that fails returns `nil` and an [error object](#errors-of-socket-operations), such as one with the message `"cannot connect to HOST:PORT: Connection refused"`. The option `timeout` limits the connection, across every address of the host, to that many seconds, fails with the message `"timeout while connecting to HOST:PORT"` when it runs out, and becomes the timeout of the socket.

A TCP socket has these methods.

| Method | Effect |
| --- | --- |
| `send(data, i, j)` | Sends a string or a vector, or the part of it from position `i` to position `j`, and returns the position of the last element sent. |
| `receive(pattern, max_bytes)` | Receives data as a vector. [Receiving from a TCP socket](#receiving-from-a-tcp-socket) describes the patterns. |
| `settimeout(seconds)` | Limits every later wait of the socket. [Timeouts](#timeouts) describes the limit. |
| `getsockname()` | Returns the local numeric address and port. |
| `getpeername()` | Returns the numeric address and port of the other end. |
| `reader(max_bytes)` | Returns a coroutine that yields what has arrived on each resume. [Receiving from a TCP socket](#receiving-from-a-tcp-socket) describes it. |
| `close()` | Closes the connection. A second `close` does nothing. |

A socket declared with the `<close>` attribute closes when its block ends, which is the usual way to release a connection. The garbage collector also closes a socket that the program no longer refers to.

A method other than `close` on a closed socket raises `"attempt to use a closed socket"`. When the connection fails during `send` or `receive`, for example because the other end reset it, the method returns `nil` and an error object whose message is such as `"receive: Connection reset by peer"`.

### Errors of socket operations

Socket operations report failures the way file operations do. A failed operation returns `nil` and an _error object_, a table with the fields `code` and `message`, whose `__tostring` gives the message. A program that prints the error or passes it to `tostring` reads the message, and a program that decides what to do next reads `code`.

```lus nocheck
local sock, err = network.tcp.connect("db.internal", 5432, { timeout = 5 })
if not sock then
    if err.code == "timeout" or err.code == "refused" then
        return retry_later()
    end
    error(err)
end
```

The codes are `"timeout"`, `"refused"`, `"reset"`, `"closed"`, `"unreachable"`, `"resolve"`, `"address"`, `"denied"`, `"limit"`, `"tls"`, `"certificate"`, and `"io"`, which [`network.tcp`](/manual/api#network.tcp) defines. Misuse raises instead: a bad argument, a socket that the program closed, and a missing permission. `network.fetch` raises the same error objects, since it returns a response.

## TLS sockets

A _TLS socket_ is a TCP socket whose bytes travel encrypted through TLS 1.2 or TLS 1.3. Protocols such as those of PostgreSQL, Redis, and mail servers run over one. [`network.tls.connect(host, port, options)`](/manual/api#network.tls.connect) opens a connection, runs the TLS handshake, and returns the socket. The socket has every method of a TCP socket, and `send` and `receive` carry plain text.

```lus nocheck
pledge("network")

local sock <close> = network.tls.connect("example.com", 443)
sock:send("GET / HTTP/1.1\r\nHost: example.com\r\nConnection: close\r\n\r\n")
print(vector.tostring(sock:receive("*l")))   --> HTTP/1.1 200 OK
```

The client checks that the certificate of the server chains to a trusted authority and names the server. By default the trusted authorities are those of the system. `options` is a table with any of these fields.

| Field | Value |
| --- | --- |
| `servername` | The name to check the certificate against and to send through SNI. The default is `host`. |
| `alpn` | A list of protocol names to offer through ALPN, such as `{ "h2", "http/1.1" }`. |
| `ca` | PEM text of the authorities to trust in place of those of the system. |
| `cert`, `key`, `password` | PEM text of a client certificate and its private key, with the password of an encrypted key. |
| `verify` | `false` to accept any certificate. The default is `true`. |
| `timeout` | The timeout of the socket in seconds, which also bounds the handshake. |

A certificate that does not verify closes the socket, and the call returns `nil` and an error object with the code `"certificate"` and a message such as `"certificate verification failed for example.com: The certificate is not correctly signed by the trusted CA"`.

Some protocols start in plain text and switch to TLS after an exchange of messages, as SMTP does with its `STARTTLS` command. [`sock:starttls(options)`](/manual/api#tcp_socket:starttls) switches a TCP socket to TLS at that point and returns the same socket. A client passes the options above without `timeout`, and a socket that verifies the server must name it with `servername`. A server passes `server = true` with its `cert` and `key`, or `certs`, a list of them that SNI picks from, and `alpn` for the protocols it accepts. A server of implicit TLS calls `starttls` right after `accept`.

```lus nocheck
local tls = { server = true, cert = read("cert.pem"), key = read("key.pem") }
local conn = server:accept()
conn:starttls(tls)              -- the handshake as the server
conn:send("+OK ready\r\n")       -- every byte now travels over TLS
```

The server reads the certificates once for each options table, so a server keeps one table for all its connections. [`sock:tlsinfo()`](/manual/api#tcp_socket:tlsinfo) returns a table with the protocol `version`, the `cipher` suite, the `alpn` protocol, and the `servername` of a TLS socket, or `nil` for a plain one.

The handshake, `send`, and `receive` of a TLS socket are suspension points, like the operations of a TCP socket.

## Receiving from a TCP socket

A TCP connection carries a stream of bytes with no boundaries between messages, so each `receive` call specifies how much to read. [`socket:receive(pattern, max_bytes)`](/manual/api#tcp_socket:receive) reads according to one of the following patterns and returns a vector.

| Pattern | Result | Limit |
| --- | --- | --- |
| `"*l"`, the default | One line, without its line feed and without a carriage return before it | 1 MiB, or `max_bytes` |
| A positive integer `n` | Exactly `n` bytes, or the bytes that remain when the connection ends first | `n` itself |
| `"*a"` | Everything up to the end of the connection | 64 MiB, or `max_bytes` |

Text protocols read lines with `"*l"`. Binary protocols usually send a length first, so the program then reads that many bytes with an integer pattern. `"*a"` is for a peer that sends one message and closes the connection.

At the end of the connection, every pattern returns the bytes that remain. Once nothing remains, the result is an empty vector, which is how a program detects the end of the connection. An integer that is zero or negative raises `"invalid receive size: N"`. Any other pattern raises `"invalid receive pattern: PATTERN"`.

The optional positive integer `max_bytes` sets the limit of `"*l"` and `"*a"`. A line or a stream that exceeds its limit closes the socket and returns `nil` and an error object with the code `"limit"` and the message `"receive limit exceeded"`. A server passes a small `max_bytes` so that a peer that never sends a line break cannot make the program use memory without limit. The following calls read a request line of at most 8 KiB and an upload of at most 8 MiB.

```lus nocheck
local request_line = socket:receive("*l", 8192)
local upload = socket:receive("*a", 8 * 1024 * 1024)
```

A program that moves bytes as they arrive, such as a relay or a parser of a stream, reads through [`socket:reader(max_bytes)`](/manual/api#tcp_socket:reader). It returns a coroutine, and each `coroutine.resume` of it returns `true` and whatever the socket received, between 1 and `max_bytes` bytes, 64 KiB by default. At the end of the connection the coroutine ends. It has the shape of the [streamed bodies](#streamed-bodies) of HTTP, so `network.lines` reads it line by line, and a `network.serve` handler may return it as the body of a response.

```lus nocheck
-- Relays an upstream connection to the client of a handler as it arrives.
network.serve("127.0.0.1", 8080, function(req)
    local upstream = network.tcp.connect("backend.internal", 9000, { timeout = 5 })
    upstream:send("STREAM\r\n")
    return 200, upstream:reader()
end)
```

## TCP servers

A _TCP server_ listens on a port and accepts the connections that clients open to it. [`network.tcp.bind(host, port, backlog)`](/manual/api#network.tcp.bind) starts one and returns it. `backlog` is the number of connections that the system keeps waiting until `accept` takes them, 128 by default. With port `0`, the operating system chooses a free port, which [`server:getsockname()`](/manual/api#tcp_server:getsockname) returns together with the numeric address.

A server has the methods `accept`, `settimeout`, `getsockname`, and `close`. `accept()` waits for the next connection and returns it as a TCP socket.

The following program is a greeting server and its client in one process. The server runs in a [detached coroutine](/manual/concurrency#detached-coroutines), which Lus resumes whenever the connection it waits for is ready. The main chunk connects, sends a name, and waits for the reply, during which the server coroutine runs. The final `coroutine.resume` waits for the server coroutine to end and returns its error if it failed, which `assert` then raises.

```lus
pledge("network")

local server = network.tcp.bind("127.0.0.1", 0)
local address, port = server:getsockname()

local greeter = coroutine.detach(coroutine.create(function()
    local client <close> = server:accept()
    local name = vector.tostring(client:receive("*l", 1024))
    client:send(`hello, $name\n`)
end))

local sock <close> = network.tcp.connect(address, port)
sock:send("Lus\n")
print(vector.tostring(sock:receive("*l")))  --> hello, Lus
assert(coroutine.resume(greeter))
server:close()
```

A server that handles many clients accepts in a loop and detaches one coroutine per connection. [Detached coroutines](/manual/concurrency#detached-coroutines) has a server of this kind.

## UDP sockets

A _UDP socket_ sends and receives single messages called datagrams, without a connection. A datagram arrives whole or not at all, but the network may lose or reorder datagrams. Programs use UDP for short messages where a lost one is acceptable, such as metrics, discovery on a local network, and DNS queries.

[`network.udp.open(port, address)`](/manual/api#network.udp.open) creates a UDP socket. With an `address`, or with a `port` other than `0`, the socket is bound to that local address and port, which is what a receiver needs. The address is a numeric IPv4 address and defaults to `0.0.0.0`, which means every address of the machine. Without either argument the socket sends from a port that the system chooses, which is enough for a sender.

A UDP socket has these methods.

| Method | Effect |
| --- | --- |
| `sendto(data, address, port)` | Sends one datagram to a name or a numeric address and returns the number of bytes sent. |
| `receive(size)` | Waits for one datagram and returns its data as a vector, the numeric address of the sender, and the port of the sender. |
| `setsockname(address, port)` | Binds a socket that was opened without an address or a port. |
| `getsockname()` | Returns the local numeric address and port. |
| `settimeout(seconds)` | Limits every later wait of the socket. |
| `close()` | Closes the socket. |

`receive(size)` returns at most `size` bytes of the datagram and discards the rest of it. `size` defaults to 8 KiB and must be between 1 and 1 MiB. Any other size raises `"invalid receive size: N"`. `setsockname` on a socket that is already bound returns `nil` and an error message. A method other than `close` on a closed socket raises `"attempt to use a closed UDP socket"`.

The following program sends one datagram from one socket to another on the same machine.

```lus
pledge("network")

local receiver = network.udp.open(0, "127.0.0.1")
local _, port = receiver:getsockname()

local sender = network.udp.open()
print(sender:sendto("hello", "127.0.0.1", port))  --> 5

local data, address = receiver:receive()
print(vector.tostring(data), address)  --> hello  127.0.0.1

sender:close()
receiver:close()
```

## Timeouts

By default, a socket operation waits until it completes, so a peer that stops answering stops the code that waits for it. A _timeout_ limits how long one operation of a socket or server may wait. `settimeout(seconds)` sets the timeout for every later operation, where `seconds` may have a fraction. `nil`, a negative value, or NaN removes the timeout. With a timeout of `0`, an operation that cannot complete at once fails at once.

When a timeout runs out, the operation returns `nil` and an error object whose code is `"timeout"` and whose message is `"receive timeout"`, `"send timeout"`, `"accept timeout"`, or `"sendto timeout"`. The socket stays open and usable after a timeout.

The following server waits 50 milliseconds for a connection that never comes, so `accept` returns `nil` and the error.

```lus
pledge("network")

local server = network.tcp.bind("127.0.0.1", 0)
server:settimeout(0.05)
local sock, err = server:accept()
print(sock, err.code, tostring(err))  --> nil  timeout  accept timeout
server:close()
```

## Waiting inside detached coroutines

A program that serves several connections must wait for all of them at once, which [detached coroutines](/manual/concurrency#detached-coroutines) make possible. A socket operation inside a detached coroutine suspends only that coroutine, so the other detached coroutines run until its socket is ready. An operation with this behavior is called a _suspension point_. The TCP suspension points are `connect`, `accept`, `send`, and `receive`, and those of a TLS socket add the handshake. The UDP suspension points are `receive` and `sendto`. `network.fetch` and the coroutines of streamed bodies wait the same way.

Outside a detached coroutine, the same operation blocks its caller while the detached coroutines run. A timeout limits the wait in both cases. [Suspension points](/manual/concurrency#suspension-points) describes the rules in full.

## HTTP server

`network.serve(host, port, handler, options)` runs an HTTP/1.1 server that listens on `host` and `port` and calls `handler` once for every request, with a table that describes the request. The handler returns the status, the body, and the headers of the response. The call to `serve` returns when the server stops.

The following server answers `GET /` with a greeting and every other request with 404.

```lus nocheck
pledge("network")

network.serve("127.0.0.1", 8080, function(req)
    if req.method == "GET" and req.path == "/" then
        return 200, "hello\n", { ["Content-Type"] = "text/plain" }
    end
    return 404, "not found\n"
end)
```

`serve` runs every connection in a detached coroutine of its own, so a slow client does not delay the others. A connection stays open between requests until the client closes it or sends the header `Connection: close`.

The second form, `network.serve(server, handler, options)`, serves on a server that `network.tcp.bind` returned. A program uses it to bind port `0` and read the chosen port with `getsockname` before it serves, as a test does. A server that `serve` bound itself closes when `serve` ends, while a server passed to `serve` stays open until the program closes it. `serve` ends when the coroutine that called it is closed, or when accepting a connection fails for a reason other than a shortage of file descriptors or memory.

The following program serves in a detached coroutine and sends one request over a TCP socket from the main chunk, then stops the server with [`coroutine.close`](/manual/concurrency#cancelling).

```lus
pledge("network")

local server = network.tcp.bind("127.0.0.1", 0)
local _, port = server:getsockname()

local serving = coroutine.detach(coroutine.create(network.serve), server, function(req)
    return 200, `hello from $(req.path)`, { ["Content-Type"] = "text/plain" }
end)

local sock <close> = network.tcp.connect("127.0.0.1", port)
sock:send("GET /docs HTTP/1.1\r\nHost: localhost\r\nConnection: close\r\n\r\n")
local response = vector.tostring(sock:receive("*a"))
print(response:match("^HTTP/1.1 (%d+)"))  --> 200
print(response:match("\r\n\r\n(.*)$"))  --> hello from /docs

coroutine.close(serving)
server:close()
```

### Requests

The handler receives one table per request with the following fields.

| Field | Value |
| --- | --- |
| `method` | The request method, such as `"GET"`. |
| `path` | The request target up to the first `?`, as the client sent it. |
| `query` | The text after the first `?`, or the empty string. |
| `headers` | A table from lowercase header names to their values. The values of a repeated header are joined with `", "`. |
| `ip` | The numeric address of the client. |
| `port` | The port of the client. |
| `body` | The whole request body as a vector, which is empty for a request without a body. |
| `reader` | A coroutine that yields the request body part by part, as [streamed bodies](#streamed-bodies) do. |

The server calls the handler as soon as the headers arrived. The body waits in the connection until the handler reads it. Reading `req.body` reads the whole body, at most 16 MiB, and keeps it in the table. A handler that receives a large upload resumes `req.reader` instead, which yields each part as it arrives, with no limit on the total. A handler uses one of the two for a request. Whatever the handler leaves unread, the server drops before the next request.

`req.ip` and `req.port` come from the TCP connection. A server behind a reverse proxy, a load balancer, or a service such as Cloudflare sees the address of the proxy there. The proxy passes the address of the client in a header such as `X-Forwarded-For` or `CF-Connecting-IP`, and reading that header, from the proxies the application trusts, is the job of the application.

The server reads bodies with a `Content-Length` and bodies with `Transfer-Encoding: chunked`. It answers `Expect: 100-continue` when the handler first reads the body.

### Responses

The handler returns `status, body, headers`, in the order in which `network.fetch` returns them. `status` is an integer that defaults to 200, `body` is a string or a vector that defaults to an empty body, and `headers` is a table from header names to strings or integers. The server adds the `Date` and `Content-Length` headers when the handler leaves them out. It omits the body from the response to a `HEAD` request.

A header value may also be a list, which sends one header line for each element in order. A response sets several cookies this way, since each cookie needs its own `Set-Cookie` line.

```lus nocheck
return 200, "signed in", {
    ["Set-Cookie"] = { "session=abc123; HttpOnly; Path=/", "theme=dark; Path=/" },
}
```

`network.fetch` accepts the same lists in the headers of a request.

A coroutine in place of the body streams the response. The server sends the status and the headers, then resumes the coroutine again and again and sends each chunk that it yields, a string or a vector, at once. The body ends when the coroutine ends. A function that returns the next chunk on each call and `nil` at the end works the same way. The coroutine may wait between chunks, so a handler that sends events as they happen keeps its connection open as long as it likes. The server sends the chunks with chunked transfer coding and keeps the connection for the next request. An error in the coroutine closes the connection after the chunks already sent. Returning `req.reader` as the body sends the request body back as it arrives.

The following handler relays a stream of server-sent events from another server. Each part goes to the client as soon as it arrives from upstream.

```lus nocheck
network.serve("127.0.0.1", 8080, function(req)
    local status, upstream = network.fetch("https://api.example.com/v1/events", "GET", nil, nil, { stream = true })
    return status, upstream, { ["Content-Type"] = "text/event-stream", ["Cache-Control"] = "no-cache" }
end)
```

A handler may wait for something, such as a query to another server. A socket operation or a `coroutine.yield` inside the handler suspends only its own connection, so the other connections run during the wait. The server sets no limit on the time a handler takes.

### Upgrades

A handler upgrades its connection to another protocol by returning the status 101 and a function in place of the body. The server sends the 101 response, then calls the function with the TCP socket of the connection. The function then owns the connection, which closes when the function returns. A WebSocket server is the usual case, and it shares its port with the HTTP routes of the same handler.

When the request carries a `Sec-WebSocket-Key` header, the server completes the WebSocket handshake. It adds `Upgrade: websocket`, `Connection: Upgrade`, and the `Sec-WebSocket-Accept` value that the client checks, unless the handler sets them. The function exchanges WebSocket frames over the socket with `send` and `receive`. The socket keeps the idle timeout of the server until the function calls `settimeout`, and a negative timeout lets it wait without limit.

```lus nocheck
network.serve("127.0.0.1", 8080, function(req)
    if req.path == "/live" and req.headers.upgrade == "websocket" then
        return 101, function(sock)
            sock:settimeout(-1)
            -- read and write WebSocket frames on sock
        end
    end
    return 200, "hello\n"
end)
```

An error in the function is reported like an error of a handler, and the connection closes without a further response.

### Handler errors

When the handler raises an error, the server answers 500 with an empty body and closes that connection. It does the same when the handler returns values that make no response, such as a status that is not an integer. The other connections continue, so one failing request does not stop the server.

The server writes the error to standard error in the form `lus: network.serve: MESSAGE`. A program that records errors elsewhere passes an `on_error` function in the options. The server then calls `on_error` with the error object and writes nothing to standard error.

The following server fails on every request and collects the errors in a table.

```lus
pledge("network")

local server = network.tcp.bind("127.0.0.1", 0)
local _, port = server:getsockname()
local errors = {}

local serving = coroutine.detach(coroutine.create(network.serve), server, function(req)
    error(`no route for $(req.path)`, 0)
end, {
    on_error = function(err)
        errors[#errors + 1] = err
    end,
})

local sock <close> = network.tcp.connect("127.0.0.1", port)
sock:send("GET /missing HTTP/1.1\r\nHost: localhost\r\n\r\n")
print(vector.tostring(sock:receive("*l")))  --> HTTP/1.1 500 Internal Server Error
sock:receive("*a")
print(errors[1])  --> no route for /missing

coroutine.close(serving)
server:close()
```

### Options

`options` is a table with any of these fields.

| Field | Value |
| --- | --- |
| `idle_timeout` | How many seconds a connection may spend without progress. The default is 60. A negative value removes the limit. |
| `max_connections` | How many connections the server keeps open at once. The default is half of the file descriptors that the process may open, up to 65536. |
| `on_error` | A function that receives the error object of a failed handler in place of the line on standard error. |
| `drain_timeout` | How many seconds the open connections may take to finish after the server stops. The default is 10. A negative value removes the limit, and `0` closes them at once. |
| `tls` | A table with the PEM text of the certificate `cert` and of the private key `key` of the server, for HTTPS. A list of such tables holds one certificate for each name. |

A connection makes progress when the server reads a part of a request from it or writes a part of a response to it. A connection that makes no progress for `idle_timeout` seconds closes, whether it is between two requests or has stopped reading its response. A connection that stops in the middle of a request receives a 408 response before it closes. The head of a request has `idle_timeout` seconds in all from its first byte, so a client that sends its head a few bytes at a time receives the 408 response too. The time that the handler takes is excluded from the timeout.

While `max_connections` connections are open, further clients wait in the queue of the system until a connection closes and the server accepts the next one. When the system has no file descriptor or no memory left for a new connection, the server waits until a connection closes or a short time passes, then accepts again.

### Stopping the server

Closing the coroutine that runs `network.serve` stops the server gracefully. `serve` accepts no new connection, and a server that `serve` bound itself closes. A connection that waits between two requests closes at once. A connection in the middle of a request finishes it, sends its response with `Connection: close`, and closes. The connections still open after `drain_timeout` seconds close without their responses. [Stopping a server gracefully](/manual/processes#stopping-a-server-gracefully) closes the coroutine when the program receives a signal.

### HTTPS

With the `tls` option, `serve` answers HTTPS. The handler works as it does for HTTP, and an upgrade with the status 101 hands the function a TLS socket, so a WebSocket over HTTPS works the same way. When the option lists several certificates, the server picks the one whose name matches the name that the client asks for through SNI, and the first certificate otherwise. The server reads the certificates when `serve` starts, so a program that renews its certificates calls `serve` again to use them.

```lus nocheck
pledge("network", "fs:read=/etc/letsencrypt/live/example.com/**")

local function read(path)
    local f <close> = io.open(`/etc/letsencrypt/live/example.com/$path`)
    return f:read("a")
end

network.serve("0.0.0.0", 443, function(req)
    return 200, "hello over TLS\n"
end, { tls = { cert = read("fullchain.pem"), key = read("privkey.pem") } })
```

### Limits

The server limits the size of a request so that a client cannot exhaust its memory. The request line and the headers of a request are limited to 64 KiB and 128 header lines. `req.body` holds at most 16 MiB. A chunked body gives each chunk size as hexadecimal digits alone, on a line limited to 1 KiB. The chunk lines and trailers of a chunked body are limited to 64 KiB plus 8 bytes for every byte of the body. The server answers a head over a limit with 431 and a malformed head with 400 before the handler runs. A body that breaks its framing or its limit raises an error in the handler that reads it. When that error ends the handler, the server answers 400, 413, or 431. The connection closes after each of these answers.
