The Lus 2.0 runtime compiles to a WebAssembly module for `wasm32-wasi`. The `lus-wasm` package pairs it with a small JavaScript host that runs programs in browsers, web workers, and Node. The [playground](/playground) and the [VS Code extension](/manual/ide-setup) both run Lus through this package, so they execute exactly the same runtime as the native interpreter.

## The module

The module is built from the same Zig sources as the native interpreter.

```sh
cd runtime
zig build wasm
```

The build writes `zig-out/wasm/lus.wasm`. It keeps the safety checks of a ReleaseSafe build, because the playground runs untrusted code and a failed check must stop the program cleanly. Passing `-Dwasm-optimize=small` produces a module about 15 percent smaller without them. In the repository, `mise run wasm` builds the module and copies it into the package.

The module is a WASI reactor without a `main`. It exports every function of the [embedding API](/manual/acquis-41) in `lus.h`, a few helpers for the JavaScript host, and its memory. SQLite and the [`vector.archive`](/manual/acquis-26) codecs are included. The network and worker libraries are left out, since WASI provides neither sockets nor threads, and `io.popen` and `os.execute` raise "not available on this platform" because the host runs no processes.

## Running programs

`Lus.load` compiles the module and returns a host. In a browser or a worker the module comes from bytes, a `Response`, or a URL. In Node, `loadLus` reads the packaged module from disk.

```js
import { Lus } from "lus-wasm/browser";

const lus = await Lus.load(new URL("/wasm/lus.wasm", location.href));
const result = lus.run('print("hello from " .. _VERSION)');
// { ok: true, stdout: "hello from Lus 2.0\n", stderr: "", output: "hello from Lus 2.0\n",
//   error: null, traceback: null, exitCode: 0, truncated: false }
```

`run(source, options)` runs a whole program in a fresh state and closes the state afterwards. The result separates standard output and standard error, and also gives them interleaved in write order as `output`. When the program fails, `error` holds the message and `traceback` the stack traceback, and a call to `os.exit` sets `exitCode`.

| Option | Meaning |
| --- | --- |
| `args` | Arguments, passed to the program as `...` and in `arg`. |
| `pledges` | Permissions granted by the host, as with `lus -P`. |
| `stdin` | The bytes that `io.read` returns. |
| `files` | Files written to the file system before the run. |
| `chunkname` | The chunk name used in messages. |
| `maxOutputBytes` | Stops capturing output after this many bytes. |

## Files and environment

One host holds any number of states, and they share an in-memory file system and one set of environment variables. `lus.fs` writes, reads, lists, and removes files, and `lus.env` holds the variables that `os.getenv` sees with the `env` pledge. A program reaches the file system through the usual `io` and `fs` functions, under the usual [permissions](/manual/acquis-10).

```js
lus.fs.writeFile("/data.txt", "one\ntwo\n");
const r = lus.run(`for line in io.lines("/data.txt") do print(#line, line) end`, {
  pledges: ["fs:read=/data.txt"],
});
console.log(r.output); // "3\tone\n3\ttwo\n"
```

The WASI layer is plain JavaScript with no dependencies. It captures standard output and standard error, serves standard input, keeps files in memory with `/` as the only preopened directory, and provides the clocks, randomness, and sleeping. Where the platform allows it, which includes Node and web workers, a sleep blocks with `Atomics.wait`.

## Long-lived states

`create()` returns a state with the standard libraries open, which keeps its globals between calls, and `destroy(state)` closes it. `execute(state, code)` runs interactive input the way the playground does: an expression prints its values, and anything else runs as a chunk.

```js
const state = lus.create();
lus.execute(state, "x = 10");   // ""
lus.execute(state, "x * 2");    // "20\n"
lus.destroy(state);
```

The same states host the language server. `loadLsp(state)` loads it, and `handleMessage(state, json)` and `handleFrame(state, frame)` dispatch JSON-RPC messages and return the framed responses, which is how the VS Code extension runs the server without a native `lus`.

Every function of `lus.h` is also available through `lus.exports` for hosts that need the C interface directly.

## Exits and traps

When a program calls `os.exit` or a safety check traps, the WebAssembly instance cannot continue. The host then starts a fresh instance over the same file system on the next call, and every state of the earlier instance becomes invalid. `run` reports a trap as an error with exit code 134, and the other calls throw.

## Motivation

### One runtime everywhere

Compiling the runtime itself to WebAssembly gives the browser the same parser, compiler, virtual machine, and standard library as the native interpreter. A program that runs in the playground runs the same way from the command line, and the editor extension analyzes code with the same language server everywhere.

### A host in plain JavaScript

WASI is a small, documented interface, so the host implements it directly in plain JavaScript. The package has no dependencies, every call returns ordinary JavaScript strings, and the module's own interface is the one the embedding API already defines.
