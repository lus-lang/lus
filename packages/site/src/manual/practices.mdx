A Lus program is easier to read, safer to run, and faster when it follows a few practices, each with a reason that determines when it applies. The [guide](/manual/guide) teaches the features that these practices use. [Lus for Lua programmers](/manual/lua) shows the Lus forms of common Lua idioms.

## File layout

Arrange a file in three parts: the globals it uses, the permissions it needs, and then its own code as locals. The top of the file then shows a reader which globals and permissions the file depends on.

The first part is one `global` statement that names every global the file uses, including the names of the standard library. In a file with such a statement, any other undeclared name is a compile error, `variable 'NAME' not declared`, so a misspelled name is caught before the program runs. The `pledge` calls follow, then the locals that make up the rest of the file. The following file splits the `PATH` environment variable into its directories.

```lus
global fs, os, pledge, print, string

pledge("env=PATH")
pledge("seal")

local function search_path()
    return string.split(os.getenv("PATH") or "", fs.path.delimiter)
end

print(#search_path() > 0)  --> true
```

`pledge` is an ordinary function, so a program may also call it later. A program that needs a permission only for an optional feature, such as an upload that the user requests with a command line option, pledges it at the point where the feature starts. Pledge every other permission at the top of the file, where a reader sees it first.

## Permissions

### Pledge the narrowest permission

Pledge a permission for only the files, hosts, or variables that the program uses. `fs:read=./**` permits reads below the current directory, while `fs` permits every filesystem operation. With a narrow pledge, a path built from bad input fails with a permission error at the operation that used it, where a broad pledge could let the same path read or overwrite an unrelated file. The following program may read only below the current directory.

```lus
global io, pledge, print

pledge("fs:read=./**")
pledge("seal")

print(io.open("./missing.txt"))
--> nil  ./missing.txt: No such file or directory  2
print(catch io.open("/etc/hosts"))
--> false  ...: permission "fs:read" denied for '/etc/hosts'
print(catch io.open("./report.txt", "w"))
--> false  ...: permission "fs:write" denied for './report.txt'
```

The first call is permitted and reports that the file does not exist. The other two raise a permission error, which `catch` returns as `false` and the message. [Restricting a permission to values](/manual/permissions#restricting-a-permission-to-values) describes the patterns that a value may hold for files, hosts, and environment variables.

### Reject and seal

After the pledges, reject the permissions that the program does not need. A rejection is a permission name with the prefix `~`, which removes the permission for the rest of the run so that a later `pledge` of it raises an error. After `pledge("seal")`, the set of permissions can no longer change and every later `pledge` returns `false`. Code that runs later, such as a module or a chunk that the program loads, therefore cannot acquire a permission that the program lacked at the seal.

```lus
global pledge, print

pledge("fs:read=./**", "~exec")
pledge("seal")

print(pledge("network:http"))  --> false
```

`lus check` reports a `pledge` that follows the seal with the code `pledge-after-seal`. The person who runs a script can also limit its permissions with `-P` on the command line, as [Granting from the command line](/manual/permissions#granting-from-the-command-line) describes.

### Load dependencies, then restrict

A package runs with the permissions of the program that loads it, so only the main program pledges restrictions and seals. A package documents the permissions its functions use in its header, so the program knows what to pledge. The program loads its dependencies first, while it still holds `load` and `network:http`, then rejects what it no longer needs and seals.

```lus nocheck
global pledge, require

pledge("load", "network:http=atmosp.here", "fs:read=./data/**")

local dates = require("https://atmosp.here/2.0/dates.lus")
local csvx = require("https://atmosp.here/2.0/csvx.lus")

pledge("~load", "~network", "seal")
```

A package never calls `pledge` to acquire a permission, since a program that has sealed would make that call fail. `lus check` reports a call of `pledge` at the top level of a package as `package-pledge`.

### Run untrusted parts with fewer permissions

When a program runs code from a less trusted source, such as a plugin or a callback from a user, run that code in a coroutine that holds fewer permissions than the program. A coroutine starts with the permissions of its creator, but the rejections and the seal that it makes apply only inside it. The following function runs a plugin that may compute and read files but can never start a process or use the network.

```lus
global coroutine, io, pledge, print

pledge("fs:read", "exec")

local function run_plugin(plugin)
    local co = coroutine.create(function()
        pledge("~exec", "~network")
        pledge("seal")
        return plugin()
    end)

    return coroutine.resume(co)
end

print(run_plugin(function()  --> true  false
    return (catch io.popen("true"))
end))

print((catch io.popen("true")))  --> true
```

The plugin fails to start a process, although the program holds `exec` and can still start one afterwards. [Permissions in coroutines](/manual/permissions#permissions-in-coroutines) describes the rules.

## Errors

### Raise errors and return absent results

A function can report that it has no result in two ways. Return `nil` and a message when the absence is an ordinary outcome that the caller checks immediately, as [`io.open`](/manual/api#io.open) does for a missing file. Raise an error when the caller cannot continue, as a function does when it receives an invalid argument. A raised error needs no check at each call, because it propagates to the nearest [`catch`](/manual/guide#errors), which can be several calls away. In the following example, `find_user` returns `nil` for an unknown name and `parse_port` raises an error for an invalid port.

```lus
global error, ipairs, print, tonumber

local users = { { name = "ada" } }

local function find_user(name)
    for _, user in ipairs(users) do
        if user.name == name then
            return user
        end
    end

    return nil, `no user named $name`
end

local function parse_port(text)
    local port = tonumber(text)

    if not port or port < 1 or port > 65535 then
        error(`invalid port: $text`, 0)
    end

    return port
end

print(find_user("bob"))  --> nil  no user named bob
print(catch parse_port("http"))  --> false  invalid port: http
```

`error` adds the position where it was called to a string message unless the level is `0`, as in `parse_port`, in which case it raises the message alone. Use level `0` for a message meant for the user of a program.

### Raise tables for errors that code inspects

Raise a table when the code that catches the error handles each kind of failure differently. A handler that reads `err.kind` keeps working when the wording of the message changes, while a handler that searches the message text breaks. `catch` returns the table unchanged, with every field it was raised with. Give the table a `__tostring` metamethod so that `tostring`, interpolation, and the report of an uncaught error print a readable message.

```lus
global error, print, setmetatable, tostring

local AppError = {}

AppError.__tostring = function(e)
    return `$(e.kind): $(e.message)`
end

local function fail(kind, message)
    error(setmetatable({ kind = kind, message = message }, AppError))
end

local ok, err = catch fail("config", "missing key 'port'")
print(ok, err.kind)  --> false  config
print(tostring(err))  --> config: missing key 'port'
```

### Release resources with `<close>`

Declare a file, a socket, or a database handle with the `<close>` attribute so that Lus closes it when the variable goes out of scope, whether the block ends normally or with an error. Without the attribute, an error between opening and closing would leave the resource open. In the following example, `save` raises an error before it could call `close`, but Lus still closes the file, so the data written before the error is on disk.

```lus
global error, fs, io, os, pledge, print

pledge("fs")

local function save(path)
    local f <close> = io.open(path, "w")
    f:write("partial")
    error("disk full", 0)
end

local path = os.tmpname()
print(catch save(path))  --> false  disk full

local f <close> = io.open(path)
print(f:read("a"))  --> partial
fs.remove(path)
```

## Text and bytes

Keep text in strings and raw bytes in vectors. A string is always valid text whose operations count characters, so bytes that are not text, such as an image or a compressed block, belong in a [vector](/manual/text#vectors), which is a buffer of bytes. Files opened in binary mode, sockets, [`string.pack`](/manual/api#string.pack), and the compressors all produce vectors. The following program writes a binary header to a file and reads it back.

```lus
global fs, io, os, pledge, print, string, vector

pledge("fs")

local path = os.tmpname()
local out = io.open(path, "wb")
out:write(string.pack("<c4I2I2", "LUSB", 1, 3))
out:close()

local f <close> = io.open(path, "rb")
local bytes = f:read("a")
print(#bytes, vector.unpack(bytes, 0, "<c4I2I2"))  --> 8  LUSB  1  3  8
fs.remove(path)
```

Convert bytes to text once, where they enter the program, with [`vector.tostring`](/manual/api#vector.tostring), so that the rest of the program works with strings, which are always valid. The default mode, `"strict"`, is for data that must be valid and raises an error that names the offset of the first invalid byte. The mode `"lossy"` is for text that is only displayed and replaces each invalid sequence with U+FFFD. The following example converts a vector with one invalid byte in both modes.

```lus
global print, vector

local v = vector.fromstring("ok")
vector.resize(v, 3)
vector.set(v, 2, 0xFF)

print(catch vector.tostring(v))  --> false  ...: invalid UTF-8 at byte 2
print(vector.tostring(v, 0, 3, "lossy"))  --> ok�
```

[Text and bytes](/manual/text) describes strings, vectors, transcoding, and compression in full.

## Numbers

Lus has several kinds of number, each meant for a kind of quantity.

- An integer is a 64-bit number for counts and indexes, whose arithmetic is exact within that range.
- A float is for a measurement or a ratio, where a small rounding error is acceptable.
- A decimal is for money and for any other quantity that must keep its exact fractional part.
- A bigint is for an integer that may exceed 64 bits, such as an identifier from another system.

Use integers and floats by default, because their arithmetic is the fastest. Use decimals and bigints where a rounded or wrapped result would be wrong, which matters most for data that comes from outside the program. By default, `fromjson` reads a number with a fraction as a float and raises `number out of range` for an integer beyond 64 bits. With the option `{ exact = true }`, it reads such an integer as a bigint and a number with a fraction as a decimal, so an amount of money keeps the digits it was written with.

```lus
global fromjson, math, print

local order = fromjson('{"id": 12345678901234567890, "total": 59.70}', { exact = true })

print(math.type(order.id), order.id)  --> bigint  12345678901234567890
print(math.type(order.total), order.total)  --> decimal  59.70
print(order.total * 3)  --> 179.10
```

Arithmetic between a decimal and a float raises an error, because the result could not be exact. Convert one side first, with [`decimal`](/manual/api#decimal) or [`tonumber`](/manual/api#tonumber). [Values and types](/manual/guide#values-and-types) in the guide describes each kind of number.

## Modules

Write a module as a file that builds a local table of its public functions and returns it. Everything else in the file is local, so a module adds no globals and two modules can never overwrite each other's names. The following file is a module with one public function and one private helper.

```lus
-- geometry.lus
global math

local M = {}

local function square(x)
    return x * x
end

function M.distance(a, b)
    return math.sqrt(square(b.x - a.x) + square(b.y - a.y))
end

return M
```

A program loads the module with `require`, which runs the file and returns its table on the first `require` of a name, then returns the same table on every later one. A [`from`](/manual/guide#tables) declaration copies named fields of the table into locals.

```lus nocheck
global pledge, print, require

pledge("fs:read", "load")

local distance from require("geometry")
print(distance({ x = 0, y = 0 }, { x = 3, y = 4 }))   --> 5.0
```

Loading a module from a file requires the `load` permission and `fs:read` for the file. A program that seals its permissions without them must be started with `--include` for each of its modules, which the interpreter compiles when it starts so that `require` loads them from memory. To distribute a program, [`lus build`](/manual/tools#standalone-executables) bundles a script and the modules it requires into one executable.

## Concurrency

Lus does several things at once with detached coroutines or with workers. Use detached coroutines for work that waits, such as many network connections. Use workers for work that computes, such as processing a large data set on every processor.

Detached coroutines share one thread. Each runs until it waits for a socket, yields, or ends, then another one runs, so one thread can serve thousands of connections with code that reads from top to bottom. Two coroutines never compute at the same moment. A worker is a separate instance of the runtime on its own thread, so workers compute in parallel. Workers share no variables and exchange copies of values as messages. The following program splits a sum over two workers, each of which runs the script `squares.lus` on half of the range and sends its result with `worker.message`.

```lus nocheck
global pledge, print, worker

pledge("fs:read", "load")

local a = worker.create("squares.lus", 1, 500000)
local b = worker.create("squares.lus", 500001, 1000000)
print(worker.receive(a) + worker.receive(b))
```

Give a worker its data as arguments or as messages. A table arrives as a copy, while a vector is moved: the receiver gets its bytes and the vector of the sender becomes empty, so a large buffer is sent without a copy. Functions, coroutines, userdata, and enum members cannot be sent. [Coroutines and workers](/manual/concurrency) describes both tools with complete programs, including detached coroutines that serve network connections and workers that share a computation.

## Testing

Put the tests of a module in a file beside it whose name ends in `_test.lus`. Write each test as a local function whose name ends in `_test`. `lus test` finds these files without configuration and runs them in parallel, each in its own process and temporary directory, so a test file cannot leave globals or files behind for another.

Several features of the runner keep tests short. A plain `assert` on a comparison reports the values of both sides when it fails. A table named `NAME_cases` runs `NAME_test` once per entry, which tests many inputs with one function. The helper `raises` checks that a call raises an error that matches a pattern. The following file tests a function that converts a title to a URL slug.

```lus
-- slug_test.lus
global assert, error, raises, string, type

local function slug(title)
    if type(title) ~= "string" then
        error("title must be a string", 0)
    end

    return (string.lower(string.trim(title)):gsub("%s+", "-"))
end

local slug_cases = {
    { "Hello World", "hello-world" },
    { "  Lus  ", "lus" },
}

local function slug_test(title, want)
    assert(slug(title) == want)
end

local function bad_input_test()
    raises(function()
        slug(42)
    end, "must be a string")
end
```

Run the code blocks of your documentation with `lus test --doc`, so that an example in a Markdown file fails a test when the code it shows stops working. [Testing](/manual/testing) describes the runner in full.

## Formatting and checking

Run the formatter, the checker, and the tests on every change, in continuous integration. `lus fmt --check` lists the files whose layout differs from the standard one, so a review never has to discuss layout. `lus check` reports mistakes that would otherwise appear only when the affected line runs: undeclared and unused names, unreachable code, and a `pledge` after the seal. Both commands exit with status 1 when they report anything, so a build fails on them.

```sh
lus fmt --check src
lus check src
lus test
```

`lus fmt --write src` applies the layout in place. [Developer tools](/manual/tools) lists every diagnostic of `lus check`.

## Performance

On macOS and Linux, Lus compiles the code that runs often to machine code. A first compiler translates a function once it has run many times, then an optimizing compiler recompiles the code that keeps running, using the types of the values that the code has handled. Code is therefore fastest when the values at each operation keep the same type. These practices matter only in a loop that runs millions of times.

### Build records in one constructor

Create each kind of record in one table constructor that names every field, so that Lus reads the number of fields from the constructor and allocates exactly the memory they need. A table that receives its fields one assignment at a time grows in steps and ends up larger. Records with the same fields in every instance also keep field access fast. In the following example, the function `point` is the only place that creates points.

```lus
global print

local function point(x, y)
    return { x = x, y = y }
end

local points = {}

for i = 1, 1000 do
    points[i] = point(i, 2 * i)
end

local sum = 0

for i = 1, #points do
    sum = sum + points[i].x + points[i].y
end

print(sum)  --> 1501500
```

### Keep the elements of an array one kind

Fill an array with elements of one kind: all integers, all floats, all strings, or all tables. Lus stores such an array compactly. The first element of another kind converts the whole array to a general form that takes more memory per element and is slower to read. An integer in an array of floats counts as another kind, so write `0.0` where the array holds floats.

```lus
global math, print

local weights = {}

for i = 1, 8 do
    weights[i] = 0.0
end

weights[3] = 1.5

print(math.type(weights[1]), weights[3])  --> float  1.5
```

If the loop stored `0`, the array would hold integers, which the store of `1.5` would then convert.

### Prefer locals and small functions

Keep the variables that a hot loop updates in locals. A local is a slot of the running function, while a global is a field of the global table, so every access to a global is a table access. Library functions need no local copy, because a call to `math.sqrt` in a loop runs as fast as a call to a local that holds the same function.

Split code into small functions without concern for the cost of a call, because the optimizing compiler places the body of a small function directly in its caller. The helper `length` in the following example therefore costs the same as its expression written in the loop.

```lus
global math, print

local function length(x, y)
    return math.sqrt(x * x + y * y)
end

local total = 0.0

for i = 1, 1000 do
    total = total + length(i, i)
end

print(math.floor(total))  --> 707813
```

Define a function outside a hot loop when possible, because a function expression inside a loop creates a new function value on every iteration, which costs an allocation each time.

### Count hot loops over arrays

Iterate a hot loop over an array with a numeric `for` that counts up by one. The optimizing compiler checks the bounds of the array once, before such a loop, while a loop with `ipairs` or `pairs` calls an iterator on every step. On a loop that sums a million integers, the numeric form runs several times faster. `ipairs` is the clearer choice everywhere else.

```lus
global print

local values = { 4, 8, 15, 16, 23, 42 }

local total = 0

for i = 1, #values do
    total = total + values[i]
end

print(total)  --> 108
```

### Join many strings with `table.concat`

To build a long string from many pieces, collect the pieces in a table and join them once with [`table.concat`](/manual/api#table.concat). `s = s .. piece` in a loop copies the whole string built so far on every iteration, so the work grows with the square of the length. `table.concat` measures the result first and writes each piece once. A few concatenations, or an interpolated string outside a loop, are fast enough as they are.

```lus
global print, table

local parts = {}

for i = 1, 5 do
    parts[#parts + 1] = `item $i`
end

print(table.concat(parts, ", "))  --> item 1, item 2, item 3, item 4, item 5
```

### Measure before tuning

Measure a change before keeping it, because a guess about speed is often wrong. [`os.clock`](/manual/api#os.clock) returns the processor time that the program has used, so the difference between two calls is the time of the code between them.

```lus
global os, print

local start = os.clock()
local total = 0

for i = 1, 1000000 do
    total = total + i
end

print(total, os.clock() - start < 5)  --> 500000500000  true
```

To learn whether the compilers matter for a program, compare a default run with a run under `LUS_JIT=off`, which makes Lus interpret the whole program.

```sh
LUS_JIT=off lus app.lus
lus app.lus
```

Machine code never runs under the debugger or while a hook set with `debug.sethook` is active, so a program measured there runs slower than it does normally.
