Workers provide concurrency through separate Lus interpreter states scheduled on a process-wide thread pool. Each state has its own globals, stack, garbage collector, and message queues. The states still share one operating system process and the runtime worker pool. The host process remains the security boundary, while workers isolate interpreter state and message data.

## Creating a worker

`worker.create(path, ...)` loads a Lus script in a new state and returns a worker handle. The additional arguments are serialized into the new state and are available through the script's varargs.

```lus
-- main.lus
local worker_handle = worker.create("processor.lus", {1, 2, 3}, "sum")
```

```lus
-- processor.lus
local values, operation = ...
```

Nil, booleans, integers, floats, strings, and tables can cross a worker boundary. Tables are deep-copied and may nest up to 100 levels. Functions, threads, userdata, vectors, enums, and queries produce a serialization error. A worker therefore receives independent values and cannot mutate a table in its parent state.

`worker.status(handle)` returns `"running"` while the script is active and `"dead"` after it finishes or raises an error.

## Worker to parent messages

Inside a worker state, `worker.message(value)` appends a serialized value to the worker's outbox. The parent calls `worker.receive(handle)` to wait for and deserialize the next value.

```lus nocheck
-- processor.lus
global worker

local values = ...
local total = 0
for _, value in ipairs(values) do
    total = total + value
end
worker.message(total)
```

```lus nocheck
-- main.lus
global worker

local handle = worker.create("processor.lus", {1, 2, 3})
local total = worker.receive(handle)
assert(total == 6)
```

`worker.receive` accepts multiple handles. It waits until at least one handle has a message or reaches a terminal state, then returns one aligned result per handle. A handle without a ready message contributes `nil`.

```lus nocheck
local first = worker.create("task.lus", "first")
local second = worker.create("task.lus", "second")

local first_message, second_message = worker.receive(first, second)
if first_message then print("first:", first_message) end
if second_message then print("second:", second_message) end
```

## Parent to worker messages

The parent uses `worker.send(handle, value)` to append a value to the worker's inbox. The worker-only `worker.peek()` function blocks until it can return the next inbox value.

```lus nocheck
-- main.lus
worker.send(handle, {command = "start"})
```

```lus nocheck
-- processor.lus
global worker

local message = worker.peek()
if message.command == "start" then
    run()
end
```

Both directions preserve message order within a queue. Serialization happens before a value enters the destination queue.

## Errors

An error from the worker script is raised by `worker.receive`. A catch exposes that error through the normal `false, error` result.

```lus
local ok, result = catch worker.receive(handle)
if not ok then
    print("Worker failed:", result)
else
    process(result)
end
```

A worker that has finished and has no queued message produces `nil` from `worker.receive`.

`os.exit` terminates the process when called by the main interpreter. Inside a worker it raises the catchable error `"os.exit is unavailable in a worker"`. A worker can catch that error and continue. If it remains uncaught, `worker.receive` raises it in the parent like any other worker execution error.

## Permissions

Creating a worker requires `load` and the `fs:read` authority for its script path. The worker inherits the parent's effective pledges in sealed form. Code inside the worker can narrow those permissions with `pledge`, and the sealed state keeps its authority within the inherited set.

## Scheduling

The runtime initializes a fixed-size pool of operating system threads and schedules worker states over that pool. This M:N model supports more worker states than pool threads while keeping resource use bounded. Blocking worker operations cooperate with the pool so other runnable states can continue.
