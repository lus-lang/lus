The `lus` executable runs Lus programs and provides the tools of a Lus project as commands, such as the test runner, the formatter, and the checker. [Testing](/manual/testing) and [Developer tools](/manual/tools) describe how to use the tools.

## lus

```
lus [options] [script [args]]
lus <command> [arguments]
lus +VERSION [arguments]
```

`lus script.lus` runs a script and passes it the arguments after its name, which the script reads from `...` and from the table `arg`. With no script and no `-e`, `lus` starts an interactive session that runs each line as it is entered. When the first argument is the name of a command, `lus` runs that command.

| Command | Purpose |
| --- | --- |
| `run` | Run a script. `lus run script.lus` is the same as `lus script.lus`. |
| [`test`](#lus-test) | Run the tests of a project. |
| [`fmt`](#lus-fmt) | Format source files. |
| [`check`](#lus-check) | Find errors and likely mistakes without running the code. |
| [`doc`](#lus-doc) | Generate API documentation from doc comments. |
| [`ast`](#lus-ast) | Print the syntax tree of a file as JSON. |
| [`build`](#lus-build) | Bundle a script and its modules into a standalone executable. |
| [`compile`](#lus-compile) | Compile a script to a binary chunk. |
| [`debug`](#lus-debug) | Run a script under a debugger. |
| [`help`](#lus-help) | Print the standard library reference for a name. |
| [`agents`](#lus-agents) | Set a project up for coding agents. |
| [`version`](#lus-version) | Install, list, and select releases of Lus. |

### Options

The options come before the script name, because `lus` passes everything after the script name to the script.

| Option | Effect |
| --- | --- |
| `-e stat` | Run the string `stat` as a chunk, for a one-line program such as `lus -e 'print(2^10)'`. The option may repeat. |
| `-i` | Enter interactive mode after `script` ends, with its globals in place, to inspect the state it left. |
| `-l mod` | Require the module `mod` and store it in the global `mod` before the script runs. |
| `-l g=mod` | Require the module `mod` and store it in the global `g`. |
| `-P perm`, `--pledge perm` | Grant a [permission](/manual/permissions) to the script, such as `-Pfs:read` or `-Pnetwork`. Once the command line grants a permission, the script may pledge only what the command line grants. Use this option to limit a script that you have not read. |
| `-F name[=value]`, `--flag name[=value]` | Define a build flag, which the script reads from the readonly table `flags`. A flag with no value is `true`. A numeric value is a number. Any other value is a string. The compiler removes the branch of an `if flags.name` or `if not flags.name` that can never run with the given flags, so debugging code behind a flag costs nothing when the flag is off. |
| `--include path[:alias]` | Compile a module file, or every module in a directory, when the interpreter starts. `require` then loads the module from memory with no `load` or `fs:read` permission, so a program that has sealed its permissions can still require it. The alias is the name of the module. |
| `--readonly-env` | Make the global table and the standard library tables readonly once the script starts. An assignment to a global or to a library field then raises `attempt to modify a readonly table`, which protects a program from code that replaces a library function. |
| `--offline` | Load [remote modules](/manual/guide#modules-from-the-network) only from the module cache. A module that the cache lacks raises an error at its `require`. |
| `--reload` | Ask the server of every remote module whether it changed before the program runs, even when the cached copy is recent. |
| `--no-prefetch` | Download nothing before the program runs. Each remote module is downloaded at its `require`, with a warning. |
| `--gc-pause N` | Let the heap grow by N percent of its live size before the next collection starts. A lower value uses less memory and more processor time. |
| `-W` | Turn warnings on. [`warn`](/manual/api#warn) then writes its messages to standard error. |
| `-E` | Ignore the environment variables that configure the interpreter, such as `LUS_PATH` and `LUS_JIT`. |
| `--dis` | Print the bytecode of the script and exit without running it. The script is compiled with the flags given with `-F`. |
| `-v`, `--version` | Print the version and exit. |
| `-h`, `--help` | Print the commands and options and exit. |
| `--` | Stop handling options, for a script whose name starts with a dash. |
| `-` | Stop handling options and run standard input as the script. |

### Environment variables

| Variable | Effect |
| --- | --- |
| `LUS_PATH` | The initial value of [`package.path`](/manual/api#package.path), the list of templates that `require` searches. |
| `LUS_JIT` | The setting of the JIT compiler. `on`, the default, compiles the functions that run often. `off` interprets everything. `baseline` uses only the first tier. `eager` and `opt-eager` compile every function on its first call, which is useful for tests. |
| `LUS_JIT_THRESHOLD` | How many calls and loop iterations a function makes before the JIT compiles it. Change it to measure how the threshold affects the speed of a program. |
| `LUS_HOME` | The directory that holds installed releases and the module cache, by default `~/.lus`, or `%LOCALAPPDATA%\lus` on Windows. |
| `LUS_RELEASE_URL` | The address of a mirror of the release index that [`lus version`](#lus-version) reads, in place of `https://lus.dev/releases/`. |
| `LUS_GC_THREADS` | The number of threads that the garbage collector marks with. The default uses up to eight and leaves one processor free. A lower value, such as `1`, leaves more processor time to other programs on the machine. |

### Exit status

`lus` exits with status 0 when the script ends normally. When the script does not catch an error, `lus` prints the error and a traceback to standard error and exits with status 1. A script sets another status with [`os.exit`](/manual/api#os.exit).

## lus test

```
lus test [options] [path ...]
```

Runs the tests in the named files, or in every `*_test.lus` file inside the named directories. With no path, it searches the current directory. Files run in parallel, each in its own process and temporary directory. [Testing](/manual/testing) describes how to write tests.

| Option | Effect |
| --- | --- |
| `--filter TEXT` | Run only the tests whose names contain `TEXT`. |
| `-u`, `--update` | Rewrite the snapshots that no longer match. |
| `--doc` | Run the ` ```lus ` code blocks of Markdown files in place of test files, which keeps the examples of documentation correct. |
| `-v` | List the skipped tests of passing files too. |
| `--json` | Print one JSON record per test, for other tools to read. |
| `--jobs N` | Run at most N files at once. The default is the number of processors. |
| `--timeout S` | Stop a file that writes no output for S seconds. The default is 60. |
| `--file-timeout S` | Stop a file that runs longer than S seconds in all. The default is ten times the timeout. |

The exit status is 0 when every file passes, 1 when a test fails or a file cannot run, and 2 when a named path does not exist.

## lus fmt

```
lus fmt [--check] [--write] [--indent N] [path ...]
```

Gives source files one standard layout. With no option, it prints the formatted text of each file to standard output. For a directory, it formats every `.lus` file inside it. With no file, or with the file `-`, it reads standard input.

| Option | Effect |
| --- | --- |
| `--write` | Rewrite the files in place. |
| `--check` | List the files that are not formatted and change nothing. The exit status is 1 if the list has a file. Use this option in continuous integration. |
| `--indent N` | Use N spaces per indentation level. The default is 4. |

## lus check

```
lus check [--json] [--list] [path ...]
```

Finds errors and likely mistakes without running the code. It parses, lints, and compiles each file, then prints each problem as `file:line:column: severity: message [code]`. For a directory, it checks every `.lus` file inside it. Files named `*_test.lus` are checked with the conventions of `lus test`. The exit status is 1 when an error or a warning is reported. Hints alone leave it at 0. [Checking](/manual/tools#checking) lists the diagnostics.

| Option | Effect |
| --- | --- |
| `--json` | Print the diagnostics as one JSON array, for editors and other tools. |
| `--list` | Print every diagnostic code with its severity and summary. |

## lus doc

```
lus doc [-o DIR] [--format md|json] file ...
```

Generates reference documentation from the `---` doc comments of each file. Each file is one module. [Documentation](/manual/tools#documentation) describes the comments.

| Option | Effect |
| --- | --- |
| `-o DIR` | Write one file per module into `DIR`. Without it, the output goes to standard output. |
| `--format md\|json` | Choose Markdown, the default, or JSON. |

## lus ast

```
lus ast [--no-comments] [--no-recover] file
```

Prints the syntax tree of a file as JSON, for tools that analyze or transform Lus code. The tree has the same nodes as the result of [`debug.parse`](/manual/api#debug.parse). [Syntax trees](/manual/tools#syntax-trees) describes the tree.

| Option | Effect |
| --- | --- |
| `--no-comments` | Omit comments from the tree. |
| `--no-recover` | Stop at the first syntax error. Without it, the parser continues past an error and lists every error in the tree. |

## lus build

```
lus build [options] script
```

Bundles a script and the modules it requires into one executable, which runs on a machine that has neither `lus` nor the source files. The command finds every `require` whose argument is a string literal. [Standalone executables](/manual/tools#standalone-executables) describes the bundle.

| Option | Effect |
| --- | --- |
| `-o FILE` | Write the executable to `FILE`. The default is the script name without its extension. |
| `-P perm`, `--pledge perm` | Grant a permission every time the executable runs. |
| `-F name[=value]`, `--flag name[=value]` | Define a build flag for the bundled code. |
| `--include path[:alias]` | Bundle a module file or directory that no literal `require` names. |
| `--aot` | Compile the program to machine code from a training run, and start the executable from `lus-runtime`. [Compiling ahead of time](/manual/tools#compiling-ahead-of-time) describes it. |
| `--train args` | The arguments of the training run of `--aot`, separated by spaces. |
| `--aot-keep-jit` | Start the executable from the running `lus`, which keeps the JIT and the compiler. |
| `--aot-static` | Compile ahead of time into the executable itself, for a system without executable memory. |
| `--runtime FILE` | Start the executable from the runtime `FILE`. |
| `--link-object FILE` | Link the executable from the link object `FILE`, keeping only what the program reaches. [Linking the runtime](/manual/tools#linking-the-runtime) describes it. |
| `--link-all` | Keep every library function of the link object. |
| `--link-map FILE` | Write the size of each linked part of the runtime and what reached it. |

## lus compile

```
lus compile [options] script
```

Compiles a script to a binary chunk, which `lus` runs as it runs a script and `load` reads in binary mode. Loading a binary chunk skips parsing. A binary chunk can be distributed without its source. The default output is the script name with the extension `.lusc`. [Binary chunks](/manual/tools#binary-chunks) describes the format.

| Option | Effect |
| --- | --- |
| `-o FILE` | Write the chunk to `FILE`. |
| `-s`, `--strip` | Omit debug information, which makes the chunk smaller and removes line numbers from its error messages. |
| `-F name[=value]`, `--flag name[=value]` | Define a build flag, whose value is fixed in the chunk. |
| `-P perm`, `--pledge perm` | Grant a permission to the initializers of [`<meta>` variables](/manual/guide#values-computed-when-the-file-is-compiled), which run during the compilation. The chunk itself runs with the permissions of the command that runs it. |

## lus debug

```
lus debug [--stdio | --port N] [-P perm]... [script [args]]
```

Runs a script under the Debug Adapter Protocol, which editors such as VS Code use to set breakpoints, step through code, and inspect variables. An editor starts this command itself. [Debugger](/manual/tools#debugger) describes the features.

| Option | Effect |
| --- | --- |
| `--stdio` | Read requests from standard input and write replies to standard output. This is the default. |
| `--port N` | Accept one client on `127.0.0.1:N`, for an editor that connects to a running adapter. |
| `-P perm`, `--pledge perm` | Grant a permission to the program. |

## lus help

```
lus help [name | module | --search text]
```

Prints the reference of the standard library in the terminal. The reference is part of the executable, so it describes the version that is running. With a name such as `string.find` or `tcp_socket:receive`, it prints the signature, the permissions the call needs, the stability, and the description. With a module such as `fs.path`, it lists the entries of the module. With no argument, it lists the modules. When the name matches no entry, it lists the names that contain it and exits with status 1.

| Option | Effect |
| --- | --- |
| `--search text`, `-s text` | List the entries whose name or description contains `text`. |

## lus agents

```
lus agents init [dir]
```

Adds instructions for writing and testing Lus to a project, where coding agents read them. The command writes the agent skills of the running version into `dir/.agents/skills` and links `.claude/skills` to them, then adds a Lus section to `AGENTS.md`. `dir` defaults to the current directory. Running the command again updates the skills. The [agents page](/agents) lists the skills and the prompts to start from.

## lus version

```
lus version [list [--remote [channel]] | install request | use request | remove version | which [request]] [--json]
lus +request [arguments]
```

Installs releases of Lus side by side and selects the one that `lus` runs. A project written for an older release keeps running under that release while other projects use a newer one. The releases live in the Lus home, `~/.lus` by default, which [`LUS_HOME`](#environment-variables) changes. The installers put `~/.lus/bin` on `PATH`, where `lus` is the default release.

A request names a release. `2.0.3` is that exact release. `2.0` is the newest installed or published `2.0.x`. `2` is the newest `2.x.y`. `stable` and `unstable` are the newest releases of the two channels. The unstable channel holds weekly builds of the development branch.

| Command | Effect |
| --- | --- |
| `lus version` | Print the version of the running `lus`. |
| `lus version list` | List the installed releases and mark the default. `--remote` lists the published releases of a channel instead. |
| `lus version install request` | Download a release, verify its signature and digest, and install it. The first release installed becomes the default. |
| `lus version use request` | Make an installed release the default. |
| `lus version remove version` | Delete an installed release. The default release cannot be removed. |
| `lus version which [request]` | Print the path of the executable of an installed release, by default the default release. |

The following commands install the newest `2.0.x` release, make it the default, and print where it is.

```bash
lus version install 2.0
lus version use 2.0
lus version which
```

`lus +request` runs any command under another installed release. It must be the first argument. `lus +2.0 test` runs the tests of a project under the newest installed `2.0.x`, whatever the default is. `lus +request` never downloads, so a missing release fails with the command that installs it.

```bash
lus +2.0 test
lus +unstable app.lus
```

`--json` prints one JSON object per command for scripts. The output, the exit statuses, and the layout of the Lus home are the same in every release from 2.0 on. The exit status is 0 on success, 1 when a download or a file operation fails, 2 for malformed arguments, 3 when no release matches the request, 4 when a signature or a digest does not verify, and 5 when `remove` names the default release.
