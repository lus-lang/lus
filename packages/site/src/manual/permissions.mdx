A _permission_ is the right to perform one kind of sensitive operation, such as reading files, running commands, or sending HTTP requests. Lus checks the permission before every such operation and raises an error if the program does not hold it. A script started by the `lus` command holds no permissions and acquires the ones it needs by calling [`pledge`](/manual/api#pledge).

Permissions limit the damage that a faulty program can do. A script that pledges only `fs:read` for its log directory, then seals its permissions, cannot delete a file or contact a server, even when the script has a bug, when a module it loaded misbehaves, or when its input was written to mislead it. The person who runs a script can also set its permissions on the command line, without reading its code.

## Granting permissions

`pledge` takes one or more permission names and returns one boolean for each name, in order. A result is `true` when the program now holds the permission and `false` when the grant was refused.

```lus
print(pledge("fs:read"))              --> true
print(pledge("network:http", "env"))  --> true  true
```

An operation raises an error at the call when the program does not hold the permission that the operation requires. The following script lists a directory twice, failing the first time and succeeding the second time because the script has pledged `fs:read` in between.

```lus nocheck
local ok, err = catch fs.list(".")
print(ok, err)   --> false  script.lus:1: permission "fs:read" denied for '.'

pledge("fs:read")
print(#fs.list(".") > 0)   --> true
```

The error object is a string of the form `permission "NAME" denied for 'VALUE'`. The value is the path, URL, address, or variable name that the operation requested. For an operation without such a value, the message names the operation, as in `permission "exec" denied for os.execute`, or it ends after `denied`.

`pledge` is an ordinary function, so a program may call it at any point. Most programs pledge everything they need when they start, but a program may also pledge later, for example `network:http` once a command line option enables a feature that uses the network.

Every grant succeeds in a script that runs without the `-P` option. When the person or the host program that starts a script grants permissions itself, the script may pledge only what those grants cover, with `pledge` returning `false` for everything else. [Granting from the command line](#granting-from-the-command-line) and [Permissions in an embedding host](#permissions-in-an-embedding-host) describe the two cases. A refused grant raises no error, so the error comes later, from the operation that requires the permission.

## Permission names

A permission name is either a base permission, such as `fs`, or a base permission followed by `:` and one of its parts, such as `fs:read`. Granting a base permission grants every one of its parts. The following script pledges `fs`, which lets it both create a directory with `fs:write` and read the type of the directory with `fs:read`.

```lus
pledge("fs")

local base = os.tmpname()
local dir = base .. ".d"
fs.createdirectory(dir)
print((fs.type(dir)))   --> directory
fs.remove(dir)
fs.remove(base)
```

The standard library checks the following permissions.

| Permission | What it allows |
| --- | --- |
| `fs` | Every filesystem operation. |
| `fs:read` | Reading files, listing directories, and inspecting paths. |
| `fs:write` | Creating, changing, moving, and removing files, directories, and links. |
| `load` | Running code that the program loads while it runs, from a string or from a file. |
| `exec` | Running external commands with `os.execute` and `io.popen`. |
| `env` | Reading and setting environment variables. |
| `env:read` | Reading environment variables with `os.getenv`. |
| `env:write` | Setting and removing environment variables with `os.setenv`. |
| `network` | Every network operation. |
| `network:http` | HTTP and HTTPS requests with `network.fetch`. |
| `network:tcp` | Connecting TCP sockets and binding TCP servers. |
| `network:udp` | Opening, binding, and sending from UDP sockets. |
| `network:server` | Serving HTTP with `network.serve`. |

Several functions check more than one permission.

- [`load`](/manual/api#load) requires `load`. [`loadfile`](/manual/api#loadfile), [`dofile`](/manual/api#dofile), and a `require` that loads a file require `fs:read` for the file and `load` to run it. A `require` skips every file that it may not read, so it reports the module as not found.
- [`package.loadlib`](/manual/api#package.loadlib) requires `fs:read` and `load`.
- [`io.open`](/manual/api#io.open) requires `fs:read` to read and `fs:write` to write. A mode that does both, such as `"r+"`, requires both. [`io.tmpfile`](/manual/api#io.tmpfile) and [`os.tmpname`](/manual/api#os.tmpname) require `fs:write`.
- [`io.sqlite`](/manual/api#io.sqlite) requires `fs:read` for a database file, plus `fs:write` unless it opens the file read-only.
- [`worker.create`](/manual/api#worker.create) requires `load` and `fs:read` for the script of the worker.
- [`network.serve`](/manual/api#network.serve) requires `network:server` for the address it serves and `network:tcp` to bind it.

`pledge` also accepts the names `fs:exec`, `network:tls`, `ffi`, and `worker`, which are reserved for host programs and extensions. No standard library function checks them.

`pledge` raises an error for an unknown name, such as `unknown permission: 'bogus'`. It also raises an error for a part that the base permission lacks, such as `invalid fs subpermission 'nope'`. The name `"all"` grants every permission, but only the command line and a host program may use it, so a script that pledges `"all"` gets the error `permission "all" cannot be requested from scripts`.

## Restricting a permission to values

A permission can be limited to certain paths, hosts, or variable names, so the program holds only the access it uses. For example, a script that reads its own data directory pledges `fs:read=./data/*` and cannot read any other part of the disk.

The limit is a _value_ written after `=`. In a value, `*` matches any sequence of characters, including `/` and the empty sequence, while `?` matches exactly one byte.

### Filesystem values

A filesystem value is an absolute path or a path that starts with `.`, which Lus resolves against the working directory. Any other value raises the error `filesystem permission values must be an absolute path or start with '.'`. A value without a wildcard matches that one path. A value that ends in `/*` matches everything inside the directory but not the directory itself, so a program that also lists the directory pledges both forms.

The following script pledges read access to a data directory and to everything inside it, so listing the parent directory fails. The setup and the cleanup run in [coroutines](#permissions-in-coroutines), so the main script never holds their wider permissions.

```lus
-- Prepare a directory in a coroutine, whose permissions end with it.
local base, data = coroutine.wrap(function()
    pledge("fs")
    local base = os.tmpname()
    fs.createdirectory(base .. ".data/reports", true)
    io.open(base .. ".data/reports/q1.txt", "w"):close()
    return base, base .. ".data"
end)()

pledge(`fs:read=$data`, `fs:read=$data/*`)
print((fs.type(data)))                         --> directory
print((fs.type(data .. "/reports/q1.txt")))    --> file
print((catch fs.list(fs.path.parent(data))))   --> false

coroutine.wrap(function()
    pledge("fs:write")
    fs.remove(data, true)
    fs.remove(base)
end)()
```

Before Lus compares the granted path with the requested path, it makes both absolute and resolves their symbolic links. A link that leads out of a granted directory therefore gives no access to its target. If a requested file does not exist yet, Lus resolves its parent directory and appends the file name. On macOS, `/tmp` is a link to `/private/tmp`, so a grant for either name covers both. On Windows, matching ignores the case of ASCII letters and treats both `\` and `/` as separators.

### Network values

A network value has the form `host[:port][/path]`, where the host may contain `*`. The host part matches the host of the requested URL or address. When present, the port part matches its port and the path part matches the path of a requested URL. A value that starts with `http://` or `https://` matches the whole requested URL. `network.fetch` requests its URL, while TCP and UDP operations request `host:port`.

The following pledges limit HTTP requests to the `/v1/` paths of one host, TCP to the ports of `127.0.0.1`, and UDP to the hosts whose names end in `.internal.test`.

```lus nocheck
pledge("network:http=api.example.com/v1/*")
network.fetch("https://api.example.com/v1/users")   -- allowed
network.fetch("https://api.example.com/admin")      -- permission error

pledge("network:tcp=127.0.0.1:*")
pledge("network:udp=*.internal.test")
```

Lus compares the value with the host exactly as the program wrote it. A grant for `127.0.0.1` therefore does not cover a request to `localhost`.

### Environment values

An `env` value matches the name of the environment variable that [`os.getenv`](/manual/api#os.getenv) reads or [`os.setenv`](/manual/api#os.setenv) sets. The following script may read `HOME` and no other variable.

```lus
pledge("env:read=HOME")
print((catch os.getenv("HOME")))   --> true
print((catch os.getenv("PATH")))   --> false
```

The following script may read every variable and set only the variables whose names start with `APP_`.

```lus
pledge("env:read", "env:write=APP_*")
os.setenv("APP_MODE", "test")
print(os.getenv("APP_MODE"))                  --> test
print((catch os.setenv("PATH", "/tmp")))      --> false
```

### Several values

Each grant with a value adds that value to the permission. A check succeeds when any of the values matches.

A permission that has a value stays limited to its values, so a later grant of the same permission without a value returns `true` and changes nothing. The limit of a part also applies when its base permission was granted without a value. For example, `pledge("fs")` followed by `pledge("fs:read=./data/*")` permits reads only inside `data` and writes everywhere.

## Rejecting permissions

A program rejects a permission to make sure that no later code can acquire it. A name with the prefix `~` rejects that permission for the rest of the run, after which every check of the permission fails, even if the permission was granted before. A later `pledge` of the same name raises the error `permission "NAME" was rejected`. The following script grants `exec`, then rejects it, so running a command and pledging `exec` again both fail.

```lus
pledge("exec")
pledge("~exec")
print((catch os.execute("true")))   --> false
print((catch pledge("exec")))       --> false
```

Rejecting a base permission rejects every one of its parts. A later `pledge` of one of those parts returns `true`, but the operation still fails because the base permission stays rejected.

```lus
pledge("~network")
print(pledge("network:http"))                       --> true
print((catch network.fetch("http://127.0.0.1/")))   --> false
```

Rejecting a part leaves the other parts of its base permission as they were. The following program may read every file and write none.

```lus
pledge("fs", "~fs:write")
print((fs.type(".")))                       --> directory
print((catch fs.createdirectory("nope")))   --> false
```

## Sealing permissions

A program seals its permissions once it holds everything it needs, so that no code in the program, including modules and code that it loads later, can change them. Pledging the name `"seal"` seals the permissions. From then on, `pledge` returns `false` for every grant and every rejection, even for a permission the program already holds. The operations that were permitted before the seal stay permitted.

```lus
pledge("fs:read")
pledge("seal")
print(pledge("exec"))    --> false
print(pledge("~fs"))     --> false
print((fs.type(".")))    --> directory
```

`pledge` processes its arguments in order, so a program usually pledges and seals in one call.

```lus
print(pledge("fs:read=./data/*", "~exec", "seal"))   --> true  true  true
```

An unknown name still raises an error after a seal.

## Granting from the command line

The person who runs a script grants permissions with the `-P` option of `lus`, also written `--pledge`. The script holds these permissions from its first line, without a call to `pledge`. The option may appear several times and accepts every form that `pledge` accepts, including values, rejections, `seal`, and `all`.

```bash
lus -Pfs script.lus
lus --pledge=fs script.lus
lus -Pfs:read=/srv/app/* -Pnetwork:http script.lus
lus -P~exec script.lus
lus -Pall script.lus
```

When the command line grants at least one permission, those grants are the limit of the script. A `pledge` in the script returns `true` for what the command line already allows and `false` for anything else. A person can therefore run a script that they have not read, granting what the script is supposed to need so that every other sensitive operation fails. The following script runs under `lus -Pfs:read=/srv/app/* script.lus`.

```lus nocheck
print(pledge("fs:read=/srv/app/*"))   --> true
print(pledge("fs:write"))             --> false
print(pledge("network"))              --> false
```

A command line that only rejects permissions, such as `lus -P~exec`, sets no limit, so the script may pledge anything except what the command line rejected.

`lus` reads the script file under the same rules. When the command line grants a filesystem permission, the grant must cover reading the script file. Otherwise `lus` exits with the error `permission "fs:read" denied for 'script.lus'` before the script runs.

## Permissions in coroutines

Each coroutine has its own set of permissions, so a program can run a piece of code with fewer permissions than the rest of the program has. A coroutine starts with a copy of the permissions of the coroutine that created it, after which the two sets are independent. A grant, a rejection, or a seal inside the coroutine changes only the set of that coroutine. Later changes in the creator leave the set of the coroutine unchanged. In the following script, a coroutine rejects `env`, but the main program can still read environment variables afterwards.

```lus
pledge("fs:read", "env")

local co = coroutine.create(function()
    pledge("~env")
    return (catch os.getenv("HOME"))
end)

print(coroutine.resume(co))            --> true  false
print((catch os.getenv("HOME")))       --> true
```

The following function runs code that the program trusts less, such as a plugin, in a coroutine that rejects what the code must not use, seals its permissions, then calls the code. The rejections and the seal apply only to the coroutine, so the rest of the program keeps its permissions.

```lus
pledge("fs", "network", "exec")
local notes = os.tmpname()

local function run_restricted(fn, ...)
    local co = coroutine.create(function(...)
        pledge("~fs:write", "~network", "~exec", "seal")
        return fn(...)
    end)
    return coroutine.resume(co, ...)
end

print(run_restricted(function(path)
    local readable = catch fs.type(path)
    local writable = catch fs.remove(path)
    return readable, writable
end, notes))                           --> true  true  false
print((fs.type(notes)))                --> file
fs.remove(notes)
```

Restricted code can create a coroutine of its own to restrict other code further, because every coroutine starts with the permissions of its creator. [Detached coroutines](/manual/concurrency#detached-coroutines) follow the same rules.

## Permissions in workers

A [worker](/manual/concurrency#workers) starts with a sealed copy of the permissions that its creator held when it called `worker.create`. Code in the worker uses those permissions unchanged. Every `pledge` in a worker returns `false`, including a rejection, so a worker never holds more than its creator did. To give a worker fewer permissions, create it from a coroutine that has rejected the others.

## Permissions in an embedding host

A _host_ is a program that [embeds Lus](/manual/embedding) by calling its C interface. The host creates a _state_, which is one instance of the Lus runtime. A new state holds no permissions, so the host sets them with the following functions before it runs a script.

- `lus_grant` grants a permission, with the same names and values as `pledge`.
- `lus_reject` rejects a permission for the life of the state.
- `lus_seal` seals the set.

The rule of the [command line](#granting-from-the-command-line) applies here too: once the host grants anything, a script may pledge only what those grants cover. A host can also decide each request when a script makes it, for example by asking the user. Such a host installs a function with `lus_onrequest`, which Lus calls when a script pledges a permission that the host neither granted nor rejected. The function allows or refuses the grant.

An extension written in C declares permissions of its own with `lus_defcapability` and checks them with `lus_require` and `lus_allowed`. Scripts pledge them as they pledge the built-in permissions. [Embedding](/manual/embedding#permissions) shows each of these functions in use.
