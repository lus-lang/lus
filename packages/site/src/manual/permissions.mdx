A _permission_ is the right to perform one kind of sensitive operation, such as reading files, running commands, or sending HTTP requests. Lus checks the permission before every such operation and raises an error when the program does not hold it. A script started by the `lus` command holds no permissions, and it acquires the ones it needs by calling [`pledge`](/manual/api#pledge).

Permissions limit the damage a program can do when something in it goes wrong. A script that pledged only `fs:read` for its log directory and then sealed its permissions cannot delete a file or contact a server, whether the cause is a bug, a module it loaded, or input written to mislead it. Permissions also let the person who runs a script decide what it may do, from the command line, without reading its code.

## Granting permissions

`pledge` takes one or more permission names and returns one boolean for each of them, in order. A result is `true` when the program now holds the permission and `false` when the grant was refused.

```lus
print(pledge("fs:read"))              --> true
print(pledge("network:http", "env"))  --> true  true
```

An operation that needs a permission the program does not hold raises an error at the call. The following script fails at its first line and succeeds after it pledges `fs:read`.

```lus nocheck
local ok, err = catch fs.list(".")
print(ok, err)   --> false  script.lus:1: permission "fs:read" denied for '.'

pledge("fs:read")
print(#fs.list(".") > 0)   --> true
```

The error object is a string of the form `permission "NAME" denied for 'VALUE'`, where the value is the path, URL, address, or variable name that the operation asked for. An operation without such a value names itself, as in `permission "exec" denied for os.execute`, or ends the message after `denied`.

`pledge` is an ordinary function, so a program may call it at any point. Most programs pledge everything they need when they start. A program may also pledge later, for example only when a command line option asks for a feature that uses the network.

A script that runs without the `-P` option may pledge any permission, and the grant succeeds. When the person or the host program that starts the script grants permissions itself, the script may pledge only what those grants cover, and `pledge` returns `false` for everything else. [Granting from the command line](#granting-from-the-command-line) and [Permissions in an embedding host](#permissions-in-an-embedding-host) describe both cases. A refused grant raises no error, so the operation that needed the permission is what fails later.

## Permission names

A permission name is either a base permission, such as `fs`, or a base permission followed by `:` and one of its parts, such as `fs:read`. Granting a base permission grants every one of its parts.

```lus
pledge("fs")

local base = os.tmpname()
local dir = base .. ".d"
fs.createdirectory(dir)
print((fs.type(dir)))   --> directory
fs.remove(dir)
fs.remove(base)
```

The table below lists every permission that the standard library checks.

| Permission | What it allows |
| --- | --- |
| `fs` | Every filesystem operation. |
| `fs:read` | Reading files, listing directories, and inspecting paths. |
| `fs:write` | Creating, changing, moving, and removing files, directories, and links. |
| `load` | Running code that the program loads while it runs, from a string or from a file. |
| `exec` | Running external commands with `os.execute` and `io.popen`. |
| `env` | Reading environment variables with `os.getenv`. |
| `network` | Every network operation. |
| `network:http` | HTTP and HTTPS requests with `network.fetch`. |
| `network:tcp` | Connecting TCP sockets and binding TCP servers. |
| `network:udp` | Opening, binding, and sending from UDP sockets. |
| `network:server` | Serving HTTP with `network.serve`. |

Several functions check more than one permission.

- [`load`](/manual/api#load) requires `load`. [`loadfile`](/manual/api#loadfile), [`dofile`](/manual/api#dofile), and a `require` that loads a file require `fs:read` for the file and `load` to run it. A `require` skips every file that it may not read, so it reports the module as not found.
- [`package.loadlib`](/manual/api#package.loadlib) requires `fs:read` and `load`.
- [`io.open`](/manual/api#io.open) requires `fs:read` to read and `fs:write` to write. A mode that does both, such as `"r+"`, requires both. [`io.tmpfile`](/manual/api#io.tmpfile) and [`os.tmpname`](/manual/api#os.tmpname) require `fs:write`.
- [`io.sqlite`](/manual/api#io.sqlite) requires `fs:read` for a database file, and `fs:write` as well unless it opens the file read-only.
- [`worker.create`](/manual/api#worker.create) requires `load` and `fs:read` for the script of the worker.
- [`network.serve`](/manual/api#network.serve) requires `network:server` for the address it serves and `network:tcp` to bind it.

The runtime also knows the names `fs:exec`, `network:tls`, `ffi`, and `worker`, which are reserved for host programs and extensions. `pledge` accepts them, and no standard library function checks them.

`pledge` raises an error for a name it does not know, such as `unknown permission: 'bogus'`, and for a part that the base permission does not have, such as `invalid fs subpermission 'nope'`. The name `"all"` grants every permission, and only the command line and a host program may use it. A script that pledges it receives the error `permission "all" cannot be requested from scripts`.

## Restricting a permission to values

A permission may be limited to certain paths, hosts, or variable names, so that a program holds only the access it uses. A script that reads its own data directory pledges `fs:read=./data/*`, which leaves the rest of the disk closed to it.

The limit is a _value_ written after `=`. In a value, `*` matches any sequence of characters, including `/` and the empty sequence, and `?` matches exactly one byte.

### Filesystem values

A filesystem value is an absolute path, or a path that starts with `.` and is resolved against the working directory. Any other value raises the error `filesystem permission values must be an absolute path or start with '.'`. A value without a wildcard matches that one path. A value that ends in `/*` matches everything below the directory and leaves out the directory itself, so a program that also lists the directory pledges both forms.

```lus
-- Prepare a directory in a coroutine, whose permissions end with it.
local base, data = coroutine.wrap(function()
    pledge("fs")
    local base = os.tmpname()
    fs.createdirectory(base .. ".data/reports", true)
    io.open(base .. ".data/reports/q1.txt", "w"):close()
    return base, base .. ".data"
end)()

pledge(`fs:read=$data`, `fs:read=$data/*`)
print((fs.type(data)))                         --> directory
print((fs.type(data .. "/reports/q1.txt")))    --> file
print((catch fs.list(fs.path.parent(data))))   --> false

coroutine.wrap(function()
    pledge("fs:write")
    fs.remove(data, true)
    fs.remove(base)
end)()
```

Lus makes the granted path and the requested path absolute and resolves their symbolic links before it compares them. A link that leads out of a granted directory therefore gives no access to its target. A requested file that does not exist yet is resolved through its parent directory. On macOS, `/tmp` is a link to `/private/tmp`, and a grant for either name covers both. On Windows, paths match without regard to the case of ASCII letters, and `\` and `/` are both separators.

### Network values

A network value has the form `host[:port][/path]`, and the host may contain `*`. The host part matches the host of the requested URL or address. The port part, when present, matches its port, and the path part, when present, matches the path of a requested URL. A value that starts with `http://` or `https://` matches the whole requested URL. `network.fetch` requests its URL, and TCP and UDP operations request `host:port`.

```lus nocheck
pledge("network:http=api.example.com/v1/*")
network.fetch("https://api.example.com/v1/users")   -- allowed
network.fetch("https://api.example.com/admin")      -- permission error

pledge("network:tcp=127.0.0.1:*")
pledge("network:udp=*.internal.test")
```

A value matches the host as the program wrote it. A grant for `127.0.0.1` does not cover a request to `localhost`.

### Environment values

An `env` value matches the name of the environment variable that [`os.getenv`](/manual/api#os.getenv) reads.

```lus
pledge("env=HOME")
print((catch os.getenv("HOME")))   --> true
print((catch os.getenv("PATH")))   --> false
```

### Several values

Each grant with a value adds that value to the permission, and a check succeeds when any of its values matches.

A permission that holds a value stays limited to its values. A later grant of the same permission without a value returns `true` and changes nothing. The limit of a part also holds when its base permission was granted without a value, so `pledge("fs")` followed by `pledge("fs:read=./data/*")` permits reads only below `data` and writes everywhere.

## Rejecting permissions

A program rejects a permission to make sure that no later code can acquire it. A name with the prefix `~` rejects that permission for the rest of the run. Every later check of the permission fails, including when the permission was granted before, and a later `pledge` of the same name raises the error `permission "NAME" was rejected`.

```lus
pledge("exec")
pledge("~exec")
print((catch os.execute("true")))   --> false
print((catch pledge("exec")))       --> false
```

Rejecting a base permission denies every one of its parts. A later `pledge` of one of those parts returns `true`, and the operation is still denied because the base permission stays rejected.

```lus
pledge("~network")
print(pledge("network:http"))                       --> true
print((catch network.fetch("http://127.0.0.1/")))   --> false
```

Rejecting a part leaves the other parts of its base permission as they were. The following program may read every file and write none.

```lus
pledge("fs", "~fs:write")
print((fs.type(".")))                       --> directory
print((catch fs.createdirectory("nope")))   --> false
```

## Sealing permissions

A program seals its permissions once it holds everything it needs. From then on nothing in the program can change them, including modules and code that it loads later. The name `"seal"` does this. After it, `pledge` returns `false` for every grant and every rejection, even for a permission the program already holds, and the operations that were permitted before the seal stay permitted.

```lus
pledge("fs:read")
pledge("seal")
print(pledge("exec"))    --> false
print(pledge("~fs"))     --> false
print((fs.type(".")))    --> directory
```

A program usually pledges and seals in one call, since `pledge` handles its arguments in order.

```lus
print(pledge("fs:read=./data/*", "~exec", "seal"))   --> true  true  true
```

A name that `pledge` does not know still raises its error after a seal.

## Granting from the command line

The person who runs a script grants permissions with the `-P` option of `lus`, also written `--pledge`. The script holds these permissions from its first line, without a call to `pledge`. The option accepts every form that `pledge` accepts, including values, rejections, `seal`, and `all`, and it may repeat.

```bash
lus -Pfs script.lus
lus --pledge=fs script.lus
lus -Pfs:read=/srv/app/* -Pnetwork:http script.lus
lus -P~exec script.lus
lus -Pall script.lus
```

When the command line grants at least one permission, those grants are the limit of the script. A `pledge` in the script returns `true` only for what the command line already allows, and returns `false` for anything else. This is how a person runs a script that they have not read: they grant what the script is supposed to need, and every other operation fails. The following script runs under `lus -Pfs:read=/srv/app/* script.lus`.

```lus nocheck
print(pledge("fs:read=/srv/app/*"))   --> true
print(pledge("fs:write"))             --> false
print(pledge("network"))              --> false
```

A command line that only rejects permissions, such as `lus -P~exec`, sets no limit. The script may then pledge anything except what the command line rejected.

`lus` reads the script file under the same rules. When the command line grants a filesystem permission, the grant must cover reading the script file. Otherwise `lus` exits with the error `permission "fs:read" denied for 'script.lus'` before the script runs.

## Permissions in coroutines

Each coroutine has its own set of permissions, which lets a program run a piece of code with fewer permissions than the rest of the program has. A coroutine starts with a copy of the permissions of the coroutine that created it. From then on the two sets are independent. A grant, a rejection, or a seal inside the coroutine stays inside it, and later changes in the creator do not reach the coroutine.

```lus
pledge("fs:read", "env")

local co = coroutine.create(function()
    pledge("~env")
    return (catch os.getenv("HOME"))
end)

print(coroutine.resume(co))            --> true  false
print((catch os.getenv("HOME")))       --> true
```

The following function runs code that the program trusts less, such as a plugin. It creates a coroutine, rejects what the code must not use, and seals the set before it calls the code. The rejections and the seal end with the coroutine, so the rest of the program keeps its permissions.

```lus
pledge("fs", "network", "exec")
local notes = os.tmpname()

local function run_restricted(fn, ...)
    local co = coroutine.create(function(...)
        pledge("~fs:write", "~network", "~exec", "seal")
        return fn(...)
    end)
    return coroutine.resume(co, ...)
end

print(run_restricted(function(path)
    local readable = catch fs.type(path)
    local writable = catch fs.remove(path)
    return readable, writable
end, notes))                           --> true  true  false
print((fs.type(notes)))                --> file
fs.remove(notes)
```

Restricted code may restrict further in the same way, since every coroutine starts from the set of its creator. [Detached coroutines](/manual/concurrency#detached-coroutines) follow the same rules.

## Permissions in workers

A [worker](/manual/concurrency#workers) starts with a sealed copy of the permissions that its creator held when it called `worker.create`. Code in the worker uses those permissions as they are. Every `pledge` in a worker returns `false`, rejections included, so a worker never holds more than its creator did. A program that wants a worker with fewer permissions creates it from a coroutine that rejected the rest.

## Permissions in an embedding host

A _host_ is a program that [embeds Lus](/manual/embedding) through its C interface. The host creates a _state_, which is one instance of the Lus runtime. A new state holds no permissions, and the host sets them before it runs a script.

- `lus_grant` grants a permission, with the same names and values as `pledge`.
- `lus_reject` rejects a permission for the life of the state.
- `lus_seal` seals the set.

The rule of the command line applies. Once the host grants anything, a script may pledge only what those grants cover. A host that wants to decide each request itself, for example by asking the user, installs a function with `lus_onrequest`. Lus calls it when a script pledges a permission that the host neither granted nor rejected, and the function allows or refuses the grant.

An extension written in C declares permissions of its own with `lus_defcapability` and checks them with `lus_require` and `lus_allowed`. Scripts pledge them like the built-in ones. [Embedding](/manual/embedding#permissions) shows each of these functions in use.
