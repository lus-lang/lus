A _database_ stores records in a file where a program can search, change, and combine them. A database is useful when data must remain after the program ends, when the records are too many to keep in memory or to search with a loop, or when several changes must succeed or fail together. The SQLite database engine is built into Lus, so a program opens a database with [`io.sqlite`](/manual/api#io.sqlite) and needs nothing else installed.

A program controls a database with statements in _SQL_, which is a language made for databases. The SQLite documentation at [sqlite.org](https://sqlite.org/lang.html) describes the whole language.

The following program creates a database in memory, stores three books, and prints the books published after 1900.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (id INTEGER PRIMARY KEY, title TEXT NOT NULL, year INTEGER)")

db:run("INSERT INTO books (title, year) VALUES (?, ?)", "Emma", 1815)
db:run("INSERT INTO books (title, year) VALUES (?, ?)", "Dune", 1965)
db:run("INSERT INTO books (title, year) VALUES (?, ?)", "Ulysses", 1922)

for row in db:query("SELECT title, year FROM books WHERE year > ? ORDER BY year", 1900) do
    print(row.title, row.year)
end
--> Ulysses  1922
--> Dune  1965
```

## Opening a database

`io.sqlite(path)` opens the database file at `path` and returns a database handle, creating the file if it does not exist. The whole database is that one file, which can be copied or moved like any other file while no program has it open.

The path `":memory:"` opens a database that exists only in memory and whose contents are discarded when it is closed. An in-memory database is useful for tests and for data that a program queries but has no need to keep.

Opening a database file requires the `fs:read` and `fs:write` [permissions](/manual/permissions). SQLite keeps temporary files in the same directory as the database, with names that start with the name of the database file. A program that limits its permissions to the database therefore pledges the path followed by `*`.

```lus
pledge("fs:read=./library.db*", "fs:write=./library.db*")

do
    local db <close> = io.sqlite("library.db")
    print((fs.type("library.db")))  --> file
end

fs.remove("library.db")
```

The `<close>` attribute closes the database when the variable goes out of scope, as [Closing a database](#closing-a-database) describes.

## Creating a table

A database holds _tables_. A table has a fixed set of named _columns_ and any number of _rows_, like a spreadsheet. A table of books has one row per book and one column for each property of a book, such as its title.

The SQL statement `CREATE TABLE` defines a table. `db:exec(sql)` runs SQL text that needs no values from the program and returns nothing.

```lus
local db <close> = io.sqlite(":memory:")
db:exec([[
    CREATE TABLE IF NOT EXISTS books (
        id INTEGER PRIMARY KEY,
        title TEXT NOT NULL,
        author TEXT,
        year INTEGER
    )
]])
```

Each line between the parentheses defines one column by its name, its type, and optional rules.

- The type is the kind of value that the column holds: `INTEGER` for whole numbers, `REAL` for floats, `TEXT` for strings, and `BLOB` for bytes.
- `PRIMARY KEY` declares that the value of the column identifies each row. When a new row has no value for an `INTEGER PRIMARY KEY` column, SQLite stores a new number in it, so every book has a different `id`.
- `NOT NULL` makes the column required. Inserting a row without a title raises an error.
- With `IF NOT EXISTS`, the statement has no effect when the table already exists, so a program can run it every time it starts.

`exec` accepts several statements in one string, separated by semicolons, so a program can create all its tables with one call.

## Inserting rows

The SQL statement `INSERT INTO table (columns) VALUES (values)` adds one row. `db:run(sql, ...)` runs one statement that changes data and returns two integers: the number of rows that the statement changed and the `id` of the last inserted row.

Each `?` in the SQL is a _parameter_, which is a place for a value. `run` fills the parameters with its extra arguments, in order.

```lus
local db <close> = io.sqlite(":memory:")
db:exec(
    "CREATE TABLE books (id INTEGER PRIMARY KEY, title TEXT NOT NULL, author TEXT, year INTEGER)"
)

local changed, id = db:run(
    "INSERT INTO books (title, author, year) VALUES (?, ?, ?)",
    "Emma",
    "Jane Austen",
    1815
)
print(changed, id)  --> 1  1
```

A program must pass every value to a statement as a parameter. A program that builds the SQL text from a value, as in `"... VALUES ('" .. title .. "')"`, is open to an attack. A quote in the title ends the string inside the SQL, so SQLite runs the rest of the title as SQL. A person who types such a title into a form could delete or read the whole database, an attack called _SQL injection_. A parameter prevents it, because the database receives the value separately from the statement and never reads the value as SQL.

The following program stores a title that would delete the table if it were part of the SQL text.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (id INTEGER PRIMARY KEY, title TEXT NOT NULL)")

local title = "Robert'); DROP TABLE books; --"
db:run("INSERT INTO books (title) VALUES (?)", title)

for row in db:query("SELECT title FROM books") do
    print(row.title)  --> Robert'); DROP TABLE books; --
end
```

A statement with many values is easier to read with named parameters, each written as a `:` followed by a name. The single extra argument is then a table whose fields supply the parameters of the same names.

```lus
local db <close> = io.sqlite(":memory:")
db:exec(
    "CREATE TABLE books (id INTEGER PRIMARY KEY, title TEXT NOT NULL, author TEXT, year INTEGER)"
)

db:run("INSERT INTO books (title, author, year) VALUES (:title, :author, :year)", {
    title = "Dune",
    author = "Frank Herbert",
    year = 1965,
})
```

A column has no value in the new row when the statement omits it or when its value is `nil`. SQL calls the absence of a value `NULL`.

## Reading rows

The SQL statement `SELECT columns FROM table` reads rows. `db:query(sql, ...)` runs it and returns an iterator for a `for` loop. Each row is a table with one field per selected column, named after the column. `query` fills parameters as `run` does.

The following optional parts of a `SELECT` choose and arrange the rows.

- `WHERE condition` selects only the rows for which the condition is true, such as `year > 1900` or `author = ?`.
- `ORDER BY column` sorts the rows by a column. Adding `DESC` reverses the order. Without `ORDER BY`, the order of the rows is unspecified.
- `LIMIT n` returns at most `n` rows.

```lus
local db <close> = io.sqlite(":memory:")
db:exec(
    "CREATE TABLE books (id INTEGER PRIMARY KEY, title TEXT NOT NULL, author TEXT, year INTEGER)"
)
db:run("INSERT INTO books (title, author, year) VALUES (?, ?, ?)", "Emma", "Jane Austen", 1815)
db:run("INSERT INTO books (title, author, year) VALUES (?, ?, ?)", "Dune", "Frank Herbert", 1965)
db:run("INSERT INTO books (title, year) VALUES (?, ?)", "Beowulf", 1000)

for row in db:query("SELECT title, year FROM books WHERE year < ? ORDER BY year", 1900) do
    print(row.title, row.year)
end

--> Beowulf  1000
--> Emma  1815

for row in db:query("SELECT title FROM books ORDER BY year DESC LIMIT 1") do
    print(row.title)  --> Dune
end
```

A column that holds `NULL` is absent from its row table, so reading it gives `nil`. The condition `column IS NULL` matches such rows.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (title TEXT NOT NULL, author TEXT)")
db:run("INSERT INTO books (title) VALUES (?)", "Beowulf")

for row in db:query("SELECT title, author FROM books WHERE author IS NULL") do
    print(row.title, row.author)  --> Beowulf  nil
end
```

SQL can also compute one value from all the rows that a `SELECT` matches. `count(*)` is the number of rows. `min(column)`, `max(column)`, `sum(column)`, and `avg(column)` are the smallest value, the largest value, the sum, and the average of a column. Such a query returns one row. `AS name` gives a computed column a name, which is also the name of its field in the row table.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (title TEXT NOT NULL, year INTEGER)")
db:run("INSERT INTO books VALUES (?, ?)", "Emma", 1815)
db:run("INSERT INTO books VALUES (?, ?)", "Dune", 1965)

for row in db:query("SELECT count(*) AS total, min(year) AS oldest FROM books") do
    print(row.total, row.oldest)  --> 2  1815
end
```

A query produces its rows one at a time, so a program that needs all the rows after the loop stores them in an array.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (title TEXT NOT NULL)")
db:run("INSERT INTO books VALUES (?)", "Emma")
db:run("INSERT INTO books VALUES (?)", "Dune")

local titles = {}

for row in db:query("SELECT title FROM books ORDER BY title") do
    titles[#titles + 1] = row.title
end

print(table.concat(titles, ", "))  --> Dune, Emma
```

## Updating and deleting rows

`UPDATE table SET column = value WHERE condition` changes the rows that match a condition. `DELETE FROM table WHERE condition` removes the rows that match a condition. A program runs both with `db:run`, whose first result is the number of rows that the statement changed or removed. An `UPDATE` or `DELETE` without `WHERE` applies to every row of the table.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (title TEXT NOT NULL, year INTEGER)")
db:run("INSERT INTO books VALUES (?, ?)", "Emma", 1815)
db:run("INSERT INTO books VALUES (?, ?)", "Dune", 1965)

print((db:run("UPDATE books SET year = ? WHERE title = ?", 1816, "Emma")))  --> 1
print((db:run("DELETE FROM books WHERE year > ?", 1900)))  --> 1
print((db:run("DELETE FROM books WHERE year > ?", 3000)))  --> 0
```

## Transactions

A _transaction_ is a group of changes that the database applies completely or not at all. A transfer between two accounts takes money from one and adds it to the other, so a program that failed between the two steps would lose the money. Inside a transaction, a failure at that point also undoes the first step.

`db:transaction(fn)` runs the function `fn` inside a transaction. If `fn` returns, `db:transaction` keeps all its changes and returns every value that `fn` returned. If `fn` raises an error, the database undoes every change that `fn` made, then the error propagates to the caller of `db:transaction`.

In the following program, the second transfer between two accounts exceeds the balance, so the transaction undoes its first step.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE accounts (name TEXT PRIMARY KEY, balance INTEGER NOT NULL)")
db:run("INSERT INTO accounts VALUES (?, ?)", "ada", 100)
db:run("INSERT INTO accounts VALUES (?, ?)", "ben", 20)

local function transfer(from_name, to_name, amount)
    db:transaction(function()
        db:run("UPDATE accounts SET balance = balance - ? WHERE name = ?", amount, from_name)

        for row in db:query("SELECT balance FROM accounts WHERE name = ?", from_name) do
            if row.balance < 0 then
                error("insufficient funds", 0)
            end
        end

        db:run("UPDATE accounts SET balance = balance + ? WHERE name = ?", amount, to_name)
    end)
end

transfer("ada", "ben", 30)
print(catch transfer("ada", "ben", 500))  --> false  insufficient funds

for row in db:query("SELECT name, balance FROM accounts ORDER BY name") do
    print(row.name, row.balance)
end
--> ada  70
--> ben  50
```

A transaction also makes many changes faster. Outside a transaction, the database completes each statement separately, which for a database file includes writing to the disk. A program that inserts thousands of rows should therefore run the loop inside one transaction. Starting a transaction inside another raises the error `cannot start a transaction within a transaction`.

## Closing a database

A database handle declared with the `<close>` attribute closes when its block ends, including when an error ends the block, which is the usual way to close a database. `db:close()` closes a handle that must stay open after the block that created it, such as a handle stored in a table. Any method call on a closed database, including a second call to `close`, raises the error `attempt to use a closed database`. The garbage collector closes a database that the program no longer refers to.

## Errors

A statement that SQLite rejects raises an error whose error object is the message from SQLite. SQLite rejects mistakes in the SQL, such as an unknown column. It also rejects rows that break a rule of the table, such as `NOT NULL`. A [`catch`](/manual/guide#errors) around the call captures the error.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE books (title TEXT NOT NULL)")

print(catch db:run("SELECT missing FROM books"))  --> false  no such column: missing
print(catch db:run("INSERT INTO books (title) VALUES (?)", nil))  --> false  NOT NULL constraint failed: books.title
```

Opening a database that SQLite cannot open, such as a file in a directory that does not exist, raises an error of the form `cannot open database 'PATH' (REASON)`.

## Running statements

A database handle has the following methods.

| Method | Effect |
| --- | --- |
| `db:exec(sql)` | Runs one or more statements separated by semicolons. It takes no parameters and returns nothing. |
| `db:run(sql, ...)` | Runs a single statement with parameters. It returns the number of rows the statement changed and the id of the last inserted row. |
| `db:query(sql, ...)` | Runs a single statement with parameters and returns an iterator over the result rows. Each row is a table with one field per column. |
| `db:prepare(sql)` | Returns a [prepared statement](#prepared-statements) for a statement that runs many times. |
| `db:transaction(fn)` | Runs `fn` inside a [transaction](#transactions). |
| `db:close()` | Closes the database. |

`run` and `query` accept exactly one statement. SQL text that contains a second statement raises the error `sql contains more than one statement`.

## Parameters

A statement uses one of the following parameter styles.

- A positional `?` takes the extra arguments of `run` or `query` in order.
- A named parameter, written `:name`, `@name`, or `$name`, takes the field `name` of a single table argument.

A statement that mixes the styles raises the error `statement mixes named and positional parameters`. Numbered parameters such as `?1` raise the error `numbered parameters are not supported`. The number of values must equal the number of positional parameters. Any other number raises an error that states both counts. A named parameter without a field in the table raises the error `no value for parameter ':name'`.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE users (name TEXT, age INTEGER)")
db:run("INSERT INTO users VALUES (?, ?)", "Alice", 30)
db:run("INSERT INTO users VALUES (:name, :age)", { name = "Bob", age = 25 })

for row in db:query("SELECT name FROM users WHERE age < $limit", { limit = 28 }) do
    print(row.name)  --> Bob
end

print(catch db:run("INSERT INTO users VALUES (?, ?)", "Carol"))
--> false  ...: statement has 2 parameters, but 1 values were given
print(catch db:run("INSERT INTO users VALUES (?1, 0)", "x"))
--> false  ...: numbered parameters are not supported
```

A parameter can only supply a value. The name of a table or a column must be part of the SQL text.

## Types

The following table shows how SQLite stores a Lus value that fills a parameter and what a program reads back from the row.

| Lus value | Stored as | Read back as |
| --- | --- | --- |
| `nil` | `NULL` | an absent field |
| `true`, `false` | `1`, `0` | the integer `1` or `0` |
| integer | `INTEGER` | integer |
| float | `REAL` | float |
| bigint, decimal | `TEXT` that holds its digits | string |
| string | `TEXT` | string |
| [vector](/manual/text#vectors) | `BLOB` | vector |

SQLite has no boolean type, so a stored boolean is read as `1` or `0`. A float that is NaN is stored as `NULL`.

A `TEXT` value that is not valid UTF-8 raises an error when the row is read, with a message that gives the column and the byte offset. Only another program can store such a value, because Lus strings are always valid text. A query that selects `CAST(column AS BLOB)` reads the bytes of the value as a vector.

The following program stores a string, a vector, a boolean, and a NaN, then reads them back.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE files (name TEXT, data BLOB, ok, size REAL)")
db:run(
    "INSERT INTO files VALUES (?, ?, ?, ?)",
    "a.bin",
    vector.fromstring("\u{0}\u{1}"),
    true,
    0 / 0
)

for row in db:query("SELECT * FROM files") do
    print(row.name, type(row.data), #row.data, row.ok, row.size)  --> a.bin  vector  2  1  nil
end
```

## Prepared statements

Before SQLite runs a statement, it analyzes the SQL text and plans how to execute it. A _prepared statement_ keeps the result of that work, which saves time for a statement that runs many times. `db:prepare(sql)` does the analysis once and returns a statement object whose methods `stmt:run(...)` and `stmt:query(...)` run the statement with new parameter values. These methods return the same values as `db:run` and `db:query`.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT NOT NULL, age INTEGER)")

local insert = db:prepare("INSERT INTO users (name, age) VALUES (?, ?)")

db:transaction(function()
    for _, person in ipairs({ { "Alice", 30 }, { "Bob", 17 }, { "Carol", 41 } }) do
        insert:run(person[1], person[2])
    end
end)

local adults = db:prepare("SELECT name FROM users WHERE age >= ? ORDER BY name")
local names = {}

for row in adults:query(18) do
    names[#names + 1] = row.name
end

print(table.concat(names, " "))  --> Alice Carol
```

`stmt:close()` releases a statement before its database closes. A statement declared with `<close>` is released when its block ends. Using a closed statement raises the error `attempt to use a closed statement`. Closing a database closes its statements first.

## Queries over tables

The Lus [query syntax](/manual/guide#queries), which filters, sorts, and groups lists of records, can also read a SQLite table. Indexing a database handle with the name of a table, as in `db.users`, returns a reference to that table that a query accepts as its source. Lus translates the conditions of the query into SQL, so SQLite does the filtering. Values from the program become parameters of that SQL, which protects the query from SQL injection.

```lus
local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE users (name TEXT, age INTEGER)")
db:run("INSERT INTO users VALUES (?, ?)", "Alice", 30)
db:run("INSERT INTO users VALUES (?, ?)", "Bob", 12)

local min = 18

for row in query(@db.users as u where u.age >= min select u.name) do
    print(row.name)  --> Alice
end
```

A table whose name is also the name of a method, such as `close`, has no reference, because `db.close` is the method. The garbage collector leaves a database open while the program still holds a reference to one of its tables.

## Lifetime

A query keeps its statement open while its loop runs and releases it when the loop ends, including when a `break` or an error ends it early. A program may therefore run other statements on the same database inside the loop and after it.

A database handle, a prepared statement, and a running query each have a `__close` metamethod and a `__gc` metamethod. The `<close>` attribute calls `__close`. The garbage collector calls `__gc` to release an object that the program left open. Using a prepared statement or a query after its database has closed raises the error `attempt to use a closed statement`.

## Permissions and files

A program that pledges `fs:read=PATH*` and `fs:write=PATH*` for its database, as in [Opening a database](#opening-a-database), has every permission that the database needs. A program with narrower permissions must allow each file that SQLite uses and each permission that Lus checks.

### Files of a database

A database at `PATH` uses the database file itself and the temporary files `PATH-journal`, `PATH-wal`, and `PATH-shm`. SQLite records changes in the temporary files before it writes them to the database, which keeps the database intact when a program stops in the middle of a change. A pledge for `PATH*` covers all of these files.

`io.sqlite` checks `fs:read` for the path, plus `fs:write` unless the mode is `"r"`. Lus then checks the permission again each time SQLite opens, creates, writes, or deletes one of these files. With a pledge for the exact path only, the first use of a temporary file therefore raises an error such as `permission "fs:read" denied for 'PATH-journal'`.

A database opened for writing uses the write-ahead log of SQLite, which is the `-wal` file. With the write-ahead log, other connections can read while one connection writes.

### Read-only connections

`io.sqlite(path, "r")` opens the database read-only, which requires only `fs:read`. A statement that changes data raises the error `attempt to write a readonly database`. The default mode is `"rw"`. Any other mode raises the error `invalid mode`.

A read-only connection never creates or changes a file. It can read a database that uses the write-ahead log only while the `-wal` and `-shm` files exist, which is while another connection has the database open for writing. When they are missing, the first statement raises an `fs:write` permission error for the `-wal` file. A program that reads such a database while no other connection writes to it must open it in the default mode.

### In-memory databases

A database opened with `":memory:"` uses no file and requires no permission. It therefore works in a program that has sealed its permissions without any filesystem access.

```lus nocheck
pledge("seal")

print(catch io.sqlite("app.db", "r"))  --> false  script.lus:3: permission "fs:read" denied for 'app.db'

local db <close> = io.sqlite(":memory:")
db:exec("CREATE TABLE t (n INTEGER)")
print(db:run("INSERT INTO t VALUES (?)", 42))  --> 1  1
```

### Operations that are denied

Lus denies the SQL statements that name other files, so that SQLite opens only paths that a permission check covered. SQLite also keeps its temporary data for sorting and for statements in memory, so that data is never written to a file.

- `ATTACH` and `VACUUM INTO` raise an authorization error. A plain `VACUUM` runs.
- The statements `PRAGMA data_store_directory`, `PRAGMA temp_store_directory`, and `PRAGMA lock_proxy_file`, which change where SQLite puts files, are denied in any letter case.
- A path that starts with `file:`, which SQLite would read as a URI with options, raises the error `URI filenames are not supported`.
- SQLite extensions cannot be loaded.

## Workers

A database handle keeps the permissions of the code that opened it. SQLite opens the files of a database, such as its journal, while statements run, and each of those opens is checked against the permissions that the opener held. A handle that is passed to a [coroutine with fewer permissions](/manual/permissions#permissions-in-coroutines) therefore still reaches the files that its opener could reach, so pass such a coroutine the rows it needs and keep the handle.

A call to SQLite blocks the whole program until it returns, including its [detached coroutines](/manual/concurrency#detached-coroutines). A program that moves long database work to a [worker](/manual/concurrency#workers) keeps running during that work. A database handle cannot be sent in a message, so the worker opens the same file with its own call to `io.sqlite`. Several connections may read a database while one writes to it.

## Builds

The built-in engine includes the math functions of SQLite, such as `sqrt`. A runtime built with `zig build -Dsqlite=false` omits SQLite and `io.sqlite`. The WebAssembly build includes SQLite without the write-ahead log.
