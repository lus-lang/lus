`lus test` is the test runner built into the `lus` command. A test is an ordinary function in a file whose name follows a convention, so a project needs no test library and no configuration file. The runner finds the test files and runs each one in its own process. It reports the result of every test. The [CLI page](/manual/cli#lus-test) lists its options.

## Test files and tests

A _test file_ is a Lus file whose name ends in `_test.lus`. Every top-level function in it whose name ends in `_test` is a _test_. A test passes when it returns. It fails when it raises an error, as a failed `assert` does. The rest of the top-level code runs once, before the tests. Use it to set up what the tests share.

The following file tests a function `add` with positive and with negative arguments.

```lus
-- math_test.lus
local function add(a, b) return a + b end

local function add_test()
    assert(add(2, 2) == 4)
end

local function negative_test()
    assert(add(-1, -1) == -2)
end
```

A test is declared in one of three forms: `local function NAME_test`, `function NAME_test`, and `local NAME_test = function ... end`. Prefer the local forms, because `function NAME_test` assigns a global, which [`lus check`](/manual/tools#checking) reports as `implicit-global`. Tests run in the order in which they appear in the file.

The runner collects local test functions by appending a `return` statement to the file. A test file must therefore end without a `return` of its own. A file that ends with one fails with the file error `TestFileReturns`.

## Running tests

`lus test` with no argument searches the current directory and its subdirectories for files whose names end in `_test.lus`. With arguments, it runs the named files and searches the named directories. A file named on the command line runs whatever its name is. The search skips every path that contains `node_modules`, `.git`, `zig-out`, or `.zig-cache`.

```sh
lus test                        # every *_test.lus below the current directory
lus test tests/parser           # one directory
lus test math_test.lus -v       # one file, listing skipped tests too
lus test --filter negative      # only the tests whose names contain "negative"
```

Each file runs in its own child process inside a new temporary directory, so a crash, a global, or a file written by one test file cannot affect another. Because the files are isolated, the runner runs them in parallel. By default, it runs as many files at once as there are processors. It prints one line per file as soon as the file ends, then a summary. For a file with a failure, the line is followed by each failed test with its message, each skipped test with its reason, and the standard output of the file.

```
FAIL math_test.lus (5 passed, 1 failed, 1 skipped, 2 ms)
  FAIL power_test
       math_test.lus:14: assertion failed: add(x, 1) == 5
         left:  4
         right: 5
  skip slow_test: needs the network
  output:
       setting up

1 files, 5 passed, 1 failed, 1 skipped
```

For a file whose tests all pass, the runner prints only that line. With `-v`, it also prints the skipped tests of the file.

A _file error_ is a failure of the file as a whole, such as a syntax error, an error raised by the top-level setup code, or a crash of the process. The runner reports it under `file error:` together with the standard error of the file. The summary counts the file as one with errors.

### Exit status and machine output

The exit status of `lus test` is 0 when every file passes. It is 1 when a test fails, a file has a file error, or a file times out. It is 2 when a path named on the command line does not exist.

`--json` is for tools that read the results, such as a continuous integration service. It replaces the report with one JSON record per test, each on its own line. A record has the fields `status`, `name`, and `message`. The status is `pass`, `fail`, or `skip`. The message is empty for a passing test, the error message for a failure, and the reason for a skipped test.

```
{"status":"pass","name":"add_test","message":""}
{"status":"fail","name":"power_test","message":"math_test.lus:14: assertion failed: add(x, 1) == 5\n  left:  4\n  right: 5"}
{"status":"skip","name":"slow_test","message":"needs the network"}
```

### Timeouts

A timeout stops a test that hangs, so the rest of the run can finish. The runner stops a file that writes no output for 60 seconds. `--timeout S` changes this limit. The runner also stops a file whose total run time exceeds ten times that timeout, even while it writes output. `--file-timeout S` changes this limit. When the runner stops a file, it kills every process that the file started. The report names the timeout that ended the file. The tests that finished before the timeout keep their results.

## Power asserts

A failed assertion is useful only when its message contains the values that were tested. In a test file, a failed `assert` reports the expression together with the values of its operands, so a test needs no separate function for each kind of comparison. For a comparison, the report shows both sides. For any other expression, it shows the value. It also shows a message passed as the second argument.

```lus
local function area(w, h) return w * h end

local function area_test()
    local w, h = 3, 4
    assert(area(w, h) == 13)
end

local function flag_test()
    local t = { enabled = true }
    assert(not t.enabled, "the flag must start off")
end
```

The runner reports the two failures as follows.

```
  FAIL area_test
       area_test.lus:5: assertion failed: area(w, h) == 13
         left:  12
         right: 13
  FAIL flag_test
       area_test.lus:10: assertion failed: not t.enabled
         message: "the flag must start off"
         value: false
```

Only the `assert` calls written in the test file report this way. Modules that the test file requires keep the standard `assert`.

## Case tables

A _case table_ runs one test with many inputs. The runner reports each input as a test of its own, so one failing input does not hide the others. A case table is a table named `NAME_cases`. The runner calls the test `NAME_test` once per entry. When an entry is a table, its array items are the arguments of the call. Any other entry is the single argument. The case table may be a local, a declared global, or a global assigned at the top level of the file. The following file tests `add` with three pairs of numbers and their expected sums.

```lus
local function add(a, b) return a + b end

local add_cases = {
    { 1, 2, 3 },
    { -1, 1, 0 },
    { 0.5, 0.25, 0.75 },
}

local function add_test(a, b, want)
    assert(add(a, b) == want)
end
```

The name of each run contains its entry. The array entries run first, in order. Each is named by its position, as in `add_test[2]`. The entries with other keys run after them. Each is named by its key, as in `add_test[zero]` for the entry `zero = { 0, 0, 0 }`. The order of the keyed entries is unspecified.

## Helpers

The runner defines four helper functions as globals in every test file. They handle four cases that `assert` alone does not: an error that must occur, two tables with equal contents, a test that cannot run on the current machine, and output that is too long to write by hand.

- `raises(f, pattern, ...)` calls `f(...)` and fails the test unless the call raises an error. If `pattern` is given, `tostring` of the error object must match it as a [string pattern](/manual/guide#strings-and-patterns). `raises` returns the error object, so the test can check it further.
- `same(a, b)` compares two values by content and returns a boolean. `==` on two tables is true only when both are the same table. `same` is true for two tables that hold the same keys with the same values, including nested tables. It also compares tables that refer to themselves.
- `skip(reason)` stops the current test and records it as skipped with the reason.
- `snapshot(value)` compares a value with its recorded snapshot. [Snapshots](#snapshots) describes it.

The first of the following tests checks that invalid JSON raises a parse error and that valid JSON parses to the expected table. The second compares two tables that contain themselves. The third is skipped because it needs the network.

```lus
local function parse_test()
    local err = raises(function() fromjson("{") end, "parse error")
    assert(type(err) == "string")
    assert(same(fromjson("[1, [2, 3]]"), { 1, { 2, 3 } }))
end

local function cycle_test()
    local a = {}
    a.self = a
    local b = {}
    b.self = b
    assert(same(a, b))
end

local function network_test()
    skip("needs the network")
end
```

When the function passed to `raises` returns without an error, the test fails with the message `expected an error, but the call succeeded`. When the error does not match the pattern, the test fails with a message that quotes the pattern and the error, as in `expected an error matching 'nomatch', got: a_test.lus:12: boom`.

## Snapshots

A snapshot test compares a large value, such as a parsed document or a generated report, with a recorded copy, so the expected value need not be written in the test. `snapshot(value)` renders the value as Lus source. It compares the rendering with the one recorded in `__snapshots__/FILE.snap` next to the test file, where `FILE` is the name of the test file. The first run records the snapshot. A later run with a different rendering fails and shows both versions. If the change is intended, `lus test -u` records the new rendering. Several snapshots in one test are numbered in order. The snapshot files are plain text. Commit them to version control with the tests.

```lus
local function config_test()
    snapshot({ name = "app", ports = { 80, 443 } })
end
```

The first run writes the following file, `__snapshots__/config_test.lus.snap`.

```
== config_test #1
{name = "app", ports = {80, 443}}
```

The report of a mismatch names the snapshot and shows both renderings.

```
  FAIL config_test
       config_test.lus:2: snapshot mismatch (config_test #1)
         expected: {name = "app", ports = {80, 443}}
         actual:   {name = "app", ports = {80, 8443}}
         (run lus test -u to update)
```

## Fixtures and permissions

The working directory of a test file is a new temporary directory. The runner deletes it when the file ends, so a test can create files without cleaning up. The runner creates the directory in `TMPDIR` when that environment variable is set. Otherwise it creates the directory in `/tmp`. A _fixture_ is a file that a test reads, such as sample input. Keep fixtures next to the test file. The global `TEST_DIR` is the absolute path of the directory that contains the test file, so a test opens a fixture with a path that starts with `TEST_DIR`. The environment variable `LUS_EXE` is the path of the interpreter that runs the tests. A test uses it to start another interpreter with `io.popen` or `os.execute`.

A test file starts with no [permissions](/manual/permissions) and pledges the ones it needs, as a script does. Each test starts with the permissions that the file holds after its top-level code. The runner undoes the pledges of a test when the test ends, so the next test starts without them. The following file pledges `fs:read` for every test. `env_test` also pledges `env`, which only that test holds.

```lus
pledge("fs:read")

local function fixture_test()
    local f <close> = io.open(`$TEST_DIR/fixtures/input.txt`)
    assert(f:read("l") == "first line")
end

local function env_test()
    pledge("env")
    assert(os.getenv("LUS_EXE") ~= nil)
end
```

## Detached coroutines in tests

A test may start [detached coroutines](/manual/concurrency), for example to run a server and a client in one test. The runner waits for them as the `lus` command does at the end of a script, so a test ends when every coroutine it detached has ended. The coroutines that the top-level code detaches end before the first test runs. If a detached coroutine fails and nothing collects its error, the test that detached it fails with that error.

## Doc tests

An example in documentation becomes wrong when the code it describes changes. `lus test --doc` detects this by running the code blocks of Markdown files as tests. The arguments are Markdown files or directories. In a directory, the runner finds the files whose names end in `.md` or `.mdx`. Every block fenced as ` ```lus ` is a test. Its name is the line where its code starts, as in `line 12`. A block passes when it runs to the end without raising an error.

Each block runs separately. It has none of the variables of the blocks before it. It holds every permission. Its detached coroutines must end for it to pass. Fence a block that cannot run alone, such as a fragment or code that shows an error, as ` ```lus nocheck `. The runner records such a block as skipped. The manual, the standard library specification, and the agent skills of Lus are all tested with `lus test --doc`.

```sh
lus test --doc docs/
lus test --doc README.md --filter "line 4"
```
