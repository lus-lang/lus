`lus test` is the test runner built into the interpreter. It finds test files, runs each one in its own process, and reports every test, with no library and no configuration. The [CLI page](/manual/cli#lus-test) lists its options.

## Test files and tests

A _test file_ is a Lus file whose name ends in `_test.lus`. Its top-level code runs once as setup, and every top-level function whose name ends in `_test` is a _test_. A test passes when it returns and fails when it raises an error.

The following file holds two tests.

```lus
-- math_test.lus
local function add(a, b) return a + b end

local function add_test()
    assert(add(2, 2) == 4)
end

local function negative_test()
    assert(add(-1, -1) == -2)
end
```

The runner recognizes three forms of declaration: `local function NAME_test`, `function NAME_test`, and `local NAME_test = function ... end`. Local functions keep a test file free of globals, and [`lus check`](/manual/tools#checking) warns about the assignment that `function NAME_test` makes to an undeclared global. Tests run in the order they appear in the file.

The runner appends a `return` statement to the file that hands it the tests. A test file must therefore end without a `return` of its own. A file that ends with one fails with the file error `TestFileReturns`.

## Running tests

`lus test` with no argument searches the current directory and every directory below it for files whose names end in `_test.lus`. Arguments name files or directories to search instead. A file named on the command line runs whatever its name. The search skips every path that contains `node_modules`, `.git`, `zig-out`, or `.zig-cache`.

```sh
lus test                        # every *_test.lus below the current directory
lus test tests/parser           # one directory
lus test math_test.lus -v       # one file, listing skipped tests too
lus test --filter negative      # only the tests whose names contain "negative"
```

Each file runs in its own child process inside a fresh temporary directory, and the files run in parallel, by default as many at once as there are processors. A crash, a leaked global, or a file written by one test file never affects another. The runner prints one line per file as soon as the file ends, then a summary. For a file with a failure, the line is followed by each failed test with its message, each skipped test with its reason, and the standard output of the file.

```
FAIL math_test.lus (5 passed, 1 failed, 1 skipped, 2 ms)
  FAIL power_test
       math_test.lus:14: assertion failed: add(x, 1) == 5
         left:  4
         right: 5
  skip slow_test: needs the network
  output:
       setting up

1 files, 5 passed, 1 failed, 1 skipped
```

A file whose tests all pass prints its line alone. With `-v`, the line is followed by the skipped tests of the file too.

A _file error_ is a failure of the file as a whole, such as a syntax error, an error raised by the top-level setup code, or a crash of the process. The runner reports it under `file error:` together with the standard error of the file, and the summary counts the file as one with errors.

### Exit status and machine output

The exit status of `lus test` is 0 when every file passes. It is 1 when a test fails, a file has a file error, or a file times out. It is 2 when a path named on the command line does not exist.

`--json` replaces the report with one JSON record per test, one per line, with the fields `status`, `name`, and `message`. The status is `pass`, `fail`, or `skip`. The message is empty for a passing test, the error message for a failure, and the reason for a skipped test.

```
{"status":"pass","name":"add_test","message":""}
{"status":"fail","name":"power_test","message":"math_test.lus:14: assertion failed: add(x, 1) == 5\n  left:  4\n  right: 5"}
{"status":"skip","name":"slow_test","message":"needs the network"}
```

### Timeouts

The runner stops a file that writes no output for 60 seconds, which `--timeout S` changes. It also stops a file that runs longer than ten times that timeout in all, even while it writes output, which `--file-timeout S` changes. A file that is stopped has every process it started killed, and the report names the timeout that ended it. The tests that finished before the timeout keep their results.

## Power asserts

Inside a test file, `assert` reports the expression that failed together with the values of its operands. A comparison shows both sides, and any other expression shows its value. A message passed as the second argument appears as well.

```lus
local function area(w, h) return w * h end

local function area_test()
    local w, h = 3, 4
    assert(area(w, h) == 13)
end

local function flag_test()
    local t = { enabled = true }
    assert(not t.enabled, "the flag must start off")
end
```

The two failures read as follows.

```
  FAIL area_test
       area_test.lus:5: assertion failed: area(w, h) == 13
         left:  12
         right: 13
  FAIL flag_test
       area_test.lus:10: assertion failed: not t.enabled
         message: "the flag must start off"
         value: false
```

The runner rewrites the `assert` calls of the test file itself. Modules that the test file requires keep the standard `assert`.

## Case tables

A _case table_ is a table named `NAME_cases` that runs the test `NAME_test` once per entry. An entry that is a table supplies its array items as the arguments, and any other entry is passed as the single argument. The case table may be a local, a declared global, or a global assignment at the top level of the file.

```lus
local function add(a, b) return a + b end

local add_cases = {
    { 1, 2, 3 },
    { -1, 1, 0 },
    { 0.5, 0.25, 0.75 },
}

local function add_test(a, b, want)
    assert(add(a, b) == want)
end
```

The runner names each run after its entry. The array entries run first, in order, and are named by their position, as in `add_test[2]`. The entries with other keys run after them and are named by their key, as in `add_test[zero]` for the entry `zero = { 0, 0, 0 }`. The order of the keyed entries is unspecified.

## Helpers

The runner defines four helper functions as globals in every test file.

- `raises(f, pattern, ...)` calls `f(...)` and fails the test unless the call raises an error. If `pattern` is given, `tostring` of the error object must match it as a [string pattern](/manual/guide#string-patterns). It returns the error object for further checks.
- `same(a, b)` compares two values structurally and returns a boolean. Two tables are the same when they hold the same keys with values that are the same, nested tables included. Cycles are handled.
- `skip(reason)` stops the current test and records it as skipped with the reason.
- `snapshot(value)` compares a value with its recorded snapshot, as described under [Snapshots](#snapshots).

The following tests use the first three helpers.

```lus
local function parse_test()
    local err = raises(function() fromjson("{") end, "parse error")
    assert(type(err) == "string")
    assert(same(fromjson("[1, [2, 3]]"), { 1, { 2, 3 } }))
end

local function cycle_test()
    local a = {}
    a.self = a
    local b = {}
    b.self = b
    assert(same(a, b))
end

local function network_test()
    skip("needs the network")
end
```

A call that succeeds fails the test with the message `expected an error, but the call succeeded`. An error that does not match fails it with a message that quotes the pattern and the error, as in `expected an error matching 'nomatch', got: a_test.lus:12: boom`.

## Snapshots

`snapshot(value)` renders the value as Lus source and compares the rendering with the recording in `__snapshots__/FILE.snap` beside the test file, where `FILE` is the name of the test file. The first run records the snapshot. A later run that renders something different fails and shows both versions, and `lus test -u` accepts the new rendering. Several snapshots in one test are numbered in order. The snapshot files are plain text, meant to be committed with the tests.

```lus
local function config_test()
    snapshot({ name = "app", ports = { 80, 443 } })
end
```

The recorded file `__snapshots__/config_test.lus.snap` reads as follows.

```
== config_test #1
{name = "app", ports = {80, 443}}
```

A mismatch names the snapshot and shows both renderings.

```
  FAIL config_test
       config_test.lus:2: snapshot mismatch (config_test #1)
         expected: {name = "app", ports = {80, 443}}
         actual:   {name = "app", ports = {80, 8443}}
         (run lus test -u to update)
```

## Fixtures and permissions

Each test file runs inside a fresh temporary directory, which the runner deletes when the file ends, so tests can create and delete files freely. The temporary directory is created below `TMPDIR` when that environment variable is set, and below `/tmp` otherwise. The global `TEST_DIR` holds the absolute path of the directory that contains the test file, which is where fixtures live. The environment variable `LUS_EXE` holds the path of the interpreter running the tests, for tests that start a child interpreter with `io.popen` or `os.execute`.

A test file starts with no [permissions](/manual/permissions) and pledges the ones it needs, as a script does. Each test starts from the permissions the file holds after its setup code. The pledges a test makes are undone when it ends, so tests stay independent of one another.

```lus
pledge("fs:read")

local function fixture_test()
    local f <close> = io.open(`$TEST_DIR/fixtures/input.txt`)
    assert(f:read("l") == "first line")
end

local function env_test()
    pledge("env")
    assert(os.getenv("LUS_EXE") ~= nil)
end
```

## Detached coroutines in tests

The runner waits for [detached coroutines](/manual/guide#detached-coroutines) the way the `lus` command does. The coroutines that the setup code detaches end before the first test runs. A test ends when every coroutine it detached has ended. If a detached coroutine fails and nothing collects its error, the test that detached it fails with that error.

## Doc tests

`lus test --doc` runs the code blocks of Markdown files instead of test files. Arguments name Markdown files or directories, and the search in a directory finds the files whose names end in `.md` or `.mdx`. Every block fenced as ` ```lus ` is a test named after the line where its code starts, as in `line 12`. A block passes when it runs to the end without raising an error.

Each block runs in a fresh state with every permission granted, and its detached coroutines must end for it to pass. A block fenced as ` ```lus nocheck ` is a fragment, such as a test file that needs the runner or code that shows an error, and the runner records it as skipped. The manual, the standard library specification, and the agent skills of Lus all run under `lus test --doc`.

```sh
lus test --doc docs/
lus test --doc README.md --filter "line 4"
```
