`lus test` is the test runner built into the `lus` command. A test is an ordinary function in a file whose name follows a convention, so a project needs no test library and no configuration file. The runner finds the test files, runs each one in its own process, and reports the result of every test. The [CLI page](/manual/cli#lus-test) lists its options.

## Test files and tests

A _test file_ is a Lus file whose name ends in `_test.lus`. Every top-level function in it whose name ends in `_test` is a _test_. A test passes when it returns and fails when it raises an error, as a failed `assert` does. The rest of the top-level code runs once before the tests, which makes it the place to set up what the tests share.

The following file tests a function `add` with positive and with negative arguments.

```lus
-- math_test.lus
local function add(a, b)
    return a + b
end

local function add_test()
    assert(add(2, 2) == 4)
end

local function negative_test()
    assert(add(-1, -1) == -2)
end
```

A test is declared in one of the following forms: `local function NAME_test`, `function NAME_test`, and `local NAME_test = function ... end`. Prefer the local forms, because `function NAME_test` assigns a global, which [`lus check`](/manual/tools#checking) reports as `implicit-global`. Tests run in the order in which they appear in the file.

The runner collects local test functions by appending a `return` statement to the file, so a test file must end without a `return` of its own. A file that ends with one fails with the file error `TestFileReturns`.

## Running tests

`lus test` with no argument searches the current directory and its subdirectories for files whose names end in `_test.lus`. With arguments, it runs the named files and searches the named directories. A file named on the command line runs whatever its name is. The search skips every path that contains `node_modules`, `.git`, `zig-out`, or `.zig-cache`.

```sh
lus test                        # every *_test.lus below the current directory
lus test tests/parser           # one directory
lus test math_test.lus -v       # one file, listing skipped tests too
lus test --filter negative      # only the tests whose names contain "negative"
```

Each file runs in its own child process inside a new temporary directory, so a crash, a global, or a file written by one test file cannot affect another. Because the files are isolated, the runner runs them in parallel, by default as many at once as there are processors. It prints one line per file as soon as the file ends, then a summary. For a file with a failure, the line is followed by each failed test with its message, each skipped test with its reason, and the standard output of the file.

```
FAIL math_test.lus (5 passed, 1 failed, 1 skipped, 2 ms)
  FAIL power_test
       math_test.lus:14: assertion failed: add(x, 1) == 5
         left:  4
         right: 5
  skip slow_test: needs the network
  output:
       setting up

1 files, 5 passed, 1 failed, 1 skipped
```

For a file whose tests all pass, the runner prints only that line. With `-v`, it also prints the skipped tests of the file.

A _file error_ is a failure of the file as a whole, such as a syntax error, an error raised by the top-level setup code, or a crash of the process. The runner reports it under `file error:` together with the standard error of the file and counts the file as one with errors in the summary.

### Exit status and machine output

The exit status of `lus test` is 0 when every file passes. It is 1 when a test fails, a file has a file error, or a file times out. It is 2 when a path named on the command line does not exist.

`--json` is for tools that read the results, such as a continuous integration service. It replaces the report with one JSON record per test, each on its own line. A record has the fields `status`, `name`, and `message`. The status is `pass`, `fail`, or `skip`. The message is empty for a passing test, the error message for a failure, and the reason for a skipped test.

```
{"status":"pass","name":"add_test","message":""}
{"status":"fail","name":"power_test","message":"math_test.lus:14: assertion failed: add(x, 1) == 5\n  left:  4\n  right: 5"}
{"status":"skip","name":"slow_test","message":"needs the network"}
```

### Timeouts

A timeout stops a test that hangs, so the rest of the run can finish. The runner stops a file that writes no output for 60 seconds, a limit that `--timeout S` changes. It also stops a file whose total run time exceeds ten times that timeout, even while it writes output, a limit that `--file-timeout S` changes. When the runner stops a file, it kills every process that the file started, then reports which timeout ended the file. The tests that finished before the timeout keep their results.

## Power asserts

A failed assertion is useful only when its message contains the values that were tested. In a test file, a failed `assert` reports the expression together with the values of its operands, so a test needs no separate function for each kind of comparison. The report shows both sides of a comparison or the value of any other expression, together with a message passed as the second argument.

```lus
local function area(w, h)
    return w * h
end

local function area_test()
    local w, h = 3, 4
    assert(area(w, h) == 13)
end

local function flag_test()
    local t = { enabled = true }
    assert(not t.enabled, "the flag must start off")
end
```

The runner reports the two failures as follows.

```
  FAIL area_test
       area_test.lus:5: assertion failed: area(w, h) == 13
         left:  12
         right: 13
  FAIL flag_test
       area_test.lus:10: assertion failed: not t.enabled
         message: "the flag must start off"
         value: false
```

A power assert that passes returns what the standard `assert` returns, all of its arguments, so `select(2, assert(coroutine.resume(co)))` reads the first result of the coroutine in a test file as it does anywhere else. Only the `assert` calls written in the test file report this way, while modules that the test file requires keep the standard `assert`.

## Case tables

A _case table_ runs one test with many inputs. The runner reports each input as a test of its own, so one failing input does not hide the others. A case table is a table named `NAME_cases` whose entries the runner passes to the test `NAME_test`, one call per entry. When an entry is a table, its array items are the arguments of the call. Any other entry is the single argument. The case table may be a local, a declared global, or a global assigned at the top level of the file. The following file tests `add` with three pairs of numbers and their expected sums.

```lus
local function add(a, b)
    return a + b
end

local add_cases = {
    { 1, 2, 3 },
    { -1, 1, 0 },
    { 0.5, 0.25, 0.75 },
}

local function add_test(a, b, want)
    assert(add(a, b) == want)
end
```

The name of each run contains its entry. The array entries run first, in order, each named by its position, as in `add_test[2]`. The entries with other keys run after them, each named by its key, as in `add_test[zero]` for the entry `zero = { 0, 0, 0 }`. The order of the keyed entries is unspecified.

## Helpers

The runner defines helper functions as globals in every test file for cases that `assert` alone does not handle: an error that must occur, two tables with equal contents, a test that cannot run on the current machine, and output that is too long to write by hand.

- `raises(f, pattern, ...)` calls `f(...)` and fails the test unless the call raises an error. If `pattern` is given, `tostring` of the error object must match it as a [string pattern](/manual/guide#strings-and-patterns). `raises` returns the error object, so the test can check it further.
- `same(a, b)` compares two values by content and returns a boolean. Where `==` on two tables is true only when both are the same table, `same` is true for two tables that hold the same keys with the same values, including nested tables and tables that refer to themselves.
- `skip(reason)` stops the current test and records it as skipped with the reason.
- `snapshot(value)` compares a value with its recorded snapshot. [Snapshots](#snapshots) describes it.

The first of the following tests checks that invalid JSON raises a parse error and that valid JSON parses to the expected table. The second compares two tables that contain themselves. The third is skipped because it needs the network.

```lus
local function parse_test()
    local err = raises(function()
        fromjson("{")
    end, "parse error")

    assert(type(err) == "string")
    assert(same(fromjson("[1, [2, 3]]"), { 1, { 2, 3 } }))
end

local function cycle_test()
    local a = {}
    a.self = a
    local b = {}
    b.self = b
    assert(same(a, b))
end

local function network_test()
    skip("needs the network")
end
```

When the function passed to `raises` returns without an error, the test fails with the message `expected an error, but the call succeeded`. When the error does not match the pattern, the test fails with a message that quotes the pattern and the error, as in `expected an error matching 'nomatch', got: a_test.lus:12: boom`.

## Snapshots

A snapshot test compares a large value, such as a parsed document or a generated report, with a recorded copy, so the expected value need not be written in the test. `snapshot(value)` renders the value as Lus source and compares the rendering with the one recorded in `__snapshots__/FILE.snap` next to the test file, where `FILE` is the name of the test file. The first run records the snapshot. A later run with a different rendering fails and shows both versions. If the change is intended, `lus test -u` records the new rendering. Several snapshots in one test are numbered in order. The snapshot files are plain text that belongs in version control with the tests.

```lus
local function config_test()
    snapshot({ name = "app", ports = { 80, 443 } })
end
```

The first run writes the following file, `__snapshots__/config_test.lus.snap`.

```
== config_test #1
{name = "app", ports = {80, 443}}
```

The report of a mismatch names the snapshot and shows both renderings.

```
  FAIL config_test
       config_test.lus:2: snapshot mismatch (config_test #1)
         expected: {name = "app", ports = {80, 443}}
         actual:   {name = "app", ports = {80, 8443}}
         (run lus test -u to update)
```

## Fixtures and permissions

The working directory of a test file is a new temporary directory that the runner deletes when the file ends, so a test can create files without cleaning up. The runner creates the directory where [`os.tmpname`](/manual/api#os.tmpname) creates its files, which is `TMPDIR` or `/tmp` on POSIX systems and `TMP` or `TEMP` on Windows. A _fixture_ is a file that a test reads, such as sample input, kept next to the test file. The global `TEST_DIR` is the absolute path of the directory that contains the test file, so a test opens a fixture with a path that starts with `TEST_DIR`. The environment variable `LUS_EXE` holds the path of the interpreter that runs the tests, which a test uses to start another interpreter with `io.popen` or `os.execute`.

A test file starts with no [permissions](/manual/permissions) and pledges the ones it needs, as a script does. Each test starts with the permissions that the file holds after its top-level code. The runner undoes the pledges of a test when the test ends, so the next test starts without them. The following file pledges `fs:read` for every test, while `env_test` also pledges `env` for itself alone.

```lus
pledge("fs:read")

local function fixture_test()
    local f <close> = io.open(`$TEST_DIR/fixtures/input.txt`)
    assert(f:read("l") == "first line")
end

local function env_test()
    pledge("env")
    assert(os.getenv("LUS_EXE") ~= nil)
end
```

## Detached coroutines in tests

A test may start [detached coroutines](/manual/concurrency), for example to run a server and a client in one test. The runner waits for them as the `lus` command does at the end of a script, so a test ends when every coroutine it detached has ended. The coroutines that the top-level code detaches end before the first test runs. If a detached coroutine fails and nothing collects its error, the test that detached it fails with that error. If the test itself fails, the runner closes the coroutines it detached that have not ended, as the end of a script closes them, so a coroutine that waits for a message the failed test never sent cannot stop the run.

## Coverage

`lus test --coverage` reports which lines of the code under test ran, which shows the branches and functions that no test reaches. The runner records each line that runs in a file loaded from disk, such as a module that a test requires, and leaves out the test files themselves. After the summary of the tests, it lists each covered file with the lines that ran, the lines that hold code, the percentage, and the lines that never ran.

```
coverage:
  src/greet.lus: 7 of 9 lines, 77.8%, missed 5, 11
  total: 7 of 9 lines, 77.8%
```

A line counts as covered when any test file ran it. A file that no test loads is missing from the report. `--coverage-out FILE` also writes the coverage as an lcov tracefile, a format that editors and coverage services read. Coverage runs every function in the interpreter with a line hook, so a run with `--coverage` is slower than a plain run. Code that a worker runs is not covered, because each worker has a state of its own.

## Benchmarks

A _benchmark_ is a top-level function of a test file whose name ends in `_bench`. A plain `lus test` calls each benchmark once, as a test, so a benchmark that breaks fails with the tests. `lus test --bench` runs only the benchmarks and measures how long one call takes. When a benchmark returns a function, the runner measures that function, so the work done before the return, such as building the input, stays out of the measurement. Any other benchmark is measured itself.

```lus
local function sort_bench()
    local data = {}

    for i = 1, 1000 do
        data[i] = (i * 7919) % 1000
    end

    return function()
        local copy = table.clone(data)
        table.sort(copy)
    end
end
```

The runner first doubles the number of calls in a sample until a sample takes a twentieth of the time each benchmark has, which is 1 second unless `--bench-time` sets it. It then takes up to 20 samples within that time and reports the median time per call with its spread, the median absolute deviation as a percentage of the median. A separate run of at most 16 calls with the collector stopped counts the bytes that one call allocates. The count covers the code as it runs, so an allocation that the JIT removes counts nothing. Files run one at a time with `--bench` unless `--jobs` says otherwise, so that they do not compete for the processor.

```
ok   sort_test.lus (1 benchmark, 1130 ms)
  bench sort_bench: 145.63 us per call, spread 0.6%, 8240 bytes per call
```

`lus test --bench -u` saves the results in `__benchmarks__/FILE.json` next to the test file, as the _baseline_. A later `lus test --bench` compares each result with its baseline and reports the change in percent. The change counts as faster or slower when it exceeds both 2 percent and three times the larger spread of the two runs. Otherwise it counts as no change. A slower benchmark does not change the exit status, because timings vary from one machine to the next. `--json` prints one record per benchmark with the fields `ns`, `mad`, `calls`, `samples`, and `bytes`. A record also carries `base_ns` and `base_mad` when a baseline exists.

## Doc tests

An example in documentation becomes wrong when the code it describes changes. `lus test --doc` detects this by running the code blocks of Markdown files as tests. The arguments are Markdown files or directories, in which the runner finds the files whose names end in `.md` or `.mdx`. Every block fenced as ` ```lus ` is a test named after the line where its code starts, as in `line 12`. A block passes when it runs to the end without raising an error and prints every line that its `-->` comments name.

The text after `-->` on a line of a block is a line that the block must print, to standard output or to standard error, in any order. Runs of spaces and tabs compare equal, so the tab that `print` puts between its values matches the spaces of a comment. `...` in a comment matches any text, such as the file name and the line number in front of an error message. A line that holds only a `-->` comment names output as well, which suits a loop that prints several lines.

Output that differs between platforms, such as a path with the separator of the platform, takes one comment for each platform. A comment that starts with `-->(posix)` names a line that the block prints on every system other than Windows. A comment that starts with `-->(windows)` names a line that the block prints on Windows. The runner skips the comments for the other platform and fails a comment that names any other platform.

```lus
print(fs.path.join("logs", "today.txt"))
-->(posix) logs/today.txt
-->(windows) logs\today.txt
```

```lus
for _, name in ipairs({ "ada", "grace" }) do
    print(name:upper(), #name)
end

--> ADA  3
--> GRACE  5
print(catch error("disk full"))  --> false  ...: disk full
```

The examples in the [doc comments](/manual/tools#documentation) of a `.lus` file run the same way, so the example of a function stays correct with the function. With `--doc`, the runner also reads every `.lus` file it finds and runs each ` ```lus ` block inside a `---` comment or a `--[[- ... ]]` comment. The directory of the file comes first on `package.path`, so an example requires its own module by name. A source file whose doc comments hold no example stays out of the report.

```lus nocheck
--- Doubles a number.
---
--- ```lus
--- local mathx = require("mathx")
--- assert(mathx.double(21) == 42)
--- ```
function mathx.double(x)
    return 2 * x
end
```

Each block runs separately with none of the variables of the blocks before it. A block that calls `pledge` starts with no permissions, as the same code does under `lus`, so the denials that its comments show take place. Every other block holds every permission. Its detached coroutines must end for it to pass. Fence a block that cannot run alone, such as a fragment or code that shows an error, as ` ```lus nocheck `, which the runner records as skipped. The manual, the standard library specification, and the agent skills of Lus are all tested with `lus test --doc`.

```sh
lus test --doc docs/
lus test --doc README.md --filter "line 4"
```
