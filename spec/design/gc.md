# Garbage collection

The Lus 2.0 collector is precise and non-moving. It allocates small objects from size-classed pages, marks with a bitmap per page, and sweeps lazily. It runs in one of two modes. Incremental mode interleaves tri-color marking with the program under a goal-based pacer. Generational mode keeps survivors marked as an old generation, so that minor collections trace only young objects, and switches to incremental major collections on its own when most new objects survive. Generational mode is the default. Every state owns its heap, so workers never share objects. The bytes of long strings in worker messages are shared between heaps as reference counted blobs, which each heap releases when it sweeps the string that refers to them (`workers.md`).

## The heap

Small objects live in 16 KB pages carved out of 256 KB segments aligned to their size. The first page of a segment holds the metadata of the other fifteen. Each page serves one size class, a multiple of the 16-byte granule. The classes run 16, 32, 48, and so on up to 128 bytes, then grow by a quarter (160, 192, 224, 256, 320, ...) up to 2 KB, which keeps internal fragmentation under 20 percent.

A page also holds one kind of object. Leaf pages hold strings, bigints, decimals, and vector headers, which reference no other object, so marking sets their bit and never traces them. Scan pages hold everything else. Separating the two keeps text and numbers out of the cache lines the marker reads.

Objects larger than 2 KB come straight from the backing allocator and sit in a list. Thread stacks, vector payloads, prototype code, and table parts stay in the backing allocator as well, except the small parts of a table created with known sizes, which live in the cell of the table (`tables.md`). Every byte the state holds, in pages or outside them, goes through one counting allocator, and the pacer reads its total.

A fresh page allocates by bumping a pointer. A page that was swept allocates from a free list rebuilt in address order. Allocation sites that initialize every field skip clearing the memory.

## Object metadata

Every object starts with a header of one tag byte, one flag byte, and the finalizer state. The flags are the barrier bit, the free bit of an empty cell, the large bit, and the mark bit of a large object. Small objects keep their mark bit in the bitmap of their page, one bit per granule, so a sweep reads whole 64-bit words of marks and never touches a live object.

## Sweeping

Sweeping is lazy. When a mark phase ends, every page whose objects it judged waits for a sweep. The allocator sweeps a page when its size class reaches it and then allocates from the cells the sweep freed. After four sweeps that free nothing, the allocator takes a fresh page and leaves the rest to the collector steps, so one allocation never sweeps a large part of the heap. Collector steps sweep the pages that the allocator does not reach. A page left without live objects returns to the pool of free pages, where any size class can take it, and a segment whose pages are all free goes back to the backing allocator.

A sweep frees what a dead object owns outside its cell, such as the parts of a table, the stack of a thread, or the reference of a string to a shared blob. Safe builds fill dead cells with a fixed pattern, so a use after free reads garbage instead of a plausible object.

## Marking

Marking is tri-color. White objects are unmarked. Gray objects are marked and wait on an explicit gray stack. Black objects are marked and traced, and they carry the barrier bit. A mark phase starts by clearing the mark bitmaps and marking the roots: the main thread, the registry, the globals, the per-type metatables, the metamethod names, the fixed objects, and the objects waiting for their finalizers. Steps then trace gray objects, each within a budget of bytes.

The marker pops gray objects from the top of the stack and prefetches the object eight places below the top, the first two cache lines of it. Objects often reach the stack long before they are traced, as when a large table pushes all of its elements at once, and the prefetch lets the marker trace one object while the next ones arrive from memory.

Tracing a value that refers to an object the marker traces pushes the object without reading it, with the low bit of its address set. The object is marked when it pops, after the prefetch brought it close, and an entry whose object was marked in between is dropped, because whoever marked it also queued it, or it is old. Objects without references, such as strings, are marked at once, since they never reach the stack. Reading each object once, when it is traced, took a full collection of the three million records of `tables.lus` from 31 ms to 21 ms.

When the gray stack runs empty, the atomic phase ends the mark phase without the program running. It marks the roots again, traces every live thread again because stores into stacks take no barrier, and marks the current values of open upvalues that a dead thread still owns when a live closure captured them. It traces the objects that stores turned gray, converges ephemerons, moves unreachable objects with finalizers to the finalizer queue in registration order and marks them for one more cycle, and clears weak tables. Dead threads then close their open upvalues, and the sweep starts.

Weak tables keep the semantics of Lua 5.4. Keys and values that are strings, bigints, or decimals count as values and are never cleared. An ephemeron table keeps a value alive only while its key is alive. A value with a pending finalizer is cleared from weak-value tables. Interned strings are weak: a dead interned string stays in the string table until its page is swept, and finding it again in that window marks it, which revives it. When a sweep leaves the string table less than a sixteenth full, the table shrinks (`strings.md`).

Inline caches record slot numbers, never pointers, so they need no tracing. Table array parts that hold only integers or only floats store bare numbers, and the marker skips them.

## Parallel marking

On native targets, a mark phase that runs while the program is stopped traces on several threads once its gray stack holds enough work. Such phases are the whole mark phase of a full collection, the atomic phase, and every minor collection. A drain starts on the calling thread and checks every 1024 objects whether more than 4096 entries wait on the gray stack. When they do, it hands the stack to the helper threads, so a small heap never wakes them. Incremental steps stay on one thread, since a step traces only a few dozen kilobytes.

Each thread traces from a gray stack of its own and claims an object by setting its mark bit with an atomic or, so exactly one thread traces each object. A thread reads the flags of a header with atomic loads, and it sets the barrier bit of an object it claimed with a plain atomic store, which loses nothing because no other thread writes those flags then. The threads take the gray stack of the state in ranges of 1024 entries through an atomic cursor. A thread whose own stack runs past two ranges gives a range to the shared pool whenever another thread waits, keeping its top entries, which its prefetch already requested. A thread with nothing left waits on the pool. The drain ends when every thread in it waits and the pool is empty. The counters that threads change while others read them, and each gray stack, sit on cache lines of their own. Sharing those lines first held eight threads to twice the speed of one.

Weak tables and ephemerons keep their exact semantics because the parallel part only marks. A thread that traces a weak table appends it to the lists of the collector under a lock. Ephemeron convergence, the separation of objects with finalizers, the clearing of weak tables, and the verifier run on the calling thread afterwards, and each drain they start may again run in parallel. Objects that stores turned gray again can appear twice in their list, so the calling thread traces that list alone, and a gray stack that holds such a list drains on one thread until it runs empty.

The helper threads belong to the process. They start on the first drain that needs them, wait between drains by spinning briefly and then sleeping on a futex, and serve one state at a time, so a worker state that finds them busy marks alone. A helper joins a drain when it wakes, and a drain never waits for a helper that has not joined, so a helper that the system schedules late never lengthens a pause. By default the collector uses one thread less than the processor count, up to eight. `LUS_GC_THREADS` sets the number, and `LUS_GC_THREADS=1` marks on the calling thread alone. The WebAssembly build and single-threaded builds always mark alone.

A full collection of a graph of a million records with child tables (295 MB) took 17.3 ms on one thread and 6.6 ms on four and 4.4 ms on eight. On a graph of 3.5 million records (1 GB), it took 60 ms on one thread and 17 ms on eight. `fullgc.lus` builds half that first graph and collects it ten times, and it runs in 0.055 s where it ran in 0.110 s. The atomic phase of the last cycle of `gcpause.lus`, which traces the graph that the program built during the mark phase, went from 1.2 ms to 0.66 ms. The longest pause that `gcpause.lus` reports stays at about 1.4 ms, because it is the rehash of the 131,072-slot array part of its graph table rather than a collector step. Programs that never collect in full and whose heaps stay small see no change, apart from code layout: on `tables.lus` the build with parallel marking retires the same instructions as the build without it, within 0.2 percent, and takes 2 to 3 percent more cycles. The `-Dgc-stress` build lowers the thresholds to 32 entries checked every 16 objects, so the stress runs of the conformance suite drain in parallel all the time, and `-Dsanitize-thread=true` builds the runtime with ThreadSanitizer, which reports no race over the conformance suite in the stress build.

## Barriers

Every store of a collectable value into a heap object runs the barrier after the store. The fast path tests the barrier bit of the object, which only black objects carry. The stores covered are interpreter table stores (including a new string key), the same stores made by native code, which tests the barrier bit inline and calls `gc.barrierTable` for the slow part, `ops.rawSet` and everything built on it, `SETLIST`, upvalue stores and upvalue closing, `setmetatable` in both libraries, `debug.setupvalue`, `debug.upvaluejoin`, `debug.setuservalue`, the environment that `load` installs, user values of time zones, and lazily created enum members. A native that fills an object it just allocated needs no barrier, because a fresh object is white.

During a mark phase the barrier is backward: a store into a black object clears its bit and puts it on the gray-again list, and the collector traces it again before the atomic phase ends. A large table with no weak mode (at least 1024 slots) instead stays black, and the stored key and value turn gray. Filling a big table during a mark phase then never traces it again.

## Pacing

The pacer targets a heap size relative to the live data. After a cycle, `live` is the heap size when the mark phase ended less what the sweep freed. The next mark phase should end before the heap reaches `live * pause / 100`. When a major collection freed less than a sixteenth of what the program allocated since the previous one, the heap is growing, and the goal doubles until a collection frees more again. A heap that only grows then does a third less marking, and its peak size stays the same, since all of it is live. A program that turns from building to discarding waits one cycle at the doubled goal, which raises its peak. `gcpause.lus`, which builds a 50 MB graph and drops it, peaks at 235 MB where it peaked at 174 MB before. Marking traces about `live` bytes at `stepmul / 100` bytes per allocated byte, so the cycle starts at the goal less `live * 100 / stepmul`. A step runs every `stepsize` bytes of allocation. During marking, each step compares the work left with the room left before the goal and raises its budget when marking falls behind, up to 64 basic steps, which bounds the pause of a step that catches up. The defaults are a pause of 200, a step multiplier of 200, and a step size of 200 tables.

`collectgarbage("param", name [, value])` reads and sets `pause`, `stepmul`, `stepsize`, `minormul`, `minormajor`, and `majorminor`. `collectgarbage("step", n)` runs about `n` KB of work, or one basic step when `n` is zero, and returns true when a cycle finished. `collectgarbage("collect")` abandons a mark phase in progress, runs a complete cycle including its sweep, and runs pending finalizers.

## Generational mode

Generational mode uses sticky mark bits. Marks survive a collection, so every marked object is old and every unmarked object is young. The barrier bit then logs the first store into an old object since the last collection: the store clears the bit and appends the object to the remembered set. A large old table instead promotes the young key and value it receives by marking them and logging them.

A minor collection runs without interruption. It marks the roots and traces the remembered set, the old weak tables (so that entries referencing young objects are cleared or kept as in any table), and every live thread. Marking stops at marked objects, so it traces only young objects that survive, and each survivor becomes old. The atomic steps of a major collection follow: ephemerons, finalizers, weak tables, and dead threads. The sweep then visits only the pages that received objects since the previous collection, plus the large objects allocated since then. Every other page holds only old objects.

A minor collection runs after the program allocates `minormul` percent (default 20) of the heap that the last major collection left, and at least 1 MB. When the bytes that survived minor collections grow the old generation past `minormajor` percent (default 70) of that heap, the next collection is a major one, and it runs at the next collector step. A major collection clears every mark and marks to its end in one stop, on the parallel marker. Old objects die only in major collections, and a program observes their death through finalizers and weak tables. While it has either, a major collection also follows every 100 minor ones, so an old object with a finalizer is finalized even when the program allocates nothing but short-lived objects. After a major collection, the collector returns to minor collections when the major freed at least `majorminor` percent (default 50) of what the program allocated since the previous major collection. Otherwise most new objects live long, and the minor collection that follows, after the usual young allocation, tests whether that is still so. Every minor collection makes the same test: when two minor collections in a row free less than `majorminor` percent of what the program allocated before each of them, the young objects they traced live on and die old, and the next collection is a major one at the usual goal, set from the heap that the last major collection left. One such minor collection is not enough, since it may only have met a large result that the program keeps. In `logs`, the minor collection after the program joins its lines finds the 80 MB text alive, and a decision on that one collection sent the program to a major goal of 1.2 GB just as it began to discard what it allocates. Since a major collection marks in one stop, it starts at its goal, with no room kept for marking during the program. A growing heap doubles that goal, as in incremental mode. Keeping it undoubled lowered the peak of `logs` to 408 MB and of `template` to 804 MB, but it cost `tables.lus` 7 percent of its time and `template` and `json` 4 to 6 percent, which marked a growing heap more often.

A major collection that marked over many incremental steps kept every old object that died while it marked, and that floating garbage counted as live, so the goal of the next major collection was set from a heap that was mostly dead. The LRU program of the cross-language suite (4 million operations on a cache of 50,000 entries) keeps 35 MB alive, yet its incremental major collections reported 82 MB, and the major collections that minor collections asked for waited for a goal set from the 150 MB heap they found. Its heap reached 370 MB. Marking a major collection in one stop, starting it as soon as minor collections ask for it, and turning to major collections when minor collections free little took the peak resident memory and the best of seven wall times of the suite programs, ReleaseFast on an Apple M4 Max, as follows.

| program | before | after | time before | time after |
|---|---:|---:|---:|---:|
| lru | 605 MB | 89 MB | 1.30 s | 1.35 s |
| logs | 527 MB | 517 MB | 0.91 s | 0.89 s |
| template | 986 MB | 785 MB | 0.87 s | 0.85 s |

The baseline is the `rewrite` branch with constructor size feedback, which made every node of `lru` one cell and raised its peak from 410 to 605 MB. The times are the best of seven to nine runs. The `lru` time is 3 percent slower, and `fullgc.lus` and `patterns.lus` are 2 to 4 percent slower, because a major collection that marks in one stop evicts what the program had in its caches. `tables.lus`, whose heap only grows, became 8 percent faster.

On `lru` every minor collection used to trace about 6 MB of young objects that all survived, and the major collections ran at one and a half times the live data, with room kept for an incremental mark.

The `template` figures include the long strings built in place (`strings.md`), and the `logs` times vary by about 10 percent from run to run on this machine. The stop of a major collection is the price: the longest pause that `gcpause.lus` reports went from 2 to 5 ms to 3 to 7 ms on the same busy machine, since each major collection of its 50 MB graph now marks in one stop. Programs that need short pauses on large heaps select incremental mode with `collectgarbage("incremental")`.

`collectgarbage("generational")` enters generational mode with a full collection, whose survivors form the old generation. `collectgarbage("incremental")` leaves it. Both return the previous mode. In generational mode between major collections, `collectgarbage("step")` runs one complete minor collection.

## Closing a state

Closing a state runs every pending finalizer and then frees every object. The command line runner closes its state just before the process exits, and in builds without runtime safety it stops after the finalizers, the shutdown of workers, and the flush of output: the exit of the process returns the heap, which spares a last pass that reads every live object. Safe builds and embedders that call `api.close` free everything, so the allocators of the safe builds still check the whole teardown. On `tables.lus` the full teardown was a sixth of the run.

## Checking the collector

`zig build -Dgc-stress=N` runs a small collector step at every allocation point, so marking always overlaps the program, and ends a mark phase (or runs a minor collection) at every Nth point. `zig build -Dgc-verify=true` adds a heap verifier that runs at the end of every mark phase. It checks that every marked object is black and references only marked objects through strong references, which catches a missing barrier or a missing root at the collection where it matters. The conformance suite runs clean under both options together.

## Designs measured and kept out

### Allocation-site pretenuring

A prototype gave every table constructor an allocation site. The site identity was the inline cache entry of the `NEWTABLE` instruction, which no other access uses, and the optimizing tier passed the address of that entry to `newTable` and to the allocation of a table it had kept unallocated. A new table recorded its site in the unused bytes of its header. Minor collections counted, per site, the tables that survived (marked by the minor collection or promoted by a large old table) and the tables that their sweep freed. A site whose tables survived more than sixteen times as often as they died, over at least 256 of them, allocated its tables already marked and black, as old objects, while the collector was in generational mode between major collections. One table in 32 still started young, so a site whose tables began to die lost the status again.

An old table that receives a young value must be logged, and a constructor fills its table with stores right after allocating it. The prototype therefore had the slow path of the table barrier skip the log when the stored key and value are both marked or not collectable, since a black table may reference marked objects. Without that, every pretenured table was logged by its first field store and traced by the next minor collection anyway, so pretenuring saved nothing.

The benefit is bounded by what a minor collection spends on a survivor, which is one trace of a few nanoseconds. On a program that keeps two million records `{x = i, y = i * 2}` in an array while it builds eight million short-lived tables, the 48 minor collections took 4.3 ms instead of 10.5 ms, and all collector work 27 ms instead of 34 ms. The program still ran slower, 0.256 s against 0.240 s before the change, because the site record cost every table allocation a load, a header store, and a test, and the pretenured tables took the slow path of the barrier for each field store. Recording sites alone, with pretenuring switched off, cost 3 to 9 percent on `tables.lus` and the other benchmarks that allocate tables. `tables.lus` itself cannot gain: its tables all survive, so after the first major collection the collector runs incremental cycles, and 2.98 of its 3 million allocations met a pending major collection where pretenuring does not apply. `gcpause.lus` gains nothing either, because its records hold young strings and each is logged by its first store. Survivors in a sticky mark bit collector are never copied, so a survivor costs a minor collection only the trace that pretenuring would save, and a pretenured table pays for its barriers instead. Lus allocates every table young.
