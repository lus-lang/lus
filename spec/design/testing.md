# Testing the runtime

This note describes how the Lus runtime is tested, what it borrows from the testing of SQLite, and the order in which the parts are built. Its goal is a runtime that a reader can trust with any program: every tier computes the same result, every allocation failure ends in a clean error, and every parser of untrusted text survives any input.

## What exists

The runtime has five layers of tests today.

1. **Conformance.** About 6,200 tests in 106 files under `tests/conformance`, run by `lus test`. Each file runs in its own process and its own temporary directory. CI runs the suite with `LUS_JIT=off`, with the default setting, with `LUS_JIT=eager`, and with `LUS_JIT=opt-eager`, on Linux, macOS, and Windows. The language server tests run alongside them.
2. **Stress builds.** `-Dgc-stress=97` collects at almost every allocation point, and `-Dgc-verify=true` checks the tri-color invariant and the write barriers after every mark. The guide in `runtime/HACKING.md` asks for a run of that build after a change to the heap, a store, or the JIT. CI does not run it.
3. **Fuzzing.** `runtime/src/fuzz.zig` holds five targets: the lexer, the parser, the compiler, formatter idempotence, and the loader of binary chunks. `zig build test` runs each target once over 18 seed programs. `mise run fuzz` mutates them for a million iterations. No target runs a program, and none reaches the standard library.
4. **WebAssembly.** `packages/wasm/scripts/conformance.mjs` runs the conformance suite through `lus.wasm` with the JIT off and eager and fails when the two disagree.
5. **Tools and embedding.** The C embedding tests in `tests/embed`, fixture tests for `lus build`, `lus check`, `lus doc`, and `lus debug`, and `lus test --doc` over the manual, the specification, and the agent skills.

Every test above is written by hand, except the fuzz inputs. A hand-written test checks what its author thought of. The bugs that the manual rewrite and the speed work found in the last month (a `having` alias that resolved to an outer variable, an integer overflow in `timecore.zig` reachable from Lus, `range` loops that never ended, a lost worker message) were each a combination of two features that no test combined.

## What SQLite does

SQLite is tested by several independent harnesses, and its developers report about 590 times as much test code as library code. The methods that matter here are these.

- **Many independent oracles.** TH3 runs the same tests on every platform and configuration. The SQL Logic Test runs millions of queries against SQLite and other engines and compares the answers. A disagreement between two implementations is a bug in one of them, and nobody has to write down the expected result.
- **Anomaly testing.** A wrapper around the allocator fails the Nth allocation. A test runs once to count its allocations, then once for each N, and checks that every run ends with `SQLITE_NOMEM`, frees what it allocated, and leaves the database intact. The same is done for I/O: a virtual file system fails the Nth read, write, or sync, and simulates a crash at every point of a transaction.
- **Fuzzing with grammar.** Random SQL from a grammar finds bugs in the planner that byte mutation never reaches, and dbsqlfuzz mutates the SQL and the database file together. Every crashing input becomes a test case.
- **Coverage as a gate.** SQLite reaches 100% branch coverage with TH3, measured on the shipped build. A branch that no test takes is either a missing test or dead code.
- **Assertions and sanitizers.** Thousands of `assert` statements stay in debug builds, and the tests run under Valgrind, the address sanitizer, and the undefined behavior sanitizer.
- **Regression discipline.** Every bug gets a test before its fix, and the test stays forever.

## The plan

The parts below are listed in the order of the bugs we expect them to find. Each part has a quick version that gates every change and a long version that runs every night.

### 1. Differential testing across tiers

The runtime runs one program in many ways: the interpreter, the default tiering, the baseline JIT that compiles a function on its first call, the baseline JIT that compiles after two calls, the optimizing tier on the first call, the optimizing tier after three calls, the optimizing tier with short chains of direct calls, the gc-stress build under both JIT tiers, the x86-64 build, whose JIT is a second backend, and the WebAssembly build with its JIT off, on, and eager, which is a third. These configurations must agree on the output of every program and on every error it raises. That agreement is an oracle that needs no expected output, the same oracle as the SQL Logic Test. Each configuration compares with the interpreter of its own architecture, since arm64 and x86-64 differ in their math libraries and in the sign of a NaN, and the WebAssembly host reports errors without a traceback. One more configuration formats the program with `lus fmt` first, which must keep its meaning.

The generator, the runner, and the reducer live in `tests/diff` and are written in Lus, so they exercise Lus too. A bug of the runtime must not hide a bug in its own test, so the three run interpreted with `LUS_JIT=off`, the generator writes each program to a file, and every configuration runs that file in a fresh process. A program therefore depends on the generator's run only through its text, and the configurations under test never share a process with the code that judges them. The WebAssembly build runs in Node through a small host script, `tests/diff/wasm.mjs`. The runner starts each process through `io.popen` with its variables set by `os.setenv`, so it runs the same way under `/bin/sh` and under `cmd.exe`. On POSIX systems perl stops a program at its time limit. On Windows the time limit of the CI step stops the run, and CI runs a short batch there. The generator builds programs from a typed model of the language. Each expression it emits has a known type, so most programs run to the end instead of stopping at the first type error. It composes the features that interact: closures and upvalues, varargs and multiple returns, `catch` with and without handlers, `<close>` variables across yields and errors, coroutines and detached coroutines, metamethods on tables, enums, groups, do-expressions, `continue`, slices, string interpolation, optional chaining, queries over tables, integer overflow, float edge cases, bigints and decimals, and string functions on WTF-8 text. The body of a program is a few units, each a function called up to 160 times from a loop whose arguments change type partway, from integers to floats, numeric strings, or values near the edges of the integer range. Code compiled for one type then meets another and leaves through its guards. Other statements change the element kind of an array in the middle of a loop, read tables of several shapes through one site, compare integers and floats near 2^53 and 2^63, and run numeric loops at the ends of the integer range.

A program prints a trace of the values it computes. The trace leaves out what the language leaves open: table addresses and the order of `pairs`. An error is printed by its message, which includes the line, so the tiers must also agree on positions.

A run that disagrees, crashes, or hangs goes to the reducer, which reads the program as a tree of lines by indentation and deletes statements, unwraps blocks, and replaces parenthesized expressions with literals while the disagreement stays, in the manner of hierarchical delta debugging. It took the first finding from 230 lines to 21 in three seconds. The small program it ends with goes into `tests/conformance/diff_regress_test.lus` once the bug is fixed, or into `tests/diff/OPEN.md` while it is open.

`mise run diff` runs the same 200 programs on every change. `mise run diff:long` runs fresh seeds until stopped, and the nightly job runs it for 80 minutes on Linux and macOS.

The first 7,000 programs found two bugs. A `__close` handler that raised while `catch` unwound could move the frame list under the handler, which then wrote through a stale pointer. The optimizing tier lost one call of a closure that incremented an upvalue in a loop, because its common subexpression key left out the memory class, so a load of a captured register stood in for a later load of the same slot. Both are fixed with regression tests.

### 2. Deeper fuzzing

The fuzz targets in `runtime/src/fuzzlib.zig` reach the code that reads untrusted text at run time: `fromjson` and `tojson`, `fromcsv` and `tocsv`, pattern matching, `string.format`, `time.parse`, `tonumber`, `bigint`, and `decimal`, `string.pack`, `string.unpack`, and their vector forms, every archive codec, and the string functions on arbitrary text. Each target runs a property written in Lus over the input, so it checks behavior and not only the absence of a crash. JSON and CSV that parse must format to text that parses to the same value, a number must print to text that reads back as the same number, `string.gsub(s, p, "%0")` must return `s` for any valid pattern, and each codec must decompress its own output. The seeds live next to each target, and every crash becomes a seed.

The JSON target found that an array with a `null` element formats as `{}`, which follows the specification of both functions but loses data (`tests/diff/OPEN.md`).

### 3. Out of memory injection

A build option `-Dfail-alloc=true` numbers every allocation of every state and every heap segment. `LUS_FAIL_ALLOC=N` makes the Nth allocation fail and every later one succeed, `N+` makes every allocation from the Nth on fail, and `count` prints how many allocations a run made. `tests/oom/run.lus`, which also runs interpreted in a normal build, counts the allocations of each conformance file, then runs the file once for each sampled N and checks three things: the process does not crash or panic, the leak checker of the safe build reports nothing, and the run ends in bounded time. A test may fail and a run may end with "not enough memory". Each distinct failure is reported once, with the smallest N that produced it. `mise run oom` samples 8 values of N per file on every change, and the nightly job samples 400, then 100 with every later allocation failing too.

The first sweeps found these bugs, all fixed: panics in `print` and in the permission registry, an index below the stack in a worker whose script failed to compile for lack of memory, a panic while canonicalizing a path permission, and leaks in `-F` flags, `pledge`, and the copy of a permission set for a worker. A hang in `workercoro_test.lus` led to three more. `coroutine.detach` and `network.serve` raised the error of a failed allocation on the new coroutine instead of the caller, which then reported "<no error object>". `worker.receive` slept on a condition when it could not open the wake source of the scheduler, which blocked the coroutines it was waiting for. `lus test` waited for the coroutines of a test that had failed, which could wait forever for a message the failed test never sent.

The numbering of allocations follows the timing of worker threads, so under the load of a sweep one number can land in a different place than it does alone. When it lands in the start of a coroutine that a test depends on, the test waits forever by construction, as any program would. The runner therefore runs a hang again three times alone, reports it only when it comes back, and counts the others on a line of their own. `LUS_FAIL_ALLOC_TRACE` prints the stack of each injected failure, which shows where a finding starts.

### 4. I/O fault injection

A build option `-Dfail-io=true` gives the process an `Io` whose file and socket operations pass through a countdown (`runtime/src/vm/faultio.zig`). Zig routes every streamed read and write of a file or a socket through one entry of its `Io` interface, so one wrapper covers `io`, `fs`, and the network library. It also counts positional reads and writes and file opens. `LUS_FAIL_IO=N` makes operation N fail with the error a real system reports: `InputOutput` for a read, `NoSpaceLeft` for a write, `ConnectionResetByPeer` for a socket, and `ProcessFdQuotaExceeded` for an open. `LUS_FAIL_IO=N:short` makes every file read and write from operation N on move one byte, which a correct caller retries. Sockets keep their full transfers in that mode. The scheduler waits for a socket edge after a short transfer, which on a real system means the buffer is empty or full, so a short transfer with data still waiting would make any correct program wait forever. `tests/oom/run.lus --io` sweeps N over the conformance suite with the same checks as the allocation sweep. `mise run io` samples 20 failures and 5 short starts per file, and the nightly job samples 200 and 50. SQLite reads and writes through its own file layer, which this wrapper does not reach.

The first sweeps found no crash or leak. They found that an error the system message table did not know, such as a failed open, reached Lus code as the Zig name of the error, so `io.open` reported `ProcessFdQuotaExceeded` where it now reports "Too many open files". An injected fault fails one side of a connection while the other side stays healthy, so a test whose peer waits without a timeout for the failed side hangs. The I/O sweep lists such hangs apart and does not count them as failures.

### 5. Coverage

A build with `-Dcoverage=true` instruments the runtime with the pass that the fuzzer of `zig build test --fuzz` uses (`runtime/src/coverage.zig`). LLVM gives every edge of the control flow graph a counter, and edge coverage counts both sides of every branch. `LUS_COVERAGE=DIR` makes every process write the edges it reached to a file of its own, so the processes that `lus test` starts all count. `LUS_COVERAGE_REPORT=DIR` merges the files and maps each edge to its source file through the debug information of the binary, so the report needs no tool outside the runtime. `LUS_COVERAGE_FILE` lists the lines of one file that hold an uncovered branch.

The coverage build is a ReleaseFast build, as releases are, so the failing sides of the bounds and overflow checks of a safe build stay out of the count, and every branch left is one written in the source. An optimized build inlines a function into each of its callers, which turns one branch of the source into one edge per call site. The report therefore keys each edge by the source position of the block it enters and counts each position once, covered when any of its copies ran. That count is the branch coverage of the source, as gcov reports it for SQLite. A line whose only uncovered branch is the error return of a `try` or the other side of a `catch` or an `orelse` is a failure path, which the allocation and I/O sweeps of parts 3 and 4 reach. The coverage binary is built with both fault layers, so a sweep run through it counts as well.

The conformance suite under the interpreter, the default tiers, and `opt-eager`, together with the doc tests, covers these branches of `runtime/src`, measured on an Apple M4 Max. ### 6. Properties and metamorphic tests

Some results have an oracle other than another tier. These tests live in `tests/conformance/props_test.lus` and draw their inputs from a seeded generator, so a failure prints the seed that reproduces it.

- Integer, bigint, and decimal arithmetic agree on random operands where all three are exact, bigints agree with decimals past 64 bits, and integer arithmetic wraps exactly where bigint arithmetic reduced to 64 bits says it does.
- `fromjson(tojson(v))` and `fromcsv(tocsv(rows))` return a value equal to `v` and `rows`.
- Random WTF-8 strings keep the string invariants: `#s` equals the count of `utf8.codes`, `s:sub(i, j) .. s:sub(j + 1)` equals `s:sub(i)`, and slices agree with `string.sub`.
- A query returns the same rows as a hand-written loop over the same table, and its groups partition the rows.
- `table.sort` agrees with an insertion sort.
- `lus fmt` keeps the meaning of a program, which the `fmt` configuration of the differential tester checks on every generated program.

### 7. Sanitizers and stress in CI

The nightly workflow runs the conformance suite in a `-Dgc-stress=1 -Dgc-verify=true` build, which collects at every allocation, on Linux and macOS with the JIT off, eager, and optimizing. It also runs the long versions of the differential tests, the allocation and I/O sweeps, and the fuzz targets, and uploads each finding.

A build with `-Dsanitize-c=true` compiles the vendored C libraries (SQLite, Zstandard, and Brotli) in safe mode with the undefined behavior sanitizer, which reports each finding with its place. Zig offers no address sanitizer, so the safe build of the Zig code and the leak checker of its allocator stand in for it there. The conformance suite and 30,000 runs of every fuzz target, including the round trips of every archive codec, found nothing under the sanitizer. A longer run stalled on a decimal with a huge exponent, whose exact sums took time quadratic in the exponent, and found that a decimal zero with a positive exponent printed one zero per digit of the exponent. Decimals now hold at most 131,072 digits before the point and 16,383 after (`spec/design/numbers.md`), and both are fixed. `mise run sanitize` runs both, and the nightly job runs the fuzz targets for 5 million runs under it.

### 8. Coverage toward 100%

SQLite measures branch coverage on the build it ships, and so will Lus. Releases are ReleaseFast builds, which carry no bounds or overflow checks, so the coverage build becomes `-Doptimize=ReleaseFast -Dcoverage=true`. The failing sides of the safety checks then leave the count, and every edge left is a branch written in the source. The first step measures that build, which replaces the numbers of part 5.

The target is the code that every program runs: `vm`, `compile`, the collector in `vm/gc.zig` and `vm/heap.zig`, and the core of `lib`, which is `base.zig`, `string.zig`, `table.zig`, `math.zig`, `coroutine.zig`, and `utf8.zig`. The report lists these as directories of their own. Each uncovered edge ends in one of three ways.

1. **A test.** Most uncovered edges are error paths and rare cases that a conformance test reaches from Lus: a metamethod that returns an unusual value, a table resize at a boundary, a compiler limit. These tests go into the conformance file of the feature they exercise, so they also run under every tier and in the differential, allocation, and I/O sweeps.
2. **A unit test.** Some states are reachable only from inside the runtime, such as an allocator that returns a block at an exact size class. A Zig unit test covers those. The unit tests run in their own binary, so the coverage build instruments that binary too, and the report merges the two by source position. A position counts as covered when either binary covers an edge into it.
3. **A mark.** A branch that no input can reach is either removed or marked. Part 10 adds `inv.always(c)` and `inv.never(c)` in the manner of SQLite's `ALWAYS` and `NEVER`. A defensive branch written as `if (inv.never(cond)) return error.Corrupt` keeps its check in a release build, raises in a test build when it is taken, and folds to a constant in the coverage build, so it leaves the count of edges. The report prints how many marks each directory holds, which keeps the marks visible and few.

The work goes file by file, starting with the files of the most uncovered edges, which `LUS_COVERAGE_FILE` lists line by line. The goal for each target directory is 100% of its edges with every mark justified in a comment. Each gated tip reports the new numbers.

**MC/DC.** Modified condition and decision coverage asks that each condition of a decision be shown to change the outcome of the decision on its own. LLVM computes it only from the coverage mapping that Clang emits, which Zig does not, and the instrumentation pass of part 5 runs after the optimizer, which may merge the conditions of `a and b` into one select. The runtime will measure MC/DC with a source transform on the target directories instead. A tool written in Zig parses each file with `std.zig.Ast`, wraps every condition of an `if`, `while`, `and`, and `or` in a call that records its value, and records the outcome of each decision. A run of the transformed runtime then writes, for each decision, the distinct vectors of condition values it saw, and the report finds for each condition a pair of vectors that differ in that condition and in the outcome, which is the unique cause form of MC/DC. The same parser serves the mutation tool of part 9. MC/DC is measured nightly and reported beside the edge coverage, without a gate, until the edge coverage of the target directories reaches its goal.

**Publication and the ratchet.** The table of part 5 grows a row for each target directory and a column for MC/DC, and the nightly summary prints the same table. The file `tests/coverage/baseline.txt` holds the covered share of each directory. A CI job on Linux builds the coverage binary, runs the conformance suite under the interpreter, the default tiers, and `opt-eager`, and fails when a directory falls more than 0.2 points below its baseline. The margin absorbs the timing of worker threads and of the collector, which changes a few edges from run to run. `mise run coverage:ratchet` writes the new baseline after a change that raises coverage, and a change that adds code without tests shows up as a drop that the author either covers or explains in the baseline commit.

### 9. Mutation testing

Coverage shows that a test runs a branch, and mutation testing shows that a test notices when the branch is wrong. A mutant is the runtime with one small change: a comparison flipped (`<` to `<=`, `==` to `!=`), a constant moved by one, `and` swapped with `or`, `true` swapped with `false`, the operands of a subtraction swapped, or one statement removed. A mutant is killed when some test fails on it, and the mutation score of a directory is the share of its mutants that the tests kill.

The tool parses each source file with `std.zig.Ast` and lists every place where a mutation applies, so every mutant is valid Zig syntax. A run samples mutants from the lines that coverage reaches, since a mutant on an uncovered line survives by construction and part 8 already counts those lines. For each mutant it copies `runtime/` to a scratch directory, applies the change, and builds. A mutant that does not compile is discarded. A mutant whose binary is identical to the binary of the unchanged source is equivalent and is discarded too, which removes most mutants that cannot change behavior. The tests then run cheapest first, and the first failure kills the mutant: the conformance suite with the JIT off in parallel, the same suite under `opt-eager`, the 200 programs of the differential gate, and the unit tests. A mutant that hangs or crashes is killed.

Each mutant needs a build, which takes minutes, so a run is a sample. The build rules apply: one build at a time with two jobs. `mise run mutate` takes a count, a seed, and a directory, prints each mutant with its verdict, and ends with the score of each directory and its confidence interval. The nightly job runs 40 mutants with a fresh seed and uploads the report. Survivors are triaged by hand. A survivor in code that matters gets a test that kills it, and the test goes in with its mutant recorded in the commit message. An equivalent mutant that the binary comparison missed goes into a list that later runs skip.

**Progress.** `tests/mutate/mutate.zig` lists the sites of five kinds of mutation in a file: flipped comparisons, `and` and `or` swapped, integer constants moved by one, swapped operands of subtractions, divisions, remainders, shifts, and orderings, and dropped statements that call or assign. It skips tests and comptime blocks. `tests/mutate/run.lus` copies the runtime, builds it unchanged as releases are built, and times the conformance files to run them cheapest first. It then samples mutants, from covered lines when it has an export of the covered positions, and kills each with the first file that fails, first with the JIT off and then under `opt-eager`, since some paths run only in optimized code. It drops a mutant that does not compile or that builds to the same binary, skips the mutants of `tests/mutate/equivalent.txt`, and ends with the score of each directory and its 95% interval. `mise run mutate` runs 40 mutants, and a nightly job runs 40 with the day of the year as the seed. A mutant that passes the conformance files then runs 200 differential programs, judged by the unchanged runtime, and last the unit tests, which need a build of their own, and the unchanged copy must pass both before sampling starts.

The first runs built 11 mutants, of which 7 died and 4 survived. Two survivors were equivalent and went into the list: a loop bound that the other condition of the loop always reaches first, and a slot size that only changes the memory a small constructor reserves. One survivor showed that no test compared a value with a constant just past the range of the signed 8-bit immediate of a comparison, which the mutant moved, and a test in `compile_test.lus` now kills it. The last survivor lies in the check of `table.appendArray` that keeps a full list from growing over an integer key that its hash part holds. Only `table.insert` in optimized code reaches that check, and no test found so far makes optimized code take that path with such a key, which stays open.

### 10. Invariants and crash tests

**Invariants.** A module `runtime/src/vm/inv.zig` provides `inv.assert(c)`, `inv.always(c)`, and `inv.never(c)`, enabled by a build option `-Dinvariants`, which is on in Debug builds and in the test binaries and off in release builds. When it is on, a false `assert` or `always` and a true `never` panic with their place. When it is off, `assert` compiles to nothing, and `always(c)` and `never(c)` return `c`, so a defensive branch keeps its check without a panic. In the coverage build they return constants, as part 8 describes. Checks that walk a whole structure run at fixed points:

- **Heap and pages.** After each collection, every page belongs to one size class, its free list stays inside it and counts the free cells, no live object sits on a free cell, and the total of the live cells matches the byte count of the state.
- **Tables.** After each resize and each rehash, the array part holds no element past its length, every key of the hash part lies in the chain of its own hash, the element kind of a typed array matches its contents, and the shape of a table with a shape matches its keys.
- **Shapes.** Every transition leads to a shape with one key more than its parent, and the slot of each key lies inside the table it describes.
- **Frames and the stack.** On every call and return, the base, the top, and the frame of each call lie inside the stack, and the frames of a thread are ordered.
- **Strings.** At each allocation, the length is within the limit, the ASCII flag matches the bytes, the count of characters matches the WTF-8 text, and a short string is interned exactly when the string table holds it.

The checks of every call and allocation are cheap. The walks of the heap and of every table are not, so they run at the end of each collection and at state close. CI runs the conformance suite in a `-Dinvariants=true` ReleaseSafe build on Linux under every JIT mode, and the nightly gc-stress runs turn them on as well.

**Durable updates.** Three calls let a program make a change survive a loss of power. `file:sync()` asks the system to write the data and the size of an open file to its disk, through `fsync`, or `FlushFileBuffers` on Windows. `fs.move(source, dest, { replace = true })` replaces an existing `dest` in one rename, through `rename`, or `MoveFileEx` with `MOVEFILE_REPLACE_EXISTING` on Windows, so a reader sees the old file or the new one and never neither. `fs.sync(dir)` makes the entries of a directory durable, so a file created, removed, or renamed in it stays that way. The documented sequence for replacing a file writes a temporary file in the same directory, syncs it, moves it over the target with `replace`, and syncs the directory. Windows flushes a file only through a handle with write access, so there `fs.sync` opens a file for writing, and a directory sync does nothing, since its file systems commit the entries of a directory through their log. `fs.sync` still asks only for `fs:read`, because it writes nothing through that handle, and a pledge describes what a program may change. `file:sync()` on a handle opened only for reading does nothing on Windows, since nothing was written through it.

**Crash tests.** The I/O fault build of part 4 gains two crash modes. `LUS_FAIL_IO=N:kill` makes write operation N write a random prefix of its bytes, possibly none, and end the process at once, as a kill would. Whatever reached the system before the kill survives it.

`LUS_FAIL_IO=N:powerloss` models the loss of power after the crash model of SQLite's atomic commit. The fault layer keeps, for each file, a journal of the writes and size changes since its last sync, and for each directory the entries created, removed, and renamed since its last sync. At operation N it rewrites what is on disk to one state that a real disk could have left, then ends the process.

- **Lost and reordered writes.** Each unsynced write survives or is lost independently of the others, so later writes may survive while earlier ones are lost. A sync of the file is the only barrier.
- **Torn sectors.** A surviving write that is the last one touching a 512-byte sector may be torn: only a run of its first bytes or only a run of its last bytes reaches the sector, since a sector is written in order and never atomically.
- **Growth before content.** A file that grew may keep its new size while the new region holds garbage, never zeros, which catches a reader that trusts a length.
- **Neighboring bytes.** By default a write damages only the bytes it writes. With the option `LUS_FAIL_IO_PSOW=0` a torn sector may also lose the old bytes around the write in that sector, which is the case that SQLite's powersafe overwrite setting covers.
- **Directory entries.** A creation, removal, or rename survives only once its directory is synced. Otherwise it may be undone: a renamed file returns to its old name, a removed file returns, and a new file disappears. A removal is all or nothing.

`tests/crash/run.lus` runs scenario programs. Each scenario updates files by one documented sequence: writing a new file, appending to a log, overwriting part of a file in place, replacing a file through a temporary file, `file:sync()`, `fs.move` with `replace`, and `fs.sync`, and committing to a SQLite database. The harness counts the write operations of a scenario, then runs it once for every N under `kill` and under `powerloss`, the latter several times with different seeds for the choices of the disk, and after each crash runs a checker that reopens what is left. The checker asserts that the update either happened in full or did not happen, and that the program could tell which. Scenarios are small, so every write point is tried and none is sampled. Each scenario also runs with one step of its sequence left out, which must show the failure that the step prevents, so a guarantee is never claimed for a step that the test cannot tell apart. SQLite writes through its own file layer, which the fault layer does not reach, so the SQLite scenario runs under a SQLite VFS shim in the fault build that applies the same model to the writes and syncs of SQLite, and checks after each crash that every committed transaction is present and no other.

The guarantees go into the manual page on the filesystem in plain prose: which sequence makes an update atomic and durable, which step each guarantee needs, what a kill leaves of a file that was being written, and what `flush`, `close`, and `sync` each promise.

**Progress.** The three calls, the two crash modes, the harness, and the section [Durable writes](/manual/filesystem#durable-writes) of the manual are in place. `file:sync()` also issues `F_FULLFSYNC` on macOS, where `fsync` leaves the data in the cache of the drive. The kill mode ends the process just before operation N, so a kill leaves exactly what the system received. Syncs, renames, deletions, and changes of size count as operations, and an N of 0 crashes after the last one, which is how the harness checks durability. The power loss model in `runtime/src/vm/faultcrash.zig` follows the rules above and keeps the entry changes of one file in order. The harness runs four scenarios, each crashed at every operation by a kill and by power losses under eight seeds, with powersafe overwrite on and off.

| Scenario | Every step | Each step left out |
| --- | --- | --- |
| Replace through a temporary file | safe | caught without the file sync and without the directory sync |
| Append with a sync per record | safe with powersafe overwrite, caught without it | caught without the sync |
| Overwrite in place with a sync | caught, as the manual says | |
| SQLite commit with `synchronous = FULL` | safe | caught with `synchronous = OFF` |

A lost append on a disk without powersafe overwrite can damage the end of the record before it in the same sector, which the manual states. CI runs the harness on Linux and macOS.

The invariant checks cover strings at each allocation, whose validity, ASCII flag, and count of characters must match their bytes, tables after each resize, whose hash part must have a size of zero or a power of two, a count of used slots that matches, and every live key where a lookup probes for it, shapes on each new shape, frames on each call, and the heap at the end of each mark phase, where every marked object must reference only marked objects. A nightly job runs the conformance suite in a `-Dinvariants=true` build, interpreted and in optimized code. The string check found that `skip` in `lus test` built its message with the flags of ASCII text and a count of bytes, so a reason with accented letters had a wrong length, which is fixed. The second round added the rest. After each sweep, a page must agree with its size class: its cells, its usable bytes, and its top, marks only where cells start, and a free list below the top, on cell boundaries, made of cells flagged free that are not marked, without a cycle. At the end of each mark phase, the bytes of the cells that hold objects, counted page by page, must match a running count that a checking build keeps beside the byte counter of the state. After each resize, an array part must hold what its kind says, holes alone for an empty kind and pointers to strings or tables for those kinds. A string must be interned exactly when the string table holds it, at its creation and when it joins the table. A return must leave its results inside the stack, in the slot of its function or below it, within the window of its caller. The suite passes all of them interpreted and in optimized code, and part 10 is complete. Part 9 comes next.

### 11. Faults beyond files

Part 10 fails a file write at every step and checks what a program can rely on afterwards. Part 11 applies the same method to the network, to coroutines and workers, and to the input a program reads. Every scenario counts its steps first, then fails each step in turn, and a checker states what must hold.

**Network faults.** The fault layer of part 4 numbers every socket operation, and part 11 numbers name lookups and the steps of a TLS handshake as well. New modes give each operation N a fault of its own kind: `N:reset` fails it with a reset connection, `N:eof` makes the peer close its sending side from that read on, `N:dns` fails a lookup, and `N:tls` fails a handshake with a certificate or protocol error. A peer that sends one byte at a time, or closes half of the connection after a set number of bytes, is a loopback peer written in Lus that the harness controls, so the trickle reaches the program through a real socket and the scheduler sees real edges. The scenarios cover `network.fetch`, `network.serve` with plain requests, streamed bodies, and the upgrade of a request to a WebSocket with status 101, and the TCP and UDP sockets. After each fault the checker asserts four things: the program received one of the errors that the manual lists for that call, no socket is left open, which the fault build counts and prints at exit, no coroutine is left waiting, which the scheduler reports at state close, and a server that lost one connection still answers a fresh request on another.

**Coroutines and workers.** The fault build numbers the suspensions of detached coroutines, and `LUS_CANCEL_AT=N` cancels the coroutine that reaches suspension N, as `coroutine.close` does. A suspension is any point where the scheduler parks a coroutine: a wait on a socket, `worker.receive`, a yield, a sleep, and the update of a `<lazy>` or `<observe>` variable that yields. Each scenario holds `<close>` variables that record their order, and the checker asserts that they ran in the reverse order of their declaration, that every other coroutine ran to its end, and that the invariants of the scheduler from part 10 hold. Workers fail in two ways. `LUS_FAIL_ALLOC` already numbers the allocations inside a worker, and a sweep scoped to the worker thread fails each one. `LUS_WORKER_FAIL=N` raises an error at step N of the message handling of a worker, a step being a receive, a send, or the copy of a message. The creator must see the failure through `worker.receive` or `worker.status` within a time limit, and must receive every message that the worker sent before the step that failed, which the scenarios check with sequence numbers.

**Truncated and corrupted input.** `tests/corrupt/run.lus` takes valid seed inputs for `fromjson`, `fromcsv`, `time.parse`, `decimal`, `bigint`, `tonumber`, `string.unpack`, the loader of binary chunks, and every archive codec. For each seed it tries every truncation and every single bit flip, and samples 4,096 of each for a seed longer than 512 bytes. Every result must be an error or a value. A crash, a panic, or a run past its time limit is a finding. A value is checked too: for the text formats it must format to text that parses to the same value, and for a codec whose format carries a checksum, such as gzip, zlib, and Zstandard frames with their checksum, a flipped bit must raise an error. A codec without a checksum may decode a flip into other data, and the manual says which codecs check their input. The loader of binary chunks must reject or load each corrupted chunk without crashing. Running a chunk that loads stays out of scope, since the manual already treats binary chunks as trusted input. The inputs run in batches, one child process per batch, and a batch that crashes is split in halves until the input that crashes it stands alone.

**Clocks and children.** In the fault build, `LUS_CLOCK` replaces the wall clock with a script: a jump back of an hour at read N, a jump forward, and a clock that starts just before a change of daylight saving time in the zone of `TZ` and runs across it. The checker asserts that `os.time`, `time.now`, and `os.date` agree with the scripted clock at each read, that `time.monotonic` never decreases, and that sleeps and timeouts, which the scheduler measures on the monotonic clock, keep their length. Children of `os.execute` and `io.popen` are killed by each common signal while they run, before they write, and while their output fills the pipe, and the call must report the signal in its status and return. The fault layer also makes the system calls that wait on a child, read a pipe, and write a pipe fail with an interruption at step N, which the runtime must retry, and a helper sends real signals to the process on POSIX systems. Windows has no interrupted system calls, so it runs only the scenarios of killed children.

These scenarios run in the nightly job, each enumerated in full where it is small and sampled where it is not, and a short sample of each runs with every change. Every finding gets a regression test, and its scenario stays.

**Progress.** Three pieces are in place. `tests/corrupt/run.lus` covers `fromjson`, `fromcsv`, `time.parse`, `decimal`, `bigint`, `tonumber`, `string.unpack`, the loader of binary chunks, and the five codecs, about 16,000 inputs in batches of 256, and runs in CI on Linux and macOS. It found no crash. Its checks of values found two things that the harness first assumed wrongly. The Zstandard frames that `compress` wrote carried no checksum, so `compress` now writes one into every frame, and gzip, zstd, and lz4 all notice a changed byte. An infinity writes as `inf`, which no number parses from, as in Lua, and the manual states it. The manual also states in the section on binary chunks that a chunk is trusted input and that `load` checks its structure but not its code.

`LUS_WORKER_FAIL=N` fails step N of the message handling of workers, and `LUS_FAIL_ALLOC_SCOPE=worker` numbers only the allocations of worker threads. `tests/faults/workers.lus` runs a worker that sends numbered messages under every step and every allocation of the worker, with a creator that receives in the main chunk and one that runs a detached coroutine meanwhile, so its wait goes through the scheduler. Every run ended within its limit, and the creator received every message sent before the failure, in order. The hang of `tests/diff/OPEN.md` did not occur, there or in 40 runs of the allocation sweep that first showed it, and stays open. Mutation runs now also kill with 200 differential programs and with the unit tests.

`LUS_FAIL_NET` gives the network five faults, each counting its own steps: `N:reset` resets the connection at transfer N, `N:eof` ends the stream at receive N, `N:dns` fails lookup N, `N:refuse` refuses connection attempt N, and `N:abort` aborts the connection of accept N. The fault build prints the count of each kind and the TCP and UDP sockets still open at exit. `tests/faults/network.lus` runs `network.fetch` against `network.serve`, against a peer that trickles its response one byte at a time and ends the body by closing, and against a peer that speaks plain HTTP to an HTTPS request, whose handshake fails for real, which replaces an injected `N:tls`. It also runs a TCP exchange of lines. The sweep found four bugs in `fetch`. A body that ends with the connection hung for 30 seconds when other coroutines kept the scheduler busy, because the reader waited for an edge that had passed. A read error in such a body ended the body early without an error. A failed TLS handshake returned `nil` and a message instead of raising. A server that closed the connection inside the status line gave `"invalid HTTP response"`. Each now has a regression test or a scenario, and the errors of `fetch` name their step and their reason. A fifth showed under load in the eager mode of the conformance suite: `fetch` closed its socket without telling the scheduler, whose kqueue poller keeps a registration until it hears of a close, so a later socket that took the same descriptor never woke. Two fetches in a row hung on every run under CPU load before the fix and on none after it.

`LUS_CANCEL_AT=N` closes the detached coroutine that makes suspension N, a wait for a socket, a timer, another coroutine, or a notification. `tests/faults/cancel.lus` cancels each suspension of a program with a server, a TCP client, a coroutine that waits for the client, and one that waits for a worker, and every `<close>` variable closed once, in reverse order. The sweep showed that a detached coroutine that failed kept its pending `<close>` variables, and the sockets they held, until the collector freed it. Such a coroutine now closes them as it fails, after the runtime takes the traceback that the report of an uncollected error prints.

`LUS_CLOCK` scripts the real clock. `tests/faults/clock.lus` runs the clock across both changes of daylight saving in New York and jumps it back an hour and forward a day, and `time.now`, `os.time`, `os.date`, and the zoned values followed it while `time.monotonic` and a socket timeout kept to the monotonic clock. Children that a signal ends report the signal from `os.execute` and from closing a pipe, and writing to such a child returns `nil` and `"Broken pipe"`. A write, a flush, or a sync of a file handle that the system refuses returns `nil`, the message, and the number of the error, as in Lua, while `fs` and `fetch` keep raising. The runtime installs no signal handler outside compile-time evaluation, and the standard library retries an interrupted system call itself, so an interruption never reaches Lus code and the fault build injects none.

Reads follow writes: `file:read` and `io.read` return `nil`, the message, and the number of the error when the system refuses a read, and the lines iterators raise it, as Lua's do. With `ignorebad`, every decoder of `string.transcode` replaces an invalid input sequence with U+FFFD, one per maximal subpart of a broken UTF-8 sequence as the URL standard decodes, and base64, base32, and hex skip what is not in their alphabet. Padding ends base64 and base32 data, so a `=` with data after it raises where it used to end the decoding silently. The corrupted input harness checks the five binary to text encodings for these rules and for a round trip of every value they decode.

`LUS_FAIL_NET=N:tls` flips one bit in the middle of chunk N of the bytes that the TLS layer reads from its socket, which is a damaged record header in one chunk and a damaged ciphertext in the next. The network harness makes a certificate authority and a server certificate with openssl and adds two scenarios: `fetch` over HTTPS against `network.serve` with TLS, and `network.tls.connect` with two requests on one connection, so that the faults land after the handshake as well as in it. Every damaged record raised a message that the reference lists, such as `"TLS handshake failed: Verification of the message MAC failed"` in the handshake and `"receive: TLS: An invalid SSL record was received"` after it, and every run ended in time, closed its sockets, and answered a fresh request.

**Limits.** SQLite tests every limit at the limit and one past it, and `tests/limits/run.lus` does the same for Lus. Each of its 42 cases generates a program from a size N that checks its own result. The harness finds by bisection the largest N that runs, then checks that the program at that N runs in every mode of the JIT, that N + 1 fails in every mode with a message of the limit and a clean exit, that a program far past the limit fails the same way, and that the limit matches the number of the reference. The cases cover the locals, parameters, upvalues, and registers of a function, with the register edges of call arguments, return values, assignment targets, interpolated strings, chains of `..`, the fields of table constructors and local groups, and the clauses of queries. They also cover constants and nested functions, enum members, the nesting of every kind of syntax, the depth of recursion and of nested native calls and resumes, the chains of `__index`, `__newindex`, and `__call`, `table.unpack`, pattern captures, format widths, the nesting of JSON, deep copies, and worker messages, and the digits of bigints and decimals. `--emit` writes the programs at their limits, and the allocation sweep runs over them. Every limit failed with its message in every mode, and the sweep of the programs at their limits found nothing. The run documented the limits that the reference lacked: 65,535 constants and nested functions per function, the register edges, the depth of each kind of nesting, the extra slot of a local group, the stack of 1,000,000 slots, 200 nested native calls and resumes, the chains of 2,000 and of 15 tables, and 32 pattern captures. It also found two limits that went to the user as questions: the names of a `global` declaration take slots of the 200 locals of their function, and `bigint` parses a numeral of any length in quadratic time.

**Threads.** Workers, the parallel marker of the collector, the waker of the scheduler, and the callbacks of `fs.watch` run on threads of their own. `tools/tsan.sh` runs the conformance suite interpreted under ThreadSanitizer and `tests/tsan/stress.lus`, which keeps sixteen workers with detached coroutines exchanging messages while the creator collects, in a plain build and in one that collects at almost every allocation. The first run found a data race. Every new state entered the root of the shape registry again, a write that raced with the reads of the registry on other threads, so the root now enters once for the process. ThreadSanitizer also reported races between the callbacks of FSEvents and the stop of a watch, where the stop drains the queue of the callbacks before it frees their record, an order that ThreadSanitizer does not see through the frameworks of the system. The stop now also takes the lock that every callback holds to its end, which states the order in a form it sees. After both changes, the suite, the stress program, and the threaded files in the collector stress build reported nothing. A nightly job on macOS runs the script.

## Gates and findings

Every bug found gets a regression test in `tests/conformance` before its fix, except bugs of allocation failure, which the sweep itself keeps finding. A bug left open is recorded in `tests/diff/OPEN.md` with its smallest reproducer, so the next person to touch that code finds it.

The quick versions run in CI on every change: 200 differential programs, every fuzz target over its seeds as part of `zig build test`, the property tests as part of the conformance suite, and 8 sampled allocation failures per conformance file. The long versions, including the I/O sweeps, run in `.github/workflows/nightly.yml`. Parts 8 to 11 come next, in the order below.
